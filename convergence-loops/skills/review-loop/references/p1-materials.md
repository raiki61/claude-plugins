# review-loop の P1（採点の素材を集める段）

## P1: 採点用の素材集め（ラベルはまだ付けない）

ラベル付けは P2（grader）で行う。ここでは生の指摘を集めるだけ。grader subagent 群は互いに入力が独立なので、単一メッセージで並行起動しろ。

**素材の返答はラウンド記録（JSON）に書け。** 欄と取りうる値は `review-record.py` が正本で、手順書は列挙を持たない。要点は 2 つ——**「条件に当たらないのでやらなかった（not_applicable）」と「やるべきだったが飛ばした（not_run）」を別の値で書くこと**（散文ではこの 2 つが区別できず、後者が前者に化けるのが元の穴だった）、そして**前ラウンドの判定を流用した素材は `carried_over` と実際に見たラウンドを書くこと**（`clean` と分ける理由は `review-record.py` の当該定義に書いてある）。埋め忘れは検証エラーで落ちるので、各素材の節で「明示的に返せ」と繰り返さない。

**対象差分は「どこから見るか」の起点であって、「どこまで見るか」の線ではない。** 人がレビューするときは全体を見て考える——**差分以外を精読した目で見ると、指摘の場所そのものが変わる**（依頼者の逐語:「差分にしか触れないのはダメ。差分以外も全部精読してから見たコードでは指摘ポイントがかわるかもしれないでしょ」）。**リポジトリを読める役に、差分だけを貼って済ませるな**——入口を渡し、理解に要る限り依存先・近傍・呼び元まで読ませろ。道具を持たない遮断系（`cold-reader` / `blind-judge`）にだけは本文を貼るしかないが、**それは隔離のためであって、視野を狭めてよいという意味ではない**。

**探す役に「ここは見るな」の線を writer が引くな。** 削るのは P2 の仕事である——束ねる・出自を辿る・ラベルを落とす、という手続きは全部あちらに在る。集める側で範囲を切ると、切った外は**判定役の目に一度も入らない**。浅いセンサーは見た範囲で間違えるだけだが、視野を切られたセンサーはその外を一度も見ない。**「ここは見なくてよい」は採点の判断**で、実装を負う側がそれをやると「writer はラベルを決めない」が破れる。実測: 「対象は差分が import している依存に限れ」と書いていたため、**このプラグインが自分で依存として宣言していた役**（自作した機能とほぼ同じもの）が集合の外に落ち、3 ラウンド続けて「定番解の再発明は該当なし」が返ってきた。

代わりに 2 つを課せ。①**読む順の助言はしてよい**（差分が直接使うものから先に、等）——早く見つけるための順序であって、見るなの線ではない ②**見た範囲と、見ていない範囲を返させろ**。量や時間で打ち切ったなら、打ち切った線を書かせろ。そうしないと「見て無かった」と「見ていない」が同じ「該当なし」に化ける——**無言の省略を「なし」と誤認する**のは、このループが最初に塞いだ穴と同じ形である。返ってきた範囲は素材の `checked` / `detail` にそのまま写せ。

**検証手段を持つ役への提出基準**: 局所レビューの各 skill を呼ぶプロンプトと、リポジトリを読める grader（整合性＋迂回・外部標準照合・手順トレース）のプロンプトには、`REVIEW.md`「指摘の提出基準」を課せ——**REVIEW.md に書くだけでは局所レビューの skill には届かない**（それらは REVIEW.md を読まない自前の指示で動く）ので、writer が呼び出し時のプロンプトに本文を貼るか要点（機構・実測・提出前の自己反証・誤検出見積もり）を明記しろ。文脈遮断 grader は対象外（同基準の除外規定のとおり——センサーの浅さは仕事である）。

- **局所（writer が main session で実行）**: 欠陥は `pr-review-toolkit:review-pr`、品質は `/simplify`、認証・データ取扱い・外部 I/O に触れるなら `/security-review` も実行し、findings のみ取得しろ。**findings を機械的に集めるだけで、採点・ラベル確定はするな。** **`/simplify` は既定で修正まで行う skill なので、P1 では指摘だけ返す形で呼べ**——4 観点（再利用・単純化・効率・高度）を、修正を禁じたプロンプトでそれぞれ起こす。当てるのは P3 で、P2 が根本ユニットに束ねたあとである（P1 で当てると、採点前の木が動いて下の作業ツリー突合が成立しない）。実測: 2 つのセッションが独立にこの代用に行き着き、どちらも逸脱として記録していた——**手順書の側が現実に合っていなかった**。
 - **`pr-review-toolkit:silent-failure-hunter` と `pr-review-toolkit:type-design-analyzer` は名指しで起こせ。** （接頭辞を略すな——この手順書の裸名は `convergence-loops:<役割>` を指すと「道具と正本の場所」で定義してあり、この 2 つはそちらに存在しない。） `review-pr` の振り分けは散文の条件（「エラー処理が変わったなら」「型を足した / 変えたなら」）で、**try/except も型定義も触らない差分では起きない**。ところがこの 2 レンズが当たるクラス——黙って無力化される検査・恒真になった柵（前者）、不変条件を平坦な値で持つ設計（後者）——は、差分の形に関係なく出る。実測: このループ自身のレビューで 3 周続けて型設計のレンズが 1 度も起動されず、3 周目に外部の目が「平坦な文字列空間」として同じ欠陥を挙げた。**宣言済みの依存が既に手元に在るのに使っていない**形である。
 - `review-pr` は 6 観点（欠陥・コメント・テスト・エラー処理・型設計・簡素化）を持ち、findings を返すだけで PR へのコメント投稿もコードの修正もしない。簡素化観点も同じく指摘止まりで、修正まで行う `/simplify`（下の作業ツリー確認を参照）の代わりにはならない。
 - **findings を受け取れなかった素材は、記録に `awaiting_human` と書いて P2 へ進むな。**欠落したまま P2 が「局所 findings なし」と読むと、無いことが合格に化ける（`not_run` との区別は `review-record.py` が正本）。
 - **P1 の局所レビュー全体の前後で `git status --short` と `git stash list` と `git diff --shortstat <BASE>` を取り、作業ツリーが変わっていないことを確認しろ。** 変わっていたら戻せ（P0 で固定した BASE 起点の差分追跡が崩れる）。**確認の対象を道具名で列挙するな**——`/simplify` は既定で修正まで行う skill なので最も疑わしいが、実際には**指摘だけを返すはずの grader が検証のためにファイルを書き換えて戻し忘れた**ことがある（型ガードを削って緑になることを実証した跡）。どの道具が汚したかを当てるのでなく、P1 を抜ける時点の作業ツリーを機械で突き合わせろ。
 - 直前ラウンドから対象差分にロジック変更が無いラウンドは `/simplify` の再実行を持ち越してよい。

- **整合性 ＋ 標準機構の迂回（grader subagent・findings 非共有の独立フレーム）**: `inspector` を起動し、`REVIEW.md` の「整合性観点」に従ってリポジトリ横断の整合性を確認させろ——「標準機構の迂回」の中身・捕捉条件も正本のとおりで、ここに写しは持たない。迂回の検査は整合性確認とは**必ず独立に**実行させ、プロンプトに「お前は他の指摘を受け取っていない」と明記しろ。**この grader には P1 局所の findings を渡すな**——入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` だけにしろ。findings を共有すると全 grader がそのフレームにアンカーされ、近傍が迂回している機構に気づかなくなる（隔離フレームなら気づく——実証済みの捕捉条件）。この出力は整合性 findings とは**別系統の素材**として P2 へ渡せ。

- **文脈遮断（grader subagent・タスク文脈そのものを遮断）**: `cold-reader` を起動し、**「元の目的」も機能名もタスクの説明も一切渡さず、対象差分の本文と `REVIEW.md` の「コード衛生観点」のセクション本文（writer がプロンプトに貼って渡せ。観点の中身と遮断の理由は貼る本文＝正本のとおりで、ここに写しは持たない）だけ**を入力にしろ。上の整合性＋迂回 grader が「タスク文脈は共有しつつ findings を非共有」なのに対し、これは「diff が何の機能かを知らせない」点が新しい——整合性側がリポジトリ近傍から「このコードベースの標準機構」の逸脱を拾うのに対し、こちらは近傍を見ずに「言語 / フレームワーク一般の衛生」の逸脱を拾う（入力が違うため拾う層が違う）。プロンプトには **「お前はこの diff が何の機能かを知らされていない——『この用途なら妥当』という正当化はするな」** を課せ。`cold-reader` は道具を持たないので、渡された diff 本文と貼られた観点本文だけで判断する——近傍コードを読めると「このコードベースの標準機構」を学習して整合性 grader と同じ層に堕ち、隔離が崩れる。この出力も整合性・迂回素材と同様、**別系統の素材**として P2 へ渡せ。**貼り切れない差分は、この役に道具を渡して解決するな——貼る側を割れ**（ファイル単位・節単位で複数回起動し、出力を 1 つの素材にまとめる）。道具を渡して「この入口以外を開くな」と言い渡す形は、隔離が指示だけになる（**道具は path で縛れない**——この手順書が他所で書いているとおり）。割れば遮断は保ったまま通る。実測: 24 万字の差分を 3 分割して回した。**割ったことと、割り方は素材に書け**（読んだ範囲が変わる）。

- **外部標準照合（grader subagent・web で外部一次情報を当たる）**: `investigator` を起動し、`REVIEW.md` の「外部標準照合観点」に従わせろ——観点の中身（問題クラスの抽出・一次情報での裏取り・粒度・「定番解なし」も正当な結論・受容済み弱点の再照合）は正本のとおりで、ここに写しは持たない。入力は対象差分の本文と変更ファイル一覧と「元の目的」テキストと `REVIEW.md`、および PR 説明・README・残件メモ等で「自覚済み・受容済み」と明記された弱点のリスト（writer が抽出して渡せ。無ければ「なし」と明示しろ）で、**P1 局所の findings は渡すな**（findings に当たると問題クラスの抽出がそこへ寄り、近傍にしか目が行かなくなる）。この grader だけはリポジトリの外（web・公式ドキュメント・当該 OSS の issue / PR・ソース）を当たり、「エコシステムの定番解」からの逸脱を見る。**あわせて手元の依存も見ろ**——`REVIEW.md`「外部標準照合観点」の「手元の依存の使い残し」のとおり（内容は正本のとおりで、ここに写しは持たない）。**差分が import している依存から先に読ませろ**——差分から機械的に導ける集合なので着手が速い。**そこで打ち切らせるな**: このリポジトリが依存として宣言しているもの（言語のパッケージに限らず、プラグイン・ツールの宣言を含む）は、import されていなくても「既に手元に在るのに使っていない」の当たりどころである。読み切れなければ、どこまで見てどこを見ていないかを返させろ。依存の宣言ファイルに変更が無いラウンドは前ラウンドの判定を持ち越せ。この出力も整合性・衛生素材と同様、**別系統の素材**として P2 へ渡せ。**この grader は P4 が毎ラウンド P1 をやり直すため毎ラウンド走るが、web の引き直しは「アプローチ」をキーにせよ——初回ラウンドと、機構を足す / 変えたラウンドだけ引き直し、体裁だけのラウンド（テスト追加・リネーム・コメント）は前ラウンドの判定を持ち越せ。ただし確証に要る一次情報は必要な分すべて取れ（コスト削減を理由に取得を打ち切るな——削ってよいのは冗長・二次情報の重複 fetch だけ）。迷ったら引き直せ（頻度より精度を優先）。**

- **手順トレース（grader subagent・該当 PR のみ）**: 対象差分に実行手順の文書（README 等）・スクリプト・CI 定義が含まれる場合に起動しろ。`investigator` を起動し（この観点は読解でなく実行で確かめる——`REVIEW.md`「検証の原理」の「読むより動かす」——ので、コマンドを叩ける役）、入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` の「手順トレース観点」で、**P1 局所の findings は渡すな**。変更された手順書・スクリプトの全文を Read させた上で「手順トレース観点」（初期状態からの逐次実行・暗黙の環境状態・誤爆半径）に従わせろ——観点の中身は正本のとおりで、ここに写しは持たない。状態を変える実行はこの役が自らに禁じているので、実機で確かめられなかった箇所は「未実測」と明記して仮説として返させろ。この出力も別系統の素材として P2 へ渡せ。手順書・スクリプト・CI に変更が無いラウンドは前ラウンドの判定を持ち越してよい。

- **ゲートの実効性確認（writer が実行・該当 PR のみ）**: 対象差分が検証ゲート（CI ジョブ・assert・テスト・pre-commit）を新設・変更しているなら、そのゲートが検知すべき違反を、**条件の腕ごとに 1 つずつ**作って赤くなることを確認し、確認後に戻せ。**検査をまるごと外して赤いことは、腕が守られている証拠にならない**——実測: 人に聞く印を修正必須のユニットに付ける禁止（設計が最も強く禁じた形）は、検査全体を外せば赤くなるのに、`label` が修正必須である腕には 1 度も当たっていなかった（ローカルで再現できるステップは手元で実行しろ）。**壊していない写しでも 1 本走らせて緑を確認しろ**——仕掛け自体が壊れていると全部の腕が同じ色に出て、**逆の結論を書ける**（実測: 置換前の文字列が合わずに 1 腕が黙って飛び、別の実行者は全腕が「塞げていない」と出て危うくそう報告しかけた。古い測定結果がディスクに残っていて正常な入力が赤になった例もある）。これは**検査が空振りしても合格に見える形**で、この確認がまさに塞ごうとしているものと同じである。結果（赤を確認できた／できなかった／未確認とその理由。対照の緑も）を、P2 への素材に含めろ。**赤を一度も確認できていないゲートを「検証済み」と扱うな**——検査は、検査自体が失敗・空振りしたとき合格扱いにならないこと（fail-closed）まで含めて初めて機能する。赤の確認は当該ゲートを変更したラウンドだけやり直せばよい。**本物の作業ツリーを壊すな——腕ごとにリポジトリの写しを `mktemp -d` の下に作り、写しの上で壊して検査一式を走らせろ**（リポジトリの内側に作ると、この工程の前後で取る作業ツリー突合と記録ディレクトリが汚れる）（`.git` は要らない。検査が自分の位置から根を決める作りなら写しでそのまま走る）。「並行して読んでいる役が返るまで待て」という順序の約束で塞ぐな——**守ったかを確かめる手段が無く、上の「局所」が置いた作業ツリー突合は前後 2 点の比較なので、壊して戻すサイクルを原理的に検出できない**（端点は必ず一致する）。実測: 共有の木を壊して戻す形で回したとき、3 つの役がこれを「別セッションの書き換え」として観測し、1 つは構文の壊れた写しを踏んだ。写しなら順序への依存自体が消え、腕を並行して回せる（実測: 34 腕を 6 並列で 3 分）。

- **代役の忠実性（writer が実行）**: 対象差分が**外部との継ぎ目**（別プロセス・別サービス・ブラウザ・外部 API・プロトコル）に触れるなら、**テストの代役（モック・スタブ・フェイク）の形が実物と一致するか**を、実物から取った値1件で確認しろ。代役は本物の再現度でなく「実装の誤りが観測できるか」で線を引くが、**入力の形が実物と違う代役は誤りを観測できない**——代役にだけ通る形でテストが緑になる。不一致の箇所は素材として P2 へ渡せ。

- **主経路の実行観測（writer が実行）**: 対象差分が利用者から見える経路・外部との継ぎ目を変えているなら、その経路を **実際に1回動かし、通った値を観測しろ**。観測の対象は「テストが緑になること」ではなく **本番と同じ経路を流れた実物**である。**動かしていない経路を「検証済み」と扱うな**——P1 の他の観点は全て差分を読む役で、実行して初めて現れる欠陥（実行環境固有の挙動・中間層による値の加工・描画）はどれだけラウンドを重ねても現れない。観測は経路を変えたラウンドだけやり直せばよい。

- **根拠の出所検査（writer が実行）**: 対象差分の本文・PR 説明・docstring から「正本は X」「規約は X」「合意済み」等の**事実の主張**を抽出し、その X が対象差分の内側に無いかを確認しろ（`git log -S` 等で BASE 時点の実在を見る）。**差分が自ら足したものを根拠として引用しているなら循環**で、素材として P2 へ渡せ。外部（他チーム・他システム・取り込み元）との合意を主張する箇所は、BASE に痕跡が無ければ **「未確認の前提」**として扱え——循環した根拠は、次に読む人が「確認済み」と受け取るため、未確認のまま設計判断の土台になる。
