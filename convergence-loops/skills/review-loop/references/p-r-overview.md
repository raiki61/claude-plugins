# review-loop の P-R（収束の前の俯瞰 R1〜R4）

## P-R: 俯瞰（収束ゲート・完了宣言の前に必ず）

`[block]` が 0・CI 緑でも、それは収束の**必要条件にすぎない**。R1〜R4 を実行し全て通るまで収束を宣言するな。**R1・R2 は P4 で前倒し実行しているので、最後の実行以降に再発火条件（P4）へ当たっていなければその結果を使ってよい**——当たっているなら回し直せ。R3・R4 はここで必ず実行しろ。対象はループ開始時点からの**累積差分**（対象差分＝ `git diff <BASE>`）。**`judge` / `inspector` は shell を持たないので、累積差分は writer が `git diff <BASE> > <file>` でファイルに落とし、その path と変更ファイル一覧を渡せ**（貼るな——Read を持つ役は自分で読む。`git diff` の出力を自分の文脈に出さない。P1 の grader と同じ）。R1・R3・R4 の subagent は `verdict: pass | redesign-needed | unverifiable` のいずれかと理由を返せ（R2 の verdict は後述の比較 grader が確定する。ただし `premise-invalid` だけは R2 subagent が直接返す）。**返った verdict と理由は、そのままラウンド記録の `reviews` に写せ**（P4 の突合が読む。writer が verdict を要約し直したり丸めたりするな）。1つでも `redesign-needed` なら非収束——P1 から新ラウンドに戻れ（`premise-invalid` は `redesign-needed` と違って再設計ラウンドには送らない——停止条件「前提不成立」の項が扱う。そこで別 context の judge が根拠を検算し、仮定を偽と示せたら次の周で R2 を回し直す）。

- **R1 冗長と最小性** — `judge`（設計判断なので上位の役）。**前段としてコメントの削除候補を取れ**（writer が段取る）: `pr-review-toolkit:comment-analyzer` を、累積差分が触れたファイルを対象に起動しろ。この役は「コードをなぞっただけのコメントは削除候補に挙げろ」「削除を勧めるなら理由を明示しろ」を定義に持っている。**writer は呼び出し時のプロンプトに次の 3 つを足せ**——定義に無く、足さないと迷ったときに残す側へ倒れる: ①削除候補ごとに**同じ内容がどこにあるかを名指しさせる**（コード・他のコメント・文書・テスト名。名指しできないなら削らない）——名指しは後から確かめられるので、提案が意見のまま残らない ②**残すと判断したコメントにも、それが運んでいる事実を一文で言わせる**——削る側にだけ義務があると、黙って残す方が安くなる ③残してよい線は `REVIEW.md`「導線を作る手段の優先順位」のとおり（内容は正本のとおりで、ここに写しは持たない）。あわせて**コメントアウトされたコード・編集の実況（「〜を追加した」）・名前のすぐ隣で名前を言い直しているもの**を、具体的な引き金として明示的に探させろ。以前ここには、コメントを剥がした写しを文脈を知らない読み手に精読させる自作の仕掛けが在ったが、3 ラウンド回して削除の実績が 0 件で、写しにリポジトリ全体が入るため隔離も 2 ラウンド続けて破れた（同じ期間に注釈の割合は 22% → 29% に増えた）。落として、既に依存に入っている役に寄せてある。
  **前段の一覧が取れなかったからといって、`reviews.R1` の verdict まで `not_run` に倒すな**——R1 の残りの仕事（最小性・場当たり累積・処方の正当化・問いの台帳の監査）は前段なしでも判定できるので、そちらで verdict を決め、理由に「コメントの削除候補は未取得（理由）」を明記しろ。実測: 前段が取れないと verdict ごと倒す形にしていたとき、`not_run` は阻害要因なので**このリポジトリ自身のレビューは原理的に収束できなかった**（安全側に倒したつもりが、収束不能という別の壊れ方になっていた）。
  R1 の judge にはこの一覧と目的テキストと累積差分を渡し、次を判定させろ: **削除候補のうち、名指しされた「同じ内容の在り処」が実在するもの** → 削る（do-now）／**残すと判断されたのに運んでいる事実を言えなかったもの** → 削る候補として扱う／説明が目的とずれた箇所 → 注記でなく構造か名前で直す（do-now）。**あわせて問いの台帳の監査**——`split` の origin が凍結した目的の内側なら、また `fork` の選択肢に零処方（取り下げ・既存の機構 1 つ）が列挙も棄却もされずに人へ回されているなら `redesign-needed`（逃げ道の検知）。そのうえで累積差分が最小か。(a) 小修正が積み重なって本来1根本で済むものを症状パッチしていないか（場当たり累積）。(b) 単一の修正でも、他所から導ける内容を重複して述べていないか・より少ない記述（コード/文章）で同じ目的を運べる箇所がないか。**ただし simplify は制約付き**: 削ってよいのは削っても変更の *検証済みの値打ち*（コードなら挙動・テスト、設計/論拠文書なら *導出の再現性*）が落ちない分だけ。保護するかは**内容で判定しろ——「他所に無い情報（事実・導出根拠・why）を運ぶか」だけをキーにし、書き手の意図を判定に使うな**（意図は新 context から見えず、ループ自身が足した注記ほど「意図的」に見える）。他所に無い情報を運ぶ残余・caveat・why は消すな。**同一情報の反復は「あえての冗長」として自動保護しない**——複数箇所への配置自体が読み手の動線上必要と一文で言える場合（例: 破壊的コマンドの直前ごとの確認ガード）だけ保護し、そうでない単純反復・散在は、事実を消さない**集約・再配置（1節に抽出して各所から参照する形を含む）を simplify の義務**として指摘しろ。順序は固定で『必要な内容が在るか（＝**冷たい読み手**——文脈を持たない初見の第三者——が、書かれた指示・論拠だけから結論や手順を再現できるか。再現に要る前提・制約が省かれていないか）』→『在るとして最小か』。局所の simplification は `/simplify` が担当——ここで見るのは累積差分全体・文章の密度・抽象の重複である。**`do-now` で本ループ内に直した修正も累積差分の一部として必ず対象に含めろ——do-now を口実に症状パッチが積まれていないか、disposition（do-now/defer の判断）自体が場当たりでないかも見る。採られた処方が `REVIEW.md`「処方の最小性」に照らして正当化されているか（大きい処方に、小さい方が落ちる理由が付いているか。列挙を経ずに機構が足されていないか）もここで監査しろ。R1 は P-R の必須ゲートで、この場当たり検証を素通りするな。** **writer から scalar 推移（P4「writer（scalar 記録）」）が渡されたラウンドでは、相殺削除なき単調増の増分ごとに「他所に無い情報か」の正当化を要求しろ——正当化できない増分は集約・再配置の対象。**
- **R2 ゼロベース再導出** — `blind-judge`（元の目的から理想解を独立設計するため深い推論が要る）、**完全隔離**: この役は道具を持たないので git・実装ファイル・コミット履歴に触れられない。渡すのは『元の目的』テキストだけにし、そこから理想解を独立設計させろ。**ただし独立設計に入る前に、まず目的そのものの実在を疑え**: 「この変更が解く問いは実在するか。既存機構で自明に満たされていないか（例: 1デプロイ＝1リポジトリならリポジトリ自体が識別子で、別途記録する問いは生じない）。要件が未確定のまま実装に踏み込んでいないか」。問いが実在しない・既存機構で自明・要件未確定と判断したら、理想解の設計に進まず `premise-invalid`（解くべき問いが立っていない）を返せ——`redesign-needed` と混同するな（routing が違う: `redesign-needed`＝新ラウンドで再設計、`premise-invalid`＝別 context の judge が根拠を検算してから人へ。停止条件「前提不成立」）。問いが実在するなら通常どおり理想解を独立設計しろ。**理想解には、目的の当事者が日常で回す動線（反復開発・運用・撤収）まで含めろ——成果物の一回の起動で設計を閉じるな**（当事者が毎日触るものの目的には、暗黙に「日常の回し方」が含まれる）。**subagent は独立設計（または「問いが立っていない」判定）だけを返す。突合と verdict 確定を writer がやるな**——独立設計と累積差分の本文を別の比較役（`blind-judge`・新しい context）に貼って渡し、本質的な食い違いの有無で verdict を確定させろ（writer≠grader を収束判定でも守る）。P0 で「元の目的」が `unverifiable` なら R2 も `unverifiable`。
- **R3 全体整合** — `inspector`: 変更全体でファイル横断の整合（命名・規約・界面・docs 追従）。**R3 が見るのは diff が触れた範囲の整合**（変更したものが既存と揃っているか）。**既定・推奨の文書間一致**（変更が触れる文書群が読者に示す推奨ツール・手順・構成が単一に収束しているか——一次検出は P1 整合性観点、ここは最終ゲートの再確認）も含む。diff が触れていない横断リスクは R4 が見る。
- **R4 見えてないスコープ** — `inspector`、**SRE・セキュリティ・データガバナンスの複数レンズ**で、diff の中でなく **diff が解こうとしている領域に潜む、変更が手を付けていない横断リスク**を探せ（観点は `REVIEW.md`「横断リスク観点」——レート制限・濫用耐性、PII の外部送信、可用性の外部結合、誤爆半径、移行退行の棚卸し（BASE 能力インベントリ）。列挙は代表例で限定ではない）。R1〜R3 が diff 内中心なのを補う。この grader には `REVIEW.md`「横断リスク観点」を **Read させて**従わせろ——移行退行の棚卸し（BASE 能力インベントリ）の中身・発火条件・BASE 比較の基準・明示返答の要求は正本のとおりで、ここに写しは持たない。棚卸しが発火する diff（移行・手順・開発フロー・UX）で「消えた能力」の有無の明示返答を欠いた出力は受け取るな（無言の省略を禁ずる）。**該当リスクは「この変更で導入・露呈したか」で扱いを分けろ**——この変更が導入・露呈させたものは本ループで回収（`redesign-needed`）、純粋に既存かつ無関係なものは最終報告に `[suggest]` 以下で surface するに留め `pass` を妨げない（`REVIEW.md`「別 Issue への先送りを既定にするな」の因果判定に従う）。
