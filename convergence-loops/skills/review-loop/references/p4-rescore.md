# review-loop の P4（再採点と収束の判定の段）

## P4: 再採点と収束判定（writer が段取り、判定は grader）

やり直しの段取りは writer が担い、採点・突合の判断は全て grader に置く:

1. **writer**: CI を再実行（緑維持。赤なら P3 に戻って先に直せ）。
2. **writer**: P1 を新しい context でやり直せ——局所レビューの再実行と、各 grader subagent の新規起動。**前ラウンドの grader 出力・修正の経緯を P1 / P2 の subagent に渡すな**（渡すと前ラウンドのフレームにアンカーされ、再採点が追認になる）。続けて P2 grader を新しい context で再起動し、根本ユニットを再採点させろ。
3. **突合（機械）**: 下の形のまま打て——Python の名前を `python3` や `python` に替えるな。`run-python.sh` は `python3`・`python`・`py -3` の順に、実際に起きて 3.12 以上の物を選ぶ（Windows の `python3` が Microsoft Store へ誘う代わりの物や、Python 2 の `python` を飛ばす）。Python 2 で回すとこのツールは構文エラーの**終了コード 1**（＝「阻害要因あり」）で落ち、**壊れているのか未収束なのかが区別できない**——この機械が終了コードで 3 値を分けている、その要が破れる。選べなければ `run-python.sh` が訳を出して**終了コード 127** で終わる（Python を入れてから打ち直せ。非収束の判定ではない）。

   ```bash
   bash "${CLAUDE_PLUGIN_ROOT}/scripts/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/scripts/review-record.py" .claude/review-rounds/
   ```

   ディレクトリを渡すと `round-<N>.json` を全部読み、最新を今ラウンドとして突合し、**履歴**（全ラウンドの推移）を出す。履歴は次ラウンドの P2「履歴との突合」に渡す入力で、最終報告の冒頭にも使う。連番に穴があれば落ちる（前ラウンド分を消すな）。**終了コード 2 は「記録が不正」で、1（阻害要因あり）と取り違えるな**——2 は記録を直して再実行する合図であって、非収束の判定ではない。機械が拾うもの: `[block]`（新規か残存か。残存には印が付く——ただし**この印は手順書の stuck（2 ラウンド連続）より広く発火する**ので、印だけで stuck と診断するな）・未対応の `do-now`・素材と R1〜R4 の未実施・**連続 2 ラウンド**（前ラウンドに阻害があれば、今ラウンドが阻害なしでも「1 ラウンド目」として阻害要因に数える。**writer が数えるな**）・持ち越しの連鎖（実際に見たラウンドが途中で書き換わっていないか）・defer 台帳（前ラウンドで `defer` と確定したキーが `reopen_evidence` 無しに `[block]` / `do-now` へ戻れば記録の不正）・**問いの台帳**（前ラウンドの `held` / `escalate` が今ラウンドに無ければ記録の不正。同じ `[block]` が 3 ラウンドの記録に続けて在るのに、**未決の** `stuck` か `fork` として台帳に無ければ記録の不正）・**阻害要因の帰属**（各阻害要因が保留中の問いの origin か `depends` に帰属するかを分け、**帰属する阻害要因が在って、帰属しない阻害要因が 0 なら「答え無しに進める仕事は無い。ここで止めて聞け」と出す**。writer が数えるな。前提不成立が `escalate` で確定したときは件数に依らず先に出る——止まる経路の全体は「停止条件」が正本）・scalar の増加。記録を消すなの理由は「ツールと正本の場所」に書いてある。ここで足すのは 1 つだけ——新しい context の再採点は前ラウンドの受容判断を知らないので、台帳を P2 の judge に渡さないと同じ提案が毎ラウンド再燃して収束しない（渡し方は P2「履歴との突合」）。
4. **writer（問いの台帳）**: P2 の judge が返した問いを、記録の `questions` に**そのまま写せ**（フィールドと値は `review-record.py` が正本）。**writer が要約し直したり丸めたりするな**——`reviews` の verdict と同じ規律である。judge は書くツールを持たないので、台帳を記録に置くのは writer の仕事だが、中身を決めるのは judge だ。人に聞く候補が無いラウンドは空の配列を書け。
5. **writer（scalar 記録）**: 規模指標を記録の `scalars` に書け。文書・手順書を含むなら変更した文書の追加行（`git diff --numstat <BASE> -- '*.md'` の追加行の合計。コードの追加行と同じ物差しで、ファイル全体の行数ではない）を `doc_lines` に、コードを含むなら `bash ${CLAUDE_PLUGIN_ROOT}/scripts/comment-ratio.sh <BASE>` の出力（手で数え直すな——物差しが揺れるとラウンド間の比較が成立しない）。**scalar はゲートにしない**——増加は R1 への入力であって、閾値で止めるものではない（測れるものをゲートにすると、規則が測れるものへ寄る）。

採点を writer の自己申告にするな（採点は P2 grader、突合は上の機械）。

**1ラウンド = P1 → P4 を1周**（P-R から差し戻されて P1 に戻った場合も1ラウンド）。判定後の分岐:

- 新規/残存 `[block]` > 0、**または P2 grader が `do-now` とした `[suggest]` が未対応のまま（新たな構造的 defer 理由の提示なし）** → P3 に戻り当該根本ユニットを直し、再度 P4。
- `[block]` = 0 かつ CI 緑 → P-R へ進め。

**ただし R1（最小性）と R2（ゼロベース再導出）は `[block]` = 0 を待つな。** この 2 つは**第 1 ラウンドで必ず走らせ**、以降は下記の再発火条件で回せ。P-R の位置に置いたままだと、欠陥の多い差分では永久に到達しない——**欠陥が多いほど枠自体の検査が遠ざかる**という逆向きの構造になる（実例: 5 ラウンド連続で新規 `[block]` が出続け、R1 が初めて走ったのは 6 ラウンド目。走った瞬間に「機構の規模が実態に対して大きい」と差し戻し、-1,193 行の削減になった）。

**R1 / R2 の再発火条件**（どれかに当たったら P-R を待たずに回す）:
- 差分が**機構を足した／置き換えた**（コメント・テストだけのラウンドは持ち越してよい）
- 差分が、P0-3 の制約が測られた対象を**削除・置換した**（＝**前提のドリフト**。制約を測った経路を差分自身が削れば前提は壊れるのに、それを検知する仕組みは他に無い）
- 累積差分の行数が前回 R1 実行時から **1.5 倍**を超えた
- 累積差分の行数が前のラウンドの **2/3 以下**に減った（処方の向きが「足す」から「消す・畳む」に変わった周は、設計が組み替わっているのに行数が減るので、上の項だけでは前の判定を流用してしまう。減る向きは直前のラウンドと比べる——1 周目と比べると、足してから畳んだ周が 1 周目より多いまま残り、転換が見えない）
- **台帳の未決の問いが前ラウンドから変わった**（R1 だけ。R2 は台帳を監査しないので持ち越してよい）——「行が増えたか」でなく「**監査対象が変わったか**」で見る。問いの `key` だけを見ていたとき、同じ `key` のまま種類・出どころ・選択肢を総取り替えする周と、`resolved` を `held` に戻す周が、どちらも監査を素通りした（実測）。票の持ち越しを決める定番（Gerrit の `copyCondition` は変更の種類を、GitHub の保護ブランチは差分を変える push を見る）と同じ述語である——**台帳を監査する経路は R1 しか無い**のに、上の条件はどれも差分の中身についての条件である。`fork` / `split` は処方が機構に及ぶ種類なので**その周の差分に機構の追加が無いのが普通の姿**で、問いが立った周ほど R1 が持ち越しになり、監査が一度も走らない構成が正規の記録として成立していた（同梱の雛形 3 周がまさにその形で、機械も通した）。**この条件だけは機械が縛る**——問いが新しく載った周に `reviews.R1` が `carried_over` なら記録の不正で落ちる。

**R1〜R4 の verdict はラウンド記録の `reviews` に書け**（値は `review-record.py` が正本）。R1 / R2 を再発火条件に当たらず持ち越すラウンドは `carried_over` と実際に走らせたラウンド、R3 / R4 に到達しなかったラウンド（`[block]` が残った等）は `not_applicable` と到達しなかった理由。**散文の最終報告だけに書くな**——記録に無い verdict は、走らせたかどうかを誰も確かめられない。
