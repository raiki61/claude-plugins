# doctor-loop の正直な限界と由来

## この型が保証しないもの（正直な限界）

- **特定の発見を期日に保証できない**——走査は確率的な探索で、手筋は当たり率を上げ、検証が外れを濾すが、「この根本が今日見つかる」は約束できない。
- **暗黙知は人が入れない限り現れない**——「あそこが怪しい」という依頼者の勘は、正典にも git 履歴にも載っていない。範囲指定でループに注入するのは依頼者の仕事である。
- **読むだけでは安全を立証できない**——提案に添えられるのは検証計画までで、安全の立証は採用後の実装とテストが行う。
- **実装待ち行列は動かせない**——候補の多くが「既知で設計済み・未実装」だと判明することがある。その場合の成果物は新候補ではなく「待ち行列が動かない理由」のセクションであり、それを動かすのは人の采配である。

## 付録: 由来の対応表（この型は枯れている）

| このループの部品 | 確立した先行手法 |
|---|---|
| 改善して標準化まで一周 | kaizen（大野耐一「標準のないところに改善はない」）・SDCA |
| レンズの品揃え | ソフトウェア保守の標準分類（ISO/IEC/IEEE 14764: 是正・適応・完全化・予防・追加） |
| 減らす→直す→縛る→定着 | 5S（整理・整頓・清掃・清潔・躾） |
| 変更頻度×複雑度で深読み先を選ぶ | ホットスポット分析（Tornhill『Your Code as a Crime Scene』） |
| 根本の木・上方向の展開 | FTA（故障の木）・なぜなぜ分析・イシューツリー（MECE 分解） |
| 反証で刈り、生き残りに予算を厚く | ゲーム木探索の刈り込みと予算配分 |
| 敵対検証・反証を試みる | ACH（競合仮説分析）・悪魔の代弁人 |
| 増し掛け（独立 3 票） | 合議制の審級・冗長化による誤り検出 |
| 消す前に用途を疑う | チェスタトンのフェンス |
| 死んだ試みの探索 | 生存者バイアス点検（Wald の爆撃機） |
| 目的だけからの独立再導出 | ゼロベース設計 |
| 模範との構造比較 | 構造写像・ベンチマーキング（適用条件の確認込み） |
| 走査は機械に・判断は人に | 職務分離（作業者に自分の検査水準を決めさせない） |
| 新規ゼロが続いたら飽和・抜き取りで検算 | 理論的飽和（Glaser & Strauss）・受入抜き取り検査 |
| 報告の初見検査 | 校閲・初見読者テスト |
| 消化の三分類・情報の価値順 | トリアージ・決定分析の VoI（情報の価値） |
