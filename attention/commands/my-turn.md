---
description: 持ち主（このプラグインを使う人）のターンの PR を進める。/catchup でその PR に戻った後に打つ。PR が作る仕組みが補っている前提を消せないかから始めて、指摘やレビューの観点を木のように掘り、世の中の解と突き合わせ、既存の OSS で足りるのに自作していないかをゼロベースで疑う。持ち主がレビュアーなら、最後に出す指摘をインラインコメントの下書きにして見せて止まる（投稿はしない）。works-dispatch プラグインが、/catchup に続けて会話の 2 ターン目に送る。
---

持ち主は、このプラグインを使う人（この会話の相手）である。「自分の番」は持ち主が次に動くターンを指す。

対象は、この会話で `/catchup` した PR である。会話にその返答が無ければ、先に `/catchup <PR 番号>` を打てと返して止まれ。

立場は、`/catchup` がページに書いた `headline`（いまのターンの太字。この会話で書いたフィールドの JSON に在る）が言ったもの（持ち主がその PR の作者か、レビュアーか）を使う。

全体を通して、次を守る。

- 確かめていない領域を残さない。
- 「作者が決める」は結論の選択（どの案を採るか・別の issue にするか）にだけ掛かる。調べること（前提・世の中の解・自作になった訳・相乗り）は作者に委ねず、ここで調べる。
- 「消える」「要らなくなる」「穴が塞がる」と書く前に、実物（コード・SQL・起動スクリプト・ツールの原典）で木の末端まで確かめる。確かめていなければ、その文に「未確認」と書き添える。

0. 掘る前に、前提を取り直す（修正の工場 works-factory の判定役が、判断の前に集める材料と同じ考え方）。
   - PR の今の状態を `gh pr view <番号> --json state,mergedAt,headRefOid,statusCheckRollup` で取り直す。merge 済み・閉じている・head が手元と違うなら、先にそれを持ち主に言って止まる。
   - この PR の会話とレビュー（`gh pr view <番号> --json comments,reviews`）と行のコメント（`gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`）を全部読み、自分が前に出した指摘・決着した指摘・許した指摘を一覧にする。同じ指摘を重ねて出さず、前の自分の言ったことと食い違うことを書かない。
   - 本文・コメント・触っているコードが名指す PR・issue・設計の判断の記録（ADR）を読み、後から設計を変えた PR や閉じた issue で前提が古くなっていないかを確かめる。読めなかったものは「無い」と書かずに「未確認」と書く。
1. この PR が作る仕組みを 1 文で言い、それが要る理由（その仕組みが補っている前提）を 1 文で言う。例: 「戻し先の版を新しい DB の上で動かして確かめる関門を作る。要るのは、自前の DB の初期化が、どこまで流したかの記録を持たないから」。
2. 木を探索するように深掘りする。起点の 1 本は必ず「1 で言った前提（仕組みが補っている前提）を消す形はあるか（消せば、この仕組みのどこが要らなくなるか）」にする。ほかの起点は指摘やレビューの観点で、作者の側なら受けた指摘を 1 件ずつ起点にする。作者が頼んだ観点と文書の枠（PR の本文や設計文書が立てた段・項目）だけを起点にしない。掘って出てきた問いを子の問いに分け、子の問いごとに末端まで掘る。最後に相乗りを、次の 2 つの範囲で見る。
   - 掘った問いどうし（一つの直しで複数が片づく・一つの直しが別の問いの答えを壊す）。
   - この PR の外。同じ環境・仕組み・ツールを作る予定の open な issue と PR を `gh issue list --state open --search <語>` と `gh pr list --state open --search <語>` で探す（語は 1 の仕組みと、それが要る環境の名前）。向こうの環境に相乗りできるか・向こうがこちらの部品を使えるかを見て、探した語を返答に書く。

   どの直しをどう組めばよいかを考え、その相乗りが本当に成り立つかを確かめる。
3. 世の中が同じ問題をどう解いているかを当たる。当てる順は次のとおり。
   1. まず PR が作る部品の全体（1 の仕組みが解こうとしている問題。例: 本番の切り戻しをどう安全にするか・DB の移行をどのツールでするか）に、世の中の解（OSS・定番のツール・定番の手順）を当てる。
   2. 次に、見つけた指摘 1 件ずつと、こちらが出す直し方の案に当てる。

   当てた先ごとに「世の中の解」と「こちらの案と同じか・違うならどちらを採るか」を返答に書く。見つからなければ、探した場所を書いて「見つからない」と書く。それでもわからなければ、持ち主に聞く。
4. 汚い自作の領域（既存の OSS や世の中の定番で足りるのに、手で作っている部分）に踏み込んでいないかを疑う。OSS があるかもしれないし、世界がやっていない自作には何かしらの理由があるはずである。今まで進んできた前提は気にせず、ゼロベースで疑う。自作を見つけたら、次の 3 つをする。
   - なぜ自作になったかを履歴（`git log`・その行を入れた PR・issue）で掘る。
   - 今の書き方のままツールを当てるのでなく、ツールに寄せて（こちらの書き方を変えて）どの自前の処理・規則・検査が消えるかを、ファイルや関数の単位で数える。
   - 寄せても消えない物は、なぜ消えないかをツールの原典（公式の文書・ソース）で確かめる。
5. 持ち主がレビュアーなら、最後に、出す指摘をインラインコメントで出す想定の下書きにして見せ、そこで止まる。見せる前に、次を自分で確かめる。
   - 1 で言った前提を消す案を 1 つ以上検討したか。
   - 作者が頼んだ観点と文書の枠の外の指摘が 0 件なら、なぜ 0 件かを返答に 1 文で書いたか。
   - 「消える」「要らなくなる」「穴が塞がる」を、末端まで確かめずに書いていないか。

   GitHub へは投稿しない。別の issue にするかは作者が決めることなので、こちらからは提案しない（2 で見つけた、既に在る open な issue・PR に相乗りできることは、指摘に事実として書く）。作者の側なら、この項目は飛ばす。
