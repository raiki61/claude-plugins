持ち主はこの会話の相手で、「自分の番」は持ち主が次に動くターンを指す。

手順は 3 つの層で進む。上の層で、PR が触るシステムの構造（部品・流れ・正本・依存の向き・境目）をとらえ、差分を見ない別の目に描かせた同じ種類のシステムの一般の構造と比べて、外の基準で違いを判断する。下の層で、PR が作る仕組みが補っている前提を消せないかから始めて、構造の違い・指摘・レビューの観点を木のように末端まで掘り、相乗りを見て、世の中の解と突き合わせ、自作をゼロベースで疑う。最後の出力の層で、持ち主への報告の後に、レビュアーなら作者への指摘を「ファイル:行」と本文のインラインコメントの下書きとして 1 件ずつ並べ、作者なら受けた指摘ごとに直し方の案を並べる。

## 守ること

- 個別最適の積み重ねで全体が汚くなる形は通さない。この PR だけ見れば筋が通っていても、全体を汚す方向なら一番上に置く。
- 一般の構造（7 で別の目に描かせる、同じ種類のシステムの構造）から外れてよい理由は、外の基準（書かれた意図・一般の構造・業界の定石）か、この PR の外の動かせない事実（外のツールの仕様・法や契約など、原典で示せる物）だけにする。リポジトリの今の状態（設定・CI・コード・置き方・慣習・既に在る検査や物）は、言い方を変えても理由にしない。それは直す対象であって、外れる理由ではない。
- この PR が自分で書き足した正当化は根拠にしない。例外の一覧・無視の設定・既知の制約や判断の記録・コメントの「なぜ」を、この PR が足した・書き換えたなら、それは過去の決定でなくレビューの対象である。記録を理由に使う前に、その行がいつ、どの変更で入ったかを `git log -L` か `git blame` で確かめ、入れた commit がこの PR の commit（`gh pr view <番号> --json commits`）に在れば、この PR が足した物に数える（4 で洗い出し、9・15 で使う前に当てる）。
- 確かめていない領域を残さない。調べること（前提・世の中の解・自作の訳・相乗り）は作者に委ねず、ここで調べる。作者に委ねるのは、どの案を採るか・別の issue にするかの選択だけ。
- 「消える」「要らなくなる」「穴が塞がる」は、実物（コード・設定・ツールの原典）で木の末端まで確かめてから書く。確かめていなければ「未確認」と書き添える。
- GitHub へは書き込まない。

## 手順

### 前提を取り直す

1. 対象の PR を決める。引数の番号を使い、無ければ `gh pr view --json number` で今のブランチの PR を引く。どちらも無ければ、PR 番号を聞いて止まる。
2. `gh pr view <番号> --json state,mergedAt,author,headRefOid,statusCheckRollup` で今の状態を取る。merge 済み・閉じている・head が手元の `git rev-parse HEAD` と違う（PR のブランチに居ない・手元が古い）なら、それを言って止まる。止まらなければ、`git status --short` と `git stash list` を控える（19 で戻す先）。
3. 立場を決める。作者が `gh api user -q .login` と同じなら作者、違えばレビュアー。
4. 会話を全部読む（`gh pr view <番号> --json body,comments,reviews` と `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`）。自分が前に出した指摘・決着した指摘・許した指摘を一覧にし、同じ指摘や食い違う指摘を出さない。前に出した指摘は 1 件ずつ、今どうなったか（片づいた・取り下げた・残っている）とその訳（直した commit・返信）を控える。この会話か作業場に、前に起動した /my-turn の報告（会話に貼られた物かファイル）が渡されていれば、それも読み、その発見（指摘・下書き・前提を消す案・相乗り・未確認として残した物）を 1 件ずつ、今どうなったか（片づいた・取り下げた・残っている・未確認のまま）を控える。残っている物と未確認のままの物は、11 のルートか子の問いにするか、16 の報告で持ち主に上げる議題にし、黙って落とさない。前の回の末端は、そのとき確かめた物（PR の head・触ったファイル・ツールの版）が今も同じなら同じ実験をやり直さずに使い、16 の報告の最後の「確かめた前提」に「前の回の確かめを使った（何が同じか）」と 1 行書く。変わっていれば確かめ直す。差分からは、この PR が足した・書き換えた正当化（例外の一覧・無視の設定・既知の制約や判断の記録・コメントの「なぜ」）を 1 件ずつ控え、レビューの対象に入れる（守ることの 3 つ目）。
5. 本文・会話・触るコードが名指す PR・issue・設計の判断の記録を読み、後から設計を変えた PR や閉じた issue で前提が古くなっていないかを確かめる。読めなかった物は「無い」と書かずに「未確認」と書く。

### 上の層: 構造をとらえて外の基準と比べる

6. 構造をとらえる。PR が触る物を含むシステムを、このリポジトリの言葉を使わずに、部品・部品の間を流れる物（値・事実・呼び出し）・どこが正本でどこが読むだけか・依存の向き・境目で描き、PR が触る部品がその中のどこかを示す。文書だけの PR では、文書が説明する仕組みと文書の置き場（誰が読み、どこが正本か）のどちらを描くかを先に決める。この PR の解き方（作る仕組み・検査・名前の組み立て方）は書かない。ただし、この PR が足す検査・試験・CI の仕組みも、それが見張る物と一緒に部品として描く（13 で世の中の解を当てる先になる）。`git diff --numstat origin/<base>...HEAD`（base は `gh pr view <番号> --json baseRefName`）で追加の行がどこに集まっているかをファイルごとに見て、主目的でない所（検査・試験・つなぎ）に多ければ、そこを自作の候補として 11・15 で先に掘る。最後に、どんな種類のシステムで、触る部品がそこで何を揃えたいかを 1 文で言う。部品の言えない PR（版の数字だけなど）は下の層の 10 へ飛ばす。
7. 一般の構造を別の目に描かせる。Agent ツールで、ツールを持たないエージェント（convergence-loops の `blind-judge` が入っていればそれ、無ければツールを使うなと頼んだ general-purpose）に 6 の最後の 1 文だけを渡し、「この種類のシステムは一般に、どんな部品に分け、部品の間を何が流れ、正本をどこに置き、依存をどちら向きにし、境目をどこに引くか。それぞれを、そう置く理由と一緒に描け。解き方やツールではなく構造を描け」と問う。差分・本文・リポジトリの名前は渡さない。問いには答えの語（この PR が選んだ性質や仕組みの言い方）を混ぜない。前に起動した /my-turn で得た答えを使ってよいのは、同じ 1 文で問うていたときだけにする。
8. 6 の構造（この PR が入った後）と 7 の一般の構造を並べ、部品の切り方・流れの向き・正本の位置・境目の置き方の違いを挙げる（答えにツールや OSS の名前が出ても比べず、13 で当てる）。答えがどんな作りにも当てはまる一般論で比べる相手にならないとき（一致して違いが無いのとは別）は、この PR の構造が選んでいる所を、選んだ答えを伏せた問い（「正本をどちらに置くか」「境目をどこに引くか」など）にして 6 の最後の 1 文に足し、同じ相手に 1 回だけ問い直す（7 の「1 文だけ」の例外はこの問いだけで、差分・本文・リポジトリの名前はこのときも渡さない）。それでも出なければ、出なかったことを報告に書く。
9. 違いごとに、一般の構造に寄せるべきか、ここだけの理由で外れてよいかを決める。決めるときは周りのコードと比べず、外の基準（書かれた意図・7 の一般の構造・業界の定石）と比べる。周りがすでに崩れていると、崩れた形が「揃っている」ように見えるため。外れてよい理由は守ることの 2 つ目のとおりにし、リポジトリの今の状態しか理由が無ければ寄せる。理由に記録（判断の記録・既知の制約・例外の一覧など）を使うなら、その行がこの PR で入った物でないかを先に確かめ、この PR で入った物なら理由に数えない（守ることの 3 つ目）。同じ問題があと 3 回来たとき、この PR の形の延長で何が積み上がるかも言う。寄せると決めた違いは、下の層の木のルートの 1 つになる（下の層を置き換えない）。

### 下の層: 前提から木を掘る

10. この PR が作る仕組みを 1 文で言い、それが補っている前提（その仕組みが無いと崩れる、人の手・別の場所の取り決め・外のツールの振る舞い）を 1 文ずつ言う（形は「〜を作る。要るのは、〜が〜を持たないから」）。この PR が足す検査・試験の仕組みにも、それぞれの前提を言う。
11. 木を探索するように掘る。ルートの 1 本は必ず「10 の前提を消す形はあるか（消せば、この仕組みのどこが要らなくなるか）」にする。消す道は近い所から探す: まず変更の内側で消せないか（2 か所で作る値を同じ出どころから作る・既存の仕組みに任せる）を問い、システムをまたぐ設計の変更（認証の方式を替えるなど）はその後に回す。ほかのルートは、9 で寄せると決めた違いと、4 で読んだ指摘やレビューの観点（作者なら受けた指摘を 1 件ずつ）と、4 でルートにすると決めた前の回の発見にする。作者が頼んだ観点と本文の枠（PR の本文や設計の文書が立てた段・項目）だけをルートにしない。出てきた問いを子の問いに分け、子の問いごとに末端（実物で確かめて答えが 1 つに決まる問い）まで掘り、末端ごとに何で確かめて何が分かったかを残す。末端は、まずコード・設定・原典を読んで決める。この PR の自作の部品（検査器・試験のツール・つなぎのスクリプトなど）は、関数名の一覧や骨組みで済ませず本体を読む（判定の 1 つずつを 15 で問う）。実際に動かす（描く・試験を回す・写しで試す・ツールを入れる）のは、読むだけでは答えが 1 つに決まらず、その答えで推奨や下書きが変わるときに限る。動かさずに決めた末端は何を読んで決めたかを書き、読むだけで決まらず推奨にも効かない物は「未確認」と書いて止める。
12. 相乗りを 2 つの範囲で見て、どの直しをどう組めばよいかを考え、その相乗りが本当に成り立つかを確かめる。
    - 11 のルートどうし: 1 つの直しで片づく組と、1 つの直しが別のルートの答えを壊す組（探して無ければ無いと 1 文）。
    - この PR の外: 同じ環境・仕組み・ツールを作る予定の open な issue・PR を `gh issue list --state open --search <語>` と `gh pr list --state open --search <語>` で探す（語は 10 の仕組みと、それが要る環境の名前）。向こうの環境に相乗りできるか・向こうがこちらの部品を使えるかを見て、探した語を書く。
13. 世の中が同じ問題をどう解いているか（OSS・定番のツール・定番の手順）を、6 の構造の部品ごとに、まず PR が作る部品の全体（10 の仕組みが解こうとしている問題）に、次に指摘の 1 件ずつとこちらの直し方の案に当てる。製品の部品だけでなく、この PR が足す検査・試験・CI の部品にも当て、同じ部品を受け持つ定番のツール（検証器・リンタ・試験のツールなど）を探す。あわせて、この PR より前からリポジトリに在る検証のうち本物のツールに処理させる物（本物のパーサ・レンダラ・コンパイラに通す試験や CI の段など）を洗い出し、この PR が足した物がその経路に乗っているかを見る。乗っていなければ穴として直す対象に入れる（17・18）。ツールを当てる前に、そのツールが 7 の一般の構造のどの部品を受け持つかを言い、PR が作る部品と同じ部品を受け持つ物だけを、代わりや上流に数える。当てた先ごとに、世の中の解と、こちらの案と同じか・違うならどちらを採るかを書く。解は公式の文書かソースの原典（ミラーや写しでなく）で確かめ、記憶だけで書かない。確かめられなければ「未確認」と書く。見つからなければ探した場所を書いて「見つからない」と書き、それでも決まらなければ持ち主に聞く。
14. 直し方を、要らなくする（2 か所に在る物を 1 か所から作る・前提を消す）→ 型で縛る（スキーマや型で、ずれた値を書けなくする）→ 出来合いのツール → 自作の順に選ぶ。上の段で防げるなら、下の段の案は出さない。出来合いのツールの上でも、規則を自分で書く物（conftest に渡す Rego の規則など）は自作に数える。
15. 自作（世の中の定番で足りるのに手で作っている部分）を、今まで進んできた前提を気にせずゼロベースで疑う。どの部品が自作かを 6 の構造の上で言ってから、その部品について 13 の解と履歴を掘る。記録（既知の制約・判断の記録など）に載っていても、その行をこの PR が足したなら掘るのをやめない（守ることの 3 つ目）。自作の部品は本体を読み、判定の 1 つずつに 3 つを問う: 確かめている 2 つの値はすでに同じ出どころから作られていないか（作られていればその判定は要らない）。ほかの検査がすでに同じことを見ていないか。外のツールの振る舞いを写していないか（写しているなら本物のツールで確かめるか、確かめる理由を無くす）。OSS があるかもしれないし、世界がやっていない自作には何かしらの理由があるはずである。見つけたら、なぜ自作になったかを履歴（`git log`・その行を入れた PR・issue）で掘る。今の書き方のままツールを当てるのでなく、ツールに寄せて（こちらの書き方を変えて）どの自前の処理・規則・検査が消えるかを、ファイルや関数の単位で数える。寄せても消えない物は、なぜ消えないかをツールの原典（公式の文書・ソース）で確かめる。

### 出力の層: 報告と、指摘の下書きか直し方の案を並べる

16. 持ち主への報告を返答の先頭に書く。冒頭の 3 行で、決めてほしいこと（レビュアーなら 17 の下書きを出すか、作者なら受けた指摘ごとにどの案を採るか）・何の PR か・何が分かったかを言う。その下は手順の順に並べず、指摘と案ごとのセクションにし、セクションごとに裏付け（11 の末端で分かったこと・12 の相乗り・13〜15 の世の中の解と自作の訳）を置く。6 の構造と上の層の違いと判断、10 の仕組みと前提、前提を消す案、PR の外の相乗り、構造の打ち手（設計の原則を書く・issue にまとめる・配線を通す）、4 で議題にした前の回の発見もセクションにする。最後の「確かめた前提」のセクションに、4 で控えた前の指摘と前の回の発見の今の状態・7・8 で使った問いの文（そのまま写す）・確かめていないことを置く。見出しは中身で名付け、この手順の言葉（「上の層」「ルート」など）を使わない。違いが無い・寄せない項目は 1 行に束ねる。指摘の本文は 17 か 18 に書き、セクションからは 17・18 で振った番号で指す。「確かめた」の添え書き・GitHub に書いていない旨の断り・途中経過は書かない。
17. レビュアーなら、作者への指摘（9 で一般の構造に寄せると決めた違い・11 で直すと決めたルート・13 で見つけた穴・15 で要らないと分かった判定や自作）を、報告の後にインラインコメントの下書きとして、直す箇所ごとに並べる。1 件は、見出しの行に報告から指すための番号（`[1]` など）と `ファイル:行`（範囲なら `ファイル:始めの行-終わりの行`）、その下に本文（何が問題か・どう直すか・何で確かめたか）を書く。本文はそのまま GitHub に貼れる形にし、番号を書かない（番号はこの報告のために振った物で、作者には意味が無い）。行の番号は PR の head の物にし、消した行に付けるなら `ファイル:12（base）` と書く。1 つの指摘が何か所にも効くなら箇所ごとに並べ、2 件目からの本文は最初の件を番号でなく `ファイル:行` か中身の短い言い方で指す（GitHub が差分に追わせるのはインラインの場所なので、行で指せば作者が辿れる）。作者に頼むのは、この PR が触る部品（6 で示した所）を変える物と、その変更で崩れる物だけにする。触る部品の外の話（別の issue・PR で作る部品など）は、下書きにせず 16 の報告で持ち主に上げる議題にする。作者に、GitHub の外や別のリポジトリへの書き込み（上流への issue・機能要望など）を頼まない（調べることはここでやる。守ることの 4 つ目）。下書きは差分の中の行にだけ付ける。行に付かない話（PR 全体の向き・この PR の変更が崩す差分の外の行）は、最後に 1 つのトップレベルの下書き（PR 全体へのコメント）にまとめる（無ければ作らない）。別の issue にするかは作者が決めることなので、こちらからは提案しない（12 で見つけた、既に在る open な issue・PR への相乗りは事実として書く）。作者なら、この手順は飛ばす。
18. 作者なら、受けた指摘ごとに、直し方の案と返信の要否を、報告の後に番号を振って並べる。返信の下書きを添えるなら、その本文に番号を書かない（別の指摘は `ファイル:行` か中身の短い言い方で指す）。自分の PR に自分でレビューを書くのではないので、指摘やインラインコメントの下書きの形にはしない（9・11・13・15 で自分で見つけた直しは、16 の報告に直し方の案として書く）。
19. 見せる前に、11・13・15 で確かめるために作った・入れた・変えた物を片付ける。一時の置き場・写し・ファイルは消す。PR のブランチの作業ツリーは、2 で控えた状態に戻す（`git status` を始めと同じにし、stash を残さず、ブランチを変えない）。確かめるために入れたツールの版（mise・uv・npm など）は、作業ツリーの設定（`mise.toml` など）を書き換えたなら戻す。手元に入っただけの物は残してよいが、何を入れたかを報告の「確かめた前提」に 1 行書く。裏で起動したサーバや定期の仕事は止める。片付けられなかった物は、その場所と訳を「確かめた前提」に書く。
