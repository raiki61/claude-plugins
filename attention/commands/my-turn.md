持ち主はこの会話の相手で、「自分の番」は持ち主が次に動くターンを指す。

## 守ること

- 個別最適の積み重ねで全体が汚くなる形は通さない。この PR だけ見れば筋が通っていても、全体を汚す方向なら一番上の指摘にする。
- 確かめていない領域を残さない。調べること（前提・世の中の解・自作の訳・相乗り）は作者に委ねず、ここで調べる。作者に委ねるのは、どの案を採るか・別の issue にするかの選択だけ。
- 「消える」「要らなくなる」「穴が塞がる」は、実物（コード・設定・ツールの原典）で木の末端まで確かめてから書く。確かめていなければ「未確認」と書き添える。
- GitHub へは書き込まない。

## 手順

### 前提を取り直す

1. 対象の PR を決める。引数の番号を使い、無ければ `gh pr view --json number` で今のブランチの PR を引く。どちらも無ければ、PR 番号を聞いて止まる。
2. `gh pr view <番号> --json state,mergedAt,author,headRefOid,statusCheckRollup` で今の状態を取る。merge 済み・閉じている・head が手元の `git rev-parse HEAD` と違う（PR のブランチに居ない・手元が古い）なら、それを言って止まる。
3. 立場を決める。作者が `gh api user -q .login` と同じなら作者、違えばレビュアー。
4. 会話を全部読む（`gh pr view <番号> --json body,comments,reviews` と `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`）。自分が前に出した指摘・決着した指摘・許した指摘を一覧にし、同じ指摘や食い違う指摘を出さない。
5. 本文・会話・触るコードが名指す PR・issue・設計の判断の記録を読み、後の変更で前提が古くなっていないかを確かめる。読めなかった物は「未確認」と書く。

### 上の層: 構造をとらえて外の基準と比べる

6. 構造をとらえる。PR が触る物を含むシステムを、このリポジトリの言葉を使わずに、部品・部品の間を流れる物（値・事実・呼び出し）・どこが正本でどこが読むだけか・依存の向き・境目で描き、PR が触る部品がその中のどこかを示す。この PR の解き方（作る仕組み・検査・名前の組み立て方）は書かない。最後に、どんな種類のシステムで、触る部品がそこで何を揃えたいかを 1 文で言う。部品の言えない PR（版の数字だけなど）は下の層の 10 へ飛ばす。
7. 一般の構造を別の目に描かせる。Agent ツールで、ツールを持たないエージェント（convergence-loops の `blind-judge` が入っていればそれ、無ければツールを使うなと頼んだ general-purpose）に 6 の最後の 1 文だけを渡し、「この種類のシステムは一般に、どんな部品に分け、部品の間を何が流れ、正本をどこに置き、依存をどちら向きにし、境目をどこに引くか。それぞれを、そう置く理由と一緒に描け。解き方やツールではなく構造を描け」と問う。差分・本文・リポジトリの名前は渡さない。
8. 6 の構造（この PR が入った後）と 7 の一般の構造を並べ、部品の切り方・流れの向き・正本の位置・境目の置き方の違いを挙げる（答えにツールや OSS の名前が出ても比べず、13 で当てる）。答えがどんな作りにも当てはまる一般論で比べる相手にならないとき（一致して違いが無いのとは別）は、この PR の構造が選んでいる所を、選んだ答えを伏せた問い（「正本をどちらに置くか」「境目をどこに引くか」など）にして 6 の最後の 1 文に足し、同じ相手に 1 回だけ問い直す（7 の「1 文だけ」の例外はこの問いだけで、差分・本文・リポジトリの名前はこのときも渡さない）。それでも出なければ、出なかったことを報告に書く。
9. 違いごとに、一般の構造に寄せるべきか、ここだけの理由で外れてよいかを決める。決めるときは周りのコードと比べず、外の基準（書かれた意図・7 の一般の構造・業界の定石）と比べる。周りがすでに崩れていると、崩れた形が「揃っている」ように見えるため。「今そうなっているから」は外れてよい理由にしない。同じ問題があと 3 回来たとき、この PR の形の延長で何が積み上がるかも言う。寄せると決めた違いは、下の層の木のルートの 1 つになる（下の層を置き換えない）。

### 下の層: 前提から木を掘る

10. この PR が作る仕組みを 1 文で言い、それが補っている前提（その仕組みが無いと崩れる、人の手・別の場所の取り決め・外のツールの振る舞い）を 1 文ずつ言う（形は「〜を作る。要るのは、〜が〜を持たないから」）。
11. 木を探索するように掘る。ルートの 1 本は必ず「10 の前提を消す形はあるか（消せば、この仕組みのどこが要らなくなるか）」にする。ほかのルートは、9 で寄せると決めた違いと、4 で読んだ指摘やレビューの観点（作者なら受けた指摘を 1 件ずつ）にする。作者が頼んだ観点と本文の枠（PR の本文や設計の文書が立てた段・項目）だけをルートにしない。出てきた問いを子の問いに分け、子の問いごとに末端（実物で確かめて答えが 1 つに決まる問い）まで掘り、末端ごとに何で確かめて何が分かったかを残す。
12. 相乗りを 2 つの範囲で見て、どの直しをどう組めばよいかを考え、その相乗りが本当に成り立つかを確かめる。
    - 11 のルートどうし: 1 つの直しで片づく組と、1 つの直しが別のルートの答えを壊す組。
    - この PR の外: 同じ環境・仕組み・ツールを作る予定の open な issue・PR を `gh issue list --state open --search <語>` と `gh pr list --state open --search <語>` で探す（語は 10 の仕組みと、それが要る環境の名前）。向こうの環境に相乗りできるか・向こうがこちらの部品を使えるかを見て、探した語を書く。
13. 世の中が同じ問題をどう解いているか（OSS・定番のツール・定番の手順）を、まず PR が作る部品の全体（10 の仕組みが解こうとしている問題）に、次に指摘の 1 件ずつとこちらの直し方の案に当てる。当てた先ごとに、世の中の解と、こちらの案と同じか・違うならどちらを採るかを書く。見つからなければ探した場所を書いて「見つからない」と書き、それでも決まらなければ持ち主に聞く。
14. 直し方を、要らなくする（2 か所に在る物を 1 か所から作る・前提を消す）→ 型で縛る（スキーマや型で、ずれた値を書けなくする）→ 出来合いのツール → 自作の順に選ぶ。上の段で防げるなら、下の段の案は出さない。出来合いのツールの上でも、規則を自分で書く物（conftest に渡す Rego の規則など）は自作に数える。
15. 自作（世の中の定番で足りるのに手で作っている部分）を、今まで進んできた前提を気にせずゼロベースで疑う。見つけたら、なぜ自作になったかを履歴（`git log`・その行を入れた PR・issue）で掘る。今の書き方のままツールを当てるのでなく、ツールに寄せて（こちらの書き方を変えて）どの自前の処理・規則・検査が消えるかを、ファイルや関数の単位で数える。寄せても消えない物は、なぜ消えないかをツールの原典（公式の文書・ソース）で確かめる。

### 見せる

16. 持ち主への報告を返答の先頭に書く。上の層の違いと判断（問い直しても違いが出なかったときはそのこと）を一番上に、10 の仕組みと前提、11 の木をルートごとに（末端で何が分かったか）、12 の組と PR の外の相乗り（無ければ無いと 1 文）、13〜15 の世の中の解と自作の訳をその次に置き、構造の打ち手（設計の原則を書く・issue にまとめる・配線を通す）も書く。
17. 作者なら、直し方の案を報告に並べて止まる。レビュアーなら、作者への指摘をインラインコメントの下書きにして見せ、そこで止まる。作者への指摘では、別の issue にすることは提案しない（12 で見つけた、既に在る open な issue・PR への相乗りは事実として書く）。
18. 見せる前に確かめる: 9 の判断を、周りのコードでなく外の基準と比べて決めたか。10 の前提を消す案を 1 つ以上検討したか。11 のルートの全部が末端で分かったことと一緒に報告に在り、直すと決めたルートに指摘か報告の案が在るか。12 の 2 つの範囲を書いたか（無ければ無いと 1 文）。作者が頼んだ観点と本文の枠の外の指摘が 0 件なら、その訳を 1 文書いたか。「消える」「要らなくなる」「穴が塞がる」を、末端まで確かめずに書いていないか。
