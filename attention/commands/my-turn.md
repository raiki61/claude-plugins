持ち主はこの会話の相手で、「自分の番」は持ち主が次に動くターンを指す。

## 守ること

- 個別最適の積み重ねで全体が汚くなる形は通さない。この PR だけ見れば筋が通っていても、全体を汚す方向なら一番上の指摘にする。
- 確かめていない領域を残さない。調べること（前提・世の中の解・自作の訳・相乗り）は作者に委ねず、ここで調べる。作者に委ねるのは、どの案を採るかの選択だけ。
- 「消える」「要らなくなる」「穴が塞がる」は、実物（コード・設定・ツールの原典）で末端まで確かめてから書く。確かめていなければ「未確認」と書き添える。
- GitHub へは書き込まない。

## 手順

1. 対象の PR を決める。引数の番号を使い、無ければ `gh pr view --json number` で今のブランチの PR を引く。どちらも無ければ、PR 番号を聞いて止まる。
2. `gh pr view <番号> --json state,author,headRefOid` で今の状態を取る。merge 済み・閉じている・head が手元の `git rev-parse HEAD` と違う（PR のブランチに居ない・手元が古い）なら、それを言って止まる。
3. 立場を決める。作者が `gh api user -q .login` と同じなら作者、違えばレビュアー。
4. 会話を全部読む（`gh pr view <番号> --json body,comments,reviews` と `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`）。自分が前に出した指摘・決着した指摘・許した指摘を一覧にし、同じ指摘や食い違う指摘を出さない。
5. 本文・会話・触るコードが名指す PR・issue・設計の判断の記録を読み、後の変更で前提が古くなっていないかを確かめる。読めなかった物は「未確認」と書く。
6. 位置を言う。PR が触る物が、世間一般のシステムの全体像（例: 資源を作る層・配信の層・ワークロード・横断の秘密情報や観測）の中のどの部品・どの境目で、そこで何を揃えたいかを、このリポジトリの言葉を使わずに 1〜2 文で言う。この PR の解き方（作る仕組み・検査・名前の組み立て方）は書かない。部品の言えない PR（版の数字だけなど）は 9 まで飛ばす。
7. 理想の形を別の目に描かせる。Agent ツールで、ツールを持たないエージェント（convergence-loops の `blind-judge` が入っていればそれ、無ければツールを使うなと頼んだ general-purpose）に 6 の文だけを渡し、「この部品は一般にどんな問題として扱われ、どんな形で解かれているか（定番の型・OSS・仕様）。綺麗な理想の形を描け」と問う。差分・本文・リポジトリの名前は渡さない。
8. 7 の理想の形と、この PR の作り（と周りの今の形）を並べ、違いを挙げる。
9. 違いごとに、理想に寄せるべきか、ここだけの理由で外れてよいかを決める。「今そうなっているから」は外れてよい理由にしない。同じ問題があと 3 回来たとき、この PR の形の延長で何が積み上がるかも言う。
10. この PR が作る仕組みと、それが補っている前提（その仕組みが無いと崩れる、人の手や別の場所の取り決め）を 1 文ずつ言う。
11. 問いを木に掘る。起点は 9 で寄せると決めた違い・10 の前提を消す形・受けた指摘とレビューの観点の全部にする（作者が頼んだ観点と本文の枠だけにしない）。問いを子の問いに分け、末端まで掘る。
12. 相乗りを見る。掘った問いどうし（1 つの直しで片づく・壊し合う）と、同じ環境や仕組みを作る open な issue・PR（`gh issue list --state open --search <語>`・`gh pr list --state open --search <語>`）を当たり、探した語を書く。
13. 指摘と直し方の案の 1 件ずつに、世の中の解（OSS・定番のツール・定番の手順）を当て、こちらの案と同じか・違うならどちらを採るかを書く。見つからなければ、探した場所を書く。
14. 直し方を、要らなくする（2 か所に在る物を 1 か所から作る・前提を消す）→ 型で縛る（スキーマや型で、ずれた値を書けなくする）→ 出来合いのツール → 自作の順に選ぶ。上の段で防げるなら、下の段の案は出さない。規則を自分で書く物（conftest の Rego など）は自作に数える。
15. 自作が残るなら、なぜ自作になったかを履歴（`git log`・その行を入れた PR）で掘り、上の段に寄せると消える処理をファイルや関数の単位で数え、寄せても消えない訳を原典で確かめる。
16. 持ち主への報告を返答の先頭に書く。8・9 の違いと判断を一番上に置き、構造の打ち手（設計の原則を書く・issue にまとめる・配線を通す）も書く。
17. 作者なら、直し方の案を報告に並べて止まる。レビュアーなら、作者への指摘をインラインコメントの下書きにして見せ、そこで止まる。作者への指摘では、別の issue にすることは提案しない（既に在る open な issue・PR への相乗りは事実として書く）。
18. 見せる前に確かめる: 9 で寄せると決めた違いと、10 の前提を消す案が指摘か報告に在るか。本文の枠の外の指摘が 0 件なら、その訳を 1 文書いたか。
