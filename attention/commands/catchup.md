## 役割分担

- **スクリプト（機械）**: 私の最後の痕跡・私宛の依頼・その後の出来事・状態を全部出す。判断はしない
- **あなた（AI）**: 材料を読み、足りないもの（本文・CI の理由・依頼が済んでいるか）を確かめて、
  下の**型**に畳む。**機械の出力は貼らない**——全文を求められたときだけ、1 文字も
  変えずコードブロックで貼る
- **作者が私でない PR** では、機械が末尾に「変更の地図（材料）」を付ける（置き場所・骨組み・配線。
  行は 1 文字も変えていない）。あなたはそこから**選んで並べ**、下の**地図**の形にする。散文は
  自分で書くが、コードの行は写すだけ

## やること

1. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py <番号または URL>` を実行する。番号だけなら
   カレントのリポジトリを見る。
2. **本文の冒頭を読む**: `gh pr view <番号> --json body -q .body | head -40`（issue なら `gh issue view`）。
   件名を書くのに要る。機械の出力には題名しか無い。
3. 機械の出力に次があれば、**書く前に確かめる**（確かめずに機械の言葉を写すと、答えが逆になる——
   実測: 済んでいる申し送りを「相手の発言があり私は発言していない」のまま写して、初見の読み手が
   「未対応の問い合わせが残っている」と読んだ）:
   - `CI: 赤` — 出力の URL か `gh pr checks <番号>` で**落ちた理由**を読む。「次にやること」はこれ次第
   - `（名指しは無い。私の件への発言）` — その発言が私への依頼か、私の push で**既に済んでいないか**を
     本文と差分で確かめる。機械は push を返事と数えない
   - 止めている原因が別の PR / issue にあるなら、その番号の**誰の番か**を 1 回引く
     （`gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt`）。「未承認」だけでは
     読む人が「今日動くべきか」を決められない
4. 型に畳んで出す。**説明を足すのは、型だけでは「次にやること」を読んだ人が実行できないとき
   だけ**（変更の勘所が要るなら「変更前 → 変更後」の数行の抜き書き。差分の全文ではない）。
5. **作者が私でない PR** なら、型の後ろに**地図**を付ける（下の「地図」）。自分の PR には付けない
   ——戻るときに失われているのは会話の位置で、地図は読み直しの作業になる。

## 型

**同僚に口で話すときの散文**で、**太字の 1〜2 文で始める**。段落の順は固定で、段落は短く。
コードブロック・表・ラベル列を使わない——等幅の枠に並んだラベル列は「機械の出力」に見えて、
読む前に構える（実測: 本人が「読む気が失せる」）。下の例は書き方の一つで、文言を写す型ではない
——決まった言い回しは場面に関係なく毎回出て雑音になる。

```
**#1276（現場コネクタの要件の下書き）は私の PR で、動かすのは私のもう 1 本の
PR #1596 の側です。#1596 にレビュー依頼を出せば進みます。**

最後に触ったのは 2 日前（9/1）で、main を取り込んで push しました。その後は
誰も動いていません。8/27 に 250489 さんから「lint の新しい規則に合わせて 1 行
直して」と申し送りが来ていましたが、9/1 の取り込みで済んでいます。返信は
要りません。

止めているのは CI の赤 3 本で、全部同じ文書検査です。中身は docs/_draft/ の
ADR 参照 10 か所で、下書きを規則の対象から外す #1596（私の PR、レビュー依頼が
未送）が通れば消えます。承認はまだ無く、衝突も未解決スレッドもありません。

次は、#1596 のレビュー依頼を出す → 通ったら main を取り込み直す → 緑を確認 →
#1276 のレビュー依頼先を決める。

見ていないのは、この PR の古い方のコミット 43 件（私の痕跡があれば見落とし
ます）と、GitHub の外のやり取りです。
```

- **1 段落目（太字）**: `#番号（件名）` と立場、**どこで止まっているか**を確かめた結果で。機械の
  「私の番」を写さない。止まり方は 3 つのどれかで、それを進める一手を添える——私が動かせる／
  別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと
  他人の PR 待ちに読まれる。実測）。誰の番でもない（レビュー依頼が誰にも出ていない等）なら、
  渡す先を決めるのが私だと分かるように。
  件名は機械のタイトルから型の接頭辞と括弧書きを落とした**全角 12 字以内**の名詞句。
  **ここだけ読んで用が足りるように書く**
- **作者が私でない PR だけ、1 段落目の直後に「何をする PR か」を 1〜2 文**: 本文の冒頭か、
  機械の地図にある作者の先頭コメントの言葉で。レビューで渡された件で失われているのは、会話の
  位置より「何の PR か」の方（実測: 型だけ出したら次の問いが「内容は」だった）。自分の PR には
  書かない
- **2 段落目（最後にしたこと）**: `N 日前（M/D）` に何をしたか。**その後の動きを同じ段落に続ける**
  ——誰も動いていないならその旨、誰かが動いたなら誰が何をしたか。**人は名前で**
  （「相手」と書くと、レビュー依頼を出していない件で「相手が誰か」で止まる——実測）。私宛の依頼が
  あれば、いつ誰から何が来て、済んでいるか未対応かを書く。未対応なら次の一手の先頭
- **3 段落目（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。1 段落目に出した別の
  番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。CI は落ちた本数と中身の箇所数を
  分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・未解決スレッドの観測値を
  末尾に 1 文。止めているものが無いなら、無いことが分かるように
- **4 段落目（次にやること）**: 動作を `→` で繋ぐ。番号は書くだけで説明しない。空にしない——
  待ちなら、何を待ち、動いたら何をするか
- **最後の 1 行（見ていないもの）**: この報告が見ていない範囲だと分かる 1 行。機械の末尾から、この件に
  固有のもの（上限で切れた分・結び付いていない commit）と GitHub の外を挙げ、それぞれ何を見落としうるかを
  添える。削らない。地図を付けるときは「下の N file は私が選んだもので、残りは末尾に一言だけ」も足す
- **全体で 12 行前後、350 字前後（地図を除く）。** 段落は 4 文以内。**文体は です・ます**
- **同じ番号を説明するのは 1 回、「止めているもの」で**。番号そのものは何度出てもよい

## 地図（作者が私でない PR だけ）

型の後ろに、**この PR が全体のどこに何を足すか**を、木と実コードで見せる。engineer にはコードの
行そのものが散文より早い——散文は翻訳で、読む側が頭の中でコードに戻す往復が要る。IDE が読み
やすいのは色だけでなく 3 つの約束を守っているからで、ここでも守る: **案内（木）と読む場所
（file の中身）を混ぜない。書いてあるものは作者の言葉で見せる（file 名・step 名・docstring・先頭
コメント）。記号は誰もが知っているものだけ（path・+/−・字下げ。木の `~` だけはこの節の印）。**
端末には IDE の 2 つの窓が無いので、順番で代える——上に木、下に file ごとの節。

**この節だけはコードブロックを使う**（型の「コードブロック・表を使わない」の例外）。言語名を
付けると端末が色を付ける（yaml / bash / python / diff / json / dockerfile / asciidoc。無い言語は
plaintext になるだけ）。木は `diff` の枠にして新規の行だけ緑にする。

材料は機械の末尾「変更の地図（材料）」——規模、変更ファイル、同じ階層の既存、名前の言及（当たった
行つき）、新規ファイルの先頭と骨組み、既存ファイルの変更。`| ` の後ろは実物の行。**そこに無い行が
要るときは `gh pr diff <番号>` の実物から写す**（file ごとの絞り込みは無いので、`diff --git` の
見出しで該当 file の範囲を探す）。記憶で書かない。

順に 5 つ。

1. **変更ファイルの木**（```diff）。機械の「変更ファイル」と「同じ階層の既存」から組む。周辺の
   既存も薄く並べ（多い階層は数件と「… ほか N」）、新規は行頭 `+`、既存への追記は `~` と ±行数。
   path と数字だけで、**私の言葉を書かない**。木の前に 1 文——規模（機械の「規模」の数字）。
   周辺の何が何かを書けるのは、hunk か先頭コメントにその名前が出ている file だけ（例: bake の
   コメントにある values-local.yaml）。それ以外は path だけ並べる。機械に「同じ階層の既存」が
   無ければ、変更 file だけの木にする
2. **この PR が言っていること**を 1 文。型の 2 段落目と同じ文を繰り返さず、作者の印（先頭
   コメントの (a)(b) など）を導入する。機械の先頭が「8 行で切った」と言っていれば、切れた文を
   使わず `gh pr diff` で全文を見てから写す
3. **道順**を 1 文——「入口 → そこから呼ばれる検査 → 渡す設定 → 既存への配線の順に N file」
4. **file ごとの節**を 3〜6 つ。境目は罫線 `---` 1 本。見出しは太字で `n/N path` と（新規／既存に追記）。
   その下に**どこから使われるか**を 1 行。機械の「名前の言及」の下の行が `uses:`・`run:`・`-f`・
   import のようなコードの行なら関係として書く。コメント行の言及は関係に数えない。道具が既定の
   名前で読む file（docker-bake.hcl・Dockerfile・.tool-versions など）は名前が行に出ないので、読む側の
   コマンド行（`docker buildx bake` など）を関係にする。評価語は入れない。中身は
   - 新規: 先頭コメントか docstring（作者の自己紹介）→ 骨組み（step 名・def・上位 key）→ 肝の
     数行（`gh pr diff` の実物から。作者が先頭コメントで名指した箇所か、名前の言及で当たった行）。
     ワークフローの step 一覧には、その step が使う file を `#` で添える（名前の言及の行か
     `gh pr diff` の run: 行で確かめたものだけ。これが流れの図の代わり。図は描かない）
   - 既存: ```diff で hunk。大きい変更は追加行の骨組みだけ
5. **残りの file** を末尾に 1 文——名前と ±行数と、機械の先頭コメントにあればその 1 句。無ければ
   名前だけ

**選び方**: 入口（`on:` を持つワークフローのように、他の変更 file を `uses:`・`run:`・`-f` で使い、
自分は他から使われない file）→ 入口が使う file（大きい既存の追記でも入れる。既存なら追加行の
骨組みだけ）→ 既存への 15 行以内の追記。入口が使わない大きな既存の追記（README や台帳）は
末尾の 1 文へ。入口が使わない新規 file（テストなど）は、使われる側の節の「どこから使われるか」で
触れ、末尾の 1 文にも名前を入れる。

**守ること**:
- コードの行は機械の `| ` か `gh pr diff` の実物から**写す**。記憶で書かない
- 枠の中は 1 行 60 桁以内（日本語は 2 桁）。超える行は、変更の肝（名前・条件・追加された断片）を
  残して前後を `…` で省くか、行末を `…` で切る。sha は先頭 7 桁と `…`、長い正規表現や URL は肝の
  1 要素だけ残す。分岐や条件そのものを `…` で隠さない。骨組みの 2 行を 1 行に縮めない（実物に無い
  行になる）。散文（コメント・docstring）は語の切れ目で折り返してよい。見出しと枠の外の散文は
  対象外（折り返しても読める）
- **注釈は行の上に `#` で**、右に日本語を置かない（折り返した瞬間に行の形が壊れる）
- 1 節 15 行まで。入口のワークフローの節だけ 40 行まで——step 一覧は切らず、先頭コメントは
  主張の行（(a)(b) など）だけ、`on:` は契機の行だけ、permissions・concurrency・defaults は落とす。
  全体で 150 行前後まで。超えるなら節を 4 つ（入口・検査の本体・渡す設定・配線 1 つ）に絞る
- 作者の言葉（先頭コメント・docstring）が無い file は骨組みだけ出し、説明を足さない
- 機械に中身が無い（gh pr diff が失敗・上限超え）ときは木だけ出し、中身は出せなかったと 1 文書く

節の形（例。文言を写す型ではない）:

    ---
    **2/6 deploy/scripts/ci-kind-checks.py** （新規）
    1 の 4 つの step から呼ばれる検査の本体。bats 29 件が同じ物を叩く。

    ```python

      ci-kind-checks.py bake-match <bake.json> …
    ```

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・
  直訳横文字、この件の中でしか通じない略号。機械の理由文（「私の件に相手の発言があり…」）を
  そのまま写すな——確かめた結果を書く。「〜と思われる」「〜のようだ」を使うな——確かめていない
  ことは「（未確認）」と付けて書く
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）

書けたら自分に問え——**2 行目だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか。**

## 守ること

- **求められていないのに欠陥探しへ広げるな。** 説明は読む人の理解のためで、レビューを始める合図ではない
- **出力に無いことを断定するな。** 確かめたなら確かめた結果を書く。推測で埋めるな
- **地図のコードを記憶で書くな。** 機械の `| ` の後ろから写す。写したものが実物と違えば、読む人は
  次に開いた file で裏切られる
- 日付・件数は機械の数字をそのまま使う
- open 全件の棚卸しはこの道具の仕事ではない。それは `/whose-turn`
