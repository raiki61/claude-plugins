## 一覧（仕様 `attention/docs/catchup-spec.md` の写し。数値の正本はそちら）

`/catchup [対象] [焦点]`。対象は 1 つ、焦点は 0〜3 語（`指摘`・`地図`・`CI`）。`/catchup setup` は準備の口（下の「準備」）。

| 対象 | 例 | 移る | GitHub | 主な材料 |
|---|---|---|---|---|
| 番号 | `1505` `#1505` | PR の head へ | 見る | PR / issue |
| URL | `https://…/pull/1505` | 同上 | 見る | PR / issue |
| ブランチ名 | `feat/123-x` | そこへ | 枝の PR が有れば | PR、無ければ手元 |
| 引数なし・`this`・焦点だけ | `/catchup` `/catchup 指摘` | 移らない | 今の枝の PR が有れば | PR、無ければ手元 |
| commit | `2971ea2` `HEAD~2` `v1.2` `2971ea2..HEAD` | 移らない | 見ない | その commit（範囲なら全部） |
| 会話の話題 | `新しく出たもの` `今の修正` | 移らない | 結び付いた番号だけ | 結び付く対象か、会話 |

| 旗 | 効き | 効く対象 |
|---|---|---|
| `--switch` | 該当の枝へ移る | 番号・URL・ブランチ名 |
| `--full` | 本文・発言の上限を外す | 全部 |
| `--frame <path>` | その 1 file の変更を上限なしで | PR・commit（手元は what-am-i-doing.py の `--frame`） |
| `--limit N` | その後の出来事の件数（既定 12） | PR・issue |
| `-R owner/repo` | リポジトリを指す | 番号 |
| `--me <login>` | 「私」を差し替える | PR・issue |
| `--render <材料> <欄>` | ページを描き、一覧（`index.html`）を組み直し、VS Code で開く。材料は `--out` が書いた JSON の path、欄は AI が書いた JSON の path | 全部（会話の話題は材料が `-`） |
| `--setup [--check]` | VS Code で見る準備（`--check` は確かめるだけ） | なし |

ページは `~/.cache/attention/catchup/<owner>-<repo>/<番号>.html`（役割分担）。節はこの順で、機械が材料の有る節だけを描く。焦点の語で絞ったときも見出し・いまの番・前回からは描き、後ろは絞った材料の節だけ（説明と図は `地図` のときだけ書く）:

| # | 節 | 中身 | 書くのは |
|---|---|---|---|
| 1 | 見出し | 件名・番号・状態・作者・規模・閉じる issue | 機械 |
| 2 | いまの番 | 番の札と立場、`headline`、`next`、止めているものの行 | 札と行は機械、文は AI |
| 3 | 前回から | 番の受け渡しの流れ（GitHub の PR の会話の流れの形）、`where`、`turn` | 流れは機械、文は AI |
| 4 | この PR がすること | `figure`、`explain` | AI |
| 5 | 指摘 | 人が入っている未解決スレッド（差分の抜粋・私と相手の最後の発言・前回から変わったか） | 機械 |
| 6 | CI | 赤ごとに、落ちた step のログの末尾 | 機械 |
| 7 | 変更 | 前回から（私の痕跡以降）と全体の差分 | 機械 |
| 8 | 手元 | 「ブランチ」の行と「手元のブランチ」の節 | 機械 |
| 9 | 見ていないもの | `unseen` と機械の申告 | 両方 |

対象ごとに描かれる節（○ 描く／△ 材料が有れば／– 描かない）:

| 対象 | いまの番 | 前回から | がすること | 指摘 | CI | 変更 | 手元 |
|---|---|---|---|---|---|---|---|
| PR | ○ | ○ | ○ | △ | △ | ○ | △ |
| issue | ○ | ○ | △ | – | – | – | △ |
| 枝に PR 無し | ○ | ○ | △ | – | – | △ | ○ |
| commit | ○ | ○ | △ | – | – | ○ | – |
| 会話の話題 | ○ | ○ | – | – | – | – | – |

会話の話題が番号・枝・commit に結び付いていれば、この表の**その対象の行**（受け口で先に解く）。話題の行は、会話にしか無いものだけ。

上限と、続きを出す口（材料の上限。ページの差分は全部載る）。「切れた」は機械が数で言う——「N 行で切った」「上限 N 件」「古い方 N 件」「本文の残り N 行」。切れていればその口で取ってから書き、取ったものは見ていないものに書かない（もう見ている）:

| 何 | 上限 | 続き |
|---|---|---|
| 作者の本文 | 60 行 | `--full` / `gh pr view` |
| 閉じる issue・参照先の冒頭 | 12 行 | `--full` / `gh issue view` |
| 閉じる issue・参照先の件数 | 3 件ずつ | `--full` |
| 相手の発言（スレッド） | 40 行 | `--full` |
| その後の出来事 | 12 件 | `--limit` |
| 指摘（スレッド）の件数 | 10 件 | `--full` |
| CI の赤の件数 | 3 件 | `--full` |
| 取った commit | 100 本 | 見ていないものに書く |

## 受け口

機械は `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py`（以下 catchup.py）。`--switch` を付けるのは番号・URL・ブランチ名だけで、`this`・commit・会話の話題では付けない。

**どの呼び方でも、引数の末尾に `--out` を付け、返ってきたパスを Read で読む。** catchup.py の出力は Claude Code の Bash の 1 回あたりの上限（約 30,000 バイト。門はバイトで測るので、日本語はおよそ 1 万文字で当たる）を常に越える（実測 2026-09-16: 1 件で 91,701〜158,078 バイト）。付けずに走らせるとツール側でファイルへ退避され、走らせ直しで `gh` の呼び出しごと 2 回走る。`--out` は値を取らないので末尾に置く（前に置くと後ろの位置引数を吸わないが、並びが読みにくい）。**`cat` で読むな**——同じ量が再び Bash の出力に乗って、また退避される。2,000 行を越える回があるので、Read が途中で切れたら offset を進めて続きを読む。

`--out` は節ごとの行番号も返す（`節（Read の offset）: … / 159 指摘 / 971 変更の地図`）。**読むのは `変更の地図` の頭まで**——見出し・私が最後にしたこと・求められていること・その後・状態・つながっている先・本文・指摘・CI は全部読み、地図は規模・変更ファイル・名前の言及・新規ファイルの先頭と骨組みまで（説明と図の材料）。既存ファイルの変更の枠（今の姿に帯）は、説明の 2 段落目に要るときだけ読む——差分はページに機械が全部載せるので、写すために読む必要は無い。取り直しは要らない——同じファイルの続きを読むだけで、`gh` も `git` も走らない（実測 2026-09-16: #1720 は 2,168 行のうち骨組み 158 行・指摘 812 行・地図 1,199 行）。

`--out` はもう 1 行、**描く材料**の path を返す（`描く材料は <path> に書いた`）。HTML の雛形が描く構造（見出し・番・出来事・指摘・CI・差分・手元）を JSON にしたもので、AI は読まない（手で直さない）。`--render` にそのまま渡す。

- **番号・URL・ブランチ名** → `catchup.py --switch <それ> --out`。番号だけならいま居るリポジトリ（別のリポジトリは URL か `-R owner/repo`）
- **引数なし・`this`・焦点の語だけ** → `catchup.py this --out`（`catchup.py 指摘 --out` も同じで、対象は今のブランチに落ちる）
- **commit** → `catchup.py <それ> --out`。GitHub には何も聞かず、手元の git の commit として出る（題と本文、木、変更の中身。範囲は親との差 1 つ、merge は第 1 親との差）。PR を立てずに既定ブランチへ直接 commit する運用で、後から変更を読み直す口。commit の範囲 `A..B`（`2971ea2..b27cb3d`・`HEAD~4..HEAD`・`e824033^..HEAD`）も同じ形で、差は A の版と B の版の間、本文は各 commit の題（全文は `git show <sha>`）。`--frame` も効く
- **会話の話題**（`新しく出たもの`・`今の修正`・`さっきの 4 件` など、番号でも commit でも枝でもない語）→ **先に、会話の中で何に結び付いているかを解く。** 番号・枝・commit に結び付いていれば対象はそれで、話題の形では書かない——番号なら `catchup.py <番号>`（`--switch` は付けない。戻る呼び方ではない）、直前に commit した話なら `catchup.py HEAD`、このセッションで入れた commit が複数なら `what-am-i-doing.py` の「このセッションの間に入ったコミット」の一番古い sha に `^` を付けた範囲 `catchup.py <古い sha>^..<新しい sha>`。ページは、その対象を直接呼ばれたときと同じ形（説明・変更まで全部）。会話にしか無い話題（レビューで見つけた指摘の束・検討中の案）だけ、`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/what-am-i-doing.py --topic "<語句>" --out` でその語句が出た往復を取り、話題の形（下の「会話の話題」）で書く——語句は 1 つ（引用符で括る。複数の語は続けた 1 句として当たる。0 件なら肝の 1 語か言い換えでもう 1 回）。実測: 「今の修正」を話題の形で書いたら、commit 4 件は push 済みで手元は空、型だけの返答になり「何も出ない」と言われた
- **`setup`**（`/catchup setup`）→ 対象ではなく準備の口。下の「準備」
- **焦点の語** → 対象の後ろにそのまま（`catchup.py --switch 1569 指摘 --out`）。末尾の材料をその 1 つ（複数可）に絞る、急ぐときの口で既定ではない。無ければ機械が「無い」と 1 行出す。指摘・CI を PR でない対象に付けると「その材料は PR / issue のもの」と出る。地図は commit にも効く

対象の読み方:

- 数字だけの語は番号が先。7 桁以上で手元の commit に解ければ commit（迷うなら `HEAD~n` か 8 桁以上）。同じ語が枝の名前にも当たるなら枝が勝つ（移る）。焦点の語と同じ名前の枝・タグは対象にできない（先に焦点として読む）
- 引数なし・`this`・ブランチ名で移った後は、今の枝から意図を汲む。順に: 枝の PR → 無ければブランチ名の番号（`chore/1513-…` → #1513。PR か issue かは GitHub が返した種類のとおりで、機械が「（… だった。違えば番号を渡す）」と 1 行断る。issue と決めつけない）→ それも無ければ手元だけ（機械は GitHub に聞かず、手元のブランチと未コミットの変更の中身、既定ブランチより先の commit が有ればその差を出す。止めない——止めると書きかけの人に何も返らない）→ 手元に未コミットも、push していない commit も、既定ブランチより先の commit も無ければ、**会話から対象を推定する** → 推定もできなければ聞き返す。ブランチ名で呼ばれたときは推定しない（枝そのものが対象。差が無ければその旨を欄で）
- **会話からの推定**: 直近に出たものを 1 つ（番号・ブランチ・commit・話題。直前に commit した話なら HEAD の commit）。同じ往復に複数あれば 番号 → ブランチ → commit → 話題 の順。会話が要約で前半が消えていれば `what-am-i-doing.py` で往復を取ってから決める。2 つ以上が同じ強さなら推定しない（聞き返す）。番号は、会話に URL か owner/repo が無ければいま居るリポジトリの番号と見る（URL が出ていればそれで呼ぶ）。推定した対象で機械を呼び直す——番号は `catchup.py <番号>`、commit は `catchup.py <sha>`、話題は `what-am-i-doing.py --topic "<会話でその話題を指した、読む人の語>"`（0 件なら肝の 1 語で 1 回）。`--switch` は付けない（引数なしは移らない。移りたければ番号で呼び直してもらう）。ページは、その対象を直接呼ばれたときと同じ形（一覧の表のその対象の行。節も全部）
- **聞き返す**（**質問で返してよいのはここだけ**）: ページを描かない。手元の事実（枝の名前・PR も番号も無い・未コミットも push していない commit も無い）を 1〜2 文で言い切ってから、渡せるもの（番号・URL・ブランチ名・commit・話題の語）を 1 文で聞く。末尾に機械の「見ていないもの」の 3 項目（script 名は `/what-am-i-doing` の呼び名に置き換える）
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。GitHub の remote が無い・detached だけは「PR が無い」と同じに扱い、手元だけを出す

移る（`--switch`。戻るとき、会話の位置と一緒に手元の枝も失われている）:

- 移る先: PR は head の枝（手元に無ければ origin からその 1 本だけ `git fetch` して作って移る。名前と追跡先は `gh pr checkout` と同じ）。issue は名前にその番号を持つ手元の枝が 1 本のときだけ（origin からは探さない）。ブランチ名はその枝（origin にだけ有れば origin/<名前> を追跡する枝を作って移る）
- 移らない条件（理由と今どこに居るかが、見出しの URL の直下の「ブランチ」の行に出る）: 追跡 file に未コミット（未追跡だけなら移る）／merge・rebase・cherry-pick の途中／別の worktree に checkout 済み／origin にももう無い（merge 済みで削除）／fetch が失敗／fork の PR で手元の同名の枝が head の commit を含まない／`index.lock` が有る。ブランチ名で移れなかったときは、機械がその枝に PR が有れば PR として、無ければ枝の tip の commit として出す（枝全体の差は移ってから）
- 機械が手元を変えるのは `git switch` とその 1 本の fetch だけ。pull・merge・stash・commit・`gh pr checkout` はしない。戻すのは `git switch -`。移った・既に居たときは末尾に「手元のブランチ」の節が付く（push していない commit・PR の head より後ろの数・未コミットの木）。移らなかったときは「ブランチ」の行だけ

## 役割分担

- **機械（catchup.py）**: 事実だけを出し、判断しない。`--out` で 2 つを書く——AI が読む文字の材料（見出し・私の最後の痕跡・私に求められていること・その後の出来事・私の痕跡以降に変わった file・いまの状態・つながっている先・見ていないもの、続いて 本文（材料）→ 指摘（材料）→ CI が落ちた理由（材料）→ 変更の地図（材料）→ 手元のブランチ）と、ページの雛形が描く構造の JSON。`--render` が、その JSON と AI の欄を雛形（`attention/templates/catchup.html`）に流し込み、`~/.cache/attention/catchup/<owner>-<repo>/<番号>.html` を書く（同じ件は上書き）。同じ置き場の `index.html` は、ページごとに 1 行（件・件名・誰の番・次の一手・更新）を並べる一覧で、描くたびに組み直す。描いた後、生きている VS Code の窓のすべてでページを開く（`ATTENTION_CATCHUP_OPEN=0` なら開かない。開けなくても失敗にしない）
- **あなた（AI）**: 材料を読み、書く前に確かめ、**欄の JSON**（下の「欄」）を書いて `--render` を呼ぶ。コードの行・差分・指摘の発言・CI のログ・木は機械がページに載せるので、写さない。日付・件数は機械の数字。「私」は gh の認証ユーザで、手元の `git config user.email` と一致する commit は私の push（commit を呼んだときの作者判定は「PR でないとき」）
- **材料の語のうち、欄で使う所**: `取り込み先`・`上に積む`・`依頼先の候補`・`私の痕跡以降に変わった file`・見出しの「ブランチ」の行・`← 私が返す番`・`← 私が最後に発言している（相手の番）`・見ていないもの。綴りはそのまま探せばよいが、欄にはこの語を写さず、中身を書く

## やること

1. 受け口のとおりに機械を呼ぶ（`--out` 付き）。報告を Read で読む（読む範囲は受け口）。
2. **本文を読む**: 「本文（材料）」に作者の本文と、閉じる issue・本文が # で指す issue / PR の冒頭。件名（`headline`）と説明（`explain`）の材料。上限で切れていれば `gh pr view <番号> --json body -q .body`（issue は `gh issue view`、commit は `git show`）で全文を読む。
3. **書く前に確かめる 4 つ**（確かめずに機械の言葉を写すと答えが逆になる——済んでいる申し送りが「未対応の問い合わせ」に読まれた実測）。確かめた結果は欄（`headline`・`where`・`turn`・`next`）に書く:
   - `CI: 赤` → 「CI が落ちた理由（材料）」で落ちた理由を読む（焦点で他に絞って付いていなければ `catchup.py <番号> CI --out` で呼び直す。`--switch` は要らない）。読めなかったチェック（Actions の run でない等）は URL を開く。`next` はこれ次第
   - `（名指しは無い。私の件への発言）` → 私への依頼か、私の push で**既に済んでいないか**を本文と差分で確かめる（機械は push を返事と数えない）
   - 止めている原因が別の PR / issue → その番号の**誰の番か**を 1 回引く（`gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt`）。「未承認」だけでは読む人が今日動くべきかを決められない
   - 会話に GitHub に無い依頼（口頭・チャットのレビュー依頼など）が出ていれば、立場は会話の側を信じて書く（私が動かせる）。GitHub に依頼が無いことは 1 文添える
   - 取り込みが「GitHub が判定中（UNKNOWN）」なら `gh pr view <番号> --json mergeable -q .mergeable` を 1 回だけ引き直す（機械を丸ごとは呼び直さない）。まだ UNKNOWN なら「衝突の有無は GitHub が判定中（未確認）」と書く
4. **欄の JSON を書く**（下の「欄」）。置き場は、描く材料の path の `.json` を `-fields.json` に替えた path（同じ一時の階層）。Write で書く。
5. **描く**: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py --render <描く材料の path> <欄の JSON の path>`。欄に直す所があれば、機械が 1 件 1 行で言って終了コード 2 で止まる——直して呼び直す。機械が `--out` のときに「描く材料を組めなかった」と言っていれば、ページは描けない——欄に書くはずだった中身（`headline`・`where`・`turn`・`next`）を端末に短く返し、ページを描けなかったことと機械の言い分を 1 文添える。
6. **返答**: 機械が標準出力に出した 2 行——ページの path と 1 行の要約——だけを、そのまま返す。説明・指摘・差分を端末に書き足さない（ページに在る）。全文を求められたときだけ、報告のファイルを 1 文字も変えずにコードブロックで貼る。

## 欄（AI が書く JSON）

```json
{
  "headline": "1 文。番号と件名、立場、どこで止まっているか（状態の値は書かない）",
  "where": "最後にしたことと、その後の動き",
  "turn": "止めているものの原因と、誰が外せるか（止めているものの行の値は書かない）",
  "next": ["一手", "その次", "…"],
  "unseen": ["機械の申告に足す、見ていないもの"],
  "explain": ["背景と課題", "何をどう変えるか", "使う側から見た変化と、含まれないもの"],
  "figure": {"caption": "図の題", "rows": [
    {"label": "変更前", "steps": [{"text": "箱"}, {"text": "箱", "tone": "bad"}], "notes": [{"at": 1, "text": "注記", "tone": "bad"}]},
    {"label": "変更後", "steps": [{"text": "箱"}, {"text": "箱", "tone": "good"}]}]}
}
```

`headline`・`where`・`turn`・`next` は必須。`unseen`・`explain`・`figure` は無ければ省く（`figure` は `null` でもよい）。`title` は会話の話題のときだけ（材料が無いので件名をここに）。知らない欄・空の文字列は機械が止める。

文体は**常体の短い文**（「〜した」「〜の番」）。1 文 1 情報。**1 段落は 3 文まで**（長くなるなら段落を割る）。**状態の値（CI の本数・承認・取り込み・未解決の件数）は文に書かない**——いまの番の「止めているものの行」に機械が出しているので、文で繰り返すと 1 枚に同じことが 3 回並ぶ。ページは読む人が上から 5 秒（いまの番）・1 分（前回から・この PR がすること）・5 分（指摘・変更）の順に読むので、上の欄ほど短く。文中の `` `…` `` はコードの札、`#番号`・commit の sha・`@名前` は機械がリンクや札にする。下の例は書き方の一つで、文言を写す型ではない（決まった言い回しは場面に関係なく毎回出て雑音になる）。

```json
{
  "headline": "#2015（切断時の終了コードの直し）はレビュアーの私が返す番で、私の指摘 3 件に作者が今日の夕方まとめて返信した。",
  "where": "10/15 09:41 に、テストが例外の包み方を手で写していることを指摘した。その後、作者が 15:32 に push し、15:44〜15:45 に 3 件へ返信した。",
  "turn": "止めているのは私の返事だけ。3 件のうちコードで直したのは 1 件（4cf1df3aa）、残る 2 件は作者が #2010 と #2076 に分けた。",
  "next": ["4cf1df3aa を読み、失敗した日付のデータが解放されるかを確かめる", "#2010・#2076 への分割を受けるかを決める", "3 件に返信して解決にする", "承認するか、追加の指摘を出す"]
}
```

- **`headline`（いまの番の 1 行目。ここだけ読んで用が足りるように）**: **1 文で**、`#番号（件名）` と立場、**どこで止まっているか**を確かめた結果。進める一手は `next` の先頭に書く（ページは `next` の先頭を大きく描く）。件名は機械のタイトルから型の接頭辞と括弧書きを落とした**全角 12 字以内**の名詞句。止まり方は 3 つ——私が動かせる／別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと他人の PR 待ちに読まれる）。機械の「取り込み先」が既定ブランチでなく、その枝の PR が open なら、**その番号と誰のものかを入れる**（その PR が入るまで、この PR は既定ブランチに届かない）。私の一手で動くのが私の番だけ（返信すれば私の側は終わるが、PR は下書きのまま・依頼未送・別の番号待ち）なら「進む」と書かず、「私の側は終わり、その後は X さんの番」と書く（実測: 返信 2 件で「進みます」と書いたが、返信後も下書きで親の PR 待ちだった）。私の PR で依頼が誰にも出ていないなら、渡す先を決めるのが私だと分かるように。私が入っていない他人の PR で、GitHub にも会話にも依頼が無いなら「作者 X を待っている」（渡す先を決めるのは作者）。閉じた件（merged・closed）は「済み。動くものは無い」と言い切る。PR でないときの言い切りは下の「PR でないとき」
- **`where`（前回から）**: `N 日前（M/D）` に何をしたか。N は機械の行に有ればそれ、無ければ（作成・渡された時点の行は日付だけ）機械の日付から今日までを数える（年は今年と見る）。同じ日なら「今日（M/D）」、前日なら「昨日（M/D）」。**その後の動きを同じ欄に**——誰も動いていないならその旨、動いたなら誰が何を（**人は名前で**。「相手」と書くと誰かで止まる）。発言を「」に入れるのはその人の語そのままのときだけ。私宛の依頼があれば、いつ誰から何が来て、済んでいるか未対応か（未対応なら `next` の先頭）。その後に push があれば「私の痕跡以降に変わった file」の件数を同じ欄に。機械が「この件で私はまだ何もしていない」と言うなら、その旨から始め、起点は私に渡された時点（誰の何で）か作成（誰が立てた）にする。末尾に手元の 1 文——`--switch` で呼んだときは今のブランチを絶対名で（「手元は main から feat/123-x に移した」／「手元に feat/123-x は無かったので origin から取り、main から移した」／「手元は feat/123-x に居る」／「手元は main のまま（手元に未コミット 3 件があるので feat/123-x へ移していない）」／「手元に feat/123-x は無く、origin にももう無い（PR は merge 済み）。手元は main のまま」）。移らなかったときの今のブランチは**機械の行の末尾の括弧から写す**。推測で main と書かない。手元の 1 文を書くのは、機械が「ブランチ」の行か「手元のブランチ」の節を出したときだけ
- **`turn`（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。`headline` に出した別の番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。機械の「上に積む」があれば、この PR を base にしている PR として番号と誰のものかを 1 文（この PR が止まると一緒に止まる）。CI は落ちた本数と中身の箇所数を分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・CI の本数・返事待ちの指摘の件数は、止めているものの行に機械が出すので書かない。書くのは、そのうちどれが効いていて、原因は何か。止めているものが無いなら、無いことが分かるように
- **`next`（次にやること）**: 1 項に 1 つの動作。**空にしない**——待ちなら、何を待ち、動いたら何をするか。私が入っていない PR で待ちなら「依頼が来たら本文と変更を読む」「レビューを返す」と来た場合を並べ、来ない場合を最後の項に「来なければこの PR で私が動くことは無い」と言い切る。機械がブランチに移らなかったときはその一手を先頭に——**機械の行が `→` で一手を書いていればその後ろをそのまま写す**（文言は機械が状況で変える。自分で組み立てない）。別の worktree なら「<path> で続ける」。手元に無いだけなら機械が origin から取って移るので `gh pr checkout` を書き足さない。一手が「依頼先を決める」なら、機械の「依頼先の候補」を括弧で添えてよい（候補の名前と機械が付けた理由のまま）。「X に依頼を出す」とは書かない（決めるのは私）。ページは、先頭の項が「前回から」の commit の sha を含めば「差分へ」、返信・会話・指摘の語を含む最初の項に「指摘へ」、CI・赤の語を含む最初の項に「CI へ」の飛び先を付ける
- **`unseen`（見ていないもの）**: 機械の申告（上限で切れた分・GitHub の外・結び付いていない commit・痕跡の基準が近似）はページの末尾に機械が並べる。AI が足すのは、機械が言っていない穴だけ——確かめようとして確かめられなかったこと（読めなかった CI のログ・引けなかった別の番号）、会話の要約で消えた分。機械が数で出しているもの（未解決の件数・CI の本数・承認の数）は見ている——書かない
- **`explain`（説明。本文か差分が有るとき）**: この件が何のために・何を・どう変えるかを、この件も周辺の部品も知らない人に。上の欄も差分も「なぜ」を言わない（28 file の PR で型と木だけ出したら「内容が初見に分かりづらい」と言われた実測）。段落は 3 つでこの順——1. **背景と課題**（この変更の前はどうで、何が困っていたか。扱う部品を、読む人が知らない前提で名指す）2. **何をどう変えるか**（「変更前 → 変更後」で、部品を役割で名指して。file が多ければ末尾に 1 文、役割ごとの file 数と残りが何の追随か）3. **使う側から見た変化と、含まれないもの**（既定値・移行や設定の要否・作者が「含まれない」と書いたもの）。全体は **200〜800 字**——物差しは差分の規模（file 数）と本文の密度の大きい方（1 file・本文の中身 10 行以内なら 200 字、10 行超なら 400 字前後、20 行超か 15 file なら 740 字、28 file でも 800 字まで）。言葉は作者のもの（本文・先頭コメント・commit の題の語）。この件の中でしか通じない名前は初出で「中身 → 記号」。**path・設定の key・関数名・引数名は入れない**（変更の節の仕事）。評価語を入れない。状態と経緯は書かない（上の欄の仕事）。本文が薄い（無い・1 行だけ）なら、その旨を 1 文書いてから `gh pr diff`（commit は `git show`）で分かることを事実で書く。先頭コメントが「8 行で切った」と言っていれば、切れた文を作者の言葉として写さず全文を見る。書けたら自分に問え——**この件を知らない人が、ここだけ読んで「何のために・何を・どう変えるか」を自分の言葉で言えるか**
- **`figure`（図。説明の上に描かれる）**: 部品が 2 つ以上あって関係（呼ぶ・渡す・分岐する・前後で入れ替わる）が言えるなら**極力描く**——一直線の鎖でも描く。読み飛ばすかは読む人が決める（実測: 経路が 2 本になる変更を「1 文で言える」と見て描かず、なぜ無いのかと聞かれた）。形は行（`rows`）ごとに箱（`steps`）を左から矢印で繋ぐ鎖で、変更前と変更後を上下の 2 行に（前後が無い形なら 1 行）。変わった箱に `tone`（悪かった所は `bad`、良くした所は `good`）、箱の下の補足は `notes`（`at` はその行の箱の番号、0 から）。**ラベルは `explain` で付けた役割の語と作者の語だけ**、関係は機械の「名前の言及」か本文が言うものだけ（推測なら「（未確認）」）。図の名詞を全部、説明か本文の語に指で当てられないなら描かない。描かないのは部品が 1 つ・関係が無い（版の数字や台帳の追記だけ）・焦点で指摘か CI に絞ったとき
- 同じ番号を説明するのは 1 回、`turn` で。番号そのものは何度出てもよい

PR でないとき（欄ごとの言い切り。材料が無いことは、無いと書く——「空にしない」と「断定しない」を両方満たす形）:

- **枝に PR 無し**（未コミット・push していない commit・既定ブランチより先の commit のどれかが有るとき。どれも無ければ受け口の推定か聞き返し）: `headline` は「今のブランチ main に PR は無く、名前にも番号が無い」。`turn` は「GitHub 側は見ていない」と断って、手元の事実（未コミット・push していない commit・PR が無いこと）。`next` は手元から決まる一手（push する・PR を立てる・書きかけを続ける）
- **commit**: 作者が私かは機械の名前でなく `git show -s --format=%ae <sha>` と `git config user.email` の一致で決める（違えば作者の名前で）。枝は `HEAD~n` なら今の枝、sha なら `git branch --contains <sha>` を 1 回。`headline` は「2971ea2 は 9/6 に私が作った commit で、いま居る枝 main に入っている（PR を経たかは見ていない）。動かすものは無い」——「済み」とは言わない。`where` に手元の 1 文は書かない（枝の名前が無い）。`turn` は「GitHub 側も手元の未コミットも見ていない」と断り、止めているものは無いと書く。`next` は「PR が有るなら番号で呼び直す」「前後を読むなら HEAD / HEAD~n で呼ぶ」「手元は引数なしで呼ぶ」。範囲 `A..B` は「e824033 から b27cb3d までの commit 4 件は 9/6 に私が main に入れた」と、機械の見出しの括弧（含まれる両端）で言い切る（A は範囲の外なので 4 件の 1 つとして書かない）
- **会話から推定した番号**: `headline` の直後に「今のブランチ main には PR も名前の番号も無く、会話に出ていた #N を出している」を 1 文。手元の 1 文は、最初の `this` の手元の節から書く（絶対名。その枝に移していないことも）

## 会話の話題（番号でも commit でも枝でもない語で呼ばれたとき）

受け口で番号・枝・commit に解けた話題はここではない（その対象の形で全部出す）。会話の中にしか無い話題（レビューで見つけた指摘の束・検討中の案）は、材料を `-` にして描く: `catchup.py --render - <欄の JSON>`（欄の JSON は一時の階層に置く。置き場は `~/.cache/attention/catchup/topics/` で、`title` ごとに 1 枚）。欄は同じで、`title` に話題の名前（読む人の語）を足す。`headline` は「「新しく出たもの」は #1505 の再レビューで私が見つけた suggest 4 件で、まだ PR には書いていない」のように**話題が何かを言い切る**。材料は会話そのもので、要約で前半が消えていれば `what-am-i-doing.py --topic` の往復で補う。結び付いた番号があれば、その番号の機械の出力で「PR に書いたか・相手が動いたか」を確かめる。会話に無いことは書かず、会話の中で確かめていないことは「（未確認）」。引数なしから会話で番号を推定したときは違う（受け口——番号で呼ばれたときと同じ形）。

## 準備（`/catchup setup`）

ページは VS Code の Remote-SSH の窓で、拡張 Simple HTML Viewer が開く。準備は `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py --setup` 1 本で、機械が次をする:

1. 生きている VS Code の窓を探す（`code --status` が通る socket）
2. 拡張が `~/.vscode-server/extensions` に無ければ `code --install-extension austin-spagnolo.simple-html-viewer` で入れる
3. `~/.vscode-server/data/Machine/settings.json` に 2 つを足す——`workbench.editorAssociations` の `"**/.cache/attention/**/*.html": "simpleHtmlViewer.preview"` と `"simpleHtmlViewer.autoRefresh": "onFileChange"`。他の key は消さず、書く前に同じ階層へ控え（`settings.json.bak-<日時>`）を置く。注記（`//`）の有る file は書き直さず、足す行を示す
4. 見本のページを描いて開く
5. したことと、まだ足りないものを並べる

`/catchup setup` と打たれたら、これを走らせて出力をそのまま返す。何も変えずに確かめるだけなら `--setup --check`。窓が繋がっていない（VS Code を閉じている）と拡張は入れられない——繋いでからもう一度と返す。

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・直訳横文字、この件の中でしか通じない略号、機械の理由文（「私の件に相手の発言があり…」）の丸写し（確かめた結果を書く）、「〜と思われる」「〜のようだ」（確かめていないことは「（未確認）」と付けて書く）
- **この命令書の語を欄に持ち込まない**——材料・機械・型・欄・焦点・スクリプト。ページの節の名前（指摘・CI・変更・手元）は指してよい（「下の指摘 3 件」）。本文（PR の説明文）は普通の語として使ってよい。機械が script 名（what-am-i-doing.py・catchup.py）で書いた口は `/what-am-i-doing`・`/catchup` の呼び名に置き換える
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）。書けたら自分に問え——**`headline` だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか**

## 守ること

- **求められていないのに欠陥探しへ広げるな。** 説明は読む人の理解のためで、レビューを始める合図ではない
- **出力に無いことを断定するな。** 確かめたなら確かめた結果を書く。推測で埋めるな
- **図のラベルを記憶で書くな。** 説明か本文に無い語が要るなら描かない
- **端末にページの中身を書き足すな。** 返すのはページの path と 1 行の要約だけ（ページを開けば全部ある）
- **番号でない語で呼ばれても、質問で返すな。** 会話の話題として描く。例外は受け口の 1 か所（手元にも会話にも対象が無いとき）だけで、その形も受け口に
- **機械がブランチに移らなかったとき、自分で stash・commit・`git switch` を打つな。** 未コミットは別のセッションが編集中の木かもしれない（同じ checkout を複数のセッションで共有していることがある）。理由と一手を `next` に書くだけ。移った後に、移る前に読んだ file を編集するなら読み直す——中身は移った先の枝のもの。PR の commit が手元に無いときも `git fetch` を打たない
- **subagent・Agent・Workflow を立てるな。** `gh` は Bash で直列に呼ぶ。並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる
- **描く材料の JSON を手で直すな。** 事実が違っていれば、機械を呼び直す
- **例の一覧を許可の一覧と読まない。** 文言・場面の例は書き方の一つで、例に無いものも規則に当たれば書く
- 日付・件数は機械の数字をそのまま使う（今日から日数を数えるのは、`where` の「N 日前」の 1 か所だけ）
- open 全件の棚卸しはこの道具の仕事ではない。それは `/whose-turn`
