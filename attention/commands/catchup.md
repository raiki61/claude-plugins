## 受け口

`/catchup [対象] [焦点]`。対象と焦点を読んで、機械の呼び方を決める。

- **番号か URL** → `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py --switch <番号または URL>`。番号だけなら
  カレントのリポジトリを見る。`--switch` で、該当ブランチ（PR は head のブランチ、issue は名前に番号を持つ
  手元のブランチが 1 本のとき）へ機械が `git switch` で移る——戻るとき、会話の位置と一緒に手元の枝も
  失われている。PR の枝が手元に無ければ、機械が origin からその 1 本だけ fetch して作って移る（名前と追跡先は
  `gh pr checkout` と同じ）。移った・移らなかった理由は見出しの URL の下の「ブランチ」の行に出る（追跡ファイルに
  未コミットがある・別の worktree に checkout 済み・origin にももう無い・fork の枝で照合できない、など。
  移らなかった行の末尾に今どこに居るかが付く）。移った、または既に居たときは末尾に「手元のブランチ」の節が
  付く。機械が手元を変えるのはこの `git switch` とその 1 本の fetch だけで、手元にある枝は動かさない
  （pull・stash・commit・`gh pr checkout` はしない）
- **引数なし・`this`** → `catchup.py this`。**焦点の語だけ**（`/catchup 指摘`）→ `catchup.py 指摘`（対象は
  同じく今のブランチに落ち、末尾はその語の材料だけ）。今のブランチの PR。無ければブランチ名の番号
  （`chore/1513-…` → #1513）を issue として出し、その旨を機械が 1 行書く。どちらでも末尾に「手元のブランチ」
  （push していない commit・未コミットの木）が付く。PR も番号も無ければ機械が止まるので、番号を聞く
- **焦点の語（`指摘`・`地図`・`CI`）** → 対象の後ろにそのまま渡す（`catchup.py --switch 1569 指摘`）。末尾の材料は
  **有れば全部出る**——地図は PR なら常に、指摘は人が入っている未解決スレッドが有れば、CI は赤が有れば。
  作者が私かどうかでは出し分けない（この道具を呼ぶこと自体が、自分の PR でも中身を忘れている印）。
  焦点はその 1 つに**絞る**口で、急ぐときに使う。絞った材料が無ければ機械が「無い」と 1 行書く
- **それ以外の語**（`新しく出たもの`・`さっきの 4 件` など、会話の中にしか無い話題）→ catchup.py は
  走らせない（番号でないので弾かれる）。`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/what-am-i-doing.py --topic "<語句>"`
  でその語句が出た往復を取る——語句は 1 つ（引用符で括る。複数の語は続けた 1 句として当たる。0 件なら
  肝の 1 語か言い換えでもう 1 回）——、会話を主な材料にして、下の「会話の話題」の形で書く。話題が会話の中で
  番号に結び付いていれば（#1505 のように出ている）、その番号で catchup.py も走らせて「PR に書いたか・相手が
  動いたか」を機械の事実で補う（この呼び出しには `--switch` を付けない——話題を追う補いで、その PR に
  戻る呼び方ではない）。**質問で返さない**——「それは何で・どこまで進んで・次に何をするか」を
  型で出す（実測: 弾かれて「どうしたいか」を聞き返した返答は、追いつく役に立たなかった）

## 役割分担

- **スクリプト（機械）**: 私の最後の痕跡・私宛の依頼・その後の出来事・状態を全部出す。判断はしない。
  末尾の先頭に作者の本文（と閉じる issue の本文の冒頭）を、行を変えずに出す
- **あなた（AI）**: 材料を読み、足りないもの（CI の理由・依頼が済んでいるか）を確かめて、
  下の**型**に畳み、PR なら**説明**を書く。**機械の出力は貼らない**——全文を求められたときだけ、1 文字も
  変えずコードブロックで貼る
- 機械は末尾に、まず**本文**（作者の言葉。どの呼び方でも）、次に**コードで見せる材料**を有るものだけ
  この順で付ける（指摘＝スレッドごとの相手の発言
  （40 行まで。超えた分は機械がその旨を出す）と head のその行の前後、CI＝落ちた step のログの末尾
  （行頭の job・step・時刻と色の印は落としてある）、地図＝置き場所・骨組み・配線。地図と指摘の行は
  1 文字も変えていない）。あなたはそこから**選んで並べ**、下の**箇所**の形にする。散文は自分で書くが、
  コードの行は写すだけ

## やること

1. 受け口のとおりに機械を呼ぶ。
2. **本文を読む**: 機械の末尾「本文（材料）」に作者の本文（60 行まで）と、閉じる issue の本文の冒頭が
   ある。本文が # で指す issue / PR の冒頭も 3 件まで。件名（型の 1 段落目）と**説明**の材料。上限で切れていれば `gh pr view <番号> --json body -q .body`
   で全文を読む（issue なら `gh issue view`）。読んだら、機械の「本文の残り N 行」は見ていないものに
   写さない——もう見ている。
3. 機械の出力に次があれば、**書く前に確かめる**（確かめずに機械の言葉を写すと、答えが逆になる——
   実測: 済んでいる申し送りを「相手の発言があり私は発言していない」のまま写して、初見の読み手が
   「未対応の問い合わせが残っている」と読んだ）:
   - `CI: 赤` — 末尾の「CI が落ちた理由（材料）」で**落ちた理由**を読む（赤が有れば機械が付けている。
     焦点で他に絞って CI の材料が付いていなければ `catchup.py <番号> CI` で呼び直す。`--switch` は要らない）。「次にやること」はこれ次第。読めなかった
     チェック（Actions の run でない等）は URL を開く
   - `（名指しは無い。私の件への発言）` — その発言が私への依頼か、私の push で**既に済んでいないか**を
     本文と差分で確かめる。機械は push を返事と数えない
   - 止めている原因が別の PR / issue にあるなら、その番号の**誰の番か**を 1 回引く
     （`gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt`）。「未承認」だけでは
     読む人が「今日動くべきか」を決められない
4. 型に畳んで出す。型の中に足してよいのは、型だけでは「次にやること」を読んだ人が実行できない
   ときの「変更前 → 変更後」の数行だけ（差分の全文ではない）。PR の内容は型に詰めず、次の説明で。
5. 型の後ろに、まず**説明**（PR で地図を付けるとき。下の「説明」の節）、次に機械が出した材料の節を
   **全部、機械と同じ順で**付ける——**指摘**（人が入っている未解決
   スレッドがあるとき。機械の「未解決スレッド: N 件（うち人が入っているもの n 件）」の n がそれ）、
   **CI**（赤があるとき）、**地図**（PR なら常に）。作者が私かどうかで落とさない（実測: 自分の PR で
   木が出ず、欲しかった）。焦点の語で呼んだときは、その節だけ。
   機械が「手元のブランチ」の節を出したとき（`this` で呼んだ、または `--switch` で移った・既に居た）は、
   push していない commit と未コミットの件数（PR の head より後ろならその数も）を型の 2 段落目に 1 文で
   言い、未コミットの木があれば末尾に ```diff の枠でそのまま貼る（無ければ書かない）。
6. `--switch` を付けて呼んだときは、見出しの「ブランチ」の行を読み、**手元がいまどのブランチに居るか**を
   型の 2 段落目に 1 文で言う（下の型の 2 段落目）。移らなかった理由が「未コミット」なら、自分で stash・
   commit・`git switch` を打たない——その未コミットは別のセッションが編集中の木かもしれない。「次にやること」
   に書くだけ。

## 型

**同僚に口で話すときの散文**で、**太字の 1〜2 文で始める**。段落の順は固定で、段落は短く。
コードブロック・表・ラベル列を使わない——等幅の枠に並んだラベル列は「機械の出力」に見えて、
読む前に構える（実測: 本人が「読む気が失せる」）。下の例は書き方の一つで、文言を写す型ではない
——決まった言い回しは場面に関係なく毎回出て雑音になる。

```
**[#1276](https://github.com/o/r/pull/1276)（現場コネクタの要件の下書き）は私の PR で、
動かすのは私のもう 1 本の PR #1596 の側です。#1596 にレビュー依頼を出せば進みます。** 現場コネクタ（工場の設備と
繋ぐ部品）に何が要るかを docs/_draft/ に書き出した下書きです。

最後に触ったのは 2 日前（9/1）で、main を取り込んで push しました。その後は
誰も動いていません。8/27 に 250489 さんから「lint の新しい規則に合わせて 1 行
直して」と申し送りが来ていましたが、9/1 の取り込みで済んでいます。返信は
要りません。手元は main から docs/1276-connector に移しました（push していない
commit も未コミットもありません）。

止めているのは CI の赤 3 本で、全部同じ文書検査です。中身は docs/_draft/ の
ADR 参照 10 か所で、下書きを規則の対象から外す #1596（私の PR、レビュー依頼が
未送）が通れば消えます。承認はまだ無く、衝突も未解決スレッドもありません。

次は、#1596 のレビュー依頼を出す → 通ったら main を取り込み直す → 緑を確認 →
#1276 のレビュー依頼先を決める。

見ていないのは、この PR の古い方のコミット 43 件（私の痕跡があれば見落とし
ます）と、GitHub の外のやり取りです。下の地図の 3 file は私が選んだもので、残りは
末尾に一言だけです。
```

- **1 段落目（太字）**: `[#番号](URL)（件名）` と立場、**どこで止まっているか**を確かめた結果で。
  URL は機械の見出しの下の行から写す（対応する端末では番号だけが表示されてクリックで開ける）。
  他の番号は `#番号` のまま——機械がその URL を出していないので、組み立てない。機械の
  「私の番」を写さない。止まり方は 3 つのどれかで、それを進める一手を添える——私が動かせる／
  別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと
  他人の PR 待ちに読まれる。実測）。誰の番でもない（レビュー依頼が誰にも出ていない等）なら、
  渡す先を決めるのが私だと分かるように。
  件名は機械のタイトルから型の接頭辞と括弧書きを落とした**全角 12 字以内**の名詞句。
  **ここだけ読んで用が足りるように書く**
- **太字の後ろに、同じ段落で「何をする PR か」を 1〜2 文**（太字にしない。作者を問わない）: 本文の
  冒頭か、機械の地図にある作者の先頭コメントの言葉で。戻るとき「何の PR か」も失われている（実測:
  型だけ出したら次の問いが「内容は」だった）。段落は増やさない——5 つが上限際。ここは名指しで、
  内容の説明は後ろの「説明」の節。1〜2 文で足りない分をここに詰めない
- **2 段落目（最後にしたこと）**: `N 日前（M/D）` に何をしたか。**その後の動きを同じ段落に続ける**
  ——誰も動いていないならその旨、誰かが動いたなら誰が何をしたか。**人は名前で**
  （「相手」と書くと、レビュー依頼を出していない件で「相手が誰か」で止まる——実測）。私宛の依頼が
  あれば、いつ誰から何が来て、済んでいるか未対応かを書く。未対応なら次の一手の先頭。
  **`--switch` で呼んだときは、この段落の末尾に手元の位置を 1 文**——今のブランチを絶対名で（移った先だけ
  名指すと、移らなかったとき読む人は今どこに居るか知らないまま編集に入る）。5 通り: 「手元は main から
  feat/123-x に移しました」／「手元に feat/123-x は無かったので origin から取り、main から移しました」／
  「手元は feat/123-x に居ます」／「手元は main のままです（手元に未コミット 3 件があるので feat/123-x へ
  移していません）」／「手元に feat/123-x は無く、origin にももうありません（PR は merge 済み）。手元は
  main のままです」。**移らなかったときの今のブランチは、機械の行の末尾の括弧から写す**——移らなかった行には
  必ず付く（「（手元は … のまま）」、読めなければ「（手元の位置は読めない）」、git の外なら「（手元に git の
  checkout が無い）」）。推測で main と書かない（実測: 別の枝に居るのに「手元は main のままです」と報告した）。
  `this` のときの push・未コミットの件数の 1 文と同じ場所で、字数は増やさない
- **3 段落目（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。1 段落目に出した別の
  番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。CI は落ちた本数と中身の箇所数を
  分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・未解決スレッドの観測値を
  末尾に 1 文。止めているものが無いなら、無いことが分かるように
- **4 段落目（次にやること）**: 動作を `→` で繋ぐ。番号は書くだけで説明しない。空にしない——
  待ちなら、何を待ち、動いたら何をするか。機械がブランチに移らなかったときはその一手を先頭に——
  **機械の行が `→` で一手を書いているときは、その後ろをそのまま写す**（未コミット・origin にももう無い・
  fork で照合できない、はどれも機械が一手を持っている。自分で組み立てない——文言は機械が状況で変える）。
  別の worktree なら「<path> で続ける」。手元に無いだけなら機械が origin から取って移るので、`gh pr checkout` を
  自分で書き足さない。移ったときは switch を書かない
- **最後の 1 行（見ていないもの）**: この報告が見ていない範囲だと分かる 1 行。機械の末尾から、この件に
  固有のもの（上限で切れた分・結び付いていない commit）と GitHub の外を挙げ、それぞれ何を見落としうるかを
  添える。削らない。地図の節を付けるときは「下の地図の N file は私が選んだもので、残りは末尾に一言だけ」も足す
- **全体で 12 行前後、350 字前後（後ろの節を除く）。** 段落は 4 文以内。**文体は です・ます**
- **同じ番号を説明するのは 1 回、「止めているもの」で**。番号そのものは何度出てもよい

## 説明（PR のとき。焦点で指摘か CI に絞ったときは付けない）

型の後ろ、材料の節の前に `## 説明` の見出しで、**この PR が何のために・何を・どう変えるか**を、
この PR も周辺の部品も知らない人に口で話す散文で書く。型の 1 段落目の 1〜2 文は「何の件か」の
名指しで、内容の説明ではない。木と箇所も説明の代わりにならない——木は置き場所、箇所は実物の行で、
どちらも「なぜ」を言わない（実測: 28 file +1030 行の PR で、型の 1〜2 文と地図の 1 文だけでは
「新版とは何か・なぜ権限の縮小が同じ PR に入るか・2 経路とは何か」が読めず、本人が「内容自体が
どんななのか初見にわかりづらい」と言った）。

材料は機械の「本文（材料）」（作者の本文、閉じる issue と本文が # で指す issue / PR の冒頭）と、地図の
先頭コメント・docstring・既存ファイルの変更の枠。背景は Closes の無い参照先（「あわせて #1105」）に書いてあることが多く、
機械は 3 件まで引く。それより多ければ `gh issue view <番号>` で読む。本文が薄い（無い・1 行だけ）なら、
その旨を 1 文書いてから `gh pr diff` で分かることを事実で書く。機械の先頭コメントが「8 行で切った」と
言っていれば、切れた文を作者の言葉として写さず、`gh pr diff` で全文を見る。

段落は 3 つで、この順。段落は 4 文以内。全体は **200〜800 字**で、PR の規模に合わせる——1 file +2 行の
PR なら 200 字、15 file なら 740 字（下の例）、28 file でも 800 字まで（実測: 上限を「行」で書いたら、
改行無しの 2000 字が出た。字で数える）。長くなるのは path と括弧を並べたときで、それは下の箇所の仕事:

1. **背景と課題** — この変更の前はどうで、何が困っていた（何が要った）か。閉じる issue が
   あればその題名と本文の冒頭から、作者が本文に「なぜ」を書いていればその言葉で。この PR が
   扱う部品が何か（「検索 MCP サーバの新版」のように）を、読む人が知らない前提で名指す
2. **何をどう変えるか** — 「変更前 → 変更後」で。仕組みを、部品を役割で名指して言う（chart の
   受け口・CI の描画検査・権限の terraform）。ここで付けた役割の語を、下の木と箇所の見出しの下の
   1 行でそのまま使う——説明と木を同じ語で繋ぐ。複数の変更が 1 つの PR に入っているなら 1 つずつ
   1〜2 文と、なぜ同じ PR かを作者が書いていればその理由。file が多い PR は段落の末尾に 1 文、
   役割ごとの file 数と、残りが何の追随か（「28 file のうち chart 6・CI 3・terraform 2。残る 17 file は
   compose・手順書・設定例の追随」）——木で説明されない file が何かを、木の前に言う（実測: 無いと
   初見が 17 file の役を聞いた）
3. **使う側から見た変化と、含まれないもの** — マージすると誰の何が変わるか。既定値（「既定は
   無効で、有効にするまで何も描画されない」）、移行や設定の要否、作者が「この PR に含まれない」と
   書いたもの。使う側の変化が無いなら、無いと分かる 1 文で終える

- **言葉は作者のもの**——本文・先頭コメント・commit の題の語で書く。製品名・標準仕様（Helm・
  terraform・K8s）はそのまま。このリポジトリの部品（MCP サーバ・backend・テナント）は初出で製品での
  役割を 1 句（「文書を検索する MCP サーバ」）。この PR の中でしか通じない名前（部品名・ジョブ名・
  テナント名・ラベル名）は初出で「中身 → 記号」（「検索 MCP サーバの新版（contents-search-revised）」）。
  逆（「research-loop（調査の手順書）」）にしない——記号を先に見た人は括弧を読む前に止まる。中身が
  言えない名前は出さない
- **path・設定の key・関数名・引数名は説明に入れない**——それは箇所の見出しと `#` 注釈の仕事。
  説明に出る記号は部品の名前だけ——作者が本文でその名で呼ぶ仕組み（blobDataSync・dataVolume・
  standing.sh）は部品の名前で、その置き場所（`deploy/standing/values.yaml`・`mcpServers.<name>.dataVolume`）
  は path。括弧は 1 文に 1 つまで（実測: 28 file の PR で path と key を括弧に
  並べた説明は 2000 字になり、初見 2 人が言い直しは正確なのに「分からない語」を 15 個挙げた）
- **評価語を入れない**（妥当・きれい・良い）。diff から読んだ機構は「〜している」の事実で書く。

- **状態と経緯は書かない**——承認・CI・衝突・誰が何を言ったかは型の仕事。ここは PR が main に
  入ったときの姿だけ。型の文を繰り返さない

書けたら自分に問え——**この PR を知らない人が、ここだけ読んで「何のために・何を・どう変えるか」を
自分の言葉で言えるか。木の各 file が何の役か、説明の語で言えるか。path が 1 つでも入っていないか。
固有名を全部拾って、初出に中身が付いているか（実測: 800 字に収めた説明でも「docs ロール」「雛形」が
中身なしで残った）。**

## 箇所（コードで見せる共通の形）

地図の file ごとの節、指摘の 1 件、会話の話題の 1 項目は、**同じ形**で書く。engineer にはコードの
行そのものが散文より早い——散文は翻訳で、読む側が頭の中でコードに戻す往復が要る。IDE が読み
やすいのは色だけでなく 3 つの約束を守っているからで、ここでも守る: **案内（木）と読む場所
（file の中身）を混ぜない。書いてあるものは作者の言葉で見せる（file 名・step 名・docstring・先頭
コメント・指摘した人の文）。記号は誰もが知っているものだけ（path・+/−・字下げ・行番号。木の `~` だけは
地図の印）。**

**この節だけはコードブロックを使う**（型の「コードブロック・表を使わない」の例外）。言語名を
付けると端末が色を付ける（yaml / bash / python / diff / json / dockerfile / asciidoc。無い言語は
plaintext になるだけ）。

- 境目は罫線 `---` 1 本。見出しは太字で `n/N path`（地図なら（新規／既存に追記）、指摘なら
  `path:行`（指摘 n））
- その下に 1 行——地図なら**どこから使われるか**、指摘なら**誰が何を求めているか**を、その人の言葉で。
  評価語は入れない。地図の file には、説明で付けた役割の語を添える（「chart の受け口」のように）——
  説明と木を同じ語で繋ぐ
- **変更は、機械が帯を入れた「今の姿」をそのまま貼る**（地図の「既存ファイルの変更」、会話の話題の
  「変更の中身」）。言語名の枠（```python 等）に `| ` の後ろを 1 文字も変えず写す。読み方は 1 つ——
  実線の枠 `┏ … ┗` の中が変わった所で、行頭が `#│`（その言語のコメント記号に `│`）の薄い行は前、
  色の行は今（コメント記号だけの行は今足したコメント）。追加は今だけ、削除は前だけ、変更は前の下に今。
  間 3 行以内の変更は 1 枠にまとめてあり、挟まった変わっていない行の数は帯に書いてある。点線 `┅` は
  畳んだ区間（長い関数の変わっていない所・多すぎる前の行）。unified diff は貼らない——patch の形式で、`@@` は人に意味が無く、`+`/`-` は構文の色を
  消す（実測: 「機械がわかりやすい形。人間もそうか」「色が重要」）。帯は機械が置くので、自分で
  注釈を足したり削ったりしない（実測: 手で置くとずれた）。同じ行が消えて別の所に足された（移動）
  のは機械には分からないので、見出し下の 1 文で言う
- 枠には実物の行だけ。機械の `| ` の後ろか、`gh pr diff` か、head の file から**写す**。記憶で書かない。
  **注釈は行の上に `#` で** `# path:行（役割）` の形。右に日本語を置かない（折り返した瞬間に行の形が
  壊れる）

- 指摘なら、枠のあとに**「直すなら」を 1 文**か、変更前 → 変更後の数行。相手の修正案があればそれを

- 作者の言葉（先頭コメント・docstring）が無い file は骨組みだけ出し、説明を足さない。機械に中身が無い

## 指摘（人が入っている未解決スレッドがあるとき、または `指摘` を付けたとき）

型の後ろに、**私が返す番の指摘を 1 件ずつ**「箇所」で見せる。戻るとき失われているものの 1 つが
**何を言われて、どこで止まっているか**——自分の PR でも、レビューで渡された PR で作者が返してきた件でも。
材料は機械の末尾「指摘（材料）」——スレッドごとに、相手の最後の発言（40 行まで）、`← 私が返す番` か
`← 私が最後に発言している（相手の番）` の印、head のその行の前後（`| 行番号 行`）。

順に 3 つ。

1. **道順**を 1 文——「未解決 N 件。[block] n・[suggest] n・[nit] n で、私が返す番は n」（印は発言の
   先頭の語と機械の `←` から数える。無ければ数えない）。[block] を先に並べる
2. **件ごとの箇所**（`← 私が返す番` の件だけ。見出しの N はその数）: 見出し `n/N path:行`（指摘 n）→
   1 行「250489 さんが求めているのは …」を相手の言葉で（`[block]`・`私が返す番` を括弧で添える）→
   枠に head の行を機械の `| ` から写す（指摘の行を含む意味のある単位——関数なら def から。機械の前後
   5 行で足りなければ `gh api` か手元の head から足す。注釈 `# path:行` を上に。行番号は
   残す）→ **直すなら** 1 文（相手の修正案があればそれを写す。無ければ書かない）
3. **末尾に 1 文**——`← 私が最後に発言している（相手の番）` の件は、path と行の名前だけ並べる

**守ること**: 指摘が妥当かの判断は書かない——求められたら別に確かめて答える。相手の発言を要約せず、
求めている中身はその人の語で写す。機械が「行: 今の head に無い」「行 N は head のファイルの外」と言う
件は、行を出さずにその旨を書く。

## CI（赤があるとき、または `CI` を付けたとき）

型の後ろに、**落ちたチェックを 1 件ずつ**「箇所」で見せる。材料は機械の末尾「CI が落ちた理由（材料）」
——チェックごとに、失敗した step のログを最後の `##[error]` まで（`| ` の後ろ。行頭の印と時刻は
機械が落としてある）。見出し `n/N チェック名`、その下に 1 行——最後の `##[error]` の文をそのまま。
枠は ```plaintext に機械の `| ` の行から、落ちた理由が読める 3〜15 行。「直すなら」は書かない
（原因の判断は型の 3 段落目で）。ログを取れなかったチェックは、URL を書いて「ログは取れなかった」と 1 文。

## 地図（PR のとき。焦点で他に絞ったときは付けない）

説明の後ろに、**この PR が全体のどこに何を足すか**を、木と実コードで見せる。端末には IDE の 2 つの窓が
無いので、順番で代える——上に木、下に file ごとの箇所。

材料は機械の末尾「変更の地図（材料）」——規模、変更ファイル、同じ階層の既存、変更ファイルの木、
名前の言及（当たった行つき）、新規ファイルの先頭と骨組み、既存ファイルの変更。**そこに無い行が
要るときは `gh pr diff <番号>` の実物から写す**（file ごとの絞り込みは無いので、`diff --git` の
見出しで該当 file の範囲を探す）。

順に 4 つ。

1. **変更ファイルの木**（```diff）。機械の「変更ファイルの木」を**そのまま**貼る（周辺の既存は
   機械が名前の近い順に数件と「… ほか N」で並べ、新規は行頭 `+`、変更は `~`、削除は `-`）。
   組み直さない、**私の言葉を書かない**。木の前に 1 文——規模（機械の「規模」の数字）。
   周辺の何が何かを書けるのは、変更の枠か先頭コメントにその名前が出ている file だけ。手元がその
   checkout でないと木は変更 file だけになる。それでよい
2. **道順**を 1 文——「入口 → そこから呼ばれる検査 → 渡す設定 → 既存への配線の順に N file」。
   部品は説明で付けた役割の語で。作者の印（先頭コメントの (a)(b) など）があればここで導入する
3. **file ごとの箇所**を 3〜6 つ（上の「箇所」の形）。「どこから使われるか」は、機械の「名前の言及」の
   下の行が `uses:`・`run:`・`-f`・import のようなコードの行なら関係として書く。コメント行の言及は
   関係に数えない。道具が既定の名前で読む file（docker-bake.hcl・Dockerfile・.tool-versions など）は
   名前が行に出ないので、読む側のコマンド行（`docker buildx bake` など）を関係にする。中身は
   - 新規: 先頭コメントか docstring（作者の自己紹介）→ 骨組み（step 名・def・上位 key）→ 肝の
     数行（作者が先頭コメントで名指した箇所か、名前の言及で当たった行）。ワークフローの step 一覧には、
     その step が使う file を `#` で添える（名前の言及の行か `gh pr diff` の run: 行で確かめたものだけ。
     これが流れの図の代わり。図は描かない）。入口の節は step 一覧を切らず、先頭コメントは主張の行だけ、
     `on:` は契機の行だけ、permissions・concurrency・defaults は落とす
   - 既存: 機械の「既存ファイルの変更」の枠（今の姿に帯）を、関数ごとにそのまま。上限で切れた
     続きは `catchup.py <番号> --frame <path>`
4. **残りの file** を末尾に 1 文——名前と ±行数と、機械の先頭コメントにあればその 1 句。無ければ
   名前だけ

**選び方**: 入口（`on:` を持つワークフローのように、他の変更 file を `uses:`・`run:`・`-f` で使い、
自分は他から使われない file）→ 入口が使う file（既存なら機械の枠を関数ごと。上限で切れた分は
`--frame`）→ 既存への小さな追記。入口が使わない大きな既存の追記（README や台帳）は末尾の 1 文へ。
入口が使わない新規 file（テストなど）は、使われる側の節の「どこから使われるか」で触れ、末尾の 1 文にも
名前を入れる。材料の合計の目安と、超えたときに何から落とすかは「箇所」の規則（300 行前後、鎖の末端の
helper から）に従う。

## 会話の話題（番号でない語で呼ばれたとき）

会話の中にしか無い話題（レビューで見つけた指摘の束・検討中の案）を、**型と同じ 5 段落**で書く——
何か・最後にしたこと・止めているもの・次にやること・見ていないもの。1 段落目は「「新しく出たもの」は
#1505 の再レビューで私が見つけた suggest 4 件で、まだ PR には書いていません」のように、**話題が何かを
言い切る**。材料は会話そのもので、要約で前半が消えていれば `what-am-i-doing.py --topic` の往復で補う。
話題が番号に結び付いていれば、その番号の機械の出力で「PR に書いたか・相手が動いたか」を確かめる。
「やること」の 2〜3（本文を読む・CI 赤を確かめる）は結び付いた番号があるときだけ。その番号の説明・地図・指摘・CI の
節は付けない——後ろに付くのは、下の項目ごとの箇所だけ。

型の後ろに、まず**手元の木**——`what-am-i-doing.py` の「いま手元に残っているもの」に未コミットの木が
あれば、```diff の枠で**そのまま**貼る（`this` で呼んだときと同じ扱い。実測: 貼らずに出したら
「tree が出てない」と言われた）。無ければ書かない。

次に、読む順を 1 文（「main の配線 → switch_branch の本体 → tree_blocker の判定、の 3 関数」）と、
**関数ごとの箇所**（`n/N path  関数名`（変更／新規）＋ 1 文 ＋ 枠）。枠は `what-am-i-doing.py` の
「変更の中身」（関数まるごと、帯は機械が入れた）から、その関数の枠を `| ` の後ろごと言語名の枠に写す。
上限で切れていれば `what-am-i-doing.py --frame <path>`。手元の変更でない項目（既存の箇所を指すだけ）は
head か手元の file から関数ごと `sed -n` で写す。会話に無いことは書かず、会話の中で確かめていないことは
「（未確認）」と付ける。

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・
  直訳横文字、この件の中でしか通じない略号。機械の理由文（「私の件に相手の発言があり…」）を
  そのまま写すな——確かめた結果を書く。「〜と思われる」「〜のようだ」を使うな——確かめていない
  ことは「（未確認）」と付けて書く
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）

書けたら自分に問え——**2 行目だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか。** 説明は
**この PR を知らない人が、何のために・何を・どう変えるかを自分の言葉で言えるか。**

## 守ること

- **求められていないのに欠陥探しへ広げるな。** 説明は読む人の理解のためで、レビューを始める合図ではない
- **出力に無いことを断定するな。** 確かめたなら確かめた結果を書く。推測で埋めるな
- **箇所のコードを記憶で書くな。** 機械の `| ` の後ろ、`gh pr diff`、head の file から写す。写したものが
  実物と違えば、読む人は次に開いた file で裏切られる
- **番号でない語で呼ばれても、質問で返すな。** 会話の話題として型で出す。会話にも記録にも無ければ、
  無いと書いて番号を聞く
- **機械がブランチに移らなかったとき、自分で stash・commit・git switch を打つな。** 未コミットは別の
  セッションが編集中の木かもしれない（同じ checkout を複数のセッションで共有していることがある）。
  理由と一手を「次にやること」に書くだけ。移った後に、移る前に読んだ file を編集するなら読み直す——
  中身は移った先の枝のものに変わっている
- **subagent・Agent・Workflow を立てるな。** `gh` は Bash で直列に呼ぶ。地図や指摘で diff を読む仕事が
  増えても同じ——並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる（実測 2026-09-02）
- 日付・件数は機械の数字をそのまま使う
- open 全件の棚卸しはこの道具の仕事ではない。それは `/whose-turn`
