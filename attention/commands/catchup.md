## 一覧（仕様 `attention/docs/catchup-spec.md` の写し。数値の正本はそちら）

`/catchup [対象] [焦点]`。対象は 1 つ、焦点は 0〜3 語（`指摘`・`地図`・`CI`）。

| 対象 | 例 | 移る | GitHub | 主な材料 |
|---|---|---|---|---|
| 番号 | `1505` `#1505` | PR の head へ | 見る | PR / issue |
| URL | `https://…/pull/1505` | 同上 | 見る | PR / issue |
| ブランチ名 | `feat/123-x` | そこへ | 枝の PR が有れば | PR、無ければ手元 |
| 引数なし・`this`・焦点だけ | `/catchup` `/catchup 指摘` | 移らない | 今の枝の PR が有れば | PR、無ければ手元 |
| commit | `2971ea2` `HEAD~2` `v1.2` | 移らない | 見ない | その commit |
| 会話の話題 | `新しく出たもの` | 移らない | 結び付いた番号だけ | 会話 |

| 旗 | 効き | 効く対象 |
|---|---|---|
| `--switch` | 該当の枝へ移る | 番号・URL・ブランチ名 |
| `--full` | 本文・発言の上限を外す | 全部 |
| `--frame <path>` | その 1 file の変更を上限なしで | PR・commit（手元は what-am-i-doing.py の `--frame`） |
| `--limit N` | その後の出来事の件数（既定 12） | PR・issue |
| `-R owner/repo` | リポジトリを指す | 番号 |
| `--me <login>` | 「私」を差し替える | PR・issue |

返答の節（この順。付く条件を満たす節は全部付ける。作者が私かどうかで出し分けない。焦点の語で絞ったときは、型と、絞った節だけ——説明と絵は `地図` のときだけ付き、`## 手元` の節も付けない。型の 2 段落目の手元の 1 文は型の一部なので、焦点に関係なく書く）:

| # | 節 | 付く条件 | 上限 |
|---|---|---|---|
| 1 | 型 | 常に | 目安 12 行・450 字（上限ではない） |
| 2 | 説明 | 本文か差分が有る | 3 段落・200〜800 字 |
| 3 | 絵 | 部品 3 つ以上で並びが言葉で遠い | 1 図・60 桁・14 行 |

| 5 | CI | 赤が有る | 1 件ずつ・3〜15 行 |
| 6 | 地図 | 差分が有る | 箇所 3〜6（file が足りなければ有るだけ）・300 行前後 |
| 7 | 手元 | 手元の節を機械が出した | 木は全部 |

対象ごとに付く節（○ 付く／△ 材料が有れば／– 付かない）:

| 対象 | 型 | 説明 | 絵 | 指摘 | CI | 地図 | 手元 |
|---|---|---|---|---|---|---|---|
| PR | ○ | ○ | △ | △ | △ | ○ | ○ |
| issue | ○ | △ | – | – | – | – | ○ |
| 枝に PR 無し | ○ | △ | – | – | – | △ | ○ |

| 会話の話題 | ○ | – | – | – | – | – | △ |

上限と、続きを出す口。「切れた」は機械が数で言う——「N 行で切った」「上限 N 件」「古い方 N 件」「本文の残り N 行」。切れていればその口で取ってから書き、取ったものは見ていないものに書かない（もう見ている）。「--full で出る」「gh pr diff で見る」は切れた印ではない（扱いは型の最後の 1 行）。`--frame` は 1 file だけを出すので合計の上限は掛からない:

| 何 | 上限 | 続き |
|---|---|---|
| 作者の本文 | 60 行 | `--full` / `gh pr view` |
| 閉じる issue・参照先の冒頭 | 12 行 | `--full` / `gh issue view` |
| 閉じる issue・参照先の件数 | 3 件ずつ | `--full` |
| 相手の発言（スレッド） | 40 行 | `--full` |
| その後の出来事 | 12 件 | `--limit` |
| 変更の中身 1 file | 300 行 | `--frame <path>` |
| 変更の中身 合計 | 800 行 | `--frame <path>` |
| 取った commit | 100 本 | 見ていないものに書く |
| 指摘（スレッド）の件数 | 10 件 | `--full` |
| CI の赤の件数 | 3 件 | `--full` |
| 機械が置く帯の幅 | 78 桁 | なし（AI は触らない。60 桁の規則の外） |

| 何 | 今の値 | 足す口 |

## 受け口

機械は `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py`（以下 catchup.py）。`--switch` を付けるのは番号・URL・ブランチ名だけで、`this`・commit・会話の話題では付けない。

- **番号・URL・ブランチ名** → `catchup.py --switch <それ>`。番号だけならいま居るリポジトリ（別のリポジトリは URL か `-R owner/repo`）
- **引数なし・`this`・焦点の語だけ** → `catchup.py this`（`catchup.py 指摘` も同じで、対象は今のブランチに落ちる）
- **commit** → `catchup.py <それ>`。GitHub には何も聞かず、手元の git の commit として出る（題と本文、木、変更の中身。範囲は親との差 1 つ、merge は第 1 親との差）。PR を立てずに既定ブランチへ直接 commit する運用で、後から変更を読み直す口
- **会話の話題**（`新しく出たもの`・`さっきの 4 件` など、番号でも commit でも枝でもない語）→ catchup.py は走らせない（弾かれる）。`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/what-am-i-doing.py --topic "<語句>"` でその語句が出た往復を取る——語句は 1 つ（引用符で括る。複数の語は続けた 1 句として当たる。0 件なら肝の 1 語か言い換えでもう 1 回）。会話の中で番号に結び付いていれば（#1505 のように出ている）、`catchup.py <番号>` も走らせて「PR に書いたか・相手が動いたか」を機械の事実で補う（`--switch` は付けない——戻る呼び方ではない）
- **焦点の語** → 対象の後ろにそのまま（`catchup.py --switch 1569 指摘`）。末尾の材料をその 1 つ（複数可）に絞る、急ぐときの口で既定ではない。無ければ機械が「無い」と 1 行出す。指摘・CI を PR でない対象に付けると「その材料は PR / issue のもの」と出る。地図は commit にも効く

対象の読み方:

- 数字だけの語は番号が先。7 桁以上で手元の commit に解ければ commit（迷うなら `HEAD~n` か 8 桁以上）。同じ語が枝の名前にも当たるなら枝が勝つ（移る）。焦点の語と同じ名前の枝・タグは対象にできない（先に焦点として読む）
- 引数なし・`this`・ブランチ名で移った後は、今の枝から意図を汲む。順に: 枝の PR → 無ければブランチ名の番号（`chore/1513-…` → #1513。PR か issue かは GitHub が返した種類のとおりで、機械が「（… だった。違えば番号を渡す）」と 1 行断る。issue と決めつけない）→ それも無ければ手元だけ（機械は GitHub に聞かず、手元のブランチと未コミットの変更の中身、既定ブランチより先の commit が有ればその差を出す。止めない——止めると書きかけの人に何も返らない）→ 手元に未コミットも、push していない commit も、既定ブランチより先の commit も無ければ、**会話から対象を推定する** → 推定もできなければ聞き返す。ブランチ名で呼ばれたときは推定しない（枝そのものが対象。差が無ければその旨を型で）
- **会話からの推定**: 直近に出たものを 1 つ（番号・ブランチ・commit・話題。直前に commit した話なら HEAD の commit）。同じ往復に複数あれば 番号 → ブランチ → commit → 話題 の順。会話が要約で前半が消えていれば `what-am-i-doing.py` で往復を取ってから決める。2 つ以上が同じ強さなら推定しない（聞き返す）。番号は、会話に URL か owner/repo が無ければいま居るリポジトリの番号と見る（URL が出ていればそれで呼ぶ）。推定した対象で機械を呼び直す——番号は `catchup.py <番号>`、commit は `catchup.py <sha>`、話題は `what-am-i-doing.py --topic "<会話でその話題を指した、読む人の語>"`（0 件なら肝の 1 語で 1 回）。`--switch` は付けない（引数なしは移らない。移りたければ番号で呼び直してもらう）。返答は、その対象を直接呼ばれたときと同じ形（一覧の表のその対象の行。節も全部）
- **聞き返す**（**質問で返してよいのはここだけ**）: 型を書かない。手元の事実（枝の名前・PR も番号も無い・未コミットも push していない commit も無い）を 1〜2 文で言い切ってから、渡せるもの（番号・URL・ブランチ名・commit・話題の語）を 1 文で聞く。末尾に機械の「見ていないもの」の 3 項目（script 名は `/what-am-i-doing` の呼び名に置き換える）
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。GitHub の remote が無い・detached だけは「PR が無い」と同じに扱い、手元だけを出す

移る（`--switch`。戻るとき、会話の位置と一緒に手元の枝も失われている）:

- 移る先: PR は head の枝（手元に無ければ origin からその 1 本だけ `git fetch` して作って移る。名前と追跡先は `gh pr checkout` と同じ）。issue は名前にその番号を持つ手元の枝が 1 本のときだけ（origin からは探さない）。ブランチ名はその枝（origin にだけ有れば origin/<名前> を追跡する枝を作って移る）
- 移らない条件（理由と今どこに居るかが、見出しの URL の直下の「ブランチ」の行に出る）: 追跡 file に未コミット（未追跡だけなら移る）／merge・rebase・cherry-pick の途中／別の worktree に checkout 済み／origin にももう無い（merge 済みで削除）／fetch が失敗／fork の PR で手元の同名の枝が head の commit を含まない／`index.lock` が有る。ブランチ名で移れなかったときは、機械がその枝に PR が有れば PR として、無ければ枝の tip の commit として出す（枝全体の差は移ってから）
- 機械が手元を変えるのは `git switch` とその 1 本の fetch だけ。pull・merge・stash・commit・`gh pr checkout` はしない。戻すのは `git switch -`。移った・既に居たときは末尾に「手元のブランチ」の節が付く（push していない commit・PR の head より後ろの数・未コミットの木）。移らなかったときは「ブランチ」の行だけ

## 役割分担

- **機械（catchup.py）**: 事実だけを出し、判断しない。見出し（立場・状態・URL・「ブランチ」の行）→ 私の最後の痕跡 → 私に求められていること → その後の出来事 → 私の痕跡以降に変わった file → いまの状態（承認・取り込み・取り込み先とその枝の PR・依頼先の候補・CI・未解決スレッド）→ つながっている先（閉じる issue・上に積む PR・参照）→ 見ていないもの → 材料をこの順で: 本文（材料）→ 指摘（材料）→ CI が落ちた理由（材料）→ 変更の地図（材料）→ 手元のブランチ。指摘は相手の最後の発言（40 行まで）と head のその行の前後、CI は落ちた step のログの末尾（行頭の job・step・時刻と色の印は落としてある）、地図は規模・変更ファイル・同じ階層の既存・変更ファイルの木・名前の言及・新規ファイルの先頭と骨組み・既存ファイルの変更（今の姿に帯）。`| ` の後ろの行は 1 文字も変えていない
- **あなた（AI）**: 材料を読み、書く前に 4 つを確かめ、型に畳み、後ろの節を付ける。散文は自分で書くが、コードの行は写すだけ。機械の出力は貼らない（全文を求められたときだけ、1 文字も変えずコードブロックで）。日付・件数は機械の数字。「私」は gh の認証ユーザで、手元の `git config user.email` と一致する commit は私の push（commit を呼んだときの作者判定は型の「PR でないとき」）
- **機械からそのまま写す語**（綴りを変えると探せない）: 飛び先 path:行・取り込み先・上に積む・依頼先の候補・私の痕跡以降に変わった file・見出しの「ブランチ」の行・手元のブランチ・本文（材料）・指摘（材料）・CI が落ちた理由（材料）・変更の地図（材料）・変更の中身・見ていないもの・`← 私が返す番`・`← 私が最後に発言している（相手の番）`・枠の見出しの `（言語名 X）`（X を ```X に）

## やること

1. 受け口のとおりに機械を呼ぶ。
2. **本文を読む**: 「本文（材料）」に作者の本文と、閉じる issue・本文が # で指す issue / PR の冒頭。件名（型の 1 段落目）と説明の材料。上限で切れていれば `gh pr view <番号> --json body -q .body`（issue は `gh issue view`、commit は `git show`）で全文を読む。
3. **書く前に確かめる 4 つ**（確かめずに機械の言葉を写すと答えが逆になる——済んでいる申し送りが「未対応の問い合わせ」に読まれた実測）:
   - `CI: 赤` → 「CI が落ちた理由（材料）」で落ちた理由を読む（焦点で他に絞って付いていなければ `catchup.py <番号> CI` で呼び直す。`--switch` は要らない）。読めなかったチェック（Actions の run でない等）は URL を開く。「次にやること」はこれ次第
   - `（名指しは無い。私の件への発言）` → 私への依頼か、私の push で**既に済んでいないか**を本文と差分で確かめる（機械は push を返事と数えない）
   - 止めている原因が別の PR / issue → その番号の**誰の番か**を 1 回引く（`gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt`）。「未承認」だけでは読む人が今日動くべきかを決められない
   - 会話に GitHub に無い依頼（口頭・チャットのレビュー依頼など）が出ていれば、立場は会話の側を信じて書く（私が動かせる）。GitHub に依頼が無いことは 1 文添える
   - 取り込みが「GitHub が判定中（UNKNOWN）」なら `gh pr view <番号> --json mergeable -q .mergeable` を 1 回だけ引き直す（機械を丸ごとは呼び直さない）。まだ UNKNOWN なら「衝突の有無は GitHub が判定中（未確認）」と書く
4. 型に畳む。型に足してよいのは、型だけでは「次にやること」を読んだ人が実行できないときの「変更前 → 変更後」の数行だけ（差分の全文ではない）。内容は型に詰めず説明で。
5. 型の後ろに節を、一覧の順で全部付ける（説明 → 絵 → 指摘 → CI → 地図 → 手元）。見出しは `## 説明`・`## 指摘`・`## CI`・`## 地図`・`## 手元`。焦点で呼んだときはその節だけ（説明・絵・手元は一覧の「返答の節」の括弧のとおり）。作者が私かどうかで落とさない（この道具を呼ぶこと自体が、自分の PR でも中身を忘れている印）。

## 型（5 段落。どの対象でも）

**同僚に口で話すときの散文**で、**太字の 1〜2 文で始める**。段落の順は固定。コードブロック・表・ラベル列を使わない（例外は箇所の枠と絵で、どちらも型の外）。全体で 12 行前後・450 字前後を目安に（後ろの節を除く）、段落は 4 文以内、**文体は です・ます**。字数は上限ではなく判定は読みやすさ——2 行目だけで用が足りるか、1 文 1 情報、要らない修飾が無いか。超えるなら要素（立場・一手・観測値・見ていないもの）でなく修飾を削る。下の例は書き方の一つで、文言を写す型ではない（決まった言い回しは場面に関係なく毎回出て雑音になる）。

```
**[#1276](https://github.com/o/r/pull/1276)（現場コネクタの要件の下書き）は私の PR で、
動かすのは私のもう 1 本の PR #1596 の側です。#1596 にレビュー依頼を出せば進みます。** 現場コネクタ（工場の設備と
繋ぐ部品）に何が要るかを docs/_draft/ に書き出した下書きです。

最後に触ったのは 2 日前（9/1）で、main を取り込んで push しました。その後は
誰も動いていません。8/27 に 250489 さんから「lint の新しい規則に合わせて 1 行
直して」と申し送りが来ていましたが、9/1 の取り込みで済んでいます。返信は
要りません。手元は main から docs/1276-connector に移しました（push していない
commit も未コミットもありません）。

止めているのは CI の赤 3 本で、全部同じ文書検査です。中身は docs/_draft/ の
ADR 参照 10 か所で、下書きを規則の対象から外す #1596（私の PR、レビュー依頼が
未送）が通れば消えます。承認はまだ無く、衝突も、返事待ちの指摘もありません。

次は、#1596 のレビュー依頼を出す → 通ったら main を取り込み直す → 緑を確認 →
#1276 のレビュー依頼先を決める。

見ていないのは、この PR の古い方のコミット 43 件（私の痕跡があれば見落とし
ます）と、GitHub の外のやり取りです。下の地図の 3 file は私が選んだもので、残りは
末尾に一言だけです。
```

- **1 段落目（太字）**: `[#番号](URL)（件名）` と立場、**どこで止まっているか**を確かめた結果で、進める一手を添える。URL は機械の見出しの下の行から写す（他の番号は `#番号` のまま——機械が出していない URL を組み立てない）。機械の「私の番」の行は写さない。止まり方は 3 つ——私が動かせる／別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと他人の PR 待ちに読まれる）。私の PR で依頼が誰にも出ていないなら、渡す先を決めるのが私だと分かるように。私が入っていない他人の PR で、GitHub にも会話にも依頼が無いなら「作者 X を待っている」（渡す先を決めるのは作者）——このとき太字に私の一手は書かず、来た場合・来ない場合は 4 段落目で。閉じた件（merged・closed）は「済み。動くものは無い」と言い切る（機械も見出しで「済み」と出す）。件名は機械のタイトルから型の接頭辞と括弧書きを落とした**全角 12 字以内**の名詞句。**ここだけ読んで用が足りるように書く。** 同じ段落に太字でなく「何をする PR か」を 1〜2 文（本文の冒頭か地図の先頭コメントの言葉で。作者を問わない。内容の説明は「説明」の節で、ここに詰めない。段落は増やさない）。PR でないときの言い切りは下の「PR でないとき」
- **2 段落目（最後にしたこと）**: `N 日前（M/D）` に何をしたか。N は機械の行に有ればそれ、無ければ（作成・渡された時点の行は日付だけ）機械の日付から今日までを数える（年は今年と見る）。同じ日なら「今日（M/D）」、前日なら「昨日（M/D）」。**その後の動きを同じ段落に**——誰も動いていないならその旨、動いたなら誰が何を（**人は名前で**。「相手」と書くと誰かで止まる）。私宛の依頼があれば、いつ誰から何が来て、済んでいるか未対応か（未対応なら一手の先頭）。その後に push があれば「私の痕跡以降に変わった file」の件数を同じ文に（名前は 1〜2 なら文に入れ、3 以上は数だけ言い、名前は次にやることか地図に任せる。木に印は足さない）。機械が「この件で私はまだ何もしていない」と言うなら、その旨から始め、起点は私に渡された時点（誰の何で。N 日前）か作成（誰が N 日前に立てた）にして、そこからの動きを続ける。末尾に手元の 1 文（「手元」の節）。`--switch` で呼んだときは今のブランチを絶対名で。5 通り: 「手元は main から feat/123-x に移しました」／「手元に feat/123-x は無かったので origin から取り、main から移しました」／「手元は feat/123-x に居ます」／「手元は main のままです（手元に未コミット 3 件があるので feat/123-x へ移していません）」／「手元に feat/123-x は無く、origin にももうありません（PR は merge 済み）。手元は main のままです」。移らなかったときの今のブランチは**機械の行の末尾の括弧から写す**（「（手元は … のまま）」「（手元の位置は読めない）」「（手元に git の checkout が無い）」）。推測で main と書かない。手元の 1 文を書くのは、機械が「ブランチ」の行か「手元のブランチ」の節を出したときだけ——`--switch` を付けずに番号で呼んだとき（会話の話題の補い・その他の理由で付けなかった番号）には出ないので書かない。例外 2 つ（commit・会話から推定）は下の「PR でないとき」
- **3 段落目（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。1 段落目に出した別の番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。機械の「取り込み先」が既定ブランチでなく「その枝の PR」が open なら、その番号も別の番号として 1 段落目とここで扱う（所有を先に——その枝の PR が入るまで、この PR は既定ブランチに入らない。merged や「無い」なら書かない）。機械の「上に積む」があれば、この PR を base にしている PR として番号と誰のものかを 1 文（この PR が止まると一緒に止まる）。CI は落ちた本数と中身の箇所数を分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・返事待ちの指摘の観測値を末尾に 1 文（「未解決スレッド」は GitHub の語で、返答には書かない）。止めているものが無いなら、無いことが分かるように
- **4 段落目（次にやること）**: 動作を `→` で繋ぐ。番号は書くだけで説明しない。**空にしない**——待ちなら、何を待ち、動いたら何をするか。私が入っていない PR で待ちなら「依頼が来たら本文と地図を読む → レビューを返す。来なければこの PR で私が動くことは無い」のように、来た場合を `→` で繋ぎ、来ない場合を 1 文で言い切る。機械がブランチに移らなかったときはその一手を先頭に——**機械の行が `→` で一手を書いていればその後ろをそのまま写す**（未コミット・origin にももう無い・worktree の dir 無し、は機械が `→` で書く。fork で照合できない件だけは `→` 無しで「gh pr checkout N で取り直せる」と機械が書くので、それを写す。文言は機械が状況で変える。自分で組み立てない）。別の worktree なら「<path> で続ける」。手元に無いだけなら機械が origin から取って移るので `gh pr checkout` を書き足さない。移ったときは switch を書かない。一手が「依頼先を決める」なら、機械の「依頼先の候補」を括弧で添えてよい——候補の名前と機械が付けた理由（この PR に発言あり・変更 file の commit 者、のように機械の語のまま）。「X に依頼を出す」とは書かない（決めるのは私で、この返答はまだ決めていない）。候補が「なし」なら添えない
- **最後の 1 行（見ていないもの）**: 機械の「見ていないもの」から、この件に固有のもの（上限で切れた分・結び付いていない commit・痕跡の基準が近似のとき「数件ずれうる」）と GitHub の外を挙げ、それぞれ何を見落としうるかを添える。**削らない**——ただし機械が口を添えた項は、その口で見たなら書かない: 「diff の全文」は地図の枠に変更 file が全部入っていれば書かない。「発言の全文」と「名指しの無い発言が私への問いか」は、人の発言が有るか `（名指しは無い。私の件への発言）` の行が有るときだけ `--full` で取って確かめてから落とす（発言が bot だけ・0 件なら取らずに落とす）。機械が script 名（what-am-i-doing.py・catchup.py）で書いた口は `/what-am-i-doing`・`/catchup` の呼び名に置き換える。地図を付けるときは、変更 file が箇所の数（3〜6）以下で全部枠に出ているなら「下の地図の N file で全部」、選んだなら「下の地図の N file は私が選んだもので、残りは末尾に一言だけ」を足す。手元だけなら GitHub 側（PR があっても見ていない）、commit なら GitHub 側・前後の commit・取り込まれたか、会話の話題なら会話の要約で消えた分
- 同じ番号を説明するのは 1 回、「止めているもの」で。番号そのものは何度出てもよい

PR でないとき（段落ごとの言い切り。材料が無いことは、無いと書く——「空にしない」と「断定しない」を両方満たす形）:

- **枝に PR 無し**（未コミット・push していない commit・既定ブランチより先の commit のどれかが有るとき。どれも無ければ受け口の推定か聞き返し）: 1 段落目「今のブランチ main に PR は無く、名前にも番号がありません」。3 段落目は「GitHub 側は見ていない」と断って、手元の事実（未コミット・push していない commit・PR が無いこと）。4 段落目は手元から決まる一手（push する・PR を立てる・書きかけを続ける）
- **commit**: 作者が私かは機械の名前でなく `git show -s --format=%ae <sha>` と `git config user.email` の一致で決める（違えば作者の名前で）。枝は `HEAD~n` なら今の枝、sha なら `git branch --contains <sha>` を 1 回。1 段落目「2971ea2 は 9/6 に私が作った commit で、いま居る枝 main に入っています（PR を経たかは見ていません）。動かすものはありません」——「済み」とは言わない。2 段落目の手元の 1 文は、機械が「ブランチ」の行を出しても書かない（枝の名前が無い）。3 段落目は「GitHub 側も手元の未コミットも見ていない」と 1 文で断り、止めているものは無いと書く。4 段落目は「PR が有るなら番号で呼び直す → 前後を読むなら HEAD / HEAD~n で呼ぶ → 手元は引数なしで呼ぶ」
- **会話から推定した番号**: 太字の直後に「今のブランチ main には PR も名前の番号も無く、会話に出ていた #N を出しています」を 1 文（4 文の数に入れない）。手元の 1 文は、最初の `this` の手元の節から書く（絶対名。その枝に移していないことも）。会話の話題の言い切りは「会話の話題」の節

## 説明（本文か差分が有るとき。焦点で指摘か CI に絞ったときは付けない）

型の後ろ、材料の節の前に `## 説明` で、**この件が何のために・何を・どう変えるか**を、この件も周辺の部品も知らない人に口で話す散文で書く。型の 1〜2 文は名指しで、木と箇所は置き場所と実物の行——どれも「なぜ」を言わない（28 file の PR で型と木だけ出したら「内容が初見に分かりづらい」と言われた実測）。commit も PR 無しの枝も同じ形・同じ字数。

材料は「本文（材料）」（作者の本文、閉じる issue と本文が # で指す issue / PR の冒頭。背景は Closes の無い参照先に書いてあることが多く、機械は 3 件まで引く。多ければ `gh issue view <番号>`）と、地図の先頭コメント・docstring・既存ファイルの変更の枠。本文が薄い（無い・1 行だけ）なら、その旨を 1 文書いてから `gh pr diff`（commit は `git show`）で分かることを事実で書く。先頭コメントが「8 行で切った」と言っていれば、切れた文を作者の言葉として写さず `gh pr diff`（commit は `git show`）で全文を見る。

段落は 3 つでこの順、段落は 4 文以内（2 段落目末尾の file 数の 1 文は 4 文の外）。全体は **200〜800 字**——行でなく字で数え、書いたら `wc -m` で数えてから出す。物差しは差分の規模（file 数）と本文の密度の**大きい方**。本文の行数は中身の行だけで数える（空行・「🤖 Generated with」などの署名・session の URL を除く。機械の括弧の数字はそれ込み）。1 file +2 行で中身 10 行以内なら 200 字、中身 10 行超なら 400 字前後、中身 20 行超か 15 file なら 740 字（下の例）、28 file でも 800 字まで。長くなるのは path と括弧を並べたときで、それは箇所の仕事:

1. **背景と課題** — この変更の前はどうで、何が困っていた（何が要った）か。閉じる issue の題名と本文の冒頭から、作者が「なぜ」を書いていればその言葉で。扱う部品が何かを、読む人が知らない前提で名指す（「検索 MCP サーバの新版」）
2. **何をどう変えるか** — 「変更前 → 変更後」で。仕組みを、部品を役割で名指して言う（chart の受け口・CI の描画検査・権限の terraform）。ここで付けた役割の語を、木と箇所の見出しの下の 1 行でそのまま使う。複数の変更が 1 つに入っているなら 1 つずつ 1〜2 文と、なぜ同じ PR かを作者が書いていればその理由。file が多ければ段落の末尾に 1 文、役割ごとの file 数と、残りが何の追随か（「28 file のうち chart 6・CI 3・terraform 2。残る 17 file は compose・手順書・設定例の追随」）——木で説明されない file が何かを木の前に言う
3. **使う側から見た変化と、含まれないもの** — 取り込むと誰の何が変わるか。既定値、移行や設定の要否、作者が「含まれない」と書いたもの。変化が無いなら、無いと分かる 1 文で終える

- **言葉は作者のもの**——本文・先頭コメント・commit の題の語で。製品名・標準仕様（Helm・terraform・K8s）はそのまま。このリポジトリの部品（MCP サーバ・backend・テナント）は初出で役割を 1 句（「文書を検索する MCP サーバ」）。この件の中でしか通じない名前（部品名・ジョブ名・ラベル名）は初出で「中身 → 記号」（「検索 MCP サーバの新版（contents-search-revised）」）。逆にしない——記号を先に見た人は括弧を読む前に止まる。中身が言えない名前は出さない。file 名が本文で部品の名前として出るなら、拡張子込みの名前（figure-check.py）は部品の名前として書いてよい（階層は書かない）
- **path・設定の key・関数名・引数名は入れない**——箇所の見出しと `#` 注釈の仕事。出る記号は部品の名前だけ（作者が本文でその名で呼ぶ仕組みは部品の名前、その置き場所は path）。括弧は 1 文に 1 つまで（並べた説明は 2000 字になり、初見 2 人が「分からない語」を 15 個挙げた）
- **評価語を入れない**（妥当・きれい・良い）。diff から読んだ機構は「〜している」の事実で。本文にも diff にも無いことは書かず、確かめていない推測には「（未確認）」
- **状態と経緯は書かない**——承認・CI・衝突・誰が何を言ったかは型の仕事。ここは取り込まれたときの姿だけ。型の文を繰り返さない

書けたら自分に問え——**この件を知らない人が、ここだけ読んで「何のために・何を・どう変えるか」を自分の言葉で言えるか。木の各 file が何の役か、説明の語で言えるか。path が 1 つでも入っていないか。固有名を全部拾って、初出に中身が付いているか。絵を付けたなら、その名詞を全部、説明か本文の語に指で当てられるか。**

## 箇所（指摘・地図・手元・会話の話題が共有する形）

engineer にはコードの行そのものが散文より早い——散文は翻訳で、頭の中でコードに戻す往復が要る。3 つの約束: **案内（木）と読む場所（file の中身）を混ぜない。書いてあるものは作者の言葉で見せる（file 名・step 名・docstring・先頭コメント・指摘した人の文）。記号は誰もが知っているものだけ（path・+/−・字下げ・行番号。木の `~` だけは地図の印）。** **この節だけはコードブロックを使う**。**言語名は必ず付ける。** 機械が各枠の見出しの末尾に置く `（言語名 X）` が有ればそれを写し（木は diff、絵は text、CI のログは plaintext）、無い枠（`gh pr diff`・`git show`・head の file から写した行）は拡張子から自分で付ける（py → python、md → markdown、sh → bash、yml → yaml、ts → typescript。他は拡張子そのまま）。**例に無い名前でも付ける**——色が付かなくても害は無い。plaintext は拡張子が無く中身（shebang など）からも分からないときだけで、機械が plaintext と書いた file でも中身で分かればその名前に（実測: 例の一覧に無い .md を plaintext にして色が消えた）。

- 境目は罫線 `---` 1 本。見出しは太字で `n/N` と backtick の `path:行` と括弧の種別。種別は（新規）（既存に追記）（既存を書き換え）（削除）（改名 旧: path）（指摘 n）のどれか——追記は木の `~` で削除行 0、書き換えは削除行あり、改名は機械の「旧:」から。行は機械の「飛び先 path:行」から写す（コードなら枠の先頭、散文なら機械が取った文脈の先頭、新規 file は 1、指摘なら指摘の行。backtick に入れるのは端末でクリックで開けるから）。飛び先は枠の先頭で、関数の頭とは限らない——枠の途中の関数だけを出すなら、行は `git show <sha>:<path>`（PR は head の sha）で def の行を引いて書く。行が無いのは **file ごと削除された file だけ**（head にもう無い）で、そこだけ素の文字で `n/N path`（削除）。**path と `path:行` の前後は半角スペースで離す**（見出し・注釈・散文の中でも。端末のクリックが隣の文字を巻き込む）。「手元で開く」のようなラベル行は付けない
- その下に 1 行——地図なら**どこから使われるか**（機械の「名前の言及」の下の行が `uses:`・`run:`・`-f`・import のようなコードの行なら関係。コメント行の言及は数えない。道具が既定の名前で読む file（docker-bake.hcl・Dockerfile・.tool-versions）は読む側のコマンド行を関係にする）、指摘なら**誰が何を求めているか**を、その人の言葉で。名前の言及にも出典にも無い散文 file は、関係を推測で書かず、file の役割を 1 行（出典の順は front matter の description → 最初の見出し → 先頭コメント → 本文の語）。地図の file には説明で付けた役割の語を添える（説明と木を同じ語で繋ぐ）。評価語は入れない。作者の言葉（先頭コメント・docstring）が無い file は骨組みだけ出し、説明を足さない。機械に中身が無い（取れなかった・上限超え）ときは、無い旨を 1 文
- 枠は、機械が帯を入れた「今の姿」を言語名の枠に `| ` の後ろを 1 文字も変えず写す。読み方は 1 つ——実線の枠 `┏ … ┗` の中が変わった所で、行頭が `#│`（その言語のコメント記号に `│`）の薄い行は前、色の行は今（コメント記号だけの行は今足したコメント）。追加は今だけ、削除は前だけ、変更は前の下に今。間 3 行以内の変更は 1 枠で、挟まった変わっていない行の数は帯にある。点線 `┅` は畳んだ区間。帯は自分で足したり削ったりしない（手で置くとずれる）。移動（同じ行が消えて別の所に足された）は機械には分からないので、見出し下の 1 文で言う。unified diff は貼らない（`@@` は人に意味が無く、`+`/`-` は構文の色を消す）
- 枠には実物の行だけ——機械の `| ` の後ろ、`gh pr diff`、head の file から**写す**。記憶で書かない。同じ file に枠が複数あれば 2 つ目以降の枠の上に、その言語のコメント記号で `# path:行 （役割）`（記号は機械の薄い行の行頭と同じ。行はその枠の飛び先。1 つ目は見出しが兼ねる）。右に日本語を置かない（折り返した瞬間に行の形が壊れる）
- 枠の中は 1 行 60 桁以内（日本語は 2 桁。機械の帯 78 桁は除く）。超える行は肝（名前・条件・追加された断片）を残して前後を `…` で省くか、行末を `…` で切る。sha は先頭 7 桁と `…`、長い正規表現や URL は肝の 1 要素だけ。分岐や条件そのものを `…` で隠さない。骨組みの 2 行を 1 行に縮めない（実物に無い行になる）。折り返してよいのは散文（コメント・docstring・md の段落）だけで、語の切れ目で折る——続きの行は字下げしない、行頭に 。、）を置かない、`**` や backtick の対は割らない。code の行と `#│` の薄い行は折り返さず `…` で切る（折り返すと実物に無い行になる）。「1 文字も変えず」はコードの行の話。見出しと枠の外は対象外
- **1 節は関数まるごとで、前後を長めに。** 指した行だけの数行では、読む人が file を開いて前後を確かめに行く。関数の途中で切らない。減らすのは関数の数で、行ではない。順は**呼ぶ側 → 本体 → 呼ばれる helper**。合計は 300 行前後を目安に（折り返す前の、機械の枠の行で数える）、超えるなら鎖の末端の helper から落とす（指摘と CI は私が動く材料、地図は読み直す材料）。前後の広さは機械が決め（一覧「前後の広さ」）、足りない所を AI が足す:
  - コード: 関数まるごと。長い関数は機械が変更の前後を残して畳む（`--frame` は 1 file の上限を外すだけで畳みは外れない）。畳まれた中を読むなら file を開く——PR なら head の file（手元がその checkout なら file、無ければ `git show <head の sha>:<path>`。sha は `gh pr view <番号> --json headRefOid -q .headRefOid`、別リポジトリは `-R owner/repo`）、commit なら `git show <sha>:<path>`、手元なら作業ツリーの file。機械が既存ファイルの変更の見出しに「文脈は 3 行——手元に base と head の commit が無い」と断っていれば、AI は fetch を打たず、head の file を `gh api -H 'Accept: application/vnd.github.raw' repos/<owner>/<repo>/contents/<path>?ref=<head の sha>` で取って関数まるごとに広げる。取れなければ 3 行のまま写し、地図の道順の 1 文に「前後は 3 行（手元に PR の commit が無い）」と書く
  - 散文・設定（md・yaml・json など）: 機械は変更の前後 10 行（一覧の表）。AI は見出し・上位 key のような意味の単位まで file から足してよい——足すのは飛び先から 30 行以内の見出し・key まで。足したら見出しの `path:行` を足した先頭に合わせる。遠ければ足さず、足さなかったとは書かない。**file の種類で節を落とすな**（md が主のリポジトリでは木しか残らない）
  - 指摘: AI は指摘の行を含む意味の単位（関数なら def から）まで head から足す（手元にその commit が無ければ上の `gh api`）
  - CI: 落ちた理由が読める 3〜15 行

## 指摘（人が入っている未解決スレッドがあるとき、または `指摘` を付けたとき）

`## 指摘` で、**私が返す番の指摘を 1 件ずつ**箇所で見せる（戻るとき失われているのは、何を言われてどこで止まっているか——自分の PR でも、レビューで渡された PR で作者が返してきた件でも）。付くのは機械の「未解決スレッド: N 件（うち人が入っているもの n 件）」の n が 1 以上のとき。材料は「指摘（材料）」——スレッドごとに相手の最後の発言、`← 私が返す番` か `← 私が最後に発言している（相手の番）` の印、head のその行の前後（`| 行番号 行`）。

1. **道順**を 1 文——「未解決 N 件。[block] n・[suggest] n・[nit] n で、私が返す番は n」（印は発言の先頭の語と機械の `←` から数える。無ければ数えない）。[block] を先に
2. **件ごとの箇所**（`← 私が返す番` の件だけ。N はその数）: 見出し `**n/N \`path:行\` （指摘 n）**` → 1 行「250489 さんが求めているのは …」を相手の言葉で（`[block]`・`私が返す番` を括弧で添える）→ 枠に head の行を機械の `| ` から写す（注釈は要らない——見出しが兼ねる。行番号は残す）→ **直すなら** 1 文か変更前 → 変更後の数行（相手の修正案があればそれを写す。無ければ書かない）
3. **末尾に 1 文**——`← 私が最後に発言している（相手の番）` の件は、path と行の名前だけ並べる

指摘が妥当かの判断は書かない——求められたら別に確かめて答える。相手の発言を要約せず、求めている中身はその人の語で写す。機械が「行: 今の head に無い」「行 N は head のファイルの外」「行: 取れない（手元にその commit が無く、GitHub からも読めなかった）」と言う件は、行を出さずにその旨を書く。

## CI（赤があるとき、または `CI` を付けたとき）

`## CI` で、**落ちたチェックを 1 件ずつ**箇所で見せる。材料は「CI が落ちた理由（材料）」——チェックごとに、失敗した step のログを最後の `##[error]` まで（`| ` の後ろ）。見出し `n/N チェック名`、その下に 1 行——最後の `##[error]` の文をそのまま。枠は ```plaintext に機械の `| ` の行から、落ちた理由が読める 3〜15 行。「直すなら」は書かない（原因の判断は型の 3 段落目）。ログを取れなかったチェックは、URL を書いて「ログは取れなかった」と 1 文。

## 地図（差分が有る対象。焦点で他に絞ったときは付けない）

`## 地図` で、説明の後ろに、**この件が全体のどこに何を足すか**を木と実コードで見せる（上に木、下に file ごとの箇所）。材料は「変更の地図（材料）」——規模、変更ファイル、同じ階層の既存、変更ファイルの木、名前の言及（当たった行つき）、新規ファイルの先頭と骨組み、既存ファイルの変更。そこに無い行が要るときは `gh pr diff <番号>` の実物から写す（file ごとの絞り込みは無いので `diff --git` の見出しで探す）。commit と PR 無しの枝（「<既定ブランチ> より先の commit N 件の変更（材料）」）は木と変更の中身だけで、規模・同じ階層・名前の言及・先頭と骨組みは出ない（新規 file は全文が枠。続きは commit が `--frame`、枝が `git diff -W`）。関係は枠の中の import・呼び出しの行から読み、無ければ file の役割を 1 行。

1. **木の前に 1 文**——規模は機械の「規模」の行から file 数と ±行数だけ。中央値・上位 25% は、この PR の行数が上位 25% を超えるときだけ「直近マージの上位 25%（N 行）より大きい」と 1 句添え、それ以外は写さない。commit と PR 無しの枝には規模の行が無いので、見出しの file 数だけ書き、行数は木に任せる（足さない）。**木**（```diff）は機械の「変更ファイルの木」を**そのまま**（周辺の既存は機械が名前の近い順に数件と「… ほか N」。新規 `+`・変更 `~`・削除 `-`）。組み直さない、私の言葉を書かない。周辺の何が何かを書けるのは、枠か先頭コメントにその名前が出ている file だけ。手元がその checkout でないと木は変更 file だけになる。それでよい
2. **道順**を 1 文——「入口 → そこから呼ばれる検査 → 渡す設定 → 既存への配線の順に N file」。部品は説明で付けた役割の語で。作者の印（先頭コメントの (a)(b) など）があればここで導入。file が 1 つなら「その file の何を見るか」の 1 文。枠が 3 行のまま（箇所の「コード」）ならその旨もここ
3. **file ごとの箇所**を 3〜6（file が足りなければ有るだけ）。選び方は、入口（`on:` を持つワークフローのように、他の変更 file を `uses:`・`run:`・`-f` で使い、自分は他から使われない file）→ 入口が使う file → 既存への小さな追記。入口が使わない大きな既存の追記（README や台帳）は 4 へ。入口が使わない新規 file（テストなど）は使われる側の節の 1 行で触れ、4 にも名前を入れる。中身は
   - 新規: 先頭コメントか docstring（作者の自己紹介）→ 骨組み（step 名・def・上位 key）→ 肝の数行（先頭コメントで名指した箇所か、名前の言及で当たった行）。ワークフローの step 一覧には、その step が使う file を `#` で添える（名前の言及の行か `gh pr diff` の run: 行で確かめたものだけ）。step 一覧が新規 file の中の流れの図の代わりで、ここに図は描かない。入口の節は step 一覧を切らず、先頭コメントは主張の行だけ、`on:` は契機の行だけ、permissions・concurrency・defaults は落とす
   - 既存: 「既存ファイルの変更」の枠を関数ごとにそのまま。1 file の上限で切れた続きは `catchup.py <番号> --frame <path>`（commit は `catchup.py <sha> --frame <path>`）
4. **残りの file** を末尾に 1 文——名前と ±行数と、先頭コメントにあればその 1 句。無ければ名前だけ。file が多ければ役割ごとにまとめて数で（説明の 2 段落目末尾と同じ形）。commit では先頭コメントの句は無い

## 手元（機械が「手元のブランチ」の節を出したとき。会話の話題では what-am-i-doing.py の「いま手元に残っているもの」）

- 型の 2 段落目に 1 文: push していない commit と未コミットの件数（PR の head より後ろならその数も）。`this` で呼んだときも `--switch` で移った・既に居たときも同じ場所で、字数は増やさない。未コミットの木があれば、`## 手元` で末尾に ```diff の枠でそのまま貼る（無ければ節を書かない。焦点で絞ったときも書かない。貼らずに出したら「tree が出てない」と言われた）。組み直さない
- PR も番号も無い枝・会話の話題では、木の下に機械の「変更の中身」を箇所の形で——読む順を 1 文（「main の配線 → switch_branch の本体 → tree_blocker の判定、の 3 関数」）→ 関数ごとの箇所（見出しは `n/N` と backtick の `path:行` ＋ 関数名（変更／新規）＋ 1 文 ＋ 枠）。上限で切れていれば `what-am-i-doing.py --frame <path>`。既定ブランチより先の commit が有れば、機械が枝全体の差の木と変更の中身も出すので `## 地図` として同じ形で付ける

## 会話の話題（番号でも commit でも枝でもない語で呼ばれたとき）

会話の中にしか無い話題（レビューで見つけた指摘の束・検討中の案）を、型と同じ 5 段落で——何か・最後にしたこと・止めているもの・次にやること・見ていないもの。1 段落目は「「新しく出たもの」は #1505 の再レビューで私が見つけた suggest 4 件で、まだ PR には書いていません」のように**話題が何かを言い切る**。材料は会話そのもので、要約で前半が消えていれば `what-am-i-doing.py --topic` の往復で補う。結び付いた番号があれば、その番号の機械の出力で「PR に書いたか・相手が動いたか」を確かめる（「やること」の 2〜3 はこのときだけ）。話題の語で呼ばれたとき（対象は話題で、番号は補い）は、その番号の説明・地図・指摘・CI の節は付けない——後ろに付くのは「手元」だけ（`what-am-i-doing.py` の「いま手元に残っているもの」の木と「変更の中身」から。手元の変更でない項目——既存の箇所を指すだけ——は head か手元の file から関数ごと `sed -n` で写す）。引数なしから会話で番号を推定したときは違う（受け口——番号で呼ばれたときと同じ形）。会話に無いことは書かず、会話の中で確かめていないことは「（未確認）」。

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・直訳横文字、この件の中でしか通じない略号、機械の理由文（「私の件に相手の発言があり…」）の丸写し（確かめた結果を書く）、「〜と思われる」「〜のようだ」（確かめていないことは「（未確認）」と付けて書く）
- **この命令書の語で返答に持ち込んでよいのは、節の見出しになる 説明・指摘・CI・地図・手元 だけ**（「下の地図の 3 file」のように節を指してよい）。材料・機械・型・箇所・焦点・スクリプトは持ち込まない。本文（PR の説明文）は普通の語として使ってよい。作者の本文がその語（箇所・枠・飛び先など）を使っていれば、作者の語として説明に書いてよい。機械が script 名（what-am-i-doing.py・catchup.py）で書いた口は `/what-am-i-doing`・`/catchup` の呼び名に置き換える
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）。書けたら自分に問え——**2 行目だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか**

## 守ること

- **求められていないのに欠陥探しへ広げるな。** 説明は読む人の理解のためで、レビューを始める合図ではない
- **出力に無いことを断定するな。** 確かめたなら確かめた結果を書く。推測で埋めるな
- **箇所のコード・絵のラベルを記憶で書くな。** 写したものが実物と違えば、読む人は次に開いた file で裏切られる。説明か本文に無い語が要るなら描かない
- **番号でない語で呼ばれても、質問で返すな。** 会話の話題として型で出す。例外は受け口の 1 か所（手元にも会話にも対象が無いとき）だけで、その形も受け口に
- **機械がブランチに移らなかったとき、自分で stash・commit・`git switch` を打つな。** 未コミットは別のセッションが編集中の木かもしれない（同じ checkout を複数のセッションで共有していることがある）。理由と一手を「次にやること」に書くだけ。移った後に、移る前に読んだ file を編集するなら読み直す——中身は移った先の枝のもの。PR の commit が手元に無いときも `git fetch` を打たない（箇所の「コード」の `gh api`）
- **subagent・Agent・Workflow を立てるな。** `gh` は Bash で直列に呼ぶ。diff を読む仕事が増えても同じ——並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる
- **path と `path:行` の前後は半角スペースで離す**（見出し・注釈・散文の中でも。端末のクリックが隣の文字を巻き込む）
- **例の一覧を許可の一覧と読まない。** 言語名・文言・場面の例は書き方の一つで、例に無いものも規則に当たれば付ける・書く（例に無い .md を plaintext にした実測）
- 日付・件数は機械の数字をそのまま使う（今日から日数を数えるのは、型の 2 段落目の「N 日前」の 1 か所だけ）
- open 全件の棚卸しはこの道具の仕事ではない。それは `/whose-turn`
