## 一覧

`/catchup [対象] [焦点]`。対象は 1 つ、焦点は 0〜3 語（`指摘`・`地図`・`CI`）。`/catchup setup` は準備の口。対象・旗・ページの節・材料の上限と続きを出す口の表は `${CLAUDE_PLUGIN_ROOT}/docs/catchup-ref.md` の「一覧」にある——旗や続きの口を使うとき、節の描かれ方を確かめるときだけ Read で読む（毎回は読まない）。

## 受け口

機械は `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py`（以下 catchup.py）。`--switch` を付けるのは番号・URL・ブランチ名だけで、`this`・commit・会話の話題では付けない。

**どの呼び方でも、引数の末尾に `--out` を付け、返ってきたパスを Read で読む。** catchup.py の出力は Claude Code の Bash の 1 回あたりの上限（約 30,000 バイト。門はバイトで測るので、日本語はおよそ 1 万文字で当たる）を常に越える（実測 2026-09-16: 1 件で 91,701〜158,078 バイト）。付けずに走らせるとツール側でファイルへ退避され、走らせ直しで `gh` の呼び出しごと 2 回走る。`--out` は値を取らないので末尾に置く（前に置くと後ろの位置引数を吸わないが、並びが読みにくい）。**`cat` で読むな**——同じ量が再び Bash の出力に乗って、また退避される。2,000 行を越える回があるので、Read が途中で切れたら offset を進めて続きを読む。

`--out` は節ごとの行番号も返す（`節（Read の offset）: … / 159 指摘 / 971 変更の地図`）。**読むのは `変更の地図` の頭まで**——見出し・私が最後にしたこと・求められていること・その後・状態・つながっている先・本文・指摘・CI は全部読み、地図は規模・変更ファイル・名前の言及・新規ファイルの先頭と骨組みまで（説明と図の材料）。既存ファイルの変更の枠（今の姿に帯）は、説明の 2 段落目に要るときだけ読む——差分はページに機械が全部載せるので、写すために読む必要は無い。取り直しは要らない——同じファイルの続きを読むだけで、`gh` も `git` も走らない（実測 2026-09-16: #1720 は 2,168 行のうち骨組み 158 行・指摘 812 行・地図 1,199 行）。

`--out` はもう 1 行、**描く材料**の path を返す（`描く材料は <path> に書いた`）。HTML の雛形が描く構造（見出し・番・出来事・指摘・CI・差分・手元）を JSON にしたもので、AI は読まない（手で直さない）。`--render` にそのまま渡す。

- **番号・URL・ブランチ名** → `catchup.py --switch <それ> --out`。番号だけならいま居るリポジトリ（別のリポジトリは URL か `-R owner/repo`）
- **引数なし・`this`・焦点の語だけ** → `catchup.py this --out`（`catchup.py 指摘 --out` も同じで、対象は今のブランチに落ちる）
- **commit** → `catchup.py <それ> --out`。GitHub には何も聞かず、手元の git の commit として出る（題と本文、木、変更の中身。範囲は親との差 1 つ、merge は第 1 親との差）。PR を立てずに既定ブランチへ直接 commit する運用で、後から変更を読み直す口。commit の範囲 `A..B`（`2971ea2..b27cb3d`・`HEAD~4..HEAD`・`e824033^..HEAD`）も同じ形で、差は A の版と B の版の間、本文は各 commit の題（全文は `git show <sha>`）。`--frame` も効く
- **会話の話題**（`新しく出たもの`・`今の修正`・`さっきの 4 件` など、番号でも commit でも枝でもない語）→ **先に、会話の中で何に結び付いているかを解く。** 番号・枝・commit に結び付いていれば対象はそれで、話題の形では書かない——番号なら `catchup.py <番号>`（`--switch` は付けない。戻る呼び方ではない）、直前に commit した話なら `catchup.py HEAD`、このセッションで入れた commit が複数なら `what-am-i-doing.py` の「このセッションの間に入ったコミット」の一番古い sha に `^` を付けた範囲 `catchup.py <古い sha>^..<新しい sha>`。ページは、その対象を直接呼ばれたときと同じ形（説明・変更まで全部）。会話にしか無い話題（レビューで見つけた指摘の束・検討中の案）だけ、`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/what-am-i-doing.py --topic "<語句>" --out` でその語句が出た往復を取り、話題の形（下の「会話の話題と準備」）で書く——語句は 1 つ（引用符で括る。複数の語は続けた 1 句として当たる。0 件なら肝の 1 語か言い換えでもう 1 回）。実測: 「今の修正」を話題の形で書いたら、commit 4 件は push 済みで手元は空、型だけの返答になり「何も出ない」と言われた
- **`setup`**（`/catchup setup`）→ 対象ではなく準備の口。下の「会話の話題と準備」
- **焦点の語** → 対象の後ろにそのまま（`catchup.py --switch 1569 指摘 --out`）。末尾の材料をその 1 つ（複数可）に絞る、急ぐときの口で既定ではない。無ければ機械が「無い」と 1 行出す。指摘・CI を PR でない対象に付けると「その材料は PR / issue のもの」と出る。地図は commit にも効く

対象の読み方:

- 数字だけの語は番号が先。7 桁以上で手元の commit に解ければ commit（迷うなら `HEAD~n` か 8 桁以上）。同じ語が枝の名前にも当たるなら枝が勝つ（移る）。焦点の語と同じ名前の枝・タグは対象にできない（先に焦点として読む）
- 引数なし・`this`・ブランチ名で移った後は、今の枝から意図を汲む。順に: 枝の PR → 無ければブランチ名の番号（`chore/1513-…` → #1513。PR か issue かは GitHub が返した種類のとおりで、機械が「（… だった。違えば番号を渡す）」と 1 行断る。issue と決めつけない）→ それも無ければ手元だけ（機械は GitHub に聞かず、手元のブランチと未コミットの変更の中身、既定ブランチより先の commit が有ればその差を出す。止めない——止めると書きかけの人に何も返らない）→ 手元に未コミットも、push していない commit も、既定ブランチより先の commit も無ければ、**会話から対象を推定する** → 推定もできなければ聞き返す。ブランチ名で呼ばれたときは推定しない（枝そのものが対象。差が無ければその旨を欄で）
- **会話からの推定**: 直近に出たものを 1 つ（番号・ブランチ・commit・話題。直前に commit した話なら HEAD の commit）。同じ往復に複数あれば 番号 → ブランチ → commit → 話題 の順。会話が要約で前半が消えていれば `what-am-i-doing.py` で往復を取ってから決める。2 つ以上が同じ強さなら推定しない（聞き返す）。番号は、会話に URL か owner/repo が無ければいま居るリポジトリの番号と見る（URL が出ていればそれで呼ぶ）。推定した対象で機械を呼び直す——番号は `catchup.py <番号>`、commit は `catchup.py <sha>`、話題は `what-am-i-doing.py --topic "<会話でその話題を指した、読む人の語>"`（0 件なら肝の 1 語で 1 回）。`--switch` は付けない（引数なしは移らない。移りたければ番号で呼び直してもらう）。ページは、その対象を直接呼ばれたときと同じ形（一覧の表のその対象の行。節も全部）
- **聞き返す**（**質問で返してよいのはここだけ**）: ページを描かない。手元の事実（枝の名前・PR も番号も無い・未コミットも push していない commit も無い）を 1〜2 文で言い切ってから、渡せるもの（番号・URL・ブランチ名・commit・話題の語）を 1 文で聞く。末尾に機械の「見ていないもの」の 3 項目（script 名は `/what-am-i-doing` の呼び名に置き換える）
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。GitHub の remote が無い・detached だけは「PR が無い」と同じに扱い、手元だけを出す

移る（`--switch`。戻るとき、会話の位置と一緒に手元の枝も失われている）:

- 移る先: PR は head の枝（手元に無ければ origin からその 1 本だけ `git fetch` して作って移る。名前と追跡先は `gh pr checkout` と同じ）。issue は名前にその番号を持つ手元の枝が 1 本のときだけ（origin からは探さない）。ブランチ名はその枝（origin にだけ有れば origin/<名前> を追跡する枝を作って移る）
- 移らない条件（理由と今どこに居るかが、見出しの URL の直下の「ブランチ」の行に出る）: 追跡 file に未コミット（未追跡だけなら移る）／merge・rebase・cherry-pick の途中／別の worktree に checkout 済み／origin にももう無い（merge 済みで削除）／fetch が失敗／fork の PR で手元の同名の枝が head の commit を含まない／`index.lock` が有る。ブランチ名で移れなかったときは、機械がその枝に PR が有れば PR として、無ければ枝の tip の commit として出す（枝全体の差は移ってから）
- 機械が手元を変えるのは `git switch` とその 1 本の fetch だけ。pull・merge・stash・commit・`gh pr checkout` はしない。戻すのは `git switch -`。移った・既に居たときは末尾に「手元のブランチ」の節が付く（push していない commit・PR の head より後ろの数・未コミットの木）。移らなかったときは「ブランチ」の行だけ

## 役割分担

- **機械（catchup.py）**: 事実だけを出し、判断しない。`--out` で 2 つを書く——AI が読む文字の材料（見出し・私の最後の痕跡・私に求められていること・その後の出来事・私の痕跡以降に変わった file・いまの状態・つながっている先・見ていないもの、続いて 本文（材料）→ 指摘（材料）→ CI が落ちた理由（材料）→ 変更の地図（材料）→ 手元のブランチ）と、ページの雛形が描く構造の JSON。`--render` が、その JSON と AI の欄を雛形（`attention/templates/catchup.html`）に流し込み、`~/.cache/attention/catchup/<owner>-<repo>/<番号>.html` を書く（同じ件は上書き）。同じ置き場の `index.html` は、ページごとに 1 行（件・件名・誰の番・次の一手・更新）を並べる一覧で、描くたびに組み直す。描いた後、生きている VS Code の窓のすべてでページを開く（`ATTENTION_CATCHUP_OPEN=0` なら開かない。開けなくても失敗にしない）
- **あなた（AI）**: 材料を読み、書く前に確かめ、**欄の JSON**（下の「欄」）を書いて `--render` を呼ぶ。コードの行・差分・指摘の発言・CI のログ・木は機械がページに載せるので、写さない。日付・件数は機械の数字。「私」は gh の認証ユーザで、手元の `git config user.email` と一致する commit は私の push（commit を呼んだときの作者判定は参照の「PR でないとき」）
- **材料の語のうち、欄で使う所**: `取り込み先`・`上に積む`・`依頼先の候補`・`私の痕跡以降に変わった file`・見出しの「ブランチ」の行・`← 私が返す番`・`← 私が最後に発言している（相手の番）`・見ていないもの。綴りはそのまま探せばよいが、欄にはこの語を写さず、中身を書く

## やること

1. 受け口のとおりに機械を呼ぶ（`--out` 付き）。報告を Read で読む（読む範囲は受け口）。
2. **本文を読む**: 「本文（材料）」に作者の本文と、閉じる issue・本文が # で指す issue / PR の冒頭。件名（`headline`）と説明（`explain`）の材料。上限で切れていれば `gh pr view <番号> --json body -q .body`（issue は `gh issue view`、commit は `git show`）で全文を読む。**前提も読む**: 本文はふつう、仲間が知っている前提（製品が何か・部品の役割・前の番号の中身）を飛ばして書かれている。説明は初めて見る人に向けるので、本文が言っていない前提は、手元のリポジトリの README の冒頭と、触る部品の file の先頭（docstring・先頭コメント）、本文が指す前の番号の冒頭（材料に出ている）で埋める。読むのは前提を言うのに要る分だけ。
3. **書く前に確かめる 4 つ**（確かめずに機械の言葉を写すと答えが逆になる——済んでいる申し送りが「未対応の問い合わせ」に読まれた実測）。確かめた結果は欄（`headline`・`where`・`turn`・`next`）に書く:
   - `CI: 赤` → 「CI が落ちた理由（材料）」で落ちた理由を読む（焦点で他に絞って付いていなければ `catchup.py <番号> CI --out` で呼び直す。`--switch` は要らない）。読めなかったチェック（Actions の run でない等）は URL を開く。`next` はこれ次第
   - `（名指しは無い。私の件への発言）` → 私への依頼か、私の push で**既に済んでいないか**を本文と差分で確かめる（機械は push を返事と数えない）
   - 止めている原因が別の PR / issue → その番号の**誰の番か**を 1 回引く（`gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt`）。「未承認」だけでは読む人が今日動くべきかを決められない
   - 会話に GitHub に無い依頼（口頭・チャットのレビュー依頼など）が出ていれば、立場は会話の側を信じて書く（私が動かせる）。GitHub に依頼が無いことは 1 文添える
   - 取り込みが「GitHub が判定中（UNKNOWN）」で、件がまだ open なら（merged・closed なら取り込みは済んでいるので見ない） `gh pr view <番号> --json mergeable -q .mergeable` を 1 回だけ引き直す（機械を丸ごとは呼び直さない）。まだ UNKNOWN なら「衝突の有無は GitHub が判定中（未確認）」と書く
4. **欄の JSON を書く**（下の「欄」）。置き場は、描く材料の path の `.json` を `-fields.json` に替えた path（同じ一時の階層）。Write で書く。
5. **描く**: `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py --render <描く材料の path> <欄の JSON の path>`。欄に直す所があれば、機械が 1 件 1 行で言って終了コード 2 で止まる——直して呼び直す。機械が `--out` のときに「描く材料を組めなかった」と言っていれば、ページは描けない——欄に書くはずだった中身（`headline`・`where`・`turn`・`next`）を端末に短く返し、ページを描けなかったことと機械の言い分を 1 文添える。
6. **返答**: 機械が標準出力に出した 2 行——ページの path と 1 行の要約——だけを、そのまま返す。説明・指摘・差分を端末に書き足さない（ページに在る）。全文を求められたときだけ、報告のファイルを 1 文字も変えずにコードブロックで貼る。

## 欄（AI が書く JSON）

```json
{
  "headline": "60 字までの 1 文。誰が何をしたので、いま誰が何をする番か（番号・件名・状態の値は書かない）",
  "where": ["最後にしたこと", "その後の動き（1 項 1 事実）", "…"],
  "turn": ["止めているものの原因と、誰が外せるか（止めているものの行の値は書かない）", "…"],
  "next": ["一手", "その次", "…"],
  "unseen": ["機械の申告に足す、見ていないもの"],
  "lead": "1 文。どこの何を、誰のためにどう変えるか",
  "figure": {"kind": "graph", "caption": "図の題", "nodes": [{"id": "a", "text": "箱"}, {"id": "b", "text": "箱", "in": "after"}], "edges": [{"from": "a", "to": "b", "text": "渡す", "in": "after"}]},
  "terms": [{"term": "この件の中でしか通じない語", "means": "何で、何をするか"}],
  "explain": ["前提", "背景と課題", "何をどう変えるか", "使う側から見た変化と、含まれないもの"],
  "points": {"caption": "変えたこと", "items": [{"title": "何を", "before": "前", "after": "後", "code": [{"path": "差分の file", "find": "その差分に在る名前"}]}]}
}
```

`headline`・`where`・`turn`・`next` は必須。`unseen`・`lead`・`figure`・`terms`・`explain`・`points` は無ければ省く（`figure` は `null` でもよい）。`title` は会話の話題のときだけ（材料が無いので件名をここに）。知らない欄・空の文字列は機械が止める。

文体は**常体の短い文**（「〜した」「〜の番」）。1 文 1 情報。**`where` と `turn` は短い文の並び**（1 項 1 事実、60 字まで、4 項まで。`turn` に書くのは止めているものと、それを誰が外せるかだけ——関係する別の番号の紹介や推測の経緯は書かない。ページは箇条で描く。時刻と件数を段落に詰めると頭に入らないと言われた）。この PR がすることの節は読み手が違い、`explain` は 1 段落 5 文まで。**状態の値（CI の本数・承認・取り込み・未解決の件数）は文に書かない**——いまの番の「止めているものの行」に機械が出しているので、文で繰り返すと 1 枚に同じことが 3 回並ぶ。ページは読む人が上から 5 秒（いまの番）・1 分（前回から・この PR がすること）・5 分（指摘・変更）の順に読むので、上の欄ほど短く。文中の `` `…` `` はコードの札、`#番号`・commit の sha・`@名前` は機械がリンクや札にする。下の例は書き方の一つで、文言を写す型ではない（決まった言い回しは場面に関係なく毎回出て雑音になる）。

```json
{
  "headline": "私の指摘 3 件に作者が今日の夕方まとめて返信した。読んで返す私の番。",
  "where": ["昨日（10/15）、テストが例外の包み方を手で写していると指摘した", "作者が 15:32 に push し、15:44 に 3 件へ返信した"],
  "turn": ["止めているのは私の返事だけ", "3 件のうちコードで直したのは 1 件（4cf1df3aa）", "残る 2 件は、作者が #2010 と #2076 に分けた"],
  "next": ["4cf1df3aa を読み、失敗した日付のデータが解放されるかを確かめる", "#2010・#2076 への分割を受けるかを決める", "3 件に返信して解決にする", "承認するか、追加の指摘を出す"]
}
```

- **`headline`（いまの番の 1 行目。ここだけ読んで用が足りるように）**: **60 字までの 1 文で**、誰が何をしたので、いま誰が何をする番か——**どこで止まっているか**を確かめた結果。番号・件名・立場の札はページの頭と節の見出しに機械が出すので書かない（書くと 1 文が 2 行に延び、頭に入らないと言われた）。進める一手は `next` の先頭に書く（ページは `next` の先頭を大きく描く）。止まり方は 3 つ——私が動かせる／別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと他人の PR 待ちに読まれる）。機械の「取り込み先」が既定ブランチでなく、その枝の PR が open なら、**その番号と誰のものかを入れる**（その PR が入るまで、この PR は既定ブランチに届かない）。私の一手で動くのが私の番だけ（返信すれば私の側は終わるが、PR は下書きのまま・依頼未送・別の番号待ち）なら「進む」と書かず、「私の側は終わり、その後は X さんの番」と書く（実測: 返信 2 件で「進みます」と書いたが、返信後も下書きで親の PR 待ちだった）。私の PR で依頼が誰にも出ていないなら、渡す先を決めるのが私だと分かるように。私が入っていない他人の PR で、GitHub にも会話にも依頼が無いなら「作者 X を待っている」（渡す先を決めるのは作者）。閉じた件（merged・closed）は、同じ 1 文の中で「済みで、動くものは無い」と言い切る（「merge 済みで、私が動くものは無い。」）。PR でないときの言い切りは参照の「PR でないとき」
- **`where`（前回から。並びの先頭の項）**: `N 日前（M/D）` に何をしたか。N は機械の行に有ればそれ、無ければ（作成・渡された時点の行は日付だけ）機械の日付から今日までを数える（年は今年と見る）。同じ日なら「今日（M/D）」、前日なら「昨日（M/D）」。**その後の動きを後ろの項に**——誰も動いていないならその旨、動いたなら誰が何を（**人は名前で**。「相手」と書くと誰かで止まる）。発言を「」に入れるのはその人の語そのままのときだけ。私宛の依頼があれば、いつ誰から何が来て、済んでいるか未対応か（未対応なら `next` の先頭）。その後に push があれば「私の痕跡以降に変わった file」の件数を同じ欄に。機械が「この件で私はまだ何もしていない」と言うなら、その旨から始め、起点は私に渡された時点（誰の何で）か作成（誰が立てた）にする。末尾に手元の 1 文——`--switch` で呼んだときは今のブランチを絶対名で（「手元は main から feat/123-x に移した」／「手元に feat/123-x は無かったので origin から取り、main から移した」／「手元は feat/123-x に居る」／「手元は main のまま（手元に未コミット 3 件があるので feat/123-x へ移していない）」／「手元に feat/123-x は無く、origin にももう無い（PR は merge 済み）。手元は main のまま」）。移らなかったときの今のブランチは**機械の行の末尾の括弧から写す**。推測で main と書かない。手元の 1 文を書くのは、機械が「ブランチ」の行か「手元のブランチ」の節を出したときだけ
- **`turn`（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。`headline` に出した別の番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。機械の「上に積む」があれば、この PR を base にしている PR として番号と誰のものかを 1 文（この PR が止まると一緒に止まる）。CI は落ちた本数と中身の箇所数を分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・CI の本数・返事待ちの指摘の件数は、止めているものの行に機械が出すので書かない。書くのは、そのうちどれが効いていて、原因は何か。止めているものが無いなら、無いことが分かるように
- **`next`（次にやること）**: 1 項に 1 つの動作を 60 字まで（理由は `turn` へ）。ページは先頭の 3 手を出し、残りは畳む。**空にしない**——待ちなら、何を待ち、動いたら何をするか。閉じた件（merged・closed）は、先頭を「この件で私が動くものは無い」にし、任意の後片付け（残った会話を解決にする・後から読み直す）があれば後ろに「（任意）」を付けて並べる。私が入っていない PR で待ちなら「依頼が来たら本文と変更を読む」「レビューを返す」と来た場合を並べ、来ない場合を最後の項に「来なければこの PR で私が動くことは無い」と言い切る。機械がブランチに移らなかったときはその一手を先頭に——**機械の行が `→` で一手を書いていればその後ろをそのまま写す**（文言は機械が状況で変える。自分で組み立てない）。別の worktree なら「<path> で続ける」。手元に無いだけなら機械が origin から取って移るので `gh pr checkout` を書き足さない。一手が「依頼先を決める」なら、機械の「依頼先の候補」を括弧で添えてよい（候補の名前と機械が付けた理由のまま）。「X に依頼を出す」とは書かない（決めるのは私）。ページは、先頭の項が「前回から」の commit の sha を含めば「差分へ」、返信・会話・指摘の語を含む最初の項に「指摘へ」、CI・赤の語を含む最初の項に「CI へ」の飛び先を付ける
- **`unseen`（見ていないもの）**: 機械の申告（上限で切れた分・GitHub の外・結び付いていない commit・痕跡の基準が近似）はページの末尾に機械が並べる。AI が足すのは、機械が言っていない穴だけ——確かめようとして確かめられなかったこと（読めなかった CI のログ・引けなかった別の番号）、会話の要約で消えた分。機械が数で出しているもの（未解決の件数・CI の本数・承認の数）は見ている——書かない
- **この PR がすること（`lead`・`figure`・`terms`・`explain`・`points`）の読み手**: この件を**初めて見るエンジニア**。HTTP・DB・LLM・CI のような一般の技術は知っているが、このリポジトリが何の製品か、どんな部品で出来ているか、この件の前の議論や番号の中身は知らない。技術に疎い人向けにやさしく言い換えるのではない——前提を飛ばさず、仕組みの水準まで**詳しく**書く。上の欄（いまの番・前回から）は仲間向けに短く、この節は初見向けに詳しく、と読み手が違う。節の全部が同じ読み手で、変更点や図だけを読む人もいる——ひとこと・図・変更点に出る語も、説明に出る語と同じに扱う。本文が薄い（無い・1 行だけ）なら、その旨を 1 文書いてから `gh pr diff`（commit は `git show`）で分かることを事実で書く
- **`lead`（ひとこと。節の先頭に大きく出る）**: 1 文・120 字まで。製品の中の**どこの**話か、**誰の**ために**何を**どう変えるかを、前提を知らない人に（「勤怠アプリの承認画面で、承認者が差し戻しの理由を書けるようにする」）。目的は一通りにしか読めない形で（「X が黙って替わらないようにする」のような打ち消しは、何が変わるのかが逆に読める）。番号・記号だけで済ませない
- **言葉の選び方（この節の全部に。いちばん先に効かせる）**: 初見の人が新しく覚える語の数を最小にする。この順で:
  1. **業界で定着した語で言う**: 社内の呼び名・作者の造語・コードの名前は、それが何かを、この業界の技術者なら誰でも通じる語で言い換える（「`Ledger`」ではなく「残高の動きの記録」、「ホップ表」ではなく「中継先の一覧」）。ここで言う一般の言葉は**業界の標準の技術語**で、やさしい日本語ではない——スパン・ターン・マイグレーション・upsert・ファクトリ・契約テスト・プロンプトインジェクションは、そのまま使う。標準の語を日本語に作り替えない（「処理の記録」ではなくスパン、「移行の SQL」ではなくマイグレーション。作り替えると、初見の技術者は頭の中で標準の語に戻す手間を負う——読み役 3 人が揃って詰まった実測）。標準の語が有るのに社内で別の名で呼んでいるなら、標準の語を先に、社内の名を後ろに添える。仕組みは、何のためにあるかまで言う（「分析用の書き出しに社員の氏名を残さないため、氏名を hash に置き換える」。何をするかだけでは、壊れたときに何が困るのかが読めない）
  2. **名前は、読む人がこの先で出会うときだけ残す**: 差分・画面・設定・議論でその名前を探すことになるなら、一般の言い方の後ろに 1 回だけ添える（「残高の動きの記録（`Ledger`）」）。それ以外のコードの名前・社内の呼び名は出さない
  3. **新しい概念を減らす**: 件の結論に効かない仕組み・例外の一覧・途中の経緯は説明に入れない。変更点でも、1 点の中に初めて出る概念を 2 つ以上入れない（入るなら、その点は細かすぎる）
  4. **語は作らない**: 標準の技術語があればそれを使う（「保存先の口」ではなく「保存先のインターフェース」）
  5. **一般の言葉で言えず、節の中に何度も出る語だけを `terms` に置く**——一覧は最後の手段で、目安は 5 個まで
- **`terms`（この節に出てくる語。説明の前に一覧で出し、文の中の同じ語には点線が付いて、乗せると意味が出る）**: 上の 5 に当たる語を `{"term": 語, "means": 意味}` で（機械の上限は 16 個）。`means` は 160 字まで、何で・何のために・何をするかを 1〜2 文で（「締め: 月末に勤怠を確定させる処理。締めた月は承認者しか直せない」）。一般の技術語（API・トークン・migration）と、標準の名前（PostgreSQL・Helm）は載せない。製品名でも、このリポジトリでの役割が初見に分からないもの（「Sentry: 例外を集めるサービス。ここでは本番の 5xx だけを送る」）は載せてよい。定義を文の中に長い括弧で差し込まない——1 文が長くなって追えなくなる（初見の読み役が、括弧の入れ子で詰まった実測）
- **`explain`（説明。語の一覧の下）**: この件が何のために・何を・どう変えるか。上の欄も差分も「なぜ」を言わない（28 file の PR で型と木だけ出したら「内容が初見に分かりづらい」と言われた実測）。**1 段落 1 話題**で、段落はこの順で 4〜6 つ:
  1. **前提**: この製品・システムが何をするものか（1 文。README の冒頭の語で）と、この件が触る部品がその中のどこで何をしていて、どうつながっているか
  2. **背景と課題**: 変更の前はどう動いていて、誰が何に困っていたか。いまの本番・既定がどうなっているか。前の番号（#120 など）は番号だけで済ませず、何をした件で、この件とどうつながるかを言う
  3. **何をどう変えるか**（1〜2 段落）: 仕組みの全体の流れ——何が入力で、どこを通り、何が出るか——と、作者が決めた主なこと（上限・既定値・置き場所・断るとき）。**決めたことには理由を添える**（作者が書いた理由・比べた案。振る舞いが場所で違うなら、なぜ違うか）。採らなかった案を出すなら、採らなかった理由も一緒に（理由の無い「採用しなかった」は、読む人に問いだけを残す）。因果は原因を先に書き（「通知の送り手は 1 本しか無い。だから送る前に設定を読む形にした」）、「そのため」で後ろから結ばない。理由が材料に無ければ「理由は本文に無い」と書く。本筋と別の変更を同じ件に束ねているなら、なぜ一緒に入れたかを言う（言わないと、ついでの変更に見える）。file が多ければ、どこが中心でどこが追随か（読みどころ）を 1 文
  4. **使う側から見た変化と、含まれないもの**: 既定の振る舞いが変わるか。既存の設定・配備・利用者に要る作業と、そのままだと壊れる所（壊れるなら何をすれば直るか）。作者がどう確かめたか（本文に有れば）。作者が「含まれない」「未決」と書いたもの

  字数は 400〜1600 字。物差しは差分の規模（file 数）と本文の密度の大きい方（1 file・本文の中身 10 行以内なら 400 字前後、20 行超か 15 file なら 1000 字前後、28 file を超えても 1600 字まで）。短くまとめるより前提を飛ばさないことを先にするが、**1 文 1 情報**（条件を 1 文に 2 つ以上詰めない）・1 段落 5 文まで。言葉は作者のもの（本文・先頭コメント・commit の題の語）。**説明と変更点で同じことを書かない**——説明は全体の流れと主な決定とその理由、変更点は 1 つずつの具体（数え方・エラーの一覧・個々の試験）。file の path・関数名・引数名は入れない（変更点の仕事）。使う側が触る名前（API・表・列・設定の項目）は、役割を言ってから書いてよい。評価語を入れない。状態と経緯は書かない（上の欄の仕事）。先頭コメントが「8 行で切った」と言っていれば、切れた文を作者の言葉として写さず全文を見る
- **`points`（変更点。図のすぐ下に図の凡例として並び、押すと前と後とコードが開く）**: 変更を 1 点ずつ 10 点まで。`title`（何を）・`before`（前。無かったなら省く）・`after`（後）・`code`（その変更の差分。`{"path": 差分の file, "find": その file の差分に在る字}` を 4 つまで。`find` は変更の地図に出ている関数・テスト・設定の名前で、その変更の塊（消した行・前後の変わっていない行を含む）のどこかに在ればよい。行番号では指さない。省くと file の差分を全部）。**初見が仕組みを掴むのに要る変更を選ぶ**——差分の全部を並べる一覧ではない（細部の全部はページの変更の節に機械が出す）。小さな追随（文言・型・試験の言い換え）は 1 点にまとめるか省く。ページは変更点を**図の凡例**として図のすぐ下に番号と題だけで並べ、押すと前と後とコードが開く。乗せると図の箱と線が光り、箱や線を押すとその横に項の前と後が出る——なので**題だけで何の変更かが分かる**ようにし、図の箱と線には `points` で番号を結ぶ（`in`・`was` の付いた箱と `in` の付いた線は必ず。結べない変更点は「図の外」と出る）。6 点以上なら `group`（20 字まで。「Terraform」「chart」「アプリ」「試験」のような置き場か役割）で束ね、同じ `group` の点は続けて並べる——`title` は何がどう変わるかの一言（30 字まで。「締め直しで行を置き換える」）、`before` は困っていたことを振る舞いで 1 文（80 字まで。「同じ月を締め直すと、前回の締めの行が残って 2 行になった」）、`after` はどうなるかを 1 文（80 字まで。「前回の行を置き換え、1 月 1 行に保つ」）。理由・経緯・前の番号は説明へ、数値の列挙や細部はコード（`code`）へ回し、ここに足さない（後の文が中央 90 字になったページで「頭に入らない」と言われた実測）。字数は機械が止める。`code` が差分に無ければ機械が止める——ただし `find` を書けば、この PR で変えていない file（受け先の API の型など）も PR の先頭の版から引ける（詳しくは `docs/catchup-figures.md`）
- **書けたら 2 つ確かめる（この節の全部に）**: (1) ひとこと・図・説明・変更点に出てくる名詞を 1 つずつ見て、一般の技術語でないものを拾う。拾った語ごとに、一般の言葉に言い換えられないかを先に試し、言い換えられないものだけ、前の文で中身を言うか `terms` に置く。(2) **この件を初めて見た同僚が、この節だけ読んで、仕組みと、なぜそう決めたかを自分の言葉で説明し直せるか**
- **`figure`（図。ひとことの下）**: 部品が 2 つ以上あって関係（呼ぶ・渡す・分岐する・前後で入れ替わる）が言えるなら**極力描く**——一直線の鎖でも描く。読み飛ばすかは読む人が決める（実測: 経路が 2 本になる変更を「1 文で言える」と見て描かず、なぜ無いのかと聞かれた）。描かないのは部品が 1 つ・関係が無い（版の数字や台帳の追記だけ）・焦点で指摘か CI に絞ったとき。**形は中身で選ぶ**（`kind`）。1 枚で言い切れなければ、形の違う図を 3 枚まで並び（`[…]`）にする（やり取りの図と画面の図、など）。**描く前に `${CLAUDE_PLUGIN_ROOT}/docs/catchup-figures.md` を Read で読む**（形ごとの JSON・前と後・順に見せる・自由に書く図・字の決まり）。
- 上の欄（`headline`〜`next`）で同じ番号を説明するのは 1 回、`turn` で。番号そのものは何度出てもよい。説明の節は読み手が違う（初見）ので、そこに出す前の番号は、上の欄と別に中身を一言添える

PR でないとき（枝に PR 無し・commit・会話から推定した番号）は、欄ごとの言い切りの形が違う——`${CLAUDE_PLUGIN_ROOT}/docs/catchup-ref.md` の「PR でないとき」を Read で読んでから書く。

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・直訳横文字、この件の中でしか通じない略号、機械の理由文（「私の件に相手の発言があり…」）の丸写し（確かめた結果を書く）、「〜と思われる」「〜のようだ」（確かめていないことは「（未確認）」と付けて書く）
- **この命令書の語を欄に持ち込まない**——材料・機械・型・欄・焦点・スクリプト。ページの節の名前（指摘・CI・変更・手元）は指してよい（「下の指摘 3 件」）。本文（PR の説明文）は普通の語として使ってよい。機械が script 名（what-am-i-doing.py・catchup.py）で書いた口は `/what-am-i-doing`・`/catchup` の呼び名に置き換える
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）。書けたら自分に問え——**`headline` だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか**

## 守ること

- **求められていないのに欠陥探しへ広げるな。** 説明は読む人の理解のためで、レビューを始める合図ではない
- **出力に無いことを断定するな。** 確かめたなら確かめた結果を書く。推測で埋めるな
- **図のラベルを記憶で書くな。** 説明か本文に無い語が要るなら描かない
- **端末にページの中身を書き足すな。** 返すのはページの path と 1 行の要約だけ（ページを開けば全部ある）
- **番号でない語で呼ばれても、質問で返すな。** 会話の話題として描く。例外は受け口の 1 か所（手元にも会話にも対象が無いとき）だけで、その形も受け口に
- **機械がブランチに移らなかったとき、自分で stash・commit・`git switch` を打つな。** 未コミットは別のセッションが編集中の木かもしれない（同じ checkout を複数のセッションで共有していることがある）。理由と一手を `next` に書くだけ。移った後に、移る前に読んだ file を編集するなら読み直す——中身は移った先の枝のもの。PR の commit が手元に無いときも `git fetch` を打たない
- **subagent・Agent・Workflow を立てるな。** `gh` は Bash で直列に呼ぶ。並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる
- **描く材料の JSON を手で直すな。** 事実が違っていれば、機械を呼び直す
- **例の一覧を許可の一覧と読まない。** 文言・場面の例は書き方の一つで、例に無いものも規則に当たれば書く
- 日付・件数は機械の数字をそのまま使う（今日から日数を数えるのは、`where` の「N 日前」の 1 か所だけ）
- open 全件の棚卸しはこの道具の仕事ではない。それは `/whose-turn`
