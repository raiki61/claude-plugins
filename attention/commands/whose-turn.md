open 全件を見渡すフェーズにいる。

いま話題が 1 件（特定の PR・issue・ブランチ）に閉じているなら、ここで止めろ。スクリプトは走らせず、
その 1 件には `/catchup <番号>` を使う。全件走査はその答えを出さないし、母集団を 1 件に絞る引数も無い。

## 役割分担

- **スクリプト（機械）**: 母集団を固定し、判断材料（自分の番 / 相手の番の別・作者・障害の持ち主・自分のレビュー・相手の沈黙・逃がした先の生死・呼びかけとスレッドの全文）を全部出す。判断はしない
- **あなた（AI）**: 材料を読んで「返信が要るか」「見て閉じるだけか」を判定する。母集団を増減させない

## やること

1. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/whose-turn.py --materials $ARGUMENTS` を実行する（引数なし＝自分。`<login>` で他の人、`--all` で全員分を人別に）。出力は `==== ここから下は判定の材料。貼らない ====` の印で 2 つに分かれる。上が報告、下が呼びかけ投稿とスレッドの全文。PR・issue の各行の 2 行目はその URL。

2. 「呼びかけに返信が無い」の各行を、印の下の全文と添えられた事実（直前はあなたの発言 / 👍 済み / open PR が参照）から 4 つに分け、根拠を 1 行ずつ付ける:
   - **要返信** — 質問・確認依頼・レビュー依頼で、まだ答えていない
   - **回答済み** — 本人の質問への答えや、本人が委ねた判断の結果。返す義務は無い
   - **FYI** — 共有・決定通知・お礼。返す義務は無い
   - **別所で継続** — 話が別の PR / issue に移っている（「open PR が参照」があればそちらを読む）

3. `### PR #N スレッド` の材料（返す番があるスレッドの、相手の最後の発言の全文）を 3 つに分け、根拠を 1 行ずつ付ける:
   - **見て閉じる** — 直した報告。コミット SHA や「直しました」で終わり、問いが無い。差分を見て resolve するだけ
   - **要回答** — 問いが返っている。答えるまでそのスレッドは止まる
   - **別所へ逃がした** — 行き先の issue / PR が示されている。行に「逃がした先の open issue で、参照後に動いていないもの」があれば、そこが落ちかけている

   全文で決められないとき（前後の文脈が要るとき）だけ `gh pr view N --comments` / `gh issue view N --comments` で読む。毎回読み直すな——出力は既に本文を持っている。推測で決めるな。

4. スクリプトは PR を「自分の番（今日動かせる）」と「相手の番（相手が動くまで進まない）」の 2 節に分けている。**節を言い直すな。** 挙げてよいのは、出力に並んでいる事実どうしの食い違いだけ——「承認済みなのに未解決スレッドが残る」「レビュー依頼が出ているのに相手が何日も無言」「逃がした先が動いていない」など。節の名前や定義の言い換えは、ずれではない。

5. **死角を、決まった手順だけで潰す。** 出力末尾の「見ていないもの」で「該当 N 件」が付いた行は、上の判定に穴が実際に開いている場所だ。次の 2 つだけ、機械的に確かめる。**各 5 件まで**で、超えた分は「未確認 N 件」と書く:
   - **Team 宛のレビュー依頼**（該当 N 件）: 依頼先の Team に自分が入っていれば、その PR は自分の番。`gh api orgs/<org>/teams/<slug>/members --jq '.[].login'` を Team ごとに 1 回。読めなければ（権限不足）「確かめられない」と書く
   - **本文コメントの噛み合い**（該当 N 件、番号つき）: 挙がっている PR を `gh pr view N --comments` で読み、**自分の最後の発言が、その前の相手の問いに答えているか**だけを見る。答えていなければ「呼びかけ」の要返信に加える

   それ以外の死角（GitHub の外・Projects と通知・担当未設定の issue・スレッドの経緯・close 済みの逃がし先）は確かめに行かない。確かめられないものは、確かめられないと書く。

## 守ること

- **死角の確認は手順 5 の 2 つと上限の中だけ。** それ以上は広げない——全部読みに行けば全件走査の意味が無くなる。読まなかったものは「見ていない」と書き、埋めたことにするな。
- **日数はスクリプトが出した数字をそのまま使う。** 「最後の発言」の日付から数え直すな。日数は今の状態になってからで、誰にも依頼していない PR は最後に動かした日から数えている。発言日から数えると放置に見える。
- **出力に無いことを断定するな。** 材料が足りなければ「材料に無い」と書く。節の名前の言い換えで埋めるな。

## 返答の形

節は**読む人の行動**で割る——今日開くもの、開かないもの、見ていないもの。機械の出力の節（自分の番・相手の番・
呼びかけ・担当 issue）をそのまま写すな。**1 つの番号が行を持つのは 1 つの節だけ。** 他の節から
番号に触れてよいのは、2 件が同じ判断で決まるときだけ（「#1581 と同じ場で返す」）。

**件名を付ける番号は、全部リンクにする。** `[#番号](URL)` の形で、URL は機械の各行の 2 行目から写す。
機械に行が無い番号（死角の確認で節 1 に加えた行）だけ、作者と一緒に `gh pr view N --json author,url` で
1 回引く。どちらでもない URL を組み立てるな——GHES では host が違い、issue と PR で path も違う。
対応する端末では番号だけが表示されてクリックで開け、非対応なら `#番号 (URL)` と展開される。件名を
付けない番号（根拠の中で引く逃がし先・参照元）にはリンクも付けない——機械がその URL を出していない。

この 5 節を、この順・この名前で出す。0 件でも節を消さず「なし」と書く。

### 1. `## 自分の番 — N 件`

今日あなたが動かせるものを全部。**1 行目は `[#番号](URL) 件名`**、2 行目は字下げして `日数  役割  動作 — 根拠`。
根拠が長ければ次の行に続ける。レビュアーの行は、その下に `本文:` と `規模:` の 2 行（機械の行をそのまま）:

```
  [#1505](https://github.com/o/r/pull/1505) shigam 本番追随の前段
        4 日  レビュアー 再レビュー — 250489 が block 1・suggest 7 に対応し
        e50961754 を push
        本文: 本番 shigam を main へ追随させる作業（#1500）の PR ①。
        規模: 23 ファイル +467/-401
  [#1584](https://github.com/o/r/pull/1584) merge queue の台帳
        0 日  実装者     依頼先を決める
```

件名を番号の横に置くのは、番号を見た目がそのまま「何の件か」へ進めるようにするため。日数・役割・動作を
2 行目の固定桁に置くのは、その列だけを縦に見て「すぐ終わる件」と「腰を据える件」を分けられるようにする
ため（1 行目に並べると件名の長さで列がずれる）。

- **番号・日数は機械の出力のまま。** 数え直すな
- **役割は `実装者` か `レビュアー`。** 機械の出力に `作者:` 行が無ければ自分の PR で `実装者`、あれば
  `レビュアー`（機械は作者が自分でないときだけ `作者:` を出す）。呼びかけから立てた行は機械の出力に
  作者が無いので、`gh pr view N --json author` で 1 回だけ引く。列を揃えるため `実装者` の後ろは空白 5 つ、
  `レビュアー` の後ろは 1 つ
- **件名は機械のタイトルから作る。** 型の接頭辞（`fix(ci):` など。scope の語は使ってよい）と括弧書きを
  落とし、何の件かを名指す名詞句に**全角 12 字以内**で縮める。**固有名（ジョブ名・ツール名・ファイル名）は
  そのまま残す**——それで上限を超えるのはよい。一般語に言い換えると（`helm-chart-check` → 「chart 検査」）
  何の件か特定できなくなる。タイトルに無い語・状態・評価を入れない（状態は根拠が受け持つ）。
  **`#番号` は件名に入れるな**——別の件と読まれる。要るなら根拠に書く。件名の場所を作るために根拠の引用を
  削るな——削るのは件名の側。同じ番号には報告のどこでも同じ件名を使う
- 件名を付けるのは**母集団の番号（節 1〜4 の主語）だけ**。根拠の中で引く番号（逃がし先・参照元の PR）
  には付けない——機械がその題名を出していない
- 機械の `レビュー依頼:` は**いま保留中の依頼**だけを出す（レビューが付くと消える）。行が無いのは
  「未依頼か返答済み」で、「一度も依頼していない」ではない。履歴を断定するなら timeline を引け
- **動作はこの 9 語から選ぶ**（2 つ繋げてよい: 「レビューしてマージ」）:
  `レビュー` `再レビュー` `指摘に答える` `判断を返す` `返信する` `見て閉じる` `マージ`
  `依頼先を決める` `CI を直す`
  閉じた語彙にするのは、動作の列だけを縦に見て「すぐ終わる件」と「腰を据える件」を分けられる
  ようにするため。当てはまらない行が出たら、いちばん近い語を使い、根拠側で補え
- **根拠は 2 行目の動作の後ろに 1 句**: 相手・状態・block の要点など、なぜ今その動作なのか。根拠の続きの
  行を足してよいのは、人にしか決められない判断が要るときだけ。根拠が動作の定義の言い直しにしかならないとき
  （「依頼先を決める」＝人へのレビュー依頼が無い）は書かない
- **レビュアーの行には、根拠の下に「何の PR か」の 2 行**: 機械の `本文:`（作者の本文の 1 文）と `規模:`
  （N ファイル +A/-D）を、その順で 1 行ずつそのまま。件名 12 字では次の問いが「内容は？」になる（実測）。
  規模は今日どれから読むかを決める材料で、直近マージの中央値（150 行前後）と比べて大きいなら `規模:` の
  行末に 1 句添える。実装者の行には書かない（本文は自分が書いた）
- **1 件ずつ書く。同じ動作でもまとめない**（まとめてよいのは「端の場合」の 40 件超だけ）。まとめ行は
  番号と件名の対応が読めなくなる
- **要返信の呼びかけは、その PR の行に合流させる。** 呼びかけの節に二度書くな。
  機械の出力の「自分の番」にも「相手の番」にも無い番号（issue の呼びかけなど）だけ、ここに行を立てて
  1 行目の末尾に `（呼びかけから）` と付ける
- **死角の確認で加えた行**は 1 行目の末尾に `（本文を読んで移動）` と付ける。機械に行が無い番号なので、
  作者と URL は `gh pr view N --json author,url` で 1 回引く

**並びはスクリプトが出した順のまま。並べ替えるな。** 加えた行（呼びかけ・死角）だけ、同じ日数の
行の最後に差し込む。この規則があるので、読む人は並びを機械の出力で検算できる。

### 2. `## 相手の番 — N 件`

`食い違い無し N 件` の見出しの下に、役割で 2 段落——`実装者 N — [#番号](URL) 件名・…`（自分の PR。相手の
レビューか再確認を待っている）と `レビュアー N — [#番号](URL) 件名・…`（人の PR。作者の対応を待っている）。
段落の中はスクリプト順。折り返してよい（件数が増えても行は 1 つずつ増えない）。**食い違いのある件は
段落に入れず**、`[#番号](URL) 件名（役割）— 食い違い` の 1 行にだけ出す（同じ番号を 2 回書かない。段落の数と
行の数を足すと見出しの件数になる）。食い違いの条件は 3 つだけ:

- 逃がした先の issue / PR が、参照された後に動いていない
- 自分の承認が出ているのに、未解決スレッドが作者側に残っている
- 相手が何日も無言のまま（機械が出した「〜以降 発言なし」の行がある）

### 3. `## 担当 issue — N 件`

`[#番号](URL) 件名（N 日）` を `・` で繋いだ 1 段落。open PR が動かしていない issue があれば、そこだけ 1 句添える。

### 4. `## 返さなくてよい呼びかけ — N 件`

種別ごとに 1 行（`回答済み` `共有だけ` `別の PR / issue で継続` `決められない`）。各件は
`[#番号](URL) 件名（根拠 1 句）` の形。要返信は節 1 に合流済みなので、ここには出さない。

### 5. `## 見た範囲`

3 行以内。母集団（open PR N 件・issue N 件・担当未設定 N 件）／死角の確認で何を何件読み、判定が
変わったのは何件か／見ていないもの。**番号は書かない**——未確認の件数だけ言う。

### 全体

**目安は 1 画面（50 行前後）。** 節 2〜5 は件数が増えても行が 1 つずつ増えない形なので、伸びるのは節 1
だけになる。節 1 が 25 行を超えるなら「端の場合」の形でまとめて縮めろ。**機械の出力の全文は、
「全文を見せて」と求められたときだけ** 1 文字も変えずコードブロックに貼る。それまでは貼らない。

**表は使うな。** 根拠は文なので、セルに入れると端末で細切れになる。**1 行は 60 桁以内（日本語は
2 桁）を目安に**——2 行目の固定桁が折り返すと、縦に見る列が崩れる。長い根拠は 3 行目に送る。桁は表示される幅で
数える——`[#番号](URL)` は対応する端末では番号の幅だけ。非対応の端末では 1 行目に URL が展開されて
伸びるが、固定桁は 2 行目にあるので、それは許す。

**1 行目の字下げは 2 桁のまま。4 桁以上にするな**——字下げコードブロックに落ちて、リンクが `[#番号](URL)` の
生のまま出る。`--all`（人別）でも、人の見出しの下で字下げを深くして並べるな。人は `###` の見出しで分ける。

### 端の場合

- **自分の番が 0 件**: 節 1 は `なし` の 1 行。他の節はそのまま出す——今日動かすものが無いことと、
  誰で止まっているかは別の情報で、後者は消さない
- **PR が 40 件以上**: 節 1 で同じ動作・同じ根拠の件をまとめる。1 行目に `[#番号](URL) 件名` を `・` で繋ぎ
  （端末幅 100 桁を超えるなら別のまとめにする）、2 行目は 1 つ:
  `[#1584](URL) merge queue の台帳・[#1593](URL) 二重拡張子 YAML` ／ `      0 日  実装者     依頼先を決める`。
  節 2 は羅列のまま。それでも収まらないなら、節 1 の根拠を落として 2 行目を `日数 役割 動作` だけにする。
  **件名は最後まで残せ**——番号だけの行は、読む人が何の件かを引き直すことになる。**行を落とすな**——
  落とすと母集団と合わなくなる

## やらないこと

- `gh pr list` / `gh issue list` / `gh search` で一覧を組み立て直すな。取り方の正本は同梱の `scripts/whose-turn.py` で、判定の定義と見ていないものは `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/whose-turn.py --help` にある。
- 出力に無い項目を足すな。スクリプトが失敗したら、そのエラーをそのまま報告して終わる。
- subagent・Agent・Workflow を立てるな。手順 5 の読みも含めて `gh` は Bash で直列に呼ぶ（5 件で数秒）。並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる（実測 2026-09-02）。
