# /catchup の仕様（正本）

「これどうなってたっけ」への答えを出すツール /catchup（attention プラグインのコマンド。並行作業から戻った人に、PR などの件のどこで止まっていたか・次に何をするかを出す）が、何を受け取り、何をして、何を返すかを決める文書。
読むのは /catchup を直す側（人と、直す AI）で、直す前にここを読み、直す物をここに合わせる。
スキルの文書（`attention/skills/catchup/SKILL.md` と、そこから指す `references/` の別ファイル。AI が実行時に読む指示書）・README（`attention/README.md`。人が読む説明）・
機械（`attention/scripts/catchup.py` と `attention/scripts/lib/changemap.py`・`attention/scripts/lib/catchup_html.py`、雛形 `attention/templates/catchup.html`）・テスト（`tests/catchup-case.py` ほか）は
この文書に従う。食い違ったら、この文書を直すか、相手をこの文書に合わせる。どちらにするかは人が決める。
実行時の AI が読むのはスキルの文書（本文と別ファイル）だけで、この文書は読まない。現状との差（セクション 10）が残る間、実行時の挙動はスキルの文書と
コードのとおり。
スキルの文書の本文（`SKILL.md`）は呼ばれるたびに会話へ丸ごと載り、会話の間ずっと残るので、毎回要る部分と落とし穴だけを置き、
5,000 字以下に保つ（リポジトリのスキルの書き方の標準 `docs/standards/skill-authoring.md`。長い会話で Claude Code が自動で文脈を縮めた〔圧縮した〕後は、各スキルの頭の 5,000 トークンしか付け直されない。日本語の 5,000 字はおよそ 4,400 トークンで、その内に収まる）。
フィールドの書き方・対象の読み方・一覧・PR でないとき・準備・図の形は `attention/skills/catchup/references/` に主題ごとに分け、
本文が「その場面で読む」と指す（2026-10-18 に `commands/catchup.md` と `docs/catchup-ref.md`・`docs/catchup-figures.md` から移した）。
2026-10-16 の測りで、works-dispatch（同じリポジトリの、PR を作業場に開いて Claude Code の会話を立て、/catchup を送るプラグイン）が起動する PR の会話の最初の要求 72〜75k のうち、スキルの文書の本文が 25.1k を占めていた。

書く量は、スキルの文書が「どう書くか」を持つので、ここは「何を・いつ・どこまで」だけ。数値は全部ここに集め、
スキルの文書と README はこの数値を写す。規則には根拠の実測を添えて残す——消すと同じ所でまた割れる。

版: attention 0.24.1 時点の姿に、2026-10-15 の HTML 化（セクション 5。変えた所に日付を付けた）を足した姿を写し、末尾の「現状との差」に、まだ従っていない所を並べる。

## 1. 目的

並行作業から戻った人が、**その件のどこで止まっていたか・次に何をするか**を、この 1 返答だけで取り戻す。
読み手は自分（戻ってきた人）で、会話の文脈も手元のブランチも失っている前提。

3 本の住み分け: 1 件に戻るのが /catchup、open 全件の棚卸しが /whose-turn、いま居るセッションの経緯が /what-am-i-doing。

## 2. 原則（7 つ。以下の全部がこれに従う）

1. **指定があれば、そこへ移ってから追いつく。** PR・issue・ブランチの指定があれば、機械が手元のブランチをそこへ
   `git switch` で移し、そのブランチの上で報告する（戻るとき、会話の位置と一緒に手元のブランチも失われている）。
   指定が無い・既に居るなら、今のブランチから意図を汲む（ブランチの PR → 名前の番号の issue → 手元だけ）。
   移る先が無いこともある（commit・detached・PR を立てずに既定ブランチへ直接 commit する運用）。そのときは
   移らず、その旨を言って報告する。
2. **フル実装の形が主。** 返答は 1 枚のページで、「いまのターン → 前回から → この PR がすること → 指摘 → CI → 変更 → 手元」の
   全部組みが既定（セクション 5。2026-10-15 までは端末の「型 → 説明 → 絵 → 指摘 → CI → 地図 → 手元」）。
   焦点の語で絞るのは急ぐときの口で、既定ではない。作者が自分かどうかで出し分けない。
3. **黙って落とさない。** 材料が有るセクションは落とさない（対象の種類を問わず——commit にも本文と差分が
   有れば説明を書く）。機械の上限で切れた分には必ず続きを出す口（`--full`・`--frame`・`--limit`）があり、
   AI は切れていればその口で取ってから書く。上限は「読む人が埋もれない」ためで、「出さない」ためではない。
   無いものは「無い」と書き、見ていないものは申告する（セクション 8）——空にしない・断定しない・削らない。読む人が
   無言の省略を「なし」と誤認するのが、一番戻れない形。
4. **実物の行を、前後を長めに、言い換えずに。** 指した行・変わった行だけの数行では、読む人が file を開いて
   前後を確かめに行く（実測: 「エンジニアは前後も含めてコードを見たい」「前後が無いと判断もキャッチアップも
   できない」）。単位は関数まるごと（機械が `git diff -W` で切る）で、量を減らすときはまとまり（関数）の数を
   減らし、行を削らない。散文・設定・指摘・CI のように関数の無い所も、意味の単位（見出し・上位 key・
   落ちた理由が読める範囲）まで広げる。今の数値はセクション 7 の表。見せるのは実物と作者の言葉——コードは写す、
   相手の発言は要約しない、木は組み直さない、記憶で書かない。散文は翻訳で、頭の中でコードに戻す往復が要る。
   2026-10-15 からは、ページの差分・指摘の発言・CI のログは機械が実物を描く（AI は写さない。5.4）。
5. **割れて困るものは機械が決め、AI は写す。** 飛び先の行番号・帯・木・日付と件数・写す語・枠の言語名は
   機械が出し、AI は綴りを変えずに写す（セクション 6）。AI に選ばせた所は走行ごとに割れる（実測: 言語名を選ばせたら
   .md の枠が走行によって markdown と plaintext に分かれた）。機械は事実を出して判断はしないが、「どれに
   するか」の選択は機械へ寄せる。2026-10-15 からはもう一歩進めて、写すだけだった所（差分・指摘・ログ・ターンの図・止めて
   いるものの行）は機械がページに描き、AI は判断の要るフィールド（5.1〜5.3）だけを書く。
6. **手元を勝手に変えない。** 機械が手元を変えるのは `git switch` とその 1 本の `git fetch` だけ。AI は
   stash・commit・switch・fetch を打たない（セクション 9）。checkout は別のセッションと共有されていることがあり、
   未コミットは誰かの編集中の木かもしれない。移れなければ理由と一手を書いて止まる。
7. **例は「写す型」でも「許可の一覧」でもない。** スキルの文書の例示（言語名・文言・場面）は書き方の一つ——文言を
   写すと決まった言い回しが場面に関係なく毎回出て雑音になり、一覧を許可と読むと例に無いものが落ちる。例に
   無いものも規則に当たれば付ける・書く。付けて損の無いもの（枠の言語名）は必ず付ける（実測: 例の一覧に
   無い .md を plaintext にして色が消えた）。/catchup の枠は 2026-10-15 から機械が描く（5.4）。

## 3. 受け口

`/catchup [対象] [焦点]`。対象は 1 つ。焦点は 0〜3 語。対象の種類は 6 通り。

| 対象 | 例 | 移る | GitHub | 主な材料 |
|---|---|---|---|---|
| 番号 | `1505` `#1505` | PR の head へ | 見る | PR / issue |
| URL | `https://…/pull/1505` | 同上 | 見る | PR / issue |
| ブランチ名 | `feat/123-x` | そこへ | ブランチの PR が有れば | PR、無ければ手元 |
| 引数なし・`this`・焦点だけ | `/catchup` `/catchup 指摘` | 移らない | 今のブランチの PR が有れば | PR、無ければ手元 |
| commit | `2971ea2` `HEAD~2` `v1.2` `2971ea2..HEAD` | 移らない | 見ない | その commit（範囲なら全部） |
| 会話の話題 | `新しく出たもの` `今の修正` | 移らない | 結び付いた番号だけ | 結び付く対象か、会話 |

GitHub を見るかは対象の種類でなく、PR が結び付くかで決まる——引数なし・this・ブランチ名でも、ブランチに PR が有れば
番号と同じ材料を見る。見ないのは commit と、番号に結び付かない会話の話題だけ。

- 番号だけなら、いま居るリポジトリ。別のリポジトリは URL か `-R owner/repo`
- 「今のブランチから意図を汲む」の順: ブランチの PR → 無ければブランチ名の番号（`chore/1513-…` → #1513）を引いて
  その旨を 1 行（PR でも issue でも、GitHub が返した種類のとおり）→ それも無ければ手元だけ（止めない——
  止めると書きかけの人に何も返らない）→ 未コミット・push していない commit・既定ブランチより先の commit の
  どれも無ければ、**会話から対象を推定する**——直近に出たものを 1 つ（番号・ブランチ・commit・話題。直前に
  commit した話なら HEAD の commit。同じ往復に複数あれば 番号 → ブランチ → commit → 話題 の順。2 つ以上が
  同じ強さなら推定しない）。推定した対象で機械を呼び直し、直接呼ばれたときと同じ形で返す（移らない）。推定
  できなければ、何をキャッチアップしたいかを聞き返す（質問で返してよいのはこの 1 か所だけ。型は書かず、手元の
  事実を言い切ってから渡せるものを聞く）。ブランチ名で呼ばれたときは推定しない（ブランチそのものが対象）
- ブランチ名は、手元のブランチ・origin にだけ有るブランチのどちらでも受ける。移った後は `this` と同じに解く。移れなかった
  とき（追跡 file に未コミットなど）は理由と今の位置を見出しに書き、そのブランチに PR が有れば PR として、無ければ
  ブランチの tip の commit として出す（ブランチ全体の差は移ってから）
- commit は sha・`HEAD~n`・タグ・`ブランチ名` でない任意の commit 指定。範囲 `A..B`（`A...B` は merge-base
  から）も commit と同じ形で、差は A の版と B の版の間、本文は各 commit の題（古い順）。同じ語がブランチの名前にも当たるなら
  ブランチが勝つ（移る）。数字だけの語は番号が先で、7 桁以上で手元の commit に解ければ commit（迷うなら `HEAD~n`）。
  焦点の語と同じ名前（`ci`・`指摘`・`地図`）のブランチ・タグは対象にできない（先に焦点として読む）
- 会話の話題は、番号でも commit でもブランチでもない語。AI は先に、会話の中で何に結び付いているかを解く——番号・
  ブランチ・commit に結び付いていればそれが対象（直前に commit した話なら HEAD、このセッションで入れた commit が
  複数なら 一番古いもの^..一番新しいもの の範囲）で、直接呼ばれたときと同じ形で全部出す（移らない）。会話に
  しか無い話題だけ、機械は弾き、AI が会話を材料に話題の形で書く（実測: 「今の修正」を話題の形で書いたら、
  commit 4 件は push 済みで手元は空、型だけになって「何も出ない」と言われた）。
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。
  PR が有り得ない状態——GitHub の remote が無い・detached——だけは「PR が無い」と同じに扱い、手元だけを出す
- **質問で返さない。** どの種類でも、型で出す。例外は上の 1 か所——手元にも会話にも対象が無いとき

焦点の語は `指摘`・`地図`・`CI`。付けると末尾の材料をその 1 つ（複数可）に絞り、無ければ機械が「無い」と
1 行出す。指摘・CI を PR でない対象に付けたときは「その材料は PR / issue のもの」と 1 行出す。地図は差分が
有る対象（commit）にも効く。

オプション（機械）:

| 旗 | 効き | 効く対象 |
|---|---|---|
| `--switch` | 該当のブランチへ移る | 番号・URL・ブランチ名 |
| `--full` | 本文・発言の上限を外す | 全部 |
| `--frame <path>` | その 1 file の変更を上限なしで | PR・commit（手元は what-am-i-doing.py の `--frame`） |
| `--limit N` | その後の出来事の件数（既定 12） | PR・issue |
| `-R owner/repo` | リポジトリを指す | 番号 |
| `--me <login>` | 「私」を差し替える | PR・issue |

スキルの文書は番号・URL・ブランチ名に `--switch` を付けて呼ぶ。`this`・commit・会話の話題では付けない。

## 4. 移る（`--switch`）

- 移る先: PR は head のブランチ。issue は名前にその番号を持つ手元のブランチが **1 本のとき**だけ。ブランチ名はそのブランチ
- 手元に無い PR のブランチは、origin からその 1 本だけ `git fetch` して作って移る。名前と追跡先は `gh pr checkout`
  と同じ。issue のブランチは origin から探さない（番号で選ぶのは当て推量）。ブランチ名で来たブランチが手元に無く origin に
  だけ有れば、origin/<名前> を追跡するブランチを作って移る（`git switch` の既定と同じ）
- **移らない**条件（理由と、今どこに居るかを見出しの「ブランチ」の行に書く）: 追跡 file に未コミットが
  ある（未追跡だけなら移る）／merge・rebase・cherry-pick の途中／別の worktree に checkout 済み／origin にも
  もう無い（merge 済みで削除）／fetch が失敗（認証は端末に聞かず失敗する）／fork の PR で手元の同名のブランチが
  head の commit を含まない／`index.lock` が有る
- 手元を変えるのは `git switch` とその 1 本の `git fetch` だけ。pull・merge・stash・commit・`gh pr checkout`
  はしない。戻すのは `git switch -`
- 移った・既に居たときに「手元のブランチ」のセクションが付く（push していない commit・PR の head より後ろの数・
  未コミットの木）。移らなかったときは見出しの「ブランチ」の行に理由と今の位置だけ
- AI は、移らなかったとき自分で stash・commit・switch を打たない（別のセッションが編集中の木かもしれない）。
  理由と一手を「次にやること」に書く。移った後に編集するなら file を読み直す

## 5. 返答の形（フル実装）

**2026-10-15 に変えた**: 返答は端末の長い文から、機械が決まった雛形で描く **1 枚の HTML** になった。端末に返すのは
ページの path と 1 行の要約だけ。実測: 端末の返答は 4,000〜28,000 字（中央値 約 15,000 字）で、その約 9 割は AI が
機械の枠を写しただけのコードだった。AI が自分で書いた部分は約 1,000 字。写すだけの部分は機械が描けば割れず
（原則 5）、AI の手間も減る。持ち主は VS Code の Remote-SSH で、拡張 Simple HTML Viewer を使って見る（5.10）。
雛形の見た目は、同じ日に持ち主が承認した試作（GitHub Primer の色、差分は diff2html 3.4.56、構文の色は
highlight.js 11.12.0。どちらも雛形に埋め込み、実行時に外を読まない）。

流れ: AI は機械を `--out` で呼び、文字の材料（AI が読む）と描く材料（JSON。AI は読まない）を受け取る。材料を読み、
書く前に確かめ（セクション 6）、**フィールドの JSON**（5.1〜5.3）を書いて `catchup.py --render <描く材料> <フィールド>` を呼ぶ。機械がページを
書いて一覧を組み直し、VS Code で開き、path と 1 行を出す。AI はその 2 行だけを返す。

ページのセクションはこの順。機械が材料の有るセクションだけを描く:

| # | セクション | 中身 | 書くのは |
|---|---|---|---|
| 1 | 見出し | 件名・番号・状態・作者・規模・閉じる issue | 機械 |
| 2 | いまのターン | ターンの札と立場、`headline`、`next`、止めているものの行（未解決の会話・CI・承認・取り込み・取り込み先・依頼先の候補・担当） | 札と行は機械、文は AI |
| 3 | 前回から | ターンの受け渡しの流れ（GitHub の PR の会話の流れの形。印・誰が・何を・いつを縦に並べ、最後に「いま」）、`where`、`turn` | 流れは機械、文は AI |
| 4 | この PR がすること | `lead`、`figure`、`explain`、`points`（変更点ごとに差分を開ける） | AI（差分は機械） |
| 5 | 指摘 | 人が入っている未解決スレッド | 機械 |
| 6 | CI | 赤ごとに、落ちた step のログの末尾 | 機械 |
| 7 | 変更 | 前回から（私の痕跡以降）と全体の差分 | 機械 |
| 8 | 手元 | 「ブランチ」の行と「手元のブランチ」のセクション | 機械 |
| 9 | 見ていないもの | `unseen` と機械の申告 | 両方 |

対象の種類ごとに描かれるセクション（○ 描く／△ 材料が有れば／– 描かない）:

| 対象 | いまのターン | 前回から | がすること | 指摘 | CI | 変更 | 手元 |
|---|---|---|---|---|---|---|---|
| PR | ○ | ○ | ○ | △ | △ | ○ | △ |
| issue | ○ | ○ | △ | – | – | – | △ |
| ブランチに PR 無し | ○ | ○ | △ | – | – | △ | ○ |
| commit | ○ | ○ | △ | – | – | ○ | – |
| 会話の話題 | ○ | ○ | – | – | – | – | – |

会話の話題が番号・ブランチ・commit に結び付いていれば、その対象の行（セクション 3）。話題の行は、会話にしか無いものだけ。

焦点の語で絞ったときは、絞った材料のセクションだけ（説明と図は `地図` のときだけ書く）。

### 5.1 フィールド（旧「型」。いまのターンと前回から）

AI が書く JSON。`headline`・`where`・`turn`・`next` は必須、`unseen`・`lead`・`figure`・`explain`・`points` は無ければ省く。`title` は
会話の話題のときだけ（材料が無いので件名を AI が書く）。知らないフィールド・空の文字列・範囲の外は、機械が 1 件 1 行の
日本語で言って終了コード 2 で止める（`catchup_html.validate_fields`）。

旧「型」の 5 段落は、フィールドに 1 対 1 で移った。段落ごとの規則（何を書くか）は変えていない:

| 旧 | フィールド | 中身 |
|---|---|---|
| 1 段落目（太字） | `headline` | 誰が何をしたので誰が何をするターンか。60 字までの 1 文（番号と件名は書かない。2026-10-16）。所有を先に。取り込み先のブランチの PR。「私の側は終わり」。状態の値は書かない |
| 2 段落目 | `where` | `N 日前（M/D）` に何をしたか、その後の動き（人は名前で）、私宛の依頼、変わった file の数、手元の 1 文 |
| 3 段落目 | `turn` | 止めているもの・原因・誰が外せるか。別の番号の説明はここで 1 回。上に積む PR。赤い CI の原因の数。止めているものの行の値は繰り返さない |
| 4 段落目 | `next` | 一手ずつの並び（旧の `→` の鎖を項に割った）。空にしない |
| 最後の 1 行 | `unseen` | 機械の申告に足す穴だけ（機械の申告はページの末尾に機械が並べる） |

変えたこと:

- **文体は常体の短文**（旧: です・ます）。ページは読む人が上から 5 秒（いまのターン）・1 分（前回から・この PR がすること）・
  5 分（指摘・変更）の順に読む作りで、承認された試作のフィールドが常体だった
- **字数の目安（12 行・450 字）は外した。** 段落がフィールドに割れ、ページのセクションが場所を決めるので、行の目安は意味を失った。
  判定は読みやすさのまま——`headline` だけで用が足りるか、1 文 1 情報
- **「見ていないもの」を削らない規則は機械に移った。** 機械の申告はページの末尾に機械がそのまま並べ、AI は足すだけ
  （原則 3 の「無言の省略」を機械の側で塞ぐ）
- **いまのターンは一言・次の一手・札・箇条（2026-10-16）。** `headline` は 60 字までで番号と件名を書かない。`next` は 1 項 60 字まで
  で、ページは先頭の 3 手を出して残りを畳む。状態は短い札を 1 列に並べる。`where`・`turn` は 1 項 1 事実の短い文の並び（60 字まで・4 項まで）で、
  ページは箇条で描く。時刻と件数を段落に詰めたら「いまの番が頭に入らない」と言われた。1 つの文字列も受ける
- **状態は 1 か所（2026-10-16）。** CI の本数・承認・取り込み・未解決の件数は、いまのターンの「止めているものの行」に機械が出す。
  `headline` と `turn` で同じ値を繰り返していた（1 枚に同じ状態が 3 回出て読みにくいと言われた）ので、文には書かない。
  `headline` は 1 文にし、次の一手は `next` の先頭に任せる（ページは `next` の先頭を大きく描く）
- 対象が PR でないときの言い切り（「今のブランチ main に PR は無く…」「2971ea2 は 9/6 に私が…」「「新しく出たもの」は…」）と、
  閉じた件の「済み」は、旧と同じでフィールドに書く

### 5.2 説明のセクション（`lead`・`figure`・`terms`・`explain`・`points`。初見向けに詳しく）

**2026-10-16 に変えた**: 読み手を「この件を初めて見るエンジニア」と決めた。一般の技術は知っているが、製品が何か・
部品の役割・前の番号の中身は知らない。本文は仲間向けに前提を飛ばして書かれているので、それを写すと説明も前提を
飛ばす（持ち主が「説明がもはや色々前提にしている」と言った）。上のフィールド（5.1）は仲間向けに短く、このセクションは初見向けに
詳しく、と読み手を分ける。前提は README の冒頭・触る部品の file の先頭・本文が指す前の番号の冒頭で埋める。

セクションの並びは、ひとこと（`lead`）→ 図（`figure`）→ 変更点（`points`）→ このセクションの語（`terms`）→ 説明（`explain`）。
幅（2026-10-16）: ページは 1600px まで広げ（デスクトップで最も多い 1920 幅の画面の VS Code の枠に合わせる）、読む文の
1 行は 46em（46 字前後。WCAG 2.2 の 1.4.8 の日本語 40 字の目安に近い）にそろえる。図・変更点の凡例・差分は広く使い、窓が
1400px 以上なら凡例を図の右に置いて、スクロールしても見えたままにする。窓が 1200px 以上なら、左にセクションと件数の目次を固定し、説明の右に
「このセクションの語」を並べる。コードは凡例や箱の中で開かず、画面の 9 割の窓（dialog。Esc で閉じる）で開く。図は、向き（横・縦）と
前後の 2 枚の並べ方（上下・左右）を全部組んでみて、字が等倍以上で窓に収まる形のうち高さが一番低いものを機械が選ぶ（AI の
`dir` は同じくらいなら優先）。どれも縮めないと入らなければ、縮め方が一番小さい形にする。囲みは、その枚に在る箱だけを包む（2026-10-16「全体の再デザインがいる」と言われて組み直した。高さだけで
選ぶと縮めた形ほど低くて勝ち、横に長い図の字が 9px まで小さくなって「図が小さい」と言われ、字の大きさを先に守る形にした）。
変更点は図の凡例として図のすぐ下に番号と題だけを並べ、押すと前と後とコードが開く。項に乗せると図の箱が光り、箱を
押すと、その横に札が出て項の前と後が並び、コードは札のボタンで開く（凡例の項へ飛ばしたりコードの窓をいきなり開いたりすると
「ストレスが大きい」と言われた）。線も番号とコードを持て、線の字を押すと同じ札が出る（資格情報の種類や受け先の API が受け取る形を
見たいと言われた。2026-10-16）。凡例は、窓が 1400px 以上なら図が少し縮んでも右に置く。
コードは差分に無い file も `find` で指せ、`--render` が PR の先頭の版（材料の `head.oid`）から、手元に同じ commit があれば `git show`、
無ければ GitHub から読む。`group` で束ねる（2026-10-16。表・色の札・小さく積んだ前後と試して、どれも「頭に入らない」と言われ、
持ち主が「変えたことも全部図でやってくれていい」と言った）。
セクションの全部が同じ読み手で、変更点や図だけを読む人もいるので、語の扱いはセクションの全部に当てる。

- `lead`: 1 文・120 字まで。製品のどこの話か・誰のために何をどう変えるか
- 言葉: 初見の人が新しく覚える語の数を最小にする。社内の呼び名・造語・コードの名前は、まず業界で定着した技術語（スパン・
  マイグレーション・upsert のような標準の語。やさしい日本語ではない）で言い換え、読む人がこの先で出会う名前だけを 1 回添える。件の結論に効かない仕組みは入れない。2026-10-16 に持ち主が
  「用語を一般的な言葉で言えるように最大限努力するのが先」と言った——語の一覧を足したら、サブエージェントは社内の語を残して
  一覧で定義する方に流れ、1 件 15 語になった。次の試しでは逆に、サブエージェントが標準の技術語まで日本語に作り替え（「処理の記録」＝スパン）、
  初見の読み役 3 人が揃って詰まったので、一般の言葉は業界の標準語だと決めた
- `terms`: 一般の言葉で言えず、セクションの中に何度も出る語だけ（目安 5 個、機械の上限 16 個）、語と意味（160 字まで）。ページは説明の前に一覧で
  出し、文の中の同じ語に点線を引いて、乗せると意味を出す。定義を文の中に括弧で差し込むと 1 文が長くなり、初見の
  読み役が括弧の入れ子で詰まった（2026-10-16、3 件の試しで）ので、定義は文の外に出す。語は作らない（標準の技術語が
  あればそれ、社内の呼び名はそのまま使って意味を言う）
- `explain`: 1 段落 1 話題で、前提／背景と課題／何をどう変えるか（1〜2 段落）／使う側から見た変化と含まれないもの の
  順で 4〜6 つ（機械は 0〜6 個を許す）。仕組みは入力・通り道・出力と作者が決めた主なことまでで、決めたことには理由を
  添える（材料に無ければ無いと書く）。使う側の段落には、既存の設定・配備に要る作業と壊れる所、作者がどう確かめたか。
  1 文 1 情報・1 段落 5 文まで。説明と変更点で同じことを書かない（説明は流れと決定、変更点は 1 つずつの具体）。
  file の path・関数名は入れない（変更点の仕事）。評価語・状態・経緯は入れない
- `points`: 変更を 1 点ずつ（題・前・後）10 点まで。各点に、差分の file と、その差分に在る字（`find`）で、その変更の
  差分を 4 つまで結ぶ。行番号では指さない（行を知るには差分の枠まで読むことになり、読む量が 1 件 4 万〜6 万字増える。
  2026-10-16 実測）。機械が差分に当たるかを確かめ、ページは点を押すとその差分を開く

字数（`explain`）の物差しは、差分の規模（file 数）と本文の密度の大きい方。本文の行数は中身の行だけで数える（空行・
署名・session の URL を除く。機械の括弧の数字はそれ込み）:

| 材料 | 目安 |
|---|---|
| 1 file・本文の中身 10 行以内 | 400 字前後 |
| 本文の中身 20 行超か 15 file | 1000 字前後 |
| 28 file 以上 | 1600 字まで |

（旧は 200〜800 字・3 段落。初見に前提と仕組みを言うには足りなかった）

### 5.3 図（`figure`。ひとことの下。極力描く）

極力描く。部品が 2 つ以上あって関係（呼ぶ・渡す・分岐・前後）が言えるなら、一直線の鎖でも描く（読み飛ばすかは
読む人が決める。2026-09-10 に決めた——以前は「並びが言葉で遠いときだけ」で、経路が 2 本になる変更を描かずに、
なぜ無いのかと聞かれた）。描かないのは部品が 1 つ・関係が無い・焦点で指摘か CI に絞ったとき。ラベルは説明と作者の語だけ、
関係は機械の「名前の言及」か本文が言う関係だけ（推測は「（未確認）」）。

**2026-10-16 に変えた**: 形を 1 つ（箱を左から矢印で繋ぐ鎖を前後 2 行）に決めていたのをやめ、中身で形を選ぶ
（`kind`）。鎖では、部品の分岐・往復・画面・値の表を言えなかった。AI は形ごとの決まったフィールド（JSON）だけを書き、
座標・色・動きは機械が付ける（AI が書く量を図 1 枚あたり数百字に抑える）。

| kind | 中身 | 上限 |
|---|---|---|
| `graph` | 部品のつながり・データの流れ・構成。囲み・表の列・変更点の番号・差分を箱に持てる | 箱 20・線 30・囲み 6 |
| `sequence` | 役者の間のやり取りの順 | 役者 6・やり取り 20 |
| `steps` | 時間の順の段（担い手の列を持てる） | 列 5・段 16 |

- 順に意味があれば `play`（graph はコマ 2〜10、sequence・steps は `true`）。機械が、画面に入った図を順に光らせ、

`figure-check.py` は /catchup では使わない。/what-am-i-doing の端末の絵には今も使う）

### 5.4 箇所（2026-10-15 で廃止。変更のセクションを機械が描く）

旧は、指摘・地図・会話の話題が共有する「箇所」の形（罫線・太字の `path:行`・言語名つきの枠に機械の `| ` の行を写す・
60 桁・字下げを落とす・文字列の中を畳む）を AI が組んでいた。今は機械が差分を GitHub の Files changed と同じ形
（行番号・`+`/`-` の色・行の中の差・構文の色。diff2html と highlight.js）で全部描くので、AI は行を写さない。
原則 4（実物の行を、言い換えずに）は機械の側で満たす——差分は機械が取った実物で、要約しない。

文字の材料（AI が読む側）の枠・帯・飛び先・言語名・前後の広さは変えていない（セクション 7）。AI は説明を書くために読む。

### 5.5 指摘

機械が、人が入っている未解決スレッドを 1 件ずつ GitHub のレビューのスレッドの形で描く: 見出し（path:行。GitHub の
その発言へのリンク）と札（私が返すターン／相手のターン・前回から変更あり／変わっていない・行がずれている）→ 指摘の行を含む
差分の抜粋（PR 全体の差分の hunk から前 5 行・後 4 行。差分に無い行なら head の前後の行）→ 私の最後の発言（冒頭だけ）と
相手の最後の発言（全文。引用の行は落とす）を古い順に → 前回から file が変わっていれば、その差分への飛び先。
「前回から変わったか」は「私の痕跡以降に変わった file」の一覧で決める（関数の単位ではなく file の単位）。妥当かの判断は書かない。

### 5.6 CI

機械が、落ちたチェックを 1 件ずつ描く: チェック名とログへのリンク、最後の `##[error]` の文、失敗した step のログの
末尾（材料と同じく最後の `##[error]` まで。`##[error]` の行に色）。ログが取れなかったチェックはその旨。

### 5.7 変更（旧「地図」）

機械が差分を、見え方を切り替えられる形で描く。PR では **前回から**（私の痕跡の基準の commit から head まで、作者側が
触った file だけ。取り込みが挟まれば base 側の変更が混ざりうると断る）と **PR 全体**（GitHub の Files changed と同じ
base...head の文脈 3 行）の 2 つで、前回からが有れば既定。全体では前回から変わっていない file を畳む。手元に base と
head の commit が有れば git、無ければ `gh pr diff` と GitHub の compare から取る。差分が上限（`MAP_DIFF_CAP`。40 万字）を
超えたら載せず、GitHub への飛び先だけ。commit・範囲はその差、PR 無しのブランチは未コミット（追跡している file）と既定
ブランチより先の差。木・同じ階層・名前の言及は描かない（GitHub と同じ並びの file の見出しで足りる）。規模（file 数・±行数・
直近マージの中央値と上位 25%）はセクションの見出しの横に。

### 5.8 手元

機械の「ブランチ」の行と「手元のブランチ」のセクション（push していない commit・PR の head より後ろの数・未コミットの木）を、
そのまま 1 つの枠に。AI は `where` の末尾に手元の 1 文を書く（5.1）。

### 5.9 置き場と一覧（2026-10-15 に足した）

- ページは `~/.cache/attention/catchup/<owner>-<repo>/<番号>.html`。同じ件は上書き。commit は `commit-<sha>`、範囲は
  `range-<a>-<b>`、PR 無しのブランチは `branch-<名前>`（origin が無ければ置き場は `local-<ルートの名前>`）、会話の話題は
  `topics/<title の hash>`
- 書くのは同じ階層の一時ファイルから置き換え（拡張の自動の再読み込みが書きかけを読まない）
- 一覧 `~/.cache/attention/catchup/index.html` は、ページごとに 1 行（件・件名・誰のターン——待ちなら誰を待つか——・次の一手・
  更新・相対リンク）を新しい順に。描くたびに、各ページの頭に埋めた小さな JSON を読んで組み直す（別の一覧の file を
  持たないので、並行して描くセッションが互いの行を消さない。消したページは次の組み直しで落ちる）
- ページは外を読まない 1 つの HTML で、どのブラウザでも開ける。スクリプトで描くので、スクリプトを止めた表示では中身が出ない
  （その旨を noscript で出す）

### 5.10 開き方と準備（2026-10-15 に足した）

- 描いた後、`ATTENTION_CATCHUP_OPEN=0` でなければ VS Code で開く。CLI は PATH の `code`、無ければ
  `~/.vscode-server/cli/servers/*/server/bin/remote-cli/code` の新しいもの。窓の socket（`vscode-ipc-*.sock`）を `TMPDIR`（無ければ
  `/tmp`）と XDG_RUNTIME_DIR から新しい順に集め、`code --status` が 0 で返るものを生きているとし、生きている**全部**で
  `code --reuse-window <ページ>` を打つ。実測（2026-10-15）: herdr の中の会話は、herdr を起動した時の古い VSCODE_IPC_HOOK_CLI を
  継いでいた。持ち主が見ていた窓は、生きた 2 つの socket の古い方で答えた。生きた socket が無い（VS Code が繋がっていない。
  同じ日に観測）なら開かず、path を出すだけ。開けなくても catchup は失敗にしない。`code` は外部コマンドなので時間を区切る
  （`CODE_TIMEOUT_SEC`）
- works-dispatch が起動する会話は `ATTENTION_CATCHUP_OPEN=0` を持つ（持ち主の窓に何十枚も開かない）
- 準備は `/catchup setup`（`catchup.py --setup`）: 生きた窓を探す → 拡張 `austin-spagnolo.simple-html-viewer` が
  `~/.vscode-server/extensions` に無ければ入れる → `~/.vscode-server/data/Machine/settings.json` に
  `workbench.editorAssociations` の `"**/.cache/attention/**/*.html": "simpleHtmlViewer.preview"` と
  `"simpleHtmlViewer.autoRefresh": "onFileChange"` を足す（他の key は消さない。書く前に同じ階層へ控えを置く。注記の有る
  file は書き直さず、足す行を示す）→ 見本を描いて開く → したことと足りないものを出す。`--setup --check` は何も変えずに
  確かめるだけ。確かめた事実（2026-10-15）: この 2 つを Remote の Machine の設定に置けば効き、`/` を含む glob が Remote の
  file に当たる。拡張のスクリプトは信頼したワークスペースで動く（既定の `simpleHtmlViewer.activeContent: trustedWorkspaces`）

  繋がっていなければ path だけ。ページはどのブラウザでも開ける

## 6. 機械と AI の分担

機械（`catchup.py`）は事実だけを出し、判断しない。文字の材料（AI が読む）とページの構造（雛形が描く）は同じ取得から
組む。AI は材料を読み、**書く前に確かめ**、フィールドを書く。コードの行・差分・発言・ログ・木は機械がページに載せ、AI は写さない。

確かめること（スキルの文書の「書く前に確かめる」）: `CI: 赤` なら落ちた理由／`（名指しは無い。私の件への発言）` なら私への
依頼か・既に済んでいないか／止めている原因が別の番号なら、その番号の誰のターンか（`gh pr view` を 1 回）／会話に GitHub に
無い依頼が出ていれば、誰のターンか・次に誰が何をするか（立場）は GitHub ではなく会話の側に従って書く／取り込みが判定中（UNKNOWN）なら 1 回だけ引き直す。

AI が材料から**読んでフィールドに使う**語（綴りを変えると探せない。テストがスキルの文書・README・この文書で同じ綴りを検査する）:
`取り込み先`・`上に積む`・`依頼先の候補`・`私の痕跡以降に変わった file`・見出しの `ブランチ` の行・`手元のブランチ`・
`本文（材料）`・`指摘（材料）`・`CI が落ちた理由（材料）`・`変更の地図（材料）`・`見ていないもの`・`← 私が返すターン`・
`← 私が最後に発言している（相手のターン）`。描く口 `--render` と、開かない旗 `ATTENTION_CATCHUP_OPEN=0` も同じ綴りで持つ。

端末に返すのはページの path と 1 行の要約だけ（全文を求められたときだけ、報告のファイルを 1 文字も変えずコードブロックで）。
日付・件数は機械の数字。「私」は `gh` の認証ユーザで、手元の `git config user.email` と一致する commit は私の push と数える。

## 7. 上限と、続きを出す口

| 何 | 上限 | 続き |
|---|---|---|
| 作者の本文 | 60 行 | `--full` / `gh pr view` |
| 閉じる issue・参照先の冒頭 | 12 行 | `--full` / `gh issue view` |
| 閉じる issue・参照先の件数 | 3 件ずつ | `--full` |
| 相手の発言（スレッド） | 40 行 | `--full` |
| その後の出来事 | 12 件 | `--limit` |
| 変更の中身 1 file | 300 行 | `--frame <path>` |
| 変更の中身 合計 | 800 行 | `--frame <path>` |
| 取った commit | 100 本 | 見ていないものに書く |
| レビュー依頼の出来事 | 100 件 | 100 件を取り切り、それより前が有りうるときだけ見ていないものに書く（件数は無い） |
| 指摘（スレッド）の件数 | 10 件 | `--full` |
| 私の発言以降の変更（1 スレッド） | 200 行 | `--full` / `gh pr diff` |
| CI の赤の件数 | 3 件 | `--full` |
| 機械が置く帯の幅 | 78 桁 | なし（AI は触らない。60 桁の規則の外） |

`--frame` は 1 file だけを出すので、合計の上限は掛からない。この表と下の表は文字の材料（AI が読む側）の値で、ページの
差分は上限（`MAP_DIFF_CAP` の文字数）まで全部載る（5.7）。

前後の広さ（原則 4。機械の既定値。足りなければ AI が file・head から足す）:

| 何 | 今の値 | 足す口 |
|---|---|---|
| 長い関数を畳む閾値 | 200 行 | file を開く |
| 畳むとき変更の前後に残す | 30 行 | file を開く |
| 枠に残す前の行（変更前） | 15 行 | `gh pr diff` |
| 散文・設定の文脈 | 前後 10 行 | file を開く |
| 散文で AI が意味の単位まで足す上限 | 飛び先から 30 行 | なし |
| 指摘の行の前後 | 関数まるごと（字下げのある def / class も境目。境目が無い・200 行超・窓より小さい関数は前後 5 行） | head から足す |
| 枠の共通の字下げ | 落とす（見出しに桁数） | なし（AI は戻さない） |
| 文字列リテラルを畳む閾値 | 中が 8 行超（先頭 3・末尾 1 を残す） | file を開く |
| CI のログ | 3〜15 行 | URL を開く |
| 近い変更を 1 枠にまとめる間 | 3 行 | なし |

原則 3 により、AI は「上限で切れた」と機械が言っていれば、その口で取ってから書く。取ったものは見ていない
ものに書かない（もう見ている）。取れなかったものだけ見ていないものに残す。

## 8. 見ていないもの（機械が申告してページの末尾に並べ、AI が `unseen` で足す）

- PR / issue: 上限で切れた分（コメント・レビュー・スレッド・commit の総数と取った数）、結び付いていない
  commit（名前ごと）、GitHub の外のやり取り、痕跡の基準が近似のとき
- PR のレビュー依頼の出来事: 機械は新しい 100 件だけを取る。100 件を取り切り、GitHub がそれより前の出来事を「無い」と
  答えなかった（hasPreviousPage が true か、返ってこなかった）ときだけ、1 項を出す。総数は取れないので件数は書かない。
  /catchup を呼んだ利用者（以下「私」）が作者の PR では、取った 100 件に人宛の依頼が無いと、機械は「私は人へ依頼して
  いない」と見て判定する。だが、取っていない古い出来事に依頼があれば、その判定は違う。そこで機械は、判定が次のどちらかに
  なったときだけ、同じ項の末尾に「前に依頼していれば、こう読む」の 1 文を足す（判定の文言は、文字の材料の見出しの次の
  行と、ページの頭の札に出る）:
  - 理由が「人宛のレビュー依頼を出した記録は無い」（依頼先の候補も出している）→ 前に依頼していれば再依頼のターンで、
    依頼先の候補は要らない
  - 待ちが「担当 X 待ち」（X は担当〔assignee〕の login）→ 前に依頼していれば担当待ちではなく、依頼先を決めるのは私
- 手元だけ: GitHub 側（PR があっても見ていない）
- commit: GitHub 側、前後の commit（範囲は親との差 1 つ。merge は第 1 親との差）、取り込まれたか・origin
  との前後
- 会話の話題: 会話の要約で消えた分

## 9. 守ること

- 求められていないのに欠陥探しへ広げない。説明は理解のためで、レビューの合図ではない
- 出力に無いことを断定しない。確かめていないことは「（未確認）」
- 図のラベルを記憶で書かない
- 番号でない語で呼ばれても質問で返さない
- 機械が移らなかったとき、自分で stash・commit・switch を打たない。PR の commit が手元に無くても `git fetch` を打たない
- subagent・Agent・Workflow を立てない。`gh` は Bash で直列に呼ぶ
- スキルの文書の語（材料・機械・型・フィールド）と GitHub / CI の語をフィールドに持ち込まない。初出は「中身 → 記号」
- 端末にページの中身を書き足さない。返すのはページの path と 1 行の要約だけ
- 描く材料の JSON を手で直さない（事実が違えば機械を呼び直す）
- open 全件の棚卸しはしない（/whose-turn）
