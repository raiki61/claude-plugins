# /catchup の仕様（正本）

「これどうなってたっけ」への答えを出す道具 /catchup が、何を受け取り、何をして、何を返すかを決める文書。
命令書（`attention/commands/catchup.md`。AI が実行時に読む指示書）・README（`attention/README.md`。人が読む説明）・
機械（`attention/scripts/catchup.py` と `attention/scripts/lib/changemap.py`）・テスト（`tests/catchup-case.py` ほか）は
この文書に従う。食い違ったら、この文書を直すか、相手をこの文書に合わせる。どちらにするかは人が決める。
実行時の AI が読むのは命令書だけで、この文書は読まない。現状との差（10 節）が残る間、実行時の挙動は命令書と
コードのとおり。この文書は直す側（人と、直す AI）が読む。

書く量は、命令書が「どう書くか」を持つので、ここは「何を・いつ・どこまで」だけ。数値は全部ここに集め、
命令書と README はこの数値を写す。

版: attention 0.22.0 時点の姿を写し、末尾の「現状との差」に、まだ従っていない所を並べる。

## 1. 目的

並行作業から戻った人が、**その件のどこで止まっていたか・次に何をするか**を、この 1 返答だけで取り戻す。
読み手は自分（戻ってきた人）で、会話の文脈も手元の枝も失っている前提。

3 本の住み分け: 1 件に戻るのが /catchup、open 全件の棚卸しが /whose-turn、いま居るセッションの経緯が /what-am-i-doing。

## 2. 原則（5 つ。以下の全部がこれに従う）

1. **指定があれば、そこへ移ってから追いつく。** PR・issue・ブランチの指定があれば、機械が手元の枝をそこへ
   `git switch` で移し、その枝の上で報告する（戻るとき、会話の位置と一緒に手元の枝も失われている）。
   指定が無い・既に居るなら、今の枝から意図を汲む（枝の PR → 名前の番号の issue → 手元だけ）。
   移る先が無いこともある（commit・detached・PR を立てずに既定ブランチへ直接 commit する運用）。そのときは
   移らず、その旨を言って報告する。
2. **フル実装の形が主。** 返答は「型 → 説明 → 絵 → 指摘 → CI → 地図 → 手元」の全部組みが既定（4 節）。
   焦点の語で絞るのは急ぐときの口で、既定ではない。作者が自分かどうかで出し分けない。
3. **出せるものは全部出す。** 材料が有る節は落とさない（対象の種類を問わず——commit にも本文と差分が
   有れば説明を書く）。機械の上限で切れた分には必ず続きを出す口（`--full`・`--frame`・`--limit`）があり、
   AI は切れていればその口で取ってから書く。上限は「読む人が埋もれない」ためで、「出さない」ためではない。
4. **コードで見せる箇所は、前後を長めに。** 指した行・変わった行だけの数行では、読む人が file を開いて
   前後を確かめに行く（実測: 「エンジニアは前後も含めてコードを見たい」「前後が無いと判断もキャッチアップも
   できない」）。単位は関数まるごと（機械が `git diff -W` で切る）で、量を減らすときは節（関数）の数を
   減らし、行を削らない。散文・設定・指摘・CI のように関数の無い所も、意味の単位（見出し・上位 key・
   落ちた理由が読める範囲）まで広げる。今の数値は 7 節の表。
5. **例は許可の一覧ではない。** 命令書の例示（言語名・文言・場面）は書き方の一つで、例に無いものも規則に
   当たれば付ける・書く。付けて損の無いものは必ず付ける——枠の言語名がそれで、機械の `（言語名 X）` が有れば
   写し、無ければ拡張子から AI が付ける。例に無い名前でも付ける（色が付かなくても害は無い。実測: 例の一覧に
   無い .md を plaintext にして色が消えた）。今の規則は 5.4。

## 3. 受け口

`/catchup [対象] [焦点]`。対象は 1 つ。焦点は 0〜3 語。対象の種類は 6 通り。

| 対象 | 例 | 移る | GitHub | 主な材料 |
|---|---|---|---|---|
| 番号 | `1505` `#1505` | PR の head へ | 見る | PR / issue |
| URL | `https://…/pull/1505` | 同上 | 見る | PR / issue |
| ブランチ名 | `feat/123-x` | そこへ | 枝の PR が有れば | PR、無ければ手元 |
| 引数なし・`this`・焦点だけ | `/catchup` `/catchup 指摘` | 移らない | 今の枝の PR が有れば | PR、無ければ手元 |
| commit | `2971ea2` `HEAD~2` `v1.2` | 移らない | 見ない | その commit |
| 会話の話題 | `新しく出たもの` | 移らない | 結び付いた番号だけ | 会話 |

GitHub を見るかは対象の種類でなく、PR が結び付くかで決まる——引数なし・this・ブランチ名でも、枝に PR が有れば
番号と同じ材料を見る。見ないのは commit と、番号に結び付かない会話の話題だけ。

- 番号だけなら、いま居るリポジトリ。別のリポジトリは URL か `-R owner/repo`
- 「今の枝から意図を汲む」の順: 枝の PR → 無ければブランチ名の番号（`chore/1513-…` → #1513）を引いて
  その旨を 1 行（PR でも issue でも、GitHub が返した種類のとおり）→ それも無ければ手元だけ（止めない——
  止めると書きかけの人に何も返らない）→ 未コミット・push していない commit・既定ブランチより先の commit の
  どれも無ければ、**会話から対象を推定する**——直近に出たものを 1 つ（番号・ブランチ・commit・話題。直前に
  commit した話なら HEAD の commit。同じ往復に複数あれば 番号 → ブランチ → commit → 話題 の順。2 つ以上が
  同じ強さなら推定しない）。推定した対象で機械を呼び直し、直接呼ばれたときと同じ形で返す（移らない）。推定
  できなければ、何をキャッチアップしたいかを聞き返す（質問で返してよいのはこの 1 か所だけ。型は書かず、手元の
  事実を言い切ってから渡せるものを聞く）。ブランチ名で呼ばれたときは推定しない（枝そのものが対象）
- ブランチ名は、手元の枝・origin にだけ有る枝のどちらでも受ける。移った後は `this` と同じに解く。移れなかった
  とき（追跡 file に未コミットなど）は理由と今の位置を見出しに書き、その枝に PR が有れば PR として、無ければ
  枝の tip の commit として出す（枝全体の差は移ってから）
- commit は sha・`HEAD~n`・タグ・`ブランチ名` でない任意の commit 指定。同じ語が枝の名前にも当たるなら
  枝が勝つ（移る）。数字だけの語は番号が先で、7 桁以上で手元の commit に解ければ commit（迷うなら `HEAD~n`）。
  焦点の語と同じ名前（`ci`・`指摘`・`地図`）の枝・タグは対象にできない（先に焦点として読む）
- 会話の話題は、番号でも commit でも枝でもない語。機械は弾き、AI が会話を材料に書く。会話の中で番号に
  結び付いていれば、その番号で機械も走らせて補う（このとき移らない）
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。
  PR が有り得ない状態——GitHub の remote が無い・detached——だけは「PR が無い」と同じに扱い、手元だけを出す
- **質問で返さない。** どの種類でも、型で出す。例外は上の 1 か所——手元にも会話にも対象が無いとき

焦点の語は `指摘`・`地図`・`CI`。付けると末尾の材料をその 1 つ（複数可）に絞り、無ければ機械が「無い」と
1 行出す。指摘・CI を PR でない対象に付けたときは「その材料は PR / issue のもの」と 1 行出す。地図は差分が
有る対象（commit）にも効く。

オプション（機械）:

| 旗 | 効き | 効く対象 |
|---|---|---|
| `--switch` | 該当の枝へ移る | 番号・URL・ブランチ名 |
| `--full` | 本文・発言の上限を外す | 全部 |
| `--frame <path>` | その 1 file の変更を上限なしで | PR・commit（手元は what-am-i-doing.py の `--frame`） |
| `--limit N` | その後の出来事の件数（既定 12） | PR・issue |
| `-R owner/repo` | リポジトリを指す | 番号 |
| `--me <login>` | 「私」を差し替える | PR・issue |

命令書は番号・URL・ブランチ名に `--switch` を付けて呼ぶ。`this`・commit・会話の話題では付けない。

## 4. 移る（`--switch`）

- 移る先: PR は head の枝。issue は名前にその番号を持つ手元の枝が **1 本のとき**だけ。ブランチ名はその枝
- 手元に無い PR の枝は、origin からその 1 本だけ `git fetch` して作って移る。名前と追跡先は `gh pr checkout`
  と同じ。issue の枝は origin から探さない（番号で選ぶのは当て推量）。ブランチ名で来た枝が手元に無く origin に
  だけ有れば、origin/<名前> を追跡する枝を作って移る（`git switch` の既定と同じ）
- **移らない**条件（理由と、今どこに居るかを見出しの「ブランチ」の行に書く）: 追跡 file に未コミットが
  ある（未追跡だけなら移る）／merge・rebase・cherry-pick の途中／別の worktree に checkout 済み／origin にも
  もう無い（merge 済みで削除）／fetch が失敗（認証は端末に聞かず失敗する）／fork の PR で手元の同名の枝が
  head の commit を含まない／`index.lock` が有る
- 手元を変えるのは `git switch` とその 1 本の `git fetch` だけ。pull・merge・stash・commit・`gh pr checkout`
  はしない。戻すのは `git switch -`
- 移った・既に居たときに「手元のブランチ」の節が付く（push していない commit・PR の head より後ろの数・
  未コミットの木）。移らなかったときは見出しの「ブランチ」の行に理由と今の位置だけ
- AI は、移らなかったとき自分で stash・commit・switch を打たない（別のセッションが編集中の木かもしれない）。
  理由と一手を「次にやること」に書く。移った後に編集するなら file を読み直す

## 5. 返答の形（フル実装）

節はこの順。付く条件を満たす節は全部付ける。

| # | 節 | 付く条件 | 上限 |
|---|---|---|---|
| 1 | 型 | 常に | 目安 12 行・450 字（上限ではない） |
| 2 | 説明 | 本文か差分が有る | 3 段落・200〜800 字 |
| 3 | 絵 | 部品 3 つ以上で並びが言葉で遠い | 1 図・60 桁・14 行 |
| 4 | 指摘 | 人が入っている未解決スレッド | 1 件ずつ |
| 5 | CI | 赤が有る | 1 件ずつ・3〜15 行 |
| 6 | 地図 | 差分が有る | 箇所 3〜6（file が足りなければ有るだけ）・300 行前後 |
| 7 | 手元 | 手元の節を機械が出した | 木は全部 |

対象の種類ごとに付く節（○ 付く／△ 材料が有れば／– 付かない）:

| 対象 | 型 | 説明 | 絵 | 指摘 | CI | 地図 | 手元 |
|---|---|---|---|---|---|---|---|
| PR | ○ | ○ | △ | △ | △ | ○ | ○ |
| issue | ○ | △ | – | – | – | – | ○ |
| 枝に PR 無し | ○ | △ | – | – | – | △ | ○ |
| commit | ○ | △ | △ | – | – | ○ | – |
| 会話の話題 | ○ | – | – | – | – | – | △ |

焦点の語で絞ったときは、型と、絞った節だけ（説明と絵は `地図` のときだけ付く）。

### 5.1 型（5 段落。どの対象でも）

同僚に口で話す散文。太字の 1〜2 文で始まり、段落の順は固定。コードブロック・表・ラベル列を使わない。
文体は です・ます。全体は 12 行前後・450 字前後を目安に、段落は 4 文以内。**字数は上限ではなく、判定は
読みやすさ**——2 行目だけ読んで用が足りるか、1 文 1 情報、要らない修飾が無いか。目安を超えるなら、要素
（立場・一手・観測値・見ていないもの）でなく修飾を削る。

1. **太字**: `[#番号](URL)（件名 12 字以内）` と立場、どこで止まっているか（私が動かせる／別の番号を
   動かすと進む／誰かを待っている）と一手。別の番号が私のものなら所有を先に。同じ段落に太字でなく
   「何をする PR か」を 1〜2 文
2. 最後にしたこと: `N 日前（M/D）` に何をしたか。その後の動き（人は名前で）。私宛の依頼と、済んでいるか。
   私の痕跡以降に変わった file の数。移る呼び方なら手元の位置を 1 文（絶対名。移らなかった理由も）
3. 止めているもの: 何が・原因・誰が外せるか。別の番号の説明はここで 1 回。取り込み先が既定ブランチで
   ないときはその枝の PR、上に積む PR。CI は本数と箇所数。承認・衝突・未解決スレッドの観測値を末尾に 1 文
4. 次にやること: 動作を `→` で繋ぐ。空にしない。機械が一手を `→` で書いていればそのまま写す
5. 見ていないもの（1 行）: 機械の末尾から、この件に固有のものと GitHub の外。削らない

対象が PR でないときの 1 段落目は、言い切りで始める——「今のブランチ main に PR は無く、名前にも番号が
ありません」「2971ea2 は 9/6 に私が main へ直接 commit した …」「「新しく出たもの」は #1505 の再レビューで
私が見つけた suggest 4 件で …」。

閉じた件（merged・closed）は「済み。動くものは無い」と言い切る（機械も見出しで「済み」と出す。「待ち」と出すと
読む人が迷う——実走の実測）。

対象が PR でないときの 3・4 段落目: 3 段落目は「GitHub 側は見ていない」と断ったうえで、手元の事実
（未コミット・push していない commit・PR が無いこと）を書く。4 段落目は手元から決まる一手（push する・PR を
立てる・commit を番号か URL で呼び直す・書きかけを続ける）。材料が無いことは、無いと書く（「空にしない」と
「断定しない」を両方満たす形）。

### 5.2 説明（3 段落・200〜800 字）

この件が何のために・何を・どう変えるかを、この件も周辺の部品も知らない人に。材料は作者の本文（閉じる
issue・本文が指す issue / PR の冒頭を含む）と、地図の先頭コメント・docstring・変更の枠。段落は 背景と課題／
何をどう変えるか／使う側から見た変化と含まれないもの。path・設定の key・関数名は入れない（箇所の仕事）。
評価語を入れない。状態と経緯は書かない（型の仕事）。記号は初出で「中身 → 記号」。
本文が薄いなら、その旨を 1 文書いてから差分で分かることを事実で書く。commit も PR 無しの枝も同じ形・同じ字数。

字数の物差しは、差分の規模（file 数）と本文の密度の大きい方。本文の行数は中身の行だけで数える（空行・署名・
session の URL を除く。機械の括弧の数字はそれ込み）:

| 材料 | 目安 |
|---|---|
| 1 file・本文の中身 10 行以内 | 200 字 |
| 本文の中身 10 行超 | 400 字前後 |
| 本文の中身 20 行超か 15 file | 740 字 |
| 28 file | 800 字まで |

### 5.3 絵（説明の 2 段落目の直後。条件に当たるときだけ）

部品が 3 つ以上で、並びが言葉で遠い（間に挟まる・経路が 2 本・向きが変わる・同居する）ときだけ。判定は
「絵を消すと 2 段落目に 1 文以上足さないと『どこに何が入るか』が言えないか」。ラベルは説明と作者の語だけ、
線は機械の「名前の言及」か本文が言う関係だけ（推測は「（未確認）」）。1 行 60 桁（日本語は 2 桁）・14 行
以内・変更前と変更後は上下。出す前に `figure-check.py` を通す。焦点で指摘か CI に絞ったとき・1〜2 file の変更では描かない。

### 5.4 箇所（指摘・地図・会話の話題が共有する形）

罫線 `---` で区切り、見出しは太字で `n/N` と backtick の `path:行`（行は機械の「飛び先 path:行」から。
file ごと削除された file だけ行が無い）。その下に 1 行——どこから使われるか／誰が何を求めているか、その
人の言葉で。枠は言語名つきのコードブロックに、機械の `| ` の後ろを 1 文字も変えず写す（帯は機械が置く。
unified diff は貼らない）。**言語名は必ず付ける。** 機械が各枠の見出しの末尾に置く `（言語名 X）` が有ればそれを写し
（highlight.js の名前。表に無い種類は拡張子そのまま。木は diff、絵は text、CI のログは plaintext）、無い枠
（`gh pr diff`・`git show`・head の file から写した行）は拡張子から AI が付ける。**例の一覧に無い名前でも付ける**
（色が付かなくても害は無い）。plaintext は拡張子が無く中身（shebang など）からも分からないときだけ（実測: 例に
無い .md を plaintext にして色が消えた）。**1 節は関数まるごとで、前後を長めに**（原則 4）。関数の途中で切らない。
減らすのは関数の数で、行ではない。順は呼ぶ側 → 本体 → helper。枠の中は 1 行 60 桁以内（機械が置く帯 78 桁は
除く。散文——コメント・docstring・md の段落——は語の切れ目で折り返してよく、「1 文字も変えず」はコードの行の話）。
注釈は行の上に、その言語のコメント記号で `# path:行 （役割）`（記号は機械の薄い行の行頭と同じ）。コードを記憶で書かない。**path と `path:行` は前後を半角スペースで
離す**（見出し・注釈・散文の中でも。端末のクリックは隣の「（」「。」を path に巻き込む）。機械の出力も同じ。

前後の広さは機械が決め、足りない所を AI が広げる:

- コード: 関数まるごと。長い関数は変更の前後を残して畳む（点線 ┅。閾値と残す行数は 7 節）。畳まれた
  中を読むなら file を開く（`--frame` は 1 file の上限を外すだけで、畳みは外れない）。開く file は、PR なら
  head の file（手元がその checkout なら file、無ければ `git show <head の sha>:<path>`）、commit なら
  `git show <sha>:<path>`、手元なら作業ツリーの file。head の sha は機械の出力に無い。
  `gh pr view <番号> --json headRefOid -q .headRefOid`（別リポジトリなら `-R owner/repo` を足す）で取る
- 散文・設定（md・yaml・json など）: 関数の境目が無いので機械は変更の前後 N 行（7 節）。AI は見出し・
  上位 key のような意味の単位まで file から足してよい（足すのは飛び先から N 行以内。7 節。足したら見出しの
  `path:行` を足した先頭に合わせる。遠ければ足さず、足さなかったとは書かない）
- PR の base と head の commit が手元に無い（機械が「文脈は 3 行——」と断る）: AI は `git fetch` を打たず、
  head の file を `gh api` の contents（`?ref=<head の sha>`）で取って関数まるごとに広げる。取れなければ
  3 行のまま写し、道順の 1 文に「前後は 3 行（手元に PR の commit が無い）」
- 指摘: 機械は指摘の行の前後 N 行（7 節）。AI は指摘の行を含む意味の単位（関数なら def から）まで
  head から足す
- CI: 落ちた理由が読める範囲（7 節）

### 5.5 指摘

私が返す番の未解決スレッドを 1 件ずつ箇所で。先頭に道順 1 文（件数と印の内訳）、末尾に相手の番の件の
名前だけ。枠は指摘の行を含む意味の単位まで（5.4）。相手の発言は要約せずその人の語で写す。妥当かの判断は書かない。「直すなら」は相手の修正案が
あるときだけ。

### 5.6 CI

落ちたチェックを 1 件ずつ箇所で。見出しはチェック名、1 行は最後の `##[error]` の文、枠はログの 3〜15 行。
「直すなら」は書かない（原因の判断は型の 3 段落目）。ログが取れなかったチェックは URL とその旨。

### 5.7 地図

説明の後ろに、木の前の 1 文（規模: file 数と ±行数。中央値・上位 25% は、この PR が上位 25% を超えるときだけ
1 句）→ 木 → 道順 1 文 → file ごとの箇所 3〜6 → 残りの file 1 文。木は機械のものをそのまま
```diff で貼り、組み直さない。選び方は入口 → 入口が使う file → 既存への小さな追記。上限で切れた続きは
`--frame`。散文・設定の file も枠で出す（file の種類で節を落とさない）。

### 5.8 手元

機械の「手元のブランチ」の節から、push していない commit と未コミットの件数を型の 2 段落目に 1 文。
未コミットの木があれば末尾に ```diff で貼る。PR も番号も無い枝・会話の話題では、その下に「変更の中身」を
箇所の形で（読む順 1 文 → 関数ごとの箇所）。PR も番号も無い枝で既定ブランチより先の commit が有れば、機械が
その差（merge-base..HEAD。枝全体の差）の木と変更の中身も出すので、地図として同じ形で付ける（続きは `git diff -W`）。

## 6. 機械と AI の分担

機械（`catchup.py`）は事実だけを出し、判断しない。AI は材料を読み、**書く前に 3 つを確かめ**、型に畳む。

確かめる 3 つ: `CI: 赤` なら落ちた理由／`（名指しは無い。私の件への発言）` なら私への依頼か・既に済んで
いないか／止めている原因が別の番号なら、その番号の誰の番か（`gh pr view` を 1 回）。

AI が機械から**そのまま写す**語（綴りを変えると探せない。テストが命令書・README・この文書で同じ綴りを
検査する）: `飛び先 path:行`・`取り込み先`・`上に積む`・`依頼先の候補`・`私の痕跡以降に変わった file`・
見出しの `ブランチ` の行・`手元のブランチ`・`本文（材料）`・`指摘（材料）`・`CI が落ちた理由（材料）`・
`変更の地図（材料）`・`変更の中身`・`見ていないもの`・`← 私が返す番`・`← 私が最後に発言している（相手の番）`・
枠の見出しの `（言語名 X）`（X を ```X に）。

機械の出力は貼らない（全文を求められたときだけ、1 文字も変えずコードブロックで）。日付・件数は機械の数字。
「私」は `gh` の認証ユーザで、手元の `git config user.email` と一致する commit は私の push と数える。

## 7. 上限と、続きを出す口

| 何 | 上限 | 続き |
|---|---|---|
| 作者の本文 | 60 行 | `--full` / `gh pr view` |
| 閉じる issue・参照先の冒頭 | 12 行 | `--full` / `gh issue view` |
| 閉じる issue・参照先の件数 | 3 件ずつ | `--full` |
| 相手の発言（スレッド） | 40 行 | `--full` |
| その後の出来事 | 12 件 | `--limit` |
| 変更の中身 1 file | 300 行 | `--frame <path>` |
| 変更の中身 合計 | 800 行 | `--frame <path>` |
| 取った commit | 100 本 | 見ていないものに書く |
| 指摘（スレッド）の件数 | 10 件 | `--full` |
| CI の赤の件数 | 3 件 | `--full` |
| 機械が置く帯の幅 | 78 桁 | なし（AI は触らない。60 桁の規則の外） |

`--frame` は 1 file だけを出すので、合計の上限は掛からない。

前後の広さ（原則 4。機械の既定値。足りなければ AI が file・head から足す）:

| 何 | 今の値 | 足す口 |
|---|---|---|
| 長い関数を畳む閾値 | 200 行 | file を開く |
| 畳むとき変更の前後に残す | 30 行 | file を開く |
| 枠に残す前の行（変更前） | 15 行 | `gh pr diff` |
| 散文・設定の文脈 | 前後 10 行 | file を開く |
| 散文で AI が意味の単位まで足す上限 | 飛び先から 30 行 | なし |
| 指摘の行の前後 | 関数まるごと（境目が無い・200 行超・平らな file は前後 5 行） | head から足す |
| CI のログ | 3〜15 行 | URL を開く |
| 近い変更を 1 枠にまとめる間 | 3 行 | なし |

原則 3 により、AI は「上限で切れた」と機械が言っていれば、その口で取ってから書く。取ったものは見ていない
ものに書かない（もう見ている）。取れなかったものだけ見ていないものに残す。

## 8. 見ていないもの（機械が申告し、AI が型の 5 段落目に写す）

- PR / issue: 上限で切れた分（コメント・レビュー・スレッド・commit の総数と取った数）、結び付いていない
  commit（名前ごと）、GitHub の外のやり取り、痕跡の基準が近似のとき
- 手元だけ: GitHub 側（PR があっても見ていない）
- commit: GitHub 側、前後の commit（範囲は親との差 1 つ。merge は第 1 親との差）、取り込まれたか・origin
  との前後
- 会話の話題: 会話の要約で消えた分

## 9. 守ること

- 求められていないのに欠陥探しへ広げない。説明は理解のためで、レビューの合図ではない
- 出力に無いことを断定しない。確かめていないことは「（未確認）」
- 箇所のコード・絵のラベルを記憶で書かない
- 番号でない語で呼ばれても質問で返さない
- 機械が移らなかったとき、自分で stash・commit・switch を打たない。PR の commit が手元に無くても `git fetch` を打たない
- subagent・Agent・Workflow を立てない。`gh` は Bash で直列に呼ぶ
- 命令書の語（材料・機械・型）と GitHub / CI の語を返答に持ち込まない。初出は「中身 → 記号」
- path と `path:行` の前後は半角スペース（端末のクリックが隣の文字を巻き込む）
- 枠に言語名を必ず付ける。機械の `（言語名 X）` が有れば写し、無ければ拡張子から。例の一覧は許可の一覧ではない
- open 全件の棚卸しはしない（/whose-turn）
