# 変更が、枯れた解を作り直していないかを、順位まで確かめる

**芯の決まり: 「この問題を自分が初めて解いているはずがない」から始める。リポジトリの外（公式の文書・当のオープンソースのプロジェクトの issue と変更とソース）と、宣言した依存の入っている実ファイルを当たる。特徴が一致するからといって、変更を標準と同じと判定しない。一次情報が選択肢をどの順に並べているかを見つけ、変更がどの選択肢に乗るかを書き、いちばん上でなければ、上の物を採れない訳を書く。**

リポジトリの中の検索と、差分だけの審査も狙いは近いが、元が違う。この観点だけが外へ行く。

## 落とし穴（先に読む）

- **特徴の一致は同じ形ではない。** 枯れた解の劣化した変種は、まさに特徴が一致する形で現れる。（一度測った時: シェルを通さず許可リストを使う変更に、3 回続けて審査が「標準と同じ」を返した。だが標準（OWASP の、OS コマンドインジェクションの防ぎ方の cheat sheet）は「データとコマンドを構造で分ける」を「文字列を検証する」より上に置いていて、変更は下の方に乗っていた。）
- **まず自分の目で見る。** 手元のレビューの指摘から始めない。それを見ると、問題の種類の選び方がそちらへ寄る。
- **変更の目的が渡されない時は、目的を推測で作らない。** 問題の種類は、変更とその依存先から引く。
- **出典の URL なしに断定しない。** ブログや Q&A は仮説に留める。裏が取れなければ「確証なし」と書く。点を確かめるのに要る一次情報は全部取る。落としてよいのは重なる情報源と、同じ事を言う二次情報だけ。
- **「既に手元に在る」に数えるのは、宣言した依存だけ。** ほかの依存が連れてきただけのパッケージは、親が乗り換えた日に消える。それに寄りかかるのは使い残しでなく、採るかどうかの設計の判断。（一度測った例: 宣言に無い検証のライブラリが入っている依存のフォルダに在る事を訳に、「検証の層を自作している」が 3 回続けて審査で挙がり、毎回「依存に上げるか」という別の判断に落ちて、決まらないまま持ち越された。）
- **「手元に在るのに使っていない」は、import している物だけではない。** 変更が import する依存（すぐ出せる集合）から始めるが、そこで止めない。リポジトリが依存に宣言している物——パッケージだけでなく、宣言したプラグインや道具も——は、何も import していなくても探す所である。（一度測った時: プロジェクト自身が依存に宣言した役が import の集合の外に落ち、「作り直しは無い」が 3 回の審査で続けて返った。）
- **「探したが枯れた解は無く、自作は妥当」も正しい結論。** 社内に固有の領域や、事実上の標準がまだ無い領域では合格とする。枯れを疑う事と、何でも既存に押し込む事は違う。
- **「見ていない」は「見て無かった」ではない。** 見た範囲と見ていない範囲を書く。量や時間で止めたならどこで止めたかを書く。差分は見始める所で、見終える所ではない。依る先・近く・呼び元を要るだけ読む。
- **読むだけ。** ファイルを作らず、直さず、消さない。コマンドが拒まれたか要る物に届かなかったら、その確かめは実測していないとして、打ったコマンドとどう拒まれたかを書く。通すために綴りを変えて打ち直さない。
- **外への問い合わせに、対象の名を入れない。**

## 手順

「見る物」は変更の全体に当て、「順位」は変更が解く一般の問題ごとに当てる。

### 見る物

- 対象のリポジトリが自分の審査の手引きを持っていれば、それも読む。
- **問題の種類を抜き出す**: 差分が解いている問題を 1 文で抜き出す。一般の種類（初期化の順・認証と認可・やり直し・キャッシュ・並行の制御・シリアライズなど）に入るなら、枯れた解の有無を疑う。
- **一次情報で裏を取る**: Web で枯れた解と知られた落とし穴を探し、公式の文書・当のプロジェクトの issue と変更・ソースで確証を取る。
- **手元の依存の使い残し**: 宣言した依存の入っている実ファイルを読み、手で作った働きと同じ物が無いか、また既に使っている依存の**設定やオプションで済む話でないか**を確かめる。Web の検索は「世の中に枯れた解があるか」しか見ないので、**「既に手元に入っているのに使っていない」は素通りする**。取り違えの形は 2 つ: (1) 同じ働きを手で書いている（手で書いた側は、本家が持つ付随の働きを欠く事が多い）、(2) 上流の設定 1 つで避けられる問題を、下流に変換を足して潰そうとしている。
- **粒度**: API の使い方だけでなく、自作の小道具・流れや基盤そのものまで見る。いちばん梃子が効くのは「仕組みごと自作していたが、枯れた解があった」の発見。
- **注記の密度を手がかりに**: 説明を厚く書かないと読めない所は、自作が厚い印でもある。枯れた解に乗っていれば読み手が既に知っているので、説明は要らない。注記の割合が飛び抜けて高いファイルや関数を、まず「そもそも自作すべきだったか」で疑う（注記を削る話に直行しない。削るべきは説明でなく、説明を要るようにしている自作かもしれない）。
- **受け入れ済みの弱さも照らし直す**: 変更の説明・README・残りのメモで「分かっていて受け入れた」と書かれた弱さも、照らしから外さない。分かっている事は、解き方が無い事を意味しない（標準の仕組みや、標準が決めている項目〔フィールド〕で置き換えられる、人の手の運用が典型）。

### 順位: 変更が解く一般の問題ごとに

1. 問題を一般の問題の種類として書く。
2. 一次情報で、定番の解と、知られた落とし穴を探す。
3. **順位**: 一次情報が並べる順に、上から選択肢を書く。一次情報を引く。
4. 変更がどの選択肢に乗るかを、その並びの字のまま書く。
5. いちばん上でなければ、上の物それぞれを採れない訳を書く。
6. 順位の無い問題なら、並びは 1 つでよい。順位を付けられる一般の問題が無ければ、そう書き、訳を書く。

## 済んだと言える時

- 一般の問題ごとに、引いた一次情報つきの選択肢の順位・変更が乗る選択肢・上の物それぞれを採れない訳が在る。または、順位を付けられる問題が無かった訳を書いた。
- 指摘ごとに次が在る: **仕組み**（コードの上の因果を 1 文で）・**実測**（動かせる物は動かす。動かせなければ「実測していない」と書き、仮説として出す）・先に済ませた**自分での崩し**（決まりを引くなら、その条件が当たるかを確かめ、周りの実際のコードを読み、崩せなかった物だけを出す）・**誤検出の見積もり**（どんな時にこの指摘が誤りになるかを 1 行）。
- 見た範囲と見ていない範囲を、両方書いた。

## 返し方

一般の問題ごとに: 問題・引いた一次情報つきの選択肢の順位・変更が乗る選択肢・上の物を採れない訳。次に指摘を、それぞれ上の 4 つを付けて。最後に見た範囲と見ていない範囲。場所は、今のファイルのパスと行の番号で、読んで確かめた物で指す。パッチの中の行ではない。ファイルを読めないなら、パスと関数の名などで指す。

## 例

入力: 変更が、外のサービスへの呼び出しを、決まった時間だけ寝てやり直す自前の繰り返しで包む。リポジトリは、そのサービスのクライアントのライブラリを既に依存に宣言している。

返し: 問題: 外への呼び出しのやり直し。順位（クライアントの公式の文書を引用）: 1 クライアントが持つ、間隔を延ばすやり直しの設定。2 手で書いた繰り返し。変更が乗るのは: 2。1 を採れない訳: 見つからない。指摘（実測していない・仮説）: 宣言した依存の設定で済む。見た範囲: クライアントの入っている実ファイル。見ていない範囲: ほかの呼び元。

## 一緒に使うと良いもの

- 外のサービスへの問い合わせ（Web の検索・取りに行く URL）に、見ているリポジトリ自身の名や字を入れない決まり。
