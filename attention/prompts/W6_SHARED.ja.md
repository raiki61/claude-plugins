問いの木の 1 つのノードへの答え方:
- あなたは木の 1 つの問いに答える。末端まで答える: 本物を確かめれば答えが決まる問いまで。何を確かめ、何が分かったかを言う。
- コード・設定・一次の出典を読んで先に決める。PR の自作の部品（検査器・試験のツール・つなぎの台本）は、関数の名前の一覧や骨組みでなく本体を読み、その中の検査の 1 つずつに下の 3 つの問いを当てる。
- 読むだけで、何も走らせない（描画・試験・写しでの試し・インストールをしない）。末端なら、決めるのに何を読んだかを言う。読んでも答えが決まらないなら "unverified" を返し、決めるには何を走らせればよいかを answer に書く。
- status: 読んだ物で答えが決まれば "leaf"、children に挙げる下の問いで決まるなら "split"、読んだが終えられないか走らせる必要があるなら "unverified"、確かめても答えが 1 つに決まらず人が決めるなら "undecided"。
- children: 子の答えがあなたの答えを変えるときだけ分ける。網羅のために子を足さない。子ごとに howParentChanges（どの答えがあなたの答えをどう変えるか）・weight（"big": 答えが反転しうる、"medium": 条件か範囲が変わる、"small": 根拠が 1 つ増えるか減る）・見る所を書く。howParentChanges を書けない子は足さない。
- premises: 確かめずに仮定した物。上の道の前提が違うと分かったら、answer に根拠を書いて "leaf" を返す。根拠が揃わないなら "unverified"。
- evidence（末端のとき）: 根拠の 1 つずつを path・line・quote で（共通の決まりの形）。files: 読んだファイルの全部（リポジトリのルートからの相対）。urls: 頼った URL の全部。gh で読んだ issue・PR・検索は、その URL を書く。
- 公式の一次の文書かソースコードだけを使い（ミラーや写しでなく）、記憶を使わない。二次の記事しか無ければ "unverified"。
- answer は数行に収め、本文を貼らずに在り処を指す。

問いが世の中の解か自作の部品を問うとき:
- OSS・標準のツール・標準の手順が同じ問題をどう解くかを、構造の部品ごとに問う。まず PR が作る部品の全体（その仕組みが解こうとする問題）、次に見つけた物と直しの案の 1 つずつ。PR が足す検査・試験・CI の部品にも当て、同じ部品を持つ標準のツール（検証器・linter・試験のツール）を探す。
- ツールを当てる前に、それが一般の構造のどの部品を持つかを言う。PR が作る部品と同じ部品を持つツールだけを数え、名前が似ていても別の部品を持つ物は数えない。数えたツールを "replacement"（PR の部品を丸ごと置き換えられる）か "foundation"（その上に PR の部品を建てると自前の処理が消える）に分け、PR の部品のファイルを parts に挙げる。
- 当てる先ごとに、世の中の解と、こちらの案が同じかを書く。違えばどちらを採るか。見つからなければ、どこを探したかと "not found" を書く。
- 自作の部品は、ここまでの道が何を仮定していても、ゼロから疑う。構造のどの部品が自作かを名指し、その世の中の解と履歴を掘る。記録（既知の制約・判断）が挙げていても、その行をこの PR が足したなら掘り続ける。
- 自作の部品の本体を読み、その中の検査の 1 つずつに問う: 比べる 2 つの値は既に 1 つの元から作られているか（なら検査は要らない）。ほかの検査が既に同じ物を見ていないか。外のツールの振る舞いを写していないか（なら本物のツールで確かめるか、確かめる訳を消す）。
- OSS が在るかもしれず、世の中がしない自作には何かの訳が在る。見つけたら、なぜ自作になったかを履歴（git log、その行を足した PR と issue）で掘る。
- ツールを今の書き方に当てはめない。こちらの書き方をツールに寄せ、ファイルか関数ごとに、どの自前の処理・決まり・検査が消えるかを数える。消えない物は、なぜかをツールの一次の出典で確かめる。
- 出来合いのツールの上に自分で書く決まり（conftest の Rego の規則など）は自作に数える。
