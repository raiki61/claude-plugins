# /catchup の「この PR がすること」の書き方（ひとこと・説明・変更点・図を書く前に読む）

/catchup（1 件の PR などについて、前回から何が起きたかを 1 枚の HTML のページに描くコマンド）を動かす AI が、ページの「この PR がすること」のセクションに描くフィールド（`lead`・`figure`・`terms`・`explain`・`points`）を JSON で書く前に読む。

目次:

- 読み手と順
- 言葉の選び方
- `lead`（ひとこと）
- `terms`（語の一覧）
- `explain`（説明）
- `points`（変更点）
- `figure`（図）
- 書けたら確かめる

前提: **機械**は `catchup.py` で、`--out` を付けて呼ぶと AI が読む文字の報告（**材料**）を書き、`--render` でページを描く。材料の「変更の地図」のセクションは、変更ファイルの木・名前の言及（変更ファイルの追加行が、ほかの変更ファイルの名前を挙げている所）・新規ファイルの骨組み・既存ファイルの変更の抜粋を並べる。字数と個数の上限は機械が見て、越えたら 1 件 1 行で言う。

## 読み手と順

読み手は、この件を初めて見るエンジニア。HTTP・DB・LLM・CI のような一般の技術は知っているが、このリポジトリが何の製品か、どんな部品で出来ているか、この件の前の議論や番号の中身は知らない。やさしく言い換えるのでなく、前提を飛ばさずに、仕組みの水準まで詳しく書く。ひとことだけ・図だけ・変更点だけを読む人もいるので、どのフィールドに出る語も同じに扱う。

ページはこの順に描く: ひとこと（`lead`）→ 図（`figure`）と、その凡例の変更点（`points`）→ 語の一覧（`terms`）→ 説明（`explain`）。

本文が薄い（無い・1 行だけ）なら、その旨を説明に 1 文書き、`gh pr diff`（commit は `git show`）で分かることを事実で書く。

## 言葉の選び方

初見の人が新しく覚える語の数を最小にする。この順で:

1. **業界で定着した語で言う。** 社内の呼び名・作者の造語・コードの名前は、それが何かを、この業界の技術者なら誰でも通じる語で言い換える（「`Ledger`」でなく「残高の動きの記録」、「ホップ表」でなく「中継先の一覧」）。標準の技術語（スパン・ターン・マイグレーション・upsert・ファクトリ・契約テスト・プロンプトインジェクション）はそのまま使い、日本語に作り替えない（作り替えると、読む人が頭の中で標準の語に戻す手間を負う）。標準の語が有るのに社内で別の名で呼んでいるなら、標準の語を先に、社内の名を後ろに添える。仕組みは、何のためにあるかまで言う（「分析用の書き出しに社員の氏名を残さないため、氏名を hash に置き換える」）。
2. **名前は、読む人がこの先で出会うときだけ残す。** 差分・画面・設定・議論でその名前を探すことになるなら、一般の言い方の後ろに 1 回だけ添える（「残高の動きの記録（`Ledger`）」）。ほかのコードの名前・社内の呼び名は出さない。
3. **新しい概念を減らす。** 件の結論に効かない仕組み・例外の一覧・途中の経緯は入れない。変更点の 1 点に、初めて出る概念を 2 つ以上入れない。
4. **語を作らない。** 標準の技術語があればそれを使う（「保存先の口」でなく「保存先のインターフェース」）。
5. **一般の言葉で言えず、セクションの中に何度も出る語だけを `terms` に置く。** 一覧は最後の手段で、目安は 5 個まで。

## `lead`（ひとこと）

セクションの先頭に大きく出る 1 文。製品の中のどこの話か、誰のために何をどう変えるかを、前提を知らない人に言う（「勤怠アプリの承認画面で、承認者が差し戻しの理由を書けるようにする」）。目的は一通りにしか読めない形で書く（「X が黙って替わらないようにする」のような打ち消しは、何が変わるのかが逆に読める）。番号・記号だけで済ませない。

## `terms`（語の一覧）

説明の前に一覧で出る。文の中の同じ語には点線が付き、ポインタを乗せると意味が出る。

- 形は `[{"term": 語, "means": 意味}]`。`means` は、何で・何のために・何をするかを 1〜2 文で書く（「締め: 月末に勤怠を確定させる処理。締めた月は承認者しか直せない」）。
- 一般の技術語（API・トークン・migration）と標準の名前（PostgreSQL・Helm）は載せない。製品名でも、このリポジトリでの役割が初見に分からない物は載せてよい（「Sentry: 例外を集めるサービス。ここでは本番の 5xx だけを送る」）。
- 定義を文の中に長い括弧で差し込まない。1 文が長くなって追えなくなる。

## `explain`（説明）

この件が何のために・何を・どう変えるかを書く。ページの上のフィールドも差分も「なぜ」を言わないので、ここで言う。1 段落に 1 つの話題で、段落をこの順に 5〜6 つ並べる:

1. **前提**: この製品・システムが何をする物か（1 文。README の冒頭の語で）。この件が触る部品がその中のどこで何をしていて、どうつながっているか。最後に、その部品が世間一般のシステムの全体像（資源を作る層・配信の層・ワークロード・横断の秘密情報や観測など）の中のどの部品・どの境目に当たり、そこで何を揃えたいかを 1 文で書く。この 1 文は、このリポジトリの言葉を使わず、この件の解き方を書かない（4 で別のエージェントに渡す）。
2. **背景と課題**: 変更の前はどう動いていて、誰が何に困っていたか。いまの本番・既定がどうなっているか。前の番号（#120 など）は、何をした件で、この件とどうつながるかを言う。
3. **何をどう変えるか**（1〜2 段落）: 仕組みの全体の流れ（何が入力で、どこを通り、何が出るか）と、作者が決めた主なこと（上限・既定値・置き場所・断るとき）。
   - 決めたことには理由を添える（作者が書いた理由・比べた案。振る舞いが場所で違うなら、なぜ違うか）。理由が材料に無ければ「理由は本文に無い」と書く。
   - 採らなかった案を出すなら、採らなかった理由も一緒に書く。
   - 因果は原因を先に書く（「通知の送り手は 1 本しか無い。だから送る前に設定を読む形にした」）。
   - 本筋と別の変更を同じ件に束ねているなら、なぜ一緒に入れたかを言う。
   - ファイルが多ければ、どこが中心でどこが追随か（読みどころ）を 1 文で言う。
4. **一般の形との違い**: 1 の最後の 1 文だけを、Agent ツールで、ツールを持たないエージェント（convergence-loops の `blind-judge` が入っていればそれ、無ければツールを使うなと頼んだ general-purpose）に渡し、「この部品は一般にどんな問題として扱われ、どんな形で解かれているか（定番の型・OSS・仕様）」を描かせる。差分・本文・リポジトリの名前は渡さない（差分を読んだ目は、この件の作りを一般の形と取り違える）。一般の形は自分で書かず、結果を待つ。段落には、一般の形を 1〜2 文、この件が入った後のその部品の全体の形を 1 文、両者の違いを事実で並べる。違いの良し悪しと、寄せるべきかは書かない。部品を言えない件（版の数字や台帳の追記だけ）は、この段落を省く。
5. **使う側から見た変化と、含まれないもの**: 既定の振る舞いが変わるか。既存の設定・配備・利用者に要る作業と、そのままだと壊れる所（壊れるなら何をすれば直るか）。作者がどう確かめたか（本文に有れば）。作者が「含まれない」「未決」と書いた物。

書き方:

- 字数は 400〜1600 字（4 の段落は数えない）。差分の規模（ファイルの数）と本文の密度の大きい方で決める: 1 ファイル・本文の中身 10 行以内なら 400 字前後、20 行超か 15 ファイルなら 1000 字前後、28 ファイルを超えても 1600 字まで。
- 短くまとめるより、前提を飛ばさないことを先にする。ただし 1 文 1 情報（条件を 1 文に 2 つ以上詰めない）・1 段落 5 文まで。
- 言葉は作者の物（本文・先頭のコメント・commit の題の語）を使う。先頭のコメントが「8 行で切った」と言っていれば、切れた文を写さず全文を見る。
- 説明と変更点で同じことを書かない。説明は全体の流れと主な決定とその理由、変更点は 1 つずつの具体。
- ファイルのパス・関数名・引数名は入れない（変更点に書く）。使う側が触る名前（API・表・列・設定の項目）は、役割を言ってから書いてよい。
- 評価の語、状態と経緯（ページの上のフィールドの仕事）は書かない。

## `points`（変更点）

図のすぐ下に、図の凡例として番号と題だけで並ぶ。押すと前と後とコードが開き、ポインタを乗せると図の箱と線が光る。

- 形は `{"caption": "変えたこと", "items": [{"title": "何を", "before": "前", "after": "後", "code": [{"path": "差分のファイル", "find": "その差分に在る字"}], "group": "置き場"}]}`。
- 初見が仕組みを掴むのに要る変更を選ぶ（差分の全部はページの変更のセクションに機械が出す）。小さな追随（文言・型・試験の言い換え）は 1 点にまとめるか省く。
- `title` は、題だけで何がどう変わるかが分かる一言（「締め直しで行を置き換える」）。
- `before` は困っていたことを振る舞いで 1 文（「同じ月を締め直すと、前回の締めの行が残って 2 行になった」）。前に無かった物なら省く。`after` はどうなるかを 1 文（「前回の行を置き換え、1 月 1 行に保つ」）。理由・経緯・前の番号は説明へ、数値の列挙や細部は `code` へ回す。
- `code` の `find` は、変更の地図に出ている関数・テスト・設定の名前で、その変更の塊（消した行・前後の変わっていない行を含む）のどこかに在ればよい。行番号では指さない。`code` を省くと、そのファイルの差分を全部出す。`find` を書けば、この PR で変えていないファイル（受け先の API の型など）も PR の先頭の版から引ける。
- 6 点以上なら `group`（置き場か役割。「Terraform」「chart」「アプリ」「試験」）で束ね、同じ `group` の点を続けて並べる。

## `figure`（図）

部品が 2 つ以上あって関係（呼ぶ・渡す・分岐する・前後で入れ替わる）が言えるなら、一直線の鎖でも描く。描かないのは、部品が 1 つ・関係が無い（版の数字や台帳の追記だけ）・焦点で `指摘` か `CI` に絞ったとき。説明に一般の形との違いを書いたなら、`table` の図を 1 枚足し、列を「一般の形」と「この件が入った後」にして、違いを 1 項目 1 行で並べる（`tone` は付けない）。

形（`kind`）は中身で選ぶ。1 枚で言い切れなければ、形の違う図を 3 枚まで並び（`[…]`）にする（やり取りの図と画面の図など）。

| 中身 | kind |
|---|---|
| 部品のつながり・データの流れ・構成 | `graph` |
| 誰が誰に何を送るかの順（API・認証の往復） | `sequence` |
| 時間の順の段（ジョブ・移行の手順・状態の移り） | `steps` |
| 画面の見た目（設定画面・フォーム） | `screen` |
| 項目ごとの値（既定値・権限・対応表） | `table` |
| 名前ごとの前と後の短い対比 | `compare` |
| 上のどれにも収まらない | `html` |

### 前と後

前後で変わる図は、1 つの図の中で箱・線・行・部品に `in` を付ける（`"before"` は前だけに在る、`"after"` は後だけに在る）。両方に在って字が変わるなら、`was` に前の字を書く（`was` が使えるのは箱・箱の列・画面の部品・表のセル）。線の字が変わるなら、前の線に `in: "before"`、後の線に `in: "after"` を付けて 2 本にする。機械が前と後の 2 枚に描き分ける。`tone` は変わった所の色（`bad` は悪かった所、`good` は良くした所）で、変わっていない所には付けない。

### 図と変更点を結ぶ

箱と線に、それに当たる変更点の番号（`points` の `items` を 1 から数えた順番）を `"points": [1]` の形で書く。`in` か `was` の付いた箱と、`in` の付いた線には必ず書く（差分の外で作る物・つなぐ物なら `[]`）。結べない変更点は、ページに「図の外」と出る。箱や線を押すと、その横に札が出て、変更点の前と後と、自分の `code` を開くボタンが並ぶ。

### 形ごとの決まり

- **graph**: 座標は書かない（機械が並べる）。`group` は囲み、`sub` は箱の下の補足、`fields` は表の列（`{name, type}`。列も `in`・`was` で前後を描く）、`code` はその箱の差分、`dashed: true` は弱い・任意のつながり。
- **graph の線**（`edges`）: どこからどこへ、どんなデータが流れるか（入出力）を表す。線の字は流れる物の名前だけにする（「渡す」より「文書を multipart で渡す」）。細かい形や資格情報の種類は字に足さず、押すと出る札とコードに任せる（字が長いと図が横に広がって縮む）。線の `code` は、変えた行より先に、流れるデータの形を決めている所を指す: 受け先の API のリクエストとレスポンスの型・キューのメッセージの型・渡す資格情報の種類と Secret のキー・通信を許す規則（NetworkPolicy など）。
- **差分に無いファイルの `code`**: この PR で変えていない受け先の API の型を見せたいときは、そのファイルの path と型の名前を `find` に書く。機械が PR の先頭の版から読み、`find` の行の前 2 行からその塊の終わりまでを「この PR では変えていない」と断って出す。
- **steps**: `lanes` は担い手の列（`{id, text}`。省いてよい）で、段の `lane` はそのどれかの id。段の `text` は何をするか、`when` はいつ（「配備の前」）、`tag` は段に付ける短い印（「新」）、`note` は段の補足。
- **screen**: 部品（`type`）は heading・text・field・textarea・select・radio・checkbox・toggle・button・tabs・list・alert。字は差分の画面の文言から写す（作らない）。見取り図であって画面そのものではないと、題か `caption` で分かるようにする。
- **順に見せる（`play`）**: 順番に意味があるとき（処理の流れ・往復）だけ付ける。graph はコマ（`{text, nodes: [id], edges: ["from>to"]}`）を 2〜10、sequence と steps は `true`。機械が画面に入った図を順に光らせ、線の上に点を流す。
- **html**: 上の形に収まらないときだけ。HTML・インラインの SVG・CSS・SVG の動き（animate）が使える。スクリプト・イベント（`on…`）・外を指す `url(`・フォームの送信は機械が止める。幅は枠（100%）に合わせる。字が枠からはみ出すと、機械がページに注記を出す。

### 図の字

箱・線・役者・段の字は短くし、長い説明は説明か変更点へ回す。ラベルに使う語は、説明（`explain`）と作者（PR などを書いた人）の語だけにする。関係（線）は、材料の「名前の言及」か本文が言う物だけを描き、推測なら「（未確認）」と付ける。図の名詞を全部、説明か本文の語に当てられないなら描かない。

## 書けたら確かめる

1. ひとこと・図・説明・変更点に出てくる名詞を 1 つずつ見て、一般の技術語でない物を拾う。拾った語ごとに、一般の言葉に言い換えられないかを先に試し、言い換えられない物だけ、前の文で中身を言うか `terms` に置く。
2. この件を初めて見た同僚が、このセクションだけ読んで、仕組みと、なぜそう決めたかを自分の言葉で説明し直せるかを問う。
3. ページの上のフィールドで説明した番号を、ここに出すなら、中身を一言添える（読み手が違う）。
