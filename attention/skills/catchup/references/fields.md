# /catchup の欄の書き方（欄の JSON を書く前に毎回読む）

/catchup（1 件の PR などについて、前回から何が起きたかを 1 枚の HTML のページに描く命令）を動かす AI が、欄の JSON を書く前に毎回読む（SKILL.md の手順 4。どの件でも毎回）。中身は欄ごとの書き方・文体・例・言葉。

前提（語は SKILL.md と同じ）:
- **機械**は `catchup.py`。`--out` を付けて呼ぶと、AI が読む文字の報告（**材料**）と、ページの構造の JSON（**描く材料**）を書く。**焦点**は /catchup の対象の後ろに付ける語（`指摘`・`地図`・`CI`）で、材料とページの後ろの節を付けた語の節だけに絞る。**変更の地図**は材料の中の節で、変更ファイルの木・名前の言及（変更ファイルどうしが名前で指し合う行）・新規ファイルの骨組み・既存ファイルの変更の抜粋を並べる。**機械の行**は、機械が材料やページに出した 1 行（「止めているものの行」は、ページのいまの番の節に機械が出す、承認・CI・取り込み・返事待ちの件数などの状態の行）。**欄**は AI が書く下の JSON で、SKILL.md の手順 5 で描く材料と一緒に機械の `--render` に渡り、ページに描かれる。
- **私**は gh の認証ユーザ＝この道具を使ってページを読む人。欄は全部その人の立場で書く（書き手の AI はその人の代理）。「私の指摘」はその人が出した指摘、「私宛の依頼」はその人への依頼、「私の番」はその人が動く番。
- **痕跡**は、私がこの件に残した発言・レビュー・push。材料の「私が最後にしたこと」が最後の痕跡で、「私の痕跡以降」はその時点より後。
- この文書が言い切りの形を書くのは PR と issue のときだけ。PR でないとき（枝に PR 無し・commit・会話から推定した番号）の形と、図の `kind` ごとの JSON はこの文書に無く、SKILL.md の手順 4 が読む先を指す。

## 欄（AI が書く JSON）

```json
{
  "headline": "60 字までの 1 文。誰が何をしたので、いま誰が何をする番か（番号・件名・状態の値は書かない）",
  "where": ["最後にしたこと", "その後の動き（1 項 1 事実）", "…"],
  "turn": ["止めているものの原因と、誰が外せるか（止めているものの行の値は書かない）", "…"],
  "next": ["一手", "その次", "…"],
  "unseen": ["機械の申告に足す、見ていないもの"],
  "lead": "1 文。どこの何を、誰のためにどう変えるか",
  "figure": {"kind": "graph", "caption": "図の題", "nodes": [{"id": "a", "text": "箱"}, {"id": "b", "text": "箱", "in": "after"}], "edges": [{"from": "a", "to": "b", "text": "渡す", "in": "after"}]},
  "terms": [{"term": "この件の中でしか通じない語", "means": "何で、何をするか"}],
  "explain": ["前提", "背景と課題", "何をどう変えるか", "使う側から見た変化と、含まれないもの"],
  "points": {"caption": "変えたこと", "items": [{"title": "何を", "before": "前", "after": "後", "code": [{"path": "差分の file", "find": "その差分に在る名前"}]}]}
}
```

`headline`・`where`・`turn`・`next` は必須。`unseen`・`lead`・`figure`・`terms`・`explain`・`points` は無ければ省く（`figure` は `null` でもよい）。最上位の `title`（上の形には無い。`points` の中の `title` とは別）は会話の話題のときだけ足す（材料が無いので件名をここに）。知らない欄・空の文字列は機械が止める。

文体は**常体の短い文**（「〜した」「〜の番」）。1 文 1 情報。**`where` と `turn` は短い文の並び**（1 項 1 事実、60 字まで、4 項まで。`turn` に書くのは止めているものと、それを誰が外せるかだけ——関係する別の番号の紹介や推測の経緯は書かない。ページは箇条で描く。時刻と件数を段落に詰めると頭に入らないと言われた）。この PR がすることの節は読み手が違い、`explain` は 1 段落 5 文まで。**状態の値（CI の本数・承認・取り込み・未解決の件数）は文に書かない**——いまの番の「止めているものの行」に機械が出しているので、文で繰り返すと 1 枚に同じことが 3 回並ぶ。ページは読む人が上から 5 秒（いまの番）・1 分（前回から・この PR がすること）・5 分（指摘・変更）の順に読むので、上の欄ほど短く。文中の `` `…` `` はコードの札、`#番号`・commit の sha・`@名前` は機械がリンクや札にする。下の例は書き方の一つで、文言を写す型ではない（決まった言い回しは場面に関係なく毎回出て雑音になる）。

```json
{
  "headline": "私の指摘 3 件に作者が今日の夕方まとめて返信した。読んで返す私の番。",
  "where": ["昨日（10/15）、テストが例外の包み方を手で写していると指摘した", "作者が 15:32 に push し、15:44 に 3 件へ返信した"],
  "turn": ["止めているのは私の返事だけ", "3 件のうちコードで直したのは 1 件（4cf1df3aa）", "残る 2 件は、作者が #2010 と #2076 に分けた"],
  "next": ["4cf1df3aa を読み、失敗した日付のデータが解放されるかを確かめる", "#2010・#2076 への分割を受けるかを決める", "3 件に返信して解決にする", "承認するか、追加の指摘を出す"]
}
```

- **`headline`（いまの番の 1 行目。ここだけ読んで用が足りるように）**: **60 字までの 1 文で**、誰が何をしたので、いま誰が何をする番か——**どこで止まっているか**を確かめた結果。番号・件名・立場の札はページの頭と節の見出しに機械が出すので書かない（書くと 1 文が 2 行に延び、頭に入らないと言われた）。進める一手は `next` の先頭に書く（ページは `next` の先頭を大きく描く）。止まり方は 3 つ——私が動かせる／別の番号を動かすと進む／誰かを待っている。別の番号が私のものなら**所有を先に言う**（言わないと他人の PR 待ちに読まれる）。機械の「取り込み先」が既定ブランチでなく、その枝の PR が open なら、**その番号と誰のものかを入れる**（その PR が入るまで、この PR は既定ブランチに届かない）。私の一手で動くのが私の番だけ（返信すれば私の側は終わるが、PR は下書きのまま・依頼未送・別の番号待ち）なら「進む」と書かず、「私の側は終わり、その後は X さんの番」と書く（実測: 返信 2 件で「進みます」と書いたが、返信後も下書きで親の PR 待ちだった）。私の PR で依頼が誰にも出ていないなら、渡す先を決めるのが私だと分かるように。私が入っていない他人の PR で、GitHub にも会話にも依頼が無いなら「作者 X を待っている」（渡す先を決めるのは作者）。閉じた件（merged・closed）は、同じ 1 文の中で「済みで、動くものは無い」と言い切る（「merge 済みで、私が動くものは無い。」）。PR でないときは、この形でなく別の言い切りの形で書く（頭の前提のとおり、この文書には無い）
- **`where`（前回から。並びの先頭の項）**: `N 日前（M/D）` に何をしたか。N は機械の行に有ればそれ、無ければ（作成・渡された時点の行は日付だけ）機械の日付から今日までを数える（年は今年と見る）。同じ日なら「今日（M/D）」、前日なら「昨日（M/D）」。**その後の動きを後ろの項に**——誰も動いていないならその旨、動いたなら誰が何を（**人は名前で**。「相手」と書くと誰かで止まる）。発言を「」に入れるのはその人の語そのままのときだけ。私宛の依頼があれば、いつ誰から何が来て、済んでいるか未対応か（未対応なら `next` の先頭）。その後に push があれば「私の痕跡以降に変わった file」の件数を同じ欄に。機械が「この件で私はまだ何もしていない」と言うなら、その旨から始め、起点は私に渡された時点（誰の何で）か作成（誰が立てた）にする。末尾に手元の 1 文——`--switch`（手元を対象の枝へ移させる旗）で呼んだときは今のブランチを絶対名（「今のブランチ」でなく名前そのもの）で（「手元は main から feat/123-x に移した」／「手元に feat/123-x は無かったので origin から取り、main から移した」／「手元は feat/123-x に居る」／「手元は main のまま（手元に未コミット 3 件があるので feat/123-x へ移していない）」／「手元に feat/123-x は無く、origin にももう無い（PR は merge 済み）。手元は main のまま」）。移らなかったときの今のブランチは**機械の行の末尾の括弧から写す**。推測で main と書かない。手元の 1 文を書くのは、機械が「ブランチ」の行か「手元のブランチ」の節を出したときだけ
- **`turn`（止めているもの）**: 何が止めていて、原因は何で、誰が外せるか。`headline` に出した別の番号は**ここで 1 回**説明する（何の PR か・誰のものか・状態）。機械の「上に積む」があれば、この PR を base にしている PR として番号と誰のものかを 1 文（この PR が止まると一緒に止まる）。CI は落ちた本数と中身の箇所数を分け、複数本で原因が 1 つなら 1 つだと言い切る。承認・衝突・CI の本数・返事待ちの指摘の件数は、止めているものの行に機械が出すので書かない。書くのは、そのうちどれが効いていて、原因は何か。止めているものが無いなら、無いことが分かるように
- **`next`（次にやること）**: 1 項に 1 つの動作を 60 字まで（理由は `turn` へ）。ページは先頭の 3 手を出し、残りは畳む。**空にしない**——待ちなら、何を待ち、動いたら何をするか。閉じた件（merged・closed）は、先頭を「この件で私が動くものは無い」にし、任意の後片付け（残った会話を解決にする・後から読み直す）があれば後ろに「（任意）」を付けて並べる。私が入っていない PR で待ちなら「依頼が来たら本文と変更を読む」「レビューを返す」と来た場合を並べ、来ない場合を最後の項に「来なければこの PR で私が動くことは無い」と言い切る。機械がブランチに移らなかったときはその一手を先頭に——**機械の行が `→` で一手を書いていればその後ろをそのまま写す**（文言は機械が状況で変える。自分で組み立てない）。別の worktree なら「<path> で続ける」。手元に無いだけなら機械が origin から取って移るので `gh pr checkout` を書き足さない。一手が「依頼先を決める」なら、機械の「依頼先の候補」を括弧で添えてよい（候補の名前と機械が付けた理由のまま）。「X に依頼を出す」とは書かない（決めるのは私）。ページは、先頭の項が「前回から」の commit の sha を含めば「差分へ」、返信・会話・指摘の語を含む最初の項に「指摘へ」、CI・赤の語を含む最初の項に「CI へ」の飛び先を付ける
- **`unseen`（見ていないもの）**: 機械の申告（上限で切れた分・GitHub の外・結び付いていない commit・痕跡の基準が近似）はページの末尾に機械が並べる。AI が足すのは、機械が言っていない穴だけ——確かめようとして確かめられなかったこと（読めなかった CI のログ・引けなかった別の番号）、会話の要約で消えた分。機械が数で出しているもの（未解決の件数・CI の本数・承認の数）は見ている——書かない
- **この PR がすること（`lead`・`figure`・`terms`・`explain`・`points`）の読み手**: この件を**初めて見るエンジニア**。HTTP・DB・LLM・CI のような一般の技術は知っているが、このリポジトリが何の製品か、どんな部品で出来ているか、この件の前の議論や番号の中身は知らない。技術に疎い人向けにやさしく言い換えるのではない——前提を飛ばさず、仕組みの水準まで**詳しく**書く。上の欄（いまの番・前回から）は仲間向けに短く、この節は初見向けに詳しく、と読み手が違う。節の全部が同じ読み手で、変更点や図だけを読む人もいる——ひとこと・図・変更点に出る語も、説明に出る語と同じに扱う。本文が薄い（無い・1 行だけ）なら、その旨を 1 文書いてから `gh pr diff`（commit は `git show`）で分かることを事実で書く
- **`lead`（ひとこと。節の先頭に大きく出る）**: 1 文・120 字まで。製品の中の**どこの**話か、**誰の**ために**何を**どう変えるかを、前提を知らない人に（「勤怠アプリの承認画面で、承認者が差し戻しの理由を書けるようにする」）。目的は一通りにしか読めない形で（「X が黙って替わらないようにする」のような打ち消しは、何が変わるのかが逆に読める）。番号・記号だけで済ませない
- **言葉の選び方（この節の全部に。いちばん先に効かせる）**: 初見の人が新しく覚える語の数を最小にする。この順で:
  1. **業界で定着した語で言う**: 社内の呼び名・作者の造語・コードの名前は、それが何かを、この業界の技術者なら誰でも通じる語で言い換える（「`Ledger`」ではなく「残高の動きの記録」、「ホップ表」ではなく「中継先の一覧」）。ここで言う一般の言葉は**業界の標準の技術語**で、やさしい日本語ではない——スパン・ターン・マイグレーション・upsert・ファクトリ・契約テスト・プロンプトインジェクションは、そのまま使う。標準の語を日本語に作り替えない（「処理の記録」ではなくスパン、「移行の SQL」ではなくマイグレーション。作り替えると、初見の技術者は頭の中で標準の語に戻す手間を負う——読み役 3 人が揃って詰まった実測）。標準の語が有るのに社内で別の名で呼んでいるなら、標準の語を先に、社内の名を後ろに添える。仕組みは、何のためにあるかまで言う（「分析用の書き出しに社員の氏名を残さないため、氏名を hash に置き換える」。何をするかだけでは、壊れたときに何が困るのかが読めない）
  2. **名前は、読む人がこの先で出会うときだけ残す**: 差分・画面・設定・議論でその名前を探すことになるなら、一般の言い方の後ろに 1 回だけ添える（「残高の動きの記録（`Ledger`）」）。それ以外のコードの名前・社内の呼び名は出さない
  3. **新しい概念を減らす**: 件の結論に効かない仕組み・例外の一覧・途中の経緯は説明に入れない。変更点でも、1 点の中に初めて出る概念を 2 つ以上入れない（入るなら、その点は細かすぎる）
  4. **語は作らない**: 標準の技術語があればそれを使う（「保存先の口」ではなく「保存先のインターフェース」）
  5. **一般の言葉で言えず、節の中に何度も出る語だけを `terms` に置く**——一覧は最後の手段で、目安は 5 個まで
- **`terms`（この節に出てくる語。説明の前に一覧で出し、文の中の同じ語には点線が付いて、乗せると意味が出る）**: 上の 5 に当たる語を `{"term": 語, "means": 意味}` で（機械の上限は 16 個）。`means` は 160 字まで、何で・何のために・何をするかを 1〜2 文で（「締め: 月末に勤怠を確定させる処理。締めた月は承認者しか直せない」）。一般の技術語（API・トークン・migration）と、標準の名前（PostgreSQL・Helm）は載せない。製品名でも、このリポジトリでの役割が初見に分からないもの（「Sentry: 例外を集めるサービス。ここでは本番の 5xx だけを送る」）は載せてよい。定義を文の中に長い括弧で差し込まない——1 文が長くなって追えなくなる（初見の読み役が、括弧の入れ子で詰まった実測）
- **`explain`（説明。語の一覧の下）**: この件が何のために・何を・どう変えるか。上の欄も差分も「なぜ」を言わない（28 file の PR で型と木だけ出したら「内容が初見に分かりづらい」と言われた実測）。**1 段落 1 話題**で、段落はこの順で 4〜6 つ:
  1. **前提**: この製品・システムが何をするものか（1 文。README の冒頭の語で）と、この件が触る部品がその中のどこで何をしていて、どうつながっているか
  2. **背景と課題**: 変更の前はどう動いていて、誰が何に困っていたか。いまの本番・既定がどうなっているか。前の番号（#120 など）は番号だけで済ませず、何をした件で、この件とどうつながるかを言う
  3. **何をどう変えるか**（1〜2 段落）: 仕組みの全体の流れ——何が入力で、どこを通り、何が出るか——と、作者が決めた主なこと（上限・既定値・置き場所・断るとき）。**決めたことには理由を添える**（作者が書いた理由・比べた案。振る舞いが場所で違うなら、なぜ違うか）。採らなかった案を出すなら、採らなかった理由も一緒に（理由の無い「採用しなかった」は、読む人に問いだけを残す）。因果は原因を先に書き（「通知の送り手は 1 本しか無い。だから送る前に設定を読む形にした」）、「そのため」で後ろから結ばない。理由が材料に無ければ「理由は本文に無い」と書く。本筋と別の変更を同じ件に束ねているなら、なぜ一緒に入れたかを言う（言わないと、ついでの変更に見える）。file が多ければ、どこが中心でどこが追随か（読みどころ）を 1 文
  4. **使う側から見た変化と、含まれないもの**: 既定の振る舞いが変わるか。既存の設定・配備・利用者に要る作業と、そのままだと壊れる所（壊れるなら何をすれば直るか）。作者がどう確かめたか（本文に有れば）。作者が「含まれない」「未決」と書いたもの

  字数は 400〜1600 字。物差しは差分の規模（file 数）と本文の密度の大きい方（1 file・本文の中身 10 行以内なら 400 字前後、20 行超か 15 file なら 1000 字前後、28 file を超えても 1600 字まで）。短くまとめるより前提を飛ばさないことを先にするが、**1 文 1 情報**（条件を 1 文に 2 つ以上詰めない）・1 段落 5 文まで。言葉は作者のもの（本文・先頭コメント・commit の題の語）。**説明と変更点で同じことを書かない**——説明は全体の流れと主な決定とその理由、変更点は 1 つずつの具体（数え方・エラーの一覧・個々の試験）。file の path・関数名・引数名は入れない（変更点の仕事）。使う側が触る名前（API・表・列・設定の項目）は、役割を言ってから書いてよい。評価語を入れない。状態と経緯は書かない（上の欄の仕事）。先頭コメントが「8 行で切った」と言っていれば、切れた文を作者の言葉として写さず全文を見る
- **`points`（変更点。図のすぐ下に図の凡例として並び、押すと前と後とコードが開く）**: 変更を 1 点ずつ 10 点まで。`title`（何を）・`before`（前。無かったなら省く）・`after`（後）・`code`（その変更の差分。`{"path": 差分の file, "find": その file の差分に在る字}` を 4 つまで。`find` は変更の地図に出ている関数・テスト・設定の名前で、その変更の塊（消した行・前後の変わっていない行を含む）のどこかに在ればよい。行番号では指さない。省くと file の差分を全部）。**初見が仕組みを掴むのに要る変更を選ぶ**——差分の全部を並べる一覧ではない（細部の全部はページの変更の節に機械が出す）。小さな追随（文言・型・試験の言い換え）は 1 点にまとめるか省く。ページは変更点を**図の凡例**として図のすぐ下に番号と題だけで並べ、押すと前と後とコードが開く。乗せると図の箱と線が光り、箱や線を押すとその横に項の前と後が出る——なので**題だけで何の変更かが分かる**ようにし、図の箱と線には、それに当たる変更点の番号（`points` の `items` の並びを 1 から数えた順番）を箱や線の側に `"points": [1]` の形で書いて結ぶ（`in`〔前か後の片方にだけ在る印〕・`was`〔前の字〕の付いた箱と、`in` の付いた線は必ず。結べない変更点は「図の外」と出る）。6 点以上なら `group`（20 字まで。「Terraform」「chart」「アプリ」「試験」のような置き場か役割）で束ね、同じ `group` の点は続けて並べる——`title` は何がどう変わるかの一言（30 字まで。「締め直しで行を置き換える」）、`before` は困っていたことを振る舞いで 1 文（80 字まで。「同じ月を締め直すと、前回の締めの行が残って 2 行になった」）、`after` はどうなるかを 1 文（80 字まで。「前回の行を置き換え、1 月 1 行に保つ」）。理由・経緯・前の番号は説明へ、数値の列挙や細部はコード（`code`）へ回し、ここに足さない（後の文が中央 90 字になったページで「頭に入らない」と言われた実測）。字数は機械が止める。`code` が差分に無ければ機械が止める——ただし `find` を書けば、この PR で変えていない file（受け先の API の型など）も PR の先頭の版から引ける
- **書けたら 2 つ確かめる（この節の全部に）**: (1) ひとこと・図・説明・変更点に出てくる名詞を 1 つずつ見て、一般の技術語でないものを拾う。拾った語ごとに、一般の言葉に言い換えられないかを先に試し、言い換えられないものだけ、前の文で中身を言うか `terms` に置く。(2) **この件を初めて見た同僚が、この節だけ読んで、仕組みと、なぜそう決めたかを自分の言葉で説明し直せるか**
- **`figure`（図。ひとことの下）**: 部品が 2 つ以上あって関係（呼ぶ・渡す・分岐する・前後で入れ替わる）が言えるなら**極力描く**——一直線の鎖でも描く。読み飛ばすかは読む人が決める（実測: 経路が 2 本になる変更を「1 文で言える」と見て描かず、なぜ無いのかと聞かれた）。描かないのは部品が 1 つ・関係が無い（版の数字や台帳の追記だけ）・焦点で指摘か CI に絞ったとき。**形は中身で選ぶ**（`kind`）。1 枚で言い切れなければ、形の違う図を 3 枚まで並び（`[…]`）にする（やり取りの図と画面の図、など）。`kind` の選択肢と形ごとの JSON・前と後・順に見せる・自由に書く図・字の決まりはこの文書には無く、SKILL.md の手順 4 が、図を描くときに読む先を指す（上の例の `graph` は形の一つ）。
- 上の欄（`headline`〜`next`）で同じ番号を説明するのは 1 回、`turn` で。番号そのものは何度出てもよい。説明の節は読み手が違う（初見）ので、そこに出す前の番号は、上の欄と別に中身を一言添える

## 材料の語のうち、欄で使う所

`取り込み先`・`上に積む`・`依頼先の候補`・`私の痕跡以降に変わった file`・見出しの「ブランチ」の行・`← 私が返す番`・`← 私が最後に発言している（相手の番）`・見ていないもの。綴りはそのまま探せばよいが、欄にはこの語を写さず、中身を書く

## 言葉

この件を知らない同僚に口で説明するときの言葉で書く。**1 文 1 情報、能動態、肯定形。**

- **使うな**: GitHub と CI の語（reviewDecision・スレッド・rollup・CHANGES_REQUESTED）、コンサル英語・直訳横文字、この件の中でしか通じない略号、機械の理由文（「私の件に相手の発言があり…」）の丸写し（確かめた結果を書く）、「〜と思われる」「〜のようだ」（確かめていないことは「（未確認）」と付けて書く）
- **この命令書の語を欄に持ち込まない**——材料・機械・型・欄・焦点・スクリプト。ページの節の名前（指摘・CI・変更・手元）は指してよい（「下の指摘 3 件」）。本文（PR の説明文）は普通の語として使ってよい。機械が script 名（what-am-i-doing.py・catchup.py）で書いた口は `/what-am-i-doing`・`/catchup` の呼び名に置き換える
- **使ってよい**: 製品名・標準仕様名（Helm・pgvector 等）、IT で定着した英語（API・CI 等）
- **どうしても要る語**は、初出で「中身 → 記号」の順——「まだ承認されていない（REVIEW_REQUIRED）」
- **同じものは同じ語で呼ぶ。** /whose-turn・/what-am-i-doing と語を揃える（状態語・立場・動作）。書けたら自分に問え——**`headline` だけを見た人が、何の話で・自分が動くのか・急ぐかを言えるか**
- **例の一覧を許可の一覧と読まない。** 文言・場面の例は書き方の一つで、例に無いものも規則に当たれば書く
