# /catchup

1 件の PR / issue・ブランチ・今のブランチ・commit・会話の話題について、「前回私が触ってから何が起きたか」を 1 枚の HTML に描く。「私」は gh の認証ユーザ（使う人）。`/catchup [対象] [焦点]`。対象は 1 つ、焦点は 0〜3 語（`指摘`〔未解決のスレッド〕・`地図`〔変更の地図〕・`CI`。順に `threads`・`map`・`ci` でもよい）。付けるとページをその語に絞る（既定は全部）。呼ばれたら、すぐ下の「受け口」セクションのとおりに機械を呼ぶ。

## 守ること（踏むと壊れる所）

- 機械（`bash "${CLAUDE_PLUGIN_ROOT}/scripts/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/scripts/catchup.py"`。`python3` に替えて打たない。以下 catchup.py）は、**どの呼び方でも引数の末尾に `--out` を付け、返ってきたパスを Read で読む。`cat` で読むな。** 出力は Bash の 1 回あたりの上限（約 30,000 バイト。バイトで測るので日本語ならおよそ 1 万文字）を常に越え（実測 2026-09-16: 1 件で 91,701〜158,078 バイト）、付けないとファイルへ退避され、走らせ直しで `gh`（GitHub の CLI）ごと 2 回走る。`cat` も退避される。Read が途中で切れたら offset を進める
- **機械がブランチに移らなかったとき、自分で stash・commit・`git switch` を打つな。** 未コミットは別のセッションが編集中の木かもしれない（checkout は共有しうる）。理由と一手をフィールドの `next` に書くだけ。PR の commit が手元に無いときも `git fetch` を打たない。移った後に、移る前に読んだ file を編集するなら読み直す——中身は移った先のブランチのもの
- **端末にページの中身を書き足すな**（返すものは手順 6）
- **質問で返すな。** 番号でない語は会話の話題として描く。例外は手元にも会話にも対象が無いときだけ（[references/targets.md](references/targets.md) の「聞き返す」）
- gh が無い・未認証・失敗は「PR が無い」ではない。止まって理由を書く（黙って手元だけの報告に落とさない）。GitHub の remote が無い・detached（どのブランチにも居ない HEAD）だけは「PR が無い」と同じに扱い、手元だけを出す
- **描く材料の JSON を手で直すな**（事実が違えば機械を呼び直す）。**subagent・Agent・Workflow を立てるな**（`gh` は Bash で直列に。並列化は起動の overhead で分単位を失い、結果待ちを誤ると 10 分止まる）
- 出力に無いことを断定するな（確かめたなら結果を書く）。求められていないのに欠陥探しへ広げるな（説明は理解のためで、レビューの合図ではない）。日付・件数は機械の数字をそのまま使う（今日から日数を数えるのは `where` の「N 日前」だけ）。open 全件の棚卸しは `/whose-turn`

## 受け口

`--switch` を付けるのは番号・URL・ブランチ名だけで、`this`・commit・会話の話題（番号に解けたときも）では付けない。焦点の語は対象の後ろにそのまま置く。

- **番号・URL・ブランチ名** → `catchup.py --switch <それ> --out`。番号だけならいま居るリポジトリ（別のリポジトリは URL か `-R owner/repo`）
- **引数なし・`this`・焦点の語だけ** → `catchup.py this --out`（`catchup.py 指摘 --out` も同じで、対象は今のブランチに落ちる）
- **commit・範囲 `A..B`** → `catchup.py <それ> --out`
- **会話の話題**（番号でも commit でもブランチでもない語）→ 先に、会話の中で番号・ブランチ・commit に結び付くかを解く。結び付けばその対象で呼び（`--switch` 無し）、無ければ機械は手順 5 の `--render` だけ呼ぶ（描く材料は `-`）
- **`setup`** → [references/setup.md](references/setup.md)（走らせるコマンドと、機械が何をするか）を読んで従う

呼ぶ前に [references/targets.md](references/targets.md)（会話の話題の解き方・commit と焦点の語・数字の語の読み方・今のブランチから意図を汲む順・会話からの推定・聞き返す形・移る先と移らない条件）を読むのは、対象が会話の話題・数字だけ・引数なしで今のブランチに PR も番号も無いとき、commit を呼ぶとき・焦点の語を付けるとき、機械が移らなかったとき。
旗（`--full`・`--frame`・`--limit`・`--me`）や続きを出す呼び方を使うとき、ページのセクションの描かれ方や材料の上限を確かめるときは [references/list.md](references/list.md)（対象・旗・セクション・上限の表と、機械が書くもの）を読む。

## 役割分担

- **機械（catchup.py）**: 事実だけを出し、判断しない。`--out` が材料と描く材料を書き、`--render` がページを描いて VS Code で開く（材料の並び・ページの置き場・開き方は [references/list.md](references/list.md) の「機械が書くもの」）
- **あなた（AI）**: 材料を読み、書く前に確かめ、フィールドの JSON を書いて `--render` を呼ぶ。コードの行・差分・指摘の発言・CI のログ・木は機械がページに載せるので写さない。手元の `git config user.email` と一致する commit は私の push

## やること

1. 受け口のとおりに呼ぶ。`--out` はセクションごとの行番号（`セクション（Read の offset）: … / 159 指摘 / 971 変更の地図`）と、描く材料の path（`描く材料は <path> に書いた`。AI は読まず、`--render` にそのまま渡す）を返す。**`変更の地図` のセクションより前**（見出し・私が最後にしたこと・求められていること・その後・状態・つながっている先・本文・指摘・CI）**は全部読み、地図のセクションは頭だけ**——規模・変更ファイル・名前の言及・新規ファイルの先頭と骨組み。その後ろの既存ファイルの変更（関数ごとの今の中身に、変えた行の印を付けた抜粋）は、説明（`explain`）の背景の段落に要るときだけ読む——差分は機械がページに全部載せるので、写すために読まない。取り直しは要らない（続きを読むだけで `gh` も `git` も走らない）
2. **本文を読む**: 「本文（材料）」に作者の本文と、閉じる issue・本文が # で指す issue / PR の冒頭。件名（`headline`）と説明（`explain`）の材料。切れていれば `gh pr view <番号> --json body -q .body`（issue は `gh issue view`、commit は `git show`）で全文。本文が飛ばす前提（製品が何か・部品の役割・前の番号の中身）は、README の冒頭・触る部品の file の先頭（docstring・先頭コメント）・本文が指す前の番号の冒頭（材料に出ている）で、言うのに要る分だけ埋める
3. **書く前に確かめる**（確かめずに機械の言葉を写すと答えが逆になる——済んでいる申し送りが「未対応の問い合わせ」に読まれた実測）。確かめた結果はフィールド（`headline`＝いまのターンの 1 文・`where`＝前回からの動き・`turn`＝止めているもの・`next`＝次の一手）に書く:
   - `CI: 赤` → 「CI が落ちた理由（材料）」を読む（焦点で絞って、このセクションが無ければ `catchup.py <番号> CI --out` で呼び直す。`--switch` は要らない）。読めないチェックは URL を開く。`next` はこれ次第
   - `（名指しは無い。私の件への発言）` → 私への依頼か、私の push で**既に済んでいないか**を本文と差分で
   - 止めている原因が別の番号 → その**誰のターンか**を `gh pr view <番号> --json author,reviewRequests,reviewDecision,updatedAt` で 1 回（「未承認」だけでは今日動くべきかが決まらない）
   - 会話に GitHub に無い依頼（口頭・チャットのレビュー依頼など）が出ていれば、立場（この件で私は何者か。レビュアーなど）は会話の側を信じ、私が動かせる件として書く。GitHub に依頼が無いことは 1 文添える
   - 取り込みが「GitHub が判定中（UNKNOWN）」で件が open なら（merged・closed なら見ない。機械を丸ごとは呼び直さない） `gh pr view <番号> --json mergeable -q .mergeable` を 1 回。まだなら「衝突の有無は GitHub が判定中（未確認）」
4. **フィールドの JSON を書く。キー名・形・書き方はこの本文に無く [references/fields.md](references/fields.md)（フィールドの形・書き方・文体・例・言葉）にだけ在るので、書く前に毎回 Read で開く。** 図（`figure`）を描くなら [references/figures.md](references/figures.md)（形ごとの JSON・前と後・字の決まり）も読む。PR でないとき（ブランチに PR 無し・commit・会話から推定した番号）と会話の話題は [references/not-pr.md](references/not-pr.md)（フィールドごとの言い切りの形）も読む。置き場は描く材料の path の `.json` を `-fields.json` に替えた path（材料が `-` なら OS の一時ディレクトリ）。Write で書く
5. **描く**: `catchup.py --render <描く材料の path> <フィールドの JSON の path>`（何にも結び付かない会話の話題は、描く材料の path の代わりに `-`）。直す所は機械が 1 件 1 行で言い、終了コード 2 で止まる——直して呼び直す。`--out` が「描く材料を組めなかった」と言っていれば、`headline`・`where`・`turn`・`next` の中身を端末に短く返し、描けなかったことと機械の言い分を 1 文添える
6. **返答**: 機械が標準出力に出した 2 行——ページの path と 1 行の要約——だけを、そのまま返す。前置き・説明・指摘・差分・開いたかどうかを端末に書き足さない（ページに在る）。全文を求められたときだけ、報告のファイル（`--out` が書いた材料）を 1 文字も変えずにコードブロックで貼る
