持ち主はこの会話の相手で、「自分の番」は持ち主が次に動くターンを指す。

これは /my-turn（会話が手順を自分で回す軽い版。`commands/my-turn.md`）の重い版で、人が名前で打ったときだけ動く。/my-turn から呼ばない。

/catchup との違い: /catchup は持ち主がその場で答えを待つので裏のエージェントを立てない（一般の構造を、差分もリポジトリも見せない別の目〔遮断の目〕に描かせる 1 回だけは立てる）。/my-turn-deep は待てる手順なので、掘る段を裏の Workflow（script が裏のエージェントを決まった順に回す Claude Code の仕組み）で回す。

手順は 3 つに分かれる。この会話が前提を取り直し（1〜5）、掘る段を Workflow `my-turn-dig`（このプラグインの `workflows/my-turn-dig.js`）に渡して結果を待ち（6〜10）、返った材料から持ち主への報告と作者への下書きを書く（11〜15）。Workflow は、PR が触るシステムの構造をとらえ、差分を見ない別の目に描かせた一般の構造と比べ、PR が作る仕組みが補う前提を消せないかから始めて、構造の違い・コードの臭い・指摘を木のように末端まで掘り、相乗り（この PR の外で、同じ件を既に扱っている open な issue・PR に乗せられないか）を見て、世の中の解と突き合わせ、自作をゼロベースで疑い、末端と案の 1 件ずつを別のモデルに反証させる。設計は `attention/docs/my-turn-workflow-design.md`。

## 守ること

- 個別最適の積み重ねで全体が汚くなる形は通さない。この PR だけ見れば筋が通っていても、全体を汚す方向なら一番上に置く。
- 一般の構造（Workflow の W2 が別の目に描かせる、同じ種類のシステムの構造）から外れてよい理由は、外の基準（書かれた意図・一般の構造・業界の定石）か、この PR の外の動かせない事実（外のツールの仕様・法や契約など、原典で示せる物）だけにする。リポジトリの今の状態（設定・CI・コード・置き方・慣習・既に在る検査や物）は、言い方を変えても理由にしない。それは直す対象であって、外れる理由ではない。
- この PR が自分で書き足した正当化と、作者の返事に書いた理由は根拠にしない（外れてよい理由にも、前の指摘が片づいたかの判定にも。手順 4）。例外の一覧・無視の設定・既知の制約や判断の記録・コメントの「なぜ」を、この PR が足した・書き換えたなら、それは過去の決定でなくレビューの対象である。記録を理由に使う前に、その行がいつ、どの変更で入ったかを `git log -L` か `git blame` で確かめ、入れた commit がこの PR の commit（`gh pr view <番号> --json commits`）に在れば、この PR が足した物に数える（4 で洗い出し、Workflow の全部の段に渡す）。
- 確かめていない領域を残さない。調べること（前提・世の中の解・自作の訳・相乗り）は作者に委ねず、ここで調べる。作者に委ねるのは、どの案を採るか・別の issue にするかの選択だけ。
- 「消える」「要らなくなる」「穴が塞がる」は、実物（コード・設定・ツールの原典）で木の末端まで確かめてから書く。確かめていなければ「未確認」と書き添える。
- 掘る段（構造・一般の構造・比べ・臭い・木・相乗り・世の中の解・自作・反証）はこの会話で回さず、Workflow に回させる。Workflow が返さなかった段やノードを、この会話が代わりに調べて埋めない。「未確認」のまま報告に出す。Workflow が使えない環境なら、10 のとおり止まる。
- GitHub へは書き込まない。

## 手順

### 前提を取り直す

1. 対象の PR を決める。引数の番号を使い、無ければ `gh pr view --json number` で今のブランチの PR を引く。どちらも無ければ、PR 番号を聞いて止まる。引数に `--headless` が在れば、ヘッドレスの形（9）で回す。
2. `gh pr view <番号> --json state,mergedAt,author,headRefOid,statusCheckRollup` で今の状態を取る。merge 済み・閉じているなら、それを言って止まる。head が手元の `git rev-parse HEAD` と違えば、`bash "${CLAUDE_PLUGIN_ROOT}/scripts/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/scripts/my-turn-prep.py" --sync <番号>` を打つ（`python3` に替えて打たない）。PR のブランチに居て遅れているだけ（追跡ファイルに未コミットの変更が無く、手元の先頭が PR の先頭の祖先）なら、機械が PR の先頭まで fast-forward して、出力の `synced` を真で返す。そのまま続け、何 commit 進めたか（`commits`）を 11 の報告の「確かめた前提」に 1 行書く。`ok` が偽なら `message` を言って止まる（別のブランチ・detached なら `/catchup <番号>` で PR のブランチへ移る、未コミットの変更が在る、手元が先に進んでいる・分かれている、など。どれも手元を動かさずに止まる。6 の下ごしらえも head が違えば機械で止める）。止まらなければ、`git status --porcelain` と `git stash list` を控える（15 で比べる）。
3. 立場を決める。作者が `gh api user -q .login` と同じなら作者、違えばレビュアー。
4. 会話を全部読む（`gh pr view <番号> --json body,comments,reviews` と `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`）。読んだ物は 7 で Workflow に渡すので、出力を残しておく。自分が前に出した指摘・決着した指摘・許した指摘を一覧にし、同じ指摘や食い違う指摘を出さない。前に出した指摘は 1 件ずつ、今どうなったか（片づいた・取り下げた・残っている）と、そう決めた根拠（直した commit と、確かめた実物）を控える。片づいたと決めてよいのは、指摘を直した commit の差分（`git show <commit>`）と今の head の実物（コードを読む・打って確かめる）で、指摘の中身が解けたと確かめたときだけにする。作者の返信（「直した」「意図どおり」「別の PR でやる」など）は主張として控え、片づいたかの根拠にしない（作者の説明を読んでから判定させると AI のレビューの見逃しが増え、説明を伏せて差分だけで判定させると減ると測られている。https://arxiv.org/html/2603.18740v1 ）。返信しか無い・差分と実物で決まらない物は「残っている」にし（前の回の発見で元が未確認だった物は「未確認のまま」を保つ）、返信の言い分は、下で控える作者の返事に書いた理由に入れる。取り下げたは、指摘を出した側が会話で取り下げた物だけにする。この確かめは前提を取り直す段の仕事で、掘る段（Workflow に回す段）ではないので、この会話でする。作者なら、受けた指摘を 1 件ずつ控える。この会話か作業場に、前に起動した /my-turn-deep か /my-turn の報告（会話に貼られた物かファイル）が渡されていれば、それも読み、その発見（指摘・下書き・前提を消す案・相乗り〔この PR の外で、同じ件を既に扱っている open な issue・PR に乗せられる物〕・未確認として残した物）を 1 件ずつ、今どうなったか（片づいた・取り下げた・残っている・未確認のまま）を控える。前の報告に書いた発見とその判定（「片づいた」「問題ない」など）は決着済みとして扱わず、確かめ直す主張として扱い、片づいたかは上と同じく直した commit の差分と今の実物だけで決める。前の回の確かめ（実物で答えが決まった問いの結果）を使い回すときも、使うのは実物で確かめた結果（何を読み・何を打って何が出たか）だけで、前の回の判定の文は使い回さない。残っている物と未確認のままの物は 7 で Workflow に渡し、木のルートにさせる。黙って落とさない。push の後なら、前の指摘の確かめとは別に、前の回の head から今の head までの差分を、Workflow が初めて見る PR として最初の段（PR が触るシステムの構造をとらえる段）から回す（6 の下ごしらえは差分を 2 本作る。1 本目は PR 全体〔base から今の head まで。prep の `diff`〕、2 本目は前の回の後に足された分だけ〔`--prior` の記録の head から今の head まで。prep の `priorDiff`。rebase の後で前の head が今の head の祖先でないときと、その間に merge の commit が在るとき〔base を PR のブランチに merge した後〕は作らず null〕。Workflow は 1 本目で PR 全体を見たうえで、2 本目に載った所を前の回の後に足された物として掘る）。差分からは、この PR が足した・書き換えた正当化（例外の一覧・無視の設定・既知の制約や判断の記録・コメントの「なぜ」）と、作者の返事に書いた理由を 1 件ずつ控え、レビューの対象に入れる（守ることの 3 つ目）。
5. 本文・会話・触るコードが名指す PR・issue・設計の判断の記録を読み、後から設計を変えた PR や閉じた issue で前提が古くなっていないかを確かめる。読めなかった物は「無い」と書かずに「未確認」と書き、7 で Workflow に渡す。

### 掘る段を Workflow で回す

6. 下ごしらえを打つ。前の回の記録 `"$(git rev-parse --git-common-dir)/attention/my-turn/<番号>.json"` が在れば `--prior` に渡す（以下、機械は `bash "${CLAUDE_PLUGIN_ROOT}/scripts/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/scripts/<台本>"` で打ち、`python3` に替えない）:
   `my-turn-prep.py <番号> [--prior <記録>] [--headless]`（ヘッドレスの形なら `--headless` を付ける）。
   - 出力の JSON（以下 prep）の `ok` が偽なら、`message` を言って止まる（head の食い違い・取り込み先の取り違え・環境変数 `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` が置かれている〔全部の段が 1 つのモデルになり、反証を書いた段と別のモデルにできない〕など）。
   - `unchanged` が真なら、前の回から差分が変わっていない（PR の差分の patch-id が同じで、前の回の記録が読んだ・根拠にしたファイルと決まりの文書の指紋も全部同じ。前の回に結果を返さなかったエージェントが 1 体でも在る記録なら、prep は真にしない）。ただし、4 で控えた指摘のうち、前の回の記録の `priorFindings` に無い物（前の回の後に来た指摘）が在れば、近道を取らずに 7 へ進む。近道を取るなら、前の回の記録を読んで、11〜14 をその中身で書き、「前の回から差分が変わっていないので掘り直していない」と報告の頭に 1 行書く。記録の `ファイル:行` は前の回の head（記録の `head`）の行なので、今の head と違えばそう添える。Workflow は呼ばない。
   - `priorUnreadable` が null でなければ、前の回の記録を読めなかった（切れた・壊れた JSON など。中身は読めない訳）。prep は前の回が無いものとして全部を掘る形で返しているので止まらずに進み、記録を読めずに全部を掘り直したことと、その訳を報告に書く。
   - `remoteMatched` が偽なら、PR のリポジトリを指す remote が見つからず、`origin` の base で範囲を取っている。fork の作業場なら範囲がずれうるので、そのことを報告に書く。
   - `baseNote` が空でなければ、取り込み先のブランチが書き換わっていて（rebase の後の force push など）、prep が範囲の始まりを merge-base から替えたか、替えられずに merge-base のまま取った。どちらかと訳を、報告の「確かめた前提」に 1 行書く。
7. Workflow に渡すファイルを、prep の `recordDir`（6 の記録と同じ `$(git rev-parse --git-common-dir)/attention/my-turn`。PR のリポジトリの git dir の中で、commit されない）に書く。
   - `<番号>-thread.md`: 4 で読んだ PR の本文・コメント・レビュー・インラインの指摘を、そのまま写した物。
   - `<番号>-justifications.md`: 4 で控えた、この PR が足した正当化と作者の返事に書いた理由。1 件ずつ、在り処と、入れた commit。
8. Workflow の入力（args）を組む。JSON の値で、文字列にして渡さない。
   - `caller`: 文字列 `"attention:my-turn-deep"`。この手順から起動した合図で、Workflow はこの値が無い・違う起動を、エージェントを立てずに止める（AI が誤って Workflow を自分から起動したときに止める歯止めで、鍵ではない。値を写して渡せば通る）。
   - `pr`・`repo`（`<owner>/<repo>`）・`workdir`（`git rev-parse --show-toplevel`）・`stance`（`reviewer` か `author`）・`now`（今の日時。`date -u +%Y-%m-%dT%H:%M:%SZ`）。
   - `prep`: 6 の JSON をそのまま（前の回の記録から使い回せる物 `priorReuse` も、この中で渡る）。
   - `files`: `{"thread": <7 で書いた thread の path>, "justifications": <7 で書いた justifications の path>, "record": prep の record}`。
   - `priorFindings`: 4 で控えた前の指摘・受けた指摘・前の回の発見の一覧。1 件ずつ `{"id", "kind", "finding", "at", "state"}`。`kind` は `earlier`（自分が前に出した指摘）・`received`（作者として受けた指摘）・`prior-run`（前の回の発見）、`state` は `settled`（片づいた。4 のとおり、直した commit の差分と今の実物で確かめた物だけ。Workflow は `settled` をルートにせず、前の決めとして照合に使うので、作者の返信だけで付けない）・`withdrawn`（取り下げた）・`remaining`（残っている）・`unverified`（未確認のまま）、`at` は在り処（`ファイル:行` か URL。無ければ空）。
   - `unread`: 5 で読めなかった物の一覧（文字列）。
   - `blindJudge`: 差分もリポジトリも見せずに一般の構造を描かせる遮断の目（冒頭の「/catchup との違い」の段落）に使う役。convergence-loops の `blind-judge`（ツールを持たず、渡された問いだけから考える役）が使えれば `"convergence-loops:blind-judge"`。使えるか分からない・無ければ渡さない（Workflow がツールを使うなと頼んだ既定の役を立てる）。
   - 上限（`limits`）と段ごとのモデル（`models`）は既定のまま渡さない。
9. Workflow を起動して、ターンを終える。待ち続けない。
   - 既定の形: Workflow のツールを名前 `my-turn-dig`（このプラグインの物。一覧に `attention:my-turn-dig` と出ていればその名）で呼び、8 の args を渡す。終わりの知らせが来たら、返った値（記録そのもの）を記録のファイルに書く。知らせの出力のファイル（`<output-file>`）を渡して `my-turn-prep.py --save-record <prep の record> <出力のファイル>` を打つ（知らせに出力のファイルが無ければ、返った値を `<recordDir>/<番号>-result.json` に書いて、それを渡す）。書けなかったら（`ok` が偽）、`message` を報告の「確かめた前提」に 1 行書く（次の回は前の回の記録が無いものとして掘り直す）。返った値を材料に 11 から続ける。
   - ヘッドレスの形: 8 の args を `<recordDir>/<番号>-args.json` に書き、Bash の run_in_background で `my-turn-headless.py <その path>` を打つ（`--budget-usd` の既定は 100。`nohup` や `&` で切り離さない）。この台本が、設定・フック・CLAUDE.md・プラグインを読まず、環境変数のうち、名前が CLAUDE か ANTHROPIC で始まる物（設定のフォルダ `CLAUDE_CONFIG_DIR` と認証の経路を除く）を持ち込まない `claude -p` の会話を作業場で起動し、その会話が Workflow を回す。返った値（記録）は、この台本が prep の `record` に書く。終わりの知らせが来たら、台本が出した 1 行の JSON を読む。`materials` が null なら、その JSON（`message` が在ればそれ）と `output`（`claude -p` の出力のファイル）の中身を言って止まる。`materials` が在れば、そのファイルを材料に 11 から続ける。`ok` が偽で `message` が在れば（記録を書けなかった回など。`record` が null）、`message` を報告の「確かめた前提」に 1 行書く。`models` の `unexpected`（段の表〔`my-turn-dig.js` が段ごとに決めたモデルの一覧。設計の 9〕に無いモデル）と `expectedMissing`（使われなかった、表のモデル）は、空でなければ 15 で報告に書く。
10. Workflow のツールが無い・呼べない（設定の `disableWorkflows` が真など）なら、その訳と直し方（`/config` の Dynamic workflows を入れる。`--headless` 付き〔9 のヘッドレスの形〕でも呼べなければ、`--headless` を付けない 9 の既定の形で呼び直す）を言って止まる。この会話で掘る段を代わりに回さない。返った値に `stopped` が在れば、Workflow が途中で止めた。`stopped` の値ごとの訳は次のとおりで、その訳と、返った値に在れば `counts` を言って止まる。`caller`: 8 の `caller` が無いか違う（1 行の訳は `message`）。`W1`: 構造の段が返らなかった。`args`: 入力が足りない（`missing` の一覧）。`refuter model equals writer model`: 反証の段（掘った答えの末端〔木の、それ以上分けない問い〕と直し方の案を、書いた段と別のモデルに崩させる段）が、書いた段と同じモデルになった。同じだと反証にならないので止める。

### 報告と、指摘の下書きか直し方の案を並べる

材料（Workflow が返した値）のフィールド: `purpose`（PR の目的の 1 文 `purpose`・手段の一覧 `means`・PR が書いた理由 `claims`・二度問うても目的の文に残った手段の語 `leaked`）、`structure`（構造・PR の種類の 1 文 `kind`・仕組みと前提 `mechanisms`・自作の部品 `selfMade`）、`general`（一般の構造 `text`・出なかったか `notFound`・出なかった訳 `why`・問い直したか `askedAgain`・使った問いの文 `questions`）、`compare`（違いの一覧 `diffs`。1 件ごとに判断 `decision`・外の基準 `basis`・同じ問題があと 3 回来たときに積み上がる物 `ifThreeMore`）、`smells`（コードの臭いの問いと答え）、`roots` と `nodes`（木。ノードごとに問い・状態・答え・確かめた物・根拠の写し・直すかの見立て `worth`・指摘の種類 `findingKind`・場所 `locations`・保守の手間 `cost`・反証の判定）、`ledger`（指摘の台帳。掘って見つけた指摘を機械が 1 件ずつにした一覧。1 件ごとに番号 `id`〔`L1` など〕・状態 `state`〔`finding`: 指摘・`unverified`: 未確認・`undecided`: 決まらない・`reopened`: 「このままでよい」を反証が崩して戻した物〕・指摘の 1 文 `claim`・場所 `locations`・根拠 `evidence`・元のノード `from`・反証の判定 `verdict`・重さの札 `label`・段 `level`〔`design`: この PR の設計で決めること・`detail`: 部品の仕様どおりにすれば済む細部・`taste`: 好み〕・行き先 `route`〔`draft`: 下書き・`report`: 報告だけ・`fold`: `into` の件に畳む。`into` は畳む先を辿った最後の件・`drop`: 落とす。落とすなら当たる決まり `rule`〕・行き先の訳 `why`・乗る直し方の案 `fixes`）、`linesReturned`（行き先を決める段が返ったか。偽なら全部の件が `report`）、`gapRounds`（抜けの点検＝木の全部を見て、まだ問われていない問いを探す段の、回ごとの結果）、`fixes`（直し方の案・組・PR の外の相乗り・反証で外した物）、`undecided`（決まらない問い）、`restsOnUnverified`（未確認の上に乗る答え）、`unread`、`priorFindings`、`excluded`（本文から外した lock file などの一覧）、`reusedFromPrior`（前の回の確かめを使ったノードと、同じだったファイル）、`counts`（件数。根拠の写しの照合は `counts.quotes`、台帳の状態と行き先の数は `counts.ledgerStates` と `counts.routes`、未確認を掘り直した数は `counts.redig`）、`version`（記録の形の版）。ノードの答えの `files`・`urls` は読んだファイルと web のページ、`evidence` は根拠（`path`・`line`・`quote`。`quote` は `path` の `line` 行目から写した 1 行）。

11. 持ち主への報告を返答の先頭に書く。冒頭の 3 行で、決めてほしいこと（レビュアーなら 12 の下書きを出すか、作者なら受けた指摘ごとにどの案を採るか）・何の PR か・何が分かったかを言う。`counts.allNull`（Workflow が始めたのに 1 体も結果を返さなかった段の一覧）に段が在れば、その段ごとに「この段は回らなかった（API の失敗など）。見て何も無かったのではない」と冒頭の 3 行の直後に書く。その下は段の順に並べず、指摘と案ごとのセクションにし、セクションごとに裏付け（ノードの末端で分かったこと・`fixes` の組と相乗り・世の中の解と自作の訳）を置く。`structure` の構造と、`compare` の違いと判断、`mechanisms` の仕組みと前提、前提を消す案（`roots` の先頭のルート）、PR の外の相乗り（`fixes.outside`）、構造の打ち手（設計の原則を書く・issue にまとめる・配線を通す〔作った物を、実際に呼ばれる経路につなぐ〕）、`priorFindings` のうち残っている物と未確認の物、`undecided`（持ち主に聞く問い）もセクションにする。`general.notFound` が真なら、一般の構造が出なかったことを、`general.why` の訳（`notFound`: 問い直しても出なかった・`notComparable`: 一般的すぎて比べられなかった・`noAnswer`: 遮断の目が返らなかった・`noParts`: 部品の言えない PR で問わなかった・`failed`: この段が回らなかった）と一緒に報告に書く。反証で崩れた末端と、それに乗って外れた案（`fixes.removed`）は、外れた訳と一緒に 1 行ずつ書き、残った物を「正しいと確かめた」とは書かない。末端と臭いの答えには反証が 2 体立つ（誤検出だと示そうとする目と、具体の失敗の筋書きを組む目。判定の `verdict.lenses`）。2 体の判定が割れた物（`verdict` が `suspected`。`counts.seenUndecided.refuteSuspected`。この一覧と `refuteUnverifiable` には、直し方の案と組の番号 `F`・`G` も入る）は「疑い」として 2 体の訳と一緒に書き、確かめたとは書かない。最後の「確かめた前提」のセクションに、4 で控えた前の指摘と前の回の発見の今の状態・`general.questions` の問いの文（そのまま写す）・`reusedFromPrior`（前の回の確かめを使ったノードと、何が同じだったか）・確かめていないこと（`counts.notSeen` の見られなかった物と、`counts.seenUndecided` の見て決まらなかった物を分けて）・`unread`・`excluded`（本文から外して見ていないファイル）を置く。見出しは中身で名付け、Workflow の段の名前（「W6」「ルート」など）を使わない。違いが無い・寄せない項目は 1 行に束ねる。`ledger`（指摘の台帳）の全部の件を、台帳の番号（`L1` など）と一緒に報告に書く。報告から指す番号は台帳の番号にし、別の番号を振らない。行き先が `draft` の件の本文は 12 に書き、報告からは番号で指す。`report` の件は中身と行き先の訳 `why` を、`fold` の件は畳んだ先の番号を、`drop` の件は当たる決まり `rule` を、1 行ずつ書く。段が `detail`（細部）の件は 1 つのセクションにまとめ、`why` に在る部品の仕様の在り処を添える。`state` が `unverified`・`undecided` の件は確かめていない物として、`reopened` の件は「このままでよい」とした答えを反証が崩した物として（`reopenedBecause` の訳と一緒に）書く。`linesReturned` が偽なら、行き先を決める段が返らず全部の件を報告だけにしたと冒頭の 3 行の直後に書く。`purpose.leaked` が空でなければ、目的の 1 文に手段の語が残ったと「確かめた前提」に書く。「確かめた」の添え書き・GitHub に書いていない旨の断り・途中経過は書かない。
12. レビュアーなら、台帳で行き先が `draft` の件の全部を、報告の後にインラインコメントの下書きとして、直す箇所ごとに並べる。どの件を `draft` にするかは、Workflow の中で決めてある。`draft` になるのは、状態が `finding` で、段 `level` が `design`（この PR の設計で決めること）で、反証の判定が `stands` で、筋書き（`verdict.scenario`。壊れる余地の件）か手間の数え（`verdict.cost`。保守の手間・自作・削れる行数などの件）が在る件だけで、外れた件は Workflow のコードが `report` に替えてある（替えた数は `counts.repairs.lines.draftToReport`）。行き先が `draft` でない件を、この会話の判断で下書きに足さない（足したいなら 11 の報告で持ち主に上げる）。1 件の `locations` の全部を、箇所ごとに 1 件ずつ並べる。1 件は、見出しの行に台帳の番号（`[L1]` など）と `ファイル:行`（範囲なら `ファイル:始めの行-終わりの行` で、始めの行は `locations` の行にする）、その下に本文を書く。本文は、文脈（作者自身の前の返事・リポジトリの台帳などの決まり）から入り、何が起きたとき、このコードだとどう困るかを書いて止める。本文の根拠は件の `evidence`（反証の 2 体の根拠を足した `verdict.evidence` ではない）の `ファイル:行` と写しから書く。「何が起きたとき、どう困るか」は `verdict.scenario` から、手間の件なら「次にこれを変えるとき、何か所・何行を直すことになるか」を `verdict.cost` から書く。直し方もヒントも書かず、直し方の案は 11 の報告にだけ書く（作者に問題を示して選ばせる方が作者の学びになる。https://google.github.io/eng-practices/review/reviewer/comments.html 「Pointing out problems and letting the developer make a decision often helps the developer learn」）。「ここはどう考えていますか」で揃えない。リポジトリにコメントの頭に付ける印（nit・suggestion など、指摘の重さや種類を示す語）の決まり（REVIEW.md など）があれば、その決まりの印を付ける。件の重さの札 `label` は、Workflow の線引きの段が付けた物で、段 0 で Workflow に渡したリポジトリの決まりの文書の中に印の決まりが在ればその印、無ければ `block`・`suggest`・`nit`・`question`・`info` のどれかになっている。リポジトリに印の決まりが在るのに札がその印でなければ（決まりの文書が Workflow に渡らなかったときなど）、決まりが挙げる印の中から中身に合う物に置き換える。リポジトリに印の決まりが無ければ、札をそのまま頭に付ける。本文はそのまま GitHub に貼れる形にし、番号を書かない（番号はこの報告のために振った物で、作者には意味が無い）。行の番号は PR の head の物にし、消した行に付けるなら `ファイル:12（base）` と書く。1 つの指摘が何か所にも効くなら箇所ごとに並べ、2 件目からの本文は最初の件を番号でなく `ファイル:行` か中身の短い言い方で指す（GitHub が差分に追わせるのはインラインの場所なので、行で指せば作者が辿れる）。作者に頼むのは、この PR が触る部品（`structure` で示した所）を変える物と、その変更で崩れる物だけにする。触る部品の外の話（別の issue・PR で作る部品など）は、下書きにせず 11 の報告で持ち主に上げる議題にする。作者に、GitHub の外や別のリポジトリへの書き込み（上流への issue・機能要望など）を頼まない（調べることはここでやる。守ることの 4 つ目）。下書きは差分の中の行にだけ付ける。行に付かない話（PR 全体の向き・この PR の変更が崩す差分の外の行）は、最後に 1 つのトップレベルの下書き（PR 全体へのコメント）にまとめる（無ければ作らない）。別の issue にするかは作者が決めることなので、こちらからは提案しない（`fixes.outside` で見つけた、既に在る open な issue・PR への相乗りは事実として書く）。作者なら、この手順は飛ばす。
13. 作者なら、受けた指摘ごとに、直し方の案と返信の要否を、報告の後に番号を振って並べる。返信の下書きを添えるなら、その本文に番号を書かない（別の指摘は `ファイル:行` か中身の短い言い方で指す）。自分の PR に自分でレビューを書くのではないので、指摘やインラインコメントの下書きの形にはしない（Workflow が見つけたほかの直しは、11 の報告に直し方の案として書く）。
14. 見せる前に、この会話が作った一時のファイル（作業場や一時の置き場に書いた物）を消す。`recordDir` の物（記録・差分・thread・justifications・args・報告）は次の回に使うので残す。
15. 見せる前に次を確かめ、見せたら止まる（投稿はしない）。
    - 件数: `counts` と報告を照合する。`smells` の答えの全部・ノードと案の反証の判定・未確認・返らなかった段とノード（`counts.stages` の段ごとの `null` と `counts.notSeen.nullNodes`）・空で返ったフィールド（段ごとの `empty`）・飛ばした段（段ごとの `skipped`）・上限で掘らなかった問いと案（`counts.notSeen` の `cut`・`extraSmellsCut`・`fixesCut`・`gapsAfterCap`）・違う親ノードから出た同じ問いを束ねる段（W7）が返らなかったので掘らなかった子の問いと、木の抜けを探す段（W8）が返した抜け（`counts.notSeen.afterNullMerge`）・段の答えを直して当てた所（`counts.repairs` の全部）・抜けの点検の結果（`gapRounds`）・本文から外したファイル（`excluded`）が報告に在るか。
    - 写し: 掘った答えと臭いの答えの根拠は、Workflow が反証の前に照合し、指した行に無かった物を外した（`counts.quotes`。`dropped` は外した根拠、`toUnverified` は根拠が全部外れて未確認にしたノードと臭い、`unchecked` と `garbled` は照合できずに残した根拠の数、`uncheckedWhy` は照合できなかった訳の並び）。`dropped` と `toUnverified` は報告の「確かめた前提」に書き、`unchecked` か `garbled` が空でなければ、その数の根拠を確かめていないと書く。`uncheckedWhy` が空でなければ、1 件ずつ訳も書く（照合の台本が 2 回とも打たれなかった束〔`not run (<訳>)`〕や、照合した数が渡した数と合わなかった束が載る）。反証（`verdict`）の根拠はまだ照合していないので、記録が書けていれば `my-turn-prep.py --quotes <prep の record>` を打ち、写し（根拠の `quote`）が `path` の `line` 行目に実際に無かった物を報告から外すか「写しが合わない」と書き添える。記録が書けていなければ、ヘッドレスの形なら `materials` のファイルに打ち、既定の形なら材料を `<recordDir>/<番号>-result.json` に書いてそれに打つ。
    - 作業ツリー: `git status --porcelain` と `git stash list` が 2 で控えた物と同じか（裏のエージェントは読むだけを指示の文で縛っている）。違えば、何が変わったかを報告の頭に書き、戻さずに持ち主に見せる。
    - モデル: ヘッドレスの形なら、9 の `models` の `unexpected`（段の表と `models` に無い名）と `expectedMissing`（回った段に渡したのに使われなかったモデル。数えの無い回は null で、見ない）が空か。空でなければ報告に書く。
    - 判断: `compare` で「外れてよい」とした違いの 1 件ずつ、`basis` がリポジトリの今の状態でないか（今の状態なら、寄せるべき違いとして報告に上げる）。理由に使われた記録・例外・コメントが、この PR が足した・書き換えた物でないか（その物なら、根拠にならないと報告に書く）。
