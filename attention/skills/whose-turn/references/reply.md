# /whose-turn の返答の形（返答を書く前に毎回読む）

/whose-turn（open な PR・issue を全件見渡し、誰のターンか・返信が要るかを出すコマンド）の SKILL.md の手順 1〜5 で判定した結果を、読む人の行動で割った 5 つのセクションに書く形。全体の長さ・表・字下げの決まりは SKILL.md の「返答」にある。

目次:

- セクションの割り方とリンク
- 1. `## 自分の番 — N 件`
- 2. `## 相手の番 — N 件`
- 3. `## 担当 issue — N 件`
- 4. `## 返さなくてよい呼びかけ — N 件`
- 5. `## 見た範囲`
- 端の場合

前提（このファイルで使う語。定義の元は SKILL.md）:
- **機械**＝同梱のスクリプト `whose-turn.py`（SKILL.md の手順 1 で `--json` を付けて走らせ、出力の JSON を Read で読んだ物）。「スクリプト」も同じ物。「機械の行」は JSON の `sections` に並ぶ PR の 1 件（`waits`・`assigned_issues` の 1 件も）のことで、`number`・`url`・`title`・`days`・`role`・`facts` などの鍵を持つ
- **自分**＝/whose-turn を使う人（既定は gh の認証ユーザー）。この返答を読むのも同じ人
- **呼びかけ**＝ @login で名指しされたのに、その後に自分のコメントが無い投稿
- **死角の確認**＝SKILL.md の手順 5。機械が見ていない所のうち 2 つ（Team 宛のレビュー依頼に自分の Team が入っているか・本文コメントで自分の最後の発言が相手の問いに答えているか）だけを読み、機械の行に無い自分の番を見つける
- **逃がした先（逃がし先）**＝レビューのスレッドで「別に #N を立てた」と話を移した先の issue / PR

## セクションの割り方とリンク

セクションは**読む人の行動**で割る——今日開くもの、開かないもの、見ていないもの。機械の出力のセクション（自分の番・相手の番・
呼びかけ・担当 issue）をそのまま写すな。**1 つの番号が行を持つのは 1 つのセクションだけ。** 他のセクションから
番号に触れてよいのは、2 件が同じ判断で決まるときだけ（「#1581 と同じ場で返す」）。

**件名を付ける番号は、全部リンクにする。** `[#番号](URL)` の形で、URL はその件の `url` から写す。
機械に行が無い番号（死角の確認でセクション 1 に加えた行）だけ、作者と一緒に `gh pr view N --json author,url` で
1 回引く。どちらでもない URL を組み立てるな——GHES では host が違い、issue と PR で path も違う。
対応する端末では番号だけが表示されてクリックで開け、非対応なら `#番号 (URL)` と展開される。件名を
付けない番号（根拠の中で引く逃がし先・参照元）にはリンクも付けない——機械がその URL を出していない。

この 5 つのセクションを、この順・この名前で出す。0 件でもセクションを消さず「なし」と書く。

## 1. `## 自分の番 — N 件`

今日自分が動かせるものを全部。**1 行目は `[#番号](URL) 件名`**、2 行目は字下げして `日数  役割  動作 — 根拠`。
根拠の 1 句が 1 行に収まらなければ、次の行に折り返す（下の例の #1505）。レビュアーの行は、その下に `本文:` と `規模:` の 2 行（機械の行をそのまま）:

```
  [#1505](https://github.com/o/r/pull/1505) shigam 本番追随の前段
        4 日  レビュアー 再レビュー — 250489 が block 1・suggest 7 に対応し
        e50961754 を push
        本文: 本番 shigam を main へ追随させる作業（#1500）の PR ①。
        規模: 23 ファイル +467/-401
  [#1584](https://github.com/o/r/pull/1584) merge queue の台帳
        0 日  実装者     依頼先を決める
```

例の根拠の `250489` は作者の login、`block 1・suggest 7` はレビューの指摘の数（block＝マージを止める指摘、suggest＝提案）、`e50961754` は push した commit。

件名を番号の横に置くのは、番号を見た目がそのまま「何の件か」へ進めるようにするため。日数・役割・動作を
2 行目の固定桁に置くのは、その列だけを縦に見て「すぐ終わる件」と「腰を据える件」を分けられるようにする
ため（1 行目に並べると件名の長さで列がずれる）。

- **番号・日数は機械の `number`・`days` のまま。** 数え直すな
- **役割は `実装者` か `レビュアー`。** 機械の `role` が `implementer` なら自分の PR で `実装者`、`reviewer` なら
  `レビュアー`。呼びかけから立てた行は機械の `waits` に
  作者が無いので、`gh pr view N --json author` で 1 回だけ引く。列を揃えるため `実装者` の後ろは空白 5 つ、
  `レビュアー` の後ろは 1 つ
- **件名は機械の `title` から作る。** 型の接頭辞（`fix(ci):` など。scope の語は使ってよい）と括弧書きを
  落とし、何の件かを名指す名詞句に**全角 12 字以内**で縮める。**固有名（ジョブ名・ツール名・ファイル名）は
  そのまま残す**——それで上限を超えるのはよい。一般語に言い換えると（`helm-chart-check` → 「chart 検査」）
  何の件か特定できなくなる。タイトルに無い語・状態・評価を入れない（状態は根拠が受け持つ）。
  **`#番号` は件名に入れるな**——別の件と読まれる。要るなら根拠に書く。件名の場所を作るために根拠の引用を
  削るな——削るのは件名の側。同じ番号には報告のどこでも同じ件名を使う
- 件名を付けるのは**母集団の番号（セクション 1〜4 の主語）だけ**。根拠の中で引く番号（逃がし先・参照元の PR）
  には付けない——機械がその題名を出していない
- 機械の `facts` の `レビュー依頼:` は**いま保留中の依頼**だけを出す（レビューが付くと消える）。その文が無いのは
  「未依頼か返答済み」で、「一度も依頼していない」ではない。履歴を断定するなら timeline（PR のイベント履歴。`gh api repos/<owner>/<repo>/issues/N/timeline`）を引け
- **動作はこの 9 語から選ぶ**（2 つ繋げてよい: 「レビューしてマージ」）:
  `レビュー` `再レビュー` `指摘に答える` `判断を返す` `返信する` `見て閉じる` `マージ`
  `依頼先を決める` `CI を直す`
  閉じた語彙にするのは、動作の列だけを縦に見て「すぐ終わる件」と「腰を据える件」を分けられる
  ようにするため。当てはまらない行が出たら、いちばん近い語を使い、根拠側で補え
- **根拠は 2 行目の動作の後ろに 1 句**: 相手・状態・block の要点など、なぜ今その動作なのか。1 句の後に
  別の句を足して行を増やしてよいのは、人にしか決められない判断が要るときだけ。根拠が動作の定義の言い直しにしかならないとき
  （「依頼先を決める」＝人へのレビュー依頼が無い）は書かない
- **レビュアーの行には、根拠の下に「何の PR か」の 2 行**: `本文: ` の後ろに機械の `intro`（作者の本文の 1 文）を、
  `規模: ` の後ろに `size` を `N ファイル +A/-D`（`files`・`additions`・`deletions`）の形で、その順で 1 行ずつ。`intro`・`size` が `null` ならその行は書かない。件名 12 字では次の問いが「内容は？」になる（実測）。
  規模は今日どれから読むかを決める材料で、直近マージの中央値（150 行前後）と比べて大きいなら `規模:` の
  行末に 1 句添える。実装者の行には書かない（本文は自分が書いた）
- **1 件ずつ書く。同じ動作でもまとめない**（まとめてよいのは「端の場合」の PR が 40 件以上のときだけ）。まとめ行は
  番号と件名の対応が読めなくなる
- **要返信の呼びかけは、その PR の行に合流させる。** セクション 4（返さなくてよい呼びかけ）に二度書くな。
  機械の `sections` の `mine` にも `theirs` にも無い番号（issue の呼びかけなど）だけ、ここに行を立てて
  1 行目の末尾に `（呼びかけから）` と付ける
- **死角の確認で加えた行**は 1 行目の末尾に `（本文を読んで移動）` と付ける。機械に行が無い番号なので、
  作者と URL は `gh pr view N --json author,url` で 1 回引く

**並びは機械の `mine`・`theirs` の並びのまま。並べ替えるな。** 加えた行（呼びかけ・死角）だけ、同じ日数の
行の最後に差し込む。この規則があるので、読む人は並びを機械の出力（文の報告も同じ並び）で検算できる。

## 2. `## 相手の番 — N 件`

`食い違い無し N 件` の見出しの下に、役割で 2 段落——`実装者 N — [#番号](URL) 件名・…`（自分の PR。相手の
レビューか再確認を待っている）と `レビュアー N — [#番号](URL) 件名・…`（人の PR。作者の対応を待っている）。
段落の中は機械が出した順。折り返してよい（件数が増えても行は 1 つずつ増えない）。**食い違いのある件は
段落に入れず**、`[#番号](URL) 件名（役割）— 食い違い` の 1 行にだけ出す（同じ番号を 2 回書かない。2 段落に並べた件数と、
食い違いの行の数を足すと、セクションの見出しの N 件になる）。食い違いの条件は 3 つだけ:

- 逃がした先の issue / PR が、参照された後に動いていない
- 自分の承認が出ているのに、未解決スレッドが作者側に残っている
- 相手が何日も無言のまま（その PR の `facts` に「〜以降 発言なし」の文がある）

## 3. `## 担当 issue — N 件`

`[#番号](URL) 件名（N 日）` を `・` で繋いだ 1 段落。open PR が動かしていない issue があれば、そこだけ 1 句添える。

## 4. `## 返さなくてよい呼びかけ — N 件`

種別ごとに 1 行（`回答済み` `共有だけ` `別の PR / issue で継続` `決められない`）。各件は
`[#番号](URL) 件名（根拠 1 句）` の形。要返信はセクション 1 に合流済みなので、ここには出さない。

## 5. `## 見た範囲`

3 行以内。母集団（open PR N 件・issue N 件・担当未設定 N 件）／死角の確認で何を何件読み、判定が
変わったのは何件か／見ていないもの。**番号は書かない**——未確認の件数だけ言う。

## 端の場合

- **自分の番が 0 件**: セクション 1 は `なし` の 1 行。他のセクションはそのまま出す——今日動かすものが無いことと、
  誰で止まっているかは別の情報で、後者は消さない
- **PR が 40 件以上**: セクション 1 で同じ動作・同じ根拠の件をまとめる。1 行目に `[#番号](URL) 件名` を `・` で繋ぎ
  （端末幅 100 桁を超えるなら別のまとめにする）、2 行目は 1 つ:
  `[#1584](URL) merge queue の台帳・[#1593](URL) 二重拡張子 YAML` ／ `      0 日  実装者     依頼先を決める`。
  セクション 2 は羅列のまま。それでも収まらないなら、セクション 1 の根拠を落として 2 行目を `日数 役割 動作` だけにする。
  **件名は最後まで残せ**——番号だけの行は、読む人が何の件かを引き直すことになる。**行を落とすな**——
  落とすと母集団と合わなくなる
