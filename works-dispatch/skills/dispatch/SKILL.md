# dispatch

自分の番の PR を、枝ごとの作業場で開くところまでを機械でやる。「自分の番の PR」は、attention プラグインの `/whose-turn` が「自分の番」の節に並べる PR（直す番の自分の PR と、レビューする番の PR）である。

1. PR の枝ごとに作業場を用意する。代表の clone から、その枝の git worktree を herdr に作らせ（置き場は herdr の設定の `worktrees.directory`）、herdr の作業場を開く。その枝の worktree が既にあれば開き直す。どちらでも、origin の今の head へ早送りしてから渡す（手元にしか無い commit が有れば動かさない）。代表の clone 自身がその枝を開いていれば作らない（`branch_busy`）。
2. アカウントを並べ、順の頭から、使用率が上限（設定の `limit_percent`。既定 95%）に届かない件数まで PR を割り振り、Claude Code を起こす。上限は、週の枠と 5 時間の枠の両方に当てる（どちらかが上限に届いたアカウントは選ばない）。順は、週の枠の切り替わりが近い（既定 24 時間以内。設定の `reset_soon_hours`）アカウントを先に、それ以外は 5 時間と週の枠の高い方の使用率が低い順、同じなら動いている会話の少ない順。件数は、1 件あたりの使用率（dispatch が毎回の前後で測って覚える）から決める（今の使用率に 1 件ぶんずつ足して、両方の枠で上限に届かない数）。まだ測っていなければ、選べるアカウントに 1 件ずつ順に配る。
3. attention の `/catchup <番号>` を送る。これは、その PR で前回自分が触ってから何が起きたかを出す命令である。それが終わったら、設定のファイルに書いた 2 ターン目の文を送る。
4. 会話が開いている PR は、dispatch が前に送った時（dispatch の控えに残る）の後に相手の新しい返事（コメント・レビュー・commit。Bot は数えない）が有り、会話が手すき（Claude Code の会話の状態が idle）で手元の作業も無ければ、古い会話を終えて herdr の作業場を閉じ（worktree は残す）、同じ worktree に herdr の作業場を開き直し、新しい会話を起こして 3 から送り直す。送り直した会話にも、前の会話の中身を持たない新しい目で PR を見させるためである。
5. 閉じた（merge・close した）PR の枝の場所は片付ける（worktree と手元の枝を消す）。会話が手すきで手元の作業も無ければ、会話を終えてから消す。見るのは代表の clone の worktree だけで、ほかのリポジトリには触らない。PR の無い枝（issue から始めてまだ PR を作っていないもの）は消さない。

AI は使わない。このスキルは下のスクリプトを走らせ、出力をそのまま見せるだけで、判断も言い換えもしない。`${CLAUDE_PLUGIN_ROOT}` は、Claude Code がこのプラグインの入ったフォルダのパスを入れる変数である。命令は `python3` でなく、このプラグインの `hooks/run-python.sh` を通して起こす（`python3`・`python`・`py -3` の順に、実際に起きて 3.11 以上の物を選ぶ。Windows の `python3` が Microsoft Store へ誘う代わりの物でも動く）。下の命令の形をそのまま打ち、Python の名前を替えない。

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" <引数>
```

PR を開く回（引数なし・`--pr`・`--issue`）は、Bash の道具の `run_in_background` で走らせ、終わりの知らせが来てから出力を見せる。dispatch は各 PR の `/catchup` が終わるのを待ってから 2 ターン目を送るので、数分かかる。前で走らせると、Bash の道具の時間の上限で止められ、2 ターン目も報告も出ない。`--dry-run`・`--check`・`--clean`・`--init` はすぐ終わるので、前で走らせてよい。

## 前提（`--check` が全部確かめる）

`--check` は最初に、要る道具（gh・herdr・アカウントの起こし方の命令）を共通の点検の部品 tiers（依存として入るプラグイン）で確かめ、足りなければ入れ方と案内を出して止まる。入れ方は持ち主に見せ、自分では走らせない（詳しい案内は、持ち主が `/tiers:check` で見られる）。tiers は、Claude Code の会話の中では依存の `bin/` が PATH に入るので名前で探し、会話の外から打ったときは、プラグインの置き場の隣（`<マーケットプレイス>/tiers/<版>/bin/tiers` のいちばん新しい版）を探す。見つからなければ、段の点検を飛ばして「足りない物は無い」とは言わず、止まって入れ方を出す。Windows では、herdr の連携を入れる命令を PowerShell で打てる形（`$env:CLAUDE_CONFIG_DIR='…'; herdr integration install claude`）で出す。


- [herdr](https://herdr.dev)（端末を作業場ごとに分けて、中の AI の会話を外から操作できる道具）が動いている。
- Claude Code が、開いている会話を読む `claude agents --json` を持つ版である。
- 使う各アカウントに、attention プラグインがアカウント全体（user）に入っている。
- 部署の回は、herdr の設定（`~/.config/herdr/config.toml`）の作業場の行（`[ui.sidebar.spaces]` の `rows`）のどこかに `{ token = "$kind" }` がある。部署の作業場の行に、常設・毎回空／常設・持ち越し／都度の印を出すため（`$kind` は dispatch が部署の作業場に付ける herdr の印の名前）。無ければ `--check` が足す行を出し、部署を立てる回は止める（PR を開く回は注記だけ）。足したら `herdr server reload-config` を打つ。
- gh でそのリポジトリを読める（PR を開く回だけ。部署の回は GitHub を読まない）。普段の gh のアカウントで読めなければ、設定の `gh_user` に読めるアカウントを書く。
- リポジトリごとに代表の clone（枝ごとの worktree を作る元にする、ふつうの clone。設定の `source` に書く）がある。各アカウントで一度そこで Claude Code を起こし、フォルダを信頼しておく。信頼していないと、枝ごとの作業場で毎回、信頼の確認が出る。代表の clone は既定の枝（main など）に置いておく。linked worktree（`git worktree add` で作った側）は代表の clone にできない（`--check` が止める）。代表の clone が開いている枝の PR は、作業場を作れない（`branch_busy`）。

## 初めて: `/works-dispatch:dispatch setup`

`setup` はスクリプトの引数ではない。そう呼ばれたら、この節の手順を上から持ち主と進める。

部署（作業ごとの git worktree と裏の Claude Code の会話の組。`--task` で立て、`--ask` で頼み、`--land` で本流に入れる。下の「部署を立てる」）だけを使うなら、ふつうは dispatch の設定のファイルは要らない（要るときは手順 2 の終わり）。部署を立てるリポジトリ（会社）は、`--repo` に渡した代表の clone のパスか、コマンドを打ったフォルダのリポジトリで決まる。

1. 会社の形（`.claude/company.toml`。会社の名前・役・本流への入れ方）の下書きを書き、名前・説明・役の本文を直す。下書きの役は、受け持ちに常設の `担当`（`resident = true`。頼みごとに空の会話で受ける `fresh = true`）と、一度きりの `作業`（`--role` を省いたときの役。`default_role`）と、`窓口`（代表の clone で `--desk` を打った会話に、組織の決まりを役の本文として届ける）の 3 つ。担当と作業はコードの直しなので、納品の項目を `結論・差分・試験・残った疑問・枝` にする（既定の「決め手」の原典の URL を求めない）。担当の本文は、枝を切った後に触るファイルを本流から読み直すこと（前の頼みで覚えた中身で書かない）を言う。受け持ちは受ける仕事（`[[skills]]`）の項目で書き、担当の部署の名前を受け持ちの名前にすると、その説明が担当の会話に足される。組織の決まり（役は窓口・担当・作業・相談の 4 つ・名前は herdr で読んで分かる短い日本語で、作業は `<受け持ち>：<何をするか>`・会社の名前は herdr の親の作業場にだけ出し部署の名前に付けない・枝の名前は英小文字とハイフン・担当への頼みは部署の名前で宛てる・納品の後に判断が要れば、もう一度 `--deliver` で返す）はコメントで書く。`<…>` の置き字（受け持ちの名前と中身）を直す。既定はリポジトリの中に書くので、同じリポジトリを使う人にも効かせるなら commit する。commit しないなら `--local` を付けて、dispatch の設定のフォルダ（既定は `~/.config/works-dispatch/`）の `companies/` に書く。

   ```
   bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --init-company [--local] [--repo <代表の clone>]
   ```

2. PR を開く回（引数なし・`--pr`・`--issue`）も使う人は、dispatch の設定（既定は `~/.config/works-dispatch/dispatch.toml`）の下書きを書く。隣に空の `dispatch-second-prompt.md` ができるので、`/catchup` の後に送る文（2 ターン目の文）を書く。`--init` は設定がもうあると書かずに止まるので、手順 3 で設定を書くより先に打つ（もうあるなら `[[repos]]` を手で足す）。

   ```
   bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --init --repo OWNER/NAME --source <代表の clone>
   ```

   設定の `[[repos]]` が要るのは、PR を開く回のほかは、`--repo` を `OWNER/NAME` の形で指すとき、git の外から `--repo` 無しで打つとき、部署の gh を会社の形と違うアカウント（`gh_user`）にするとき、新しい worktree へ手元だけのファイルを写す（`copy_files`）ときだけ。
3. アカウントを切り替える人だけ、dispatch の設定に `accounts` を書く（下の「アカウントの書き方」）。書かなければ `claude` 1 つで動く。
4. `--check` を、足りない物が出なくなるまで走らせる（`[[repos]]` が無ければ、部署の前提だけを見る）。
5. 窓口（持ち主と話し、部署を立てる会話）は、持ち主が名前を付けて起こす（`claude --name 窓口`。アカウントを切り替える人は、そのアカウントのコマンドに `--name 窓口` を足す）。部署はその名前を SendMessage の宛先にする。名前が無いと `my-notes-31` のような自動の名前になる。起こした窓口の会話から `--desk` を打つと、代表の clone の属性に窓口（役・名前・アカウント・会話の id）を書き、herdr の表示を付け直す（下の「組み直す」）。

### アカウントの書き方

アカウントの数に決まりは無く、1 つでも 7 つでも同じ形で書く（herdr のタブ欄に使用率を並べられるのは 15 個まで）。持ち方は人で違うので、次の 3 通りを 1 つの設定に混ぜてよい。

- **`claude` をそのまま使う。** `accounts` を書かない。`claude` 1 つで動き、鍵は Claude Code 自身が保存したものを使う。
- **設定のフォルダを分ける。** アカウントごとに、`name`（使用率の控えの名前）、`command`（そのアカウントで Claude Code を起こすシェルのコマンド）、`config_dir`（そのコマンドが `CLAUDE_CONFIG_DIR` に入れるフォルダ）を書く。コマンドが `CLAUDE_CONFIG_DIR` を入れないなら、`config_dir` は書かない。鍵を自分で決めた名前の Keychain の項目に置いたなら、その名前を `keychain_service` に書く。`CLAUDE_CONFIG_DIR` をシェルの環境（`export` など）でだけ入れて `claude` を起こす人も、そのフォルダを `config_dir` に書く。dispatch は、走らせている会話の環境の値を使わず、書かなければ `~/.claude` を見るので、信頼の印・会話の一覧・使用率の控えが別のフォルダの物になる（`docs/prerequisites.md` の 3）。
- **使用率の枠が無い（Ollama、Foundry など）。** `limits = false` を足す。使用率では外さず、使用率の分かるアカウントの後ろに並べる。

## 任意: herdr の見た目を整える

dispatch はこれが無くても動く。枝ごとの作業場が増えたときに、どのアカウントに余裕があり、どの会話が何をしているかを見やすくする。

1. **herdr の連携を、アカウントごとに入れる。** `--check` が、入っていないアカウントについて、入れるコマンド（`CLAUDE_CONFIG_DIR=<フォルダ> herdr integration install claude`）を出す。herdr を立ち上げ直したときに、会話を戻すのに使われる。
2. **タブ欄に、アカウントごとの使用率を出す。** 次のコマンドが出す行を、herdr の設定（`~/.config/herdr/config.toml`）の `[ui]` に貼る。アカウントごとに表示が 1 つ（例: `p1 5h 38% 1h4m  7d 32% 2d4h`。`5h` は 5 時間の枠、`7d` は週の枠で、使用率と切り替わりまでの時間）と、5 分ごとに控えを取り直す行が 1 つ並ぶ。取り直しは、使っていないアカウントの控えが古くなったときだけ、出力 0 トークンの問い合わせを 1 回投げる。

   ```
   bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/limits.py" herdr-config
   ```

   このコマンドは、アカウントの一覧の写し（`~/.cache/claude-limits/accounts.json`）も書く。タブ欄の行は設定のファイルではなくこの写しを読むので、設定のアカウントを足したり変えたりしたら、このコマンドを走らせ直して行を貼り直す。

   使用率の控えは、dispatch がアカウントを選ぶのにも使う。Claude Code の statusline のコマンドから、受けた JSON を `bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" --min 3.9 "${CLAUDE_PLUGIN_ROOT}/dispatch/limits.py" record` の標準入力にも渡すと、使っているアカウントの 5 時間の枠がすぐ動く。社内のプロキシの内側では、herdr を起こすシェルに `HTTPS_PROXY` が要る。失敗は `~/.cache/claude-limits/probe.log` に残る。
3. **サイドバーに、会話ごとの作業内容を出す。** 作業中は動いているツールを、ターンが終わると直前に頼んだ内容を出す。次のコマンドが出す `hooks` の塊を、各アカウントの Claude Code の設定（`settings.json`）に足す。すでに `hooks` があれば、出来事ごとの並びに足す。

   ```
   bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/activity.py" settings
   ```

   そのうえで、herdr の設定の `[ui.sidebar.agents.rows_by_agent]` にある `claude` の行のどこかに、`{ token = "$act" }` を置く（`$act` は、上のフックが作業内容を送る herdr の印の名前）。

2 と 3 の行は、Python をフックと同じ決まり（`hooks/run-python.sh`。`python3`・`python`・`py -3` の順に、実際に起きる物を選び、Windows の Microsoft Store へ誘う代わりの物を飛ばす。TOML を読まない台本なので下限は 3.9）で選ぶ。2 と 3 の行は、プラグインの入った場所（版ごとのフォルダ）を指す。プラグインを更新すると、そのフォルダが消えることがある。消えた場所を指していれば `--check` が知らせるので、そのときは行を出し直す。

## 使い方: `/works-dispatch:dispatch <引数>`

- 引数なし: 自分の番の PR を全部開き、返事の有った PR を送り直し、閉じた PR の作業場を片付ける。自分が作者でレビュアーの付いていない PR も開くが、`/catchup` だけを送り、2 ターン目の文は送らない（`--pr` で指したときも同じ）。
- `--dry-run`: 何も起こさず、どの PR をどのアカウント・どの作業場で開くか、どれを送り直すか（`refresh`）、どれを片付けるかだけを出す。
- `--pr N`: 指した番号の PR だけを開く。複数なら `--pr` を重ねる。止めている実装や、見に行くだけの PR に使う。レビュアーの有無では外さず、送り直しも片付けもしない。
- `--issue N`: issue から始める。issue に結んだ枝（`gh issue develop --list`）の作業場を開き、1 ターン目の `/catchup N`（N は issue の番号。`/catchup` は issue の番号も受ける）まで送って止める（2 ターン目のレビューの文は送らない）。枝が見えなければ、issue の Development の欄に出る開いた PR（merge するとその issue が閉じる PR）の枝を使い、それも無ければ既定の枝から GitHub に枝を作って issue に結ぶ（`gh issue develop`。GitHub に書く）。閉じた issue なら枝を作らずに止める（`issue_closed`）。`--pr` とは一緒に使えない。送り直しも片付けもしない。
- `--no-second`: `/catchup` だけで止め、2 ターン目の文を送らない。
- `--clean`: 代表の clone の worktree のうち、消してよい場所を並べる。消してよいのは、枝の PR が閉じていて、会話が無く、未コミットの変更・git に足していない新しいファイル（`git status` に出るもの）・その枝の stash が無く、手元の枝の先頭が PR の head と同じものだけ。設定の `copy_files`（git が追わない手元だけのファイルの一覧。新しく作った worktree へ、`copy_from`〔省けば代表の clone〕から写す）のうち写し元と中身が違うファイルが有る場所も残し、そのファイルを出す。`.gitignore` に当たるファイル（依存・生成物など）は数えず、場所と一緒に捨てる。`--clean --apply` で本当に消す（worktree と手元の枝を消す。herdr に `--force` を付けずに消させるので、並べた後に変更が出来ていれば herdr が断り、何も消えない）。部署（下の `--task` が立てた worktree）は PR を見ずに別に並べ、都度の部署で、会話が終わり（または会話がもう無く）、未コミットの変更・手元にしか無い commit・stash が無く、枝の先頭が origin の既定の枝に入っているものだけを消せるとする。消すときは、先に `claude rm` で会話を消してから場所と窓と手元の枝を消す。常設の部署（`--resident`）は消さない。常設の部署が本流に入れ終えた前の手元の枝（`--land` が属性 `company.landed-branches` に書いた、枝と入れた時の先頭）は、どの worktree も開いていなくなり、先頭がまだ入れた時と同じなら消す（入れた後に commit を積んだ枝は消さず、記録から外す）。会社（代表の clone）は部署の回と同じに、`--repo`（設定の `[[repos]]` の名前か代表の clone のパス）か打った場所で決まる。設定のファイルが無くても動き、設定の `[[repos]]` に無い会社では、PR の作業場は見ずに（GitHub に問わずに）部署だけを片付ける。
- `--check`: 前提だけを確かめる。
- `--init`・`--init-company`: dispatch の設定・会社の形の下書きを書く（上の「初めて」。もうあれば上書きしない）。
- `--task 名前 --branch 枝 --brief 頼みのファイル`: 部署を 1 つ立てる（下の「部署を立てる」）。
- `--tree`・`--sync`: 会社のツリー図を出す・herdr の表示を付け直す（下の節）。
- `--reorg`・`--desk`: 部署の名前・役・常設か都度か・上役を付け替える・本社の会話を窓口として名付ける（下の「組み直す」）。
- `--land 部署`: 部署の成果を、会社の形の決まりで本流に入れる（下の「本流に入れる」）。

## 部署を立てる: `--task`

持ち主と話す長く生きる会話（窓口）が、作業ごとに別の会話（部署）を立てて仕事を渡す形を、1 回の呼び出しでやる。部署は、リポジトリ（会社）の git worktree 1 つ（枝 1 本）と、そこで働く Claude Code の裏の会話（`claude --bg`）1 つの組である。部署の画面は、herdr のリポジトリの作業場の子の作業場に、常に並べる。

- 窓口は長く生かす。部署は作業ごとに 1 つ立て、終わったら畳む（上の「使い方」の `--clean`）。部署の仕事を点検する役は、部署の文脈を持たない新しいサブエージェントを毎回立てる。
- 部署のペインと会話には、作業の中身の名前（例: `catchup作り直し`）を付ける。ペインの名前には、アカウントが 2 つ以上なら、そのアカウントの名前を添える（例: `catchup作り直し p2`）。会話の名前は SendMessage の宛先になる。
- 連絡の道は 2 つある。窓口と部署が同じアカウントなら、部署は区切りで SendMessage を窓口へ送り、窓口は SendMessage の `notify_when_idle` で手すきの知らせを 1 回受けられる（待つ間トークンを使わない）。アカウントが違うと SendMessage は両方向とも届かない（各会話の一覧に、同じアカウントの会話しか出ない）。その場合、部署は区切りごとに画面に短く報告を書いて止まり、窓口は herdr で部署のペイン（`attach` で裏の会話の画面を出したペイン）に打ち込み、画面を読む（`herdr pane read`）。dispatch は、どちらの道かを最初の文の後ろに書き足す。

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --task catchup作り直し --branch feat/catchup-redo --brief <頼みのファイル> [--role <役>] [--resident] [--repo OWNER/NAME か代表の clone]
```

`--repo` を省くと、コマンドを打ったフォルダのリポジトリに立てる（中のフォルダや worktree から打っても、その代表の clone になる）。打ったフォルダが git の外なら設定の最初の `[[repos]]`、それも無ければ止まって `--repo` を求める。`OWNER/NAME` で指せるのは設定の `[[repos]]` に書いたリポジトリだけ。

1. 枝の作業場を、PR と同じ置き場の決まりで用意する（代表の clone の git worktree を herdr に作らせ、置き場は herdr の `worktrees.directory`。herdr はその作業場を、リポジトリの作業場の子としてまとめる）。枝の作業場が既に在れば開き直し、git では動かさない（PR と違い、origin の head へ早送りしない。部署の枝は手元で commit を積む物のため）。無ければ作る。元は、origin にその枝が在れば origin の枝、無ければ既定の枝（`--base` で替えられる）。既定の枝の名前は GitHub に問わず、代表の clone の手元の `origin/HEAD` から取り、無ければ origin に `git ls-remote --symref origin HEAD` で問う（`--land` の本流と `--clean` も同じ元から取る）。部署の回（`--task`・`--ask`・`--land`・`--init-company`）は GitHub を読まないので、origin は手元の bare リポジトリでもよい。GitHub が要るのは、PR を開く回と、`[land]` の取り込み方が `pr` か CI の枝の関門のときだけ。
2. 使用率が上限に届かないアカウント（上限は PR を開く回の 2 と同じで、週の枠と 5 時間の枠の両方に当てる）のうち、PR を開く回の 2 と同じ順（週の枠の切り替わりが近い物を先に、ほかは使用率の低い順）の頭を 1 つ選ぶ。
3. 部署の属性（役〔`--role`。省けば会社の形の `default_role`、それも無ければ `作業`〕・常設か都度か〔`--resident` を付けるか、役の項目に `resident = true` が有れば常設（`resident`）、省けば都度（`per-task`）。常設の部署は `--clean` で畳まず、次の頼みを同じ部署で受ける〕・アカウント・会話の名前・上役〔呼んだ会話〕）を、作業場の git の設定に、属性ごとに `company.role`・`company.residency`・`company.account`・`company.name`・`company.boss` のような名前で書く（代表の clone に `extensions.worktreeConfig = true` を入れる。値は commit されず、worktree と一緒に消える）。代表の clone の `.git/info/exclude` に `.claude/settings.local.json`（部署の会話が書く許可の記録）を足す（`.gitignore` は触らない。`.claude/` を丸ごとは隠さない。exclude は全 worktree で共有なので、`.claude/` の下に新しく作ったファイルが未追跡に出なくなり、commit し忘れに気づけない）。
4. ペインに名前を付け、そのアカウントの起こし方（設定の `command`）に `--bg --name <作業の名前> --settings <設定のファイル> [--model <モデル>] [--effort <段>] "<最初の文>"` を付けて打ち込む。設定のファイルは、裏の会話が自分で別の worktree を作らないようにする（`worktree.bgIsolation = "none"`。このプラグインの templates/department-settings.json）。会社の形の役の項目に起動の設定・モデル・effort が有れば、それも渡す（下の「役の中身と起こし方」）。最初の文は「作業の頼みです。<頼みのファイル> を読んで進めてください。」に連絡の道を書き足したもの。
5. そのアカウントの会話の一覧に裏の会話が出たら、会話の id を属性に足し、同じペインで `<command> attach <id>` を打ち込んで画面を出す。herdr の表示名（役）と札（ペインに添える短い印。役・アカウント・上役）をペインに、常設か都度かと会話の持ち越し方（`常設・毎回空`・`常設・持ち越し`・`都度`）を作業場の印 `$kind` に付ける（会話の行でなく作業場の行に出す）。作業の終わりは待たない。ペインを閉じても裏の会話は続く。

呼んだ会話の名前とアカウントは、dispatch が Claude Code の会話の一覧（`claude agents --json`）から、Bash の道具に渡る `CLAUDE_CODE_SESSION_ID` で探す。一時停止（Ctrl-Z）したまま `--resume` で開き直した会話は、一覧に同じ会話の id（`sessionId`）で古い処理（古い名前のまま）と今の処理の 2 件が並ぶので、dispatch の処理から親の処理を順にたどって pid（処理の番号）の並びを作り、2 件のうち一覧の `pid` がその並びに入っている方（dispatch を走らせている、今の処理）を、どちらも入っていなければ処理の起きた時刻（`startedAt`。開き直した今の処理の方が新しい）の新しい方を選ぶ。Claude Code の外から走らせるなど見つからないときは、画面の道にして注記を出す。SendMessage の道にしたいなら `--from-name <呼んだ会話の名前> --from-account <アカウントの名>` で渡す（`--ask`〔下の「頼む・納品する」〕でも、渡せば頼み元の名前とアカウントになる）。`--dry-run` は、作業場を作るか使い直すか、アカウント、名前、部署の属性、連絡の道、最初の文を出すだけで、何も起こさない。同じ名前の会話が既に開いていれば止まる（宛先が 1 つに決まらないため）。

部署の会話が起きて attach するまでで終わるので、前で走らせてよい。会話が起きなかった（`launch_failed`・`blocked` など）ときは、終了の値 1 で知らせる。裏の会話が会話の一覧に出るのを、打ち込んだ後に何度か見直す（Windows の `claude --bg` は、裏の会話を受ける仕組みを起こすのに 2〜3 秒かかる）。ペインに `backgrounded · <id>` が出ていれば、その id の会話を使う。`git worktree add` は本社の `config.worktree`（`--desk` が書いた窓口の属性）を新しい部署に写すので、部署を立てるときに、本社と同じ値のまま写っていて今回書かない属性（窓口の会話の id・前の名前など）は消す。常設の部署（`--resident` か `resident = true` の役）は、同じ作業場のまま、頼みごとに部署の会話が次の頼みの枝を切って移る（会社の形の担当の役の本文が、頼みごとに origin の本流から決まりどおりの名前の枝を切ると決めている。dispatch は枝を切らない）。そのため、立てたときの最初の枝の名前とその時の先頭の commit も、本流に入れた枝と同じ記録（属性 `company.landed-branches`。枝 → commit）に書く。最初の枝を本流に入れないまま次の枝へ移っても、その枝の先頭が記録した commit のままなら、移った後に誰かが打つ `--land`（どの部署でも）か `--clean --apply` が、手元のその枝を消し、記録からも外す（どこかの worktree がまだその枝を開いていれば消さずに次に回し、記録より後に commit が有れば枝は残して記録から外す）。

設定に前の版の `task_cwd` が残っていれば、止めずに注記を出して無視する（部署は自分の作業場で起こす。その会社の AGENTS.md・CLAUDE.md とフックを効かせるため）。

## 会社のツリー図: `--tree`

herdr に開いている作業場と、全アカウントの会話（終わった裏の会話も）が指すリポジトリを会社として、会社ごとに受ける仕事と部署を出す。部署の行は、枝・状態（作業中・止まっている・終わった・待機中・会話なし など）・会話の名前・役・アカウント・上役・herdr の窓の有無。`--tree --json` は同じ物を JSON で出す（形は `dispatch/schemas/tree.schema.json`）。読むだけで、何も書かない。dispatch の設定が無くても動く（有れば、そのアカウントの会話の一覧も見る）。

会社の情報（名前と受ける仕事）は、リポジトリの中の `.claude/company.toml` を先に読み、無ければ設定の置き場（設定のファイルの隣）の `companies/<代表の clone の場所を符号にした名前>.toml` を読む。リポジトリの中の物は、origin の既定の枝（main など。手元の ref `origin/HEAD` が指す枝。部署を立てる `--task` と `--ask` は、読む前にその枝だけを fetch する〔`--dry-run` を除く〕。ほかの命令は fetch しない）に commit された物を先に読み、既定の枝に無いときだけ代表の clone の作業ツリーの物を読む。既定の枝に在れば、代表の clone がたまたま開いている枝や部署の worktree で書き換えた物は読まないので、変えた会社の形は既定の枝に入れてから効く。手元の `origin/<既定の枝>` が古ければ古い物を読む（`git fetch` や `--land` の push で新しくなる）。`origin/HEAD` が無い clone（作った後に origin の既定の枝を替えた、など）では既定の枝を決められないので代表の clone の作業ツリーから読み、`--check` と会社の形を読む命令が、直す命令 `git -C <代表の clone> remote set-head origin --auto` を注記に出す。`--tree`・`--task`・`--ask`・`--deliver`・`--land`・役の本文を足す SessionStart のフック（下の「役の中身と起こし方」）は同じ読み方をする。書き方は同じ TOML で、欄の名前は A2A の Agent Card に合わせた:

```toml
name = "my_notes"
description = "持ち主のノート"
[[skills]]
id = "research"
name = "調べもの"
description = "結論と原典の一句を返す"
role = "調べ役"   # 受ける役（A2A に無い、ここだけの欄）
```

## 役の中身と起こし方: 会社の形の `[[roles]]` と `gh_user`

会社の形のファイル（上の `.claude/company.toml`、無ければ設定の置き場の `companies/` の物）に、役ごとの項目と、その会社の gh のアカウントを書ける。

```toml
gh_user = "<gh のログイン名>"   # 部署の会話の gh が使うアカウント（省けば、その人の今の gh の設定のまま）
default_role = "作業"            # --role を省いたときの役（[[roles]] のどれか。省けば 作業）

[[roles]]
name = "調べ役"                                  # --role に渡す名前（部署の属性 company.role）
instructions = "結論と原典の一句を返す。"          # 部署の会話の指示に足す役の本文。短く、AGENTS.md と同じことは書かない
model = "haiku"                                  # 部署を起こすときの --model（省けばアカウントの既定）
effort = "low"                                   # 部署を起こすときの --effort（inherit なら頼んだ会話と同じ。省けばアカウントの既定）
deliver = ["結論", "決め手", "残った疑問", "枝"]   # 納品する要約の必須項目（省けば既定。下の「頼む・納品する」）
deliver_check = "python3 scripts/check_deliver.py"   # 納品の検査のシェルの命令（省けば検査しない。下の「頼む・納品する」の「納品の検査」）
resident = true                                  # この役で立てる部署は常設（--resident を付けたのと同じ。この [[roles]] の項目に書く。例: 受け持ちごとに常設で立てる担当の役）
fresh = true                                     # 頼みごとに空の会話で受ける（省けば会話を持ち越す）
[roles.settings]                                 # 部署を起こすときの --settings（その会話にだけ効く Claude Code の設定）
permissions = { deny = ["Artifact", "Workflow", "ScheduleWakeup", "SendFeedback", "ReportFindings"] }
enabledPlugins = { "pr-review-toolkit@claude-plugins-official" = false }
skillOverrides = { dataviz = "off" }
```

- 部署の会話で `/clear`・圧縮（compact）・`--resume` をすると会話の id が変わる。同じ SessionStart のフックが、そのとき（フックの入力の `source` が `clear`・`compact`・`resume`）だけ部署の属性 `company.session` を新しい id に書き直す。古い id のままだと、`--ask` が会話の動き出しを見られず、Stop のフックが部署の会話を別の会話と見て納品を促さなかった。裏の会話の短い id（`claude attach` に渡す。`/clear` の後も変わらない）は属性 `company.job` に残し、部署の窓から会話が消えて --ask が戻すとき、会話の一覧にその会話が見えなければ、部署の窓に `<アカウントのコマンド> attach <短い id>` を打って戻す（頼みを打ち込むのは戻った後）。新しく起こした会話（`startup`）では書き直さない。代表の clone（持ち主の会話がほかにも居る）では、`--desk` が書いた会話の処理の番号（属性 `company.pid`。その会話の Claude Code の処理）の会話が `/clear` などをしたときだけ書き直す（窓口は区切りで `/clear` しても、`--desk` を打ち直さなくてよい）。
- 部署の会話が番を終えて、裏で走らせた Bash（`run_in_background`。`--land` など）の終わりを待っているときは、herdr の状態が done になり、終わったように見える。このプラグインの Stop のフックが、番の終わりに会話のプロセスの子に残る Bash の道具のシェルを数え、残っていれば herdr の表示名に「・裏の処理待ち」を添え（例: `担当・裏の処理待ち`）、待ち終えた後の番の終わりに外す。待っている間は、納品していない頼みの差し戻しもしない（裏の処理が終わると Claude Code が会話を起こすので、納品はその後でよい）。Claude Code のフックには裏の処理の終わりを知らせる出来事が無く、herdr の状態（done など）は herdr が自分で見て決めるので、表示名に出す。数えられるのは Bash だけで、裏で走らせたサブエージェントは数えない。プロセスの一覧を `ps` で読むので、Windows では出さない。
- 役の本文は、このプラグインの SessionStart のフックが、会話の始まり（やり直し・圧縮の後も）に足す。足すのは部署（属性 `company.role` の有る worktree）と、`--desk` で窓口を名付けた代表の clone（部署ではないので「本社の会話」と書く）だけで、`--desk` を打っていない代表の clone やふつうの clone では何も足さない。毎回の起動の量に入るので短く書く。部署の名前（属性 `company.name`）と同じ `name` の受ける仕事（`[[skills]]`）が有れば、その説明も受け持ちとして足す（役を 1 つ〔担当〕にして、受け持ちごとの中身を部署の名前で引くため）。
- 会社の形の役（名前・本文・受け持ちの説明）を替えたら、会話を持ち越している部署と窓口にも、次の番の頭に今の文を足す（UserPromptSubmit のフック。待ち受けが知らせで会話を起こすときは、起こす字の頭に足す）。その会話に前に足した文と比べ、違うときだけ足す（足した文の控えは会話ごとに TMPDIR の `works-dispatch-role-<会話の id>`）。会話は空にしないので、持ち主との話は消えない。足すのは場所の属性の会話（`company.session`）だけ。
- 役の名前を替えるときは、今の名前の項目に前の名前を `former_names = ["<前の名前>"]` と書く（Terraform の `moved` と同じく、名前の替え方を会社の形に書いて、属性の側を手で直さない）。前の名前で宛てた頼み（`--ask 会社/前の名前`）と `--call` は今の役に当たり、属性 `company.role` に前の名前を持つ場所は、今の役の本文を受け、会話の始まりと番の頭のフックと `--sync` が属性を今の名前に書き直す。今の役の名前や、2 つ以上の役の前の名前と重なる前の名前は、注記に出して引かない。
- `settings` は、その会話の間だけ、利用者の全体の設定とリポジトリの設定の同じ鍵より先に効く。全体の設定とリポジトリの設定は触らない。道具の名前だけを `permissions.deny` に書くと、その道具は会話の文脈から消える。`skillOverrides` は Claude Code に同梱のスキルにだけ効き、プラグインのスキルには効かない（プラグインごと切るのは `enabledPlugins`）。`enabledPlugins` で works-dispatch 自身を切ると役の本文が足されないので、dispatch が注記を出す。
- `model` と `effort` は、部署を起こすとき（`--task` と、`--ask` で新しく立てるとき）だけ渡す。省けばそのアカウントの既定のまま起こし（そのアカウントの Claude Code の設定に保存した値、無ければモデルの既定。Opus 5.5 の effort は medium）、値を書けばその値で起こす。`effort` は `low`・`medium`・`high`・`xhigh`・`max`・`ultracode` のどれかか `inherit`。`inherit` なら、dispatch を打った会話（上役）の今の effort で起こす（Claude Code が Bash の道具に渡す `CLAUDE_EFFORT` を読む。読めなければ既定で起こして注記を出す）。`--effort` はその会話にだけ効き、設定の `effortLevel`・`modelSettings` より強い。知らない値は Claude Code が注意を 1 行出すだけで既定に戻す（裏の会話の注意は誰も読まない）ので、読むときに弾いて注記を出す（役は外す）。`model` の `inherit` は作っていない（上役の会話の今のモデルは、Bash の道具の環境変数にも `claude agents --json` にも出ない）。書けば注記を出して役を外す。`--ask` が既に立っている部署に頼みを送るときは、モデルと effort を渡さず、起こしたときのまま変えない（`fresh` で会話を空にする部署も）。
- 部署ごとにモデルと effort を替えるなら、受け持ち（`[[skills]]`）の項目に `model`・`effort` を書く。書ける値は役の `model`・`effort` と同じで、`model` の `inherit` は形の違う値として扱う。常設の部署はどれも役「担当」で起こすので、役の値だけでは部署ごとに替えられない。決める順は欄ごとに、部署の名前（`--task` の名前。herdr の作業場の名前）と字が同じ `name` の受け持ちの値、部署の役（`--role` か `--ask 会社/役` で決まる。受け持ちの `role` 欄ではない）の値、アカウントの既定（`--model`・`--effort` を付けず、そのアカウントの Claude Code の設定のまま）。受け持ちに `effort` だけを書けば、モデルは役の値のまま。同じ名前の受け持ちが無いか、受け持ちに書かなければ今までどおり。形の違う値はその欄だけ外し（受け持ちのほかの欄はそのまま使う）、注記を出して次の順の値で起こす（止めない）。効くのは役の値と同じく部署を新しく起こすときだけで、立っている部署は起こしたときのまま変わらない（`fresh` の `/clear` でも、落ちた会話を `--ask` が `attach` で戻すときも、前の会話のまま）。立っている部署を新しいモデルで起こし直す命令は無い。`--tree` の受ける仕事の行に、受け持ちに書いた値（形の違う値は出さず、`!` の行に注記）を出す。

```toml
[[skills]]
name = "割り振り"     # 部署の名前と同じ
role = "担当"
model = "sonnet"      # この部署だけ、役の model より優先する
effort = "low"        # この部署だけ、役の effort より優先する
```
- 効きは、`claude plugin details` の見積もりではなく、起こした会話の最初の API 要求のトークン（入力とキャッシュの書き・読みの和）で確かめる（見積もりは、フックが足す文やサブエージェントの説明の例を数えない）。
- 役は `[[roles]]` の形だけで書く。`[roles."調べ役"]` のように名前で引く表の形は読まず、`[[roles]]` の項目に移すよう注記を出す（TOML では同じ `roles` を両方の形で書けず、混ぜると片方が黙って効かないため）。`[roles.settings]` の行より後に書いた欄は `settings` の中に入るので、`deliver` などの欄は `[roles.settings]` より前に書く（`settings` の中に `deliver` が有れば注記を出す）。
- 会社の形の頭の `desk_role` は、本社で持ち主と話す会話の役（`--desk` で `--role` を省いたときの役）。省けば、本社が今持つ役、それも無ければ `窓口`。
- `--role` で名指した役が、役を書いた会社の形に無ければ止まる（書き損じで設定が黙って効かないのを防ぐ）。`--role` を省いたときの役（会社の形の `default_role`、無ければ `作業`）が会社の形に無いのは止めず、役の本文と起動の設定が付かないことを注記に出す。`default_role` が `[[roles]]` に無い名前なら、会社の形の誤りとして注記に出し、`作業` を使う。
- `resident = true` の役は、`--resident` を付けなくても常設の部署で立つ。役で宛てた頼み（`--ask 会社/役`）で部署がまだ無いときに `--resident` を付け忘れても都度の部署にならず、次に同じ役で頼んだときに同じ部署に届く。
- `fresh = true` の役は、頼みごとに空の会話で受ける。`resident` とは別の軸で、常設の席（順番を 1 本にする・宛先の名前・決まった窓）は残したまま、前の頼みの記憶を持ち越さない（記憶は太るうえ、覚えた中身で書き直すと、ほかの部署が入れた行を消す）。待ち受け（下の「頼む・納品する」）の居る部署は、納品して止まった時点で、待ち受けが自分の窓に `/clear` を打って会話を空にする（終わった会話が画面に残り、herdr に done と出続けないように。裏の処理が残る・会話が動いている・入力欄に字が在るときは空にせず、次の番の終わりにもう一度見る）。待ち受けの居ない部署（このフックの無い古い版の会話）には、今までどおり `--ask` が、部署が前の頼み（属性 `company.ask`）を納品し終えていて会話が止まっていれば、新しい頼みを打つ前に `/clear` を打ち、会話の一覧の会話の id が変わったのを見てから頼む。前の頼みが無い部署（`--task` の頼みのファイルで働いているかもしれない）と、動いている会話は空にせず、そう注記して送る。会話を持ち越す役（`fresh` でない部署と、本社の窓口）も、会話が自分で区切りと判断して `--rest` で印せば、その番の終わりに同じく空にする（下の「頼む・納品する」の「区切り」）。下書きの既定は、担当が常設・毎回空、作業が都度、相談が常設・持ち越し。部署には役の `fresh` を属性 `company.fresh` に写す（`--task`・`--ask`・`--reorg --role`・`--sync` のとき。会社の形の `fresh` を変えたら、番の終わりのフックが今いる全部の部署の属性と herdr の表示に行き渡らせる。下の「herdr の表示を付け直す」）。
- `machine = true` の役は、AI の部署を持たない役（機械窓口の道具だけを持つ。下の「機械窓口」）。`--ask` で宛てられない。
- gh のアカウントは、dispatch の設定の `[[repos]]` の `gh_user`（前提の節の、設定の `gh_user` と同じ欄）を先に、無ければ会社の形の `gh_user` を使う（commit した会社の形に書かれたアカウントは、ほかの人のものでありうるため）。dispatch は名前だけを部署の属性 `company.gh-user` に書く。フックがそれを読み、会話の Bash がコマンドごとに `gh auth token --user <名前>` で鍵を取り出して `GH_TOKEN` に入れる。鍵の値は、ファイルにも画面にも履歴にも残らない。そのアカウントで gh にログインしていなければ、`GH_TOKEN` に使えない字を入れる（gh はほかのアカウントに落ちずに、認証の誤りで止まる）。dispatch の設定の場所や gh のアカウントを前の回と替えて同じ枝の部署を立て直すと、前の回の属性は消してから書く。PowerShell の道具には `GH_TOKEN` が入らず、そこで打つ gh は、その人の今の gh の設定のアカウントで動く（フックが足す `export GH_TOKEN="$(gh auth token …)"` の行は `$(…)` で gh を走らせる形で、Claude Code が PowerShell に写すのは `export 名前=値` のように値をそのまま読める行だけのため）。鍵を `GH_TOKEN` で gh に渡している人（コンテナや CI の形）は `gh_user` を書かない（`gh auth token --user` は `GH_TOKEN` の鍵を取り出せず、部署を立てるときの確かめで止まる。`--init-company` の下書きは、取り出せないアカウントを書かない）。
- フォルダの信頼は、Claude Code が `.claude.json` の `projects` に書いたフォルダの字と、dispatch の持つ字が違っても（Windows の `C:/…` と `C:\…`、macOS の `/tmp` と `/private/tmp`）、同じフォルダを指していれば信頼済みと見る。部署の作業場に付ける信頼の印は、Claude Code が書いた区切りに揃える。
- 既定の置き場でない dispatch の設定（`--config` か `WORKS_DISPATCH_CONFIG`）で部署を立てたときは、フックがその隣の `companies/` を読めるよう、設定の場所を部署の属性 `company.config` に書く。

## herdr の表示を付け直す: `--sync`

部署の属性（正本）から、部署のペインの名前・表示名（役）・題名・札と、作業場の名前（herdr のサイドバーの 1 行目）と印 `$kind`（常設・毎回空／常設・持ち越し／都度。上の「前提」の作業場の行に出る）を付け直す。付け直す前に、会社の形の役を部署と本社の属性に写し直す（属性 `company.role` が役の前の名前〔`former_names`〕なら今の名前に、`company.fresh` は役の `fresh` に。会社の形に無い役の場所は触らない。`--dry-run` は写す物を出すだけ）。作業場の名前は、部署の worktree なら属性の `company.name`（部署の会話の名前と同じ値）、代表の clone（`--desk` で窓口の属性を書く）なら会社の名前（herdr の木の親の作業場なので、会社の名前は親にだけ出す）。代表の clone の作業場は、その git の設定に属性が書いてあるときだけ付ける。ペインは、属性の会話（`company.session`）の居るペインが分かればそのペインだけに付け、代表の clone で会話の居るペインが 2 つ以上あって結べなければ付けない（持ち主のほかの会話の名前を替えない）。今の名前・印と同じなら付け直さない。属性を持つ場所（代表の clone か部署の worktree）が 2 つ以上居る作業場は、名前が 1 つに決まらないので触らない。何度打っても同じ結果になる。属性の無い部署（手で開いた場所）は触らない。Stop のフックが表示名に添えた「・裏の処理待ち」（部署の会話が裏で走らせた Bash の終わりを待っている印。上の「役の中身と起こし方」の節）は残す。会社の形が替わったときは打たなくてよい（会話の番の終わり〔1 回の応答を終えたとき〕に裏で走る Stop のフック `dispatch/shape_hook.py` が、会社の形の中身を、前に揃えた時の控え〔代表の clone の `.git/company/shape-synced`〕と比べ、替わっていればその会社の全部の部署と本社に付け直す。会社の形は origin の既定の枝から読むので、この PC の `origin/<既定の枝>` に届いた後〔この PC からの push か `git fetch` の後〕に効く）。herdr を立ち上げ直した後などに打つ。`--sync --dry-run` は付ける物を出すだけ。

## 組み直す: `--reorg`・`--desk`

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --reorg [--name <新しい名前>] [--role <役>] [--resident | --per-task] [--boss <上役の名前> [--boss-account <アカウントの名>]] [--dry-run]
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --desk [<名前>] [--role <役>] [--dry-run]
```

- `--reorg` は、部署（属性 `company.role` の在る worktree）の中から打ち、その部署の属性を付け替える。`--role` は会社の形に無ければ止まり、`--resident`・`--per-task` を省いて `resident = true` の役に替えると常設にする。`--boss` は上役（納品を返す会話）の名前を替え、前の上役の会話の id とペイン（`company.boss-session`・`company.boss-pane`）を消す（納品は新しい上役を名前で引く）。`--name` の新しい名前を、ほかの部署がもう持っていれば止まる（宛先が 1 つに決まらなくなるため）。
- `--desk` は、代表の clone で持ち主と話す会話の中から打ち、その場所の属性に窓口（役・常設・名前・その会話のアカウントと会話の id と会話の処理の番号）を書く。役は `--role`、会社の形の `desk_role`、本社が今持つ役、`窓口` の順に決め、名前を省けば本社が今持つ名前、無ければ役の名前。手で `git config --worktree company.role …` と書いていた物の正式な口。部署の worktree で打つと止まる（部署は `--reorg`）。
- どちらも、名前を替えたら前の名前を属性 `company.former-names` に覚える。`--land` と `--ask` の宛先は、今の名前が無ければ前の名前でも部署を引く（`--land` は枝の名前でも引ける）。
- 属性を書いた後に、その場所の分だけ `--sync` と同じ物（ペインの名前・表示名・題名・札と作業場の名前）を付け直す。
- 会話の名前（Claude Code の `/rename`）は替えない。Claude Code に、外から会話の名前を替える口が無いため。替えたら、揃える `/rename <名前>` を出すので、その会話の中で打つ。
- `--dry-run` は、付け替える属性を出すだけで、何も書かない。

## アカウントを 1 つ選ぶ（手で会話を立てるとき）

dispatch を通さずに会話を立てるときも、同じ選び方でアカウントを選ぶ。

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/nodes/accounts.py" --pick
```

`main: claude — 5 時間 3%・週 1% で、高い方 3% が選べるものの中で最も低い。動いている会話 5 件` のような 1 行を出す。頭が選んだアカウントの名前、`:` の後がそのアカウントの起こし方の命令（設定の `command`）。`--json` を付けると、選んだ 1 件（`pick`）と全部の順（`accounts`）と注記（`notes`）を JSON で出す。選べるアカウントが無ければ、終了の値は 1。古い使用率の控えだけを取り直す（`--no-probe` で取り直さない）。

## 頼む・納品する: `--ask`・`--deliver`

部署への頼みと、部署からの納品（要約を返すこと）は、相手の会話の**待ち受け**が会話を起こして届ける。人の打つ入力欄に字を打ち込まないので、人が窓口に打っている途中に納品が届いても混ざらない。待ち受けの居ない会話（このフックの無い古い版の会話・落ちた会話）には、今までどおり herdr の窓（相手の会話の画面を出したペイン）に 1 行を打ち込む。アカウントが違っても届く（SendMessage は同じアカウントの会話にしか届かないので使わない）。仕組みと決めた訳は [受付の設計](../../docs/specs/2026-10-17-reception-design.md)。

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --ask <会社/役 か部署の名前> (--text <文> | --brief <ファイル>) [--task <名前> --branch <枝>] [--dry-run]
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --deliver <要約のファイル> [--dry-run]
```

どちらも打ち込んだ相手の作業の終わりを待たないので、前で走らせてよい。

- **待ち受け**: このプラグインのフックが、部署と窓口（属性 `company.role` と `company.name` の在る場所。窓口は `--desk` が書く）の会話の番の終わり（Stop）と始まり（SessionStart。`/clear`・compact・resume を含む）に、裏で待ち受けを起こす（Claude Code のフックの `asyncRewake`。終了の値 2 で手の空いた会話を起こす）。待ち受けは、その会社の受付箱の台帳 `log.jsonl` の、宛先が自分（「会社/名前」。前の名前も）の行だけを読み、宛先違いの行は会話に渡さない（会話の費用は 0）。待ち受けは会話ごとに 1 つで、印は受付箱の `wake/` に置く。窓口の待ち受けは、`--desk` が書いた会話の id の会話だけが張る（代表の clone で開いたほかの会話に知らせを横取りさせない。同じ処理の会話が `/clear` で id を替えたときは、属性の id を書き直して張る）。人の文で番が始まると、その場所の待ち受けを止める（番の終わりに張り直す）。フックの持ち時間は 7 日で、それより長く手の空いた会話は、次の番まで待ち受けの居ない会話として扱う。

- **宛先**: 部署の名前（属性 `company.name`。無ければ `--reorg`・`--desk` が覚えた前の名前）か「会社/役」。会社は herdr に開いているリポジトリ（`--tree` に出る会社の名前）で、省けば頼む側の会社。部署の名前が先に当たる。役で宛てたときは、その役の常設の部署へ届け、無ければ新しい部署を `--task` と同じ道で立てる（新しく立てるときは、部署の名前を `--task`、枝を `--branch` で渡す。省けば止まる）。役で宛てて部署の名前（`--task`）も渡したときは、その名前の部署へ届け、無ければ新しく立てる（同じ役の常設の部署が名前違いで居ても、そこへは届けない。枝は `--branch` で渡す）。宛先の会社は、頼む会話が `--tree` の「受ける仕事」を読んで選ぶ。
- **頼み（`--ask`）**: 本文を頼む側の受付箱に置き、宛先の部署の窓に「頼みです（受付 <番号>、<頼む会話> から）: <本文>」と、返し方の 1 文（要約を項目の見出しで書いたファイルにして `--deliver` で返す、という指示）を打ち込む。改行を含むか長い本文は、受付箱のファイルを指す。宛先の部署の属性に、受けた頼み（`company.ask`）と頼み元（会話の名前・アカウント・会話の id・ペイン・受付箱。`company.boss`・`company.boss-account`・`company.boss-session`・`company.boss-pane`・`company.boss-inbox`）を書く。新しく立てた部署には、最初の文で頼みを渡す。属性は毎回すべて書き直し、分からない値は消す（前の頼み元の値を残さない）。
- **順番待ち**: 待ち受けの居る部署への頼みは、宛先の会社の受付箱の `queue/` に積み、受付番号と何件目かを返す（前の頼みを納品していない部署にも止めずに積む）。部署が前の頼みを納品したら、待ち受けが次の 1 件を渡し（部署の属性に頼みと頼み元を書いてから）、会話を起こす。`fresh = true` の部署は、納品して止まった時点で空にし、空にした会話に次を渡す。同じ中身の頼みが積まれているか動いているなら、新しく積まずにその受付番号を返す。部署は頼みを 1 つずつ受け、頼み元の属性は渡すときに書く。待ち受けの居ない部署は今までどおり、前の頼みをまだ納品していなければ何もせずに止まる。先頭が詰まったら（部署が納品しないまま止まった）、`--tree` の部署の行に順番待ちの件数と置き場が出る。積んだファイルを消せば取り消せる。
- **落ちた部署の会話**: PC やサーバーの再起動で部署の窓（attach の画面）が消えると、部署の窓に会話が居なくなる。裏の会話の記録は残っているので、`--ask` は部署の窓のペインに `<アカウントのコマンド> attach <短い id>` を打って前の続きから戻し、窓に会話が戻るのを見てから頼む。短い id は会話の一覧（`claude agents --json`）の `id`（8 字）で、部署の属性の長い id（`company.session`）では Claude Code が「No job matching」と断る。窓に会話が居ないと見るのは、ペインに会話の印が無いとき、前に居るのがシェルのとき（macOS・Linux。herdr は attach の画面が終わった後も会話の印を残すことがある）、画面の終わりに「Session … has exited.」が出ているとき。会話の一覧がその会話を止まった（`stopped`・`failed`）と言うときも落ちたと見る（裏の処理が止まると、窓の attach が「Waking session …」のまま前に残り、窓の前のプロセスだけでは見分けられない）。そのときは、残った attach を Ctrl+Z でシェルに戻してから打ち直す。ペインを閉じて部署の作業場が herdr から閉じていれば、作業場を開き直してから、その新しいペインで打つ。頼みと促しの 1 行は、会話の画面に入力欄が出てから送り、会話が動き出した（会話の一覧の status が busy）かを見て確かめる。入力欄に残っていれば Enter を足し、入力欄にも画面にも見えず動き出してもいなければ打ち直す（3 回まで。Windows で、戻した直後の会話に送った文が、届かないか入力欄に残った。3 回でも確かめられなければ failed を返し、部署の窓を見て入力欄に残っていれば Enter を押すよう出す）。送る前から動いている会話には 1 回だけ打つ（打った字は、今の応答が終わった後に読まれる待ちの列〔入力欄の上に「❯ <打った字>」と並ぶ〕に回るので動き出しでは確かめられず、打ち直すと同じ頼みが何度も届いた）。入力欄に残れば Enter を足し、入力欄の上（待ちの列）に載るか入力欄から出たのを見て届いたとし、見えなくても打ち直さない。会話は、部署の属性の会話の id（`company.session`）で一覧から引き、見つからなければ、一覧のうち作業フォルダが部署の作業場で、終わっていない（`done`・`failed`・`stopped` でない）裏の会話（`claude --bg` の会話）が 1 つだけならそれで見る（0 か 2 つ以上なら見つからないとする。部署の会話で `/clear` を打つと id が変わる）。頼みを届けたとき、id が変わっていれば属性を書き直す。開き直したペインにも、`--sync` と同じ名前・表示名・札を付ける。窓の端末に貼り付けの印が残っていて打った命令が崩れた（画面に `00~` が出る）ときは、部署の窓で `reset` を打ってから打ち直すよう、`--ask` の出力で知らせて止まる。落ちる前の頼みをまだ納品していなければ、戻した会話にその納品を促す 1 行を打ち、新しい頼みは送らずに止まる（納品が届いてから頼み直す）。戻せないとき（ペインの前にシェルが居ない・作業場が開いていない）は、打つ命令を出して止まる。手で戻すときも、部署の作業場のペインで同じ命令を打つ。
- **部署の会話を止める**: 部署の窓に attach の画面が開いていると、`claude stop <短い id>` で止めても、窓の attach が会話を起こし直す（「Waking session …」。macOS で見た）。止めるなら、先に部署の窓で Ctrl+Z を押して attach の画面を終わらせ（`claude attach --help` の「Ctrl+Z drops back to your shell」。Ctrl-C では終わらない。macOS と Linux で確かめた）、それから `claude stop <短い id>` を打つ。ペインを閉じても attach は終わるが、部署の作業場も herdr から閉じる（次の `--ask` が作業場を開き直してから戻す）。短い id は `--tree` の部署の行か `claude agents` に出る。片付けるなら `--clean --apply`（都度の部署）。`claude stop` で止めた会話は、手元の確かめ（macOS と Linux の 2.1.301。Linux は裏の処理を起こし直しても）では止まったままだった。まっさらな環境での試しでは約 1 分後に起き直って頼みを済ませた例があり、何が起こしたかは分かっていない（dispatch の止まる前のフックは `claude stop` では走らないことを確かめた）。止めたままにしたいなら、1 分ほど後に `claude agents` で `stopped` のままかを見る。
- **納品（`--deliver`）**: 部署の場所から走らせる。要約の項目がそろっているかを確かめ、欠けていれば送らずに欠けた項目を出して終了の値 2 で止まる。そろっていれば頼み元の受付箱に置き、頼み元（「頼み元の会社/`company.boss`」）の待ち受けが居ればその台帳に知らせの 1 行を足し、居なければ頼み元の窓に「納品です（受付 <番号>、<部署>・枝 <枝> から）: 【結論】…【決め手】…（全文: <パス>）」を打ち込み、属性に納品済み（`company.delivered`）を書く。頼み元の窓が見つからなくても、要約は受付箱に置く。そのときは終了の値 1 で知らせ、納品済みにはしない（頼み元の窓が開いたら打ち直す）。要約のファイルは納品ごとに別にする（打ち直しで前の要約を消さない）。部署に渡す返し方の命令は、今動いている Python と dispatch.py のパスを `/` 区切りで引用符に包んだ形にする（Windows の Git Bash でも崩れない）。そのパスはプラグインの版の置き場の中なので、プラグインを上げた後は前の版を指す（Claude Code は前の版の置き場を 14 日残す）。dispatch.py は、版の置き場の中で動いていて、Claude Code の入れた物の控え（`installed_plugins.json`）が今の版を別の置き場と言えば、そちらの dispatch.py を同じ引数で起こし直す（前の版が、後の版で足した決まり〔会社の形の `[[land.after]]` など〕を黙って飛ばさないため）。
- **答え待ち（`--wait <訳>`）**: 部署の場所から走らせる。今の頼みが人の答えを要って止まっている（持ち主に聞いて、答えが数時間後になる など）と、部署の属性 `company.waiting`（受付番号）と `company.waiting-why`（訳）に書く。その頼みの間、止まる前のフックは納品を促さない（促しは番の終わりごとに同じ頼みにつき 3 回まで出るので、答えを待つ部署が無駄に番を回していた）。その会話に文が打たれると（人の答えのほか、窓に打ち込まれた知らせも）、文を受けたフックが印を外し、また納品を促す。納品でも外れる。A2A の頼みの状態 `input-required`（人の入力が要って止まっている）に当たる。役の名前は見ないので、どの役の部署でも使える。
- **区切り（`--rest`）**: 会話を持ち越す部署と窓口（`--desk` で名付けた本社の会話）が、文脈がたまり続けないよう、今は会話を空にしてよい区切りだと自分で印す（部署の属性 `company.rest` に、その場所の会話の id を書く）。その番の終わりに待ち受けが、窓の入力欄が空で会話が止まっていれば、窓に `/clear` を打って空にし、印を外す。空にした後の会話の始まりに役の本文が足され、本社の窓口は会話の id の付け直し（`company.pid` の追従）で頼みと納品をそのまま受ける。どこを区切りにするか（例: 受けた頼みを全部納品で閉じ、会話の中にしか無いことをファイルに書き終えたとき）は、各会社の形の役の本文に書き、このプラグインでは決めない。納品していない頼みが在る間は印せず、空にもしない。人がその会話に打つと印が外れる（持ち主と話している途中の会話は空にしない）。持ち主が手で compact する道はそのまま。本社の窓は、ペインの会話の印（herdr の `agent_session`）がその会話の id の物に打つ（本社に会話の居るペインがほかにも在っても、持ち主のほかの会話には打たない）。
- **部署から窓口への頼み**: 窓口（`--desk` で名付けた本社の会話）も `--ask <窓口の名前>` で宛てられ、部署と同じに受付番号と頼み元の属性が付く。窓口は受けた頼みを、回した先か結果を `--deliver` で返して閉じる（閉じるまで止まる前のフックが促し、次の頼みは順番待ちに積まれる）。持ち主の答えを待つなら `--wait` で印す。
- **要約の項目**: 見出し（`## 結論`）か行の頭の札（`結論: …`）で書く。既定は「結論」（3 行以内）・「決め手」（原文の一句と原典の URL）・「残った疑問」・「枝」（書かなければ部署の枝を機械が足す）。役ごとに会社の形（その会社の代表の clone の `.claude/company.toml`、無ければ設定の置き場の同じ書き方のファイル）の `[[roles]]` の `deliver` で替えられる（上の「役の中身と起こし方」と同じ項目に書く）。`--ask` が打ち込む返し方の 1 文には、その役の要る項目と、項目に付く決まり（結論は 3 行以内・決め手には原典の URL が要る など）を書く。決め手の URL の決まりは、決め手の項目を持つ役すべてに掛かる（既定の項目に残しているのは調べものの役のため。要らない役は `deliver` から決め手を外す。無い URL や決め手でない URL を足して通さない）。コードを書く部署なら、たとえば次のように書く:

```toml
[[roles]]
name = "作業"
deliver = ["結論", "差分", "試験", "残った疑問", "枝"]
```

- **納品の検査（`deliver_check`）**: 会社の中身の決まり（調べものの URL の原典を全部 `reference/` に残す、など）を、文で頼むだけでなく納品の時に機械で確かめる口。役の `deliver_check` にシェルの命令を書くと、`--deliver` が項目を確かめた後（`--dry-run` でも）に、部署の作業場の根（worktree の根）で走らせる。何を確かめるかは会社の側のスクリプトが持ち、dispatch は決め打ちしない。
  - 渡す物: 標準入力に JSON の物を 1 つ。`role`（役の名前）・`ask`（受付番号。`--task` だけで立てた部署は `null`）・`branch`（部署の枝）・`place`（走らせた作業場の根の絶対パス）・`items`（項目の名前 → 本文。枝は機械が足した後）・`summary`（頼み元の受付箱に置く要約の本文と同じ字）。
  - 終わりの値: 0 なら通り、そのまま送る。0 以外（スクリプトが見つからない 127 や、動かないときも）なら頼み元に送らず、`--deliver` は終了の値 2 で止まり、検査の標準出力と標準エラーを合わせた終わりの 20 行を `--deliver` の出力に出す（打った部署が読む）。訳（どの URL が `reference/` に無いか など）は検査が出力に書く。部署はそれを直して打ち直す。納品済みにしないので、止まる前のフックも差し戻し続ける（同じ頼みで 3 回まで。下の「止める前の差し戻し」）。
  - 時間の上限は付けない。検査を飛ばす旗も作らない（部署が自分で飛ばせる関所は関所にならない）。検査が壊れて誰も納品できないときは、会社の形の `deliver_check` を直して本流に入れる。

- **受付箱**: 頼み元の会社の共通の `.git` の中の `company/inbox/`。頼みと納品の本文を 1 件 1 ファイルで置き、`log.jsonl` に誰が誰に何を頼み何が返ったかを 1 行ずつ足す。`.git` の中なので commit されず、勤め先のリポジトリの `.gitignore` も触らない。部署ごとの `.git/worktrees/<部署>/` ではなく共通の `.git` に置くのは、部署を片付けても（`git worktree remove`）記録を残すため。
- **止める前の差し戻し**: このプラグインの Stop フックが、部署（`company.role` の在る場所）の会話で、受けた頼みを納品しないまま止まろうとしたら、納品の命令で返すよう差し戻す。同じ会話・同じ頼みで 3 回まで差し戻し、その後は止まるのを許す。部署でない場所と、`--ask` で頼まれていない部署（`--task` だけで立てた部署）では何もしない。

## 機械窓口: `--call` と合図

役ごとに、AI を起こさずに機械で答える道具を会社の形に書ける。どの会社にどんな道具を置くか（道具の台本そのものも）は会社の形とそのリポジトリが決め、works-dispatch は呼ぶ仕組みだけを持つ。機械窓口を付けてよいのは、**成功と失敗を機械で決められる仕事だけ**（道具は片づいたら終了の値 0、片づかなかったら 0 以外を返す）。

```toml
[[roles]]
name = "配布"
machine = true                       # AI の部署を持たない役（--ask で宛てられない）

[[roles.tools]]
name = "spread-plugins"              # 以下 4 つは MCP の道具の定義（Tool）の欄に合わせる
title = "全アカウントに配る"
description = "…"
inputSchema = { type = "object", properties = { dry_run = { type = "boolean" } }, additionalProperties = false }
command = "python3 scripts/spread-plugins.py"   # origin の既定の枝の中身（一時の worktree）の根で走らせる。入力の JSON を標準入力に渡す
fallback_role = "作業"               # 片づかなかったときに回す役（省けばその道具を持つ役。machine の役では要る）
```

```
bash "${CLAUDE_PLUGIN_ROOT}/hooks/run-python.sh" "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py" --call <会社/役> <道具の名前> [--input <JSON の字か @ファイル>] [--dry-run]
```

- **呼ばれて動く道具**（`--call`）: 片づけば答えを出して 0 で終わる。片づかなければ、外れ（`kind: "miss"`）を受付箱の台帳に残し、その入力を AI への頼みに変えて回す役に回し、受付番号を出して 3 で終わる（頼み元は呼んだ会話。待つか、自分で進めるかは頼み元が選ぶ）。回し方は `--ask` と同じで、回す役の常設の部署が在ればその順番待ちに積み、無ければ一度きりの部署を自動で立てる（名前は「<道具を持つ役>：<道具の title>」、枝は `work/<道具の name>-<受付番号の末尾 6 字>`）。入力は、物であること・`required`・`additionalProperties = false`・各鍵の `type` だけを確かめる。
- **合図で動く道具**: 出来事の欄に書いておくと、その出来事の後に呼ぶ。最初の出来事は本流に入れた後（`[[land.after]]`。下の「本流に入れる」）。
- MCP のサーバーは立てない（各会話の文脈に道具の定義を載せないため）。道具の一覧と外れの回数は `--tree` の会社の行に出る。
- 道具は会社の形を origin の既定の枝から読む（`--ask` と同じ）ので、会社の形に足した道具は本流に入ってから呼べる。

## 本流に入れる: `--land 部署`

部署（名前か枝の名前で指す。名前が無ければ、`--reorg` が覚えた前の名前でも引く）の枝を、会社の形（`.claude/company.toml`、無ければ設定の置き場の `companies/`）の `[land]` の決まりで本流に入れる。欄と例は、このプラグインの `docs/land.md`。

- 決まりが無い（`[land]` が無いか `mode = "none"`）なら何もしない。`mode = "pr"` なら、部署の枝を origin に出して PR を出し、止める。
- `mode = "ff-after-ci"` なら、関門（`gate`。CI の枝の形〔例 `release/*`〕か、手元の検証の `check`）を通し、緑で本流がまだ部署の枝の祖先なら、本流を早送りして push する。`bump = "marketplace"` なら、部署は版を上げずに出し、取り込むときに版を上げる commit を足してから関門に出す。
- 本流が先に進んでいれば、自分では merge せず、部署の窓に「本流の上に載せ直して push し直す」と打ち込んで止める。赤なら、失敗の要点を部署の窓に打ち込んで止める。部署が直したら、もう一度 `--land` を打つ。
- 入れたら、都度の部署は `--clean` と同じ決まりで片付ける（常設の部署と、会話がまだ動いている部署は残す）。会話がまだ動いているなどで残した都度の部署には入れた印（`company.landed`）を書き、次の `--land`（どの部署でも）が、会話が止まった後なら一緒に片付ける（`--clean --apply` でも片付く）。常設の部署は、入れた枝と入れた時の先頭を属性 `company.landed-branches` に書き、部署が次の頼みで枝を移った後の `--land`（どの部署でも）か `--clean --apply` が、その前の枝を手元から消す。部署の会話に「枝を移るときに前の枝を消す」を任せず機械で消すのは、会話は消し忘れても止まらず、消してよいか（入れた時の先頭のままか）を機械が確かに見られるため。
- `mode = "ff-after-ci"` と `bump = "marketplace"` で、版を最後に上げた後にフォルダの中のファイルを変えた（commit した）プラグインの `CHANGELOG.md` の `## [Unreleased]` が、版を上げる commit を足す前の時点で空（`### Fixed` のような `#` で始まる行だけ）なら、中身の無い版を作らずに `--land` 全体を止める（何も push しない。終わりの値は 1）。版を上げずに入れる道は無い（marketplace は版が変わった時だけ中身を取り直すので、上げなければ利用者に届かない）。部署が利用者に効く違いを書き足して commit したら、もう一度 `--land` を打つ。
- 書き換えの取り合いの関門: 部署が本流を最後に知った位置（属性 `company.base`。`--task` が枝を作ったときの origin の本流と、その部署の `--land` で入れた後の本流）より後に、ほかの部署が本流へ入れた行を、部署の枝が消して（書き換えて）いれば、関門に出さずに止め、部署の窓に「どの commit（件名）の、どのファイルの何行目を消すか」を打ち込む。部署が前に読んだ中身を覚えたまま書き直すと、ほかの部署が入れたばかりの行を消しても git の衝突にならず、関門の試験も通る（まっさらな環境での 2 回目の試しの 5）ため。部署はその行を残す形に取り込み直して push し、`--land` を打ち直す。わざと消すなら `--land <部署> --keep-removal` で通す。位置の記録が無い部署（0.19.8 までに立てた部署）は見ずに注記を出す（今の本流との merge-base は、載せ直した後の枝では本流の先頭になり、何も見つけないため）。入れた後は、その部署の位置を入れた後の本流に進める。
- `--dry-run` を付けると、決まりと見立て（載せ直しが要るか・入れる commit・上げる版・関門・片付け）を出すだけで、何も書かない・push しない・部署の窓に打ち込まない。打つ前の確かめに使う。終わりの値は、本当に打てば途中で止まる見立て（載せ直しが要る・中身の無い版など）か、見立てそのものの失敗（origin を読めないなど）なら 1、通る見立てなら 0。
- 会社の形の `[land]` の下に `[[land.after]]`（`role`・`tool`・省けば空の `input`）を書くと、本流へ push し終えた後に、その道具を順に呼ぶ（合図。上の「機械窓口」）。片づかなければ回し、回した頼みの頼み元は本流に入れた部署の頼み元にする。合図が片づかなくても本流に入れたことは取り消さず、`--land` の終了の値も変えない。`mode = "pr"` では本流へ push しないので呼ばない。
- CI を待つ間は戻らないので、Bash の道具の `run_in_background` で走らせ、終わりの知らせを待つ。
- 部署の会話が打つ `--land` は、Claude Code の自動の権限の判定（auto mode の classifier）に「Merge Without Review」として止められることがある。役の `settings` の `autoMode.allow` に、`--land` が会社の形の関門を通してから本流に入れる決まりであることを文で書くと、組み込みの拒否の例外になる（[Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)。`autoMode` はプロジェクトの `.claude/settings.json` からは読まれず、`--settings` で渡す役の設定からは読まれる）。`--init-company` の下書きの担当と作業はこれを持つ。それでも止められたら、部署は打ち直さずに納品で知らせ、窓口が `--land <部署の名前>` を打つ。`--land` は部署の場所の `__pycache__/` を数えない（部署を立てるときと `--land` のときに、代表の clone の `.git/info/exclude` に `.claude/settings.local.json` と一緒に足す）。

## しないこと

- 作業中の会話・未コミットの変更や push していない commit の有る会話は、送り直しにも片付けにも使わない（`busy`・`dirty`・`unpushed`）。相手の新しい返事が無い会話もそのまま（`no_news`）。前に送った後に相手の動き（コメント・レビュー・commit・head の変化）が無い PR は、会話を閉じてあっても開き直さない（`no_news`。`--pr N` で名指せば開く）。PR の作業場の外で同じブランチの会話が開いていれば、その PR は飛ばす（`already_open`）。
- シェルではない物（エディタ・dev server・別の会話）が前に居るペインには打ち込まない（`pane_busy`）。起こした Claude Code が信頼やログインの確認の画面で止まったら、`/catchup` を送らずに `blocked` と報告する。
- 依存（`.venv`・`node_modules`）は入れない。試験を走らせる段になってから、その会話の中で入れる。
- 起こした会話の `/catchup` のページ（`/catchup` が書く HTML のファイル）を、会話ごとには VS Code の窓に開かない（起こすコマンドの前に `ATTENTION_CATCHUP_OPEN=0` を置く）。全件を送り終えた後に、送った PR のページをまとめて、生きている VS Code の窓にタブで開く（`ATTENTION_CATCHUP_OPEN=0` で dispatch を走らせれば開かない。窓が無ければページの path を報告に出す）。
