# 役の中身と起動方法: 会社の形の `[[roles]]` と `gh_user`

dispatch のスキル（works-dispatch のプラグイン）の別ファイル。会社の形に役を足す・直すと頼まれたとき（書くフィールドを選ぶ）と、部署（作業ごとの worktree と、そこで働く Claude Code の会話の組）の役・model・effort・設定がどう効くかを確かめたいとき（下の項を読むだけ）に読む。ターンは会話の 1 回の応答、部署の窓は部署の会話を映した herdr（端末の画面を作業場とペインに分けて会話を並べるツール）のペイン。受け持ちは、会社の形の `[[skills]]` に 1 つずつ書く仕事の範囲（例 `割り振り`）で、名前が同じ部署に効く。場所は、属性（`git config --worktree` で書く `company.*` の値）を持つフォルダで、部署の worktree か代表の clone の作業ツリー。「場所の属性の会話」は、その場所の属性 `company.session` に書いた会話。

会社の形のファイル（`.claude/company.toml`、無ければ設定の置き場の `companies/` の物）に、役ごとの項目と、その会社の gh のアカウントを書ける。

```toml
gh_user = "<gh のログイン名>"   # 部署の会話の gh が使うアカウント（省けば、その人の今の gh の設定のまま）
default_role = "作業"            # --role を省いたときの役（[[roles]] のどれか。省けば 作業）
desk = "<会社>/<名前>"          # 任意。この会社に自前の窓口を置かず、ほかの会社の窓口（持ち主と話し仕事を配る会話）にこの会社の窓口も兼ねさせるとき、その窓口を <その会社>/<窓口の名前> で書く（--tree がこの会社の窓口と宛て方に出す。この会社の本社〔代表の clone〕に --desk で名付けた窓口が立てば、このフィールドよりそちらが先）

[[roles]]
name = "調べ役"                                  # --role に渡す名前（部署の属性 company.role）
instructions = "結論と原典の一句を返す。"          # 部署の会話の指示に足す役の本文。短く、AGENTS.md と同じことは書かない
model = "haiku"                                  # 部署を起動するときの --model（省けばアカウントの既定）
effort = "low"                                   # 部署を起動するときの --effort（inherit なら頼んだ会話と同じ。省けばアカウントの既定）
deliver = ["結論", "決め手", "残った疑問", "ブランチ"]   # 納品する要約の必須項目（省けば既定。「納品する」の「要約の項目」）
deliver_check = "python3 scripts/check_deliver.py"   # 納品の検査のシェルのコマンド（省けば検査しない。「納品する」の「納品の検査」）
persistent = true                                # この役で立てる部署は永続（--persistent を付けたのと同じ。この [[roles]] の項目に書く。例: 受け持ちごとに永続で立てる担当の役。前の版の resident = true も同じ意味で読む）
fresh = true                                     # 頼みごとに空の会話で受ける（省けば会話を引き継ぐ）
[roles.settings]                                 # 部署を起動するときの --settings（その会話にだけ効く Claude Code の設定）
permissions = { deny = ["Artifact", "Workflow", "ScheduleWakeup", "SendFeedback", "ReportFindings"] }
enabledPlugins = { "pr-review-toolkit@claude-plugins-official" = false }
skillOverrides = { dataviz = "off" }
```

- 部署の会話で `/clear`・圧縮（compact）・`--resume` をすると会話の id が変わる。同じ SessionStart のフックが、そのとき（フックの入力の `source` が `clear`・`compact`・`resume`）だけ部署の属性 `company.session` を新しい id に書き直す。古い id のままだと、`--ask` が会話の動き出しを見られず、Stop のフックが部署の会話を別の会話と見て納品を促さなかった。裏の会話の短い id（`claude attach` に渡す。`/clear` の後も変わらない）は属性 `company.job` に残し、部署の窓から会話が消えて --ask が戻すとき、会話の一覧にその会話が見えなければ、部署の窓に `<アカウントのコマンド> attach <短い id>` を打って戻す（頼みを打ち込むのは戻った後）。新しく起動した会話（`startup`）では書き直さない。代表の clone（持ち主の会話がほかにも居る）では、`--desk` が書いた会話の処理の番号（属性 `company.pid`。その会話の Claude Code の処理）の会話が `/clear` などをしたときだけ書き直す（窓口は区切りで `/clear` しても、`--desk` を打ち直さなくてよい）。
- 部署の会話がターンを終えて、裏で走らせた処理（`run_in_background` の Bash・裏で立てたサブエージェント・Monitor。`--land` など）の終わりを待っているときは、herdr の状態が done になり、終わったように見える。待っている印は、共通の点検の部品 tiers の statusline（`tiers-statusline setup` でアカウントごとに入れる。中身は tiers の README の「Status line」）が出す。会話の画面の下に「⧖ バックグラウンド作業中 N 本」を出し、herdr にその会話を作業中（working）と見分けさせる。このプラグインの Stop のフックは印を出さず、待っている間は、納品していない頼みの差し戻しをしないだけ（裏の処理が終わると Claude Code が会話を再開させるので、納品はその後でよい）。裏の処理の数は、Stop のフックの入力の `background_tasks` の running の物で数え、その一覧の無い版の Claude Code では会話のプロセスの子に残る Bash のツールのシェルを `ps` で数える（Windows では数えられず、差し戻す）。
- 役の本文は、このプラグインの SessionStart のフックが、会話の始まり（やり直し・圧縮の後も）に足す。足すのは部署（属性 `company.role` の有る worktree）と、`--desk` で窓口を名付けた代表の clone（部署ではないので「本社の会話」と書く）だけで、代表の clone では窓口の席に座る会話だけに足す（属性の会話〔`company.session`〕か、`--desk` を打った会話と同じ処理〔`/clear` の後〕か、窓口の会話が動いていないときに窓口の名前で起動した会話〔`claude --name <窓口の名前>`〕。名前の無い試しの `claude -p` や、窓口が動いている間に起きたほかの会話には足さない）。会社（会社の形の在るリポジトリ）の場所で役の本文を足さない会話（部署の属性の無い作業場の会話・代表の clone の窓口でない会話）には、ほかの会社への頼み方の 1 行（SendMessage でなく `--ask <会社の名前>` を打つ）だけを足す。SendMessage の頼みは受付の台帳に頼み元が残らず、受けた側が返し先を覚えておくしかないため。会社になる前から動いている会話には、会社になった後の最初のターン（UserPromptSubmit）で足す（その会話にまだ何も足していないときだけ）。会社でないリポジトリの会話には何も足さない。毎回の起動の量に入るので短く書く。部署の名前（属性 `company.name`）と同じ `name` の受ける仕事（`[[skills]]`）が有れば、その説明も受け持ちとして足す（役を 1 つ〔担当〕にして、受け持ちごとの中身を部署の名前で引くため）。
- `git worktree add` は、代表の clone の worktree ごとの git の設定（`config.worktree`）を新しい worktree に写す。そのため、窓口の属性（`company.role` など）を写されたまま残った worktree がある。そうした worktree も代表の clone と同じ決まりで見て、役の本文は窓口の会話にだけ足す。窓口の会話かどうかは `company.pid`（`--desk` だけが書く、窓口の会話の処理の番号）で見る。写された worktree で起動した PR の会話は、窓口として振る舞わない。
- 属性を書くとき、書いた worktree の id（git の worktree の管理の場所 `.git/worktrees/<id>` の `<id>`。代表の clone は `.`）も `company.worktree-id` に書く。読むときは、この値が読んだ設定の置き場の id と違えば、ほかの worktree から写った物として、属性が無いと読む。そのため、部署が自分の作業場から `git worktree add` で一時の worktree を切っても、その worktree は同じ名前の部署に見えない（`--move`・`--ask`・`--land` が「2 つ以上ある」で止まらない）。写った属性の上に部署を立てるときは、写った物を先に丸ごと消してから書く。この版より前に書いた属性（`company.worktree-id` が無い）は今までどおり読むので、その部署の属性が次に書かれる（頼みを受ける・納品するなど）までに切った worktree は、前と同じく部署に見える。
- 会社の形の役（名前・本文・受け持ちの説明）を替えたら、会話を引き継いでいる部署と窓口にも、次のターンの頭に今の文を足す（UserPromptSubmit のフック。待ち受けが納品などの知らせで会話を再開させるときは、会話に渡す知らせの文の前に足す）。その会話に前に足した文と比べ、違うときだけ足す（足した文の控えは会話ごとに TMPDIR の `works-dispatch-role-<会話の id>`）。会話は空にしないので、持ち主との話は消えない。足すのは場所の属性の会話（`company.session`）だけ。
- 役の名前を替えるときは、今の名前の項目に前の名前を `former_names = ["<前の名前>"]` と書く（Terraform の `moved` と同じく、名前の替え方を会社の形に書いて、属性の側を手で直さない）。前の名前で宛てた頼み（`--ask 会社/前の名前`）と `--call` は今の役に当たり、属性 `company.role` に前の名前を持つ場所は、今の役の本文を受け、会話の始まりとターンの頭のフックと `--sync` が属性を今の名前に書き直す。今の役の名前や、2 つ以上の役の前の名前と重なる前の名前は、注記に出して引かない。
- `settings` は、その会話の間だけ、利用者の全体の設定とリポジトリの設定の同じ鍵より先に効く。全体の設定とリポジトリの設定は触らない。ツールの名前だけを `permissions.deny` に書くと、そのツールは会話の文脈から消える。`skillOverrides` は Claude Code に同梱のスキルにだけ効き、プラグインのスキルには効かない（プラグインごと切るのは `enabledPlugins`）。`enabledPlugins` で works-dispatch 自身を切ると役の本文が足されないので、dispatch が注記を出す。
- `model` と `effort` は、部署を起動するとき（`--task` と、`--ask` で新しく立てるとき）だけ渡す。省けばそのアカウントの既定のまま起動し（そのアカウントの Claude Code の設定に保存した値、無ければモデルの既定。Opus 5.5 の effort は medium）、値を書けばその値で起動する。`effort` は `low`・`medium`・`high`・`xhigh`・`max`・`ultracode` のどれかか `inherit`。`inherit` なら、dispatch を打った会話（頼んだ会話）の今の effort で起動する（Claude Code が Bash のツールに渡す `CLAUDE_EFFORT` を読む。読めなければ既定で起動して注記を出す）。`--effort` はその会話にだけ効き、設定の `effortLevel`・`modelSettings` より強い。知らない値は Claude Code が注意を 1 行出すだけで既定に戻す（裏の会話の注意は誰も読まない）ので、読むときに弾いて注記を出す（役は外す）。`model` の `inherit` は作っていない（頼んだ会話の今のモデルは、Bash のツールの環境変数にも `claude agents --json` にも出ない）。書けば注記を出して役を外す。`--ask` が既に立っている部署に頼みを送るときは、モデルと effort を渡さない。会話を引き継ぐ部署は起動したときのまま変えない。`fresh` で会話を空にする部署は、次の頼みを渡す前に、会社の形の値が起動したときと違えば起動し直す（下の `fresh` の項）。
- 部署ごとにモデルと effort を替えるなら、受け持ち（`[[skills]]`）の項目に `model`・`effort` を書く。書ける値は役の `model`・`effort` と同じで、`model` の `inherit` は形の違う値として扱う。永続の部署はどれも役「担当」で起動するので、役の値だけでは部署ごとに替えられない。決める順はフィールドごとに、部署の名前（`--task` の名前。herdr の作業場の名前）と字が同じ `name` の受け持ちの値、部署の役（`--role` か `--ask 会社/役` で決まる。受け持ちの `role` フィールドではない）の値、アカウントの既定（`--model`・`--effort` を付けず、そのアカウントの Claude Code の設定のまま）。受け持ちに `effort` だけを書けば、モデルは役の値のまま。同じ名前の受け持ちが無いか、受け持ちに書かなければ今までどおり。形の違う値はそのフィールドだけ外し（受け持ちのほかのフィールドはそのまま使う）、注記を出して次の順の値で起動する（止めない）。効くのは役の値と同じく部署を新しく起動するときと、`fresh` の部署が次の頼みの前に起動し直すとき（下の `fresh` の項）。会話を引き継ぐ部署は起動したときのまま変わらない（落ちた会話を `--ask` が `attach` で戻すときも、前の会話のまま）。`--tree` の受ける仕事の行に、受け持ちに書いた値（形の違う値は出さず、`!` の行に注記）を出す。

```toml
[[skills]]
name = "割り振り"     # 部署の名前と同じ
role = "担当"
model = "sonnet"      # この部署だけ、役の model より優先する
effort = "low"        # この部署だけ、役の effort より優先する
```
- 効きは、`claude plugin details` の見積もりではなく、起動した会話の最初の API 要求のトークン（入力とキャッシュの書き・読みの和）で確かめる（見積もりは、フックが足す文やサブエージェントの説明の例を数えない）。
- 役は `[[roles]]` の形だけで書く。`[roles."調べ役"]` のように名前で引く表の形は読まず、`[[roles]]` の項目に移すよう注記を出す（TOML では同じ `roles` を両方の形で書けず、混ぜると片方が黙って効かないため）。`[roles.settings]` の行より後に書いたフィールドは `settings` の中に入るので、`deliver` などのフィールドは `[roles.settings]` より前に書く（`settings` の中に `deliver` が有れば注記を出す）。
- 会社の形の頭の `desk_role` は、本社で持ち主と話す会話の役（`--desk` で `--role` を省いたときの役）。省けば、本社が今持つ役、それも無ければ `窓口`。
- `--role` で名指した役が、役を書いた会社の形に無ければ止まる（部署を立てず、理由を出して終わる。書き損じで設定が黙って効かないのを防ぐ）。`--role` を省いたときの役は会社の形の `default_role`、無ければ `作業`。`default_role` が `[[roles]]` に無い名前なら、会社の形の誤りとして注記に出し、`作業` に代える。こうして決めた役も、役を書いた会社の形に無ければ止まる（役の名前を英語で書いた会社で、どの役でもない `作業` の部署を立てない）。会社の形を読めない（TOML が壊れているなど）ときも、`--role` を省いた頼みは止まる。
- `persistent = true` の役は、`--persistent` を付けなくても永続の部署で立つ。役で宛てた頼み（`--ask 会社/役`）で部署がまだ無いときに `--persistent` を付け忘れてもエフェメラルの部署にならず、次に同じ役で頼んだときに同じ部署に届く。
- `fresh = true` の役は、頼みごとに空の会話で受ける。`persistent`（上の項の、永続の部署で立てるかの設定）とは別の軸で、永続の席（順番を 1 本にする・宛先の名前・決まった窓）は残したまま、前の頼みの記憶を引き継がない（記憶は太るうえ、覚えた中身でファイルを書き直すと、ほかの部署がメインブランチに入れたばかりのファイルの行を消す）。会話を空にするのは `/clear`（Claude Code の、会話を空にするコマンド）で、打つのは次の項のとおり待ち受けか `--ask`（部署に頼みを送るコマンド）。
- 待ち受け（ターンの終わりにこのプラグインのフックが裏で起動し、受付箱の台帳を見て会話を再開させる処理。「頼む」のセクション）の居る部署は、納品して止まった時点で、待ち受けがその部署の窓に `/clear` を打って会話を空にする（終わった会話が画面に残り、herdr に done と出続けないように）。ただし、会話が裏で走らせた Bash（上の項の「裏の処理」）が残っているか、会話が動いているか、入力フィールドに字が在るか、待ち受けがその会話の居る窓を herdr で確かめられないときは、待ち受けは前の会話のまま次の頼みを渡さず、5 秒ごとに空にするのを試し直す（渡さない訳は台帳に `held` の行で残る）。
- 待ち受けの居ない部署（このフックの無い古い版の会話）は、今までどおり `--ask` が空にする。部署が前の頼み（属性 `company.ask`。部署が今受けている頼みの受付番号）を納品し終えていて会話が止まっていれば、`--ask` は新しい頼みを打つ前に `/clear` を打ち、会話の一覧の会話の id が変わったのを見てから頼む。前の頼みが無い部署（`--task`〔部署を立てるコマンド〕が書いた頼みのファイルで働いているかもしれない）は空にせず、「空にしなかった」と `--ask` の出力に注記して頼みを送る。納品し終えた部署を空にできない（会話が動いている・`/clear` の後に会話の id が変わったのを確かめられない）ときは、頼みを送らずに次の 2 つに分ける。待ち受けの跡〔前に待ち受けを張ったことを示す、受付箱の `wake/<場所の鍵>.pos`。場所の鍵は、場所のフォルダのパスから作る 16 字の名前。今は止まっていてもよい〕が在り、部署がターンの途中なら、頼みを順番待ちに積む（待ち受けが後で渡す）。跡が無いか、ターンの途中でないなら、終了の値 1 で止める。
- 会話を引き継ぐ役（`fresh` でない部署と、本社の窓口〔代表の clone で `--desk` を打って名付けた、持ち主と話す会話〕）も、会話が自分で区切りと判断して `--rest`（ここで会話を空にしてよいと印すコマンド）で印せば、そのターンの終わりに同じく空にする（「納品する」の「区切り」）。
- 部署には役の `fresh` を属性 `company.fresh` に写す。写すのは `--task`・`--ask`・`--reorg --role`（部署の役を替えるコマンド）・`--sync`（herdr の表示を部署の属性から付け直すコマンド）のとき。会社の形の `fresh` を変えたら、ターンの終わりのフックが今いる全部の部署の属性と herdr の表示に行き渡らせる（「herdr の表示を付け直す」）。
- 別の話で、`--init-company`（会社の形の下書きを書くコマンド）が書く下書きの既定は、担当が永続・毎回クリア、作業がエフェメラル、相談が永続・引き継ぎ。
- `fresh = true` の部署の model・effort: `/clear` は会話を空にしても、起動したときの `--model`・`--effort` を残す。そこで待ち受けは、順番待ちの次の頼みを渡す前に、会社の形の今の `model`・`effort`（部署の名前と同じ名前の受け持ち〔`[[skills]]`〕に書いた値、無ければ役の値。`inherit` は頼んだ会話の今の effort に置き換えず、`inherit` の字のまま比べる）を、部署を起動したときの値（属性 `company.launched`。`--task` が書く。この属性の無い、前の版で起動した部署は `--model`・`--effort` を付けずに起動したと見る）と比べ、違えば `--move <部署> --if-changed` を裏で走らせて起動し直す（「ほかのアカウントで起動し直す」）。起動し直した会話の待ち受けが、その頼みを渡す。持ち主が打つコマンドは無く、会社の形の `model`・`effort` を書き替えれば（リポジトリの `.claude/company.toml` なら origin の既定のブランチに入れれば）、次の頼みから効く。会話の中で `/model` を打つ形は採らない（引数で打つ `/model` は、そのアカウントの新しい会話の既定として保存され、同じアカウントで持ち主が話す会話の既定まで替わる）。
- `machine = true` の役は、AI の部署を持たない役（AI を起動せずに機械で答えるツール〔`[[roles.tools]]`〕だけを持つ。「機械窓口」）。`--ask` で宛てられない。
- gh のアカウントは、dispatch の設定の `[[repos]]` の `gh_user`（前提のセクションの、設定の `gh_user` と同じフィールド）を先に、無ければ会社の形の `gh_user` を使う（commit した会社の形に書かれたアカウントは、ほかの人のものでありうるため）。dispatch は名前だけを部署の属性 `company.gh-user` に書く。フックがそれを読み、会話の Bash がコマンドごとに `gh auth token --user <名前>` で鍵を取り出して `GH_TOKEN` に入れる。鍵の値は、ファイルにも画面にも履歴にも残らない。そのアカウントで gh にログインしていなければ、`GH_TOKEN` に使えない字を入れる（gh はほかのアカウントに落ちずに、認証の誤りで止まる）。dispatch の設定の場所や gh のアカウントを前の回と替えて同じブランチの部署を立て直すと、前の回の属性は消してから書く。PowerShell のツールには `GH_TOKEN` が入らず、そこで打つ gh は、その人の今の gh の設定のアカウントで動く（フックが足す `export GH_TOKEN="$(gh auth token …)"` の行は `$(…)` で gh を走らせる形で、Claude Code が PowerShell に写すのは `export 名前=値` のように値をそのまま読める行だけのため）。鍵を `GH_TOKEN` で gh に渡している人（コンテナや CI の形）は `gh_user` を書かない（`gh auth token --user` は `GH_TOKEN` の鍵を取り出せず、部署を立てるときの確かめで止まる。`--init-company` の下書きは、取り出せないアカウントを書かない）。
- フォルダの信頼は、Claude Code が `.claude.json` の `projects` に書いたフォルダの字と、dispatch の持つ字が違っても（Windows の `C:/…` と `C:\…`、macOS の `/tmp` と `/private/tmp`）、同じフォルダを指していれば信頼済みと見る。部署の作業場に付ける信頼の印は、Claude Code が書いた区切りに揃える。
- 既定の置き場でない dispatch の設定（`--config` か `WORKS_DISPATCH_CONFIG`）で部署を立てたときは、フックがその隣の `companies/` を読めるよう、設定の場所を部署の属性 `company.config` に書く。
