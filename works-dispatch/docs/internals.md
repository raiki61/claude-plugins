# works-dispatch の内部の作り

この文書は、works-dispatch の作りを直す人向けの参照。works-dispatch は、作業ごとに Claude Code の会話を別に立てて仕事を頼み、終わったら要約を頼んだ会話へ返させる Claude Code のプラグイン。自分の番の PR（使う人のレビューや返事を待っている PR）を、PR ごとの作業場に開いて読ませることもできる。

直す人は、直す前に、直すファイルに当たるセクション（「形」の層の向き・ノード・外への口、「受付」など）を読み、そこに書いた決まりに合わせる。使い始め方は [README](../README.md)、使う人向けの手順の全部は [SKILL.md](../skills/dispatch/SKILL.md) と、そこから主題ごとに指す別ファイル（`skills/dispatch/references/`）。

言葉（使う人向けの説明は `skills/dispatch/references/setup.md` の「言葉」）: 会社は部署を置いて回す git のリポジトリ 1 つ。会社の形はその設定ファイル `.claude/company.toml`（役・受け持ち・メインブランチへの入れ方を書く）。部署は作業ごとの git worktree と、そこで働く Claude Code の裏の会話の組。役は部署の会話の決まり（窓口・担当・作業など）。窓口は代表の clone で持ち主（このプラグインを使う人）と話し、部署に頼みを配る会話。頼みは部署への仕事の依頼（`--ask`）、納品は部署が結果の要約を頼み元へ返すこと（`--deliver`）。受付箱は頼みと納品の台帳（`.git/company/inbox/log.jsonl`）と順番待ちを置くフォルダ。区切りの印は、会話が `--rest` で付ける「ここで会話を空にしてよい」という印。終わりの印は、エフェメラルの部署が `--done` で付ける「畳んでよい」という印（どちらも部署の属性 `company.*`）。ほかのプラグインと pack: attention は `/catchup` と `/whose-turn`（自分の番の PR を並べるコマンド）を持つプラグイン。tiers は、要るツールがそろっているかを点検するプラグイン。works は、このリポジトリの別のプラグインで、コードの直しの頼みを AI の段（調べる・計画する・直す・レビューなど）の流れで回す。pack は Archon（YAML に書いた AI の段を順に回すツール）に載せるワークフローのひとまとまりで、works はその 1 つ。流れの本体のワークフローの名前が darkfactory。

## 全体

自分の番の PR（attention プラグインの `/whose-turn` が、このプラグインを使う人のターンとして並べる PR）を、ブランチごとの作業場（代表の clone〔ブランチごとの worktree を作る元にする、ふつうの clone〕の git worktree と、herdr〔端末を作業場ごとに分けて並べ、中の Claude Code の会話を外から操作できる端末のツール〕の作業場）に開き、使用率（アカウントの 5 時間と週の利用枠を使った割合）に余裕のあるアカウントの Claude Code で `/catchup <番号>` と、設定のファイルに書いた 2 ターン目の文を送る Claude Code のプラグイン。相手（その PR の自分以外の人。レビュアーや作者）の新しい返事が有れば同じ場所に会話を立て直して送り直し、閉じた PR の場所は片付ける（作業場の一生を 1 つのコマンドで回す）。issue から始める作業も、issue に結んだブランチの作業場を開いて `/catchup <issue の番号>` まで送れる（`--issue N`）。作業ごとの部署（ブランチの作業場と、そこで働く Claude Code の裏の会話）を立て、頼みのファイルを渡し、herdr に画面を並べることもできる（`--task`）。部署は会社（リポジトリ）ごとのツリー図に出し（`--tree`）、herdr の表示は部署の属性から付け直す（`--sync`）。窓口（人と話し、部署を立てて仕事を渡す、長く生きる Claude Code の会話。dispatch を呼ぶ側）と部署の形は SKILL.md とそこから指す `skills/dispatch/references/`、会社の形の設計は、このリポジトリ（claude-plugins）のルートの `docs/specs/2026-10-16-company-shape-design.md`。herdr は、端末を作業場ごとに分けて、中の AI の会話を外から操作できるツール。修正の工場 works（darkfactory）と同じ系列の名前を持つが、中身は works の何も使わない。

- dispatch 自身の判断に AI は使わない（起動した Claude Code の会話は別）。全部 Python の標準ライブラリだけのスクリプト（`dispatch/`）で、`/works-dispatch:dispatch` のスキル（`skills/dispatch/SKILL.md`）はそれを走らせて出力を見せるだけ。
- 設計の正本: [`docs/specs/2026-10-14-catchup-dispatch-design.md`](specs/2026-10-14-catchup-dispatch-design.md)。計画: [`docs/plans/2026-10-14-catchup-dispatch.md`](plans/2026-10-14-catchup-dispatch.md)。
- 変更の記録: [CHANGELOG.md](../CHANGELOG.md)。

## 形（ノードと外への口）

このセクションは、`dispatch/` のファイルを足す・直す人が、直す前に読む。直すファイルがどの層の物か（入口の側・ノード・外への口のどれか）を下の一覧で探し、その層の決まり（呼んでよい向き・置き場）に合わせて直す。急ぎの物は無く、層の向きに合わない import などは試験のチェック（下の「チェック D1〜D9」の項）が止める。

- 層は 3 つ。上の層（下の一覧の 1 が一番上）は下の層を呼ぶ。ノードは上の層を読まない（import しない。チェック D3 が見る。チェックは、試験が構文木と文字で見る決まり。下の「チェック D1〜D9」の項）。外への口は dispatch の中の物を何も読まない。外への口のうち、移り変わりの激しい 2 つのツール（herdr と Claude Code）は、ほかの層から名指しせず、口の束 `ports.py` から、ツールの名前でなく用途で付けた名前（端末の口 `term`〔今は herdr〕・会話の口 `chat`〔今は Claude Code〕）で取る（例 `from ports import chat`。下の「外のツールの口」の項。チェック D9）。ファイルを足すときや import を足すときは、どの層の物かを先に決め、この向きに合わせる。
  1. 入口の側: 流れ（どのノードを、どの順に呼ぶか）を持つ入口の `dispatch.py` と、ぶつかりを減らすために入口から分けたファイル（`orders.py`・`landing.py`・`calls.py`・`move.py`・`reorg.py`・`retire.py`・`starts.py`・`todo.py`・`reminds.py`）、前の版の置き場で打たれたときに今の版へ乗り換える `installed.py`、Claude Code が起動するフック（`*_hook.py`。フックの入力を読んで、入口の側のほかのファイルかノードを呼ぶ）。
  2. ノード（`dispatch/nodes/`）: 下の項。
  3. 外への口（`herdr.py`・`gitx.py`・`ghx.py`・`claudex.py`・`tierx.py`・`vscode.py`）と、herdr と Claude Code の口の束（`ports.py`）: 下の「外への口」と「外のツールの口」の項。
  - 入口の側とノードが共に使う部品が 2 つある。部署の窓（部署の会話を映すペイン）を決める決まり `windows.py`（端末の口と会話の口を組み合わせる）と、口の束 `Ports` を組み立てる 1 か所 `wiring.py`（composition root。どの口にどのアダプタを差すかを入口の近くの 1 か所で決める形）。
  - どの層にも入れていない任意のツールが 2 つある（`limits.py`・`activity.py`。下の「流れの外に」の項）。
- ノードは、1 つの仕事と、入出力の JSON（`dispatch/schemas/`）を持つ。ノードはほかのノードも、入口の側のファイルも import しない（チェック D3）。今この決まりに背いている所が 5 件ある（`nodes/refresh.py`・`nodes/tree.py`・`nodes/sync.py` が、役の名前と並べる順・属性の名前・`start.parse`（start ノード `nodes/start.py` の、受け持ちの起動方法 `[skills.start]` を読む関数）をほかのノードから借りる。借りるファイルと借りられるノードの組で数える）。これらは、チェックが見逃す既知の背きの一覧（`dispatch/tests/fences.py` の `D3_KNOWN`）に載せてある。直したら一覧から消し（消し忘れるとチェックが誤りにする）、新しくは載せない。
  - prs: 自分の番の PR を集める。
  - sessions: 開いている会話を読む。
  - fresh: 自分が作者でレビュアーの付いていない PR を見分け（開くが `/catchup` だけを送り、2 ターン目の文は送らない。持ち主の決め 2026-10-16）、会話の開いている PR を送り直すか決める（相手〔その PR の自分以外の人。レビュアーや作者〕の新しい返事が有り、会話が手すきで手元の作業〔未コミットの変更・git に足していないファイル・手元にしか無い commit・そのブランチの stash〕が無いときだけ）。会話の開いていない PR も、前に送った後に相手の動きも head の変化も無ければ開き直さない（`no_news`。`--pr` で名指したときは開く）。
  - accounts: アカウントを並べる。週の枠の切り替わりが近い（既定 24 時間以内）ものを先に、それ以外は 5 時間と週の高い方の使用率の低い順、同じなら動いている会話の少ない順。単独でも呼べ、`python3 dispatch/nodes/accounts.py --pick` が 1 つ選んで「名前: 起動コマンド — 選んだ訳」の 1 行を出す（`--json` で機械向け）。人が手で会話を立てるときも、dispatch と同じ選び方を通すための口。
  - assign: PR をアカウントと作業場に割り振る。全部の PR は同時に走るので、始める前に、各アカウントの使用率の残りと 1 件あたりの使用率から件数を決める。
  - cost: 1 件あたりの使用率を測って覚える。dispatch が始める前と、全件の `/catchup` が終わった後の 1 回ずつ、使用率を Anthropic の API に問い合わせ（出力 0 トークン）、アカウントごとに、前後の使用率の差に 1 を足した物（使用率は 1% 刻みで届くので、本当の増えは見えた差 + 1 より小さい。少なく見積もると 1 つのアカウントに入れすぎるので、上の端を採る）を、今回そのアカウントで開いた件数で割る。使用率の控え（`limits.py` がアカウントごとに書くファイル `~/.cache/claude-limits/<アカウント>.json`）には、Claude Code のステータスライン（statusline。画面の下の 1 行を出すコマンド）が受け取る使用率も、`limits.py record` で書き込まれる。ただし `record` は、週の枠の値を、枠が切り替わったときと控えに週の値が無いときにしか書かない（放置した会話が持つ古い値で今の値を潰さないため）。そのため控えの週の値は枠の中で動かず、cost は控えを使わずに問い合わせで取る。
  - provision: ブランチの場所（代表の clone の git worktree）と herdr（端末を作業場ごとに分けて並べ、中の会話を外から操作できる端末のツール。作業場の中の 1 枚の画面をペインと呼ぶ）の作業場を、無ければ作り、有れば開き直して、origin の head へ fast-forward する。部署（`--task`）の場所は `prepare_task` が用意し、origin に無いブランチも既定のブランチから作り、在る場所は git で動かさない。代表の clone 自身がそのブランチを開いていれば作らない（`branch_busy`）。`--issue` で issue にブランチがまだ無ければ、GitHub にブランチを作って結ぶ（`gh issue develop`）。
  - launch: Claude Code を起動する。部署は、ペインに名前を付け（`herdr pane rename`）、裏の会話（`--bg --name <名前> --settings <設定のファイル> [--model <モデル>] [--effort <段>] <最初の文>`）として打ち込み（`start_background`）、同じペインで `attach`（`<アカウントのコマンド> attach <id>`。裏の会話の画面をペインに出す）する。設定のファイルは、役に設定が無ければ `templates/department-settings.json`、有れば役の設定の上に同じ `worktree.bgIsolation = "none"` を重ねて（同じ鍵が役の設定に有っても、こちらが勝つ）部署の `.git` の場所に書いた物。
  - role: 会社の形（リポジトリの `.claude/company.toml`、無ければ設定の置き場の `companies/` の TOML）の `[[roles]]`（役の本文・モデル・effort・起動の設定・納品する要約の必須項目）と `gh_user` を読み、部署を起動するときの設定（`--settings` の JSON。役の `[roles.settings]` に、`duty_of` で引いた受け持ちの `settings` を重ねる）・`--model` と `--effort` の値（`launch_flags`。フィールドごとに、会社の形の `[[skills]]`（受け持ち。部署が受ける仕事ごとの項目）のうち `name` が部署の名前と同じ項目（無ければ「<受け持ち>：<何をするか>」の名前の「：」より前〔長い方から〕と同じ項目。`duty_of`）の値、無ければ `[[roles]]` の役の値、どちらも無ければアカウントの既定。effort の `inherit` は呼んだ会話の `CLAUDE_EFFORT`）と、フックが足す文を組み立てる。書き方は `skills/dispatch/references/roles.md`、設計は会社の形の設計 4.7・4.8。
  - turn: `/catchup` と 2 ターン目の文を送る。1 ターン目の終わりは Claude Code 自身の会話の状態で見る。会話を終える（`/exit`）口も持つ。
  - clean: 代表の clone の linked worktree のうち、消してよい場所を並べる・消す（herdr の worktree の口は手元のブランチを残すので、ブランチは続けて `gitx.delete_branch` で消す）。消してよいのは、PR が閉じていて、会話も手元の作業も無い場所（条件の全部は `dispatch/nodes/clean.py` の冒頭と `skills/dispatch/references/clean.md`）。ペインの作業場だけを畳む口（release）も持つ。
  - report: 結果を 1 件 1 行で出す。
  - tree: herdr の作業場と全アカウントの会話が指すリポジトリを会社とし、会社ごとに会社の情報（`.claude/company.toml`、無ければ設定の置き場の `companies/`）と部署（worktree・属性・会話の状態・窓〔その部署の会話を映す herdr のペイン〕）を組み立てる。
  - deliver: 依頼と納品の中身。宛先（「会社/役」か部署の名前）と頼み元の窓を決め、要約の項目（会社の形の `[[roles]]` の `deliver` で役ごとに替えられる。そのフィールドを会社の形から読むのは role ノードで、deliver は読んだ結果を受け取る）を確かめ、頼み元の会社の共通の `.git` の中の受付箱（`company/inbox/`）に本文と台帳（`log.jsonl`。頼みと納品ごとに、宛先・頼み元・届いたかを 1 行）を置き、窓に 1 行を打ち込む。Stop フックの差し戻しの判定も持つ。
  - sync: 部署の属性から、herdr のペインの名前・表示名（役）・題名（会話の名前）・札（ペインに添える短い印。役・アカウント・頼み元）を組み立て直す（何度打っても同じ）。
  - land: 部署の成果をメインブランチに入れる決まり（会社の形の `[land]`）を読み、ゲートのブランチ（CI を走らせるために、メインブランチに入れる前の commit を push するブランチ。例 `release/*`）へ出して CI の run を待ち、緑でメインブランチが祖先ならメインブランチを fast-forward して push する。メインブランチが先に進んでいれば、merge せず、land が自分で部署のブランチをメインブランチの上にリベースし、ゲートのブランチへ出して CI を待つところからやり直す。次の 2 つの場合は、land は部署の窓（部署の会話を映す herdr のペイン）に herdr で頼みを打ち込んで止まる。リベースでぶつかって機械で解けないときは、リベースを頼む。CI が赤なら、失敗の要点を付けて直しを頼む。部署は直してから `--land` を打ち直す。流れは `landing.py`（[land.md](land.md)）。
  - ledger: 受付箱の台帳（会社をまたいで足し合わせた行）から、頼みごとの今の状態と、頼みの木と、続きを組み立てる射影。木の親は次の順で決める: `--forward`（受けた頼みを自分で済ませず、ほかの部署へ回すときに `--ask` に添える旗）で回した元の頼み、頼みの行の `cause` が指す頼み、`cause` の無い古い行では、その頼みを打った場所（部署か本社）がその時刻に受けていてまだ納品していなかった頼み（台帳の行から推定する）。続きは、元の頼みの納品の行のフィールド `holders`（要約の「残った疑問」の各疑問を追う担当者）に頼みの受付番号が書いてあるとき、元の頼みからその受付番号の頼みへ結ぶ線。保存せず、`--todo`（`dispatch/todo.py`。行が指すほかの会社の受付箱もたどる）が開くたびに作り直す。行の種類の一覧 `KINDS` と状態の一覧 `STATES` を持ち、試験の Catalog が、コードの書く行の種類とスキーマ（`schemas/ledger.schema.json`・`schemas/todo.schema.json`）をこの一覧と照合する。行の形と決めた事は [受付箱の台帳の形](ledger.md)。
  - remind: 台帳のリマインダー（`--remind` で立て、`--remind-done` で閉じる、後で見ることの記録）の射影と、見る時（見る日か、待つ頼みの閉じの、先に来た方）が来たかの判じ。流れは `dispatch/reminds.py`（立てる・閉じる・`--due` の中で、担当者〔`--remind` を打った部署か窓口の会話〕の待ち受け〔下の「受付」の項の、知らせの待ち受け〕へ 1 度だけ知らせる）。形と決めた事は [受付箱の台帳の形](ledger.md) の「リマインダー」。
  - bump: Claude Code のプラグインの marketplace で、中身を変えたのに版が据え置きのプラグインの版を上げる commit を作る（`docs/releasing.md` の形。会社の形の `[land]` に `bump = "marketplace"` を書いた会社でだけ、`--land` がメインブランチに入れる前に呼ぶ）。
- 部署の属性（役・アカウント・会話の名前と id・頼み元〔部署を立てた会話〕）は、部署の worktree ごとの git の設定 `company.<名前>`（`extensions.worktreeConfig`）に置く。正本は git で、dispatch は別の台帳を持たない（会社の形の設計 4.2）。読み書きは `gitx.py` の `worktree_attrs`・`enable_worktree_config`・`set_worktree_attr`。
- 外への口は 1 つのツールに 1 ファイル。herdr（`herdr.py`）、git（`gitx.py`）、gh（GitHub の CLI。`ghx.py`）、Claude Code（`claudex.py`）、tiers（`tierx.py`。同じリポジトリの tiers プラグインの点検のコマンドを呼び、このプラグインが要る外のツール〔gh・herdr・アカウントの起動コマンド〕がそろっているかの結果の JSON を読む）、VS Code（`vscode.py`。送り終えた PR の /catchup のページを VS Code のウィンドウにタブで開く）の 6 つ。
  - 場所（git worktree）を作る・並べる・開く・消すのは herdr の worktree の口で、`herdr.py` の `worktrees`・`create_worktree`・`open_worktree`・`remove_worktree` だけが呼ぶ（herdr アダプタ）。ノードは「ブランチの場所」の言葉だけで書く。置き場は herdr の設定の `worktrees.directory`（既定 `~/.herdr/worktrees/<リポジトリ>/<ブランチの slug>`）に任せる。
  - worktree はブランチと stash を代表の clone と共有するので、手元の作業の判定（`gitx.unpushed`・`gitx.stashed`）は、その場所の HEAD とそのブランチの物だけを数える。
- 外のツールの口（設計は [外のツールの口の設計](specs/2026-10-19-ports-design.md)）。移り変わりの激しい 2 つのツールは、目的で名付けた口を通して使う。ツールを替えるときは、同じ名前の関数と値を持つアダプタを書いて `ports.py` の import を替え、口の外は直さない。
  - 端末の口 `term`（作業場・ペイン・ブランチの場所を作る・並べる・読む・打ち込む）。今のアダプタは `herdr.py`。
  - 会話の口 `chat`（会話を起動する・並べる・止める・消す、会話を空にするコマンドなどの打ち込み・環境変数・フックの入出力・画面の入力フィールドの読み方）。今のアダプタは `claudex.py`。
  - 口の外は `from ports import chat, term` で取り、使う人に見せる文はツールの名前を口の `NAME` で差し込む（`{term.NAME}`）。口の誤りの型は `term.Error`・`chat.Error`。
  - チェック D9（`dispatch/tests/fences.py` の `d9_tools_behind_ports`）が、口の外のファイルの名前と文字列の定数（docstring は除く）から、ツールの名前・コマンド・環境変数・フックのフィールドの名前を数える。まだ口へ移していない所はファイルごとの数 `D9_KNOWN` に載せ、数が増えても、減ったのに直していなくても誤りにする。数え方は `python3 dispatch/tests/fences.py --lockin [ファイル…]`。
- 流れの外に、任意のツールが 2 つある。どちらも dispatch の設定のアカウントを読む。
  - `limits.py`: 使用率の控えを作って読む。控えが古いアカウントにだけ API を問い合わせ（probe）、statusline の値を取り込み（record）、herdr のタブバーに 1 行ずつ出す（show）。アカウントごとのプラン（plan）も出す。プランは Claude Code がログインのときに書く記録（そのアカウントの Claude Code の設定のフォルダ〔`config_dir`〕の `.claude.json` の `oauthAccount`）から読む。setup-token（`claude setup-token` で作る長く使える鍵。ブラウザのログインを通らない）だけで入るアカウントはこの記録を持たず、setup-token の鍵はプランを返す口（`/api/oauth/profile`。権限 `user:profile` が要る）に断られ、使用率の応答ヘッダにもプランは出ないので、そのアカウントは「分からない」と理由とログインの手を出す。ただし、dispatch の設定のそのアカウントに `plan`（使う人が設定に書いて教えたプラン）が書いてあれば、記録が読めないときだけそれを出し、`limits.py plan --json` の `source` を `told`（記録から引いた値は `record`）にして分ける。後で記録が読めて `plan` と違えば、行にそう書く。取り直しの規則は、持ち主（このプラグインの作者）が先に作った `limits.sh` と `statusline.sh` から写した。herdr がタブバーのコマンドを打ち切る秒は、herdr の設定の値で、コードの外の雛形 `templates/herdr-tab-bar.toml` に置く。dispatch のコードには期限を足さない（D5）。
    - herdr のタブバーから呼ぶ道（show と probe）は、設定の TOML を読まず、`herdr-config` が書くアカウントの写し（`<limits_dir>/accounts.json`）を読む。herdr がタブバーのコマンドに渡す PATH は、ログインのシェルの PATH と違い、macOS では OS に付いてくる Python 3.9 が `python3` になった（2026-10-15 に実物で確かめた）。TOML を読む `tomllib` は 3.11 からなので、そのままでは起動できない。
    - 行には、マシンごとに違う Python の絶対パスを書かない。ほかのプラグインのフックと同じく、PATH の `python3` か `python` を使う。その代わり、タブバーから呼ぶファイル（`limits.py` と `vendor/claude_auth.py`）は 3.9 の文法で書き、試験（`test_tab_bar_path_reads_as_python_3_9`）が縛る。
  - `activity.py`: Claude Code のフックから、herdr のサイドバーの印 `$act` に作業内容を送る。送る先のペインは `windows.talk_window`（下の「古い版のプラグインで動いている会話の入れ替え」の項と同じ決め方）で引き、会話の id ごとに控える。
- 部署（`--task`）の流れは `dispatch.py` の `_task` だけが持ち、場所・アカウント・起動する・属性は上のノードを使い回す。部署の会話は Claude Code の裏の会話（`claude --bg`）で、置き場とブランチを dispatch（herdr 経由）が決めるために、先に herdr に作らせた worktree の中で、`worktree.bgIsolation = "none"` を渡して起動する（Claude Code に worktree を作らせない。WorktreeCreate のフックでも置き場とブランチは決められたが、フックはその会話の中の全部の worktree を置き換え、フックの作った worktree は `claude rm` が消さずに断る。2026-10-16 に試した）。部署の片付け（`--clean`）は、会話が終わりブランチがメインブランチに入った部署を `claude rm`（`claudex.remove_session`）と herdr の worktree の口で消す。連絡の道（同じアカウントなら SendMessage〔Claude Code の、名前を宛先にほかの会話へ文を送るツール。同じアカウントの会話にしか届かない〕、違えば窓口が herdr で部署のペインに打ち込み、画面を読む）は、呼んだ会話を `claude agents --json` の一覧から `CLAUDE_CODE_SESSION_ID` で探して決める（`claudex.caller`。Claude Code の文書は、この環境変数を Bash のツールの子に渡し、外のツールと会話を結ぶのに使うと書く）。一覧はアカウントの設定のフォルダごとなので、その識別子が載る一覧のアカウントが呼んだ会話のアカウントである。
- 役の本文は、プラグインの SessionStart のフック（`hooks/hooks.json` → `dispatch/role_hook.py`）が、起動した場所の属性 `company.role` を読んで会話の指示に足す（additionalContext）。部署の属性 `company.gh-user`（立てるときに、dispatch の設定の `[[repos]]` の `gh_user`、無ければ会社の形の `gh_user` を書く。違えば dispatch の設定が勝つ）が有れば、同じフックが Claude Code の `CLAUDE_ENV_FILE` に `export GH_TOKEN="$(gh auth token --user <名前> || echo gh-user-not-logged-in)"` の 1 行を足す（ログインしていないアカウントなら、使えない字を入れて gh を認証の誤りで止め、ほかのアカウントに落とさない）。hooks の文書は、このファイルを Bash のツールのコマンドごとにシェルのコードとして先に走らせると書く（"Each Bash command runs the file's contents as shell code before the command itself"）。そのため鍵の値はどこにも書かれない。起動するコマンドの前に `GH_TOKEN=…` を置く形は、裏の会話に届かなかった（[observed.md](observed.md) の試し）。要確認: `CLAUDE_ENV_FILE` の 1 行で、裏の会話の gh が名指しのアカウントで動くかは、実際に部署を起動してはまだ確かめていない（[observed.md](observed.md) の試しで確かめたのは、前に置く形が届かないことと、フックの文が会話の頭に入ることだけ）。
- 依頼と納品（`--ask`・`--deliver`）の流れは `dispatch/orders.py` が持つ（`dispatch.py` の流れの続き。ほかの部署と同時に直すため、ぶつからないよう別のファイルにした）。部署が無ければ `_task` で立てる。プラグインの Stop フック（`hooks/hooks.json`）が `orders.py stop` を呼び、部署の会話が受けた頼みを納品せずに止まるのを、上限付きで差し戻す。
- 受付（[受付の設計](specs/2026-10-17-reception-design.md)）: 知らせの待ち受けは `dispatch/wake_hook.py`（プラグインのフックの Stop・SessionStart〔`asyncRewake`〕と UserPromptSubmit〔印を外す `--resume` と、裏で待ち受けを止める `--pause`〕）、印・読んだ所・順番待ちは `nodes/wake.py`。`--ask` は待ち受けの居る部署に頼みを順番待ちに積み（`orders.queue_ask`）、`--deliver` は頼み元の待ち受けが居れば台帳に知らせの 1 行を足す。機械窓口（役ごとに会社の形に書く、AI を起動せずに機械で答えるツール。受付の設計の 5 章）の `--call` と `--land` の合図（`[[land.after]]`）の流れは `dispatch/calls.py`、ツールへの入力の確かめと、ツールが片づかなかった（0 以外で終わった）ときに AI の部署へ回す頼みの文面（`miss_text`）は `nodes/tools.py`、ツールのフィールドを読むのは `nodes/role.py`。`calls.py` は会社の形に書かれたツールのコマンドを回すので、subprocess を使ってよい所に入れた（チェック D4）。
- 区切りの印（`--rest`。`orders.rest_here`）は属性 `company.rest`（`nodes/wake.py` の `REST`）。ターンの終わり（Claude Code が応答を終えた時。Stop のフック）の待ち受け（`wake_hook.checker`）が `clear_now` で窓に `/clear` を打って外し（打ち先は `wake_hook.talk_window` が選ぶ。部署の場所で開いているペインを並べ、そのうち前で動いているプロセスが、この会話の Claude Code の処理〔処理の番号が同じ〕か、この会話の job〔属性 `company.job`〕へ `claude attach` した claude であるペインを数え、ちょうど 1 つのときだけそのペインに打つ。herdr の会話の印は古いまま残ることがあるので見ず、確かめられなければ打たずに残す）、人の文のターンの始まり（人が文を送った時。UserPromptSubmit のフック。`wake_hook.resume_from_wait`）でも外す。空にできないまま次の頼みか納品を渡すときは、`clear_now` が返す空にできなかった訳を、会話に渡す文の頭に添え、受付箱の台帳の `handed` の行にフィールド `unrested` で書く（区切りの印は残し、次のターンの終わりにまた試す）。
- 終わりの印（`--done`。`orders.finish_here`）は属性 `company.finished`（`nodes/wake.py` の `FINISHED`）。ターンの終わりの待ち受け（`wake_hook.checker`）は、この印を、毎回クリアする部署（役が `fresh = true`）の納品の後に待ち受けが窓へ打つ `/clear` より先に見る（先に空にすると、印を打った会話が居なくなり、畳むターンが来ない）。印が有り、未納品の頼みも順番待ちの頼みも無く、裏の処理も残っていなければ、待ち受けは `retire_later` で印を外し、`dispatch.py --retire` を、終わるのを待たずに起動する（`--retire` は会話を止めるので、会話の子として待たない。起動は `subprocess.Popen` に `start_new_session` を付けるだけで、`limit_hook.py` が `--move` に使う、親を init に替える殻〔`nodes/wake.py` の `detached`〕は通さない。そのため `wake_hook.py` を、subprocess を import してよいファイルの一覧〔`dispatch/tests/fences.py` の `SUBPROCESS_OK`。下の「チェック D1〜D8」の D4〕に足した）。`--retire` の流れは `dispatch/retire.py`（部署を `deliver.find_target` で引き、`dispatch._department_rows` に `assume_stopped` を渡して止めた後の見立てを先に確かめ、`launch.to_shell`・`claude stop`・`clean.retire` の順）。`--retire` が部署を片付けずに残したときと、待ち受けが `--retire` を起動できなかったときは、その訳を属性 `company.retire-kept`（`nodes/wake.py` の `RETIRE_KEPT`）に書き、`--clean` の一覧（`dispatch._running_note`）が読む（次の `--done` が消す）。終わりの印は、人の文のターンの始まり（`wake_hook.resume_from_wait`）でも外す。
- 毎回クリアする部署（役が `fresh = true`）の起動し直しは、待ち受け（`wake_hook.checker`）が順番待ちの頼みを渡す前に `restart_due` で決める。会社の形の今の model・effort（`role_hook.launch_key`。中身は `role.launch_key` が作る、model・effort〔と役の `[roles.settings]`〕を並べた JSON の文字列。effort の `inherit` は解かない）が、部署を起動したときの値（属性 `company.launched`〔`nodes/wake.py` の `LAUNCHED`〕。`_task` が書く）とも、前に起動し直さなかった値（`company.restart-kept`〔`RESTART_KEPT`〕）とも違えば、`restart_first` が印 `company.restarting`〔`RESTARTING`〕を付けてから `dispatch.py --move <会社/部署> --if-changed` を会話から切り離して起動し、終わるまで待つ（待つ間も印の更新の時刻を進める）。`--if-changed` の流れは `dispatch/move.py` の `_restart`（origin の既定のブランチを取り直して読み直し、同じアカウントを先に選んで `--move` と同じ道で起動し直す）。前の会話を止めたら `_move_dept` が印を外すので、待ち受けは印が残っていれば止められなかったと見て、印を外して今の値を `company.restart-kept` に残し、頼みを前の会話に渡す。`/clear` は起動したときの `--model`・`--effort` を残し、会話の中の `/model` はアカウントの新しい会話の既定を替えるので、起動し直す形にした。
- 永続の部署（属性 `company.lifecycle` が `persistent` の部署。頼みを終えても畳まず、同じ作業場〔git worktree〕で次の頼みを受ける）の作業場をメインブランチに追いつかせるのは `wake_hook.follow_main`。ターンの終わりの待ち受け（`wake_hook.checker`）が、受付箱の順番待ちに置かれた次の頼みをこの部署の会話に渡す前に呼ぶ。本社の窓口（代表の clone で持ち主と話す会話）の席に当たる場所（`provision.desk_seat`。代表の clone か、`--desk` が書く属性 `company.pid` を持つ場所）では何もしない。git の操作は `nodes/provision.py` の `follow_main`（origin の既定のブランチを取り直し、`gitx.fast_forward_to` で fast-forward だけする）。作業場のブランチにメインブランチに無い commit が在る（書きかけの作業）ときは、結果の状態 `local_only` を返して動かさない。fast-forward で中身の替わったファイルのうち、`provision.read_at_start` に当たる物（会話が起動するときにしか読まない物）が在れば、この部署の会話が今使っているアカウント（属性 `company.account`）を、`--move` の移す先の名指し（属性 `company.move-to`）に書く。`restart_due` は、会社の形の値が替わっていなくても、`early_due`（区切りでほかのアカウントへ早めに移すかを決める関数）が真なら起動し直すと決め、`early_due` は `company.move-to` が在れば真を返す。そのため上の `restart_first` から `--move --if-changed` が走り、同じアカウントのまま起動し直してから頼みを渡す（毎回クリアする部署。会話を引き継ぐ部署は次の区切り〔`--rest`〕で起動し直す）。進めた・進めなかった理由は、会話に渡す文の頭に添え、受付箱の台帳（`.git/company/inbox/log.jsonl`）の `handed` の行のフィールド `followed` に残す。
- 部署の作業場の並び（仕事の流れの順）は `nodes/sync.py` の `flow_order`（作業場の並びと属性と会社の形の受け持ちから、`workspace.move` に渡す動かし方を出す。会社の部署の作業場が herdr の並びで占める位置の中だけで入れ替える）と `apply_order`。herdr に当てる口は `herdr.py` の `move_workspace` で、CLI にコマンドが無いので、ソケットの API に 1 行の JSON で頼む `_request` を通す（`workspace.move` の `insert_index` は動かす前の並びで数え、その位置の作業場の前に入る。2026-10-17 に herdr 0.9.3 で確かめた）。`--sync`（`dispatch.sync_companies`。会社の並びの部署の属性を `_flow_inputs` で渡す）と、`_task` が部署を立てた後（`_order_company`。その会社の分だけ）に呼ぶ。
- 起動し直しの決め方（起動し直しの振る舞いを直す人が、どの関数を直すかを引く項）。会話を引き継ぐ部署（頼みのたびには空にしない部署）と本社の窓口（代表の clone で持ち主と話し、頼みを部署に配る会話。`--desk` で名付ける。部署の窓〔部署の会話を映す herdr のペイン〕とは別の物）は、会社の形の model・effort・設定が替わっても、区切りでだけ起動し直す。
  - いつ決めるか: 区切りの印（会話が `--rest` を打って属性 `company.rest` に書く、ここで会話を空にしてよいという印）が付いたターンの終わりに、待ち受け（`wake_hook.checker`。ターンの終わりに動くフック）が `restart_due(..., at_rest=True)` で決める。順番待ちの頼みの有る無しも、役の `fresh = true`〔頼みごとに会話を空にする役の設定〕の有る無しも、この決めには効かない。
  - 決めた後: 起動し直すなら `/clear` を打たない。起動し直さないなら、区切りのいつもの動きどおり `clear_now` で窓に `/clear` を打って空にする。
  - 区切りの印の外れ方: 持ち主がその会話に文を打つと、UserPromptSubmit のフック（`resume_from_wait`）が印を外す。`move.py` の `_restart` は、毎回クリアする部署でなければ、この印が付いていることを要る。だから持ち主と話している途中の会話は起動し直さない。
  - 窓口の起動し直し（`move.py` の `_move_desk`）: 窓口の会話がターンの途中（herdr の状態が working〔応答中〕・blocked〔許可待ちなど〕）でなく、入力フィールドが空（`claudex.typed`。`herdr pane read --ansi` の薄字〔SGR 2〕は Claude Code の次の文の候補なので数えない）のときだけ、`/exit` を打つ。打たなければ終了の値 `NOT_NOW`（75。今はしない、の意味）で終わる。そのとき `wake_hook.restart_first` は属性 `company.restart-kept`（起動し直さずに残した今の設定の値。同じ値では試し直さない控え）を書かないので、次の区切りでまた試す。
