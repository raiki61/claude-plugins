# 会話を縮める・始め直す・何もしないの計画

2026-10-25、my_notes（持ち主の、このリポジトリとは別のノートのリポジトリ。works-dispatch の会社の 1 つ）の受付 20261024-215953-c916e9（部署への頼みや問いを受けた記録。番号で引く。置き場は受付箱で、2.1 の台帳に 1 行ずつ残る）を受けて、部署「仕組み」が書いた計画。Claude Code の会話が長くなった時に、会話を要約で縮める（compact）・空にして始め直す・何もしない（そのまま続ける）のどれを選ぶかを、費用で決める設計が頼みの中身。同じ日に、持ち主が前の版を「直して出し直す」と答え（受付 20261024-233437-0143c0）、この版に書き直した。急ぎではない（今の仕組みは動いていて、壊れてはいない。直すと、余分に払っている読みの費用と、空振りの問いの費用が減る）。

前の版からの替わり方は次のとおり。前の版は、機械が要求のたびに損得を計算し、得になったら会話に問う形だった。この版は、縮める・始め直すを最初から会話の選択肢として役の本文に書き、区切りは会話が決め、元が取れるかだけを機械が決める形にした。持ち主の言葉は「部署が自分自身でnewやcompactの選択肢が見えてる状態で勝手にやってくれるのは今まで機能してた」「compactも最初から選択肢として見せておく程度で、keepaliveぐらいで、簡素にシグナル送るがいいか？」「結構最初から軽く見えてるのが勝つ可能性がある気がする」。前の版の全文は https://github.com/raiki61/claude-plugins/blob/c2b90844/works-dispatch/docs/specs/2026-10-25-compact-restart-plan.md に在る。

読み手は 2 人いる。1 人は、この計画を採るかを決める持ち主で、返してほしいのは、採るか・直すかの判断。司令塔（my_notes の、持ち主と話して部署に頼みを振り分ける会話。0 の言葉）を `/clear` で始め直す手（5.4。前の版で聞いた、席外しが長い時に司令塔を `--rest` で始め直す手を足すか、という問い）は、前の版への問いのまま答えを待っていて、この版でも選択肢として残す。もう 1 人は、採った後に実装する works-dispatch と rent-or-buy の作り手で、返す物は無く、実装の頼みを受けた時に 3〜8 を読む。works-dispatch は、Claude Code の会話を部署として立て、頼みと納品をやり取りさせるプラグイン。rent-or-buy は、少しずつ払い続ける（rent）か、まとめて 1 回払う（buy）かを、費用の式から答えるプラグイン。

作るのは計画だけで、コードは直していない。実装は、持ち主がこの計画を見た後に別の頼みで出す。

## 0. 言葉

- **縮める（compact）**: Claude Code の `/compact`。会話を要約に置き換えて、文脈（毎回の要求でモデルに送るトークン）を小さくする。
- **始め直す**: 会話を空にして、新しい会話で続ける。部署では `/clear` と起動し直しがこれに当たる。続きに要る物は、ファイル（納品の要約・共通メモ）から読み直す。
- **キャッシュ**: Claude の API の prompt caching。前の要求と頭が同じ文脈は、読みの単価で済む（書き込みの単価の 1/25〜1/40）。寿命を過ぎると消え、次の要求は文脈の全部を書き込み直す。
- **寿命**: キャッシュの寿命は 5 分か 1 時間。Claude Code は、サブスクリプションの枠の中なら会話の本体（会話そのものの要求）に 1 時間を付け、枠を超えて従量の課金になると 5 分に下げる。会話の本体以外の要求（要約など）は、5 分で送る（[Claude Code の prompt caching の文書](https://code.claude.com/docs/en/prompt-caching#which-ttl-each-request-gets)）。
- **窓・窓口**: 窓は、部署の会話を開いている画面の枠で、待ち受けはここの入力フィールドに文を打ち込む。窓口は、本社で持ち主と話して部署に仕事を配る会話（my_notes では司令塔が兼ねる）。
- **口**: compact が打たれるきっかけの道。印・keepalive の時刻の問い・強制の線などがある（4.1）。
- **役・役の本文**: 役は部署の会話の種類（担当・相談・作業など）。役の本文は、会社の形（`.claude/company.toml`）に役ごとに書き、会話の始まりに足される指示の文。
- **待ち受け**: 部署と司令塔の会話ごとに裏で動く works-dispatch のフック（`dispatch/wake_hook.py`）。ターンの終わりに動き、キャッシュの寿命の前に短い文（keepalive）を送ってキャッシュを保ち、compact するかを rent-or-buy に聞く。keepalive は最後の要求から寿命の 1 分前に送る（1 時間なら約 59 分後、5 分なら約 4 分後）。
- **印（`--compact [焦点]`）**: 会話が「ここは区切りなので compact してよい」と自分で打つ works-dispatch のコマンド。焦点は、要約で残す話題。待ち受けがターンの終わりに `/compact <焦点>` を打ち、compact の後に「compact した。続ける」の 1 行で会話を起動する。
- **問い（consult）**: 待ち受けが会話に送る「compact するなら焦点を 1 行で書け、今は困るなら `skip:` と訳を書け」という文。答えた焦点で `/compact <焦点>` を打つ。
- **強制の線**: 役の起動の設定の `autoCompactWindow`（Claude Code が自動で compact する文脈の大きさ）の 8 割。待ち受けは、ここに着いた会話を問わずに compact する。
- **司令塔**: my_notes の会社の、持ち主と話して部署に頼みを振り分ける会話（役「相談」）。頼みで区切れない、長く続く会話。
- **止まる前のフック**: 会話が止まる時に動く works-dispatch の Stop フック。未納品の頼みが在れば、納品するよう促す。`--wait`（頼みを人の答え待ちと印す）か印が在る時は促さない。

## 1. 結論

1. **選択肢は最初から会話に見せる**: 役の本文に、縮める（印）と始め直す（納品の後の `/clear`・`--done`）を書いておき、いつ縮めるかは会話が決める。my_notes の役の本文には入っている（担当・作業は 2026-10-20、相談〔司令塔〕は 2026-10-23 から）。claude-plugins の担当と作業の本文には無いので、同じ段落を足す（5.1・6 の足す 3）。
2. **元が取れるかは機械が決める**: 印を打った時に、待ち受けと同じ損得の判断をして、元が取れなければ印を付けずに、コマンドの出力で「まだ取れないので続けて」と返す（4.2）。今は印を付けてターンを終えさせ、ターンの終わりに判断し、取れなければ会話をもう 1 ターン起動している。ターンを終える応答の要求が 1 本余分に掛かり、その要求は文脈の全部を読むので、空振りのたびに払っている。
3. **損得の式を、測った値で直す**（3、前の版のまま）。今の式は compact の費用を 2 分の 1 以下に見ていて、会話の記録で試すと文脈の約 8 万トークンで「得」と言う。直すと約 13 万になる（要約の出力を 5,000 トークンと置いて数えた値。今の既定の 9,000 では 13.3〜14.2 万。3.2 の 3）。
4. **機械から送る合図は keepalive の時刻の問いと強制の線だけにする**（4.3）。ターンの終わりに問う文（works-dispatch 0.126.0 で足した物）は外す。前の版の「要求のたびに判断し、今のターンに添える」口も作らない。ターンの途中は、どの口でも compact を打てない（打てるのはターンの終わりだけ）ので、ターンの途中に合図を送っても、会話が区切りでターンを終えるのを待つことに変わりはない。
5. **終わり際の compact は、会話が自分の終わりを知っていることで減らす**: 役の本文に「納品まで、要求でおよそ 30 本（6〜9 ターン）より近い見込みなら打たない」「納品の後は打たない」と書く。30 本は、compact の元が取れるまでに要る残りの要求の数（4.2）から置いた。機械は先の要求の数を知らないので、終わり際かどうかは判断しない（5.3）。keepalive の時刻の問いに会話が「もうすぐ終わる」と答えた時は、延期の上限に数えない（4.2）。
6. **頼みを閉じた部署は、今どおり始め直す**（5.3）。
7. **「最初から見せる」形と「合図が来たら問う」形のどちらが安いかは、まだ測っていない**。入れた後に、比べる値と時期を決めて測る（8）。
8. **5.5（キャッシュが切れる前の compact）は、頼みの外から部署が足した物**で、keepalive の時刻の口の延長に収まるが、仕組みが 1 つ増える。外して 1〜7 だけを採ることもできる。

## 3. compact の損得の式を、項ごとに見直す

### 3.1 正しい式

記号は my_notes の `notes/knowledge/llm-agent-workflow-cost-design-guide.md`（以下、指南。3.5 は払った累計で打ち時を決める規則、4 は仕事がもうすぐ終わる時に打つと損をする話）の 3.5 と同じ意味で使う。

- `C`: 今の文脈。`C'`: compact の後の文脈。そのうち最初の要求で書き込む分が `C'_w`、キャッシュから読む分（システムの指示など）が `C'_r`。
- `o_s`: 要約の出力。`n`: この後に同じ会話で送る要求の数（先は分からない）。
- `p_r`・`p_w'`・`p_o`・`p_in`: 読み・寿命に合う書き込み・出力・キャッシュに無い入力の単価。Opus 5.5 で 100 万トークンあたり $0.20・$8（1 時間）か $5（5 分）・$20・$4。Sonnet 5.5 はどれも半分。比は、書き込みが読みの 40 倍（1 時間）か 25 倍（5 分）、出力が 100 倍、キャッシュに無い入力が 20 倍。

compact を打つと、要約の要求が 1 本増える。この要求は今の文脈 `C` をキャッシュから読み（キャッシュが温かい時。切れていれば `C·p_in`。[文書の「Compacting the conversation」](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation)）、要約 `o_s` を出す。その後の最初の要求が `C'_w` を書き込む。この先の `n` 本で比べると:

```
しない:  n·C·p_r
する:    C·p_r + o_s·p_o + C'_w·p_w' + C'_r·p_r + (n − 1)·C'·p_r
差:      (n − 1)·σ − F'      ここで  σ = (C − C')·p_r,  F' = C'_w·p_w' + C'_r·p_r + o_s·p_o
```

要約の要求は `C'` でなく `C` を読む（compact の前の文脈のため）ので、この 1 本は `σ` の節約を得られない。そのため、得になるのは残りの要求が `F'/σ + 1` 本を超える時である。先の `n` は分からないので、指南 3.5 の C のとおり、払った累計で決める。1 本の要求の rent を `σ`、buy を `F' + σ + Q`（`σ` は上の、要約の要求が得られない節約の分。`Q` は判断の後に払う問いの費用）と置くと、規則「払った累計 + 今の rent ≥ buy」は `S + σ ≥ F' + σ + Q` で、両辺の `σ` が消えて次になる。

```
S ≥ F' + Q       S: 前の compact からの σ の累計、Q: 判断の後に払う問いの費用（4.2）
```

### 3.2 今の式との違い

rent-or-buy 0.3.0 の `compact`（`prompt_cache/translate.py`）は `rent = (C − post)·p_r`、`buy = post·p_w' + summary·p_o + consult_cost`、規則 `S + rent ≥ buy` で、`post` は記録の `postTokens`（2.1 で約 1 万）を使う。項ごとに見ると次のとおり。

1. **要約の要求が `C` を読む分**: 入っていない。規則の `+ rent` が、この 1 本分を「払った」側に数えてしまっている。直すと、規則は `S ≥ F' + Q` になる。キャッシュに当たるかは、Claude Code の文書が「温かい間は前の部分をキャッシュから読む」と書いている（3.1 の出典）。要約の要求は「会話の本体」でなく「それ以外」の寿命（5 分）で送られるが、読むのは会話の本体が書いた前の部分なので、寿命の違いは読みに効かない。待ちでキャッシュが切れた後に compact するのは `C·p_in`（読みの 20 倍）になるので、しない（5.5）。
2. **compact の後の文脈 `C'`**: `postTokens`（約 1 万）は要約の大きさだけで、実際に書き込む量（2.7〜4.5 万）の 4 分の 1 ほど。既定の `after_tokens = 25000` も例の値で、測っていない。直し: 会話ごとに、前の compact の次の要求の書き込みと読みを記録から読んで `C'_w`・`C'_r` にする。役で違う（claude-plugins の部署は 2.7 万、my_notes と司令塔は 4.2〜4.5 万）ので、会話ごとに測った値を使うのが本筋である。rent-or-buy は役を知らないので、記録の読み取りがこの値を出し、その会話にまだ compact が無いうちだけ `prices.toml` の既定（7 日分の全体の中央値、書き込み 4 万・読み 1 万）を使う。役ごとの既定は持たない。
3. **要約の出力 `o_s`**: 既定の 5,000 は例の値だった。2026-10-25 に、実際の要約の本文から見積もった 9,000 に替えた（rent-or-buy 0.3.0 の `prices.toml` の `summary_tokens` は替え済み。ほかの直しは 7 の順で後。my_notes の受付 1cdbb1。見積もり方は rent-or-buy の設計書の 4.2）。要約の要求の使用量は記録に残らないので、出力の量そのものは測れない。会話ごとの値にはしない（次の要約の大きさは前もって分からない。持ち主 2026-10-25）。この計画の 3.2 の表・3.3・4.2・5.5 の数は、替える前の 5,000 で数えた。9,000 で数え直すと、3.3 の直した式の中央値は、claude-plugins の部署で 12.7 万から 13.3 万に、my_notes で 13.5 万から 14.2 万に上がる。
4. **問いの費用 `Q`**: 待ち受けが渡さず 0。直し: keepalive の時刻の問いの費用を、答えが返らない割合で割って渡す（4.2）。印の判断では 0（4.2）。
5. **先の `n` を見ない**: 規則は残りの要求の数を見ない。仕事がもうすぐ終わる時に打つと損をする（指南 4）。この先は手元の計算では分からず、知っているのは会話のモデルなので、役の本文で「納品が近いなら打たない」と書き（5.1）、keepalive の時刻の問いの文で「仕事がもうすぐ終わるなら `skip: <訳>` と書け」と書く。納品の後は判断しない（5.3）。

`F'` を Opus の読みの単価に直して比べる（読み 1 トークン分を 1 と数える。今の式は `C'_r` の項を持たず、直した式は既定の読み 1 万を入れた）。

| | `C'_w` | `o_s` | `F'`（1 時間） | `F'`（5 分） |
|---|---|---|---|---|
| 今の式 | 1 万 | 5 千 | 90 万（$0.18） | 75 万（$0.15） |
| 直した式 | 4 万 | 5 千 | 211 万（$0.42） | 151 万（$0.30） |

### 3.3 どこで「得」と言うか

7 日分の会話の記録の要求を順に流して、規則が最初に `buy` と言う時の文脈を数えた（compact の区切りごとに 1 回。今の式は `C'` を 1 万、直した式は 4 万で数えた）。

| | 今の式 | 直した式（1 時間） |
|---|---|---|
| my_notes の部署（中央値） | 8.5 万 | 13.5 万 |
| claude-plugins の部署（中央値） | 7.6 万 | 12.6 万 |
| 前の compact からの要求の数（中央値） | 17〜20 本 | 40〜48 本 |

文脈の大きさだけで決まる線ではない。文脈が速く育つ会話ほど、大きい所で `buy` になる（`S` は `σ` の累計で、文脈の推移の下の面積にあたり、`C` はその時点の高さのため）。

## 4. 区切りは会話が、損得は機械が決める

### 4.1 口は 3 つに絞る

compact が打たれる道（口）は次の 3 つにする。どれも、打つのはターンの終わりの待ち受けである（フックから compact は起動できない。[Claude Code のフックの文書](https://code.claude.com/docs/en/hooks)）。

1. **印**: 会話が役の本文を読んで、区切りで打つ。主の口。
2. **keepalive の時刻の問い**: 仕事の終わらないまま待っている会話に、keepalive の文の代わりに問いを送る。送るはずの要求と差し替えるので、要求は増えない。会話が印を打ち損ねたまま待ちに入った時の合図。
3. **強制の線**: 問わずに打つ。歯止め。

この外に、Claude Code の自動の compact（`autoCompactWindow`）と席外しの compact（2.2）が、さらに外側の歯止めとして残る。

### 4.2 口ごとの費用と判断

表の記号: `Q_印` は印のコマンドで増える要求の費用、`Q_k` は keepalive の時刻の問いで増える費用、`w_k` はその問いで焦点が返らない割合（どれも下の箇条書きで数える）。

| 口 | 判断の時 | 規則 | 空振りの費用（Opus・1 時間・`C = 13 万`） |
|---|---|---|---|
| 印 | 印のコマンドを打った時 | `S ≥ F'` | 約 14 万（`F'` の 7%。今の形は約 28 万） |
| keepalive の時刻の問い | keepalive の時刻 | `S ≥ F' + Q_k / (1 − w_k)` | 約 3 万（1.5%） |
| 強制の線 | ターンの終わり・keepalive の時刻 | 線に着いたら打つ | 0 |

（数は読み 1 トークン分を 1 と数えた。`F' = 211 万`。）

- **印の費用**: 印のコマンドを出す応答の要求が 1 本増える（打たなければ、その要求で次の仕事に進んでいた）。費用は `Q_印 = C·p_r + o·p_o`（`o` は 100 トークンほど）で、判断より前に払い終わっているので、規則には入れない（`Q = 0`）。
- **印を打った時に判断する**: 印のコマンドが、その場で会話の記録を読み、待ち受けと同じ rent-or-buy の `compact` を呼ぶ。`buy` なら今どおり印を書いて「ターンを終えて」と返す。`buy` でなければ印を書かず、「まだ元が取れない（訳）。印を付けなかったので、このまま続けて、次の区切りで改めて打ってよい」と返す。印からターンの終わりまでに `S` は減らない（要求のたびに増える）ので、ターンの終わりには判断し直さずに打つ。
- **今の形との差**: 元が取れない時、今の形は、印のコマンドの 1 本に加えて、ターンを終える応答の 1 本が余分に掛かる（その後に起動されたターンは、印を打たなくても要った続きの仕事）。新しい形は、コマンドの結果を読んでそのまま続けるので、余分は印のコマンドの 1 本だけになる。空振り 1 回で約 14 万が減り、2.1 の 7 日で 6 回分にあたる。
- **keepalive の時刻の問いの費用**: `Q_k ≈ (300 − 5)·p_o`。増えるのは答えの出力の分だけ（300 は答えの出力、5 は差し替わる keepalive の文の出力。どちらもトークン）。`w_k` は、keepalive の時刻の問いで焦点が返らない割合（`skip:`、書かれない、割り込まれて読めない）で、台帳から役ごとに数える。初めは 0 と置く。今の `DEFER_LIMIT`（2 回延ばされたら焦点なしで打つ）は残すが、問いの文に「仕事がもうすぐ終わるなら `skip: end` と書け」と足し、この答えは延期の数に数えず、その待ちでは問い直さない。数えると、終わり際だと答えた会話を上限で縮めることになり、終わり際を会話に任せる決め（1 の 5）と食い違う。
- **残りの要求の目安**: compact の元が取れるには、残りの要求が `F'/σ + 1` 本より多く要る（3.1）。Opus・1 時間・`C = 13 万`・`C' = 5 万` で約 27 本（要約の出力 9,000 なら約 32 本）、1 ターン 3〜5 本で 6〜9 ターン。役の本文の「およそ 30 本」はここから置いた。文脈が大きいほど `σ` が大きく、要る本数は減る（`C = 20 万` で約 15 本）。
- 要約の要求が末尾に足す指示の文の書き込み（数百トークン、5 分の書き込みの単価）は `F'` の 1% に満たないので、式から外した。
- `Q` を buy に足すと、指南の数値の試しの前提（閾値がちょうど `F'`）から外れる。指南は閾値を `F'` の 1.5〜2 倍にすると最悪の比が 2.2〜2.5 になると示している。keepalive の時刻の問いの `Q` は `F'` の数 % なので、その影響は小さい。

### 4.3 外す口

- **ターンの終わりの問い**（`TURN_CONSULT_TEXT`。works-dispatch 0.126.0）: 外す。単独の要求が 1 本増え、2.1 の 50 分で 12 回のうち 8 回が空振りだった。この問いは、寿命 1 時間の司令塔が持ち主と話している昼の間、keepalive の時刻が来ないので compact の判断が一度も回らない、という困りごと（my_notes の受付 f3f867）のために足した。司令塔の役の本文には印の段落が在り、持ち主との話が一段落した所で司令塔が自分で打つので、この口でそれを受ける。外すと失う物もある。2.1 の 50 分で焦点が返った 4 回は実際に compact に着いた回で、その中には印の打ち損ねを拾った回もありうる。印が受けきれているかは 8 で測る。ターンの終わりの強制の線の判断は残す。
- **前の版の「要求のたびに判断し、今のターンに添える」口**（ツールの結果のたびと、ターンの始まりのフックで判断し、注記を添える）と、ターンの最後の要求で初めて得になった時に今問うか次の口を待つかを比べる手: 作らない。ターンの途中に添えても、打てるのは会話がターンを終えた後で、会話が区切りでターンを終えるのを待つのは印と同じだからである。役の本文が最初から選択肢を見せていれば、注記は会話がもう知っていることを繰り返すだけになる。ツール 1 回ごとのフックの起動の重さ（数十ミリ秒）も要らない。

## 5. 場面ごとの決め方

### 5.1 部署の頼みの途中（働き続けている間・待つ前）

- **区切り**: 会話が決める。役の本文の段落（my_notes の担当・作業・機械的な作業に在る段落に、相談の本文に在る「元が取れるかは機械が計算する」と、終わり際の目安の 2 文を足した物）: 「頼みの途中で、同じ仕事の前の部分（調べ終えた所・直し終えた所など）が済み、続きがあるときは、印を打ってターンを終える。焦点には受付番号と次の手を書く。焦点に書けない長いものは、作業場の git の置き場の compact-next.md に書き、焦点にそのパスを書く。元が取れるかは機械が計算するので、文脈の量を見積もらずに打ってよい。元が取れないと返ったら、そのまま続けて、次の区切りで改めて打つ。納品まで、要求でおよそ 30 本（6〜9 ターン）より近い見込みなら打たない（4.2 の残りの要求の目安）。納品の後は打たない」。
- **足す先**: claude-plugins の担当と作業の本文（`.claude/company.toml`）にはこの段落を足し、my_notes の担当・作業・機械的な作業の本文には足りない 2 文を足す（6 の足す 3）。
- **損得**: 印を打った時に機械が決める（4.2）。
- **歯止め**: 区切りが来ないまま育ち続ける会話は、`autoCompactWindow` の自動の compact が止める。claude-plugins の部署は 20 万、my_notes の部署は 100 万。my_notes の部署で 100 万から下げるかは、8 で測ってから決める（下げると、rent-or-buy の判断より先に Claude Code の自動の compact が打ち時を決めてしまう）。

### 5.2 部署がターンを終えて待つ間（裏の処理・出した頼みの納品・`--wait` で印した人の答え待ち）

- **区切り**: 待ちに入る前に区切りなら、会話が印を打つ（5.1 の段落のとおり）。
- **合図**: keepalive の時刻の問い（4.1 の 2）。寿命 5 分なら約 4 分後に来る。寿命 1 時間なら、知らせや人の答えがたいてい 1 時間より前に着くので、問いより先に次のターンが来て、会話がそのターンで区切りを判断する。
- **歯止め**: 強制の線と、keepalive の時刻の問いで 2 回延ばされた後の焦点なしの compact（どちらも今どおり）。待ち受けが `/compact` を打つ前に窓の入力フィールドが空かを見るのも今どおり。

### 5.3 頼みを閉じた後

- **きっかけ**: 納品（`--deliver`）。
- **決め方**: 始め直す。今の仕組み（`fresh = true` の役は次の頼みの前に `/clear`、エフェメラルの部署は `--done` で畳む）をそのまま使い、機械に足す物は無い。次の頼みが前の続きなら、頼む側（司令塔か窓口）が前の納品のパスを頼みの本文に書く。これは my_notes の役「相談」の本文の決まりで、works-dispatch には足さない。
- **終わり際の compact を減らす**: 2.1 の「最後の compact の後の要求が 3 本以下」の 12 本は、compact の費用を払った直後に会話が終わっている。機械は先の要求の数を知らないので、会話に任せる。役の本文の「納品が近いなら打たない」「納品の後は打たない」がその決まりで、keepalive の時刻の問いの文の「仕事がもうすぐ終わるなら `skip:`」も同じ役をする。効いたかは 8 で測る。
- **式**: 次の頼みの `n` 本を、同じ会話で続けるか、空にして始め直すかで比べる。`B_空` は空にした直後の文脈（システムの指示・指示ファイル・役の本文）、`e` は始め直した会話がファイルから読み直す量。

```
続ける:     n·C·p_r                     （間にキャッシュが切れていれば、C·p_w' + (n − 1)·C·p_r）
始め直す:   (B_空 + e)·p_w' + (n − 1)·(B_空 + e)·p_r
```

  始め直すのが安いのは、`(B_空 + e)·(p_w' − p_r) ≤ n·(C − B_空 − e)·p_r` の時。Opus・1 時間で `B_空 = 2 万`・`e = 5 千`・`C = 15 万` なら、`n ≥ 8` で始め直すほうが安い。頼み 1 つは複数のターンにわたり、1 ターンの要求の数（2.1 の表で中央値 3〜5）の何ターン分かになるので、要求の数はふつう 8 より多く、頼みの間にキャッシュが切れていれば `n` によらず始め直すほうが安い。`B_空` は同じ場所のほかの会話のキャッシュに当たることがあり、その時はもっと安い。

### 5.4 司令塔の会話

- **区切り**: 今どおり、役の本文の段落（受けた頼みを閉じた時と、持ち主との話が一段落した時に、司令塔が自分で印を打つ。持ち主との話が終わりそうなら打たない）。印を打った時に機械が損得を決める（4.2）のは部署と同じ。
- **合図**: keepalive の時刻の問い。寿命 1 時間なので、持ち主と話している昼の間は来ず、席外しの長い夜に来る。昼の取りこぼしを受けるのは印で、ターンの終わりの問いは外す（4.3）。
- **歯止め**: 強制の線（80 万）と、autoCompactWindow の自動の compact（約 967K。1M のモデルで `autoCompactWindow` が 100 万の時に Claude Code が打つ大きさで、Claude Code の文書による。強制の線 80 万より上）。
- **始め直すか（選択肢のまま残す）**: 司令塔を `/clear` で始め直すのは、今は持ち主が手で打つ時だけ（my_notes の役「相談」の本文）。compact を重ねると要約の要約が積もって `C'` が育つ。持ち主の席外しが長い時（keepalive の止め時）に、共通メモと受付箱から続きを読める状態なら、`--rest`（会話を空にしてよいと印すコマンド）で始め直す手がある。持ち主の決めを替えることなので、この計画では足さず、前の版への問い（受付 c916e9 の残った疑問 2）の答えを待つ。足すなら、役の本文に「席外しが長くなる前に、共通メモに続きを書いて `--rest` を打ってよい」と書くだけで、機械に足す物は無い。

### 5.5 キャッシュが切れる見込みの待ちの前

- **きっかけ**: keepalive の止め時（rent-or-buy の keepalive の判断が止めると答えた時か、本数が上限に着いた時）。今も止める周には、止める判定より先に今の規則で compact を判断している（`Warm._tick` が止める判定の前に `Warm._compact` を呼ぶ）が、この後キャッシュが切れることを式に入れていない。今の規則が `buy` と言わなければ、そのまま止めてキャッシュを切らせる。keepalive の時刻の口の延長なので、4.1 の 3 つの口の中に収まる。
- **決め方**: 止める周に 5.5 の式が得と言えば、止める代わりに問いを送り、焦点が返れば compact してから止める。今の流れでは、問いを送った周は keepalive を止めずに次の周へ持ち越す（問いが keepalive の文と差し替わる）ので、5.5 の問いを送った事を控えに書き、答えの後の周は問い直さずに止める。compact の後に会話を起動しない（起動すると、そのターンが `C'` を書き込み、待ちの後にもう一度書き込むことになる）。焦点が返らなければ、問い直さずにそのまま止める（1 つの待ちで問うのは 1 回。問いの要求がキャッシュをもう 1 寿命延ばすので、切れるのはその後）。待ちの後はキャッシュが全部切れているので、最初の要求は compact しなければ `C` を、すれば `C'` の全部（システムの指示を含む）を書き込む。得になる条件は、その差が要約の要求と問いを上回ること。

```
C·(p_w' − p_r) > C'·p_w' + o_s·p_o + Q_止め / (1 − w_止め)        Q_止め = C·p_r + 330·p_w' + 300·p_o
```

  左辺の `− C·p_r` は要約の要求が `C` を読む分、`Q_止め` の中の `C·p_r` は問いの要求が読む分で、別の要求なので両方に入る（`330` は問いの文の書き込み、`300` は答えの出力で、どちらもトークン。2.1 の測った値〔297〜450、中央値 298〕に近い数。keepalive を止める時なので、問いは keepalive と差し替わらず、単独の要求になる）。Opus・1 時間で `C` が約 6.7 万、5 分で約 7.8 万を超えれば得（`C' = 5 万`・`o_s = 5 千`・`w_止め = 0`）。`w_止め` を 0 と置くのは、止め時の部署は待っているだけで、問いが人の文や知らせに割り込まれにくいため。台帳で直す。
- **Claude Code の席外しの compact との関係**: 寿命 1 時間で文脈が 20 万を超えた会話は、待ち受けより先に Claude Code が約 54 分で焦点なしで打つ（2.2）。直した式（3.3）はふつう 13 万前後で得になるので、ここまで育つ会話は少ない。設定は替えない（強制の線と同じ歯止めとして残す）。

## 6. 消す仕組みと足す仕組み

消す仕組み:

1. ターンの終わりの問い（`TURN_CONSULT_TEXT` と、`Warm._turn_end` が問いを送る所と、延期の数の控え `turned`）。ターンの終わりの強制の線の判断は残す。書いた文書（works-dispatch の `skills/dispatch/references/rest.md` の「keepalive の時刻の compact」と `roles.md` の `autoCompactWindow` の項、ルートの `docs/specs/2026-10-24-rent-or-buy-design.md` の 6、rent-or-buy の `docs/design.md` と `docs/design.ja.md` の 7 の compact の 1・2）も替える。
2. 印のターンの終わりの判断（`compact_turn` の中の `compact_worth`）と、元が取れない時に「compact しなかった」の 1 行で会話を起動する所。判断は印のコマンドへ移す（足す 2）。
3. rent-or-buy の `compact` の、規則の `+ rent`（3.2 の 1）と、`postTokens` を compact の後の文脈に使う所（3.2 の 2）。

足す仕組み:

1. rent-or-buy の `compact` の式の直し（3.2）。`C'_w`・`C'_r` を記録の compact の次の要求から読む、規則を `S ≥ F' + Q` にする、`prices.toml` の `[compact]` の既定を測った値と出典に替える。設計書（`docs/design.md` と `docs/design.ja.md`）の 4.6 に、足す項を書いてある。
2. 印のコマンド（`orders.compact_here`）が打たれた時に損得を判断する（4.2）。今の判断（`wake_hook.compact_judge`）はフックの入力（payload）から会話の記録の場所・キャッシュの寿命・強制の線を取っているが、印のコマンドはフックの入力を持たない。判断をフックの外から呼べる形に出し、記録は属性の会話の id（`company.session`）から全アカウントの `~/.claude-p*/projects` を探し、寿命と強制の線は役の起動の設定（`role_hook.cache_ttl_of`・`forced_line` が読む物）から取る。rent-or-buy の `compact` は `Q = 0` で呼ぶ。rent-or-buy が無い時は、今の `compact_worth` と同じく文脈が `COMPACT_FLOOR`（10 万トークン）以上かで決める。記録を読めない時は、今どおり印を書く（ターンの終わりの待ち受けが判断する道を、読めない時のためだけに残すかは、実装の時に決める）。
3. 役の本文（5.1 の段落）。claude-plugins の担当と作業には段落を足す。`.claude/company.toml` は部署「説明書」の受け持ちだが、消す 1 と互いに引き合う（ターンの終わりの問いだけ先に消すと、claude-plugins の部署には keepalive の時刻と強制の線しか残らず、段落だけ先に足すと合図と印が重なる）ので、割って頼まず、7 の 2 を実装する会話が通しで直し、納品に触った受け持ちとして説明書を書く（claude-plugins の担当の役の決まり）。my_notes の担当・作業・機械的な作業には、足りない 2 文（5.1）を足す。別のリポジトリなので、`--ask my_notes` で頼む。こちらは足さなくても食い違いは起きない（終わり際の目安が無いだけ）ので、同じ日でなくてよい。
4. keepalive の時刻の問いの費用 `Q_k / (1 − w_k)` を rent-or-buy に `consult_cost` で渡す（4.2）。単価は rent-or-buy の `prices.toml` を正本にし、works-dispatch に数を写さない。
5. 切れる前の compact（5.5）。rent-or-buy の `compact` に「この後キャッシュが切れる」を表す入力（例 `expiring`）を足し、その時は 5.5 の式で答える。待ち受けは、keepalive の止め時に問いを送り、compact の後に起動しない。
6. keepalive の時刻の問いの文（`CONSULT_TEXT`）に「仕事がもうすぐ終わるなら `skip: end` と書け」を足し、待ち受け（`consult_answer`）がこの答えを延期の数（`deferred`）に数えず、その待ちでは問い直さない（4.2）。
7. 台帳の行（8 で測るため）: 印のコマンドの判断（打った会話・文脈・`S`・`F'`・印を付けたか）、compact を打った口（印・keepalive の時刻の問い・強制の線）、keepalive の時刻の問いの答え（焦点・`skip:`・書かれない・読めない）。

## 8. 入れた後に測る

「最初から見せる」形（印）と「合図が来たら問う」形（ターンの終わりの問い）のどちらが安いかは、まだ測っていない（4.3 でターンの終わりの問いを外すのは、2.1 の空振りの数と持ち主の見立てによる今の決めで、ここで測って見直す）。持ち主の見立ては「結構最初から軽く見えてるのが勝つ可能性がある」。7 の 2 を入れた後に、次のとおり測って比べる。

**比べる期間と会社**:

- 前の期間は、7 の 1（式の直し）を入れてから 7 の 2 を入れるまでの 1 週間。後の期間は、7 の 2 を入れてから 2 週間。どちらも直した式で動くので、差は口の替わり方だけから出る。
- my_notes: 前は印とターンの終わりの問いの両方が在り、後は印と keepalive の時刻の問いだけ。差は「ターンの終わりの合図を外して高くなったか」を表す。
- claude-plugins: 前は役の本文に印が無く、合図だけ。後は印が加わり、ターンの終わりの問いが無くなる。差は 2 つの替わり方（最初から見せることと、ターンの終わりの合図を外すこと）の合計で、片方だけの効き目には分けられない。分けるのは my_notes の差でする。

**比べる値**（会社・役ごと。額は直した式の単価で、要求 100 本あたりに直す）:

1. 遅れの額: 規則が初めて `buy` と言ってから実際に compact されるまでに余分に読んだ額（その間の `σ` の累計）。compact されずに会話が終わった時は、終わりまでの額。会話の記録を規則に流して数える（3.3 と同じ数え方）。印が打たれず、合図も無かった分がここに出る。
2. 空振りの額: 元が取れなかった印の数 × その形の余分（前は 2 本、後は 1 本。4.2）、焦点が返らなかった問いの数 × その口の `Q`。後は台帳の行（6 の足す 7）から数える。前の期間の印は、台帳に判断の行がまだ無いので、2.1 と同じく会話の記録の「compact しなかった」の行から数える。問いは、今の台帳の行（`status` が `asked`・`skipped` など）から数える。
3. 終わり際の額: compact の後の要求が 3 本以下・10 本以下で会話が終わった数と、その compact の `F'` の合計を、compact を打った口ごと（4 と同じ分け方）に出す。役の本文で減らせるのは印の分だけで、自動の compact の分は減らない。2.1 の司令塔の値（191 本のうち 3 本以下 12 本・10 本以下 33 本）が前の目安。
4. 口の内訳: compact を打った口ごとの数。印・keepalive の時刻の問い・ターンの終わりの問い・強制の線は台帳の行で分ける。会話の記録の `trigger` は `auto` と `manual` しか無いので、残りは「Claude Code（自動の compact と席外しの compact の合算。`auto`）」と「人（`manual` から台帳の機械の分を引いた残り）」の 2 つにする。Claude Code の分が多ければ、印も合図も間に合っていない。

**時期と決め方**:

- 7 の 2 を入れて 1 週間で、台帳の行が書かれているか・数えられるかだけを見る（数え方の直しが要るなら、ここで直す）。
- 入れて 2 週間で、1〜3 の合計を前と後で比べる。差が前の額の 10% 以内なら同じと見る。どちらの期間も、compact のあった会話が会社ごとに 30 本に満たなければ、期間を延ばしてから比べる（10% と 30 本は、日ごとの揺れを見ずに置いた目安で、1 週間目の数で見直す）。
- 測るのは claude-plugins の部署「業務改革」（後でしか測れない効き目は業務改革に測る頼みを回す、という claude-plugins の役の決まり）。7 の 2 を実装した会話が、納品の前に `--ask claude-plugins/業務改革` で 2 週間後に測る頼みを出し、その受付を納品の残った疑問の担当者に書く。
- 後のほうが安いか同じなら、今の形のまま。高く、差の大半が寿命 1 時間の会話（司令塔の昼）の遅れの額なら、ターンの終わりの合図をその役にだけ戻すかを、合図の費用（2 の額）と遅れの額の差で決める。my_notes の部署の `autoCompactWindow` を 100 万から下げるかも、ここで 4 の内訳と 1 の額を見て決める。
