# 会話を縮める・始め直す・何もしないの計画

2026-10-25、my_notes の受付 20261024-215953-c916e9（同日の 20261024-220343-53eb94 で設計の頼みに差し替わった）を受けて、部署「仕組み」が書いた計画。Claude Code の会話が長くなった時に、会話を要約で縮める（compact）・空にして始め直す・何もしない（そのまま続ける）のどれを選ぶかを、費用で決める設計が頼みの中身。急ぎではない（今の仕組みは動いていて、壊れてはいない。直すと、余分に払っている読みの費用が減る）。同じ日に頼みへ追加された 4 件（受付 621ffd・5d8f5b・45c0df・b1ed3e。見出しの「足し」はこの追加）を入れてある。

読み手は 2 人いる。1 人は、この計画を採るかを決める持ち主で、返してほしいのは、採るか・直すかの判断と、5.4 の `--rest` を足すかの返事。もう 1 人は、採った後に実装する works-dispatch と rent-or-buy の作り手で、返す物は無く、実装の頼みを受けた時に 3〜7 を読む。どちらでもない読み手は、会話の compact が今どう決まり、これからどう決まるかを知るために読む（求める手は無い）。works-dispatch は、Claude Code の会話を部署として立て、頼みと納品をやり取りさせるプラグイン。rent-or-buy は、少しずつ払い続ける（rent）か、まとめて 1 回払う（buy）かを、費用の式から答えるプラグイン。

作るのは計画だけで、コードは直していない。実装は、持ち主がこの計画を見た後に別の頼みで出す。

## 0. 言葉

- **縮める（compact）**: Claude Code の `/compact`。会話を要約に置き換えて、文脈（毎回の要求でモデルに送るトークン）を小さくする。
- **始め直す**: 会話を空にして、新しい会話で続ける。部署では `/clear` と起動し直しがこれに当たる。続きに要る物は、ファイル（納品の要約・共通メモ）から読み直す。
- **キャッシュ**: Claude の API の prompt caching。前の要求と頭が同じ文脈は、読みの単価で済む（書き込みの単価の 1/25〜1/40）。寿命を過ぎると消え、次の要求は文脈の全部を書き込み直す。
- **寿命**: キャッシュの寿命は 5 分か 1 時間。Claude Code は、サブスクリプションの枠の中なら会話の本体に 1 時間を付け、枠を超えて従量の課金になると 5 分に下げる（[Claude Code の prompt caching の文書](https://code.claude.com/docs/en/prompt-caching#which-ttl-each-request-gets)）。
- **待ち受け**: 部署と司令塔の会話ごとに裏で動く works-dispatch のフック（`dispatch/wake_hook.py`）。ターンの終わりに動き、キャッシュの寿命の前に短い文（keepalive）を送ってキャッシュを保ち、compact するかを rent-or-buy に聞く。keepalive は最後の要求から寿命の 1 分前に送る（1 時間なら約 59 分後、5 分なら約 4 分後）。
- **問い（consult）**: 会話に「compact するなら残す焦点（要約で残す話題）を書け、今は困るなら `skip:` と訳を書け」と伝える文。答えた焦点で `/compact <焦点>` を打つ。
- **口**: 問いを会話に届ける道。単独の要求（問いだけを送る）、添える（どのみち起きる要求に注記を載せる）、添えてターンを早く終える（ターンの途中のツールの結果に添え、モデルがターンを終えて答える。5.1）、keepalive と差し替える、の 4 つがある。
- **役**: 部署の会話の種類（担当・相談・作業など）。会社の形（`.claude/company.toml`）に書く。
- **窓・窓口**: 窓は、部署の会話を開いている画面の枠。待ち受けはここの入力フィールドに文を打ち込む。窓口は、本社で持ち主と話して部署に仕事を配る会話（my_notes では司令塔）。
- **止まる前のフック**: 会話が止まる時に動く works-dispatch の Stop フック。未納品の頼みが在れば、納品するよう促す。`--wait`（頼みを人の答え待ちと印す）か `--compact` の印が在る時は促さない。
- **司令塔**: my_notes の会社の、持ち主と話して部署に頼みを振り分ける会話（役「相談」）。頼みで区切れない、長く続く会話。
- **強制の線**: 役の起動の設定の `autoCompactWindow`（Claude Code が自動で compact する文脈の大きさ）の 8 割。待ち受けは、ここに着いた会話を問わずに compact する。

## 1. 結論

1. compact の損得の式（rent-or-buy の `compact`）を、測った値で直す。今の式は compact の費用を 2 分の 1 以下に見ていて（3）、会話の記録で試すと文脈の約 8 万トークンで「得」と言う。直すと約 13 万になる（持ち主の見立ての「100k ぐらい」は今の式の値に近い）。
2. 問いの費用を、口ごとに、答えが返らない割合を含めて損得に入れる（4）。
3. 損得の計算は、要求のたびにフックが手元でする（ターンの始まりと、ツールの結果のたび）。`buy` になったら、注記を今のターンに添え、モデルはそのターンの最後の行に `compact: <焦点>` を書いて答える。問いのために足す要求は、働き続けている会話がターンを早く終える時の最後の応答の 1 本だけで、次のターンを待つことも無い。部署にも司令塔にも、同じ形で問う（問わずに compact する案は、持ち主の「それがよくないとおもう」で外した）。
4. ターンの最後の要求で初めて `buy` になった時だけ、単独の問いを今送るか、次の口（次のターンか keepalive）を待つかを、同じ式で比べて安い方を採る（4.3）。寿命が 1 時間なら keepalive は約 59 分後なので、持ち主と話している間は来ない。
5. 頼みを閉じた部署は、今どおり始め直す（5.3）。
6. キャッシュが切れる見込みの待ちの前には、問うたうえで、式を満たせば compact してから切らせる（5.5）。

司令塔の見立て（受付 53eb94 の「司令塔の見立て」。頼みの途中の compact は keepalive の時刻と強制の線だけ、ターンの終わりの問いは全部やめる、という案）との違いは 3 つある。

- 頼みの途中の compact を、keepalive の時刻と強制の線だけにしない。ターンの途中にも足す（2.1 の測りで、余分な読みが一番大きいのがそこ）。
- ターンの終わりの問いは、全部はやめない。式で単独の問いが安い時だけ残す。
- compact の費用の式そのものを、測った値で直す。

## 3. compact の損得の式を、項ごとに見直す（足し b1ed3e）

### 3.1 正しい式

記号は my_notes の `notes/knowledge/llm-agent-workflow-cost-design-guide.md`（以下、指南）の 3.5 と同じ意味で使う。

- `C`: 今の文脈。`C'`: compact の後の文脈。そのうち最初の要求で書き込む分が `C'_w`、キャッシュから読む分（システムの指示など）が `C'_r`。
- `o_s`: 要約の出力。`n`: この後に同じ会話で送る要求の数（先は分からない）。
- `p_r`・`p_w'`・`p_o`・`p_in`: 読み・寿命に合う書き込み・出力・キャッシュに無い入力の単価。Opus 5.5 で 100 万トークンあたり $0.20・$8（1 時間）か $5（5 分）・$20・$4。Sonnet 5.5 はどれも半分。比は、書き込みが読みの 40 倍（1 時間）か 25 倍（5 分）、出力が 100 倍、キャッシュに無い入力が 20 倍。

compact を打つと、要約の要求が 1 本増える。この要求は今の文脈 `C` をキャッシュから読み（キャッシュが温かい時。切れていれば `C·p_in`。[文書の「Compacting the conversation」](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation)）、要約 `o_s` を出す。その後の最初の要求が `C'_w` を書き込む。この先の `n` 本で比べると:

```
しない:  n·C·p_r
する:    C·p_r + o_s·p_o + C'_w·p_w' + C'_r·p_r + (n − 1)·C'·p_r
差:      (n − 1)·σ − F'      ここで  σ = (C − C')·p_r,  F' = C'_w·p_w' + C'_r·p_r + o_s·p_o
```

要約の要求が 1 本分の `σ` を食うので、得になるのは残りの要求が `F'/σ + 1` 本を超える時である。先の `n` は分からないので、指南 3.5 の C のとおり、払った累計で決める。1 本の要求の rent を `σ`、buy を `F' + σ`（要約の要求の分を含む）と置くと、規則「払った累計 + 今の rent ≥ buy」は次になる。

```
S ≥ F' + Q       S: 前の compact からの σ の累計、Q: 問いの費用（4）
```

### 3.2 今の式との違い

rent-or-buy 0.2.1 の `compact`（`prompt_cache/translate.py`）は `rent = (C − post)·p_r`、`buy = post·p_w' + summary·p_o + consult_cost`、規則 `S + rent ≥ buy` で、`post` は記録の `postTokens`（2.1 で約 1 万）を使う。項ごとに見ると次のとおり。

1. **要約の要求が `C` を読む分**: 入っていない。規則の `+ rent` が、この 1 本分を「払った」側に数えてしまっている。直すと、規則は `S ≥ F' + Q` になる。キャッシュに当たるかは、Claude Code の文書が「温かい間は前の部分をキャッシュから読む」と書いている（3.1 の出典）。要約の要求は「会話の本体」でなく「それ以外」の寿命（5 分）で送られるが、読むのは会話の本体が書いた前の部分なので、寿命の違いは読みに効かない。待ちでキャッシュが切れた後に compact するのは `C·p_in`（読みの 20 倍）になるので、しない（5.5）。
2. **compact の後の文脈 `C'`**: `postTokens`（約 1 万）は要約の大きさだけで、実際に書き込む量（2.7〜4.5 万）の 4 分の 1 ほど。既定の `after_tokens = 25000` も例の値で、測っていない。直し: 会話ごとに、前の compact の次の要求の書き込みと読みを記録から読んで `C'_w`・`C'_r` にする。役で違う（claude-plugins の部署は 2.7 万、my_notes と司令塔は 4.2〜4.5 万）ので、会話ごとに測った値を使うのが本筋である。rent-or-buy は役を知らないので、記録の読み取りがこの値を出し、その会話にまだ compact が無いうちだけ `prices.toml` の既定（7 日分の全体の中央値、書き込み 4 万・読み 1 万）を使う。役ごとの既定は持たない。
3. **要約の出力 `o_s`**: 既定の 5,000 は例の値。要約の本文は 1 万字前後（英語で約 3 千トークン）で、Claude Code はこれに捨てられる下書きを足して出すが、要約の要求の使用量は記録に残らないので、出力の量は測れていない。5,000（トークン数）を残し、出典を「本文の字数から見積もった値。出力の量は測れない」に替える。
4. **問いの費用 `Q`**: 待ち受けが渡さず 0。直し: 口ごとの費用を、答えが返らない割合で割って渡す（4.1）。
5. **先の `n` を見ない**: 規則は残りの要求の数を見ない。仕事がもうすぐ終わる時に打つと損をする（指南 4）。この先は手元の計算では分からず、知っているのは会話のモデルなので、問いの文に「仕事がもうすぐ終わるなら `skip: <訳>` と書け」と書いて、モデルの答えで外す。納品の後は判断しない（5.3）。

`F'` を Opus の読みの単価に直して比べる（読み 1 トークン分を 1 と数える。今の式は `C'_r` の項を持たず、直した式は既定の読み 1 万を入れた）。

| | `C'_w` | `o_s` | `F'`（1 時間） | `F'`（5 分） |
|---|---|---|---|---|
| 今の式 | 1 万 | 5 千 | 90 万（$0.18） | 75 万（$0.15） |
| 直した式 | 4 万 | 5 千 | 211 万（$0.42） | 151 万（$0.30） |

### 3.3 どこで「得」と言うか

7 日分の会話の記録の要求を順に流して、規則が最初に `buy` と言う時の文脈を数えた（compact の区切りごとに 1 回。今の式は `C'` を 1 万、直した式は 4 万で数えた）。

| | 今の式 | 直した式（1 時間） |
|---|---|---|
| my_notes の部署（中央値） | 8.5 万 | 13.5 万 |
| claude-plugins の部署（中央値） | 7.6 万 | 12.6 万 |
| 前の compact からの要求の数（中央値） | 17〜20 本 | 40〜48 本 |

文脈の大きさだけで決まる線ではない。文脈が速く育つ会話ほど、大きい所で `buy` になる（`S` は `σ` の累計で、文脈の推移の下の面積にあたり、`C` はその時点の高さのため）。

## 4. 問いの費用と口（足し 621ffd・5d8f5b・45c0df）

### 4.1 口ごとの費用

問いの費用は、問うたびに払う分 `Q_毎回` と、焦点が返った時だけ払う分 `Q_答え` に分け、損得には `Q_毎回 / (1 − w) + Q_答え` を入れる。`w` は、その口で問うて焦点が返らない割合（`skip:`、書かれない、割り込まれて読めない）で、台帳から口ごとに数える。焦点が 1 つ返るまでに、問うたびに払う分を平均 `1/(1 − w)` 回払うからである。初めの値は、単独の口だけ 2.1 の測りの 8/12 を使い、ほかの口は 0 から始めて台帳で直す。8/12 は 1 つの部署が 55 秒に 5 回続けた偏りを含むので、台帳で役ごとに直すまでの仮の値である。

Opus・1 時間・`C = 13 万`・`C' = 5 万` での値（読み 1 トークン分を 1 と数える。`F' = 211 万`）:

| 口 | `Q` | `F'` に対する割合 |
|---|---|---|
| 添える | 約 1 万 | 0.5% |
| 添えてターンを早く終える | 約 14 万 | 7% |
| keepalive と差し替える | 約 3 万 | 1.5% |
| 単独の要求 | 約 17 万 | 8%（`w = 8/12` なら 25%） |

- 添える: `Q_添え = g·p_w' + g·p_r·(残りの要求) + o_f·p_o`。`g` は注記（約 100 トークン）で、文脈に残って以降の要求で読まれる（ここまでが問うたびに払う分）。`o_f` は答えの 1 行（返った時だけ払う分）。
- 添えてターンを早く終える: `Q_途中 = C·p_r + Q_添え`。働き続けている会話が compact のためにターンを終えると、最後の応答の要求が 1 本増える（5.1）。この `C·p_r` は焦点が返った時だけ払う分に入れる。
- keepalive と差し替える: `Q_keepalive ≈ (300 − 5)·p_o`。keepalive は送るはずの要求なので、増えるのは答えの出力の分だけ（300 は答えの出力、5 は差し替わる keepalive の文の出力。どちらもトークン）。
- 単独の要求: `Q_単独 = C·p_r + 330·p_w' + 300·p_o`。全部が問うたびに払う分。

要約の要求が末尾に足す指示の文の書き込み（数百トークン、5 分の書き込みの単価）は `F'` の 1% に満たないので、式から外した。

`Q` を buy に足すと、指南の数値の試しの前提（閾値がちょうど `F'`）から外れる。指南は閾値を `F'` の 1.5〜2 倍にすると最悪の比が 2.2〜2.5 になると示している。添える口の `Q` は `F'` の数 % なので、その影響は小さい。

### 4.2 要求のたびに判断し、今のターンに添える

- フックは要求のたびに rent-or-buy の `compact` を手元で呼ぶ。ターンの始まり（UserPromptSubmit。人の文か、待ち受けが窓に打ち込んだ知らせ）と、ツールの結果のたび（PostToolUse）である。どちらのフックの `additionalContext` も、次の要求に載るだけで要求を増やさない（[Claude Code のフックの文書](https://code.claude.com/docs/en/hooks)）。フックが compact を起動する手は無いので、打つのは今どおりターンの終わりの待ち受けである。
- `buy` になったら、注記を添える。損得に入れる問いの費用は、ターンの始まりで判断する時は `Q_添え`（そのターンの自然な終わりに答えるので、ターンを早く終えない）、ツールの結果で判断する時は `Q_途中`。注記は「compact が得になった（文脈 X）。区切りなら、このターンの最後の行に `compact: <焦点>` を書け。途中なら続けて、区切りで書け。仕事がもうすぐ終わるなら `skip: <訳>` と書け」。
- ターンの終わりに、待ち受けが最後の応答の `compact: <焦点>` の行を読み、今の `--compact` の印と同じ道に乗せる（もう一度判断して `/compact <焦点>` を打つ）。行が無ければ打たない。止まる前のフック（0）は、この行の在るターンの終わりに納品を促さない。
- 注記は、前の注記から `S` がもう 1 回分の `F' + Q` だけ育つまで添え直さない。添える口には延期の上限を置かず、行が書かれなくても、`skip:` が返っても、焦点なしでは打たない。行が無いのは区切りが来なかっただけのことがあり、`skip:` は仕事の終わり際のことが多いので、そこで打つと 3.2 の 5 と 5.3 が避けたい終わり際の compact になる。歯止めは強制の線で、my_notes の司令塔と部署では文脈 80 万と遠いので、下げるかを 7 の 5 で測ってから決める。keepalive の口の今の決まり（`skip:` で 2 回延ばされたら焦点なしで打つ）は残す。
- フックの重さ: 会話の記録は数 MB になる。記録のファイルの大きさを前の値と比べ、育った分だけを読む。rent-or-buy を呼ばない回も、ツール 1 回ごとにフックの起動（シェルと Python）で数十ミリ秒かかる。`additionalContext` を返すには同期のフックが要るので、この時間はそのままツールの後の待ちになる。

### 4.3 ターンの最後の要求で初めて `buy` になった時

最後の要求の後にはツールの結果が無いので、注記を添える所が無い。待ち受けがターンの終わりに、2 つの手を同じ式で比べ、安い方を採る。

```
A 単独で今問う:       Q_単独 / (1 − w_単独)
B 次の口を待つ:       P_k · Q_keepalive / (1 − w_k)  +  (1 − P_k) · (k·σ + Q_添え / (1 − w_添え))
```

- `Q_添え / (1 − w_添え)` などは、4.1 の分け方（問うたびに払う分だけを `1 − w` で割る）で数える。
- `P_k`: 次に起きるのが keepalive（ターンの始まりより先）である見込み。`k`: 次のターンで注記を読んでから最後の行を書くまでの要求の数（2.1 の表の 1 ターンの要求の数。3〜5）。その間は `C` を読み続けるので、`k·σ` が待つ費用になる。待つ間に要求が無い時間は払わない。
- B を採ったら、印（受付箱の `wake/<場所の鍵>.compact.json` に `due`。場所の鍵は、部署や司令塔の会話の場所ごとの名前）を書く。次のターンの始まりのフックが印を見て注記を添えるか、keepalive の時刻に問いと差し替える。
- 寿命 5 分: keepalive は約 4 分後に来る。部署が待っている間は `P_k` が高く、B はほぼ `Q_keepalive` で済む。
- 寿命 1 時間: keepalive は約 59 分後で、持ち主と話している間は来ない（`P_k ≈ 0`）。B は `k·σ + Q_添え` になる。例の値（`C = 13 万`・`C' = 5 万`・`k = 4`）で、B は約 33 万、A は `w = 8/12` で約 52 万なので B を採る。`w` が下がって 0.2 なら、A は約 22 万で A を採る。
- `w`・`k`・`P_k` は、台帳に口ごとの結果と、ターンの終わりから次の出来事までの時間を書いて、役と寿命ごとに数える。

## 5. 場面ごとの決め方

### 5.1 部署の頼みの途中・働き続けている間（ターンの途中）

- **きっかけ**: ツールの結果（PostToolUse のフック。ツール 1 回ごとに動く Claude Code のフックで、新しく足す）。
- **決め方**: 4.2 のとおり。`Q` は `Q_途中`。ターンを終えると、最後の応答の要求と、compact の後の「続ける」の要求が起きる。後の方は `F'` の `C'_w` の書き込みに当たるので、増えるのは前の 1 本（`C·p_r`）だけである。注記を読み流されたら、払ったのは `Q_添え` だけ。
- **焦点を最後の行で受ける訳**: `--compact` のコマンドを打たせると、コマンドを打つ要求とターンを終える要求の 2 本が増える。
- **歯止め**: 区切りが来ないまま育ち続ける会話は、今の `autoCompactWindow` の自動の compact が止める。

### 5.2 部署がターンを終えて待つ間（裏の処理・出した頼みの納品・`--wait` で印した人の答え待ち）

- **きっかけ**: ターンの終わり（判断と、4.3 の比べ）、次のターンの始まり（知らせか人の答えが窓に打ち込まれる）、keepalive の時刻。
- **決め方**: 4.2・4.3 のとおり、問うてから打つ。問わずに打つのは、強制の線と、keepalive の口で 2 回延ばされた後の焦点なしの compact だけ（どちらも今どおり）。待ち受けが `/compact` を打つ前に窓の入力フィールドが空かを見るのも今どおり。
- **寿命の違い**: 5 分なら次の口はたいてい keepalive で、問いは keepalive と差し替わる。1 時間なら、知らせはたいてい 1 時間より前に着くので、次のターンの始まりに添える口が主になる。

### 5.3 頼みを閉じた後

- **きっかけ**: 納品（`--deliver`）。
- **決め方**: 始め直す。今の仕組み（`fresh = true` の役は次の頼みの前に `/clear`、エフェメラルの部署は `--done` で畳む）をそのまま使い、足す物は無い。次の頼みが前の続きなら、頼む側（司令塔か窓口）が前の納品のパスを頼みの本文に書く。これは my_notes の役「相談」の本文の決まりで、works-dispatch には足さない。
- **式**: 次の頼みの `n` 本を、同じ会話で続けるか、空にして始め直すかで比べる。`B_空` は空にした直後の文脈（システムの指示・指示ファイル・役の本文）、`e` は始め直した会話がファイルから読み直す量。

```
続ける:     n·C·p_r                     （間にキャッシュが切れていれば、C·p_w' + (n − 1)·C·p_r）
始め直す:   (B_空 + e)·p_w' + (n − 1)·(B_空 + e)·p_r
```

  始め直すのが安いのは、`(B_空 + e)·(p_w' − p_r) ≤ n·(C − B_空 − e)·p_r` の時。Opus・1 時間で `B_空 = 2 万`・`e = 5 千`・`C = 15 万` なら、`n ≥ 8` で始め直すほうが安い。頼み 1 つの要求はふつうこれより多く、頼みの間にキャッシュが切れていれば `n` によらず始め直すほうが安い。`B_空` は同じ場所のほかの会話のキャッシュに当たることがあり、その時はもっと安い。
- **しないこと**: 納品の後は compact を判断しない。指南 4 のとおり、仕事の終わり際の compact は損をする。

### 5.4 司令塔の会話

- **きっかけ・決め方**: 部署と同じ（4.2・4.3）。持ち主の文はターンの始まりなので、寿命 1 時間で持ち主と話している間は、持ち主の文に添える口が主になる。添えた注記には「持ち主との話が一段落なら書け」と書く。
- **今のまま残す物**: 役の本文が決める `--compact` の区切り（受けた頼みを閉じた時や持ち主との話が一段落した時に、司令塔が自分で打つ）、強制の線。
- **始め直すか**: 司令塔を `/clear` で始め直すのは、今は持ち主が手で打つ時だけ（my_notes の役「相談」の本文）。compact を重ねると要約の要約が積もって `C'` が育つ。持ち主の席外しが長い時（keepalive の止め時）に、共通メモと受付箱から続きを読める状態なら、`--rest` で始め直す手がある。持ち主の決めを替えることなので、この計画では足さず、選んでもらう。

### 5.5 キャッシュが切れる見込みの待ちの前

- **きっかけ**: keepalive の止め時（rent-or-buy の keepalive の判断が止めると答えた時か、本数が上限に着いた時）。今は compact を判断せずに止めて、キャッシュを切らせている。
- **決め方**: 止める代わりに単独で問い、焦点が返れば compact してから止める。compact の後に会話を起動しない（起動すると、そのターンが `C'` を書き込み、待ちの後にもう一度書き込むことになる）。焦点が返らなければ、問い直さずにそのまま止める（1 つの待ちで問うのは 1 回。問いの要求がキャッシュをもう 1 寿命延ばすので、切れるのはその後）。待ちの後はキャッシュが全部切れているので、最初の要求は compact しなければ `C` を、すれば `C'` の全部（システムの指示を含む）を書き込む。得になる条件は、その差が要約の要求と問いを上回ること。

```
C·(p_w' − p_r) > C'·p_w' + o_s·p_o + Q_単独 / (1 − w_止め)
```

  左辺の `− C·p_r` は要約の要求が `C` を読む分、`Q_単独` の中の `C·p_r` は問いの要求が読む分で、別の要求なので両方に入る。`Q_単独`（`C·p_r` と、問いの文の書き込みと答えの出力）を入れると、Opus・1 時間で `C` が約 6.7 万、5 分で約 7.8 万を超えれば得（`C' = 5 万`・`o_s = 5 千`・`w_止め = 0`）。`w_止め` を 0 と置くのは、止め時の部署は待っているだけで、問いが人の文や知らせに割り込まれにくいため。台帳で直す。
- **Claude Code の席外しの compact との関係**: 寿命 1 時間で文脈が 20 万を超えた会話は、待ち受けより先に Claude Code が約 54 分で焦点なしで打つ（2.2）。直した式（3.3）はふつう 13 万前後で打つので、ここまで育つ会話は少ない。設定は替えない（強制の線と同じ歯止めとして残す）。
