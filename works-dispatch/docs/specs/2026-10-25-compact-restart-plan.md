# 会話を縮める・始め直す・何もしないの計画

2026-10-25、my_notes の受付 20261024-215953-c916e9（同日の 20261024-220343-53eb94 で設計の頼みに差し替わった）を受けて、部署「仕組み」が書いた計画。

読み手は 2 人いる。1 人は、この計画を採るかを決める持ち主。もう 1 人は、採った後に実装する works-dispatch と rent-or-buy の作り手。works-dispatch は、Claude Code の会話を部署として立て、頼みと納品をやり取りさせるプラグイン。rent-or-buy は、少しずつ払い続ける（rent）か、まとめて 1 回払う（buy）かを、費用の式から答えるプラグイン。

作るのは計画だけで、コードは直していない。実装は、持ち主がこの計画を見た後に別の頼みで出す。

## 0. 言葉

- **縮める（compact）**: Claude Code の `/compact`。会話を要約に置き換えて、文脈（毎回の要求でモデルに送るトークン）を小さくする。
- **始め直す**: 会話を空にして、新しい会話で続ける。部署では `/clear` と起動し直しがこれに当たる。続きに要る物は、ファイル（納品の要約・共通メモ）から読み直す。
- **キャッシュ**: Claude の API の prompt caching。前の要求と頭が同じ文脈は、書き込みの単価の 1/25〜1/40 の読みの単価で済む。寿命（5 分か 1 時間）を過ぎると消え、次の要求は文脈の全部を書き込み直す。
- **待ち受け**: 部署と司令塔の会話ごとに裏で動く works-dispatch のフック（`dispatch/wake_hook.py`）。会話のターンの終わりに動き、キャッシュの寿命の前に短い文（keepalive）を送ってキャッシュを保ち、compact するかを rent-or-buy に聞く。
- **問い（consult）**: 待ち受けが会話に送る「compact するなら残す焦点を 1 行で、今は困るなら `skip:` と訳を返せ」の文。答えた焦点で `/compact <焦点>` を打つ。
- **司令塔**: my_notes の会社の、持ち主と話して部署に頼みを振り分ける会話（役「相談」）。頼みで区切れない、長く続く会話。
- **強制の線**: 役の起動の設定の `autoCompactWindow`（Claude Code が自動で compact する文脈の大きさ）の 8 割。待ち受けは、ここに着いた会話を問わずに compact する。

## 1. 結論

1. ターンの終わりの問い（0.126.0 で足した `TURN_CONSULT_TEXT`）はやめる。問いを単独の要求で送らない。問いが要るときは、どのみち起きる要求（人の文・待ち受けが送る文・keepalive）に添えて送る。
2. 問うのは司令塔（人と話す会話）だけにする。部署には人が打たないので、割り込みを確かめる問いは要らない。待ち受けは、rent-or-buy が `buy` と答えた時に問わずに compact する。
3. 部署が働き続けている間（ターンの途中）の compact を足す。今はここを判断する所が無く、my_notes では余分な読みの約 4 分の 3 がここで出ている（2.1）。ツールの結果に「compact が得になった。区切りで最後の行に焦点を書いてターンを終えよ」の注記を添える。どの時点で得になるかは機械が決め、作業のどこで区切るかはモデルが決める。
4. 頼みを閉じた部署は、今どおり始め直す。毎回クリアする役（`fresh = true`）は次の頼みの前に `/clear`、エフェメラルの部署は `--done` で畳む。続きの頼みは、前の納品のパスを頼みの本文に書いて渡す。頼みを閉じる前後には compact しない。
5. キャッシュが切れる見込みの待ちの前には、文脈が約 4〜6 万トークンを超えていれば compact してから切らせる（3.2）。

司令塔の見立て（受付 53eb94 の「司令塔の見立て」）との違いは 2 つある。1 つめは、頼みの途中の compact を keepalive の時刻と強制の線だけにせず、ターンの途中にも足すこと（2.1 の測りで、そこが一番大きい）。2 つめは、部署では keepalive の時刻にも問わないこと。

## 3. 費用の式

記号は my_notes の `notes/knowledge/llm-agent-workflow-cost-design-guide.md`（以下、指南）の 3.5 の変数表と同じ意味で使う。

- `C`: 今の文脈。`C'`: compact した後の文脈（基本の文脈 + 要約）。`B`: 空にした直後の文脈（システムの指示・ツールの定義・指示ファイル・役の本文）。
- `o_s`: 要約の出力。`n`: この後に同じ会話で送る要求の数（ツールを 1 回呼ぶごとに 1 本。先は分からない）。
- `p_r`・`p_w'`・`p_o`: 読み・寿命に合う書き込み・出力の単価。Opus 5.5 で 100 万トークンあたり $0.20・$8（1 時間）か $5（5 分）・$20。Sonnet 5.5 はどれも半分。
- `F' = C'·p_w' + o_s·p_o`: compact で払う費用（指南 3.5 の C）。`C' = 2.5 万`・`o_s = 5,000` なら、Opus の 1 時間で $0.30、Sonnet の 5 分で $0.11。
- `σ = (C − C')·p_r`: compact しないために 1 本の要求で余分に読む額。`S`: 前の compact（無ければ会話の始め）からの `σ` の累計。

### 3.1 共通の打ち時

指南 3.5 の C の規則のとおり、`S + σ ≥ F' + Q` で compact する。`Q` は compact に要る問いの費用で、問わなければ 0。rent-or-buy の `compact` が今この規則（`spent + rent ≥ buy`）を持ち、`Q` は入力の `consult_cost` で足せる。`n` を見込まない規則で、後から見た最適の 2 倍を超えなかった（指南の数値の試し。証明は無い）。

問いの費用 `Q` は、送り方で桁が変わる。

- 単独の要求で送る（今のターンの終わりの問い）: `Q_単独 = C·p_r + 330·p_w' + 300·p_o`。Opus・1 時間で、`C = 30 万` なら $0.069（`F'` の 23%）。2.1 のとおり 12 回に 8 回が無駄なら、焦点 1 つを得るのに平均 3 回払い、`F'` の 69% になる。
- keepalive と差し替える: `Q_keepalive ≈ (300 − 5)·p_o`。Opus で $0.006。
- どのみち起きる要求に添える（この計画で足す）: `Q_添え ≈ g_n·p_w' + o_f·p_o`。`g_n` は添える注記（約 100 トークン）、`o_f` は答えの 1 行。Opus で $0.002〜0.007。

### 3.2 切れる前の compact

待ちの間にキャッシュが切れる見込みなら、待ちの後の最初の要求が文脈を全部書き込み直す。待ちの前に compact すれば、書き込み直すのは `C'` だけで済む。差は `C·(p_w' − p_r) − F'` で（指南 3.5 の C の「冷える見込みの待ちの前に打つ場合」）、待ちの後の要求が 1 本でも、次を満たせば得になる。

```
C > F' / (p_w' − p_r)
```

`C' = 2.5 万` なら、Opus の 1 時間で約 3.9 万、Sonnet の 5 分で約 4.7 万である。`C' = 5 万` なら、Opus の 1 時間で約 6.4 万になる。

### 3.3 始め直す

頼みを閉じた後に、次の頼みを同じ会話で続けるか、空にして始め直すかを比べる。

```
続ける:     次の頼みの n 本の要求が、どれも C − B だけ余分に読む     (C − B)·p_r·n
            （間にキャッシュが切れていれば、最初の要求で C を書き込み直す分も足す）
始め直す:   要る物 e トークンを読み直す                             e·(p_w' + n·p_r)
```

ファイルから読み直す物は、前の文脈の一部なので `e ≤ C − B`。よって、`n ≥ 1` なら始め直すほうが安い。例: Sonnet・5 分で `C − B = 10 万`・`n = 50` なら、続けると次の頼みで約 $0.50 余分に払う。前の納品の要約（`e` は数千トークン）を読み直す費用は 1 セントに届かない。

指南 4 の「別の仕事に移るなら `/clear` が無料、同じ仕事の前半が済んだら `/compact`」の、頼みの区切りへの当てはめである。続きの頼みでも、前の頼みは閉じていて、続きに要る物は納品の要約にある。

## 4. 場面ごとの決め方

### 4.1 部署の頼みの途中・働き続けている間（ターンの途中）

- **きっかけ**: ツールの結果。待ち受けとは別の、新しく足す PostToolUse のフック（ツールの呼び出しが済むたびに動く Claude Code のフック）が見る。
- **決め方**: フックが rent-or-buy の `compact` に会話の記録を渡して聞く（手元の計算だけで、モデルへの要求は増えない）。このとき `consult_cost` に、下の「費用」の `Q_途中` を渡す。`buy` なら、ツールの結果の隣に注記を添える（Claude Code のフックの `additionalContext`。ツールの結果と同じ次の要求に載る）。注記の中身は「compact が得になった（文脈 X）。今の段が区切りなら、ツールを呼ばずに最後の行に `compact: <焦点>` を書いてターンを終えよ。区切りでなければ続け、次の区切りで書け」。
- **その後**: ターンの終わりに、待ち受けが `compact: <焦点>` の行を読み、今の `--compact` の印と同じ道に乗せる（もう一度判断して `/compact <焦点>` を打ち、「compact した。続ける」で会話を起動する）。
- **費用**: `Q_途中 = C·p_r + Q_添え`。ターンを終える最後の応答の要求が 1 本増え、文脈 `C` を読む（続けていれば、その要求で作業を進めていた）。`--compact` のコマンドを打たせると、コマンドを打つ要求とターンを終える要求の 2 本が増えるので、焦点はコマンドでなく最後の行で受ける。Opus・1 時間・`C = 30 万` で `Q_途中` は約 $0.06（`F'` の 2 割）で、ターンの終わりの単独の問いの 1 回分に近い。違いは、送るのが得になった時の 1 回だけで、割り込まれて答えを読めないことが無い（答えを書くのはモデル自身で、そのターンの中で済む）こと。
- **注記の数**: 同じ compact の周期で 1 回だけ添える。区切りが来ないまま `S` がもう 1 回分の `F'` だけ育ったら、もう 1 回添える。歯止めは今の `autoCompactWindow` の自動の compact のまま置く。
- **フックの重さ**: 会話の記録は数 MB になる。フックは記録のファイルの大きさを前回の値と比べ、一定より育ったときだけ rent-or-buy を呼ぶ（呼ばない回は数ミリ秒で終わる）。

### 4.2 部署がターンを終えて待つ間（裏の処理・出した頼みの納品・`--wait` の人の答え）

- **きっかけ**: ターンの終わりと keepalive の時刻（どちらも今の待ち受けが動く所）。
- **決め方**: rent-or-buy が `buy` と答えたら、問わずに焦点なしで `/compact` を打つ（`Q = 0`）。部署の窓には人が打たないので、割り込みを確かめる問いは要らない。窓の入力フィールドが空で会話が止まっているかを見るのは今どおりで、字が在れば打たない。会話がターンの最後の文に `compact: <焦点>` の行を書いていれば、その焦点で打つ（会話が自分から焦点を残したい時の口。書かなくてよい）。
- **切れる前**: keepalive の止め時（rent-or-buy の keepalive の判断が止めると答えた時か、本数が上限に着いた時）に、3.2 の式を満たせば compact してから止める。今は compact を判断せずに止めて、キャッシュを切らせている。
- **強制の線**: 今どおり、問わずに打つ。

### 4.3 頼みを閉じた後

- **きっかけ**: 納品（`--deliver`）。
- **決め方**: 始め直す（3.3）。今の仕組み（`fresh = true` の役は次の頼みの前に `/clear`、エフェメラルの部署は `--done` で畳む）をそのまま使い、足す物は無い。次の頼みが前の続きなら、頼む側（司令塔か窓口）が前の納品のパスを頼みの本文に書く。これは my_notes の役「相談」の本文の決まりで、works-dispatch には足さない。
- **しないこと**: 納品の後は compact を判断しない。今も、keepalive は仕事が終わると止まり、ターンの終わりの判断も仕事の終わらない待ちだけなので、足す物は無い。指南 4 のとおり、仕事の終わり際の compact は損をする。

### 4.4 司令塔の会話

- **きっかけ**: ターンの終わり（判断だけ）と、次に起きる要求（持ち主の文・待ち受けが打ち込む納品の知らせ・keepalive）。
- **決め方**: ターンの終わりに rent-or-buy に聞き、`buy` なら「compact の時が来た」という印（受付箱の `wake/<場所の鍵>.compact.json` に `due`）を書くだけで、問いは送らない。次の要求に問いを添える。
  - 持ち主の文と、待ち受けが窓に打ち込む文: UserPromptSubmit のフック（人の文のターンの始まりに動く Claude Code のフック。works-dispatch の `role_hook.py` が役の本文を足すのに使っている）の `additionalContext` で、「この返事を終えるとき、持ち主との話が一段落なら最後の行に `compact: <焦点>` を書け。途中なら書くな」を添える。
  - keepalive の時刻: 今どおり、keepalive の文を問いに差し替える。
- **その後**: そのターンの終わりに、最後の応答に `compact: <焦点>` の行が在れば、待ち受けが `/compact <焦点>` を打つ。行が無ければ打たない。印は残り、次の要求にまた添える（添えるのは `Q_添え` だけなので、延期の上限は要らない）。
- **今のまま残す物**: 役の本文が決める `--compact` の区切り（受けた頼みを閉じた時や持ち主との話が一段落した時に、司令塔が自分で打つ）、強制の線、keepalive の時刻に 2 回延ばした後の焦点なしの compact。
- **始め直すか**: 司令塔を `/clear` で始め直すのは、今は持ち主が手で打つ時だけ（my_notes の役「相談」の本文）。compact を重ねると要約の要約が積もって `C'` が育つので、持ち主の席外しが長い時（keepalive の止め時）に、共通メモと受付箱から続きを読める状態なら `--rest` で始め直す手がある。持ち主の決めを替えることなので、この計画では足さず、選んでもらう（納品の残った疑問）。

5. 切れる前の compact: keepalive の止め時に 3.2 の式で判断する。rent-or-buy に「この後キャッシュが切れる」を表す入力（例 `expiring`）を足し、その時は `C·(p_w' − p_r) ≥ F'` で `buy` を返す。指南 3.5 の C の式で、rent-or-buy の設計書の 3.5 が先送りにした「keepalive の時刻の 3 つの手（送る・compact する・止める）」の、止める直前の 1 つに当たる。
