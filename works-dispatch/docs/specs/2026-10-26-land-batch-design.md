# --land の列をまとめて 1 回だけ検査する（まとめ検査）の設計

要点: `--land` の列に並んだ複数のブランチを、1 回のゲートでまとめて入れる設計書。読んで選ぶのは持ち主で（選ぶ中身は下の 15）、急ぎではない（今の列は壊れていない）。

2026-10-26、窓口（本社で持ち主と話して部署に仕事を配る会話）の受付 20261026-090710-ed0ca2（部署への頼みの記録。番号で引く）を受けて、部署「仕組み」が書いた設計書。`--land`（部署のブランチをメインブランチに入れる works-dispatch のコマンド。中身は [land.md](../land.md)）の列に並んだブランチを重ねて、手元のゲートを 1 回だけ回す形（手元の merge queue のまとめ検査）を足す。持ち主の言葉は「おｋ。なら細かく設計書を書き上げておいて。綺麗に作るための工夫も。あ。worksfacotryの設計レビューに依頼してみようかそれで」（worksfacotry は works-factory の打ち間違い。このリポジトリの別のプラグインで、設計書を機械が段ごとにレビューする）。

**読み手に求めること**: 文中の「15」「16」は、この文書のセクション番号（15 は持ち主に選んでもらうこと、16 は今の 1 本ずつの道の能力の棚卸し）。選ぶのは持ち主だけで、実装者と部署の読み手は選ばず、内容を読む。持ち主が選ぶのは 15 の 5 つ（束の上限・合図を打つ時・束の数 1 の道で今の振る舞いを残すか・束で狭まる 3 つを受けるか・`tests/run.sh` を変える札で束を閉じるか）。この文書そのものの承認は要らない。実装は、15 を選んだ後に別の頼みで出す。設計レビューは works-factory で受け（2026-10-26）、指摘は全部この文書に入れた。今の 1 本ずつの道の能力が、この設計で残るか・替わるか・狭まるかは 16 の棚卸しに並べた。

急ぎではない。今の列は壊れていない（1 本ずつ正しく入る）。遅いだけで、2026-10-26 の夕方には 5 本が重なり、1 本 10 分前後のゲートを 1 本ずつ回して 30 分以上詰まった。

作るのは設計だけで、コードは直していない。読み手は、15 を選ぶ持ち主（上の「読み手に求めること」）、works-dispatch の実装者、列の動きを知りたい部署。

## 0. 言葉

- **今・今の道**: この文書を書いた 2026-10-26 の main の `--land` の振る舞い（この設計を入れる前。16 の棚卸しも同じ時点で数えた）。
- **部署**: works-dispatch が仕事ごとに立てる、役を持った別の会話と、その専用のブランチ・作業場（git worktree）の組。「部署の場所」はその作業場。
- **判断役**: 頼みを部署に配る会話（人ではない。my_notes の司令塔など）。`--land-order` で列の入れる順を決める（[land.md](../land.md) の「入れる順を決める」）。
- **`company.base`**: 部署の属性。部署がメインブランチを最後に知った位置（ブランチを作った時の origin のメインブランチか、前の `--land` で入れた後のメインブランチ）。書き換えの取り合い（下）のゲートが、これより後に入った行を見る起点。束が入った後は、受け取りで束の候補に進める（8.2 の 3）。
- **書き換えの取り合い**: ほかの部署が `company.base` より後に入れた行を、この部署のブランチが消している（書き換えている）こと。git の衝突にならず、ゲートの試験も通りうるので、`--land` が順の 2a で先に止める。わざと消すなら `--keep-removal` を付けて通す（[land.md](../land.md) の順の 2a）。
- **会社の形・claude-plugins**: 会社の形は、リポジトリごとに `.claude/company.toml` に書く、部署の役や `--land` の決まりの設定。claude-plugins は、この設計を最初に当てるリポジトリ（works-dispatch が入っているこのリポジトリ）の名前。
- **列**: 会社の形（`.claude/company.toml`）の `[land]` に `queue` を書いたときに在る、メインブランチへ入れる順番待ち。置き場は共通の `.git` の下のフォルダ（claude-plugins では `.git/land-queue`）。実装は `dispatch/nodes/landqueue.py`。
- **札**: 列に申し出た 1 本ごとに置き場に作るファイル（`<20 桁の時刻>-<pid>.ticket`。pid は札を作った処理の番号）。「生きた札」は、札を作った処理が排他のロックを掛けたままの札（ロックの外れた札は落ちた処理の物として消される。`landqueue.alive`）。`--land` の札は横の `.who` に部署の名前とブランチを書いて名乗る。`--queue-run`（works-dispatch の外のツールが列に並んで 1 つのコマンドを走らせる入口）の札は名乗らない。
- **先頭**: 列の `lock` のファイルを持ち、リベース・ゲート・push を進めている `--land` の処理。
- **ゲート**: メインブランチに入れる前に必ず通す検証。claude-plugins では `[land]` の `check`（`bash scripts/light-check.sh && python3 tests/land-check.py && python3 gates/hooks/coldread-gate.py branch-check …`）を手元で回す。
- **候補**: ゲートに出し、緑ならメインブランチにする commit。
- **束**: この設計で足す物。列の先頭と、その後ろに待っている札のいくつかを、1 つの候補に重ねた物。
- **束ね役**: 束を作ってゲートを回す `--land` の処理。列の先頭を取った `--land` がなる。
- **乗る札・乗る部署**: 束ね役が束に入れた、後ろの札とその部署。
- **重ねる**: 一時の場所（ブランチに乗らない git worktree）で、メインブランチの先頭の上に、各部署のブランチの commit を順に `git rebase` で写していくこと。写した commit は元の部署のブランチとは別の commit になる。
- **受け取る**: 束がメインブランチに入った後、乗った部署が、自分のブランチを束の中の自分の写しに置き換えること（8.2）。
- **束の控え**: 束ね役が push の前に列の置き場に書く JSON（8.1）。どの部署のどの写しが束に入ったかを引くための記録。入ったかどうかの正は、写しがメインブランチの祖先かの判定（8.1）。束の全員が受け取ると消す（11）ので、履歴としては残さない。入った事実は、メインブランチの commit と、各部署が出す「束で入った」の 1 行（8.2）に残る。
- **疑いの印**: 赤だった束に乗った札に付ける印（6.2）。印のある札は、次の束に乗らない。
- **初見の読み手のゲート**: `check` の中の `coldread-gate.py branch-check`。メインブランチから分かれた所からの差分で変えた文書を、AI の読み手に初見で読ませる。gates（部署「点検」の受け持ち）の物。読んだ文書の字を、ブランチの名前を鍵にして「前の回の控え」として残し、次の回は前の回から変わった所だけを読ませる。この控えは、束の控え（上）とは別の物。
- **合図**: メインブランチに入った後に走らせる処理。会社の形の `[[land.after]]` に書く。
- **束の印**: 5.3 で `WORKS_LAND_KEY` に入れる、束を表す鍵の形。疑いの印（上）とは別の物。
- **帰属**: 合図から回る頼みや、初見の読み手の呼び出しの記録を、どの部署のどの頼みに結ぶか。今は、メインブランチに入れた 1 つの部署の属性（`company.*`）から決まる。
- **棚卸しの言葉（16）**: 「残る」は今と同じに動く。「替わる」は使う側から見て動きは変わるが、できる事は減らない。「狭まる」は今できる事が減る（[ADR 0002](../../../docs/adr/0002-backward-compatibility.md) の「狭める」。受けるかは持ち主が選ぶ）。

## 1. 結論

1. `[land]` に `batch = <数>` を足す。束の上限の本数で、既定は 1（今と同じ 1 本ずつ）。`queue` を書いた会社でだけ効く。上限は 4 を推す（15 で持ち主が選ぶ）。
2. 列の先頭を取った `--land` が束ね役になり、自分と、後ろに待っている名乗った札を順位の順に、上限まで一時の場所に重ねる。重ねている間、部署の場所（部署の worktree）には触らない。例外は束ね役自身のブランチが機械で解けずにぶつかったときだけで、今と同じに束ね役の部署の場所でリベースを試す（7）。
3. 重ねた上に版上げの commit を 1 つ作り、ゲートを 1 回だけ回す。緑なら fast-forward で push し、束の全部が一度に入る。
4. 赤なら束をほどき、全員が 1 本ずつの道に戻る（Homu・bors の rollup の扱いに倣う。二分探索はしない。6）。赤の束に乗った札には疑いの印を付け、次の束に乗せない。
5. 重ねられない物（ぶつかる・書き換えの取り合い・版上げで止まる）に当たったら、そこで束を閉じる。その札は自分の順番で、1 本ずつの道を通る。列の順は追い越さない。
6. 乗った部署の処理は、自分の順番が来たら束の控えを読み、自分の写しがもうメインブランチに入っていれば受け取って終わる（数秒）。どの処理も、自分の部署の場所にしか書かない。
7. 合図（`[[land.after]]`）は束ごとに 1 回。列が空になるまで遅らせる形も書いた（9。持ち主が選ぶ）。
8. 初見の読み手のゲートは、重ねた差分に 1 回当てる。そのために、`--land` から gates に「どの commit で文書を読むか」を環境変数で渡し、gates の推し量りを安全側に締める直しが要る（5.3。点検の受け持ちに掛かる）。
9. 1 本ずつの道と束の道は、段の関数を 1 組にして共有する（12.1）。束の数 1 のときに今の振る舞いを全部残すか、束と同じ一時の場所の道に畳むかは、持ち主が選ぶ（15 の 3。残すのを推す）。5 本が並んだときのゲートは、乗れる物が全部乗れば 5 回から 2 回になる（上限 4 のとき）。

## 2. 背景と崩さない決まり

- 「main の CI は待たない」（持ち主 2026-10-16。リポジトリのルートの `docs/adr/0073-land-bumps-and-no-tags.md`）: 束にしても、緑の判断は手元のゲートだけで、push の後の CI は待たない。
- 「手元のゲートを外さない」（2026-10-20 に外して main が壊れた。何を回すか・目安の 10 分・見直しの条件は [ADR 0076](../../../docs/adr/0076-land-runs-affected-tests.md)）: 束の候補は、入る中身の全部（全員の commit と版上げ）を持った木で、ゲートはその木で回す。束に入っていない中身がメインブランチに入ることは無い。束と ADR 0076 の関係は 5.2。
- 「今ある能力と使い方を減らさない」（[ADR 0002](../../../docs/adr/0002-backward-compatibility.md)。狭める直しは人に聞く）: 今の 1 本ずつの道の能力を 16 に 1 つずつ棚卸しし、狭まる物は設計者が「意図した替わり」として決めず、15 で持ち主に選んでもらう。
- 以下の D3・D4・D5 は、[internals.md](../internals.md) の「チェック D1〜D9」の番号（試験が構文木と文字で見る決まり）。land.md の「順の 2」「2a」は、同じ land.md の `--land` の順の項目の番号（2 がリベース、2a が書き換えの取り合いのゲート）。受付の番号（9d73b4 など）は、部署への頼みの記録を引く番号。
- 期限を足さない（[internals.md](../internals.md) のチェック D5）: 束ね役も乗る札も、待つ長さに上限を置かない。今の列と同じく止めるのは人の Ctrl-C。
- ノードはほかのノードや入口の層を import しない（D3）。外へ書く関数は決まったノードからだけ呼ぶ（D4。`dispatch/tests/fences.py` の `WRITES`）。
- 列の作りは works-dispatch の 1 か所（`nodes/landqueue.py`）に持つ。`--queue-run` で並ぶ外のツールに札の形を写させない（[land.md](../land.md) の `--queue-run` の項）。

## 3. 手本と比べる

| 手本 | 重ね方 | 赤のとき | ぶつかり |
|---|---|---|---|
| Homu（rust の bors） | 1 本ずつ auto で検査 | main に触らない | — |
| rust の rollup | 人が選んで 1 つの PR に | 犯人を外して作り直す | — |
| bors-ng | 1 つの merge commit | 二分して検査し直す | 束から外す |
| GitLab merge train | 前の物を全部含めて並行 | 外して後ろを作り直す | 列から外す |
| この設計 | 一時の場所に順に rebase | ほどいて 1 本ずつ | そこで束を閉じる |

- bors-ng は、束が赤で 2 本以上なら二分する（bors-ng の `lib/worker/batcher.ex` の説明「bisected (if it failed and there are two or more patches in it)」）。束の上限は `max_batch_size` で決める（[bors の文書](https://bors.tech/documentation/)）。
- GitLab の merge train は、各 MR に「前の MR を全部含めた」パイプラインを最大 20 本並べて回し、赤の MR を外して後ろのパイプラインを作り直す。ぶつかった MR も外し、リベースして入れ直させる（[GitLab の文書](https://docs.gitlab.com/ci/pipelines/merge_trains/)）。
- rust の rollup は、赤なら犯人の PR を外して rollup を作り直し、分からないときは疑わしい PR を `rollup=never` にして 1 本ずつ検査させる（[rust の rollup の手順](https://forge.rust-lang.org/release/rollups.html)）。
- Homu は auto のブランチで 1 本ずつ検査し、緑で main を fast-forward、赤なら main に触らない（[merge queue の歴史](https://mergify.com/blog/the-origin-story-of-merge-queues)）。今の `--land` はこの形。

この設計が合わせる所: 候補に入る中身の全部をゲートに掛ける（全員）、緑で fast-forward（Homu・bors）、赤なら main に触らない（全員）、上限を置く（bors の `max_batch_size`、GitLab の 20）。合わせない所: GitLab の並行のパイプライン。手元のゲートは 1 台の機械で回り、10 分前後で機械を使い切るので、並べると全部が遅くなる（ルートの CLAUDE.md の「並べすぎない」）。並べられないので、merge train の「前の物を含めた候補を本数ぶん作る」形は取らず、bors の「束に 1 つの候補」の形を取る。

## 4. 束の作り方

### 4.1 誰が束ね役になるか

- 列の先頭を取った `--land`（`landqueue.Hold.take` が戻った処理）が束ね役になる。新しい役の処理や常駐の処理は作らない。束ね役が終わって列を抜ければ、次の札が先頭を取る。
- `batch` が 1 か、乗る札が 1 つも無ければ、束を作らず、束の数 1 の道を通る（12.1。その道で今の振る舞いを残すかは 15 の 3）。

### 4.2 どの札が乗るか

束ね役は、先頭を取った時点で待っている生きた札を、列の順位（`order` の指定の後に申し出た順。`landqueue._ranked` と同じ）で前から見て、次の条件を全部満たす間だけ乗せる。満たさない札に当たったら、そこで束を閉じる（その後ろは見ない）。

1. 名乗った札である（`.who` が在る）。名乗らない札（`--queue-run`）は中で何をするか分からないので、越えない。
2. 名乗りのブランチが今も在り、その部署の場所が見つかる（部署の名前とブランチは `.who`、場所は `ports.places` から引く）。
3. その部署の役で読んだ取り込みの決まり（`mode`・`gate`・`check`・`bump`・`main`）が束ね役と同じ。役ごとの `[land.roles.<役>]` で決まりが違う部署は、違うゲートを通る約束なので、同じ束に入れない。bors-ng の「priority の違う PR は束ねない」と同じ考え。
4. 部署の場所に未コミットの変更が無い（`ports.is_clean`。今の `--land` の確かめと同じ）。
5. ブランチがまだメインブランチに入っていない。入っているかは 2 つで見る: ブランチの先頭がメインブランチの祖先か、束の控え（8.1）にそのブランチの行が在り、ブランチの先頭がその行の元と同じで、行の写しがメインブランチの祖先か（前の束で入り、まだ受け取っていない札。写しは元と別の commit なので、祖先の判定だけでは入っていないと見え、もう一度重ねてしまう）。入っていれば、その札は自分の順番で受け取りか片付けに進むだけなので、乗せずに先へ見る（閉じない）。
6. 疑いの印が無い（6.2）。
7. 上限（`batch`）に届いていない。束ね役を 1 本に数える。
8. 15 の 5 で「閉じる」を選んだときだけ: その札のブランチが `tests/run.sh` を変えていない（5.2）。

- 先頭を取った後に申し出た札は見ない。束の中身は先頭を取った時点で決め、ゲートの間に増えない。後から来た札は次の束になる。
- 束ね役は乗る札の部署の場所を読むだけで、書かない（読むのは HEAD・属性・未コミットの有無）。
- 4.2 の 5 だけが「飛ばして先へ見る」で、ほかは「そこで閉じる」。列の順（判断役が `--land-order` で決めた順を含む）を追い越さないため。merge train はぶつかった MR を外して後ろを進めるが、この列の `--land-order` は「名を書いた順に通る」を約束しているので、追い越しを入れるとその約束が崩れる。閉じても損は小さい: 閉じた札は次の先頭になり、そこから次の束が始まる。
- 条件は全部、13 の 2 の表の試験で 1 つずつ固める。

### 4.3 重ね方

1. 一時の場所を 1 つ作り（`land.stage`。今の版上げと同じ）、origin のメインブランチの先頭に置く。
2. 束ね役から順に、各ブランチの commit（メインブランチとの分かれ目からブランチの先頭まで）を、一時の場所の先頭の上へ `git rebase --onto` で写す。ぶつかりは今の `land.auto_rebase` と同じ物だけを機械で解く（git rerere と、変更の記録の `## [Unreleased]` の見出しのすぐ下で、部署の書き足しとメインブランチの書き足しが並んでぶつかる形。[land.md](../land.md) の順の 2）。ここは `auto_rebase` の「ぶつかりを解いて続ける」の繰り返しを関数に分けて、部署の場所でも一時の場所でも使う（12.4）。
   - 写す範囲はブランチの名前でなく commit で渡す（`git rebase --onto <一時の場所の先頭> <分かれ目> <ブランチの先頭の commit>`）。ブランチの名前を渡すと、git はそのブランチを一時の場所で checkout しようとし、部署の場所が開いているブランチなので断る。一時の場所は終始ブランチに乗らない HEAD のまま進む。今の `gitx.rebase(cwd, onto)` は「今のブランチを onto の上へ」の形だけなので、この形の関数を `gitx.py` に足す（偽物の前提は 13 の 4 で確かめる）。
   - 写す物が無い（ブランチがもう一時の場所の先頭の上に在る）ときは、先頭が動かないのを誤りでなく「写し＝元」として進める。今の `auto_rebase` は先頭が動かないと失敗として返す（`land.py` の `new == old`）ので、分けた関数ではこの扱いを呼ぶ側が選べるようにする。
3. 写すたびに、その部署の書き換えの取り合いのゲート（今の順の 2a。`land.taken`）を当てる。since はその部署の `company.base`、main は写す前の一時の場所の先頭、head は写した後の先頭。当たったら、その部署で束を閉じる（7。試験: 13 の 2）。
4. 写すたびに、その部署が変更の記録を書いたかを部署ごとに見る（5.1）。書いていなければ、その部署を外して束を閉じる（試験: 13 の 2・13 の 3）。`bump.plan` を一時の場所で回すだけでは足りない: `bump.plan` は一時の場所の `## [Unreleased]` 全体を見るので、同じプラグインを先に重ねた部署の書き足しが、後の部署の書き忘れを隠す。
5. 各部署について、写す前のブランチの先頭（元）と、写した後の一時の場所の先頭（写し）を覚える。8.1 の控えに書く。

束ね役のブランチが既にメインブランチの先頭の上に在れば、写しは元と同じ commit になる（git の rebase は動かす物が無ければ commit を作り直さない）。

### 4.4 上限

- `batch` は 1 以上の整数。0 以下・整数でない物は決まりの誤りで止める（今の `[land]` の読み方 `land.read_rules` の problems に足す。試験: 13 の 2）。
- 役ごとの `[land.roles.<役>]` には書けない（`queue` と同じく、列は clone ごとに 1 つなので。試験: 13 の 2）。
- 推す値は 4。訳: 赤のときの損が上限に比例する（6.3）。2026-10-26 の詰まりは 5 本で、上限 4 なら 2 回のゲートで済む。bors の文書も rust の rollup も「束は大きくしすぎない」と書く（rust の手順「Massive rollups are rarely needed」）。持ち主に選んでもらう（15 の 1）。
- `batch` を 2 以上に書く会社は、`check` が一時の場所（git に足していないファイルが無い木）でも通ることを先に確かめる。束は一時の場所でしか回せない（16 の 2）。land.md の `batch` の説明に書く。

## 5. ゲート

### 5.1 版上げ

- 重ねた先頭の上に、版上げの commit を 1 つだけ作る（`bump.make`）。束の中の全員の変更を 1 回で見るので、上げ幅は各プラグインごとに束全体の変更から決まる（今の決め方そのまま。Added などが 1 つでも在れば minor）。
- 版上げの commit は束に 1 つ。乗った部署ごとに版を上げない。marketplace は版が変わった時だけ中身を取り直すので、束の中の全員の変更は 1 つの版で利用者に届く。
- `bump.make` の今の止まり方（中身の無い `## [Unreleased]`）は、4.3 の 4 で部署ごとに先に見て、その部署で束を閉じる。束ね役自身で止まれば、今と同じに `--land` 全体を止める。
- 部署ごとの見方: その部署の写しの範囲（写す前の一時の場所の先頭から、写した後の先頭まで）で、版上げの数え方（`bump.py` が試験と文書だけの変更を外す決まり）に当たるファイルを変えたプラグインごとに、そのプラグインの `CHANGELOG.md` の `## [Unreleased]` に、`#` で始まる見出しのほかの行をその範囲で 1 行でも足したか。1 本ずつのときは、メインブランチの `## [Unreleased]` がいつも空なので（入れるたびに版上げが中身を版へ移す）、今の `bump.plan` の判定とこの見方は同じ答えになる。この見方を `bump.py` に、ファイルを読まずに差分の字だけを受け取る関数として足し、表の形の試験で固める。

### 5.2 手元の検証

- 束（2 本以上）は `check` を一時の場所で回す。束の数 1 は、15 の 3 で「残す」なら今と同じ（版上げが無い会社は部署の場所で回し、後から足されたファイルを `_sweep` で消す）、「畳む」なら一時の場所で回す。
- `tests/land-check.py`（メインブランチとの分かれ目から変わったファイルに当たる試験だけを回す）は、束全体の差分に当たる試験を回す。分かれ目は `git merge-base HEAD refs/remotes/origin/main` で取り、一時の場所は origin のメインブランチの先頭の上に重ねるので、分かれ目はその先頭になり、束全体の差分が正しく取れる。束が大きいほど回る試験は増えるが、同じ試験を本数ぶん回すよりは少ない。
- [ADR 0076](../../../docs/adr/0076-land-runs-affected-tests.md) との関係:
  - 束のゲート 1 回を、ADR 0076 の見直しの条件（`tests/run.sh` を変えない回で 10 分を超えた・見送った赤が週 2 回より多い）の「`--land` 1 回」と数える。`tests/land-check.py` が出す、かかった時間と load average の行は、束でもそのまま出る。
  - 乗った札のどれかが `tests/run.sh` を変えると、`tests/land-check.py` は束全体で全部の試験を回す（`RUN_ALL`。claude-plugins で 25 分ほど。ADR 0076 に 2026-10-20 に測った全体 25 分 44 秒の記録が在る値で、機械の混み具合で変わる）。この回は ADR 0076 の 10 分の目安の外（見直しの条件も「`tests/run.sh` を変えない回」だけを数える）。
  - 束が大きいと、`tests/run.sh` を変えない回でも 10 分の目安に当たりうる。当たったら ADR 0076 の見直しの条件のとおりに見直す（上限を下げるのも手の 1 つ）。
  - `tests/run.sh` を変える札で束を閉じる（その札は自分 1 本で通す）かは、15 の 5 で持ち主が選ぶ。
- `scripts/light-check.sh` は、緑なら候補の木の印（共通の `.git` の `light-check-ok/<木>`）を残し、push の前のフックがその印で検査を飛ばす。束でも候補の木は 1 つなので、そのまま効く。
- CI のブランチのゲート（`gate = "release/*"` の形）: ゲートのブランチの名前は、束ね役（走っている処理）の部署の名前を `*` に入れて作る（今の `land.gate_branch` の決め方）。作った名前がメインブランチか、束に乗った部署のどれかのブランチと同じなら止める（今は走っている部署のブランチとだけ比べる。[land.md](../land.md) の `gate` の「部署のブランチと同じなら止める」を、束の全員に広げる）。GitHub の merge queue も、束ごとに一時のブランチを 1 本作る。束では、候補をゲートのブランチへ出す push（`land.publish`）を一時の場所から打つ（push の前のフックを候補の木から走らせる。16 の 1 の 3 と同じ訳）。試験: 13 の 2。

### 5.3 初見の読み手のゲート（gates の直しが要る）

今は壊れていない。束を入れると壊れる。gates の直しが入るまで、束（`batch` が 2 以上）は効かせない（14 の順の 3 を 4 より先にする）。

- 今の動き: `branch-check` は一時の場所（ブランチに乗らない HEAD）で回ると、「HEAD から辿れて、分かれ目から辿れないブランチ」が 1 本だけのときに、そのブランチを鍵にし、HEAD がそのブランチの頭より先に居れば、文書の字をそのブランチの頭で読む（`gates/hooks/coldread-gate.py` の `_branch_where`。版上げの commit が書き換える `CHANGELOG.md` を読まないための工夫。受付 9d73b4）。docstring は前提を「候補はその頭か、頭に版上げの commit を足した物」と書く。
- この鍵は 2 つの役を兼ねる: 前の回の控えの置き場（`_last_path`）と、読み手の呼び出しの記録の帰属（`reader_source(branch=…)` が、そのブランチに乗った作業場がちょうど 1 つのときに、その作業場の `company.name`・`company.ask` を引く）。
- 束での壊れ方（束ね役のブランチがメインブランチの先頭の上に在り、束ね役のブランチだけが当たる場合）:
  1. 乗った部署だけが変えた文書（メインブランチに前から在る物）は、束ね役のブランチの頭の字、つまりメインブランチと同じ字で読まれる。書き換えが無いと見えるので、その文書は読まれずに数えからも外れ、ゲートは緑を出す（`doc_excerpt` が空を返し、`branch_check` が飛ばす）。守りの検査が成り立たないのに合格に数える形で、「手元のゲートを外さない」を一部外すのと同じ。
  2. 束ね役と乗った部署の両方が変えた文書は、束ね役のブランチの頭（乗った部署の変更を含まない字）で読まれる。
  3. 前の回の控えが束ね役のブランチの鍵に混ざる。
  4. 束ね役も写し直されたときは 0 本が当たり、控えを使わずに作業ツリーから読む（正しいが、毎回全部読み直す）。
- 直し方（gates の側）:
  1. 推し量りを締める（環境変数が無くても効く守り）: ブランチの頭の字を使うのは、HEAD がその頭のちょうど 1 commit 先で、その 1 commit が版上げの commit の変えるファイル（各プラグインの `.claude-plugin/plugin.json`・`CHANGELOG.md` と marketplace の目録。`bump.apply` が書く物）だけを変えたときにする。そうでなければ鍵も読む commit も None にし、作業ツリーから読む。commit の数だけで見ると、版上げの commit が付かない束（`bump` の無い会社か、据え置きのプラグインが無い回）で乗る部署が 1 commit だけのとき、その commit を版上げと取り違えて、乗った部署の文書を読まずに通す。控えは効かないが、読まずに通ることは無くなる。会社の `check` が gates を候補の木の外（入れたプラグインの版など）から呼んでも、この守りは版のずれに頼らない。
  2. 環境変数が在れば、推し量りより先に使う。`--land` が `check` を回すときに渡す:
     - `WORKS_LAND_TIP`: 文書を読む commit（版上げの前の、重ねた先頭）。HEAD の祖先でなければ、作業ツリーに黙って戻さず、`branch-check` を終わりの値 2（誤り）で止める。
     - `WORKS_LAND_KEY`: 前の回の控えの鍵だけに使う文字列。束の数 1 なら部署のブランチの名前（今と同じ控えが効く）。束なら束ね役のブランチの名前の後ろに、半角空白と `batch` を足した物（束の印。例 `dept/foo batch`。ブランチの名前は空白を含められないので、実在のブランチの鍵とぶつからない）。束では、乗った部署の変えた文書は控えなしで読む。
     - `WORKS_LAND_BRANCH`: 帰属を引く実在のブランチ（束ね役の部署のブランチ）。`reader_source(branch=…)` にはこれを渡す。鍵（上）とは分ける。
- 帰属: 束では、乗った部署の文書の読みも、記録の上では束ね役の部署と頼みに結ばれる。今の「入れた部署ごとの記録」から狭まるので、16 の 2 に並べ、受けるかを 15 の 4 で持ち主に選んでもらう。受けないときの形: `--land` が乗った部署ごとのブランチと写しの範囲も渡し（`WORKS_LAND_MEMBERS`。9 と同じ環境変数を広げる）、gates はその文書を変えた部署のブランチで `reader_source` を引き、控えも部署ごとに分ける。gates の側の手間が増える。
- 費用: 束では、乗った部署の変えた文書を控えなしで読むので、AI を起動する回数は 1 本ずつのときの合計と同じくらい。ゲート全体の時間は、試験の側が束で減る分だけ減る。
- この直しは gates（点検の受け持ち）と works-dispatch（仕組みの受け持ち）の両方に掛かり、片方だけ入れると食い違う（環境変数を渡しても読まない・読むのに渡さない）。実装の頼みでは、1 つの会話で通しで直して入れ、触った受け持ちを納品に書く（担当の役の本文の決まり）。推し量りを締める 1 は、束が無くても今の道を悪くしない（今の候補はいつも「頭か、頭に版上げの commit を足した物」なので、答えが変わらない）。

## 6. 赤のとき

### 6.1 ほどき方

1. 束のゲートが赤なら、メインブランチには触らない（全員の手本と同じ）。
2. 束が 1 本なら、今と同じに部署に失敗の要点を頼んで止める。
3. 2 本以上なら、束をほどく。束ね役は、自分 1 本で束の数 1 の道を回し直す（同じ順番のまま。列を抜けない）。緑なら入れ、赤なら今と同じに自分の部署に頼んで止める。
4. 乗った部署の処理は、自分の順番が来ると、束の数 1 の道を通る（疑いの印があるので束にならない）。
5. 赤の後に通るのは束の数 1 の道なので、15 の 3 で「残す」を選べば、赤の部署はいつも今と同じに、メインブランチの上にリベースした土台で直せる（16 の 1 の 1）。

### 6.2 疑いの印

- 列の置き場の `suspects`（1 行に 1 つ、ブランチの名前と、赤だった時の写す前の先頭の commit）に足す。
- 印のある札は 4.2 の 6 で束に乗らない。束ね役になったときも、束の数 1 の道を通る。
- 印が消えるのは、そのブランチがメインブランチに入ったとき（その `--land` が消す）か、ブランチの先頭が印の commit から動いたとき（部署が直して push し直した。印は当たらなくなるので、見る側で読み飛ばし、次に書く処理が掃除する）。試験: 13 の 2。

### 6.3 二分探索を採らない訳

- bors-ng は二分する。束が大きく、検査が CI の上で並べられるなら、二分は赤の犯人を早く見つける。
- この列では、上限が 4 前後と小さく、ゲートは 1 台の機械で 1 本ずつしか回せない。束 4 本の赤で犯人が 1 本のとき、二分は「前半 2 本 → 当たった側の 1 本」で 2〜3 回。1 本ずつは、疑いの印で全員が 1 本ずつ回るので、いつも束の本数（4 回）で、差は 1〜2 回（実測でなく、犯人が 1 本・ゲート 1 回の長さが同じと仮定した数え方）。犯人が 2 本以上だと二分の回数は増え、差はさらに縮む。
- 1 本ずつは今の道そのもので、赤のときに頼む相手（その部署）も今と同じに決まる。二分は「束の一部をもう一度束にする」形を足すので、コードと試験が増え、途中で落ちたときの戻し方も増える（12.5・12.7 の、状態と道を増やさない考えに反する）。
- 束ね役が先に自分 1 本を回すのは、束ね役が列の先頭を持ち続けていて、自分のブランチをそのまま回すのが一番状態が少ないから。rust の rollup の「疑わしい物は 1 本ずつ検査させる」と同じ扱い。

## 7. 重ねられない物

| 当たった物 | 束ね役なら | 乗る札なら |
|---|---|---|
| ぶつかり（機械で解けない） | 今と同じく部署に頼んで止める | そこで束を閉じる |
| 書き換えの取り合い（2a） | 今と同じく止める | そこで束を閉じる |
| 版上げで止まる | 今と同じく止める | そこで束を閉じる |

- 束ね役のぶつかり: 今の `_rebase_here` と同じく、部署の場所でリベースを試し、解けなければ部署に頼んで止める（部署の会話に答えを返すのは今と同じ道）。重ねる段で当たったときに、部署の場所でもう一度リベースを試す形にする（束の道で、ゲートの前に部署の場所に触る唯一の場合）。
- 乗る札で閉じたとき、その札は次の先頭になって自分の道を通るので、ぶつかりの頼み・取り合いの止まり（`--keep-removal` で通す道も含む）・版上げの止まりは、全部今の道がそのまま出す。束ね役は乗る札の部署に何も頼まない（自分の部署の外に書かない。12.5）。
- 書き換えの取り合いを束の中で見る訳: 乗った部署どうしでも、片方が先に入れた行をもう片方が消すことがある。部署ごとに「写す前の一時の場所の先頭」を main に見立てれば、束の中で先に重ねた部署の行も守られる。
- 3 つの閉じ方は、どれも 13 の 2 で試験にする（ぶつかりは 13 の 3 の本物の git でも）。

## 8. 緑のときと受け取り

### 8.1 束の控え

- 緑なら、push の前に列の置き場の `batches/<束ね役の札の名>.json` に書く（置き換えで書き、途中で読まれても半端な中身を見せない。`landorder.write` と同じ書き方）。
  ```json
  {"main_before": "<重ねる前のメインブランチの先頭>", "candidate": "<版上げの commit>",
   "members": [{"ticket": "<札の名>", "name": "<部署の名前>", "branch": "<ブランチ>",
                "original": "<写す前の先頭>", "stacked": "<写しの先頭>"}]}
  ```
- 控えは「書いた」だけでは何も約束しない。入ったかの正は、いつも「写しがメインブランチの祖先か」（`git merge-base --is-ancestor`）で決める。控えは、どの写しが誰の物かを引くためだけに使う。push の前に落ちても、控えに書かれた写しはメインブランチに無いので、誰も受け取らない。
- 緑の後にメインブランチを取り直し、メインブランチが候補の祖先でなくなっていれば（列に並ばない処理が push した）、束の顔ぶれ（先頭を取った時に決めた物）を保ったまま、一時の場所を新しいメインブランチの先頭から 4.3 で重ね直し、版上げとゲートから回し直す。控えは重ね直した写しで書き直す。重ね直しでぶつかる・取り合いに当たる部署が出たら、7 の表のとおりにそこで束を閉じる。束ね役自身がぶつかれば、今と同じに部署の場所でリベースを試す。
- push が断られたら、今と同じにメインブランチを取り直して分ける。先に進んでいれば上と同じに重ね直して回し直し、進んでいなければ（ブランチの保護・認証）頼まずに止める。上の 2 つは今の `main_again` と断りの分け方（`landing.py` の `_main` の緑の後）を束に写した物で、試験は 13 の 3。

### 8.2 受け取り

1. 束ね役は push した後、自分の部署の場所で受け取る（下の 2 と同じ手）。
2. `batch` が 2 以上の会社の `--land` は、順番を取った後に部署の場所の HEAD を読み直し（今は順番を取る前に読んでいる。束の後では HEAD の意味が変わるので、取った後に読む。16 の 2 の 1。`batch` が 1 なら束の控えは作られないので、今のまま）、束の控えから自分の札かブランチの行を探す。この受け取りの判定は、メインブランチを取り直した直後、今の「もう入っているか」（`is_ancestor`）と部署の場所のリベース（`_rebase_here`）より前に置く。後に置くと、元のブランチをメインブランチの上にリベースしてしまい、写しと同じ中身をもう一度入れようとする。行の写しがメインブランチの祖先なら、受け取る:
   - 先に、部署の場所が汚れていないかを見る（`ports.is_clean`）。汚れていれば受け取らず、部署の窓に「中身はメインブランチに入った（束ね役 <部署>）。手元の変更を commit してから `--land` を打ち直す」と頼んで止める（終わりの値 1。控えは残す）。順番を取った後に部署の会話が書けば汚れうる（今の `_rebase_here` も、ゲートを待つ間に部署の会話が書いたときに、同じく部署に頼んで止める）。
   - HEAD が元と同じ: `git reset --keep <写し>` で部署のブランチを写しに替える。`--keep` が断れば（[git reset](https://git-scm.com/docs/git-reset) の `--keep` は、手元の変更と替わるファイルが重なるとやめる。上の確かめの後に書かれた場合）、上の汚れたときと同じに頼んで止める。origin の部署のブランチも写しに替える。期待値（`--force-with-lease` に渡す値）は、今の `auto_rebase` の `push_rebased` と同じく、今の origin の部署のブランチの値（`g.remote_rev`。無ければ空で、新しく作る）にする。元を期待値にすると、origin に出していない部署や、origin が遅れている部署で毎回断られ、origin の部署のブランチが古いまま残る。
   - origin への push が断られた（部署が origin に push し直していた）: 手元の受け取りは済ませたまま、origin の部署のブランチは替えずに注記を出して進める。中身はメインブランチに在るので失う物は無く、origin の部署のブランチは次の `--land` か片付けで揃う。
   - HEAD が元より先に進んでいる（束に乗った後に部署が commit を足した）: `git rebase --onto <写し> <元>` で足した commit だけを写しの上に移し、そのまま今の道（ゲートから）を続ける。
   - それ以外（元を含まない。部署が書き換えた）: 受け取らず、今の道を通る（中身がメインブランチに入っていればリベースで消え、残りだけが入る）。
3. 受け取ったら、`company.base` を束の候補に進め、片付け（`_tidy`）に進み、「束（束ね役 <部署>）でメインブランチに入った」と 1 行出して終わる。合図は出さない（9）。
4. 受け取りに使う git の手は、部署の場所でしか打たない。束ね役は乗った部署の場所を書かない。
5. 受け取りの手（判定と git）は 1 つの関数にしてノードに置き、`--land` と `wake_hook.follow_main` の両方から呼ぶ（11。試験: 13 の 2）。

## 9. 合図（`[[land.after]]`）

- 束ね役だけが、push の後に 1 回打つ。乗った部署は打たない。束の部署の一覧を環境変数（`WORKS_LAND_MEMBERS`。部署の名前を改行で区切った物）で足す。claude-plugins の合図（配布・CI の見張り・工場の版の見張り。工場は、works-factory プラグインが固定の commit〔`works-factory/PIN`〕で取り寄せて使う修正の工場 raiki61/works-factory。その版の見張りは、工場の main に CI が緑の新しい commit が在れば、PIN を上げる頼みを作業に回す。会社の形の `works-factory-pin` の項）は、どれもメインブランチの先頭を見るので、ツールを回すのは 1 回で足りる。
- ただし帰属は 1 回では足りない。`calls.fire`（`dispatch/calls.py`）は、入れた部署の属性から `ask`・`boss` など（`boss-account`・`boss-session`・`boss-pane`・`boss-inbox`）を取り、ツールが片づかないときに回す頼みの頼み元と、台帳の親（cause）にする。束ね役の属性だけを渡すと、乗った部署の変更で main の CI が赤になっても、その頼みは束ね役の頼み元へ回り、乗った部署の頼みには結ばれない。今の「入れた部署の頼みに結ばれる」から狭まるので、16 の 2 に並べ、受けるかを 15 の 4 で持ち主に選んでもらう。
- 受けないときの形: `--land` は乗った部署の属性の並びも `calls.fire` に渡し、`calls.fire` は回す頼みの cause を部署ごとに結ぶ（どの部署が原因か分からない頼みは、束の全員を親に並べる）。`calls.fire` は会社の形のツールを呼ぶ共有の口なので、広げるのは持ち主が選んだときだけにする。
- 持ち主が選ぶもう 1 つの形（15 の 2）: 列が空になるまで遅らせる。push した処理が置き場に `after-pending` を書き、列を抜けるときに後ろに名乗った札が居なければ自分で打って消す。居れば打たずに残し、後ろの処理が同じ手で引き継ぐ。落ちた処理の残した印は、次の `--land` が抜けるときに拾う。配布の回数は減るが、最初に入った変更が利用者に届くのが列の終わりまで遅れ、状態が 1 つ増える。帰属は束のときと同じ問いになる。

## 10. --land-order・--queue-run・--dry-run との関係

- `--land-order`: 束は列の順位の前から作るので、判断役が `order` で前に出した札がそのまま束の前に入る。今先頭で進んでいる束は止めない（今の「次の 1 本から効く」と同じ）。一覧に「次の束」の印（束ね役の次から上限まで、4.2 の条件で見積もった物）を添える。見積もりは読むだけで、束の中身を約束しない（試験: 13 の 2）。
- `--queue-run`: 名乗らない札で束を閉じる（4.2 の 1）。外のツールの push を束の中に混ぜない。外のツールが先頭のときは今と同じに 1 本で走る。
- `--dry-run`: 束を作るかの見立て（乗る札・閉じた訳・上げる版の見積もり）を、一時の場所を作らずに出す。重ねる見立てに要るぶつかりの有無は `git merge-tree --write-tree`（作業ツリーを変えずに merge の結果を出す。[git merge-tree](https://git-scm.com/docs/git-merge-tree)）で見積もり、当たらなかったぶつかりは本番の rebase で出る（見積もりなので外れうると出す。試験: 13 の 2）。

## 11. 止まった・落ちた時

| 起きた所 | メインブランチ | 残る物 | 次に起きること |
|---|---|---|---|
| 重ねる途中で落ちた | 変わらない | 一時の場所 | 残る（下の項） |
| ゲートの途中で落ちた | 変わらない | 一時の場所 | 残る（下の項） |
| 控えを書いた後・push の前に落ちた | 変わらない | 控え・一時の場所 | 誰も受け取らない |
| ゲートの間にメインブランチが進んだ | 変わらない | — | 重ね直して回し直す（8.1） |
| push の後・受け取りの前に落ちた | 束が入った | 控え | 自分の順番で受け取る |
| 乗った処理が受け取る前に落ちた | 束が入った | 控え | 次の `--land` が受け取る |
| 見直しの後・push の前に札が抜けた | 束が入った | 控え | 次の `--land` が受け取る |
| 受け取りの git が断られた | 束が入った | 控え | commit してから打ち直す（8.2） |
| 受け取りの origin への push が断られた | 束が入った | — | 注記。次の `--land` で揃う |

- 一時の場所は `dispatch-land-` の頭の名前で作る（今の版上げと同じ）。片付けは今と同じく `_main` の `finally`（`land.unstage` と `shutil.rmtree`）だけで、SIGKILL や電源断で落ちると残る。今も版上げの会社（claude-plugins を含む）では毎回一時の場所を作っていて、同じ残り方をする。残りはブランチに乗らない worktree なので、メインブランチと部署のブランチを食い違わせない。残った場所は OS の一時の場所の掃除で消え、git の worktree の記録は `git worktree prune`（人が打つか、git gc が古い物を消す）で消える。束のために拾う手は足さない（足すなら別の頼みで、今の版上げの道と一緒に）。
- 乗った部署が `--land` を打ち直さないまま残っても、メインブランチには中身が入っていて、部署のブランチだけが古い。次にその部署が `--land` を打てば 8.2 で受け取る。打たなければ、`wake_hook.follow_main`（永続の部署の作業場をメインブランチに追いつかせる待ち受けの手）は「作業場のブランチにメインブランチに無い commit が在る」と見て止まる。ここは受け取りの手を `follow_main` からも呼べる形にして塞ぐ（8.2 の 5）。
- 束の控えは、束の全員がメインブランチに入った（受け取った）か、写しがメインブランチの祖先でない（push されなかった）と分かった時点で、見た処理が消す。消し忘れても、正は祖先の判定なので、誤って受け取ることは無い。
- 束ね役が Ctrl-C で止められたとき: push の前なら何も入っておらず、乗った札は自分の順番で今の道を通る。push の後なら、受け取りは乗った部署の側がするので、束ね役が途中で止まっても欠けない。
- 乗る札の処理が、束ね役がゲートを回している間に Ctrl-C で抜けた（札が消えた）とき: 束ね役は push の直前に札の生死を見直し、消えた札が在れば、その部署から後ろを外して束を作り直す（ゲートを回し直す。試験: 13 の 2）。見直しの後（push の途中を含む）に抜けた札の中身は入りうる。札の生死はロックで見るので、この間を閉じる手は無い（閉じるには、乗る札の処理が束ね役の push を待つ約束が要り、その待ちは期限を置けない待ちを 1 つ増やす）。今の 1 本ずつの道では、列で待つ間に Ctrl-C した札は決して入らないので、束で狭まる物として 16 の 2 に並べ、15 の 4 で持ち主に選んでもらう。
  - 入っても食い違いは無い: 入った中身はゲートを通った物で、部署のブランチはその部署の次の `--land` か `follow_main` が 8.2 で受け取る。入れたくなかった部署は、入った commit を git revert で戻す。乗った処理が抜けるときに「束に乗っていたので、束ね役が入れたかもしれない」と 1 行出す（札の横に束ね役が「乗せた」印を書き、抜ける処理がそれを見て出す）。

## 12. 綺麗に作るための工夫

### 12.1 1 本ずつの道と束の道で段を共有する

- 段（12.2）の関数は 1 組で、束の数 1 の道と束の道が同じ関数を通る。違いは、重ねる場所と `check` を回す場所の 2 つの値だけにする（部署の場所で回したときだけ、後から足されたファイルを `_sweep` で消す）。
  - 15 の 3 で「残す」（推す）なら、束の数 1 は今と同じに部署の場所でリベースし（`_rebase_here`）、版上げが無ければ部署の場所で `check` を回す。束は一時の場所に重ねる。今の 1 本ずつの道の能力は 1 つも狭まらない（16 の 1）。
  - 「畳む」なら、束の数 1 も一時の場所に重ね、緑の後の受け取りで部署のブランチを替える。道は 1 つになるが、16 の 1 の「狭まる」の行を受ける。
- どちらでも、ぶつかりを解く繰り返し（12.4）、版上げ、ゲート、出す・後始末の段は 1 つ。束が赤の後は束の数 1 の道を通るので（6.1）、赤の扱いも 1 つ。
- 何が残り・替わり・狭まるかは、設計者の申告でなく、land.md の順と `_main` の分岐から機械的に数えた棚卸し（16）で決める。

### 12.2 段に分ける

`_main` を次の段の関数に分け、各段は前の段の結果（値）だけを受け取る。

1. 選ぶ（`select`）: 列の札と部署の場所を読み、束の顔ぶれを決める。読むだけ。
2. 重ねる（`stack`）: 重ねる場所（部署の場所か一時の場所）を受け取り、顔ぶれを順に写す。閉じた所と訳を返す。
3. 版を上げる（`bump`）
4. ゲート（`gate`）
5. 出す（`publish`）: 控えを書き、push する。メインブランチが進んでいれば 2 へ戻る（8.1）。
6. 受け取る（`adopt`）: 自分の部署の場所だけを替える。
7. 後始末（`finish`）: 合図・`company.base`・片付け・控えの掃除。

### 12.3 決めるだけの関数を分ける

- 束の顔ぶれを決める関数は、札の並び・各札の部署の状態（決まり・未コミット・入ったか・疑いの印）・上限を受け取って、(乗る札の並び, 閉じた札, 閉じた訳) を返すだけにし、ファイルも git も触らない。表の形の試験（入力と答えの行を並べた試験）で 4.2 の条件を全部固める。
- 受け取りの場合分け（8.2）も、(汚れ, HEAD, 元, 写し, 祖先か) を受け取って手の名前を返す関数に分ける。

### 12.4 部品を 1 つにする

- 「ぶつかりを機械で解いて続ける」繰り返しは、今は `land.auto_rebase` の中に在る。これを「rebase の始め方」を引数に取る関数に分け、部署の場所のリベースと一時の場所の重ねる段の両方から使う。ぶつかりの解き方が 2 つに分かれない。
- 束の控え・疑いの印の読み書きは `nodes/landqueue.py` に置く（列の置き場を知るのはここだけ。D4 の表に足す）。

### 12.5 状態は列の置き場の 1 か所に、書くのは自分の部署だけ

- 列の状態は、札・`order`・`batches/`・`suspects`・束ね役が札の横に書く「乗せた」印（11）（と 9 の形を選べば `after-pending`）の、置き場のフォルダの中だけに持つ。部署の属性（`company.*`）には束の情報を書かない。
- どの処理も、git で書くのは一時の場所と自分の部署の場所と origin だけ。ほかの部署の場所には書かない。部署の会話が同時に作業していても、取り合いが起きない。

### 12.6 振る舞いを先に試験で固める

実装の最初の commit は、今の 1 本ずつの道の振る舞いを固める試験だけにする（13 の 1）。段に分ける直しはその試験を通したまま入れる。試験を直してよいのは、16 で「替わる」とした行と、15 で持ち主が受けた「狭まる」の行だけ。

### 12.7 足さない物

- 期限・待つ長さの上限（D5）。
- 並行のゲート（3 の訳）。
- 束ね役の常駐の処理。列の先頭を取った `--land` がそのまま束ね役になれば、立てる・止める・落ちたのを見張る仕組みが要らない。
- 落ちた時の一時の場所を拾う手（11。今の版上げの道と同じ残り方なので）。

## 13. 試験の方針

`dispatch/tests/test_land.py` の今の分け方に合わせる（[internals.md](../internals.md) の試験の項）。判断の試験は試験用のクラス `FakeWorld`・`FakePorts` と git の偽物（`tests/fakegit.py`）で回す。本物の git を起動するのは、git の動きに頼る処理（重ねる・受け取る・ぶつかり）の試験（`World`・`Ports`）と、偽物の前提を確かめる `GitBoundary` だけ。

1. 固める試験（実装の前に書く。偽物で回せる物は偽物で）: 今の道の、入れた・赤・ぶつかり・取り合い（`--keep-removal` を含む）・版上げで止まる・ゲートの間にメインブランチが進んだ・push の断り（進んでいた・保護）・CI のブランチのゲート・代表の clone のそろえと知らせ・合図とその帰属（`calls.fire` に渡る属性）・`company.base`・片付け・`mode = "pr"`・`--dry-run`、の出力と終わりの値。今の試験で足りない所を足す。16 の 3 の「残る」の行は、どれもここのどれかで押さえる。
2. 判断の試験（`FakeWorld`・`FakePorts`）:
   - 顔ぶれの表（12.3）: 4.2 の条件の 1 つずつ・上限・`order` の順・後から来た札を見ない・名乗らない札で閉じる。
   - `batch` の読み: 0 以下・整数でない物が誤り、`[land.roles.<役>]` に書けば誤り（4.4）。
   - 疑いの印: 赤の束で乗った札に付き、次の束に乗らない。印が消える 2 つの条件（6.2）。
   - 束が赤で、束ね役が束の数 1 の道で回し直す（6.1）。
   - 乗る札が、取り合いのゲート・部署ごとの変更の記録の見方・版上げの見積もりで束を閉じる（4.3・7）。
   - 受け取りの場合分け（12.3）と、汚れた場所・`--keep` の断り・origin への push の断りの道（8.2）。
   - ゲートの間に乗る札が抜け、束を作り直す。見直しの後に抜けた札の処理が、「乗せた」印を見て 1 行出す（11）。
   - 合図が束ごとに 1 回で、`WORKS_LAND_MEMBERS` が渡る。15 の 4 で受けない形を選べば、cause が部署ごとに結ばれる（9）。
   - `check` に `WORKS_LAND_TIP`・`WORKS_LAND_KEY`・`WORKS_LAND_BRANCH` が渡る（5.3）。
   - CI のブランチの形での束: ゲートのブランチの名前と、比べる先（メインブランチと全員のブランチ）（5.2）。
   - `--dry-run` の束の見立てと、`--land-order` の「次の束」の印（10）。
   - `follow_main` から受け取りの手を呼ぶ（8.2 の 5）。
3. 本物の git の試験（`World`・`Ports`）:
   - 3 本が緑で 1 回のゲートで入り、3 つの部署が受け取る。
   - 2 本目がぶつかり、束が 1 本目で閉じ、2 本目は自分の順番で頼みが出る。
   - 受け取りの 3 つの場合（HEAD が元と同じ・先に進んだ・書き換えた）の git の動き。
   - 控えを書いた後・push の前に落ちた（誰も受け取らない）。push の後に落ちた（乗った処理が受け取る）。
   - 2 本目が変更の記録を書き忘れ、1 本目が同じプラグインの記録を書いていても、2 本目で束が閉じる（5.1 の部署ごとの見方）。
   - 前の束で入り、まだ受け取っていない札が、次の束に重ねられない（4.2 の 5）。
   - ゲートの間にメインブランチが進み、同じ顔ぶれで重ね直してゲートを回し直す。push が進んだメインブランチに断られ、同じく回し直す（8.1）。
   - 束ね役のブランチがもうメインブランチの先頭の上に在り、写しが元と同じ commit になる（4.3 の 2）。
4. `GitBoundary`（新しく使う git の手の、偽物の前提を本物で確かめる）: ブランチに乗らない場所での commit を渡す `git rebase --onto`（とぶつかったときの返し）、手元の変更と重なるときの `git reset --keep` の断り、`git merge-tree --write-tree` のぶつかりの返し、写しへの `--force-with-lease` の断り。
5. 2 つの処理が本当に列に並んで、束ね役と乗る処理が順に動く（列の試験 `test_landqueue` の、処理を分けて走らせる形に倣う。別の処理には偽物を渡せないので本物で）。
6. gates の側（点検の受け持ちの試験）: HEAD がブランチの頭の 2 commit 以上先なら作業ツリーから読む。乗った部署だけが変えた文書が読まれることを、赤を見てから緑にする試験で固める。環境変数が在れば推し量りより先に使う。`WORKS_LAND_TIP` が HEAD の祖先でなければ 2 で止まる。`WORKS_LAND_BRANCH` が在るとき、読み手の呼び出しの記録の部署が空にならない。
7. 変異テストは撃たない（ルートの CLAUDE.md）。

## 14. 実装の順

1. 固める試験だけを入れる。
2. `_main` を段に分ける（12.1・12.2）。15 の 3 で「残す」なら、振る舞いは何も変えない（固める試験が全部緑のまま）。「畳む」なら、変えてよいのは 16 の 1 の行だけ。
3. gates の推し量りの締めと環境変数（5.3）。works-dispatch の側の渡しと一緒に、1 つの会話で入れる。締めは束が無くても先に入れてよい。
4. `batch` と束（4〜8・11）。15 の 4・5 で選んだ形もここで入れる（帰属を部署ごとに結ぶなら `calls.fire` の口を広げる）。
5. 合図の形（9。持ち主が遅らせる形を選んだときだけ）。
6. `--dry-run` と `--land-order` の見立て（10）。
7. 文書（[land.md](../land.md) の `[land]` のフィールドと順、SKILL.md から指す別ファイル。`batch` を書く前に `check` が一時の場所で通るかを確かめること〔4.4〕を書く）。

各段は別に main に入れてよい。2 の後は今と同じ動き（「残す」のとき）で、`batch` を書かなければ 4 の後も今と同じ動き（HEAD を読む時と受け取りの判定は `batch` が 2 以上の会社でだけ替わる。16 の 2 の 1）。

## 15. 持ち主に選んでもらうこと

1. 束の上限（`batch` の既定と claude-plugins の値）: 4（推す）・8・上限なし。大きいほど詰まりは減るが、赤のときに回し直す本数が増える（6.3）。
2. 合図を打つ時: 束ごとに 1 回（推す）か、列が空になるまで遅らせて 1 回か（9）。
3. 束の数 1 の道で、今の振る舞いを残すか（12.1・16 の 1）:
   - 残す（推す）: 束の数 1 は今と同じに、部署の場所でリベースしてからゲートに出し、版上げが無ければ部署の場所で `check` を回す。狭まる物は無い。束が赤の後も同じ道を通るので、赤の部署はいつもメインブランチの上の土台で直せる。費用は、重ねる段が「部署の場所」と「一時の場所」の 2 つの場所を値で受け、その両方を試験すること。推す訳: ADR 0002 の既定は「減らさない」で、狭める得（道が 1 つになる）は、作りの簡潔さだけで、使う側の得ではない。
   - 畳む: 束の数 1 も一時の場所に重ねる。道は 1 つになる。16 の 1 の「狭まる」（赤のときに部署のブランチがメインブランチの上に無い・部署の場所にだけ在るファイルや設定に頼る `check` と push の前のフックが替わる）を受ける。
4. 束（2 本以上）で狭まる 3 つを受けるか（16 の 2）:
   - 合図の帰属（9）: 束ね役の頼みに寄せる（受ける）か、`calls.fire` を広げて部署ごとに結ぶか。推すのは部署ごとに結ぶ。CI の赤の直しの頼みが、原因でない部署の頼み元へ回るのは、頼みの流れを誤らせるため。`calls.fire` は仕組みの受け持ちの中なので、広げる費用も小さい。
   - 初見の読み手の記録の帰属（5.3）: 束ね役に寄せる（受ける）か、gates を広げて部署ごとに結ぶか。推すのは受ける。記録は費用の帰属を見るための物で、読み手は全部の文書を読むので守りは落ちない。gates（点検の受け持ち）の手間を増やすほどの得が無い。
   - 抜けた札が入りうる窓（11）: 受けるか、束をやめるか（窓は閉じる手が無いので、受けない形は束を使わないことになる）。推すのは受ける。窓は数秒で、入っても食い違いは無く（ゲートを通った中身）、抜けた処理が 1 行出して、git revert で戻せる。
5. `tests/run.sh` を変える札で束を閉じるか（5.2・4.2 の 8）: 閉じる（その札は自分 1 本で全部の試験を回し、ほかの札は全部回しを待たない）か、閉じない（束ごと全部の試験を 1 回回す）。推すのは閉じない。全部の試験は束の全員の変更を含む上位の検査で、緑なら 1 回（25 分ほど）で全員が入る。閉じると、その札の全部回しと、残りの束の 10 分前後が別に掛かる。閉じる方が勝つのは、全部回しが赤になりやすい時（赤なら束の全員が 1 本ずつに戻る）で、詰まりの長さと赤のときの損のどちらを重く見るかで替わる。

## 16. 今の道の能力の棚卸し

land.md の順の 1〜7 と、`landing.py` の `_main` の分岐（2026-10-26 の main）から 1 つずつ数えた。各行に、担う関数（まだ無い物は「まだ無い」）を書く。消える能力は、どちらの選び方でも無い。

### 16.1 束の数 1 の道（15 の 3 で変わる物）

「残す」を選べば、下の行は全部「残る」。「畳む」を選んだときに、次のように替わる・狭まる。

1. 順の 2 のリベースの時（`_rebase_here`・`land.auto_rebase`）: ゲートの前から、緑の後の受け取り（まだ無い）に移る。**狭まる**: 赤のとき、部署のブランチ（手元と origin）がメインブランチの上に載っていない。部署は古い土台で直すことになり、メインブランチとの組み合わせで起きた赤を手元で再現できないことがある。
2. 順の 4 の `check` を回す場所（版上げが無い会社。`checker(rules["check"], where)` と `_sweep`）: 部署の場所から一時の場所に移る。**狭まる**: 部署の場所にだけ在る物（git に足していない・無視されたファイル〔`.venv` など〕、初期化した submodule、worktree ごとの設定 `company.*`）に頼る `check` は、動きが変わるか落ちる。`_sweep` は要らなくなる。
3. push の前のフックが走る木（`land.advance`・`land.publish`）: 部署の場所の木から、一時の場所（候補の木）に移る。**替わる**: 候補そのものの木の決まりが走るので、`advance` の注記の「古いゲートが走る」問題はより起きない。ただし部署の場所にだけ在る物に頼るフックは、2 と同じく**狭まる**。
4. 順の 6 の回し直し（`main_again`。ゲートの間にメインブランチが進んだ・push の断りで進んでいた）: 部署の場所でリベースして回し直す形から、一時の場所で同じ顔ぶれを重ね直す形（8.1）に移る。**替わる**: 部署のブランチは回し直しの間に動かない。`queue` を書かない会社では、この回し直しがほかの `--land` との取り合いを防ぐ唯一の手なので、形が替わっても必ず残す。
5. 初見の読み手の前の回の控え（`_branch_where` の鍵）: 束ね役のブランチがメインブランチの先頭の上に無い回は、写しが元と替わって推し量りが 0 本になる。5.3 の `WORKS_LAND_KEY` が無ければ控えが効かず全部読み直す。**替わる**（費用が増える。読み落としは無い）。
6. 自分のブランチがぶつかったとき（`_rebase_here` の頼み）: **残る**。今と同じに部署の場所でリベースを試し、ゲートの前に部署のブランチと origin の部署のブランチが書き換わる。

### 16.2 `batch` を 2 以上に書いた会社で替わる・狭まる物（15 の 3 によらない）

1. HEAD を読む時（`_main` の `g.rev(path, "HEAD")`）: 列の順番を取る前から、取った後に移る（`batch` を 2 以上に書いた会社の全部の `--land`。束にならない回も含む。8.2 の 2）。**替わる**: 列で待つ間に部署が足した commit も入る。今もリベースが要る回は、リベースが部署のブランチの今の先頭を動かすので、待つ間の commit が入っている。それに揃う。
2. `check` を回す場所: 束はいつも一時の場所。**狭まる**（16.1 の 2 と同じ中身）。ただし `batch` を 2 以上に書いた会社だけで、書く前に確かめる（4.4）。束が赤の後は束の数 1 の道を通るので、赤の切り分けは 15 の 3 の選び方どおりになる。
3. 合図の頼み元と cause（`calls.fire` の `ask`・`boss`）: **狭まる**: 乗った部署の頼みに結ばれない（9）。15 の 4。
4. 初見の読み手の記録の部署と頼み（`reader_source(branch=…)`）: **狭まる**: 乗った部署の文書の読みが束ね役に結ばれる（5.3）。15 の 4。
5. Ctrl-C で列を抜けた札が入らないこと（`landqueue.Hold` の札とロック）: **狭まる**: 見直しの後・push の前の数秒に抜けた札は入りうる（11）。15 の 4。
6. 乗った部署の初見の読み手の控え: 効かない（読み直す）。**替わる**（費用。読み落としは無い）。
7. 乗った部署の部署の場所: ゲートの前にリベースされず、緑の後に写しを受け取る（8.2。まだ無い）。**替わる**。
8. `company.base` の書き込み（`provision.mark`）: 乗った部署は受け取りで進める（8.2 の 3。まだ無い）。**残る**（書く処理が替わるだけ）。
9. 部署の作業場の追いつき（`wake_hook.follow_main`）: 受け取りを呼べる形にする（8.2 の 5。まだ無い）。**残る**（呼ばないと、受け取っていない部署で止まる。それを塞ぐ）。

### 16.3 どちらでも残る物

担う関数はそのまま使い、束では束の中で 1 回か、部署ごとに同じ物を当てる。

- 順の 1: メインブランチの取り直しと「もう入っている」の片付け（`land.refresh`・`is_ancestor`・`_tidy`）。束では受け取りの判定を前に足す（8.2）。
- 部署の名前の探しと前の名前の注記（`_find`）、決まりの読みと知らない鍵の止め（`land.read_rules`。`batch` を足す）。
- 未コミットの確かめ（`ports.is_clean`）。束では乗る札にも当てる（4.2 の 4）。
- `mode = "none"`、`mode = "pr"`（`land.offer_pr`。束にしない）。
- `--dry-run`（`_preview`）。束の見立てを足す（10）。
- 順の 2a: 書き換えの取り合い（`_overwrite_gate`・`land.taken`）と `--keep-removal`。束では部署ごとに当てる（4.3 の 3）。
- 順の 3: 版上げ（`bump.make`）と中身の無い版で止める。束では部署ごとの見方を足す（5.1）。
- 順の 4: CI のブランチのゲート（`land.gate_branch`・`land.ci_on`・`land.publish`・`land.wait_gate`・`run_failure`）。束では比べる先を全員のブランチに広げる（5.2）。
- 順の 5: 赤の頼み（`_ask`・`land.red_text`）。
- 順の 6: push の断りの分け方（進んでいれば回し直し、保護・認証なら止める）、代表の clone のそろえと窓口への知らせ（`_follow`・`_tell_desk`）、ゲートのブランチの片付け（`land.drop_gate`）。
- 合図を呼ぶこと（`after` から `calls.fire`）。束では 1 回（帰属は 16.2 の 3）。
- 順の 7: 部署の片付けと入れた印（`_tidy`・`clean.departments`・`clean.retire`・`company.landed`）。
- 一時の場所の片付け（`_main` の `finally` の `land.unstage`・`shutil.rmtree`）。落ちた時の残り方も今と同じ（11）。
- 列: 札・名乗り・`order`・待つ間の行・Ctrl-C で札を消す（`landqueue`）。
