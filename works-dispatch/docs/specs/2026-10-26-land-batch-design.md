# --land の列をまとめて 1 回だけ検査する（まとめ検査）の設計

2026-10-26、窓口（本社で持ち主と話して部署に仕事を配る会話）の受付 20261026-090710-ed0ca2（部署への頼みの記録。番号で引く）を受けて、部署「仕組み」が書いた設計書。`--land`（部署のブランチをメインブランチに入れる works-dispatch のコマンド。中身は [land.md](../land.md)）の列に並んだブランチを重ねて、手元のゲートを 1 回だけ回す形（手元の merge queue のまとめ検査）を足す。持ち主の言葉は「おｋ。なら細かく設計書を書き上げておいて。綺麗に作るための工夫も。あ。worksfacotryの設計レビューに依頼してみようかそれで」。

急ぎではない。今の列は壊れていない（1 本ずつ正しく入る）。遅いだけで、2026-10-26 の夕方には 5 本が重なり、1 本 10 分前後のゲートを 1 本ずつ回して 30 分以上詰まった。

作るのは設計だけで、コードは直していない。実装は、持ち主が 15 の分かれ目を選んだ後に別の頼みで出す。読み手は works-dispatch の実装者と、列の動きを知りたい部署。

## 0. 言葉

- **列**: 会社の形（`.claude/company.toml`）の `[land]` に `queue` を書いたときに在る、メインブランチへ入れる順番待ち。置き場は共通の `.git` の下のフォルダ（claude-plugins では `.git/land-queue`）。実装は `dispatch/nodes/landqueue.py`。
- **札**: 列に申し出た 1 本ごとに置き場に作るファイル（`<20 桁の時刻>-<pid>.ticket`）。`--land` の札は横の `.who` に部署の名前とブランチを書いて名乗る。`--queue-run`（works-dispatch の外のツールが列に並んで 1 つのコマンドを走らせる入口）の札は名乗らない。
- **先頭**: 列の `lock` のファイルを持ち、リベース・ゲート・push を進めている `--land` の処理。
- **ゲート**: メインブランチに入れる前に必ず通す検証。claude-plugins では `[land]` の `check`（`bash scripts/light-check.sh && python3 tests/land-check.py && python3 gates/hooks/coldread-gate.py branch-check …`）を手元で回す。
- **候補**: ゲートに出し、緑ならメインブランチにする commit。
- **束**: この設計で足す物。列の先頭と、その後ろに待っている札のいくつかを、1 つの候補に重ねた物。
- **束ね役**: 束を作ってゲートを回す `--land` の処理。列の先頭を取った `--land` がなる。
- **乗る札・乗る部署**: 束ね役が束に入れた、後ろの札とその部署。
- **重ねる**: 一時の場所（ブランチに乗らない git worktree）で、メインブランチの先頭の上に、各部署のブランチの commit を順に `git rebase` で写していくこと。写した commit は元の部署のブランチとは別の commit になる。
- **受け取る**: 束がメインブランチに入った後、乗った部署が、自分のブランチを束の中の自分の写しに置き換えること（8.2）。
- **束の控え**: 束ね役が push の前に列の置き場に書く JSON（8.1）。誰が何で入ったかの唯一の記録。
- **疑いの印**: 赤だった束に乗った札に付ける印（6.2）。印のある札は、次の束に乗らない。
- **初見の読み手のゲート**: `check` の中の `coldread-gate.py branch-check`。メインブランチから分かれた所からの差分で変えた文書を、AI の読み手に初見で読ませる。gates（部署「点検」の受け持ち）の物。

## 1. 結論

1. `[land]` に `batch = <数>` を足す。束の上限の本数で、既定は 1（今と同じ 1 本ずつ）。`queue` を書いた会社でだけ効く。上限は 4 を推す（15 で持ち主が選ぶ）。
2. 列の先頭を取った `--land` が束ね役になり、自分と、後ろに待っている名乗った札を順位の順に、上限まで一時の場所に重ねる。重ねている間、部署の場所（部署の worktree）には触らない。
3. 重ねた上に版上げの commit を 1 つ作り、ゲートを 1 回だけ回す。緑なら fast-forward で push し、束の全部が一度に入る。
4. 赤なら束をほどき、全員が今の 1 本ずつの道に戻る（Homu・bors の rollup の扱いに倣う。二分探索はしない。6）。赤の束に乗った札には疑いの印を付け、次の束に乗せない。
5. 重ねられない物（ぶつかる・書き換えの取り合い・版上げで止まる）に当たったら、そこで束を閉じる。その札は自分の順番で、今の 1 本ずつの道を通る。列の順は追い越さない。
6. 乗った部署の処理は、自分の順番が来たら束の控えを読み、自分の写しがもうメインブランチに入っていれば受け取って終わる（数秒）。どの処理も、自分の部署の場所にしか書かない。
7. 合図（`[[land.after]]`）は束ごとに 1 回。列が空になるまで遅らせる形も書いた（9。持ち主が選ぶ）。
8. 初見の読み手のゲートは、重ねた差分に 1 回当てる。そのために、`--land` から gates に「どの commit がどのブランチの物か」を環境変数で渡す直しが要る（5.3。点検の受け持ちに掛かる）。
9. 今の 1 本ずつの道は「束が 1 本の場合」として同じコードに畳む（12）。5 本が並んだときのゲートは、乗れる物が全部乗れば 5 回から 2 回になる（上限 4 のとき）。

## 2. 背景と崩さない決まり

- 「main の CI は待たない」（持ち主 2026-10-16。リポジトリのルートの `docs/adr/0073-land-bumps-and-no-tags.md`）: 束にしても、緑の判断は手元のゲートだけで、push の後の CI は待たない。
- 「手元のゲートを外さない」（2026-10-20 に外して main が壊れた）: 束の候補は、入る中身の全部（全員の commit と版上げ）を持った木で、ゲートはその木で回す。束に入っていない中身がメインブランチに入ることは無い。
- 期限を足さない（[internals.md](../internals.md) のチェック D5）: 束ね役も乗る札も、待つ長さに上限を置かない。今の列と同じく止めるのは人の Ctrl-C。
- ノードはほかのノードや入口の層を import しない（D3）。外へ書く関数は決まったノードからだけ呼ぶ（D4。`dispatch/tests/fences.py` の `WRITES`）。
- 列の作りは works-dispatch の 1 か所（`nodes/landqueue.py`）に持つ。`--queue-run` で並ぶ外のツールに札の形を写させない（[land.md](../land.md) の `--queue-run` の項）。

## 3. 手本と比べる

| 手本 | 重ね方 | 赤のとき | ぶつかり |
|---|---|---|---|
| Homu（rust の bors） | 1 本ずつ auto で検査 | main に触らない | — |
| rust の rollup | 人が選んで 1 つの PR に | 犯人を外して作り直す | — |
| bors-ng | 1 つの merge commit | 二分して検査し直す | 束から外す |
| GitLab merge train | 前の物を全部含めて並行 | 外して後ろを作り直す | 列から外す |
| この設計 | 一時の場所に順に rebase | ほどいて 1 本ずつ | そこで束を閉じる |

- bors-ng は、束が赤で 2 本以上なら二分する（bors-ng の `lib/worker/batcher.ex` の説明「bisected (if it failed and there are two or more patches in it)」）。束の上限は `max_batch_size` で決める（[bors の文書](https://bors.tech/documentation/)）。
- GitLab の merge train は、各 MR に「前の MR を全部含めた」パイプラインを最大 20 本並べて回し、赤の MR を外して後ろのパイプラインを作り直す。ぶつかった MR も外し、リベースして入れ直させる（[GitLab の文書](https://docs.gitlab.com/ci/pipelines/merge_trains/)）。
- rust の rollup は、赤なら犯人の PR を外して rollup を作り直し、分からないときは疑わしい PR を `rollup=never` にして 1 本ずつ検査させる（[rust の rollup の手順](https://forge.rust-lang.org/release/rollups.html)）。
- Homu は auto のブランチで 1 本ずつ検査し、緑で main を fast-forward、赤なら main に触らない（[merge queue の歴史](https://mergify.com/blog/the-origin-story-of-merge-queues)）。今の `--land` はこの形。

この設計が合わせる所: 候補に入る中身の全部をゲートに掛ける（全員）、緑で fast-forward（Homu・bors）、赤なら main に触らない（全員）、上限を置く（bors の `max_batch_size`、GitLab の 20）。合わせない所: GitLab の並行のパイプライン。手元のゲートは 1 台の機械で回り、10 分前後で機械を使い切るので、並べると全部が遅くなる（ルートの CLAUDE.md の「並べすぎない」）。並べられないので、merge train の「前の物を含めた候補を本数ぶん作る」形は取らず、bors の「束に 1 つの候補」の形を取る。

## 4. 束の作り方

### 4.1 誰が束ね役になるか

- 列の先頭を取った `--land`（`landqueue.Hold.take` が戻った処理）が束ね役になる。新しい役の処理や常駐の処理は作らない。束ね役が終わって列を抜ければ、次の札が先頭を取る。
- `batch` が 1 なら束を作らず、自分 1 本の束として同じ道を通る（12.1）。

### 4.2 どの札が乗るか

束ね役は、先頭を取った時点で待っている生きた札を、列の順位（`order` の指定の後に申し出た順。`landqueue._ranked` と同じ）で前から見て、次の条件を全部満たす間だけ乗せる。満たさない札に当たったら、そこで束を閉じる（その後ろは見ない）。

1. 名乗った札である（`.who` が在る）。名乗らない札（`--queue-run`）は中で何をするか分からないので、越えない。
2. 名乗りのブランチが今も在り、その部署の場所が見つかる（部署の名前とブランチは `.who`、場所は `ports.places` から引く）。
3. その部署の役で読んだ取り込みの決まり（`mode`・`gate`・`check`・`bump`・`main`）が束ね役と同じ。役ごとの `[land.roles.<役>]` で決まりが違う部署は、違うゲートを通る約束なので、同じ束に入れない。bors-ng の「priority の違う PR は束ねない」と同じ考え。
4. 部署の場所に未コミットの変更が無い（`ports.is_clean`。今の `--land` の確かめと同じ）。
5. ブランチがまだメインブランチに入っていない。入っていれば、その札は自分の順番で片付けに進むだけなので、乗せずに先へ見る（閉じない）。
6. 疑いの印が無い（6.2）。
7. 上限（`batch`）に届いていない。束ね役を 1 本に数える。

- 先頭を取った後に申し出た札は見ない。束の中身は先頭を取った時点で決め、ゲートの間に増えない。後から来た札は次の束になる。
- 束ね役は乗る札の部署の場所を読むだけで、書かない（読むのは HEAD・属性・未コミットの有無）。
- 4.2 の 5 だけが「飛ばして先へ見る」で、ほかは「そこで閉じる」。列の順（判断役が `--land-order` で決めた順を含む）を追い越さないため。merge train はぶつかった MR を外して後ろを進めるが、この列の `--land-order` は「名を書いた順に通る」を約束しているので、追い越しを入れるとその約束が崩れる。閉じても損は小さい: 閉じた札は次の先頭になり、そこから次の束が始まる。

### 4.3 重ね方

1. 一時の場所を 1 つ作り（`land.stage`。今の版上げと同じ）、origin のメインブランチの先頭に置く。
2. 束ね役から順に、各ブランチの commit（メインブランチとの分かれ目からブランチの先頭まで）を、一時の場所の先頭の上へ `git rebase --onto` で写す。ぶつかりは今の `land.auto_rebase` と同じ物だけを機械で解く（git rerere と、変更の記録の `## [Unreleased]` の頭。[land.md](../land.md) の順の 2）。ここは `auto_rebase` の「ぶつかりを解いて続ける」の繰り返しを関数に分けて、部署の場所でも一時の場所でも使う（12.4）。
3. 写すたびに、その部署の書き換えの取り合いのゲート（今の順の 2a。`land.taken`）を当てる。since はその部署の `company.base`、main は写す前の一時の場所の先頭、head は写した後の先頭。当たったら、その部署で束を閉じる（7）。
4. 写すたびに、版上げの見積もり（`bump.plan`）を一時の場所で回す。中身の無い版で止まる形（`BumpError`）になったら、その部署を外して束を閉じる（5.1）。
5. 各部署について、写す前のブランチの先頭（元）と、写した後の一時の場所の先頭（写し）を覚える。8.1 の控えに書く。

束ね役のブランチが既にメインブランチの先頭の上に在れば、写しは元と同じ commit になる（git の rebase は動かす物が無ければ commit を作り直さない）。

### 4.4 上限

- `batch` は 1 以上の整数。0 以下・整数でない物は決まりの誤りで止める（今の `[land]` の読み方 `land.read_rules` の problems に足す）。
- 役ごとの `[land.roles.<役>]` には書けない（`queue` と同じく、列は clone ごとに 1 つなので）。
- 推す値は 4。訳: 赤のときの損が上限に比例する（6.3）。2026-10-26 の詰まりは 5 本で、上限 4 なら 2 回のゲートで済む。bors の文書も rust の rollup も「束は大きくしすぎない」と書く（rust の手順「Massive rollups are rarely needed」）。持ち主に選んでもらう（15 の 1）。

## 5. ゲート

### 5.1 版上げ

- 重ねた先頭の上に、版上げの commit を 1 つだけ作る（`bump.make`）。束の中の全員の変更を 1 回で見るので、上げ幅は各プラグインごとに束全体の変更から決まる（今の決め方そのまま。Added などが 1 つでも在れば minor）。
- 版上げの commit は束に 1 つ。乗った部署ごとに版を上げない。marketplace は版が変わった時だけ中身を取り直すので、束の中の全員の変更は 1 つの版で利用者に届く。
- `bump.make` の今の止まり方（中身の無い `## [Unreleased]`）は、4.3 の 4 で部署ごとに先に見て、その部署で束を閉じる。束ね役自身で止まれば、今と同じに `--land` 全体を止める。

### 5.2 手元の検証

- `check` を一時の場所で回す（版上げが無い会社でも一時の場所で回す。今は版上げが無いと部署の場所で回し、後から足されたファイルを `_sweep` で消している。一時の場所に統一すれば `_sweep` は要らない）。
- `tests/land-check.py`（メインブランチとの分かれ目から変わったファイルに当たる試験だけを回す）は、束全体の差分に当たる試験を回す。束が大きいほど回る試験は増えるが、同じ試験を本数ぶん回すよりは少ない。
- `scripts/light-check.sh` は、緑なら候補の木の印（共通の `.git` の `light-check-ok/<木>`）を残し、push の前のフックがその印で検査を飛ばす。束でも候補の木は 1 つなので、そのまま効く。
- CI のブランチのゲート（`gate = "release/*"` の形）も、候補の commit を出す所は同じなので、束にできる。

### 5.3 初見の読み手のゲート（gates の直しが要る）

今は壊れていない。束を入れると壊れる余地がある。

- 今の動き: `branch-check` は一時の場所（ブランチに乗らない HEAD）で回ると、「HEAD から辿れて、分かれ目から辿れないブランチ」が 1 本だけのときに、そのブランチを前の回の控えの鍵にし、文書の字をそのブランチの頭で読む（`gates/hooks/coldread-gate.py` の `_branch_where`。版上げの commit が書き換える `CHANGELOG.md` を読まないための工夫。受付 9d73b4）。
- 束での壊れ方: 束ね役のブランチがメインブランチの先頭の上に在ると、束ね役のブランチだけが当たる。乗った部署の写しはどのブランチからも辿れない。すると、束ね役と乗った部署の両方が変えた文書を、束ね役のブランチの頭（乗った部署の変更を含まない字）で読んでしまう。前の回の控えも束ね役のブランチの鍵に混ざる。束ね役も写し直されたときは 0 本が当たり、控えを使わずに作業ツリーから読む（正しいが、毎回全部読み直す）。
- 直し方: `--land` が `check` を回すときに、環境変数で「文書を読む commit」と「控えの鍵」を渡し、`branch-check` はそれが在れば `_branch_where` の推し量りより先に使う。
  - `WORKS_LAND_TIP`: 版上げの前の、重ねた先頭の commit（文書をここで読む）。
  - `WORKS_LAND_KEY`: 控えの鍵にするブランチの名前。束が 1 本なら部署のブランチ（今と同じ控えが効く）。2 本以上なら束ね役のブランチに束の印を足した物（乗った部署の文書は控えなしで読む）。
- 費用: 束では、乗った部署の変えた文書を控えなしで読むので、AI を起動する回数は 1 本ずつのときの合計と同じくらい。ゲート全体の時間は、試験の側が束で減る分だけ減る。
- この直しは gates（点検の受け持ち）と works-dispatch（仕組みの受け持ち）の両方に掛かり、片方だけ入れると食い違う（環境変数を渡しても読まない・読むのに渡さない）。実装の頼みでは、1 つの会話で通しで直して入れ、触った受け持ちを納品に書く（担当の役の本文の決まり）。束（`batch` が 2 以上）は、gates の側が入るまで効かせない（14 の順の 3 を 4 より先にする）。

## 6. 赤のとき

### 6.1 ほどき方

1. 束のゲートが赤なら、メインブランチには触らない（全員の手本と同じ）。
2. 束が 1 本なら、今と同じに部署に失敗の要点を頼んで止める。
3. 2 本以上なら、束をほどく。束ね役は、自分 1 本の束でゲートを回し直す（同じ順番のまま。列を抜けない）。緑なら入れ、赤なら今と同じに自分の部署に頼んで止める。
4. 乗った部署の処理は、自分の順番が来ると、今の 1 本ずつの道を通る（疑いの印があるので束にならない）。

### 6.2 疑いの印

- 列の置き場の `suspects`（1 行に 1 つ、ブランチの名前と、赤だった時の写す前の先頭の commit）に足す。
- 印のある札は 4.2 の 6 で束に乗らない。束ね役になったときも、自分 1 本の束にする。
- 印が消えるのは、そのブランチがメインブランチに入ったとき（その `--land` が消す）か、ブランチの先頭が印の commit から動いたとき（部署が直して push し直した。印は当たらなくなるので、見る側で読み飛ばし、次に書く処理が掃除する）。

### 6.3 二分探索を採らない訳

- bors-ng は二分する。束が大きく、検査が CI の上で並べられるなら、二分は赤の犯人を早く見つける。
- この列では、上限が 4 前後と小さく、ゲートは 1 台の機械で 1 本ずつしか回せない。束 4 本の赤で犯人が 1 本のとき、二分は「前半 2 本 → 当たった側の 1 本」で 2〜3 回、1 本ずつは最悪 4 回で、差は 1〜2 回。犯人が 2 本以上だと二分の回数は増え、差はさらに縮む。
- 1 本ずつは今の道そのもので、赤のときに頼む相手（その部署）も今と同じに決まる。二分は「束の一部をもう一度束にする」形を足すので、コードと試験が増え、途中で落ちたときの戻し方も増える（12 の「状態を減らす」に反する）。
- 束ね役が先に自分 1 本を回すのは、束ね役が列の先頭を持ち続けていて、自分のブランチをそのまま回すのが一番状態が少ないから。rust の rollup の「疑わしい物は 1 本ずつ検査させる」と同じ扱い。

## 7. 重ねられない物

| 当たった物 | 束ね役なら | 乗る札なら |
|---|---|---|
| ぶつかり（機械で解けない） | 今と同じく部署に頼んで止める | そこで束を閉じる |
| 書き換えの取り合い（2a） | 今と同じく止める | そこで束を閉じる |
| 版上げで止まる | 今と同じく止める | そこで束を閉じる |

- 束ね役のぶつかり: 今の `_rebase_here` と同じく、部署の場所でリベースを試し、解けなければ部署に頼んで止める（部署の会話に答えを返すのは今と同じ道）。重ねる段で当たったときに、部署の場所でもう一度リベースを試す形にする（部署の場所でのリベースは、ゲートの前に部署の場所に触る唯一の場合）。
- 乗る札で閉じたとき、その札は次の先頭になって自分の道を通るので、ぶつかりの頼み・取り合いの止まり（`--keep-removal` で通す道も含む）・版上げの止まりは、全部今の道がそのまま出す。束ね役は乗る札の部署に何も頼まない（自分の部署の外に書かない。12.5）。
- 書き換えの取り合いを束の中で見る訳: 乗った部署どうしでも、片方が先に入れた行をもう片方が消すことがある。部署ごとに「写す前の一時の場所の先頭」を main に見立てれば、束の中で先に重ねた部署の行も守られる。

## 8. 緑のときと受け取り

### 8.1 束の控え

- 緑なら、push の前に列の置き場の `batches/<束ね役の札の名>.json` に書く（置き換えで書き、途中で読まれても半端な中身を見せない。`landorder.write` と同じ書き方）。
  ```json
  {"main_before": "<重ねる前のメインブランチの先頭>", "candidate": "<版上げの commit>",
   "members": [{"ticket": "<札の名>", "name": "<部署の名前>", "branch": "<ブランチ>",
                "original": "<写す前の先頭>", "stacked": "<写しの先頭>"}]}
  ```
- 控えは「書いた」だけでは何も約束しない。入ったかの正は、いつも「写しがメインブランチの祖先か」（`git merge-base --is-ancestor`）で決める。控えは、どの写しが誰の物かを引くためだけに使う。push の前に落ちても、控えに書かれた写しはメインブランチに無いので、誰も受け取らない。

### 8.2 受け取り

1. 束ね役は push した後、自分の部署の場所で受け取る（下の 2 と同じ手）。
2. 乗った部署の `--land` は、順番を取った後に部署の場所の HEAD を読み直し（今は順番を取る前に読んでいる。束の後では HEAD の意味が変わるので、取った後に読む）、束の控えから自分の札かブランチの行を探す。行の写しがメインブランチの祖先なら、受け取る:
   - HEAD が元と同じ: `git reset --keep <写し>` で部署のブランチを写しに替える。origin の部署のブランチも `--force-with-lease`（元を期待値にして）で写しに替える（今の `auto_rebase` の `push_rebased` と同じ）。
   - HEAD が元より先に進んでいる（束に乗った後に部署が commit を足した）: `git rebase --onto <写し> <元>` で足した commit だけを写しの上に移し、そのまま今の道（ゲートから）を続ける。
   - それ以外（元を含まない。部署が書き換えた）: 受け取らず、今の道を通る（中身がメインブランチに入っていればリベースで消え、残りだけが入る）。
3. 受け取ったら、`company.base` を束の候補に進め、片付け（`_tidy`）に進み、「束（束ね役 <部署>）でメインブランチに入った」と 1 行出して終わる。合図は出さない（9）。
4. 受け取りに使う git の手は、部署の場所でしか打たない。束ね役は乗った部署の場所を書かない。

## 9. 合図（`[[land.after]]`）

- 束ね役だけが、push の後に 1 回打つ。乗った部署は打たない。合図に渡す部署の属性は束ね役の物で、束の部署の一覧を環境変数（`WORKS_LAND_MEMBERS`。部署の名前を改行で区切った物）で足す。claude-plugins の合図（配布・CI の見張り・工場の版の見張り）は、どれもメインブランチの先頭を見るだけなので、1 回で足りる。
- 持ち主が選ぶもう 1 つの形（15 の 2）: 列が空になるまで遅らせる。push した処理が置き場に `after-pending` を書き、列を抜けるときに後ろに名乗った札が居なければ自分で打って消す。居れば打たずに残し、後ろの処理が同じ手で引き継ぐ。落ちた処理の残した印は、次の `--land` が抜けるときに拾う。配布の回数は減るが、最初に入った変更が利用者に届くのが列の終わりまで遅れ、状態が 1 つ増える。

## 10. --land-order・--queue-run・--dry-run との関係

- `--land-order`: 束は列の順位の前から作るので、判断役が `order` で前に出した札がそのまま束の前に入る。今先頭で進んでいる束は止めない（今の「次の 1 本から効く」と同じ）。一覧に「次の束」の印（束ね役の次から上限まで、4.2 の条件で見積もった物）を添える。見積もりは読むだけで、束の中身を約束しない。
- `--queue-run`: 名乗らない札で束を閉じる（4.2 の 1）。外のツールの push を束の中に混ぜない。外のツールが先頭のときは今と同じに 1 本で走る。
- `--dry-run`: 束を作るかの見立て（乗る札・閉じた訳・上げる版の見積もり）を、一時の場所を作らずに出す。重ねる見立てに要るぶつかりの有無は `git merge-tree --write-tree`（作業ツリーを変えずに merge の結果を出す。[git merge-tree](https://git-scm.com/docs/git-merge-tree)）で見積もり、当たらなかったぶつかりは本番の rebase で出る（見積もりなので外れうると出す）。

## 11. 止まった・落ちた時

| 落ちた所 | メインブランチ | 残る物 | 次に起きること |
|---|---|---|---|
| 重ねる途中 | 変わらない | 一時の場所 | 次の `--land` が古い一時の場所を消す |
| ゲートの途中 | 変わらない | 一時の場所 | 同じ |
| 控えを書いた後・push の前 | 変わらない | 控え・一時の場所 | 写しが祖先でないので誰も受け取らない |
| push の後・受け取りの前 | 束が入った | 控え | 乗った部署は自分の順番で受け取る |
| 乗った処理が受け取る前に落ちた | 束が入った | 控え | その部署の次の `--land` が受け取る |

- 一時の場所は `dispatch-land-` の頭の名前で作る。`git worktree prune` と、`land.unstage` の残りを `--clean` が見つけて消す（今の版上げの一時の場所と同じ扱いに寄せる）。
- 乗った部署が `--land` を打ち直さないまま残っても、メインブランチには中身が入っていて、部署のブランチだけが古い。次にその部署が `--land` を打てば 8.2 で受け取り、打たなくても、`wake_hook.follow_main`（永続の部署の作業場をメインブランチに追いつかせる待ち受けの手）は「作業場のブランチにメインブランチに無い commit が在る」と見て止まる。ここは受け取りの手を `follow_main` からも呼べる形にして塞ぐ（受け取りの関数をノードに置き、どちらからも呼ぶ）。
- 束の控えは、束の全員がメインブランチに入った（受け取った）か、写しがメインブランチの祖先でない（push されなかった）と分かった時点で、見た処理が消す。消し忘れても、正は祖先の判定なので、誤って受け取ることは無い。
- 束ね役が Ctrl-C で止められたとき: push の前なら何も入っておらず、乗った札は自分の順番で今の道を通る。push の後なら、受け取りは乗った部署の側がするので、束ね役が途中で止まっても欠けない。
- 乗る札の処理が、束ね役がゲートを回している間に Ctrl-C で抜けた（札が消えた）とき: 束ね役は push の前に札の生死を見直し、消えた札が在れば、その部署から後ろを外して束を作り直す（ゲートを回し直す）。抜けた人は入れないつもりなので、勝手に入れない。

## 12. 綺麗に作るための工夫

### 12.1 1 本ずつの道を「束が 1 本」の場合に畳む

- 今の `_main` は「部署の場所でリベース → 版上げ → ゲート → push」で、束は「一時の場所に重ねる → 版上げ → ゲート → push → 受け取り」。束の数が 1 のときにも後者を通す形にすれば、道は 1 つになる。
- 畳むと、1 本ずつの道の振る舞いが次のように変わる。どれも意図した替わりで、実装の前に持ち主の確かめは要らない（どれも今の決まりの中の作りの替わりで、入る中身は変わらない）。
  - 部署のブランチのリベースが、ゲートの前でなく緑の後（受け取り）になる。ゲートの途中で止まっても、部署の場所は動いていない。
  - 版上げの無い会社でも、ゲートを一時の場所で回す。`_sweep` が要らなくなる。
  - push を部署の場所でなく一時の場所から打つ。push の前のフックは候補の木の物が走る（今は部署の場所の木の物。今の `advance` の注記の「古いゲートが走る」問題は、一時の場所が候補そのものなので、より確かに起きない）。
  - 自分のブランチがぶつかるときだけ、今と同じに部署の場所でリベースを試す（7）。

### 12.2 段に分ける

`_main` を次の段の関数に分け、各段は前の段の結果（値）だけを受け取る。

1. 選ぶ（`select`）: 列の札と部署の場所を読み、束の顔ぶれを決める。読むだけ。
2. 重ねる（`stack`）: 一時の場所を作り、顔ぶれを順に写す。閉じた所と訳を返す。
3. 版を上げる（`bump`）
4. ゲート（`gate`）
5. 出す（`publish`）: 控えを書き、push する。
6. 受け取る（`adopt`）: 自分の部署の場所だけを替える。
7. 後始末（`finish`）: 合図・`company.base`・片付け・控えの掃除。

### 12.3 決めるだけの関数を分ける

- 束の顔ぶれを決める関数は、札の並び・各札の部署の状態（決まり・未コミット・入ったか・疑いの印）・上限を受け取って、(乗る札の並び, 閉じた札, 閉じた訳) を返すだけにし、ファイルも git も触らない。表の形の試験（入力と答えの行を並べた試験）で 4.2 の条件を全部固める。
- 受け取りの 3 つの場合分け（8.2）も、(HEAD, 元, 写し, 祖先か) を受け取って手の名前を返す関数に分ける。

### 12.4 部品を 1 つにする

- 「ぶつかりを機械で解いて続ける」繰り返しは、今は `land.auto_rebase` の中に在る。これを「rebase の始め方」を引数に取る関数に分け、部署の場所のリベースと一時の場所の重ねる段の両方から使う。ぶつかりの解き方が 2 つに分かれない。
- 束の控え・疑いの印の読み書きは `nodes/landqueue.py` に置く（列の置き場を知るのはここだけ。D4 の表に足す）。

### 12.5 状態は列の置き場の 1 か所に、書くのは自分の部署だけ

- 列の状態は、札・`order`・`batches/`・`suspects`（と 9 の形を選べば `after-pending`）の、置き場のフォルダの中だけに持つ。部署の属性（`company.*`）には束の情報を書かない。
- どの処理も、git で書くのは一時の場所と自分の部署の場所と origin だけ。ほかの部署の場所には書かない。部署の会話が同時に作業していても、取り合いが起きない。

### 12.6 振る舞いを先に試験で固める

実装の最初の commit は、今の 1 本ずつの道の振る舞いを固める試験だけにする（13 の 1）。12.1 の畳みはその試験を通したまま入れる（12.1 に書いた替わりの所だけ試験を直す）。

### 12.7 足さない物

- 期限・待つ長さの上限（D5）。
- 並行のゲート（3 の訳）。
- 束ね役の常駐の処理。列の先頭を取った `--land` がそのまま束ね役になれば、立てる・止める・落ちたのを見張る仕組みが要らない。

## 13. 試験の方針

`dispatch/tests/test_land.py` の今の分け方に合わせる。判断の筋は git の偽物（`tests/fakegit.py` の `FakeGit`）で、rebase とぶつかりは本物の git の一時のリポジトリ（`World`）で、偽物の前提は `GitBoundary` で確かめる（[internals.md](../internals.md)）。

1. 固める試験（実装の前に書く）: 今の道の、入れた・赤・ぶつかり・取り合い・版上げで止まる・push の間にメインブランチが進んだ・合図・片付け、の出力と終わりの値。今の試験で足りない所を足す。
2. 顔ぶれの表の試験（12.3）: 4.2 の条件の 1 つずつ・上限・`order` の順・後から来た札を見ない。
3. 本物の git の試験:
   - 3 本が緑で 1 回のゲートで入り、3 つの部署が受け取る。
   - 2 本目がぶつかり、束が 1 本目で閉じ、2 本目は自分の順番で頼みが出る。
   - 束が赤で、束ね役が 1 本で回し直し、乗った札に疑いの印が付いて次の束に乗らない。
   - 受け取りの 3 つの場合（HEAD が元と同じ・先に進んだ・書き換えた）。
   - 控えを書いた後・push の前に落ちた（誰も受け取らない）。push の後に落ちた（乗った処理が受け取る）。
   - 名乗らない札で束が閉じる。
   - 合図が束ごとに 1 回。
   - `check` に `WORKS_LAND_TIP`・`WORKS_LAND_KEY` が渡る。
   - 2 つの処理が本当に列に並んで、束ね役と乗る処理が順に動く（列の試験 `test_landqueue` の、処理を分けて走らせる形に倣う）。
4. gates の側（点検の受け持ちの試験）: 環境変数が在れば推し量りより先に使う・無ければ今と同じ。
5. 変異テストは撃たない（ルートの CLAUDE.md）。

## 14. 実装の順

1. 固める試験だけを入れる。
2. `_main` を段に分け、束の数 1 の道に畳む（12.1・12.2）。振る舞いの替わりは 12.1 の 4 つだけ。
3. gates の環境変数（5.3）。works-dispatch の側の渡しと一緒に、1 つの会話で入れる。
4. `batch` と束（4〜8・11）。
5. 合図の形（9。持ち主が遅らせる形を選んだときだけ）。
6. `--dry-run` と `--land-order` の見立て（10）。
7. 文書（[land.md](../land.md) の `[land]` のフィールドと順、SKILL.md から指す別ファイル）。

各段は別に main に入れてよい。2 の後は今と同じ動きで、`batch` を書かなければ 4 の後も今と同じ動き。

## 15. 持ち主に選んでもらうこと

1. 束の上限（`batch` の既定と claude-plugins の値）: 4（推す）・8・上限なし。大きいほど詰まりは減るが、赤のときに回し直す本数が増える（6.3）。
2. 合図を打つ時: 束ごとに 1 回（推す）か、列が空になるまで遅らせて 1 回か（9）。
