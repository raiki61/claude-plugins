# 部署の受付の設計（知らせ・順番待ち・機械窓口）

2026-10-17、窓口の頼み（受付 20261016-210036-9f1434 とその追加。持ち主の OK 済み）から、作り手（部署「割り振り：知らせの道」）が書いた設計。読み手は、works-dispatch（Claude Code の会話を部署として立て、仕事を頼み、結果を返させるプラグイン）を直す作り手と、会社の形（`.claude/company.toml`）を書く人。言葉は会社の形の設計（このリポジトリの根の `docs/specs/2026-10-16-company-shape-design.md`。以下「会社の形の設計」）に従う。どの章だけを読んでも通じるように、この文書で使う言葉を次にまとめる（言葉の説明は本文に散らさずここに足す。章だけを抜き出して読むときも、この冒頭は添えて読む）。
- **会社・会社の形**: git のリポジトリ 1 つを会社と見立てる。会社の形は、そのリポジトリの `.claude/company.toml`（役・道具・本流への入れ方 `[land]` などを書く）。
- **代表の clone**: そのリポジトリの主たる手元の clone（本社）。部署はそこから切った git の worktree に立つ。
- **部署・役**: 部署は 1 つの worktree で働く Claude Code の会話（例「割り振り：知らせの道」）。役は部署の仕事の種類（作業・担当など）。立てたまま置く常設と、頼みごとに立てて畳む都度がある。役の欄 `fresh = true` は、頼みごとに空の会話で受ける役（4.3）、`machine = true` は AI の部署を持たない役（5.4）。
- **窓口**: 持ち主と話す、代表の clone で長く生きる会話。部署を立てて頼み、納品を受ける。段取りは my_notes の会社の窓口の名前。
- **窓・herdr**: herdr は端末を区画（ペイン）に分け、複数の Claude Code を並べて外から字を打てる道具。窓は部署か窓口の会話の画面を出した区画。`attach` は裏で動く会話の画面をその区画に呼び出す Claude Code の命令。
- **番**: 会話が 1 つの入力を受けてから応答を終えて止まるまで。番の途中・番の終わり（Stop フック）と言う。
- **属性**: 場所ごとの git の設定（`git config --worktree company.<名前>`）に書く値。`company.role`（役）・`company.name`（部署の名前）・`company.boss`（頼み元）・`company.session`（会話の id）・`company.ask`（今受けている頼みの受付番号）・`company.delivered`（納品した受付番号）など。部署の worktree か、`--desk` を打った代表の clone にだけ在る。
- **頼み・納品・頼み元**: 頼みは部署に仕事を渡すこと、納品は済んだ要約を返すこと、頼み元は納品を返す先の会話。どれにも受付番号（時刻で始まる id）が付く。
- **受付箱・台帳**: 受付箱は代表の clone の `.git/company/inbox/`（頼みと納品の本文の置き場）。台帳はその中の `log.jsonl`（1 行 1 件の JSON の記録）。
- **命令**: works-dispatch の `dispatch.py` に渡す口。`--ask`（頼む）・`--deliver`（納品する）・`--desk`（代表の clone の今の会話を窓口と名付け、属性を書く）・`--tree`（会社の部署と順番待ちを木で出す）・`--land`（部署の枝を本流に入れる）。`--take`・`--withdraw`・`--first`・`--note` は 4.4・4.5、`--call` は 5.3。
- **持ち主・下回り・本流**: 持ち主はこの仕組みを使い方針を決める人。下回りは works-dispatch のこと（どの会社でも同じ部品）。本流は origin の既定の枝（main）。
- **知らせ**: 送る側が宛先の会社の台帳に足す、宛先の会話あての 1 行（3.1）。待ち受けが読んで会話に渡す。
- **待ち受けの印・生きた印**: 待ち受けが受付箱の `wake/` に書くファイル（3.2）。その会話がまだ生きていると読める印を生きた印と呼ぶ。
- **0 で終わる・2 で終わる**: 台本やフックが終了の値 0・2 で終わること。待ち受けは 2 で終わると会話を起こす（3.1）。
- **受付**: 部署が頼みを受け取る口の全体。知らせの受け取り（3 章）・順番待ち（4 章）・機械窓口（5 章）から成る。
- **待ち受け**: 部署と窓口の会話ごとに 1 つ裏で動く小さな台本（`wake_hook.py`）。台帳を見張り、知らせが来たら会話を起こす（3 章）。
- **機械窓口・道具**: 役ごとに置ける、AI を起こさずに機械で答える台本（5 章）。
- **回す**: 道具が片づけられなかった仕事を、AI の部署への頼みに変えて順番待ちに積むこと（5.4）。
- **場所**: 部署か窓口の git の worktree 1 つ。**場所の鍵**は、その worktree の `git rev-parse --git-dir` の場所（代表の clone なら `.git`、部署なら `.git/worktrees/<名前>`。どちらもフォルダ）の実の道筋の sha1 の頭 16 字。
- **試し 7.N**: 7 章の N 番目の試しの結果。

## 1. 何のために作るか

1. 知らせが人の打つ入力欄に混ざる。頼み（`--ask`）と納品（`--deliver`）は、相手の窓の入力欄に herdr で 1 行を打ち込んで知らせていた（会社の形の設計 4.5）。人が窓口に打っている途中に納品が届くと、人の文と納品が 1 つの文にくっついて届く（2026-10-17 朝、持ち主の文と納品がくっついた）。
2. 部署は頼みを 1 つずつしか受けられず、前の頼みを納品していない部署への `--ask` は止まる。頼み元が待って打ち直すしかない。
3. 機械で片づく定型の仕事にも AI を起こしている。例: claude-plugins の出荷のたびに、窓口が手で全アカウントにプラグインを配っている。持ち主の言葉は「綺麗に作ってよ。調べごと以外にも使えるんだから」。
4. 頼みごとに空の会話で受ける部署（役の `fresh = true`）は、次の頼みの前に空にしていたので、終わった会話が画面に残り、herdr に done と出続けた（持ち主の指摘。ノイズ）。

4 つは互いに絡む（順番待ちの次の 1 件を渡すのも、会話を空にするのも待ち受け、道具が片づけられなかった仕事は順番待ちに積む）ので、1 本の流れで作る。

## 2. 層の分け方

- **works-dispatch（下回り）が持つ物は、どの会社でも同じ仕組みだけ**: 知らせの待ち受け、順番待ち、道具の欄の形、道具を呼ぶ口、合図の欄、片づかなかったら AI に回すこと。
- **会社の形と、そのリポジトリが持つ物**: どの会社にどんな役・道具・合図を置くか、道具の台本そのもの、道具がどの会話に何をするか。組織を作るときに決め、下回りは何も意識しない。
- **その人の手元の設定が持つ物**: その人だけの都合（例: 打ち込まない作業場）。配布物にも会社の形にも書かない。
- 例として、この文書は claude-plugins の役「配布」と道具「全アカウントに配る」（6 章）を出すが、どちらも claude-plugins のリポジトリ（`.claude/company.toml` と `scripts/`）に置き、works-dispatch には入れない。

```
 会社の形とリポジトリ                 works-dispatch（下回り）
 ┌───────────────────────┐          ┌──────────────────────────────┐
 │ [[roles]] 配布         │   読む   │ 待ち受け（wake_hook.py）       │
 │   [[roles.tools]]      │ ───────> │ 順番待ち（受付箱の queue/）    │
 │ [[land.after]]         │          │ --call・合図・回す             │
 │ scripts/…（道具の中身） │ <─────── │ 道具の command を走らせる      │
 └───────────────────────┘  走らせる └──────────────────────────────┘
```

## 3. 知らせの受け取り（待ち受け）

### 3.1 形

- 待ち受けを張るのは、部署と窓口の場所だけ。部署は `company.role` と `company.name` の在る worktree、窓口は `--desk` がそれらを書いた代表の clone。ほかの場所では待ち受けはすぐ 0 で終わる。
- 会話の番が終わるたび（Claude Code の Stop フック）と、会話が始まる・やり直すたび（SessionStart フック。`/clear`・compact・resume を含む）に、待ち受けを裏で起こす。人が打った文で番が始まるとき（UserPromptSubmit フック。裏で走らせ、入力を遅らせない）は、その場所の待ち受けを止める（印の `token` を書き替えるだけ。前の待ち受けはそれを見て 0 で終わる）。番の途中の会話を待ち受けが起こすと、その字が会話に届くか確かめていないため。フックの欄 `"asyncRewake": true` を付けると、フックは裏で走り、終了の値 2 で終わると手の空いた会話を起こし、その stderr を会話に見せる（https://code.claude.com/docs/en/hooks の「Run hooks in the background」）。
- 宛先の名指しは「会社/名前」。名前は `company.name`、前の名前（`company.former-names`）宛ても拾う。会社の名前は会社の形の `name`、無ければ代表の clone のフォルダの名前（`--tree` と同じ）。`--ask` は今の決め方（部署の名前か「会社/役」）で部署を決めた後、その部署の名前で「会社/名前」を作る。`--deliver` の宛先は「頼み元の会社/`company.boss`」。
- 送る側は、宛先の会社の受付箱（`<代表の clone>/.git/company/inbox/`。会社をまたぐときも宛先の会社の物）の台帳 `log.jsonl` に、知らせの 1 行を足す。欄は `to`（「会社/名前」）・`id`（受付番号）・`kind`・`file`（本文のパス）・`text`（会話に渡す 1 行）・`at`。`kind` は `deliver`（納品。`text` を会話に渡す）・`note`（今受けている頼みへの足し。納品と同じに `text` を渡す。4.5）・`queued`（順番待ちに積んだ。4.2 で渡す）のどれか。`to` が文字列の行だけが知らせで、ほかの行（送った記録。`to` は辞書）は待ち受けが読み飛ばす。1 行は 1 回の追記で書く。
- 待ち受けは 1 秒ごとに台帳の大きさを見て、前に読んだ所から先の書き終わった行だけを読む。宛先違いの行は会話に渡さない（会話の費用は 0）。自分宛ての行が在れば、読んだ所を進めてから（同じ行で 2 度起こさない）、`deliver` と `note` の行は `text` を、`queued` の行は 4.2 の決まりで渡す頼みを、まとめて stderr に出して 2 で終わる。
- 窓口が働いている番の間に届いた知らせは、台帳に残り、番の終わりに張り直した待ち受けが読む（入力欄には打たない）。
- 起こしたばかりの裏の会話（`claude --bg` で起こした会話。SessionStart の source が startup）の待ち受けは、会話の記録のファイル（フックの入力の `transcript_path`。最初の文を受けたときにできる）に最初の文の行（`"type":"user"`）が書かれるまで台帳を読まずに待ち、書かれてから台帳を読んで渡す（ファイルは会話の名前などの行を先に書くので、ファイルができただけでは待ち明けない）。裏の会話の処理は、最初の文を受ける前に、Claude Code の裏の会話を管理する常駐の処理（daemon）が殺して同じ会話の id で起こし直すことがあり、それまでに渡した字は処理と一緒に消える（2026-10-18、my_notes の受付 4bae53。Claude Code 2.1.302 の daemon の記録に、処理を殺した行 `bg settled <id> (killed)` と、同じ id で起こし直した行 `claimed-spare <id> (respawn)` が在った）。待つのは、最初の文の前に渡すと届かないからではない。処理が殺されなければ、最初の文の前に渡した字も届く（同じ 2026-10-18 の試しで確かめた。7 章の 2026-10-17 の試しとは別）。待つのは、殺されたときに渡した字を失わないため。人が端末で起こした会話は待たない（daemon が起こし直さず、待つと最初の文を打つまで知らせが止まる）。
- 納品していない頼み（`company.ask`）を持つ会話の待ち受けは、どの会話でも（`--move` で起こし直した会話に限らない）、会話の記録のファイル（`transcript_path`）にその受付番号が在るかを見る。無ければ、渡した字が届かなかったと見て、頼みの本文のパスを添えて渡し直し、台帳には `handed` の行に `again` の欄（値は渡し直した訳）を付けて残す。同じ会話に同じ頼みを渡し直すのは 1 度だけで、渡し直した字も届かなかったときは、それ以上は渡さない（番ごとに同じ頼みを重ねない）。ただし、部署の会話を止めて起こし直す命令 `--move` は、起こし直しの知らせのファイル `move-brief.md` を最初の文で新しい会話に読ませるので、会話の記録に `move-brief.md` の名前が在り、そのファイルの中に受付番号が在れば、届いたと見る。この確かめは、最初の文の後に処理が殺されて渡した字が消えたときも、起こし直した会話の待ち受けで働く。記録のファイルの場所が無い・読めないときは届いたと見る（確かめられないときに渡し直すと、届いていた頼みを重ねて渡すため）。

### 3.2 待ち受けの印と、予備

- 待ち受けは受付箱の `wake/<場所の鍵>.json` に印を書く。欄は `names`（受ける宛先「会社/名前」の並び）・`session`（会話の id）・`owner`（待ち受けの親、つまりその会話の Claude Code の処理の番号）・`pid`・`token`・`place`・`since`。動いている間は 5 秒ごとにファイルの更新の時刻（mtime）を進める。印を消すのは、TERM を受けた時と、親が替わった時だけ。会話を起こして終わった時・ほかの待ち受けに替わった時・会話を空にして終わった時は残す（会話は生きていて、番の終わりか始まりに張り直すため）。読んだ所は `wake/<場所の鍵>.pos`（台帳の何バイト目まで）。
- 送る側は `wake/` の印を全部読み、宛先の名前を `names` に持つ物を探す。その会話が生きている（POSIX では `owner` の処理が在る。Windows では印の更新が 15 秒以内）なら、待ち受けが今居なくても（番の途中で、番の終わりに張り直す）知らせの行を足す。
- 生きた印が無ければ（フックの無い古い版の会話・落ちた会話・7 日の持ち時間が尽きた会話・待ち受けの誤り）:
  - 納品は、今までどおり窓の入力欄に herdr で打ち込む（予備）。
  - 頼みは 4.1 の決まり。
- Windows は生き死にを印の更新で見るので、15 秒を超える番の間は生きた印が無いと見て、納品は打ち込みに戻る（Windows では 1 章の 1 が番の間だけ残る）。
- 会話を止める（`claude stop`）か、フックの持ち時間が尽きると、Claude Code は待ち受けに TERM を送る（試し 7.6・7.5）。待ち受けは印を消して終わる。会話の処理が落ちて待ち受けの親が替わったら、待ち受けは印を消して終わる。

### 3.3 1 つの場所に待ち受けは 1 つ

- Claude Code は、新しい番が始まっても前の待ち受けを止めない（試し 7.3）。新しい待ち受けは印の `token` を書き替え、前の待ち受けは 1 秒ごとに印を見て、替わっていたら 0 で終わる。新しい物は 2 秒待ってから台帳を読み始め、前の物が読み終えた所から続ける。初めての場所は、張った時の台帳の終わりから読む。
- 待つのは、場所の属性 `company.session` の会話だけ。部署で属性に会話の id が無ければ誰でも待つ。窓口（代表の clone）は属性の会話の id が要る（代表の clone では窓口でない会話も開くので、それに知らせを横取りさせない）。この確かめは印を書く前にする（待たない会話は、窓口の待ち受けの印に触らない）。
- `/clear` などで会話の id が変わったとき: 前の待ち受けの印の `session` が属性の id で、印の `owner` が今の待ち受けの親と同じなら、同じ会話のやり直しと見て属性を新しい id に書き直して待つ。部署の id は会話の始まりのフック（role_hook.py）も書き直すが、窓口は書き直さないので、窓口はこの決まりで続く。窓口を別の処理で開き直した（`claude --resume`）ときは続かないので、その会話で `--desk` を打ち直す。
- フックの持ち時間（`timeout`）は 604800 秒（7 日）にする。asyncRewake のフックには持ち時間が効き、既定は 600 秒（上の文書の「Common fields」）。7 日を過ぎて手の空いた会話は、次の番の終わりか始まりまで、生きた印の無い会話として扱われる。

## 4. 順番待ち

### 4.1 積む

- 宛先の部署が立っていて、その部署の会話の生きた印が在る（3.2）か、未納品の頼みを持ち、その場所に待ち受けの跡（`wake/<場所の鍵>.pos`）が在れば、`--ask` は頼みを宛先の会社の受付箱の `queue/<場所の鍵>/<受付番号>.json` に積み、台帳に `queued` の知らせを足す。受付番号は時刻で始まるので、名前の順が積んだ順。中身は受付番号・宛先・本文のパス・会話に渡す 1 行・本文の指紋（sha256）・頼み元の属性（`company.boss` ほか）・積んだ時刻。
- 前の頼みを納品していない部署にも止めずに積み、受付番号と何件目かを返す。
- 同じ中身（指紋が同じ）の頼みが、その部署の順番待ちに積まれているか、今動いている（部署の属性 `company.ask-digest` が同じで未納品）なら、新しく積まずにその受付番号を返す。
- 生きた印が無く、手の空いた部署（未納品の頼みが無い）には、順番待ちに積まずに、今までどおり窓に打ち込む（積むと後で待ち受けも渡して 2 度届く）。落ちていれば `attach` で戻してから打つ。`fresh` の役は打つ前に `/clear` を打ち、空にできなければ（会話が動いている・`/clear` の後に会話の id が変わったのを確かめられない）送らずに終了の値 1 で止める。7 日の持ち時間が尽きた会話や、待ち受けの誤りで止まった会話にも、これで届く。部署の窓には人が打たないので、打ち込みで混ざる恐れは窓口より小さい。
- ただし `fresh` の役で、待ち受けの跡が在り、納品し終えていて番の途中（会話の一覧で busy。人の文で番が始まると待ち受けは止まる）の部署には、窓に打たずに順番待ちに積む（打つと、今の番が終わった後に、空にしないまま前の会話に届く）。番の終わりに張った待ち受けが空にしてから渡す。
- 待ち受けの跡が一度も無く、未納品の部署（フックの無い古い版の会話）は、渡す者が居ないので積まず、今までどおり止める。
- 機械だけの役（`machine = true`。5.4）は `--ask` で宛てられず、止めて `--call` を案内する。
- 窓に打ち込む道は、打つ前に部署の頼みの錠（4.2 の終わり）を取って属性を読み直す。部署を読んでから錠を取るまでの間に、待ち受けが順番待ちの頼みを渡していれば（属性 `company.ask` が替わった）、窓に打たずに順番待ちに積む（待ち受けの跡が無ければ止める）。錠は `/clear`・打ち込み・属性を書き終えるまで持つ。

### 4.2 渡す

積んだ頼みを渡すのは待ち受けだけ。待ち受けは、張った時と、自分宛ての `queued` の知らせを見るたびに次を順に確かめる（属性 `company.ask`・`delivered`・`cleared` の値はどれも受付番号）。

1. 部署の属性が未納品（`company.ask` が在り、`company.delivered` と違う）なら渡さない。
2. 4.3 の空にする時なら、空にして 0 で終わる（渡すのは空にした後の会話の始まりの待ち受け）。空にできなければ渡さずに待ち、5 秒ごとに空にするのを試し直す（4.3）。
3. 順番待ちの先頭（名前の順で最初のファイル）を取り（`queue/<場所の鍵>/` から消す）、部署の属性に頼み（`company.ask`・`ask-digest`・頼み元の属性・`fresh`〔役の fresh を写す。4.3 の見分けに使う〕）を書き、頼みの 1 行を出して会話を起こす。

3 は部署の頼みの錠（受付箱の `wake/<場所の鍵>.lock`。OS のファイルの錠なので、持つ処理が落ちれば外れる）を取ってから、1 を読み直して確かめる。部署の受けている頼みは属性の 1 組なので、部署の属性に頼みを書く道（ここの 3・窓に打ち込む `--ask`〔4.1〕・`--take`〔4.4〕）は、どれもこの錠の中で「未納品の頼みが無い」を確かめてから書く。錠が無いと、読んでから書くまでの間にほかの道が別の頼みを書き、前の頼みの頼み元が消えて、その納品が後の頼みの頼み元へ届く（2026-10-17 に my_notes の調べもので、待ち受けが受付 73d574 を渡した 11 秒後に、その前に部署を読んでいた `--ask` が受付 df9c5b を窓に打ち、属性を書き換えた。部署は属性を手で戻して納品した）。

### 4.3 納品して止まった時点で空にする（`fresh = true`）

- 役が `fresh = true` の部署は、納品して止まった時点で会話を空にする（持ち主の指摘。終わった会話が画面に残り herdr で done と出続けるノイズを消す）。番の終わりに張った待ち受けが、部署の属性が納品済み（`company.delivered` が `company.ask` と同じ）で、まだ空にしていない（`company.cleared` が `company.ask` と違う）のを見たら、自分の窓（herdr のペインのうち、場所がこの worktree で会話の居る物）に `/clear` を打ち、会話が空になった（`/clear` の後の会話の始まりで新しく張られた待ち受けが、新しい会話の id で待ち受けの印〔3.2〕を書いた）のを見てから、属性 `company.cleared` に受付番号を書いて 0 で終わる。`/clear` の後の会話の始まりで張った待ち受けが、順番待ちに次が在れば 4.2 で渡す。空になったのを見られなければ `company.cleared` を書かず、この待ち受けが続く（下の「空にできないとき」と同じに扱う。見られないまま 0 で終わると、後を継ぐ待ち受けが張られず、次の番まで誰も順番待ちを渡さない。2026-10-17 に my_notes のノートの手入れで約 70 分止まった）。
- 空にする時は、番の終わり（Stop）と、前の会話を持って始まった時（SessionStart の source が resume・compact。落ちた部署を `attach` で戻した時など）。空で始まった時（startup・clear）は空にしない。
- 空にできないとき: 会話がまだ動いている、窓の入力欄に字が在る、自分の会話の居る窓を 1 つに確かめられない、herdr が打ち込みを受け付けない、`/clear` を打ったが空になったのを見られない。どれも前の会話のまま次を渡さず、待ち受けが 5 秒ごとに空にするのを試し直す（2026-10-17 に my_notes の受付 6f32b7 が、26 万トークンの前の会話のまま渡った。前の版はここで次を渡していた）。順番待ちに次が在れば、渡さない訳を台帳に `held` の 1 行で残す（訳ごとに 1 度）。裏の処理が残っている（Stop フックの入力の `background_tasks` が空でない）ときは止めず、空にしないまま次を渡す（下の「子の頼みの返事を待つ間」と同じ形。裏の処理の知らせを、それを始めた会話で受ける）。試し直しは、会話の次の番が始まるまで続く。次の番は、待っている間も次の 2 つで始まるので、止まり続けない。1 つは、裏の処理（run_in_background の Bash など）が終わった時で、Claude Code がその会話を起こして番を始める。もう 1 つは、人が部署の窓に文を打った時。どちらでも、番が始まると今の待ち受けは止まり、その番の終わり（Stop）に新しく張った待ち受けが、空にするのをまた試す。窓は、窓の前のプロセスにこの会話の処理か、この会話の裏の処理へ attach した claude が居るかで確かめる。attach の短い id は、フックが継ぐ環境変数 `CLAUDE_JOB_DIR` の名前（`<設定のフォルダ>/jobs/<短い id>`）で、待ち受けは属性 `company.job` もそれに書き直す（裏の会話を起こし直すと短い id が替わり、会話の id の頭とも違う。2026-10-17 の割り振りは、属性の a5b0bc07 のまま窓を確かめられず、窓は 8c4a1102 に attach していて、40 分渡さなかった）。段取りは台帳の `held` を見て、`--take` でほかの部署へ回せる。待ち受けそのものが居なくなって止まった部署（順番待ちが在り、納品し終えているのに、待ち受けの台本が動いていない）は、`--tree` の順番待ちの行と、そこへ積んだ `--ask` が「渡す待ち受けが居ない」と出す。どちらの止まり方も、`--nudge <部署>` か、そこへ積む `--ask` が動かす（4.4）。
- 子の頼みの返事を待つ間: 部署が出して返事の来ていない頼み（子の頼み）が在る間は、頼みごとに空にする部署（`fresh = true`）は、納品し終えていても空にしない（持ち主の承認 dc0aa2。子の返事を、その頼みを出した会話で受ける）。順番待ちに次が在れば、空にしないまま次を渡し、文の頭に空にしない訳（返事を待つ子の受付）を付け、台帳の `handed` の行にも `kept` で残す。子の頼みは、出した会話の id（頼みの行の `from.session`）が今の会話と同じ物と、今の会話が始まった後（空にしないまま渡した頼みを前へたどった、最初の頼みを渡した時より後）に出した物を数える。compact・resume で会話の id が替わっても数え落とさず、次の頼みを受けた後も前の頼みの子の返事を待ち、全部閉じたターンの終わりに空にする。前の版は次も渡さずに待ち、子の先が自分の返事を待っていると輪になり、輪でない鎖（子の先が裏の処理で止まる、子が畳まれた部署の順番待ちに残る）では輪をほどく手も効かずに、2026-10-18 に割り振りと見渡しが何時間も止まった。今は、納品し終えた部署は子の返事待ちと裏の処理では止まらないので、この 2 つの待ちからは輪も鎖もできない（空にできない訳のうち、窓を確かめられない・`/clear` の後に空になったのを見られない、などで止まった部署は輪をたどる手に載らず、`--nudge` で動かす）。輪になるのは、納品していない頼みを受けたまま番を終えた部署どうしである。部署 A の子の頼みが B の順番待ちに積まれたまま、B も納品していない頼みを受けたまま番を終え、B の子の頼みが A の順番待ちに積まれている、という形である。部署は 3 つ以上でも、会社をまたいでもよい（2026-10-18 に my_notes の調べもの・ノートの手入れと、claude-plugins の割り振り・点検・見直しで起き、段取りが `--take` で回すまで 2〜6 時間止まった）。待ち受けは、納品していない頼みが在って番が終わった時に、順番待ちが在り子の頼みが在れば、子の頼みの宛先（台帳の頼みの行の `to.path`）をたどる。たどるのは、宛先も同じく止まっていて（待ち受けが居て、納品していない頼みが在る）、子の頼みがまだ宛先の順番待ちに在る線（頼んだ部署から積まれた部署への矢印）だけで、たどれる部署を全部たどる。たどった線のうち、両端の部署がどちらもこの部署へ戻ってこられる線だけを候補にする（候補の線は、どれもどこかの輪に載る。この部署へ戻れない部署へ向かう線は輪の外なので候補にしない）。候補の線の中で受付番号の一番小さい頼み（一番古く出された物）を選ぶ。輪がいくつ重なっていても、その輪のどの部署から見ても同じ線の集まりなので、どの待ち受けが見つけても同じ頼みを選ぶ。選んだ頼みは、それが積まれていた部署の会社で、`--take <受付> --ask <会社>/<既定の役> --task <積まれていた宛先の部署の名前>：<受付の末尾 6 字> --branch work/ask-<受付の末尾 6 字>` で作業の部署へ回す（4.4 の `--take` と同じ。段取りが手で打っていた物。会社と既定の役はその会社の会社の形から読み、`--take` はその会社の代表の clone で打つ）。順番待ちから取り出すのは 1 度しか通らないので、2 度は回らない。会話から切り離して走らせ、出力は見つけた部署の受付箱の `takes/` に、台帳には `knot` の行（輪の部署の名前 `chain` と輪の頼み `edges`）を残す。`--take` が 0 以外で終わったとき（取り合いで負けた・頼み直せずに順番待ちへ戻した）だけ、同じ待ち受けが最初の回を含めて 3 回まで回す（終わりの値を書くのは切り離して走らせる殻なので、Windows では回し直さない。納品していない頼みを持つ部署の待ち受けは 5 秒ごとに見直さないので、回し直すのは次に知らせが来た時）。輪が重なっていれば 1 件回しても輪が残り、回した頼みが渡って部署が動いた後の確かめで、残りを順にほどく。輪をたどる途中で何が起きても、待ち受けは止めない。子の返事は今までどおり頼みを出した会話で受け、受けた頼みごとに空にすることも変えない。
- herdr の表示: 終わった会話（done）に `/clear` を打つと idle（待機中）に替わった（試し 7.7）。
- 今まで `--ask` が次の頼みの前に打っていた `/clear` は、待ち受けの居る部署では打たない（空にするのは納品の時点に移る）。待ち受けの跡（受付箱の `wake/<場所の鍵>.pos`）の無い部署（このフックの無い古い版の会話）には、順番待ちを渡す者が居ないので、`--ask` が窓に打ち込む道（4.1）を残し、その道では今までどおり、頼みを打つ前に `/clear` を打つ（空にできなければ送らずに止める）。

### 4.4 先頭が詰まったとき

部署が納品せずに止まると、止まる前のフックが 3 回まで納品を求める。それでも納品しなければ、順番待ちはそこで止まる。`--tree` に部署ごとの順番待ちの件数を出す。順番待ちのファイルは手で動かさず、受付番号で 1 件を扱う口を使う（どれも順番待ちの在る受付箱と頼み元の受付箱の台帳に残す）。

- `--take <受付>`: 積んだ順を飛ばして今受ける。`--ask <宛先>` を添えれば、受付番号と頼み元をそのままにほかの部署へ頼み直す（`taken`）。
- `--withdraw <受付>`: 渡さずに取り下げる（`withdrawn`）。
- `--first <受付>`: その順番待ちの先頭に回す（`reordered`。追い越した件を添える）。件に回した時刻（`front`）を書き、待ち受けは回した件を回した時刻の新しい順に、ほかの件より先に渡す。渡すのは今までどおり、今の頼みの納品の後。
- `--nudge <部署>`: 渡す待ち受けが居ないか、待ち受けが渡さずに待っている（台帳のその場所の最後の行が `held`）部署を動かす（`nudged`）。窓に会話が居なければ attach で戻し、居て手が空いていて入力欄が空なら、`/reload-plugins` を打ってから、番を 1 つ回す 1 行を打つ（番の終わりに今の版の待ち受けが張り直して渡す。会話が前の版のプラグインのままだと、張り直すのも前の版の待ち受けで、同じ訳でまた止めるので、先に読み直させる。前の版かは外から確かには分からないので毎回打つ。2026-10-19 の割り振り）。待ち受けの居る部署へ積む `--ask` も、止まっていれば同じことをする。待ち受けが渡さない訳がすぐ替わる物（会話が動いている・入力欄の字）のときは打たない（待ち受けの `/clear` とぶつけない）。子の返事待ちと裏の処理を訳に `held` を残すのは今の版より前の待ち受けだけなので、打って今の版の待ち受けに張り直させる。順番待ちに頼みが残る部署は、`--clean` も `--land` の掃除も畳まない（訳は `queued`。畳むと積まれた頼みが誰にも渡らない。2026-10-18 に、畳まれた部署の順番待ちに受付 b1109e・526db7 が残った）。前は「部署の窓に 1 文打つ」と人に打たせていた。

納品できない頼みで先頭が詰まらないよう、頼み元の会話が終わった（窓が無く、会話の一覧にも生きた頼み元の会話が無い）納品は、頼み元の名前に宛てた知らせを台帳に置いて納品済みにする（`posted`）。2026-10-17 の点検は、頼み元 my-notes-ad の会話が終わった後の納品を 4 回打ち直して止まり、後ろの頼みが 5 時間渡らなかった。

### 4.5 今受けている頼みへの足し（`--note`）

番の途中の部署に、頼みの変更・足し・取り下げを届ける口。新しい仕組みは作らず、3 章の待ち受けに乗せる（持ち主の言葉「syncawake みたいなの使うんじゃないの」。`asyncRewake` のこと）。

```
python3 dispatch.py --note <受付> (--text <文> | --brief <ファイル>)
```

- 受付の頼みが順番待ちに在れば、その件の渡す 1 行の後に足しの 1 行を添える（順は替えない）。
- 部署が今受けている（属性 `company.ask` が受付で、未納品）なら、宛先の会社の台帳に `kind: "note"` の知らせを足す。待ち受けが居れば今起こし、番の途中なら番の終わりに張り直した待ち受けが読んで起こす（会話の入力欄には打たない）。4.2 の 1（未納品なら渡さない）は順番待ちの決まりで、足しは止めない。
- 待ち受けの跡（`wake/<場所の鍵>.pos`）の無い部署（待ち受けのフックの無い前の版で起こした会話）には、部署の窓に打ち込む（予備）。
- もう納品した頼みには足さず止める（新しい頼みとして `--ask` で頼む）。
- 部署は足しに別の納品をせず、今の頼みの納品にまとめる。取り下げの足しなら、そこで止めて、どこまで済んだかを納品で返す。
- 打った場所・宛先・頼み元の受付箱の台帳に `kind: "note"`（`ask` に受付、`id` に足しの受付番号）で残す。

## 5. 機械窓口（道具）

### 5.1 2 つの形

- **呼ばれて動く道具**: 会話か人が `--call` で呼ぶ。答えをその場で返す。
- **合図で動く道具**: 会社の形の出来事の欄に書いておき、その出来事の後に下回りが呼ぶ。最初の出来事は「本流に入れた」（`[land]`。5.5）。

どちらも、同じ道具の定義を同じ走らせ方で走らせ、片づかなければ同じ決まりで AI に回す。

### 5.2 道具の欄

役ごとに `[[roles.tools]]` で書く。欄の形は MCP（Model Context Protocol）の道具の定義 Tool に合わせる（https://modelcontextprotocol.io/specification/2026-07-28/schema#tool）。MCP のサーバーは立てない。各会話の文脈に道具の定義を載せないためで、要るときに `--tree` で見せる。

- `name`（要る）: MCP の Tool.name。英数字・`_`・`-`・`.` の 1〜128 字。
- `title`（任意）: MCP の Tool.title。人の読む名前。
- `description`（任意）: MCP の Tool.description。
- `inputSchema`（要る）: MCP の Tool.inputSchema。根は `type = "object"`。
- `command`（要る。ここだけの欄）: 走らせるコマンドの字。シェル（POSIX は `sh -c`）で走らせる。
- `fallback_role`（ここだけの欄）: 回す役（5.4）。

走らせ方:

- 入力は JSON の物で、`command` の標準入力に渡す。下回りが確かめるのは、物であること・`required` の鍵が在ること・`additionalProperties = false` なら知らない鍵が無いこと・`properties` の各鍵の `type`（string・number・integer・boolean・array・object）だけで、ほかの決まりは道具が自分で確かめる。
- origin の既定の枝（会社の形を読むのと同じ ref）の中身を一時の worktree に出し、その根で走らせる（会社の形と同じリポジトリの台本を相対のパスで書ける）。代表の clone の作業ツリーでは走らせない（持ち主がほかの枝を開いていることがあり、その枝に台本が在るとは限らない。0.24.0 で、配る台本が見つからなかった）。環境はそのまま継ぐ。下回りから期限は足さない。
- 機械窓口を付けてよいのは、**成功と失敗を機械で決められる仕事だけ**。道具は、片づいたら終了の値 0 と答え（標準出力）を返し、片づかなかったら 0 以外を返す。片づいたかを AI の判断に頼る仕事は、道具にせず `--ask` で頼む。

### 5.3 呼ぶ口

```
python3 dispatch.py --call <会社/役> <道具の名前> [--input <JSON の字か @ファイル>]
```

- `--ask`（AI に判断を頼む口）と分ける。会社を省けば呼んだ場所（git の代表の clone）の会社。入力を省けば `{}`。
- 片づいた: 答えを出して 0 で終わる。台帳に `{kind: "call", status: "done", role, tool}` を残す。
- 片づかなかった: 台帳に外れ `{kind: "miss", role, tool, input, code, tail}`（`tail` は標準出力と標準エラーの終わりの 20 行）を残し、その入力を AI への頼みに変えて回し（5.4）、受付番号を出して 3 で終わる。頼み元は呼んだ会話（`--ask` の頼み元と同じ決め方。`--from-name`・`--from-account` でも渡せる）。待つか、自分で進めるかは頼み元が選ぶ。頼み元が分からなければ、回したうえで「納品の返り先が無い」と出す。
- 回すこと自体ができなければ（部署を立てられないなど）、訳を出して 1 で終わる。
- 外れは台帳の `kind: "miss"` の行で数えられる。`--tree` は役ごとに道具と外れの回数を出す。
- 回す頼みの本文: 「機械の道具「<title>」（<役>/<name>）が片づけられなかった（終了の値 N）。入力: <JSON>。道具の出力の終わり: <tail>。この入力の仕事を進める。」

### 5.4 回す先

- 道具ごとに、会社の形の `fallback_role` で回す役を書ける。省けばその道具を持つ役。回す役は同じ会社の、AI の部署を持つ役（`machine = true` でない）に限る（違えば会社の形を読むときに外す）。
- 回すときは今の `--ask` の宛て方と同じ: 回す役の常設の部署が在ればその順番待ちに積み（4.1）、無ければ一度きりの部署を自動で立てる（役は回す役）。
- 自動で立てるときは人が名前と枝を渡せないので、名前は「<道具を持つ役>：<道具の title、無ければ name>」（例: 配布：全アカウントに配る）、枝は `work/<道具の name>-<受付番号の末尾 6 字>`（name は英小文字にし、英数字でない字を `-` にする）。
- AI の部署を持たない役は `machine = true` と書く（例: 配布）。その役の道具は回す役を必ず書く。書いていない道具は、会社の形を読むときに形の誤りとして外し、`--call`・`--tree`・`--land` が誤りを出す。

### 5.5 合図

出来事の欄の下に `after` の並びで書く。最初の出来事は本流に入れた後（`[land]`）:

```toml
[[land.after]]
role = "配布"
tool = "spread-plugins"
input = {}
```

- `--land` が本流へ push し終えた後に、並びの順に、`--call` と同じ走らせ方で呼ぶ（`--land` を打った処理の中で、本流に入れた後の origin の既定の枝の中身で）。片づかなければ回す。回した頼みの頼み元は、本流に入れた部署の頼み元（その部署の `company.boss` ほか）。窓口が頼んだ仕事の後片付けは窓口に返る。
- 合図で動いた結果は `--land` の出力に 1 行ずつ出す。合図が片づかなくても、本流に入れたことは取り消さず、`--land` の終了の値も変えない。`--land` を打った場所に頼み元の属性が無い（代表の clone から打ったなど）ときは、回した頼みに返り先が無いと出す。
- `mode = "pr"`（本流に入れるのは人が PR を merge する）の会社では、`--land` は本流へ push しないので合図は呼ばない。

## 6. 例: claude-plugins の役「配布」

works-dispatch の外（claude-plugins のリポジトリ）に置く。

- 役「配布」: `machine = true`、道具「全アカウントに配る」（`name = "spread-plugins"`）だけを持つ。回す役は「作業」。
- 中身（`scripts/spread-plugins.py`）: dispatch の設定のアカウントごとに `claude plugin marketplace update raiki61` と、入っている raiki61 のプラグインだけの `claude plugin update` を打つ。その後、herdr の Claude の会話のうち、**部署の会話（場所に `company.role` が在る）と窓口だけ**に `/reload-plugins` を打つ（持ち主の作業の会話に打つと herdr で done に替わりノイズになる。この決まりは組織の物なので、works-dispatch でなくこのスクリプトに置く）。入力欄に字が入っている会話は飛ばす。その人だけの除外（持ち主は `plugins1` の作業場）は手元の設定 `~/.config/claude-plugins/spread.toml` の `skip`（herdr の作業場の名前の並び）に置く。1 つでも失敗したら 0 以外で終わる（作業に回る）。
- 合図: `[[land.after]]` に「配布/spread-plugins」を書き、本流に入れるたびに配る。

## 7. 試しで分かったこと（2026-10-17、Claude Code 2.1.302・herdr 0.9.3・macOS）

1. 裏の会話（`claude --bg`）でも、asyncRewake のフックが 2 で終わると、手の空いた会話が起きて返事をした。
2. 別のアカウントからの納品で起きる: p1 のアカウントの部署の形の場所から打った `--deliver` が、main のアカウントの裏の窓口の会話を起こし、窓口が要約に返事をした（作った版の待ち受けを `--plugin-dir` で読ませた会話で試した）。
3. 新しい番が始まっても、前の待ち受けは止まらない。次の番の終わりに 2 つ目が並んで動いた（3.3 の 1 つにする決まりが要る訳）。
4. 待ち受けの親は Claude Code の処理。
5. 持ち時間: 15 秒の物は 14 秒で TERM を受けて終わり、会話は起きなかった。86400 秒の物は 12 分を超えて動き続けた（既定の 600 秒で切られない）。
6. 会話を止めると（`claude stop`）、動いていた待ち受けは TERM を受けた。
7. herdr で done と出ている会話に `/clear` を打つと、表示が idle に替わった（試しの部署で）。
8. `/clear` の後の SessionStart の asyncRewake のフックが 2 で終わると、空になった会話の番が始まった（端末を模した対話の会話で。その会話はログインの無い子で、返事の中身までは見ていない）。

確かめ残り: 窓口が番の途中に、前の待ち受けが 2 で終わったときの振る舞い（3.3 で前の物は次の番の終わりまで残るが、その間は印の token が同じなので、その待ち受けが起こすことがある）。持ち時間を 7 日まで置いたときの振る舞い（数え方の上限は文書に無い）。台帳 `log.jsonl` は増え続ける（切り替え・掃除の決まりは作らない）。

2026-10-17 に works-dispatch の `dispatch/`（試験と写しを除く）・SKILL.md・docs を読んで洗い出した。重い順。

1. **版上げ `[land] bump = "marketplace"`**（`dispatch/nodes/bump.py` 全体、`nodes/land.py` の `BUMPS`）: Claude Code のプラグインの marketplace の置き方（`.claude-plugin/marketplace.json`・各 `plugin.json`・CHANGELOG の `## [Unreleased]` と節の名前で上げ幅を決める・文書だけの直しは patch・commit の題の字）を丸ごと持つ。会社の形で選べるのは入れるか入れないかだけで、ほかの版の付け方を書く口が無い。合う会社は claude-plugins だけ。合図（5.5）の形にすれば、版上げも会社の側の道具に出せる。
2. **載せ直しの頼みの字**（`nodes/land.py` の `rebase_text`）: 版上げの決まりが無い会社にも「版を上げ直して push し直して」と頼む。
3. **納品の項目ごとの決まり**（`nodes/deliver.py` の `check`・`rules_of`）: 項目の名前が「結論」なら 3 行以内、「決め手」なら URL が要る、を名前で決め打ちしている。項目の並びは役の `deliver` で替えられるが、項目ごとの決まりを書く欄が無い。調べものの決まりで、コードの役には合わない。`--deliver` が足りないときの案内（`orders.py`）は役の項目に関係なく「結論は 3 行以内、決め手には原典の URL」と出し、止まる前のフックの差し戻し（`deliver.stop_verdict`）は役に無くても「残った疑問」に書けと言う。
4. **役の名前の決め打ち**: 窓口の役 `DESK_ROLE = "窓口"`（`reorg.py`。2026-10-17 に、会社の形の頭の `desk_role` と本社が今持つ役が無いときだけ使う形にした。役の名前を替えたときは `[[roles]]` の `former_names` で前の名前を今の役に引く）と、`--task` で役を省いたときの既定 `DEFAULT_ROLE = "作業"`（`dispatch.py`。会社の形の `default_role` が在れば効かない）。最初の文の頭「作業の頼みです。」（`dispatch.py` の `_brief_text`）も役に関係なく出る。
5. **`--init-company` の下書き**（`dispatch.py` の `COMPANY_DRAFT`）: 持ち主の組織の決まり（4 つの役・枝の名前の付け方・部署の名前の付け方・納品の項目・`--land` の後に納品・auto mode の許し）を丸ごと書く。下書きなので消せるが、ほかの形の下書きが無い。
6. **CI と PR は GitHub**（`nodes/land.py` の `ci_on`・`landing.py`・`ghx.py` の `create_pr`・`--issue` の `gh issue develop`）: 関門の CI は GitHub Actions、`mode = "pr"` は `gh pr create`。`gate = "check"` なら GitHub に頼らない。
7. **手元の無視の決まり**（`nodes/provision.py` の `LOCAL_EXCLUDES` の `__pycache__/`）: Python の会社の都合をどの会社にも足す。
8. **PR を開く流れ**（`nodes/prs.py`・`nodes/turn.py`・`claudex.py` の `/catchup` 探し・`vscode.py`）: 1 ターン目は attention の `/catchup`、2 ターン目はレビューの文で、勤め先（guided-resolver）の PR の回し方に合わせている。会社と部署の流れとは別の入口（`dispatch.py` を引数なしで打つ物）。

## 9. 受け持ちを起こす（周期と命令）

2026-10-17、my_notes の段取りの頼み（受付 20261017-032407-07ed54）から、作業の部署が足した。困っていたこと: 一度きりの部署は窓口が頼むたびに立てるので会社の形に現れず、決まった間隔で部署を起こす口も無かった。見直しの部署（my_notes の業務改革）を一度きりの作業で回すと、見られる側の窓口が、起こすかと結果の上げ先を決めてしまう。

- **書く所**: 受け持ち（`[[skills]]`）の下の `[skills.start]`。役の種類は足さない（持ち主の決めた 4 つの役のまま。どの役で起こすかは受け持ちの `role`）。受け持ちの名前が起こした部署の名前になるので、受け持ちの `description` が部署の会話の始まりに足される（role_hook.py）。欄は `skills/dispatch/references/start.md`。
- **起こす条件と起こす者**: 周期（`every`）なら `--due`、命令なら `--start`。`--start` を打って受け持ちを起こしてよい会話（打つ側）は、`by` に会話の名前を並べて絞れる（Claude Code の外から打つ人はいつでも起こせる）。どちらも窓口の判断を通らない。
- **結果の返す先**: `report_to`。起こした者の会話でなく、ここを頼み元の属性に書く（見る役を見られる側から離し、結果を統治する側に直に上げる。段取りの調べの納品 20261017-010745-886ea1 の、IIA〔内部監査人協会〕の形）。
- **宛て方**: `--ask` と同じ（宛先「会社/受け持ちの役」、部署の名前は受け持ちの名前）。常設の受け持ちは、その部署の順番待ちに積む（4.1。同じ中身なら積まない）。一度きりの受け持ちは部署を立て、枝は `work/<受け持ちの id>-<受付番号の末尾 6 字>`。前の回の部署が立っていれば起こさない（Kubernetes の CronJob の `concurrencyPolicy: Forbid` と同じ。https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/ ）。
- **周期の数え方**: 前に起こした時（受付箱の台帳の `kind: "start"`・`status: "sent"` の行）から `every` が過ぎていれば起こす。過ぎた回が幾つ有っても 1 回だけ（anacron と同じく、ずっと動いているとは限らない機械のための数え方。https://man7.org/linux/man-pages/man8/anacron.8.html ）。
- **刻む者**: 頼みと納品。入口の `--ask` と `--deliver` が通るたびに、works-dispatch が `--due` を裏で打つ。裏の `--due` は、その `--ask` か `--deliver` を打った会話から切り離して走り、`--ask` と `--deliver` はその終わりを待たない。出力は `--ask` か `--deliver` を打った場所の会社の受付箱の `due.log` に書き足す。WordPress の WP-Cron と同じ形で、時計でなく来た仕事が刻む（"WP-Cron works by checking, on every page load, a list of scheduled tasks to see what needs to be run." https://developer.wordpress.org/plugins/cron/ ）。同じ間に 2 つ走っても、会社ごとの錠（受付箱の下の `due.lock`）を持つ方だけが台帳を数えて起こし、もう一方はその会社を待たずに飛ばすので、同じ受け持ちを 2 度起こさず、待つ処理も溜まらない。裏の `--due` には打った会話の印（環境変数 `CLAUDE_CODE_SESSION_ID`・`HERDR_PANE_ID`）を渡さない（渡すと、打った部署自身の受け持ちを起こす頼みが「宛先はこの会話自身」で止まる）。前は段取りの役の本文の「番ごとに `--due` を打つ」の一文だけで刻んでいて、打ち忘れると点検が黙って起きなかった（2026-10-18、my_notes の段取りの頼み 20261018-014232-82ddd5）。OS の予定は持ち主が置かないと決めた（2026-10-17「一旦cronは不要で。」）。頼みも納品も来ない間は刻まれない（WP-Cron の "no page loads occur" と同じ穴）。その間も刻みたい人は、手元の OS の予定（launchd・cron・systemd の timer・タスク スケジューラ）に `--due` を打たせる。どの OS のどの予定を使うかは下回りに入れない（8 章と同じ考え）。launchd の `StartInterval` の仕事は眠っている間は飛ばされる（https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/ScheduledJobs.html ）が、上の数え方で起きた後の刻みに 1 回起こす。Claude Code の予定の機能は刻みに使わない: `/loop` と CronCreate は会話に結び付き、会話が閉じると止まり、7 日で切れる。クラウドの予定は手元の herdr と作業場に届かない（https://code.claude.com/docs/en/scheduled-tasks ）。
