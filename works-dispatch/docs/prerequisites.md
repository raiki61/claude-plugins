# 前提と、なぜ要るか

works-dispatch（作業ごとに Claude Code の会話を別に立てて仕事を頼む、自分の番の PR〔このリポジトリの別のプラグイン attention の `/whose-turn` が、使う人が次に手を打つ物として並べる PR〕を作業場に開いて読ませるプラグイン）の前提ごとの理由。読むだけでよく、確かめるのは `dispatch.py --check`（`dispatch/dispatch.py`）が全部やる。使い始め方と言葉（窓口〔人と話して仕事を配る会話〕・部署〔作業ごとに立てる、worktree の作業場とその中の会話の組〕・会社〔部署を立てる元のリポジトリ〕）は [README](../README.md)、使う人向けの手順の全部は [SKILL.md](../skills/dispatch/SKILL.md) と、そこから主題ごとに指す別ファイル（`skills/dispatch/references/`）。

設定のファイルの下書き（既定 `~/.config/works-dispatch/dispatch.toml`。フィールドの書き方は `skills/dispatch/references/setup.md`）は `dispatch.py --init --repo OWNER/NAME --source <代表の clone>` が書く。代表の clone は、PR や部署ごとの worktree を作る元にする、ふつうの clone（本体の checkout）。

**要る段: 2**（[tiers](../../tiers/README.md) は、プラグインが要る外のツールがそろっているかを点検する、このリポジトリの別のプラグインで、要るツールを段 0〜3 に分ける。段 2 までに入るのは Claude Code・gh・herdr・アカウントの起動コマンド）。`--check` は最初に、tiers のコマンド `tiers --tier 2 --json` に、設定のファイル（上の `dispatch.toml`）の各アカウントの起動するコマンドを `--launcher <コマンド>` で 1 つずつ足して呼ぶ（`dispatch/tierx.py`）。`--json` は機械の読む形で返させる指定。足りなければ、足りない物ごとに入れ方の行を出し、各行の下に字下げで tiers の案内（`--json` の出力の `guide`。tiers 0.2.0 から。古い tiers なら入れ方の行だけ）を出す。終わりに、同じ案内を人の読む形で見られる入口（人が打つ `/tiers:check` と、会話が Bash のツールで打つ `tiers --tier 2`。`/tiers:check` は会話からは呼べない）を 1 行添えて止まり、下の番号付きの確かめには進まない。tiers は `plugin.json` の `dependencies` で入り、Claude Code がその `bin/` を PATH に入れる。見つからない（依存の入っていない古い入れ方・Claude Code の外から走らせた）ときは、入れるコマンド（`claude plugin install tiers@<マーケットプレイス>`。このリポジトリから入れたなら `tiers@raiki61`）を注記にして、段の点検は飛ばしたまま下の番号付きの確かめを続ける。`dependencies` の依存は `claude plugin update` では入らないので、tiers を足した works-dispatch の版（0.7.0）へ update しただけのときは、この `claude plugin install` のコマンドで入れる。下の 1 と 3 と 5 は tiers の点検と重なるが、dispatch の普段の実行（PR を開く）と `--task` の実行（部署を立てる）が使う確かめなので残す。

1. **herdr が動いている。** herdr は、端末を作業場（workspace）とペインに分けて並べ、中の AI の会話を外から API で操作できるツール。手元の版の API に、PR を開く道が使う 12 の口（`dispatch/dispatch.py` の `HERDR_METHODS`。`agent.*` の 3 つ、`pane.list`・`pane.send_text`・`pane.process_info`〔コマンドを打つ前にペインの前がシェルかを見る〕、`workspace.list`・`workspace.close`、`worktree.*` の 4 つ）があることと、代表の clone の worktree を並べられることを確かめる。代表の clone は本体の checkout であること（linked worktree でない）も確かめる。
2. **Claude Code の `claude agents --json`。** 開いている会話を、アカウントごとに読む公式の口。PR を開くとき、同じリポジトリとブランチの会話が開いていれば、その PR は飛ばす。
3. **起動するコマンドと設定のフォルダ。** アカウントごとに、Claude Code を起動するシェルのコマンドと、そのコマンドが `CLAUDE_CONFIG_DIR` に入れるフォルダを書く。コマンドが `CLAUDE_CONFIG_DIR` を入れないなら、`config_dir` は書かない。書くと、信頼の記録と会話の一覧を読む場所がずれる。アカウントを切り替えない人は `accounts` を書かず、`claude` 1 つで動く。
   - `config_dir` を書かないアカウントのフォルダは、作業場のペインで新しく起きるログインのシェルが持つ `CLAUDE_CONFIG_DIR` で決める（`wiring._login_config_dir`）。無ければ `~/.claude` になる。dispatch を走らせている会話の値は使わない。dispatch はふつう、別のアカウントの会話の中から走るためである。
   - 鍵（そのアカウントの Claude Code のログインのトークン。使うのは `limits.py` の使用率の問い合わせだけ）は共通の `scripts/claude_auth.py`（リポジトリのルートに在り、プラグインは `dispatch/vendor/` の写しを使う）の `account_token` で探す。探す順は 3 段ある。最初は、利用者が作った Keychain の項目（`keychain_service`、無ければフォルダの名前から導いた `claude-code-oauth-<名>`。`~/.claude` なら `default`、`~/.claude-p1` なら `p1`）。次は、Claude Code 自身が置いた Keychain の項目。最後は、フォルダの `.credentials.json`。
   - `limits = false` は、使用率の枠の無いアカウント（Ollama、Foundry など）の印。使用率の控え（下の 8）を読まず、取り直さず、使用率で外さない。
   - `named_only = true` は、名指しのときだけ使うアカウントの印。自動の選び方（部署の起動・`--move` の移る先・区切り〔部署が次の頼みを受ける前か、`--rest` で会話を空にしてよいと印したターンの終わり〕で使用率の高いアカウントから早めに移す先・PR を開く回）に入れず、会社の形（`.claude/company.toml`。部署の役と受け持ちを書くファイル）の役（`[[roles]]`）か受け持ち（`[[skills]]`。部署ごとの仕事の範囲）に `account = "<名前>"` と書いたときと、`--move <部署> --account <名前>` で名指したときだけ使う。名指しても、使用率が上限のときと使える時間帯の外は使わない（`dispatch/nodes/accounts.py`）。会社の形の `account` で名指したのに使えないときは、ほかのアカウントで立てずに止める（そのアカウントでしか動かないモデルを役に書いたとき、黙って別のモデルで立たないため）。モデルの別名の読み替え先は、そのアカウントの設定のフォルダの `settings.json` の `env` から読んで、dispatch の `--tree`（会社と部署の一覧）と `--check`（始める前の確かめ）の出力に出す。
   - `max_open` は、会社の形の `account` でそのアカウントを名指して部署を立てるとき、そのアカウントに開いていてよい終わっていない会話の数（1 以上の整数。既定 1）。達していれば名指しを使わない。既定の 1 は、鍵 1 つで同時に 1 件しか走らない口（CheapestInference など）に合わせた数で、同時に何件も受けられる口（Foundry のデプロイなど）は、その口の流量の枠に合わせて上げる（`dispatch/nodes/accounts.py` の `prefer`）。
   - `hours` は、使える時間帯の決まったアカウントの印（例 `hours = "08:00-16:00 UTC"`。時刻の基準は必ず書く）。外と、終わりまで `hours_margin_minutes`（既定 30 分）を切った間は選ばない（`dispatch/nodes/accounts.py`）。
4. **`/catchup` を持つプラグイン。** `/catchup` は attention プラグイン（同じリポジトリのプラグイン）のコマンドで、PR のどこで止まっていたかを出す。このプラグインが要るのは、PR を開く使い方（`--task` を付けない dispatch）でだけ。この使い方で dispatch は、PR のブランチの作業場（PR ごとに作る git worktree と、それを映す herdr の画面）を作り、そこに Claude Code の会話を起動して、その会話の最初の入力として `/catchup` を送る。送る名前は dispatch が組み立てる。アカウント全体（user）に入れたプラグインの中から、`skills/catchup/SKILL.md` か `commands/catchup.md` のファイルを持つものを探し、そのプラグインの `plugin.json`（`.claude-plugin/plugin.json`）の名前を使って `/<名前>:catchup`（attention なら `/attention:catchup`）を送る。持つものが 1 つに決まらない（無い・2 つ以上ある）と、`--check` と PR を開く dispatch は止まる。名前を組み立てる訳: 人が Claude Code の画面で `/catchup` と打つと、補完がプラグイン名を足してくれる。dispatch が文字を打ち込むのに使う herdr（端末を作業場ごとに分け、中の Claude Code の会話へ外から文字を打ち込むツール）は、渡した文字をそのまま打ち込み、補完を通さない。
5. **gh でリポジトリを読める。** gh で今有効なアカウントで読めないリポジトリには、設定に `gh_user` を書く。鍵は `gh auth token --user` で取り出し、gh を呼ぶ子のプロセスにだけ `GH_TOKEN` として渡す。gh にはフォルダごとにアカウントを替える仕組みが無く、`gh auth switch` はマシン全体を替えるので使わない。
6. **代表の clone を、どれか 1 つのアカウントで信頼済みにしておく。** Claude Code のフォルダの信頼は、リポジトリのルートごとに、アカウントごとの `.claude.json` に記録される。代表の clone の信頼は、そこから作った worktree（別のフォルダ）にも、ほかのアカウントにも効かない。そこで dispatch は、作業場（PR や部署ごとの worktree）を開いて会話を起動するたびに（新しく作った worktree でも、前に作ってあった worktree でも）、dispatch の設定のファイルの `accounts`（上の 3 で書くアカウントの一覧）のどれかが代表の clone を信頼済みなら、その会話を起動するアカウントに、代表の clone とその worktree の信頼の印（`.claude.json` の `projects["<リポジトリのルートのパス>"].hasTrustDialogAccepted`。公式の文書が手で信頼する手として書くもの）を付ける。どのアカウントも代表の clone を信頼していなければ何も書かず、Claude Code の信頼の確認がふつうに出る。信頼済みにするふつうの手は、どれか 1 つのアカウントの Claude Code を代表の clone のフォルダで起動し、出てくる信頼の確認で信頼を選ぶこと。人が見ていない会話など、Claude Code の対話の画面を開けない会話からは、代わりにその印を 1 つのアカウントの `.claude.json`（`~/.claude.json`。`CLAUDE_CONFIG_DIR` を入れて起動するアカウントは `<CLAUDE_CONFIG_DIR>/.claude.json`）に手で `true` と書く（`projects` の鍵に書くリポジトリのルートのパスは、シンボリックリンクを解いた絶対パスにする。Claude Code は解いた形で引くので、macOS の `/tmp/…` は `/private/tmp/…` と書く。同じアカウントの Claude Code の会話が動いている間に書くと、その会話が覚えている古い中身で `.claude.json` を書き戻し、印が消えることがある。消えたら書き直す。CLI に信頼を付けるコマンドは無い。手で書く形は https://code.claude.com/docs/en/permissions#project-allow-rules-and-workspace-trust ）。1 つのアカウントに書けば、ほかのアカウントと worktree には dispatch が広げる（後から `accounts` に足したアカウントにも、そのアカウントで作業場の会話を起動するときに広げる）。dispatch は、どのアカウントも信頼していない clone に自分から印を付けない。信頼すると、その clone の `.claude` の設定とフックが確かめ無しに効くので、信頼するかは clone の中身を知る人（かその人に任された会話）が決め、中身を信頼できる clone だけを信頼する。
7. **手元だけのファイルの置き場（任意）。** `copy_files` に書いた、git が追わないファイル（`.env.local`・`*.local.yaml`・`.claude/settings.local.json` など）を、新しく作った worktree へ写す。写す元は `copy_from` で、省けば代表の clone。
8. **使用率の控え（任意）。** `limits_dir/<アカウント名>.json`。無ければ、そのアカウントは使用率が分からないものとして、会話を起動するアカウントを選ぶ順（週の枠の切り替わりが近い〔設定の `reset_soon_hours`。既定 24 時間以内〕物を先に、ほかは使用率の低い順。`dispatch/nodes/accounts.py`）の最後に置く。作るのは `dispatch/limits.py`。
9. **herdr の連携（任意）。** `--check` が `herdr integration status` の claude の行を、アカウントのフォルダごとに読む。herdr の文書によれば、Claude Code の作業中の判定は herdr が画面から読み、連携のフックは会話の識別子を herdr に渡すだけである。そこで、無いときは止めずに、入れるコマンドを出す。
10. **部署の前提（部署〔`--task` で立てる、作業ごとの worktree と Claude Code の会話の組〕を立てる実行だけ足りない物、ほかの実行は注記）。** herdr の API に `pane.rename`・`pane.report_metadata`・`pane.read`・`pane.send_keys`・`workspace.rename`（`TASK_HERDR_METHODS`。1 の 12 とは別の集まり。部署の窓〔部署の会話を映すペイン〕と作業場に名前を、窓に札を付ける・画面を読む・入力フィールドに残った字に Enter を足す・裏の会話が止まって「Waking session …」のまま残った attach の画面〔`claude attach` で裏の会話をペインに映す画面〕を Ctrl+Z で終わらせ、シェルに戻す）が有ること、PATH の `claude --help` に `--name`・`--bg`・`--settings` が有ること。設定に前の版の `task_cwd` が残っていれば、止めずに注記を出して無視する。
11. **古いパス（任意）。** herdr の設定に足したタブバーの行（`dispatch/limits.py` を呼ぶ）と、各アカウントの `settings.json` に足した、herdr のサイドバーに作業内容を送るフック（`dispatch/activity.py` を呼ぶ）は、プラグインの版ごとのフォルダを指す。`--check` は、それらが消えた版の `limits.py` や `activity.py` を指していないかを見る。

持ち主（このプラグインの作者）は、herdr の作業中の判定の規則（`~/.config/herdr/agent-detection/claude.toml`）も、手元で上書きしている。この規則はここに入れない。上書きは herdr が配る規則の写しなので、herdr を上げるたびに写し直しが要る。そのうえ、上書きが見る印（背景の作業が残る間に statusline〔Claude Code が画面の下に出す、利用者が決めた状態の行〕が出す行）は、持ち主の statusline にしか無い。上書きの無い人は、herdr が配る規則のまま使う。
