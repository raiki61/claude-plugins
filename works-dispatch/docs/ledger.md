# 受付箱の台帳の形と、頼みの状態の読み方

頼み（`--ask` で部署に出す仕事の依頼）が済んだか・動いているか・答え待ちかを一覧で出す口が無く、手で数えると数が合わなかった。そこで、頼みごとの今の状態と頼みの木を台帳から毎回作り直して出す `dispatch.py --todo` を足した。台帳（受付箱の `log.jsonl`）は正本のまま置き、行にフィールドを 2 つと種類を 2 つ足しただけで、今ある台帳は書き換えずに読める。`--todo` の出力を読むだけなら、「頼みの状態」と「見せ方」のセクションで足りる。台帳に新しい種類の行を書くコードを足す人は、下の「種類を足すときの決まり」を読む（足し忘れると試験が落ちる）。

語の中身は次のとおり。

- 会社: works-dispatch が部署を置いて回す、1 つの git のリポジトリ。
- 部署: 会社の中で、仕事ごとに立てる作業場（git worktree）と、そこで働く Claude Code の会話の組。部署が預かる仕事の範囲を受け持ちと呼ぶ。
- メインブランチ: 会社のリポジトリの main のブランチ。部署はブランチで作業し、`--land`（部署のブランチをメインブランチに入れる `dispatch.py` のコマンド）でメインブランチに入れる。
- 受付箱: 会社のリポジトリの `.git/company/inbox/`。頼みと納品の本文を 1 件 1 ファイルで置き、台帳 `log.jsonl` に出来事を 1 行 1 件の JSON で末尾に足す。
- 受付番号: 頼みや納品の 1 件ずつに付く番号（例 `20261018-014838-3cd0d2`）。末尾の 6 文字（`3cd0d2`）で呼ぶことが多い。この文書に出る受付番号は、my_notes（持ち主のメモのリポジトリで、これも会社の 1 つ）か claude-plugins（works-dispatch が入っているこのリポジトリで、これも会社の 1 つ）の受付箱で引ける。
- 納品: 頼みを受けた部署が、結果の要約を返すこと（`--deliver`）。残った疑問は、要約の頭書き（1 行目と閉じの行が `+++` の TOML）の `[[open]]` に 1 件ずつ、疑問（`question`）と担当者（`holder`。その疑問を最後まで追う者で、受付番号・`owner:choose`・`owner:confirm`・頼み元の名前のどれか）で書く。
- 回す: 受けた頼みを自分で済ませず、ほかの部署へ頼んで閉じること（`--ask … --forward`）。
- 足し: 頼んだ後で、受けている頼みに打つ追記（`--note`）。
- 射影: 正本の出来事の列から、読むための形（ここでは頼みの状態と木）を組み立てた物。イベントソーシングの語（projection）。
- 機械窓口: AI の会話を起動せずに、決まった台本（`--call` で呼ぶツール。`calls.py`）を動かして頼みを片づける役。片づいたら `call` の行、片づかなければ `miss` の行を台帳に書く。

作り直す所は `dispatch/nodes/ledger.py`、出すコマンドは `dispatch/todo.py`、行の形は `dispatch/schemas/ledger.schema.json`、`--todo --json` の形は `dispatch/schemas/todo.schema.json`。決めたのは 2026-10-18、受付 20261018-014838-3cd0d2（持ち主の頼みを、my_notes の社長室〔持ち主への中継の部署〕と段取り〔部署への頼みを配る部署〕が中継した物）。

## 困っていたこと

- 頼みが済んだ・動いている・答え待ち・取り下げのどれかを出す口が無かった。社長室が 2026-10-18 の朝に my_notes の台帳を `ask` の行と `deliver`・`forwarded` の行の突き合わせで数えると、頼み 527 件のうち閉じて見えたのは 345 件だけだった。取り下げ（`withdrawn`）、何段もの回し、別の会社の受付箱での納品を拾えないためである。今の読み方で同じ台帳を同じ日の夕方に読むと、my_notes が打った頼み 632 件（朝より後に増えた分を含む）は、済 592・取り下げ 18・順番待ち 17・動いている 3・届かず 2 で、どれにも当たらない物は無い。
- 回して閉じた頼みに足しを打つと「もう納品した」で止まり、回した先を台帳から手で探していた（my_notes の受付 730760 から 66374c へ回した例）。
- 残った疑問の担当者は、要約のファイルの文の中にしか無く、台帳から項目どうしでたどれなかった（受付 8482db）。

## 決めたこと

1. 正本は台帳のまま。形は変えず、フィールドと種類を足すだけにする。
2. 頼みの状態と木は射影で、ファイルに書かない。開くたびに全部の台帳を頭から読む（Fowler の Complete Rebuild〔射影を捨てて出来事の列から作り直す〕、Marten の Live の射影〔読むたびに出来事から組み、保存しない〕と同じ）。2026-10-18 に my_notes から打つと、4 つの会社の台帳の 3,684 行を読み、台帳を探すのに 1 秒、組むのに 0.6 秒、コマンドの全体で 3 秒ほどだった。待つのが苦になる長さ（10 秒ほど）になったら、射影を保存する形を考え直す。
3. 状態は、頼みに当たる行を時刻の順に当て、最後に当たった物にする（Linear の Agent Session が状態を「最後に出した activity」で決めるのと同じ考え）。ただし済・取り下げ・回したの 3 つは終わりで、後の行で戻さない。これは Linear には無い、works-dispatch の足しである（納品の後に来る足しや知らせの行で、済んだ頼みが動いているに戻らないため）。
4. 親子は、行のフィールドで項目どうしを結ぶ（iCalendar の RELATED-TO、JSCalendar の relatedTo と同じく、人や部署を経ずに受付番号で指す）。残った疑問の担当者は、要約の頭書き（TOML）の `[[open]]` の `holder` から、納品の行のフィールド `holders` に写す（文から拾わない。頭書きの無い古い要約だけは、下の「古い行の扱い」のとおり「残った疑問」の文から拾う）。
5. 見せ方は個人の仕事の一覧に寄せる。誰のターンかは出さない（部署の様子は今までどおり `--tree`〔会社ごとの部署の一覧〕が出す）。

5 は持ち主の言葉による。「ようは、個人のタスク管理ツールに収束すると思う最終的な見た目は。だから誰の番とかないし、そういう最終系を見据えた設計がいると思う」（2026-10-18。my_notes の受付箱の、社長室が受けた受付 5f4b05 への足し cf11c9）。

## 行の形

### よく出るフィールド

- `id`: 受付番号。頼み・納品の要約のファイル（部署が頼み元へ返す結果の要約を書いたファイル。種類 `deliver`）・足し（頼みに後から書き足す補足。`--note` で送り、種類 `note`）のどれの受付番号かは種類で違う（下の表と表の補い）。頼みを指さない種類（`moved`・`followed`・`hopped`・`retired`・`call`・`miss`）の行には無い。リマインダーの行（`remind`・`reminded`・`remind-done`）では、リマインダーそのものの受付番号。
- `kind`: 出来事の種類。
- `at`: 時刻（UNIX 時刻の秒）。
- `status`: `ask` の行では結果で、`sent`（届いた）・`queued`（順番待ちに積んだ）・`failed`（届かなかった）。`deliver` の行では `sent`（頼み元に届けた）・`posted`（頼み元の会話が無く、台帳に置いた）・`failed`（届かなかった）。ほかの行にも別の値（`noticed` など）が付くことがあるが、状態には使わない。
- `to`: 宛先。ふつうの行（知らせでない行）では宛先の部署を表す辞書（`to.path` が宛先の作業場のパス）。知らせの行（宛先の待ち受け〔会話の裏で台帳を読み、自分宛ての行で会話を再開させる台本〕に宛てた行）では、宛先の作業場のパスの文字列。
- `from`: 打った側。`from.place` が打った作業場のパス、`from.name` が打った部署の名前。
- `place`: 行を書いた作業場のパス（`handed` などの行）。
- `file`: 頼みや納品の本文のファイルのパス。パスの中の受付箱のフォルダで、どの会社の受付箱かが分かる。
- `boss`: 頼み元。`boss.inbox` が頼み元の会社の受付箱のパス。
- `child`: `forwarded` の行の、回した先の頼みの受付番号。`reminded` の行の、知らせの代わりに出した頼みの受付番号（下の「リマインダー」）。
- `for`: 回して閉じた頼みへの返しの納品の行で、返す先の頼みの受付番号。
- `why`: `waiting` の行の、答え待ちの訳。順番待ちに無い頼みを閉じた `withdrawn` の行の、閉じた理由（下の「台帳と、順番待ち・作業場が食い違うとき」）。
- `was`: 順番待ちに無い頼みを閉じた `withdrawn` の行の、閉じる前の状態（`queued`〔順番待ち〕・`working`〔動いている〕・`waiting`〔答え待ち〕。下の「頼みの状態」の表の値）。

### 種類

`id` と、頼みの受付番号の入るフィールドは、種類によって違う。下の表の「頼みのフィールド」がそのフィールドの名前で（`id` ならその行のフィールド `id`、`ask` ならその行のフィールド `ask`〔種類の `ask` とは別〕に頼みの受付番号が入る）、`ledger.KINDS`（種類からフィールドの名前への辞書）に書いてあり、`ledger.subject(row)` で引く。「状態」は、その行が頼みの状態をどう変えるか（「—」は変えない）。

| 種類 | 頼みのフィールド | 中身 | 状態 |
| --- | --- | --- | --- |
| ask | id | 頼んだ | 行の `status` の値で決まる（`sent` なら動いている、`queued` なら順番待ち、`failed` なら届かず） |
| queued | id | 順番待ちに積んだ（知らせの行。下の補い） | — |
| handed | id | 部署に渡した（永続の部署〔頼みを終えても畳まず、同じ作業場で次の頼みを受ける部署〕では、待ち受け〔ターンの終わりに動くこのプラグインのフック〕が渡す前に作業場をメインブランチの先頭へ進める。進めたのと同じ待ち受けがこの頼みを渡したときだけ、フィールド `followed` に種類 `followed` の行の `detail` と同じ文が入る） | 動いている |
| held | id | 渡さず待った | — |
| taken | id | 順番待ちから取った | 動いている（`--take` を打った部署がその場で受けたとき。下の補い） |
| reordered | id | 順番待ちの先頭に回した | — |
| withdrawn | id | 取り下げた | 取り下げ |
| forwarded | id | ほかの部署へ回して閉じた | 済（回した） |
| deliver | ask | 納品した | 済 |
| note | ask | 足した | —（数える） |
| waiting | id | 答え待ちにした | 答え待ち |
| resumed | id | 答え待ちが外れた | 動いている |
| nudged | id | 止まった部署を動かした | — |
| knot | id | 互いの返事を待ち合う頼みの輪をほどいた | — |
| start | id | 受け持ちの部署を、起動方法のとおりに起動した | — |
| moved | 無し | 部署か窓口の会話を起動し直した（`status` が `skipped` なら、区切り〔会話を空にしてよい切れ目。頼みのたびに会話を空にする部署（役が `fresh = true`）では次の頼みを渡す前、ほかの部署と窓口では、その会話が自分で `--rest`（ここで会話を空にしてよいと印すコマンド）を打ったターン（会話が 1 つの入力に答え終えるまで）の終わり〕で、待ち受け（ターンの終わりに動くこのプラグインのフック）が走らせる `--move` が、使用上限に当たる前にほかのアカウントへ移そうとして、移る先が無いなどで移さなかった。または、`--move` が待つ間に部署か窓口が消えて〔作業場が無いか、属性 `company.role` が外れた〕待つのをやめた〔`why` が「待っている間に部署か窓口が消えた」〕。`status` が `waiting`（種類の `waiting` とは別）なら、API の提供元に要求を断られて（使用上限・使える時間帯の外など）止まった会話を、このプラグインのフックが自動で走らせる `--move` が、移さずに待ち始めた（人の手は要らない。`--move` が待った後に自分で見直し、今のアカウントが使えれば同じ会話に続きの 1 行を打ち、使えずにほかのアカウントが空いていればそこへ移す）。訳は `skills/dispatch/references/move.md`） | — |
| followed | 無し | 永続の部署の作業場を、順番待ちの先頭の頼み（この行のフィールド `next` にその受付番号）を渡す前にメインブランチの先頭へ進めた、または進めなかった（`detail` に、何をしたか・進めなかった訳。会話の裏の処理が動いていて進めなかったときは、遅れていれば足りない commit の数も書く。もう先頭に在れば書かない） | — |
| hopped | 無し | 前の版のプラグインで立った待ち受けが、頼みを渡す前に、今入っている版の待ち受けに替わった（`from` に前の版の置き場、`to` に今の版の置き場。替わる直前に書く。替われずに前の版のまま待ち直したときは、`status` が `failed` で `detail` に訳を書いた同じ形の行を続けて書く） | — |
| retired | 無し | 部署を畳んだ | — |
| call | 無し | 機械窓口が頼みを片づけた | — |
| miss | 無し | 機械窓口が片づけられなかった（`rerun_of` が有れば、片づかずに回った頼みの中での打ち直しなので回さなかった） | — |
| remind | 無し | リマインダーを立てた | — |
| reminded | 無し | リマインダーの担当者に知らせた | — |
| remind-done | 無し | リマインダーを閉じた | — |
| handover | 無し | 部署か窓口の受け持ちを、同じ会社のほかの部署（後継）へ移した（`--handover`。`status` が `started` と `done` の 2 行。下の「足したフィールドと種類」） | — |

表の補い:

- 知らせの行は、`to` が文字列の行（上の `to` の説明のとおり、宛先の待ち受けに宛てた行）で、種類のフィールド `kind` とは別に、`to` の形で見分ける。知らせの行は、どの種類でも `id` が頼み（足しの知らせなら足し、リマインダーの知らせならリマインダー）の受付番号である（`--land` や `--move` が部署に送る、頼みを指さない知らせでは `null`）。リマインダーの知らせは、`id` を「知らせが何についてか」の受付番号とする今の意味のまま使うので、行の形の版は上げない。
- 知らせでない `deliver` の行は、`id` が要約のファイルの受付番号で、頼みはフィールド `ask` にある（種類の `ask` とは別の物）。知らせでない `note` の行も、`id` が足しの受付番号で、頼みはフィールド `ask` にある。
- `start` の行の受け持ちは、会社の形（`.claude/company.toml`）の `[[skills]]` に書く、部署ごとの仕事の範囲で、起動方法はその受け持ちに書いた、部署を立てるコマンド（`--start`・`--due` が打つ）。
- `forwarded` の行は、`id` が回した元の頼み、`child` が回した先の頼みである。
- `taken` の行は、`--take` を打った作業場のパスを `by.place` に持つ。`--ask` を付けずに部署の作業場で打つと、打った部署がその場で頼みを受け、`to` は受けた部署の名前と役になり、状態は動いているになる（表の「打った部署が受けたとき」）。`--ask <宛先>` を付けて打ったとき（ほかの部署へ頼み直す。`to.ask` が宛先）は、`taken` の行は状態を変えず、同じ受付番号で書く頼み直しの `ask` の行の `status` が状態を決める。
- `ask` の行の `status`: `sent` なら動いている、`queued` なら順番待ち、`failed` なら届かず。順番待ちの頼みは、待ち受けが部署に渡すと `handed` の行で動いているになる（待ち受けが居なくて渡らないときは `--nudge` で動かす。`skills/dispatch/references/queue.md`）。届かずの頼みを works-dispatch は送り直さない。打った会話が打ち直すと、新しい受付番号の別の頼みになり、届かずの頼みはそのまま残る。
- `deliver` の行のうち、ふつうの行（知らせでない行）の届かなかった物（`status: failed`）と、回して閉じた頼みへの返し（`for` の有る行）は当てない。知らせの `deliver` の行は、そのまま済にする。
- `resumed` は、答え待ちのときだけ動いているに戻す。
- `note` は状態を変えず、射影のフィールド `notes` に足しの数を数える（終わった頼みへの足しも数える）。
- `remind`・`reminded`・`remind-done` は頼みの木に入らない。納品の残った疑問の担当者に書かれたリマインダーは、頼みの続きのリマインダーとして結ぶ（下の「頼みの木」の続き）。形は下の「リマインダー」。

### 足したフィールドと種類

- `ask` の行の `cause`: その頼みを打った作業場（打った部署の git worktree）が、そのとき受けていて、まだ納品していない頼みの受付番号（無ければ `null`）。イベントソーシングの言う causation id（その出来事を起動した元の出来事の id）に当たる。機械窓口（上の語の一覧のとおり、AI の会話を起動せずに決まったツールで頼みを片づける役）が `--land` の合図（メインブランチに入れた後に呼ぶツール。会社ごとの設定ファイル `.claude/company.toml`〔会社の形。役・部署・受け持ちを書く〕の `[[land.after]]` のセクションに、呼ぶツールを書く）で回す頼み（`dispatch/calls.py` の関数 `fire` が出す）は、`--land` でメインブランチ（main）に入れた部署が受けていた頼みを `cause` にする（その部署が頼みを受けていなければ `null`）。
- `ask` の行の `cause_boss`: `cause` の頼みの頼み元（`forwarded` の行の `boss` と同じ形。会話の名前 `name`・会話の id `session`・アカウント `account`・ペイン `pane`・受付箱 `inbox`）。`cause` が有り、頼み元が分かる（打った部署の属性に頼み元の名前か会話の id が在る）ときだけ書く。子の頼みの答えを `--deliver --for <受付>` で元の頼み元へ返すときに引く。頼み元が部署でも、部署でない会話でも、打った時の部署の属性（部署の作業場の git の設定に書く頼み元。`company.boss` など）から写す。子の行に写しておくのは、部署の属性は部署が次の頼みを受けると新しい頼み元で書き替わり、元の頼みの行は頼み元の受付箱にしか無いことがある（頼み元が部署でない会話や別の会社の会話のとき）からである。`cause` は有るが `cause_boss` の無い古い行では、`--deliver --for` が、会社をまたいでたどった台帳（下の「会社をまたぐ読み方」）から、`id` が子の `cause` に当たる `ask` の行（元の頼みの行）の最後の物を探し、その行の `from` の `name`・`session`・`account` と、`file`（本文のファイル）の在るフォルダ（頼み元の会社の受付箱）を `inbox` にして組み立てる（`pane` は `null`）。元の頼みの行が見つからなければ組み立てない。
- `ask` の行の `causes`: 束（`[land] batch` を 2 以上にした会社で、`--land` が 1 回のゲートでまとめてメインブランチに入れた部署のブランチの組。docs/specs/2026-10-26-land-batch-design.md）の合図で回した頼みだけが持つ、`cause` に並べる親の受付番号の並び。束に乗った部署（束ね役でない部署）が受けていて、まだ納品していない頼みを書く。合図のツールはどの部署の変更が原因かを知らないので、乗った部署の頼みにも結ぶ。射影は、この頼みを `causes` の頼みの子にも並べる（木の親 `parent` は `cause` の 1 つのままで、`parent_by` も `cause` のまま。並べた頼みの `open` は、この頼みが開いている間は開いていると出る）。
- `miss` の行（機械窓口が片づけられなかった `--call` の記録。外れの行）の `ask` と `rerun_of`（上の表で `miss` の「頼みのフィールド」が「無し」なのは、`miss` の行が頼みの状態を変えないからで、この 2 つは `ledger.subject` では引かない。`--call` が打ち直しを見分けるためだけに読む）: `ask` は、片づかなかった仕事を回す頼みのために振った受付番号（回すこと自体ができなかったときも、振った番号を書く）。`rerun_of` は、打ち直しなので回さなかったときに、`ask` の代わりに書く。打ち直しと見なすのは、`--call` を打った部署が受けていて、まだ納品していない頼み（上の `ask` の行の `cause` と同じ決め方で選ぶ）が、同じ役・同じツール・同じ入力の外れの行の `ask` に在るとき。つまり、片づかずに回った頼みを受けた部署が、その頼みの中で同じ `--call` をもう一度打ったときで、`rerun_of` にはその受けている頼みの受付番号を書く。このとき `--call` は同じ頼みをもう 1 つ積まず、打った会話にツールの標準出力と標準エラーの終わりの 20 行を出して、終了の値 1 で終わる。`ask` を書かなかった前の版の `dispatch.py` が書いた外れの行から回った頼みの中で打ち直したときは、打ち直しと見分けられず、前と同じく回す（積まれた頼みは `--withdraw`〔頼みを取り下げるコマンド〕で取り下げる）。
- `ask` の行の `title`: `--todo` に出す 1 行の題（頼みの本文の頭書きの `title` か、1 行だけの本文）。60 文字を超えれば切って「…」を付ける。`--take`（順番待ちの頼みを 1 件取り出し、打った部署が受けるか、ほかの部署に頼み直すコマンド）で回し直した行は、順番待ちの件に残した題を引き継ぐ。頭書きの入る前に積まれた件のように題を持たなければ `null`（そのときは上の古い行と同じく本文のファイルから読む）。
- `deliver` の行の `holders`: 残った疑問の担当者の並び `[{"holder": 担当者の文字列, "ask": 受付番号か null}]`。頭書きの `holder` が受付番号なら `ask` にそれを入れ、ほかは `null`。頭書きの無い古い要約から作った行では、`ask` に入るのは担当者の文字列の中の長い形の受付番号（`20261018-120448-b6778d` の形の全部）だけ。この `holders` のフィールドを持つ行では、`--todo` は `ask` が `null` の担当者の文字列から受付番号を拾わない（名前に英字の a〜f と数字が並ぶと、末尾の 6 文字の受付番号と取り違えるため）。担当者の文字列から拾うのは、`holders` のフィールドの無い古い行だけ（下の「古い行の扱い」）。
- `waiting`: 部署が頼みを人の答え待ちと印した（`--wait`。答え待ちの訳〔理由の文〕を `why` に書く）。打った作業場の会社と頼み元の受付箱の両方に書く。
- `resumed`: 人が文を打って答え待ちの印が外れた（`wake_hook.resume_from_wait`）。`waiting` と同じ 2 か所に書く。
- `waiting` の行の `parked`: `true` なら、答え待ちのまま保留にした（`--wait <訳> --park`）。頼みと頼み元を部署の属性 `company.parked` へ移し、今の頼みを空けたので、部署は次の頼みを受ける。状態は `parked` の無い `waiting` と同じ答え待ちで、閉じるのはその受付番号の納品（`--deliver <要約> --for <受付>`）だけ。
- `deliver` の行の `parked`: `true` なら、保留にした頼みへの返し。`for` を書かないので、ふつうの納品と同じに頼みを済にする。
- `deliver` の行の `status` の `self`: 頼み元（`--handover` で読み替えた後の物）がこの部署自身（今の名前・`--handover` で継いだ名前・この部署の会話の id のどれか。`--reorg --name` で替える前の名前は数えない）なので、要約を受付箱に置き、だれにも知らせずに閉じた。済にする。
- `handover`: 部署か窓口（前の部署）の受け持ちを、同じ会社の部署（後継）へ移した。後継の場所から打つ `--handover <前の名前>` が、後継の会社の台帳に書く。`status` が `started` の行が `from`（前の部署の名前 `name`・前の名前 `former`・宛先の並び `names`・役・会話の id・アカウント・`path`・`place`〔worktree の git の場所〕・本社か `head`・移す前の属性 `attrs`・前の待ち受けが読んだ所 `pos` と台帳の終わり `end`〔バイト〕）と `to`（後継の名前・役・会話の id・アカウント・ペイン・`path`・`place`）と、移した順番待ち `queue` と保留の頼み `parked` の受付番号の並びを持つ。`done` の行は、全部の手順を済ませた印で、`id` が同じ。`done` の無い `started` の行が在れば、同じコマンドを打ち直すと残りの手順を続ける。受付番号・`cause`・`forwarded` の行は替えない。後で読む側は、この行で読み替える（`--deliver` は、頼み元が前の部署〔名前で見る。前の部署の前の名前も含む〕で、この行より前に頼んだ頼み〔受付番号の頭の時刻で比べる〕なら、後継へ返す。`dispatch/nodes/handover.py` の `successor`）。
- 知らせの行の `handover` と `copied`: `--handover` が、前の部署の待ち受けがまだ読んでいなかった、前の宛先宛ての知らせ（`pos` から `end` まで）を、後継の宛先宛てに写し直した行。`handover` が引き継ぎの `id`、`copied` が元の行の鍵（`id`・`kind`・`file`・`at`・`to` の並び）で、打ち直しで同じ知らせを 2 度写さない。頼みの木（`build`）は写しの行を数えない。後継の待ち受けは、前の宛先宛ての知らせを、属性 `company.inherited` の `since`（= `end`）より後の物だけ拾う（それより前は、前の待ち受けが読んだか、写し直した物）。

相関の id（頼みの木のルートの受付番号）は行に持たない。親を `cause` でたどればルートは決まるので、行に重ねて書くと食い違う元になるだけだからである。今はどの会社の台帳も 1 台の機械に在り、全部を読める。会社ごとに別の機械に分かれ、親の行を読めなくなったら、ルートの受付番号を行に持つかを考え直す。

### 行の形の版

台帳の行そのものには版のフィールドが無い。`ledger.schema.json` は、試験で照合するときに台帳を `{"schema": 版, "rows": [行]}` の包みに入れて読む形で、`schema` の版はこの包みにだけ在る（今は 1）。

## 会社をまたぐ読み方

頼んだ会社と受けた会社は、同じ受付番号の行をそれぞれの台帳に書く。`--todo` は打った作業場の会社の受付箱から始め、読んだ行が指すほかの会社の受付箱を順にたどって、全部の台帳を読む（`todo.inboxes_from`）。ほかの受付箱は、次の 2 つの手で見つける。

1. 行の `file` と `boss.inbox` のパスの中の受付箱のフォルダ。
2. 行の `to.path`・`from.place`・`place` の作業場のパスを `git rev-parse --git-common-dir` で引いて、その会社の受付箱を出す。

2 が要るのは、相手の会社にだけ頼んだ（相手からはこちらに頼んでいない）とき、本文のファイルが頼んだ側の受付箱に在るので、1 では相手の受付箱が出てこないからである。在る場所だけ読む。

読んだ行は、全部のフィールドが同じ物を 1 つにまとめ（同じ行が両方の台帳に在るため）、時刻の順に並べる（`ledger.merge`）。会社が開いていなくても（herdr〔端末の画面を作業場に分けて会話を並べるツール〕に作業場が無くても）、台帳だけで組む。回した元の頼みの `ask` の行が、読んだ台帳のどこにも無いとき（読めない会社の台帳にだけ在るとき）は、`forwarded` の行から頼みの行を組み立て、回した先をたどれるようにする。

## 頼みの状態

| 状態 | 画面の字 | JSCalendar | iCalendar | 開いている |
| --- | --- | --- | --- | --- |
| queued | 順番待ち | needs-action | NEEDS-ACTION | はい |
| working | 動いている | in-process | IN-PROCESS | はい |
| waiting | 答え待ち | in-process | IN-PROCESS | はい |
| done | 済 | completed | COMPLETED | いいえ |
| dropped | 取り下げ | cancelled | CANCELLED | いいえ |
| failed | 届かず | failed | 無し | いいえ |

JSCalendar の列は Task の progress、iCalendar の列は VTODO の STATUS の値。「開いている」は頼み自身の値で、子か続きのどれかが開いていれば、その頼みも開いていると見る（射影のフィールド `open`）。届かずを開いている物に数えないのは、打った会話がその場で届かなかったと知るからである。回して閉じた頼みは、状態を済にし、`forwarded: true` を付ける（別の状態にはしない）。

## 頼みの木

ある頼み（子）の親は、次の順で 1 つだけ決める（射影のフィールド `parent_by` に、どれで決めたかを残す）。輪になる親はつながない。

1. `forwarded`: 子が、回した行の `child` に当たれば、その行の `id`（回した元の頼み）が親。
2. `cause`: 子の頼みの行の `cause` が指す頼み。フィールドが有れば、値が `null` か、読んだ台帳に無い頼みでも、下の 3 で補わない（親は無い）。
3. `inferred`: `cause` のフィールドの無い古い行だけ、打った作業場から親を推す。
   1. 子を打った時（同じ時刻を含む）までに作業場が受けた頼み（`ask` の `sent` の行の宛先か、`handed` の行の作業場が受けた物）のうち、子を打った作業場（`from.place`）のパスが、受けた作業場のパスと同じか、その下のフォルダである物を集める。
   2. 受けた部署の名前が分かる物は、子を打った部署の名前（`from.name`）と同じ物だけに絞る。
   3. 子を打った時にまだ閉じて（済・取り下げ・回したのどれかになって）いなかった物のうち、最後に受けた物を親と見る。

並べた親: 子の頼みの行に `causes`（束の合図で回した頼み）が在れば、そこに並ぶ頼みの子にも子を並べる（射影のフィールド `children` に足す）。木の親（`parent`）は上の順で決めた 1 つのままで、輪になるものは並べない。

3-3 で閉じた物を外すのは、窓口（持ち主と話して仕事を配る、頼みを受けては返す常設の会話）が、前に受けて閉じた頼みの子として新しい頼みを出したと読まないためである。

続き（射影のフィールド `follows`）: 頼み A の納品の残った疑問の担当者が受付番号 B なら、A の続きに B を結ぶ（A → B）。担当者が部署の名前や持ち主の物は、射影のフィールド `questions` に残すだけで、開いている物には数えない。その疑問を閉じる出来事が台帳に無いからである。`holders` のフィールドの無い古い納品の行は、要約のファイルを読んで担当者を拾う（`todo.questions`）。担当者の受付番号がリマインダー（下の「リマインダー」）の物なら、頼みでなく、続きのリマインダー（射影のフィールド `reminders`）に結ぶ。頼みの木には入れず、リマインダーが閉じていない間は、A を開いている物と見る（後でしか起きない事を追う疑問を、立てたリマインダーに追わせる。my_notes の受付 20261020-195701-cbef3b）。

ルートは親の無い頼みで、多くは持ち主か人が会話から出した頼みである。古い行で 3 の推しが当たらなかった頼みもルートになる。

## 見せ方（`--todo`）

- `dispatch.py --todo`: 開いているブランチ（頼みの木で、ルートから分かれた部分。git のブランチではない）だけを、ルートを更新の新しい順に、字下げの木で出す。行は `- [状態] 題  受付番号  更新の日時`。更新の日時は、台帳の行のうちその頼みの受付番号についての行（頼み・納品・答え待ちなど）の、最後の行の時刻で、子の頼みの行は含めない。答え待ちには訳を、続き（納品の残った疑問の担当者になった頼み。子の頼みとは別。上の「頼みの木」の続き）には `→ 続き: 受付番号` を、続きのリマインダーには `→ 続き（リマインダー）: 受付番号  何を見るか` を添える（閉じた物は、済んだブランチも出すとき〔`--all`・`--todo <受付番号>`・`--html`〕だけ、`（リマインダー、閉じた）` で出す。`--state`・`--to` の平らな並びと数えの 1 行は、頼み自身の状態だけで決め、続きのリマインダーは見ない）。`--todo <受付番号>` にリマインダーの受付番号を渡すと、そのリマインダーの 1 行（下の「リマインダー」の `--todo` の行と同じ形）と、それを納品の残った疑問の担当者に書いた頼みを出す（`--json` は `reminders` と `held_by`）。
- `--todo <受付番号>`: その頼みから下だけ（済んだ物も出す）。末尾の 6 文字でもよい。
- `--all`: 閉じたブランチ（済・取り下げ・届かず）も出す。
- 頭の「!」の注記: 頼みの木の前に、1 件 1 行で「!」で始まる行として出す。中身は 2 種類。1 つは、台帳をたどった受付箱ごとの壊れの知らせ（`health.py`）で、次の 3 つを出す。裏の処理（フックが会話から切り離して走らせる `--move`・`--retire`・`--take`）の失敗。30 分（`health.QUEUE_STALE_MIN`）より長く誰も受けないままの順番待ち。上限（`health.LEDGER_LIMIT`。32 MiB）を超えた台帳の大きさ。もう 1 つは、台帳では開いているのに順番待ちの件も受けた作業場も無い頼み（`todo.strays`。下の「台帳と、順番待ち・作業場が食い違うとき」）。
- 数えの 1 行: 「!」の注記とリマインダーの後、頼みの木の前に、`件数: 順番待ち N・動いている N・答え待ち N・済 N・取り下げ N・届かず N（全 N 件、済の割合 N%）。開いている頼みでいちばん動きの無い物: 受付番号（N 日前に更新）` を出す。済の割合は、済の件数を、届かずを除いた全件で割った物（届かずは誰も受けていない）。済の割合は % の整数に丸めて出し、分母が 0 なら `-`。古さは、その頼みについて台帳に書かれた最後の行の日時から、`--todo` を打った時刻までの間（N 日・N 時間・N 分のどれかで出す）。数えるのは、`--todo <受付番号>` で頼みを渡せばその頼みと下に繋がる頼み（その頼みを受けた部署が出した頼みと回した先を、下へたどった物。続きは含めない）、`--to` を付ければ宛先の当たる頼みで、どちらも付けなければ台帳の全部の頼みで、どの場合も閉じた物を含む全部の状態の頼み（`--state` では絞らない。済の割合の分母が要るため）。数えを作る関数は `dispatch/nodes/ledger.py` の `tally`。
- `--state <状態>` と `--to <宛先>`（絞り込み）: どちらかを付けると、頼みの木にせず、当たった頼みを更新の古い順（動きの無い間の長い順）に 1 行ずつ平らに並べる。行は木と同じ形の後ろに `  宛先 会社/名前  N 日前`（最後の更新からの古さ）を足した物。`--state` はカンマで区切って幾つでも渡せ、状態の英語の名前（`queued`・`working`・`waiting`・`done`・`dropped`・`failed`。`dispatch/nodes/ledger.py` の `STATES` に画面の字との対応が在る）か画面の字（順番待ち・動いている・答え待ち・済・取り下げ・届かず）で書く。知らない状態は、使える物を出して止まる。`--to` は宛先の部署の名前・会社の名前・「会社/名前」のどれかと同じ頼みに当たる。`--state` を省けば開いている状態（順番待ち・動いている・答え待ち）だけ、`--all` で全部の状態。受付番号と一緒に付ければ、選ぶ先をその頼みと下に繋がる頼みに限る。2026-10-19 に Taskwarrior（端末の作業の管理ツール）へ台帳を流して一覧を試し、新しく得た表示（状態・宛先の絞り込み・件数・済の割合・古さ）がどれも台帳から作れたので、Taskwarrior は使わずにここへ足した（経緯は持ち主のノートのリポジトリ my_notes の記録で、受付番号 20261019-125332-9e0796 の納品（Taskwarrior の試しの結果）と、この直しを頼んだ受付番号 20261020-052829-d4495e の頼み。このリポジトリの外に在る）。
- `--json`: `todo.schema.json` の形で、読んだ受付箱の並び `inboxes` と、上と同じ絞り込みをした木 `forest`（`--state`・`--to` を付ければ、当たった頼みを子の無いノードにして平らに並べた物）と、数え `summary`（状態ごとの件数 `counts`・全件 `total`・済の割合 `done_ratio`〔0〜1。分母が 0 なら `null`〕・いちばん更新の古い開いた頼み `oldest_open`〔`id`・`updated`・経った秒 `age`。無ければ `null`〕・絞り込み `filter`〔`states` と `to`。付けなければ `null`〕）を出す（全部の頼みの辞書は出さない）。
- `--html <ファイル>`: 1 枚の HTML のページに書く。CSS とスクリプトはページの中に在り、ブランチは HTML の details 要素で畳む。`--all` も受付番号も付けなければ、済んだブランチを初めは隠し、ページの「済んだ物も出す」で出す。続きの印は、ページの中のその頼みへ飛ぶ。ページの頭に数えの 1 行を出し、`--state`・`--to` を付ければ当たった頼みを平らに並べる（済んだ物も初めから出す）。

題は頼みの行のフィールド `title`（頼みの本文の頭書き〔1 行目と閉じの行が `+++` の TOML〕の `title`、頭書きが無ければ 1 行だけの本文そのもの。`--ask` が書き、60 文字を超えれば切って「…」を付ける）。`title` の無い古い行だけ、`deliver.task_title`（`dispatch/nodes/deliver.py` の関数）が本文のファイルから決める。次の順に見て、最初に取れた物を題にする。どちらも 60 文字を超えれば切って「…」を付ける。誰のターンか・どの部署が持つかは出さない。

1. 持ち主の言葉: 本文に「## 持ち主の言葉」のセクションか、「持ち主の言葉（そのまま）:」で始まる行があれば、持ち主の言葉を題にする。セクションなら、見出しの次の、字の在る最初の行。行の形なら、「:」の後ろに字があればそれを、無ければ次の字の在る行を取る。取った行の箇条の印（`- ` や `1.`）は外す。
   - 取った行が「で始まり、対になる」のすぐ後ろが行の終わり・次の「・（・、・。のどれかなら、その「」の中だけを題にする（「「都度が何個か」（補足）」なら「都度が何個か」）。
   - 」の後ろにほかの字が続けば、「」は言葉の一部なので外さず、行をそのまま題にする（「「困りごと」が題になる」はそのまま）。
2. 本文の最初の文（`deliver.ask_title`）: 持ち主の言葉が無ければ、本文を文（括弧の外の「。」で切った単位）に分け、次を飛ばした最初の文を題にする。
   - 回した側の添え書き（「…が回した:」から区切りの `---` まで）と、決まり文句の行（「前提が違う」で始まる行など）
   - 見出し（`#` で始まる行）
   - 誰からの何かだけを言う文（「社長室からの頼みです（穴の直し）。」「知らせです（返事は要りません）。」「段取りから社長室へ。」）

   文の頭の項目名（「困っていること:」「頼み:」など）は外す。飛ばした後に何も残らなければ、最初の行の頭の `#` を外して題にする。

見出しを題にしないのは、段取りの頼みが「## 困りごと」「## 困っていること」のような中身を言わない見出しから始まり、題が見出しの名前で並んだため（2026-10-19、my_notes の受付箱の頼み 679 件のうち 141 件）。見出しの名前の一覧を足して飛ばす形にしなかったのは、見出しの書き方が替わるたびに一覧を直すことになるため。部署の名前（`--task`）を題にしなかったのは、その場で立てる部署の名前が役の名前（「作業」など）とブランチの受付番号で、中身を言わないため。

木を文字から HTML 1 枚に出して畳む形は markmap（Markdown から mindmap を描くツール）と details 要素に倣い、済んだブランチを隠す切り替えは Workflowy・Dynalist・MindNode（アウトライナー）に倣った。ただし、それらのアウトライナーのように保存を自分で持つ形にはしない（正本は台帳だけ）。

## 足しを回した先へ送る

足しを打った頼みが順番待ちに無く、その頼みを受けている部署が無いか、その部署がもう納品していれば、`orders._forwarded_to` が射影の回した線（`parent_by` が `forwarded` の親子）だけをたどり、まだ終わっていない（済・取り下げ・届かずでない）頼みを探す（`ledger.forwarded_open`。回した先が済んでいれば、さらにその回した先をたどる）。

- 1 件: 「回して閉じた頼みなので、回した先の受付 … に足す」と出して、そちらに足す。
- 0 件: 「回した先もみな閉じた」で止める（新しい頼みで `--ask` する）。
- 2 件以上: 並べて止め、打つ人にどれかの受付番号で打ち直させる。

読む台帳は、打った作業場の会社と herdr に開いている会社の受付箱から、`--todo` と同じく行が指すほかの会社の受付箱へたどった物（`todo.inboxes_from`）で、開いていない会社にだけ在る回した先も見つける。

`cause` や推した親（`inferred`）の線はたどらない。回した先と違い、子の頼みは元の頼みの代わりではないからである。

## 入れる手を別の頼みに預けた部署

このセクションは、今動いている Stop フック（Claude Code の会話がターンを終えるときに走るフック）の振る舞いと、そう決めた訳の記録である。部署（works-dispatch が仕事ごとに立てる作業場〔git worktree〕と、そこで働く Claude Code の会話の組）が差し戻されない・差し戻され続ける訳を調べる人と、`orders.stop_after` のまわりを直す人が読む。差し戻しは、部署の会話がターンを終えるのを Stop フックが止めて、やり残した手を打つよう言い返すことである。

Stop フック（`orders.py stop`）は、頼み（`--ask` で部署に出す仕事の依頼）を納品し終えた（納品は、頼みを受けた部署が結果の要約を頼み元へ返すこと。`--deliver`）部署のブランチがメインブランチ（会社〔works-dispatch が部署を置いて回す git のリポジトリ〕の main）に入っていなければ、部署の会話がターンを終えるのを止めて、`--land`（部署のブランチをメインブランチに入れるコマンド）で入れるよう差し戻す（`orders.stop_after`。会社の形〔会社ごとの設定ファイル `.claude/company.toml`〕の `[land]` の取り込み方 `mode` が `ff-after-ci`〔ゲート（入れる前に通す検証）が緑ならメインブランチを fast-forward で進める形〕の会社だけ。取り込み方の一覧は `docs/land.md`）。部署が入れられない訳（メインブランチの CI の赤など）を別の頼みに預けたとき（入れる手や赤の直しを、ほかの部署か窓口〔持ち主と話して部署に仕事を配る会話〕に `--ask` で頼んだとき）は、預けた先の答えが出るまで差し戻さない（`orders.leftover` が返す種類 `handed`）。この振る舞いを足した頼みは受付 2a2001（受付番号〔頼みや納品の 1 件ずつに付く番号。例 `20261018-014838-3cd0d2`〕の末尾の 6 文字。以下の「受付」も同じ）。

- 預けた先: 部署が今の頼み（部署が最後に受けた頼み。ここでは納品し終えている）を受けてから、自分で出した頼み（`orders.handed_open`）。台帳（会社の受付箱〔会社のリポジトリの `.git/company/inbox/`〕の `log.jsonl`。出来事を 1 行 1 件の JSON で足す）の頼みの行で見分ける。納品の前に出した物は、頼みの行の `cause`（頼みを打った部署がそのとき受けていて、まだ納品していない頼みの受付番号）が今の頼みの物。納品の後に出した物は、`cause` が null で（`--ask` は納品の後には `cause` を null で書く）、頼みの行の時刻（`at`）が今の頼みの納品の行の時刻と同じかそれより後の物。納品の行は、納品のコマンド（`--deliver`）が頼み元の会社の受付箱の台帳に書く。頼み元が部署と同じ会社ならそれは部署の会社の受付箱で、別の会社なら部署の属性（部署の作業場の git の設定に書く値）`company.boss-inbox` が指す受付箱である。どちらの場合も拾えるよう、部署の会社の受付箱と `company.boss-inbox` の受付箱の両方の台帳を読んで 1 つに合わせ（全部のフィールドが同じ行は 1 つにまとめる）、その中から今の頼みの納品の行（フィールド `ask` が今の頼みの受付番号で、届かなかった物でない行）を探す（何度か納品していれば、いちばん早い物の時刻と比べる。遅い物と比べると、1 回目と 2 回目の納品の間に出した頼みを落とす）。差し戻しの文は、`--land` が自動の権限の判定（Claude Code がコマンドを打たせるかを決める判定）に止められたら、打ち直さずに `--ask` で窓口に入れるのを頼むよう勧める。差し戻しは今の頼みを納品し終えた部署にだけ来るので、そうして窓口に出す頼みは今の頼みの納品の後に出す物になり、`cause` が null の方として数える。
- 答えが出たか: 預けた先の頼みから、回した線と続きの 2 種類のつながりだけを先へたどり、たどった中にまだ終わっていない頼み（状態が済・取り下げ・届かずのどれでもない頼み）が在れば、答えが出ていないと見る（`ledger.awaited`）。つながりは射影（台帳の行から読むたびに組み立て直す、頼みの状態と頼みの木。ファイルには書かない）で引く。頼みの木は、頼みごとに親を 1 つ決めてつないだ木で、ある頼みを親に持つ頼みをその頼みの子と呼ぶ。回した線は、頼みを受けた部署がその頼みを自分で済ませずにほかの部署へ回したとき（`--ask … --forward`。回した元の頼みは済になる）の、元の頼みから回した先の頼みへのつながりで、射影では `parent_by`（子の親を何で決めたかを書くフィールド）が `forwarded` の親子として、回した先の頼みが元の頼みの子の 1 つになる。続きは、次の形で決まる頼みである（射影のフィールド `follows`）。たどった頼みを受けた部署は、納品の要約の頭書き（1 行目と閉じの行が `+++` の TOML）の `[[open]]` に、残った疑問を 1 件ずつ、疑問の文 `question` と担当者 `holder`（その疑問を最後まで追う者）で書く。`holder` には、部署の名前のほか、その疑問を追わせるために出した頼みの受付番号を書ける。`holder` の値が受付番号のとき、その受付番号の頼みが続きになる。受付番号がリマインダーの物なら、そのリマインダーが閉じていない間は、答えが出ていないと見る（`ledger.awaited` がリマインダーの受付番号を返す）。`holder` が受付番号でない物（`owner:choose` など）は続きにならない。
- たどった頼みの子の頼みのうち、回した先でない物（その頼みを `cause` に持つ頼み）はたどらない。受けた部署が頼みの途中で出した別の仕事で、預けた答えを待つ物ではない。射影のフィールド `open`（頼みが開いているか。頼み自身が順番待ち・動いている・答え待ちのどれかか、子か続きのどれかが開いているか、続きのリマインダーが閉じていなければ開いていると見る）は子を全部たどるので、持ち主への中継のように頼みを受けたまま別件を出し続ける部署の先では閉じない（2026-10-19 の my_notes〔持ち主のメモのリポジトリで、会社の 1 つ〕の受付 22e6bf で実測。`open` で見ると、22e6bf が閉じた後も別件の子が開いていて、差し戻しがいつまでも再開しなかった）。一方、ここでたどる 2 種類の線（回した線と続き）は、どちらも `open` がたどる線（子と続き。回した先も子の 1 つ）に含まれる。そのため、預けた先からたどって当たった、まだ終わっていない頼みは、それ自身が開いているので `--todo`（頼みの状態と木を台帳から作り直して出すコマンド）にも開いていると出る。預けた先の頼みも、`open` がその頼みまでたどるので開いていると出る。ただし、`--todo` で預けた先が開いていると出ても、答えが出ていないとは限らない。開いているのが子だけなら、答えは出ていると見る。終わらないまま残った頼み（受けた作業場が消えたなど）は、`--todo` が木の前に出す「!」で始まる注記の行が、`--withdraw`（頼みを取り下げて閉じるコマンド）で閉じるよう出す。
- 今の頼みより前の頼みを受けていた間に出した頼みは、預けた先に数えない。部署が自分の納品の残った疑問の担当者に、ほかの部署が出した頼みの受付番号を書いただけの物も数えない（差し戻しを外すために、答えの出ない頼みを担当者に書く抜け道にしない）。今の頼みを受けてから出した頼みは、メインブランチに入れる件と関係が無くても数える（台帳の行からは用件を見分けられない）。そのため `--clean`（部署や作業場のうち消してよい物を並べ、残す物には訳と次に打つ手を添えるコマンド）は、預けた先の答えを待つ部署を、出した頼みの返事（納品）をまだ待つ部署とは別の行で出し、ブランチが入っていないことと、預けた先の受付と、入れる手を預けたのでなければ `--land <部署>` で入れることを、一緒に出す。
- 部署が出した頼みの返事を待つ間と、預けた先の答えを待つ間は、差し戻した回数（会話と頼みごとの控え。上限 3 回）を 0 に戻す。頼む前に上限まで差し戻された部署にも、返事や預けた先の答えが出てまだブランチが入っていなければ、また差し戻す。
- 差し戻すのは、ブランチを入れていない部署の会話がターンを終えるときだけである。預けた先の答えが出ても、部署の会話は起きない。止まったままの部署は `--clean` の一覧で「ブランチがメインブランチに入っていない」と出る。

預けたことを部署が自分で印す口を別に作る案（答え待ちの印を立てる `--wait` を納品の後にも打てるようにし、印の間は差し戻さない）は採らなかった。印を外す時を部署が手で決めることになり、預けた先が閉じても印が残る。台帳から毎回作り直せば、預けた先が閉じた後、部署の会話が次にターンを終えるときに、だれも印を外さなくてもまた差し戻す。

## 台帳と、順番待ち・作業場が食い違うとき

台帳だけから組み立てる射影（上の語の一覧のとおり、出来事の列から読むための形を組んだ物。`--todo` など）は、台帳に閉じる行の無い頼みを開いている物と出し続ける。2026-10-19 に my_notes（持ち主のメモのリポジトリで、会社の 1 つ）の作業場で `--todo` を打つと、次の 2 種類の計 7 件が、実際には順番待ちにも部署にも無いのに、開いている物として出ていた。この直しの頼みは受付 948ac0。

- 順番待ちの件が、台帳に行を残さずに消えた（6 件）: 2026-10-17 の 00:09 ごろ、my_notes の部署の 1 つの段取り（部署への頼みを配る部署）が、調べものの部署宛ての順番待ちの 6 件（5b3433・0d8bde・edd872・91e2d3・34bd4e・3b9582）のファイルを、手で受付箱の `withdrawn/` フォルダに移し、同じ本文を臨時の部署に頼み直した。頼み直した先（a8e3ec・2041a6・680ec4・4133c1 など）は別の頼みで、7 件には数えない。`--withdraw` が入ったのは同じ日の 11:31 で、それまでは取り下げの行を書く口が無かった。台帳には `ask`（`queued`）の行だけが残り、順番待ちと出た。
- 受けた作業場が、納品せずに消えた（1 件）: 2026-10-16 に窓口（持ち主と話して部署に仕事を配る会話）が 75aeee を my_notes の部署の 1 つの点検（部署の名前は `work-check-dept`）に送り、69 秒後に同じ本文を claude-plugins の点検へ 71003e として送り直した（71003e は 7 件に数えない）。71003e は済んだが、75aeee を受けた作業場（worktree のフォルダ）は納品しないまま消され、台帳では動いていると出た。

閉じ方は、台帳に取り下げ（`withdrawn`）の行を足すことにした。古い行は書き換えない。イベントソーシングの定石で、正本（ここでは台帳）に記録した出来事は書き換えず、その効果を打ち消す補償の出来事を足す（Microsoft の Event Sourcing pattern）。コードを直しても台帳に残った過去の出来事は直らないので、補償の出来事が要る。射影の側で順番待ちのフォルダ（受付箱の `queue/`）や作業場のフォルダを見て状態を変える形は採らなかった。正本が台帳とフォルダの 2 つになり、フォルダが一時に読めないだけで状態が揺れるからである。

- 見つける: `--todo` の頭の「!」の注記（`todo.strays`）が、次の 2 つを出す。順番待ちと出るのに、読んだどの受付箱の `queue/` にも件が無い物。動いている・答え待ちと出るのに、最後に受けた作業場（`ledger.received_at`。届かなかった〔`status: failed`〕物を除く `ask` の行の `to.path`、`handed` の行の `place`、打った部署がその場で受けた `taken` の行の `by.place`〔上の表の補い〕のうち最後の物）のフォルダが無い物。どちらも木からは外さない。
- 閉じる: `--withdraw <受付>`（1 件ずつ）。順番待ちに件が在れば今までどおり取り下げる。どの順番待ちにも無ければ、台帳の状態が開いている（順番待ち・動いている・答え待ち）頼みに限り、`withdrawn` の行に `was`（前の状態）と `why`（理由）を添えて、その頼みの行の在る受付箱のそれぞれに足す。最後に受けた作業場がまだ在り、その部署の属性 `company.ask`（部署の worktree の git の設定に書く、部署が今受けている頼みの受付番号）がその受付で、まだ納品していなければ、閉じずに止める（部署がまだ受けている頼みは、取り下げを `--note` で足す）。作業場が在っても、`company.ask` がほかの頼みに替わっていれば閉じる。

注記は作業場のフォルダの有無だけを見て、`company.ask` は読まない（開いている頼みの数だけ git を打つと、`--todo` が遅くなる）。そのため、作業場が在るまま頼みを手放した部署の頼み（`company.ask` がほかの頼みに替わった物）は注記に出ない。そうした頼みも頼みの木には動いている・答え待ちとして出るので、木で見つけて `--withdraw` で閉じられる。

`--withdraw` の確かめと書き込みは、受けた部署の待ち受けと同じ錠（`wake.ask_lock`）の中でする。待ち受けは順番待ちの件を消してから部署の属性を書くので、錠の外で確かめると、渡している最中の頼みを閉じてしまうからである。ただし `--take <受付> --ask <宛先>`（順番待ちの件を取り、ほかの部署へ頼み直す）は、件を消してから頼み直しの `ask` の行を書くまで、部署を立てる数十秒の間がある。その間に同じ受付に `--withdraw` を打つと、頼み直した頼みを取り下げで閉じ、後の納品でも状態は戻らない。`--withdraw` は人か会話が手で打つコマンドで、同じ受付への `--take … --ask`（手で打つか、待ち受けのフックが互いの返事を待ち合う頼みの輪をほどくときに打つ）とその数十秒の間に重なったときだけ起きるので、知った上で残す。

## リマインダー

部署か窓口が、後で見ること（「この日に見る」「この頼みが閉じたら見る」）を台帳に残す形。メモの文（my_notes の段取りの `desk-backlog.md` など）に「次に X が起きたら見る」と書くだけだと、メモを読み直すまで思い出されず、条件が来ても気づかないまま流れる。台帳に持たせると、見る時が来たことを機械が知らせられる。

行の形:

- `remind`（`--remind <何を見るか>`）: `id`（リマインダーの受付番号）・`text`（何を見るか）・`holder`（担当者。知らせを受ける会話の待ち受けの宛先で、`会社/名前`。打った部署か窓口）・`on`（見る日の UNIX 時刻か `null`）・`after`（閉じるのを待つ頼みの受付番号の並び）・`from`（打った会話の `name`・`session`・`place`）。打った場所の会社の受付箱に書く。
- `reminded`: 見る時が来て担当者に知らせた。`why` に来た訳（見る日が来たか、`after` のどの頼みが閉じたかの文）。同じ受付箱に、担当者に宛てた知らせの行（上の「表の補い」のとおり `to` が文字列の行。ここでは `to` が担当者の `会社/名前`、`kind` が `note`）と並べて書く。知らせの代わりに頼んだとき（下の「見る時と知らせ方」）は、知らせの行を書かず、`child` に出した頼みの受付番号を書く。
- `remind-done`（`--remind-done <受付>`）: 閉じた。`by` に打った会話の `session` と `place`。

見る時と知らせ方:

- 見る時は、`on` の日時が過ぎた時と、`after` の頼みのどれかが閉じた時（済・取り下げ・届かず。回した頼みも済になる）の、先に来た方。`--on` は打った機械の現地時刻で読み、日付だけならその日の 0 時。`--after` だけのリマインダーは、その頼みが閉じるまで見る時が来ない。`--on` も `--after` も無いリマインダーは立てられない。条件を文でしか書けない待ち（「次に X が起きたら」「数が 25 件になったら」）は、機械が見分けられないので、見直す日を `--on` に付ける。閉じた頼みを `--after` に渡すと断る（もう見る時なので、今見る）。
- `--due`（頼みと納品のたびに裏で走る。`skills/dispatch/references/start.md`）が、会社ごとのロック（受付箱の下の `due.lock`。2 つの `--due` が同じ会社を同時に数えないためのもの）を取った中で、見る時が来てまだ知らせていない物を、担当者の待ち受けへ台帳の知らせで渡し、`reminded` の行を書く。知らせの行そのものが知らせた印になる（`reminded` の行を書く前に落ちても、次の `--due` は知らせ直さない）。知らせは 1 度だけで、閉じるまで `--todo` に出続ける。`--due --dry-run` は知らせる物を言うだけで書かない。
- 担当者の名前の部署か窓口が立っていなければ、知らせを拾う待ち受けが無い。頼みを済ませて畳まれた部署（エフェメラルの部署。頼まれたときだけ立てて、納品の後に畳む部署）などで起きる。このときは、知らせの代わりに同じ文を `--ask` と同じ道で頼む（`reminds.route`・`reminds.asker`）。宛先は次の順で決める。
  - 担当者の名前が会社の形のオンデマンドの受け持ちなら、その受け持ち。受け持ちの名前の部署が立つ。頼みごとに別の部署を立てる `per_ask` の受け持ちは除く。
  - 担当者の名前が役で、その役の永続の部署が別の名前で立っていれば、その部署。
  - それ以外（頼みごとの部署・作業の部署など、名前で立て直せない部署）は、担当者の会社の窓口。
- 頼み元は担当者の会社の窓口で、立った部署の納品は窓口の待ち受けに届く。担当者の会社が端末に開いていないか窓口が決まらなければ、頼まずに前と同じく知らせの行を書く（頼み元の無い頼みは納品の返り先が無く、部署が畳めない）。
- 頼みが通らなかったとき（受ける会社のゲートが断ったなど）は、`reminded` の行を書かず、次の `--due` で頼み直す。通ったかは `orders.ask` の終了の値でなく、台帳の頼みの行（`kind: ask` の `status` が `sent` か `queued`）で見る。部署に届いた後で立てる道が 0 以外を返すことがあるため。
- 頼みの道では、頼みの行が知らせた印にならない。頼みが通った後、`reminded` の行を書く前に落ちると、次の `--due` がもう一度頼む。同じ中身の頼みが動いている部署には積まれない（`orders.ask`）ので、起きても頼みが 2 つ並ぶことは少ない。
- 頼みも納品も無い間は、`--due` を手元の OS の予定（launchd・cron など。`skills/dispatch/references/start.md`）に打たせていなければ `--due` が走らず、知らせも出ない。works-dispatch はリマインダーのために予定を足さない（持ち主「一旦cronは不要で。」2026-10-18、my_notes の受付 bad118）。その間も、`--todo` を打てば、打ったその時刻で見る時の来た物が出る。
- `--todo` は、受付番号を渡さないとき、頼みの木（上の「頼みの木」）より前に「リマインダー:」の見出しを付けて、見る時の来た開いた物を出す（`--all` でまだ来ていない物と閉じた物も。`--json` は `reminders`）。`--html` のページには出さない。
- 見たら `--remind-done` で閉じる。見る日を替えたいときは、閉じて `--remind` で立て直す（行を書き換える種類は持たない）。

採った標準と採らなかった案:

- 見る日と、待つ頼みの閉じを、別々のトリガーとして持ち、先に来た方で鳴らす: JSCalendar（RFC 8984）の alerts に倣った。1 つの項目が複数の Alert を持ち、各 Alert が自分のトリガーで別々に鳴る。
- 文でしか書けない待ちにも見る日を付けさせる: Taskwarrior の waiting の状態は wait の日時を必ず持つ（Taskwarrior の仕様書 `doc/devel/rfcs/task.md`〔下の出典〕の「MUST」）。見る日の無い待ちは、思い出す時が無いまま残るので、作らせない。
- 頼みが閉じたら見る（`after`）: Taskwarrior の depends（待つ仕事が済むと、待っていた仕事が ready になる）に当たる。
- 知らせたら 1 度で印す（知らせの行と `reminded`）: RFC 9074 の ACKNOWLEDGED は「acknowledged (or sent, if acknowledgement is not possible)」で、受けたかを返せない知らせは送った時に印す。RFC 8984 の acknowledged も、同じ知らせを重ねて鳴らさないための値。
- 自由な条件の文を機械で評価する形: 採らない。条件の書き方を決めても、書き手が決めた書き方の外の言い方をするたびに、それを読むコードを足す要があり、足すまでは、読めない条件のリマインダーが知らせの出ないまま残る。代わりに見直す日を付けさせ、その日が過ぎた後の最初の `--due`（頼みか納品の後に裏で走る）の知らせか、`--todo` で目に入る形にした。
- cron・launchd で刻む形: 採らない（上の持ち主の決め）。

## 採った物と採らなかった案

採ったのは、自前の小さな射影（Python の標準ライブラリだけ）である。ツールは借りず、考え方だけを借りた。

- イベントソーシングの射影と作り直し（Fowler、Microsoft、Marten）: 採った。正本は追記だけのログで、読む形は作り直す。台帳はもとからこの形に近い（追記だけ・頭から読む）。
- causation id（Marten と KurrentDB が出来事の付け足しのフィールドに持つ）: `cause` として採った。
- 状態を最後の出来事で決める（Linear）: 採った（終わりの状態を戻さない足しは「決めたこと」の 3）。
- 状態の名前（JSCalendar の progress、iCalendar の STATUS）: 対応を持つ形で採った。答え待ちは標準に無いので、in-process の中の 1 つとした。
- 項目どうしをフィールドで結ぶ（iCalendar の RELATED-TO、JSCalendar の relatedTo、Beads の依存）: `cause`・`forwarded` の `child`・`holders` の `ask` として採った。
- 個人の仕事の一覧の見た目（todo.txt の 1 行 1 仕事と済の印、Taskwarrior の端末の一覧）: 見せ方の形として採った。書式そのものは採らない（台帳の行は出来事で、仕事 1 件の今の値ではない）。

採らなかった案と訳:

- KurrentDB（出来事を貯めるデータベースのサーバー）: 常駐のサーバーが要る。works-dispatch は手元で打つたびに動く Python の台本で、常駐させる物を増やさない。
- Marten（.NET の、PostgreSQL に出来事を貯めるライブラリ）: 使う言語と置き場が違う。
- Python の eventsourcing ライブラリ: 保存の置き場をライブラリの物（SQLite・PostgreSQL など）に置き換えることになり、今の JSONL の台帳と、それを読む待ち受けを作り直すことになる。得る物は射影の作り直しの決まりだけで、それは数十行で書ける。
- MCP Agent Mail（エージェントどうしの受信箱を MCP のサーバーで出すツール）: 訳は 2 つある。1 つ目はライセンスで、MIT に付けた但し書き（rider）が、OpenAI と Anthropic とその関連会社と、それらのために動く者にどの権利も与えず、さらに、それらに向けてこのソフトウェアを使わせること（make available・permit access）も禁じる。works-dispatch の部署は Claude Code の会話で、モデルは Anthropic のサーバーで動き、ツールを通して受信箱を読み書きする。これが Anthropic に使わせることに当たるかは読み方が割れうるが、破れば許しがその場で切れる条項なので、当たるおそれのある使い方はしない。2 つ目は中身で、仕事の状態を自分では持たない（仕事の置き場には Beads を勧めている）ので、ライセンスを抜きにしても、頼みの状態の正本にはならない。
- Linear（課題管理のクラウドのサービス）をツールとして使う: 台帳を外のサービスに置くことになる。考え方（最後の出来事で状態を決める）だけ採った。
- Gas Town（多数のエージェントを束ねるツール）の problems の画面: 止まったエージェントを見つけて人に見せる、誰のターンかの画面である。部署の様子は `--tree` が持ち、`--todo` は誰のターンを出さないと決めた（「決めたこと」の 5）ので、重ねない。
- Beads（エージェント向けの課題の置き場）・Taskwarrior（端末の仕事の一覧のツール）を仕事の置き場にする: 正本が二重になる（台帳と別の置き場）。Taskwarrior の公式の文書は、ファイル共有で同期したときに仕事が merge されないと書く。
- 楽観的な並行制御（読んだ後に列が変わっていれば追記を断る。イベントソーシングの書き込みの定石）: 台帳の書き手は、書く前に台帳の中身を条件にしない（読んで確かめてから書く決まりが無い）ので、断る理由になる食い違いが起きない。同時の書き込みは、追記の形で開いたファイルに 1 行を 1 回で書くことで、行が混ざらないようにしている（`deliver.log`）。書きかけの行は、読む側の `deliver.records` が飛ばす。
- 相関の id を行に持つ（CloudEvents の拡張、W3C Trace Context の trace-id、Correlation Identifier の型）: 「足したフィールドと種類」のとおり、親からルートが決まるので持たない。
- 古い行を書き換えて移す（移行）: 古い行はフィールドが無いだけで、読み方の側で補える（`inferred` と `todo.questions`）。正本を書き換えると、ほかの会社の台帳と食い違い、取り消せない。
- 射影をファイルに保存する（スナップショット）: 毎回の読み直しで足り（「決めたこと」の 2）、保存すると正本との食い違いの元が増える。

## 古い行の扱い

移行は要らない。台帳は書き換えない。

- `cause` のフィールドの無い `ask` の行: 上の「頼みの木」の 3 の `inferred`（親の決め方の 1 つで、打った作業場が受けていた頼みから親を推す。どれで決めたかは射影のフィールド `parent_by` に残る）で親を推す。`cause` のように打った時に書いた値ではなく、`cause` の無い行に限って読む側が推して補う物である。推した親は台帳に書かず、読むたびに推す。
- `title` のフィールドの無い `ask` の行: 本文のファイルから題を読む（上の「題」）。
- `holders` のフィールドの無い `deliver` の行: 要約のファイルの「残った疑問」から担当者を拾う。`--todo` が担当者の文字列から受付番号を拾うのは、この行だけである。担当者の文字列に末尾の 6 文字だけの受付番号が在れば、`--todo` が台帳から頼みの状態と木を組み立てる（上の語の一覧の「射影」。`nodes/ledger.py`）ときに頼みへ引く（読んだ台帳の頼みのうち、ちょうど 1 件に当たるときだけ）。要約のファイルが無ければ担当者は無い物とし、続き（上の「頼みの木」の続き）も結ばない。2026-10-19 に 4 つの受付箱で数えると、6 文字から頼みへ引けたのはこの古い行の 21 件だけで、`holders` のフィールドを持つ行では 0 件だった。
- `waiting`・`resumed` の行が無かった頃の答え待ち: 印が部署の属性（worktree ごとの git の設定の `company.waiting`）にしか無かったので、台帳からは動いているに見える。知った上で残す。開いている物に数える側に寄るので、仕事は漏れず、その頼みが納品されれば済になるからである。

## 種類を足すときの決まり

台帳に新しい種類（`kind`）の行を書くときは、次の 2 か所に足す。

1. `dispatch/nodes/ledger.py` の `KINDS` に、種類の名前と、頼みの受付番号の入るフィールドの名前（頼みを指さなければ `None`）を足す。例: `"paused": "id",`。状態を変える種類なら、`build` の中の、行を時刻の順に当てる `for` の `elif kind == …` の並びにも足す（状態は `STATES` に在る物から選ぶ。新しい状態を足すなら、`STATES` と `todo.schema.json` の `state` と `progress` の `enum` にも足す）。
2. `dispatch/schemas/ledger.schema.json` の `rows` の行の `kind` の `enum`。

行のフィールドの意味を変える（今のフィールドを別の意味で使う・フィールドを消す）ときは、行に版のフィールドを足して `ledger.schema.json` の `schema` の版を上げ、`build` が版の無い古い行も読めるようにする。フィールドを足すだけなら版は上げない。

`dispatch/tests/test_ledger.py` の Catalog の試験が、次を照合する。

- コードの中で台帳に書く行（`kind` と `at` を持つ辞書と、知らせを書く `wake.notice` に渡す種類）の種類が、全部 `KINDS` に在るか。
- `ledger.schema.json` の `kind` の `enum` と `KINDS` が同じか。
- `todo.schema.json` の状態の値（`state` と `progress`）が `STATES` と同じか。
