# 本流に入れる（`--land`）

会社の形に `[land]` を書く人と、`--land` が何をするかを知りたい人向け。使い始め方と言葉（部署・会社・納品）は [README](../README.md)、使う人向けの手順の全部は [SKILL.md](../skills/dispatch/SKILL.md)。

`python3 dispatch.py --land <部署>` は、部署（名前か枝の名前で指す）の枝を、会社の形（`.claude/company.toml`、無ければ設定の置き場〔dispatch の設定のファイル `~/.config/works-dispatch/dispatch.toml` の隣〕の `companies/`）の `[land]` の決まりで本流に入れる。会社の形の設計（リポジトリの根の [`docs/specs/2026-10-16-company-shape-design.md`](../../docs/specs/2026-10-16-company-shape-design.md)）の 8 章（検証をどこで回すか）と 4.10 の 1（部署の畳み方と成果の取り込み）に当たる。部署の窓は、その部署の会話の画面を出した herdr（端末を作業場ごとに分け、中の会話を外から操作する道具）のペイン。流れは、入口の `dispatch.py` から分けた `dispatch/landing.py` が持つ（ほかの部署と同時に `dispatch.py` を触るぶつかりを減らすため、別のファイルにした）。

- 欄:
  - `mode`: 取り込み方。`ff-after-ci`（関門が緑なら本流を早送り）、`pr`（部署の枝を origin に出して PR を出し、止める。`gate`・`check`・`bump` は使わない）、`none`（何もしない）。`[land]` が無ければ `none` で、何もしない。
  - `gate`: 関門（本流に入れる前に必ず通す検証）。CI の枝の形（固定の頭の後ろに `/*`。例 `release/*`。`*` に部署の名前が入る。できた枝の名前が本流か部署の枝と同じなら止める）か、`check`（手元の検証を `--land` の命令が回す）。`mode = "ff-after-ci"` なら省けない（無ければ決まりの誤りで止める）。
  - `check`: 部署が手元で回す検証のコマンド。`gate = "check"` のときは、`--land` の命令が部署の場所（版を上げるときはその一時の場所）で回す（このときは省けない）。`gate` が CI の枝の形のときは、`--land` はこの欄を回さず、部署にも送らない（会社の形のファイルに書いてあるだけの、部署向けの書き置き）。
  - `bump`: `marketplace` なら、部署は版を上げずに出し、取り込むときに `--land` の命令が版を上げる commit を足してから関門に出す。中身の無い版は作らない: 順 3 で版を上げる前に、版を最後に上げた後にフォルダの中のファイルを変えた（commit した）プラグインの `CHANGELOG.md` を見て、`## [Unreleased]` に `### Fixed` のような `#` で始まる行のほかに何も書いてなければ、版を上げずに `--land` 全体を止める（何も push しない。終わりの値は 1。どのプラグインの `CHANGELOG.md` かを出す）。部署が利用者に効く違いを書き足して commit したら、`--land` を打ち直す。版を上げずに取り込む道は用意しない。marketplace は版が変わった時だけ中身を取り直すので、上げなければ変えた中身が利用者に届かない。また、このリポジトリの試験 `VERSION_BUMP_OK`（`tests/run.sh`。ファイルを変えたのに版が据え置きのプラグインを、main と release/* の CI で赤にする）も赤になる。上げ幅は、`## [Unreleased]` に Added・Changed・Deprecated・Removed の節が有れば minor、無ければ patch。ただし版を最後に上げた後に変えたファイルが試験と文書だけ（`tests`・`test`・`docs` のフォルダの下、`test_*.py`・`*_test.py`・`conftest.py`、プラグインの直下の `README.md`・`CHANGELOG.md`・`CONTRIBUTING.md`・`LICENSE`）なら、節によらず patch にする（Semantic Versioning の minor は機能の追加に当てる物で、利用者が動かす物を変えていない直しは当たらない）。`SKILL.md` やエージェントの `.md` は Claude Code が読んで動く物なので、文書に数えない。そう決めたときは `--land` が注記を出す。
  - `main`: 本流の枝。省けば origin の既定の枝。
  - 役ごとに `[land.roles.<役>]` で上の欄を替えられる（書いた欄だけを上に重ね、書かない欄は `[land]` の値のまま。役は部署の属性 `company.role`。部署の属性は、部署の worktree ごとの git の設定 `company.<名前>` に dispatch が書く）。
- 順（`ff-after-ci`）:
  1. 本流を取り直す（origin の本流の枝を fetch する）。部署の枝がもう本流に入っていれば、片付けへ進む。
  2. 本流が部署の枝の祖先でなければ（ほかの部署が先に入れた）、関門に出さずに、部署に「本流の上に載せ直して（rebase）push し直す」と頼んで止める。
  2a. 書き換えの取り合いの関門: 部署が本流を最後に知った位置（属性 `company.base`。`--task` が枝を作ったときの origin の本流と、その部署の `--land` で入れた後の本流）より後に、ほかの部署が本流へ入れた行を、部署の枝が消して（書き換えて）いれば、関門に出さずに止め、部署の窓に「どの commit（件名）の、どのファイルの何行目を消すか」を打ち込む。部署が前に読んだ中身を覚えたまま書き直すと、ほかの部署が入れたばかりの行を消しても git の衝突にならず、関門の試験も通る（まっさらな環境での 2 回目の試しの 5）ため。部署はその行を残す形に取り込み直して push し、`--land` を打ち直す。わざと消すなら `--land <部署> --keep-removal` で通す。位置の記録が無い部署（0.19.8 までに立てた部署）は見ずに注記を出す（今の本流との merge-base は、載せ直した後の枝では本流の先頭になり、何も見つけないため）。入れた後は、その部署の位置を入れた後の本流に進める。
  3. `bump` があれば、一時の場所（枝に乗らない worktree）で、部署の枝の先頭の上に版を上げる commit を作る。部署の枝は動かさない。以下、関門に出し、緑なら本流にする commit を「候補」と呼ぶ（版を上げる commit を作ればそれ、作らなければ部署の枝の先頭）。「候補の木」はその commit の中身のファイル。
  4. 関門に出す。CI の枝なら、まず候補の木の GitHub Actions の設定（`.github/workflows`）のどれかがその枝の頭（`release/` など）を書いていることを確かめ（無ければ止める）、その枝へ候補の commit を push して（前の物は上書き）、その commit の run が現れるまで 10 秒おきに見に行き（回数に上限を置かない。期限を足さない決まり D5〔[internals.md](internals.md) の柵〕のため、上限の代わりに、run が起きない設定を push の前の確かめで弾く）、`gh run watch` で終わりを待つ（run の結論が `success` のときだけ緑、ほかは赤）。設定が枝の頭を書いていても、ほかの絞り（変えたファイルの条件など）で run が起きなければ、`--land` は待ち続ける。そのときは人が `--land` を止める（Ctrl-C）。watch が途中で戻れば、赤とせずに止める。`gate = "check"` なら、関門の枝は作らず、`check` のコマンドを候補の場所で回し、終わりの値 0 を緑、それ以外を赤とする（赤なら下の順の 5 へ、緑なら順の 6 へ進む。6 で消す関門の枝は無い）。
  5. 赤なら、部署に失敗の要点（CI なら落ちた job と step、記録の終わりの行。`check` なら出力の終わりの行）を頼んで止める。
  6. 緑なら本流を取り直し、まだ候補の祖先なら、origin の本流を候補へ早送りで push し、手元の本流も早送りし、関門の枝を消す。進んでいれば、部署に載せ直しを頼んで止める。push が断られたら本流を取り直し、先に進んでいたときだけ載せ直しを頼む（枝の保護や認証で断られたなら、頼まずに止める）。2 つの部署が同時に入れようとしても、本流に入る順は早送りで 1 本ずつに決まる。
  7. 入れたら、`--clean` と同じ決まりと部品で部署を片付ける（都度の部署で、会話が終わり、未コミットの変更・手元にしか無い commit・stash が無く、枝が本流に入っているとき。条件の全部は SKILL.md の `--clean`。常駐の部署は残す）。片付けられない都度の部署（納品の直後で会話がまだ止まりきっていない、など）は、入れた印（属性 `company.landed`。入れた commit）を書いて残し、次の `--land`（どの部署を入れるときでも）が、印の付いた部署のうち片付けられる形になった物を一緒に片付ける（`--clean` は消せる部署を並べるだけで、`--clean --apply` で消す。こちらでも片付く）。会話が止まるのを待たないのは、期限を足さない決まり D5 のため。都度の部署は `--task` で `--resident` を付けずに立てた部署（属性 `company.residency` が無い部署も都度とみなす）、常駐の部署は `--resident` を付けて立てた部署。
- `--dry-run` を付けると、決まりと、することの見立て（載せ直しが要るか・入れる commit・上げる版・関門・片付け）を出すだけで、何も書かない。部署の枝は部署の場所の HEAD を読み（部署自身の枝なので取り直さない）、本流の先頭は fetch せず origin に問い合わせて読む（`git ls-remote`。手元の ref は変えない）。上げる版は、本当に打ったときに一時の場所で回すのと同じ計算を、一時の場所を作らずに部署の場所で回して見積もる。関門の枝への push・手元の検証・部署の窓への打ち込み・片付けはしない。終わりの値は、本当に打ったときに止まると見立てた所（載せ直しが要る・中身の無い版など）と、見立てそのものが失敗した所（origin を読めないなど）では 1、通ると見立てたら 0。
- 部署への頼み（載せ直し・赤の直し）は、部署の窓への打ち込みだけ。窓が無ければ、頼みの文を出して呼んだ側に渡させる。今は頼みと納品の仕組み（`--ask`・`--deliver` の受付箱と台帳）を通さない。そちらに替える予定。
- 終わりの値: 0 は入れた・PR を出した・決まりが `none`。1 は止めた・赤・載せ直しを頼んだ。2 は決まりか引数の誤り。

例（my_notes。検証は `tools/check.py` を手元で回し、通れば早送りで入れる）:

```toml
[land]
mode = "ff-after-ci"
gate = "check"
check = "python3 tools/check.py"
```

例（claude-plugins。部署は変えたプラグインのフォルダの下の試験だけを手元で回し、関門は `release/*` への push で走る CI。版は取り込むときに上げる。`gate` が CI の枝なので `--land` は `check` を回さない。`check` の行は works-dispatch を変えたときの書き置きで、部署はほかのプラグインを変えたらフォルダを替えて回す）:

```toml
[land]
mode = "ff-after-ci"
gate = "release/*"
check = "python3 -B -m unittest discover -s works-dispatch/dispatch/tests -t ."   # 変えたプラグインの試験に替えて回す
bump = "marketplace"
```
