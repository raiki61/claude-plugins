# メインブランチに入れる（`--land`）

会社の形に `[land]` を書く人と、`--land` が何をするかを知りたい人向け。使い始め方と言葉（部署・会社・納品）は [README](../README.md)、使う人向けの手順の全部は [SKILL.md](../skills/dispatch/SKILL.md) と、そこから主題ごとに指す別ファイル（`skills/dispatch/references/`）。

この文書の言葉:
- 会社: 1 つのリポジトリで AI の会話を役ごとに分けて働かせる組織。決まりは会社の形（`.claude/company.toml`）に書く。
- 部署: 会社の中の 1 つの仕事の場。リポジトリの git worktree 1 つと、そこで動く Claude Code の会話 1 つ。部署のブランチは、その worktree のブランチ。
- 代表の clone: 部署の worktree を作る元の clone。窓口（持ち主と話す会話。`--desk` で名付ける）がここで動く。
- メインブランチ: 取り込み先の origin のブランチ（既定は origin の既定のブランチ。`main` など）。
- ゲート: メインブランチに入れる前に必ず通す検証（CI か手元のコマンド。下の `gate`）。
- 候補: ゲートに出し、緑ならメインブランチにする commit（下の順の 3）。

`python3 dispatch.py --land <部署>` は、部署（名前かブランチの名前で指す）のブランチを、会社の形（`.claude/company.toml`、無ければ設定の置き場〔dispatch の設定のファイル `~/.config/works-dispatch/dispatch.toml` の隣〕の `companies/`）の `[land]` の決まりでメインブランチに入れる。会社の形の設計（リポジトリのルートの [`docs/specs/2026-10-16-company-shape-design.md`](../../docs/specs/2026-10-16-company-shape-design.md)）の 8 章（検証をどこで回すか）と 4.10 の 1（部署の畳み方と成果の取り込み）に当たる。部署の窓は、その部署の会話の画面を出した herdr（端末を作業場ごとに分け、中の会話を外から操作するツール）のペイン。流れは、入口の `dispatch.py` から分けた `dispatch/landing.py` が持つ（ほかの部署と同時に `dispatch.py` を触るぶつかりを減らすため、別のファイルにした）。

- フィールド:
  - `mode`: 取り込み方。`ff-after-ci`（ゲートが緑ならメインブランチを fast-forward）、`pr`（部署のブランチを origin に出して PR を出し、止める。`gate`・`check`・`bump` は使わない）、`none`（何もしない）。`[land]` が無ければ `none` で、何もしない。
  - `gate`: ゲート（メインブランチに入れる前に必ず通す検証）。CI のブランチの形（固定の頭の後ろに `/*`。例 `release/*`。`*` に部署の名前が入る。できたブランチの名前がメインブランチか部署のブランチと同じなら止める）か、`check`（手元の検証を `--land` のコマンドが回す）。`mode = "ff-after-ci"` なら省けない（無ければ決まりの誤りで止める）。
  - `check`: 部署が手元で回す検証のコマンド。`gate = "check"` のときは、`--land` のコマンドが部署の場所（版を上げるときはその一時の場所）で回す（このときは省けない）。`gate` が CI のブランチの形のときは、`--land` はこのフィールドを回さず、部署にも送らない（会社の形のファイルに書いてあるだけの、部署向けの書き置き）。
  - `bump`: `marketplace` なら、部署は版を上げずに出し、取り込むときに `--land` のコマンドが版を上げる commit を足してからゲートに出す。中身の無い版は作らない: 順 3 で版を上げる前に、版を最後に上げた後にフォルダの中のファイルを変えた（commit した）プラグインの `CHANGELOG.md` を見て、`## [Unreleased]` に `### Fixed` のような `#` で始まる行のほかに何も書いてなければ、版を上げずに `--land` 全体を止める（何も push しない。終わりの値は 1。どのプラグインの `CHANGELOG.md` かを出す）。部署が利用者に効く違いを書き足して commit したら、`--land` を打ち直す。版を上げずに取り込む道は用意しない。marketplace は版が変わった時だけ中身を取り直すので、上げなければ変えた中身が利用者に届かない。また、このリポジトリの試験 `VERSION_BUMP_OK`（`tests/run.sh`。ファイルを変えたのに版が据え置きのプラグインを、main と release/* の CI で赤にする）も赤になる。上げ幅は、`## [Unreleased]` に Added・Changed・Deprecated・Removed のセクションが有れば minor、無ければ patch。ただし版を最後に上げた後に変えたファイルが試験と文書だけ（`tests`・`test`・`docs` のフォルダの下、`test_*.py`・`*_test.py`・`conftest.py`、プラグインの直下の `README.md`・`CHANGELOG.md`・`CONTRIBUTING.md`・`LICENSE`。`plugin.json` は説明〔`description`〕の字だけを変えたとき）なら、セクションによらず patch にする（Semantic Versioning の minor は機能の追加に当てる物で、利用者が動かす物を変えていない直しは当たらない）。`SKILL.md` やエージェントの `.md` は Claude Code が読んで動く物なので、文書に数えない。そう決めたときは `--land` が注記を出す。
  - `main`: メインブランチの名前。省けば origin の既定のブランチ。
  - `queue`: メインブランチへ入れる列（land-queue）の置き場。共通の `.git`（`git rev-parse --git-common-dir`）の下のフォルダの相対の名前（例 `land-queue`。絶対のパスと `..` は決まりの誤りで止める）。書けば、`--land` は順の 1 でメインブランチを取り直す直前に列へ申し出て、順の 6 で push し終える（か、止まる）まで列の先頭を持つ。同じ clone（worktree を含む）で同時に打った `--land` と、同じ形の札で同じ列に並ぶほかの処理（my_notes の `tools/land_queue.py` を使う collect など）は、申し出た順に 1 本ずつ「リベース → ゲート → push」を通り、互いの push でメインブランチが先に進んでやり直すことが無くなる。列の決まり: 申し出たときに `<time.time_ns() を 20 桁の 0 埋め>-<pid>.ticket` の札を作って排他のロック（POSIX は flock、Windows は msvcrt.locking）を掛け、終わるまで持つ。札は名の小さい順に並べ、ロックの外れた札（作ってから 10 秒を過ぎた物）は持ち主の処理が落ちた物として消す。先頭の生きた札になったら、置き場の `lock` のファイルに待たずに排他のロックを掛け、取れたら進む。待つ長さに上限は置かない（期限を足さない決まり D5）。止めるのは人の Ctrl-C で、そのときも札を消す。待つ間は、前に何本居るかを、数が変わるたびに 1 行出す。役ごとの `[land.roles.<役>]` には書けない（列は clone ごとに 1 つなので）。省けば列に入らない（前の版と同じ動き）。この鍵を知らない前の版の `--land` は、知らない鍵として止まる（列を無視して走ることは無い）。実装は `dispatch/nodes/landqueue.py`。
  - 役ごとに `[land.roles.<役>]` で上のフィールドを替えられる（書いたフィールドだけを上に重ね、書かないフィールドは `[land]` の値のまま。役は部署の属性 `company.role`。部署の属性は、部署の worktree ごとの git の設定 `company.<名前>` に dispatch が書く）。
- 順（`ff-after-ci`）:
  1. メインブランチを取り直す（origin のメインブランチを fetch する）。部署のブランチがもうメインブランチに入っていれば、片付けへ進む。
  2. メインブランチが部署のブランチの祖先でなければ（ほかの部署が先に入れた）、部署の場所でブランチをメインブランチの上に `git rebase` でリベースし、origin の部署のブランチもリベースした物にしてから先へ進む（[git rebase](https://git-scm.com/docs/git-rebase)）。ぶつかったら、機械で解ける物だけを解いて続ける。1 つは git rerere（前に手で解いたのと同じぶつかりを、git がその解き方で解く。[git rerere](https://git-scm.com/docs/git-rerere)。--land は、代表の clone の git の設定（local）に rerere.enabled と rerere.autoUpdate を true で書いてからリベースする。持ち主〔このプラグインを使う人〕がその値を git の設定のどこか〔local・global・system〕にもう書いていれば替えない）。もう 1 つは変更の記録（`CHANGELOG.md`）の `## [Unreleased]` の頭のぶつかりで、部署の側の書き足しを Unreleased のすぐ下に、メインブランチの側をその後に置く（部署は版を上げないので、部署の書き足しはいつもそこに在る）。変更の記録には git の union の merge driver を使わない（原典が、足した行の順が乱れうると書く。[gitattributes](https://git-scm.com/docs/gitattributes) の Built-in merge drivers）。ほかのぶつかりが残れば、リベースをやめて元のブランチに戻し、部署に「メインブランチの上にリベースして（rebase）push し直す」とぶつかるファイルを添えて頼んで止める。
  2a. 書き換えの取り合いのゲート: 部署のブランチが、ほかの部署が入れたばかりの行を消していないかを見る。部署が前に読んだ中身を覚えたまま書き直すと、そうした行を消しても git の衝突にならず、ゲートの試験も通ってしまう（試しの記録 [`docs/trials/2026-10-16-clean-env-2.md`](../../docs/trials/2026-10-16-clean-env-2.md) の 5 で実際に起きた）。見るのは、部署がメインブランチを最後に知った位置（属性 `company.base`。`--task` がブランチを作ったときの origin のメインブランチか、その部署の前の `--land` で入れた後のメインブランチ）より後に、ほかの部署がメインブランチへ入れた行。部署のブランチがその行を消して（書き換えて）いれば、順の 4 のゲート（CI か `check` の検証）に出さずに `--land` を止め、部署の窓（その部署の会話を出した herdr〔端末を作業場ごとに分け、中の会話を外から操作するツール〕のペイン）に「どの commit（件名）の、どのファイルの何行目を消すか」を打ち込む。部署はその行を残す形に取り込み直して push し、`--land` を打ち直す。わざと消すなら `--land <部署> --keep-removal` で通す。ファイルの名前の付け替えは git の名前の付け替えの見つけ方（`git diff -M`）で追い、部署のブランチが名前を替えたファイルはメインブランチでの古い名前と行番号で突き合わせる。新しい名前へ運んだ行は消したと数えず、止めたときに示す名前と行番号はメインブランチでの古い名前の物。git が付け替えと見なさない物（中身を大きく書き換えたファイルなど）は、消して作り直したと読む。位置の記録が無い部署（works-dispatch 0.19.8 までに立てた部署）は見ずに注記を出して先へ進む（今のメインブランチとの merge-base は、リベースした後のブランチではメインブランチの先頭になり、何も見つけないため）。メインブランチに入れた後は、`--land` が、入れた部署の位置（属性 `company.base`）を入れた後のメインブランチに進める。
  3. `bump` があれば、一時の場所（ブランチに乗らない worktree）で、部署のブランチの先頭の上に版を上げる commit を作る。部署のブランチは動かさない。以下、ゲートに出し、緑ならメインブランチにする commit を「候補」と呼ぶ（版を上げる commit を作ればそれ、作らなければ部署のブランチの先頭）。「候補の木」はその commit の中身のファイル。
  4. ゲートに出す。CI のブランチなら、まず候補の木の GitHub Actions の設定（`.github/workflows`）のどれかがそのブランチの名前の固定の頭（`gate` に書いた形の `/*` の前。`gate = "release/*"` なら `release/`）を書いていることを確かめ（無ければ止める）、そのブランチ（ゲートのブランチ。`gate` の `*` に部署の名前を入れた物。`gate = "release/*"` で部署 `fix-x` なら `release/fix-x`）へ候補の commit を push して（前の物は上書き）、その commit の run が現れるまで 10 秒おきに見に行き（回数に上限を置かない。期限を足さない決まり D5〔dispatch のコードに期限（timeout）を足さない。[internals.md](internals.md) の「チェック D1〜D9」〕のため、上限の代わりに、run が起きない設定を push の前の確かめで弾く）、`gh run watch` で終わりを待つ（run の結論が `success` のときだけ緑、ほかは赤）。push の前の確かめが見るのは、設定のファイルにブランチの頭の字が在るかだけ。字が在っても、ほかの絞り（変えたファイルの条件など）で run が起きなければ、確かめでは弾けず、`--land` は待ち続ける。そのときは人が `--land` を止める（Ctrl-C）。watch が途中で戻れば、赤とせずに止める。`gate = "check"` なら、ゲートのブランチは作らず、`check` のコマンドを候補の場所（順の 3 で版を上げる commit を作ったならその一時の場所、作らなければ部署の場所）で回し、終わりの値 0 を緑、それ以外を赤とする（赤なら下の順の 5 へ、緑なら順の 6 へ進む。6 で消すゲートのブランチは無い）。
  5. 赤なら、部署に失敗の要点（CI なら落ちた job と step、記録の終わりの行。`check` なら出力の終わりの行）を頼んで止める。
  6. 緑ならメインブランチを取り直す。メインブランチがまだ候補の祖先なら、次の 3 つを順にする。origin のメインブランチを候補へ fast-forward で push する。代表の clone（部署の worktree を作る元の clone。窓口の会話はここで動き、フックと決まりをこの作業ツリーから読む）の手元のメインブランチも、いつも `git merge --ff-only` で fast-forward する（書きかけのファイルは残る）。ゲートのブランチを消す。代表の clone を進められないとき（書きかけがメインブランチの変更とぶつかる・メインブランチに無い commit が有る・git が誤りを返す）は、そこだけ飛ばして先へ進み、その会社の窓口（代表の clone で `--desk` で名付けた、持ち主と話す会話）へ知らせる。知らせは受付箱の台帳（`.git/company/inbox/log.jsonl`）に足す 1 行で、その行が窓口の会話にターンを始めさせる。push の後の取り直しが落ちても、push した候補までは fast-forward する。代表の clone の手元のメインブランチは、部署が `--deliver`（納品）した後にも、origin のメインブランチの今の先頭まで同じく進める。取り直したメインブランチに候補に無い commit が入っていて（候補を作った後にほかの部署が先に入れた、など）、メインブランチが候補の祖先でなくなっていれば、fast-forward できないので 2 と同じに部署のブランチをリベースし、できたら順の 1 から回し直す（候補と版を上げる commit は、リベースした部署のブランチの上に作り直す。リベースできなければ部署に頼んで止める）。push が断られたらメインブランチを取り直し、先に進んでいたときだけ同じにリベースして順の 1 から回し直す（ブランチの保護や認証で断られたなら、頼まずに止める）。2 つの部署が同時に入れようとしても、メインブランチに入る順は fast-forward で 1 本ずつに決まる（`queue` を書けば、後から申し出た `--land` は前の `--land` が push し終えるまで順の 1 に入らないので、この回し直しは列に並ばない処理が push したときだけ起きる）。
  7. 入れたら、`--clean` と同じ決まりと部品（`nodes/clean.py` の `departments`・`retire`）で部署を片付ける（エフェメラルの部署で、会話が終わり、未コミットの変更・手元にしか無い commit・stash が無く、ブランチがメインブランチに入っているとき。条件の全部は `skills/dispatch/references/clean.md` の `--clean` の項。永続の部署は残す）。片付けられないエフェメラルの部署（納品の直後で会話がまだ止まりきっていない、など）は、入れた印（属性 `company.landed`。入れた commit）を書いて残し、次の `--land`（どの部署を入れるときでも）が、印の付いた部署のうち片付けられる形になった物を一緒に片付ける（`--clean` は消せる部署を並べるだけで、`--clean --apply` で消す。こちらでも片付く）。会話が止まるのを待たないのは、期限を足さない決まり D5 のため。エフェメラルの部署は `--task` で `--persistent` を付けずに立てた部署（属性 `company.lifecycle` も前の版の `company.residency` も無い部署もエフェメラルとみなす）、永続の部署は `--persistent` を付けて立てた部署。
- `--dry-run` を付けると、決まりと、することの見立て（リベースが要るか・入れる commit・上げる版・ゲート・片付け）を出すだけで、何も書かない。部署のブランチは部署の場所の HEAD を読み（部署自身のブランチなので取り直さない）、メインブランチの先頭は fetch せず origin に問い合わせて読む（`git ls-remote`。手元の ref は変えない）。上げる版は、本当に打ったときに一時の場所で回すのと同じ計算を、一時の場所を作らずに部署の場所で回して見積もる。ゲートのブランチへの push・手元の検証・部署の窓への打ち込み・片付けはしない。終わりの値は、本当に打ったときに止まると見立てた所（リベースが要る・中身の無い版など）と、見立てそのものが失敗した所（origin を読めないなど）では 1、通ると見立てたら 0。
- 部署への頼み（リベース・赤の直し）は、部署の窓への打ち込みだけ。窓が無ければ、頼みの文を出して呼んだ側に渡させる。今は頼みと納品の仕組み（`--ask`・`--deliver` の受付箱と台帳）を通さない。そちらに替える予定。
- 終わりの値: 0 は入れた・PR を出した・決まりが `none`。1 は止めた・赤・リベースを頼んだ。2 は決まりか引数の誤り。

例（my_notes。検証は `tools/check.py` を手元で回し、通れば fast-forward で入れる）:

```toml
[land]
mode = "ff-after-ci"
gate = "check"
check = "python3 tools/check.py"
```

例（claude-plugins。部署は変えたプラグインのフォルダの下の試験だけを手元で回し、ゲートは `release/*` への push で走る CI。版は取り込むときに上げる。`gate` が CI のブランチなので `--land` は `check` を回さない。`check` の行は works-dispatch を変えたときの書き置きで、部署はほかのプラグインを変えたら、`check` のコマンドの `-s` に渡すフォルダ〔`works-dispatch/dispatch/tests`〕を、変えたプラグインの試験のフォルダに替えて手元で回す）:

```toml
[land]
mode = "ff-after-ci"
gate = "release/*"
check = "python3 -B -m unittest discover -s works-dispatch/dispatch/tests -t ."   # 変えたプラグインの試験に替えて回す
bump = "marketplace"
```
