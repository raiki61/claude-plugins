# メインブランチに入れる（`--land`）

会社の形に `[land]` を書く人と、`--land` が何をするかを知りたい人向け。使い始め方と言葉（部署・会社・納品）は [README](../README.md)、使う人向けの手順の全部は [SKILL.md](../skills/dispatch/SKILL.md) と、そこから主題ごとに指す別ファイル（`skills/dispatch/references/`）。

この文書の言葉:
- 会社: 1 つのリポジトリで AI の会話を役ごとに分けて働かせる組織。決まりは会社の形（`.claude/company.toml`）に書く。
- 部署: 会社の中の 1 つの仕事の場。リポジトリの git worktree 1 つと、そこで動く Claude Code の会話 1 つ。部署のブランチは、その worktree のブランチ。
- 代表の clone: 部署の worktree を作る元の clone。窓口（持ち主と話す会話。`--desk` で名付ける）がここで動く。
- メインブランチ: 取り込み先の origin のブランチ（既定は origin の既定のブランチ。`main` など）。
- ゲート: メインブランチに入れる前に必ず通す検証（CI か手元のコマンド。下の `gate`）。
- 候補: ゲートに出し、緑ならメインブランチにする commit（下の順の 3）。

`python3 dispatch.py --land <部署>` は、部署（名前かブランチの名前で指す）のブランチを、会社の形（`.claude/company.toml`、無ければ設定の置き場〔dispatch の設定のファイル `~/.config/works-dispatch/dispatch.toml` の隣〕の `companies/`）の `[land]` の決まりでメインブランチに入れる。会社の形の設計（リポジトリのルートの [`docs/specs/2026-10-16-company-shape-design.md`](../../docs/specs/2026-10-16-company-shape-design.md)）の 8 章（検証をどこで回すか）と 4.10 の 1（部署の畳み方と成果の取り込み）に当たる。部署の窓は、その部署の会話の画面を出した herdr（端末を作業場ごとに分け、中の会話を外から操作するツール）のペイン。流れは、入口の `dispatch.py` から分けた `dispatch/landing.py` が持つ（ほかの部署と同時に `dispatch.py` を触るぶつかりを減らすため、別のファイルにした）。

- フィールド:
  - `mode`: 取り込み方。`ff-after-ci`（ゲートが緑ならメインブランチを fast-forward）、`pr`（部署のブランチを origin に出して PR を出し、止める。`gate`・`check`・`bump` は使わない）、`none`（何もしない）。`[land]` が無ければ `none` で、何もしない。
  - `gate`: ゲート（メインブランチに入れる前に必ず通す検証）。CI のブランチの形（固定の頭の後ろに `/*`。例 `release/*`。`*` に部署の名前が入る。できたブランチの名前がメインブランチか部署のブランチと同じなら止める）か、`check`（手元の検証を `--land` のコマンドが回す）。`mode = "ff-after-ci"` なら省けない（無ければ決まりの誤りで止める）。
  - `check`: 部署が手元で回す検証のコマンド。`gate = "check"` のときは、`--land` のコマンドが部署の場所（版を上げるときはその一時の場所）で回す（このときは省けない）。`gate` が CI のブランチの形のときは、`--land` はこのフィールドを回さず、部署にも送らない（会社の形のファイルに書いてあるだけの、部署向けの書き置き）。
  - `bump`: `marketplace` なら、部署は版を上げずに出し、取り込むときに `--land` のコマンドが版を上げる commit を足してからゲートに出す。中身の無い版は作らない: 順 3 で版を上げる前に、版を最後に上げた後にフォルダの中のファイルを変えた（commit した）プラグインの `CHANGELOG.md` を見て、`## [Unreleased]` に `### Fixed` のような `#` で始まる行のほかに何も書いてなければ、版を上げずに `--land` 全体を止める（何も push しない。終わりの値は 1。どのプラグインの `CHANGELOG.md` かを出す）。部署が利用者に効く違いを書き足して commit したら、`--land` を打ち直す。版を上げずに取り込む道は用意しない。marketplace は版が変わった時だけ中身を取り直すので、上げなければ変えた中身が利用者に届かない。また、このリポジトリの試験 `VERSION_BUMP_OK`（`tests/run.sh`。ファイルを変えたのに版が据え置きのプラグインを、main と release/* の CI で赤にする）も赤になる。上げ幅は、`## [Unreleased]` に Added・Changed・Deprecated・Removed のセクションが有れば minor、無ければ patch。ただし版を最後に上げた後に変えたファイルが試験と文書だけ（`tests`・`test`・`docs` のフォルダの下、`test_*.py`・`*_test.py`・`conftest.py`、プラグインの直下の `README.md`・`CHANGELOG.md`・`CONTRIBUTING.md`・`LICENSE`。`plugin.json` は説明〔`description`〕の字だけを変えたとき）なら、セクションによらず patch にする（Semantic Versioning の minor は機能の追加に当てる物で、利用者が動かす物を変えていない直しは当たらない）。`SKILL.md` やエージェントの `.md` は Claude Code が読んで動く物なので、文書に数えない。そう決めたときは `--land` が注記を出す。
  - `main`: メインブランチの名前。省けば origin の既定のブランチ。
  - `queue`: メインブランチへ入れる列（land-queue）の置き場。共通の `.git`（`git rev-parse --git-common-dir`）の下のフォルダの相対の名前（例 `land-queue`。絶対のパスと `..` は決まりの誤りで止める）。書けば、`--land` は順の 1 でメインブランチを取り直す直前に列へ申し出て、順の 6 で push し終える（か、止まる）まで列の先頭を持つ。同じ clone（worktree を含む）で同時に打った `--land` と、`--queue-run` で並ぶ外のツール（my_notes の collect など）は、申し出た順に 1 本ずつ「リベース → ゲート → push」を通り、互いの push でメインブランチが先に進んでやり直すことが無くなる。列の決まり: 申し出たときに `<time.time_ns() を 20 桁の 0 埋め>-<pid>.ticket` の札を作って排他のロック（POSIX は flock、Windows は msvcrt.locking）を掛け、終わるまで持つ。札は名の小さい順に並べ、ロックの外れた札（作ってから 10 秒を過ぎた物）は持ち主の処理が落ちた物として消す。先頭の生きた札になったら、置き場の `lock` のファイルに排他のロックを（ロックが空くのを待たずに）掛けてみて、取れたら進む。取れなければ 1 秒おいて、札の並びから見直す（列の先頭になるまで、これをくり返して待つ）。待つ長さに上限は置かない（期限を足さない決まり D5）。止めるのは人の Ctrl-C で、そのときも札を消す。待つ間は、前に何本居るかを、数が変わるたびに 1 行出す。役ごとの `[land.roles.<役>]` には書けない（列は clone ごとに 1 つなので）。省けば列に入らない（前の版と同じ動き）。この鍵を知らない前の版の `--land` は、知らない鍵として止まる（列を無視して走ることは無い）。実装は `dispatch/nodes/landqueue.py`。
  - `batch`: 束（列の先頭を取った `--land`〔束ね役〕が、後ろに待つ部署のブランチを重ねて、1 回のゲートでメインブランチに入れる組）の上限の本数（束ね役を 1 本に数える 1 以上の整数）。省けば 1 で、束を作らない（前の版と同じ動き）。2 以上には `queue` が要る（無ければ決まりの誤りで止める）。役ごとの `[land.roles.<役>]` には書けない。設計は [specs/2026-10-26-land-batch-design.md](specs/2026-10-26-land-batch-design.md)。
    - 乗せる札: 束ね役が先頭を取った時に待っていた札を前から見て、名乗りが有り、札が生きていて、部署の場所が見つかり、取り込みの決まりが束ね役と同じで、未コミットの変更が無く、疑いの印（前の束が赤だった、同じ先頭のブランチに付ける印）が無い物を、上限まで乗せる。どれかに外れた札でそこで閉じ、後ろの札は追い越さない。もう入っている札は飛ばす。
    - 束ね役は、自分のブランチを今までどおりリベースして書き換えの取り合いのゲートを通した後、一時の場所（列の置き場とは別の一時のフォルダの、ブランチに乗らない worktree）で乗る札のブランチを順に重ね（`git rebase --onto`）、版上げとゲートを 1 回だけ回す。乗る部署の場所とブランチは書かない。ぶつかる・書き換えの取り合いに当たる・変更の記録（CHANGELOG の `## [Unreleased]`）を書いていない札で閉じ、閉じた札は自分の順番で 1 本で通る。`tests/run.sh` を変える札では閉じない（ゲートの `check` が束ごと全部の試験を 1 回回す）。
    - ゲートが赤なら束をほどき、乗っていた札に疑いの印を付け、束ね役 1 本で回し直す。印の付いた札は、それぞれの順番で 1 本で通る。緑なら、push の前に列の置き場へ束の控え（どの部署のどの commit を重ねた写しが入ったか）を書き、メインブランチを fast-forward して push する。合図（`[[land.after]]`）は束ごとに 1 回で、ツールには部署の名前の並びを環境変数 `WORKS_LAND_MEMBERS`（改行で区切る）で渡す。
    - 乗った部署は、自分の順番の `--land` で受け取る。ブランチが束に重ねる前のままなら写しへ替えて「束（束ね役 X）でメインブランチに入った」と出して終わり（ゲートも合図も回さない）、束の後に commit を足していれば足した物を写しの上へ移して今までどおり入れる。列で待つ間に未コミットの変更ができていれば、受け取らずに止め、commit してから打ち直すよう頼む（列に入る前の未コミットの変更は、束でなくても今までどおり止める）。永続の部署の待ち受け（次の頼みを渡す前の作業場の追いつき）も、作業場がきれいでブランチが前のままのときだけ同じく写しへ替える（束の後に commit を足した・汚れているときは替えず、自分の `--land` で受け取る）。
    - 乗った札が自分の順番より前に列を抜けたとき（Ctrl-C など）は、「束に乗っていたので、束ね役 X が入れたかもしれない」と 1 行出す。
    - 束にしたい会社は、`batch` を書く前に、ブランチに乗らない一時の worktree（追跡外のファイルの無い物）で `check` が緑になるのを確かめる（束のゲートは部署の場所でなく一時の場所で回るので、部署の場所にだけ在るファイルに頼る `check` は束で赤になる）。
  - 役ごとに `[land.roles.<役>]` で上のフィールドを替えられる（書いたフィールドだけを上に重ね、書かないフィールドは `[land]` の値のまま。役は部署の属性 `company.role`。部署の属性は、部署の worktree ごとの git の設定 `company.<名前>` に dispatch が書く）。
- 順（`ff-after-ci`）:
  1. メインブランチを取り直す（origin のメインブランチを fetch する）。部署のブランチがもうメインブランチに入っていれば、片付けへ進む。
  2. メインブランチが部署のブランチの祖先でなければ（ほかの部署が先に入れた）、部署の場所でブランチをメインブランチの上に `git rebase` でリベースし、origin の部署のブランチもリベースした物にしてから先へ進む（[git rebase](https://git-scm.com/docs/git-rebase)）。ぶつかったら、機械で解ける物だけを解いて続ける。1 つは git rerere（前に手で解いたのと同じぶつかりを、git がその解き方で解く。[git rerere](https://git-scm.com/docs/git-rerere)。--land は、代表の clone の git の設定（local）に rerere.enabled と rerere.autoUpdate を true で書いてからリベースする。持ち主〔このプラグインを使う人〕がその値を git の設定のどこか〔local・global・system〕にもう書いていれば替えない）。もう 1 つは変更の記録（`CHANGELOG.md`）の `## [Unreleased]` の頭のぶつかりで、部署の側の書き足しを Unreleased のすぐ下に、メインブランチの側をその後に置く（部署は版を上げないので、部署の書き足しはいつもそこに在る）。変更の記録には git の union の merge driver を使わない（原典が、足した行の順が乱れうると書く。[gitattributes](https://git-scm.com/docs/gitattributes) の Built-in merge drivers）。ほかのぶつかりが残れば、リベースをやめて元のブランチに戻し、部署に「メインブランチの上にリベースして（rebase）push し直す」とぶつかるファイルを添えて頼んで止める。
  2a. 書き換えの取り合いのゲート: 部署のブランチが、ほかの部署が入れたばかりの行を消していないかを見る。部署が前に読んだ中身を覚えたまま書き直すと、そうした行を消しても git の衝突にならず、ゲートの試験も通ってしまう（試しの記録 [`docs/trials/2026-10-16-clean-env-2.md`](../../docs/trials/2026-10-16-clean-env-2.md) の 5 で実際に起きた）。見るのは、部署がメインブランチを最後に知った位置（属性 `company.base`。`--task` がブランチを作ったときの origin のメインブランチか、その部署の前の `--land` で入れた後のメインブランチ）より後に、ほかの部署がメインブランチへ入れた行。部署のブランチがその行を消して（書き換えて）いれば、順の 4 のゲート（CI か `check` の検証）に出さずに `--land` を止め、部署の窓（その部署の会話を出した herdr〔端末を作業場ごとに分け、中の会話を外から操作するツール〕のペイン）に「どの commit（件名）の、どのファイルの何行目を消すか」を打ち込む。部署はその行を残す形に取り込み直して push し、`--land` を打ち直す。わざと消すなら `--land <部署> --keep-removal` で通す。ファイルの名前の付け替えは git の名前の付け替えの見つけ方（`git diff -M`）で追い、部署のブランチが名前を替えたファイルはメインブランチでの古い名前と行番号で突き合わせる。新しい名前へ運んだ行は消したと数えず、止めたときに示す名前と行番号はメインブランチでの古い名前の物。git が付け替えと見なさない物（中身を大きく書き換えたファイルなど）は、消して作り直したと読む。位置の記録が無い部署（works-dispatch 0.19.8 までに立てた部署）は見ずに注記を出して先へ進む（今のメインブランチとの merge-base は、リベースした後のブランチではメインブランチの先頭になり、何も見つけないため）。メインブランチに入れた後は、`--land` が、入れた部署の位置（属性 `company.base`）を入れた後のメインブランチに進める。
  3. `bump` があれば、一時の場所（ブランチに乗らない worktree）で、部署のブランチの先頭の上に版を上げる commit を作る。部署のブランチは動かさない。以下、ゲートに出し、緑ならメインブランチにする commit を「候補」と呼ぶ（版を上げる commit を作ればそれ、作らなければ部署のブランチの先頭）。「候補の木」はその commit の中身のファイル。
  4. ゲートに出す。CI のブランチなら、まず候補の木の GitHub Actions の設定（`.github/workflows`）のどれかがそのブランチの名前の固定の頭（`gate` に書いた形の `/*` の前。`gate = "release/*"` なら `release/`）を書いていることを確かめ（無ければ止める）、そのブランチ（ゲートのブランチ。`gate` の `*` に部署の名前を入れた物。`gate = "release/*"` で部署 `fix-x` なら `release/fix-x`）へ候補の commit を push して（前の物は上書き）、その commit の run が現れるまで 10 秒おきに見に行き（回数に上限を置かない。期限を足さない決まり D5〔dispatch のコードに期限（timeout）を足さない。[internals.md](internals.md) の「チェック D1〜D9」〕のため、上限の代わりに、run が起きない設定を push の前の確かめで弾く）、`gh run watch` で終わりを待つ（run の結論が `success` のときだけ緑、ほかは赤）。push の前の確かめが見るのは、設定のファイルにブランチの頭の字が在るかだけ。字が在っても、ほかの絞り（変えたファイルの条件など）で run が起きなければ、確かめでは弾けず、`--land` は待ち続ける。そのときは人が `--land` を止める（Ctrl-C）。watch が途中で戻れば、赤とせずに止める。`gate = "check"` なら、ゲートのブランチは作らず、`check` のコマンドを候補の場所（順の 3 で版を上げる commit を作ったならその一時の場所、作らなければ部署の場所）で回し、終わりの値 0 を緑、それ以外を赤とする（赤なら下の順の 5 へ、緑なら順の 6 へ進む。6 で消すゲートのブランチは無い）。`check` のコマンドには環境変数を 3 つ足して渡す。`WORKS_LAND_TIP` は文書を読む commit（版を上げる前の部署のブランチの先頭）。`WORKS_LAND_KEY` は前の回の控えの鍵（前の回に読んだ文書を残した控えを引く字。今は部署のブランチの名前）。`WORKS_LAND_BRANCH` は読み手の呼び出しの記録を部署と頼みに結ぶための、部署のブランチの名前。束（上の `batch`）では、`WORKS_LAND_TIP` は重ねた先頭（束の全員の変更を読む）、`WORKS_LAND_KEY` は束ね役のブランチの名前の後ろに ` batch` を付けた字（ブランチの名前は空白を含めないので、1 本の回の控えとぶつからない）、`WORKS_LAND_BRANCH` は束ね役のブランチの名前（読み手の呼び出しの記録は束ね役に寄せる）。使うのは gates の初見の読み手のゲート（`check` の中の `coldread-gate.py branch-check`。変えた文書を AI の読み手に初見で読ませる）で、3 つのどれかが在れば、HEAD から推し量るより先に使う（[specs/2026-10-26-land-batch-design.md](specs/2026-10-26-land-batch-design.md) の 5.3）。
  5. 赤なら、部署に失敗の要点（CI なら落ちた job と step、記録の終わりの行。`check` なら出力の終わりの行）を頼んで止める。
  6. 緑ならメインブランチを取り直す。メインブランチがまだ候補の祖先なら、次の 3 つを順にする。origin のメインブランチを候補へ fast-forward で push する。代表の clone（部署の worktree を作る元の clone。窓口の会話はここで動き、フックと決まりをこの作業ツリーから読む）の手元のメインブランチも、いつも `git merge --ff-only` で fast-forward する（書きかけのファイルは残る）。ゲートのブランチを消す。代表の clone を進められないとき（書きかけがメインブランチの変更とぶつかる・メインブランチに無い commit が有る・git が誤りを返す）は、そこだけ飛ばして先へ進み、その会社の窓口（代表の clone で `--desk` で名付けた、持ち主と話す会話）へ知らせる。知らせは受付箱の台帳（`.git/company/inbox/log.jsonl`）に足す 1 行で、その行が窓口の会話にターンを始めさせる。push の後の取り直しが落ちても、push した候補までは fast-forward する。代表の clone の手元のメインブランチは、部署が `--deliver`（納品）した後にも、origin のメインブランチの今の先頭まで同じく進める。取り直したメインブランチに候補に無い commit が入っていて（候補を作った後にほかの部署が先に入れた、など）、メインブランチが候補の祖先でなくなっていれば、fast-forward できないので 2 と同じに部署のブランチをリベースし、できたら順の 1 から回し直す（候補と版を上げる commit は、リベースした部署のブランチの上に作り直す。リベースできなければ部署に頼んで止める）。push が断られたらメインブランチを取り直し、先に進んでいたときだけ同じにリベースして順の 1 から回し直す（ブランチの保護や認証で断られたなら、頼まずに止める）。2 つの部署が同時に入れようとしても、メインブランチに入る順は fast-forward で 1 本ずつに決まる（`queue` を書けば、後から申し出た `--land` は前の `--land` が push し終えるまで順の 1 に入らないので、この回し直しは列に並ばない処理が push したときだけ起きる）。
  7. 入れたら、`--clean` と同じ決まりと部品（`nodes/clean.py` の `departments`・`retire`）で部署を片付ける（エフェメラルの部署で、会話が終わり、未コミットの変更・手元にしか無い commit・stash が無く、ブランチがメインブランチに入っているとき。条件の全部は `skills/dispatch/references/clean.md` の `--clean` の項。永続の部署は残す）。片付けられないエフェメラルの部署（納品の直後で会話がまだ止まりきっていない、など）は、入れた印（属性 `company.landed`。入れた commit）を書いて残し、次の `--land`（どの部署を入れるときでも）が、印の付いた部署のうち片付けられる形になった物を一緒に片付ける（`--clean` は消せる部署を並べるだけで、`--clean --apply` で消す。こちらでも片付く）。会話が止まるのを待たないのは、期限を足さない決まり D5 のため。エフェメラルの部署は `--task` で `--persistent` を付けずに立てた部署（属性 `company.lifecycle` も前の版の `company.residency` も無い部署もエフェメラルとみなす）、永続の部署は `--persistent` を付けて立てた部署。
- `--dry-run` を付けると、決まりと、することの見立て（リベースが要るか・入れる commit・上げる版・ゲート・片付け）を出すだけで、何も書かない。部署のブランチは部署の場所の HEAD を読み（部署自身のブランチなので取り直さない）、メインブランチの先頭は fetch せず origin に問い合わせて読む（`git ls-remote`。手元の ref は変えない）。上げる版は、本当に打ったときに一時の場所で回すのと同じ計算を、一時の場所を作らずに部署の場所で回して見積もる。ゲートのブランチへの push・手元の検証・部署の窓への打ち込み・片付けはしない。`batch` が 2 以上で列に待つ札が有れば、列の今の様子・次の束の見込み・待つブランチどうしがぶつかる見込み（`git merge-tree`）も出す。このとき、列の見直しで抜けた札（持ち主の処理が落ちた札）の掃除と、`git merge-tree` が作るオブジェクト（どの ref からも指されず、git の gc が消す）だけは書く。終わりの値は、本当に打ったときに止まると見立てた所（リベースが要る・中身の無い版など）と、見立てそのものが失敗した所（origin を読めないなど）では 1、通ると見立てたら 0。
- 部署への頼み（リベース・赤の直し）は、部署の窓への打ち込みだけ。窓が無ければ、頼みの文を出して呼んだ側に渡させる。今は頼みと納品の仕組み（`--ask`・`--deliver` の受付箱と台帳）を通さない。そちらに替える予定。
- 終わりの値: 0 は入れた・PR を出した・決まりが `none`。1 は止めた・赤・リベースを頼んだ。2 は決まりか引数の誤り。

入れる順を決める（`--land-order`）: 会社の形の `[land]` に `queue` を書いたときの列（上の `queue` のフィールド）は、ふだんは申し出た順（先入れ先出し。GitHub の merge queue も同じ）に通す。判断役（頼みを部署に配る会話。my_notes〔持ち主のノートのリポジトリで、works-dispatch の会社の 1 つ〕の段取りなど）が、何を先に入れるかを決めて列に反映できる。この項を読んで手を動かすのは判断役だけで、部署は今までどおり `--land` を打てばよい。

この項の言葉: 札は、列に申し出た 1 本ごとに `queue` のフォルダ（置き場）に作るファイル（`<数>-<pid>.ticket`）。

- `python3 dispatch.py --land-order` は、待っている札を今の入れる順に出す。`--land` の札には、部署の名前・ブランチ・待った分・変えたファイルの数（メインブランチから分かれた所から）・ほかの待ちと重なるファイルを添える。`--land` は列に入るとき、札の横の `<札の名>.who` に部署の名前とブランチを書いて名乗る。名乗らない札（`--queue-run` で並ぶ外のツール〔my_notes の collect など〕の札）は「名乗りの無い札」と出る。`batch` が 2 以上なら、次の束の束ね役と乗る札の見込みを添える（名乗りと疑いの印だけで見積もるので、部署の場所・決まり・ぶつかりで外れうる）。
- `python3 dispatch.py --land-order <部署> [<部署> ...]` は、部署の名前かブランチを書いた順に、置き場の `order` へ書く。名乗りが当たる札がその順で前に出て、残りの札はその後に申し出た順で通る。いま列の先頭で進んでいる 1 本（置き場の `lock` を持ち、リベース・ゲート・push の途中の物）は止めず、次の 1 本から効く。引数に `-` だけを渡す `--land-order -` は、`order` のファイルを消して、全体を申し出た順に戻す。列に居ない名前は飛ばす。名乗った `--land` が列を抜けるとき、`order` から自分の名前とブランチの行を消すので、同じ名前で後に打った `--land`（永続の部署など）が前の指定で前に出続けることは無い。判断役の書き込みと、抜ける `--land` の消しがちょうど重なると、判断役の書いた順が失われることがある（もう一度打つ）。
- 判断役が何もしなければ、列は今までどおり申し出た順に止まらずに通る。
- 順の決め手（判断役が見る物。上から強い）:
  1. メインブランチの赤を直すか戻す物を、ほかの何より先にする（GitLab の broken master: "returning the build to a passing state takes priority over everything else development related"。<https://handbook.gitlab.com/handbook/engineering/workflow/>）。赤のままでは、後ろの `--land` がみな同じ赤で止まる。
  2. 持ち主が急ぐと言った物。
  3. 同じファイルを変える部署どうし（`--land-order` の「ほかの待ちと重なる」）は、ほかの部署が土台にしている物を先にする（後の方がリベースで合わせる。土台を後にすると、両方がリベースし直す）。
  4. 残りは申し出た順のまま（`order` に書かない）。

外のツールが列に並ぶ（`--queue-run`）: works-dispatch の外で、同じ clone からメインブランチへ自分で push するツール（my_notes〔持ち主のノートのリポジトリ〕の collect など。collect は 2026-10-20 に、列のコードの写し `tools/land_queue.py` をやめてこの形に移った）は、`--land` と同じ列（メインブランチへ 1 本ずつ入れるための順番待ち。会社の形〔`.claude/company.toml`〕の `[land]` に `queue` を書いたときだけ在る）に並んでからコマンドを走らせる。列の作りを works-dispatch の側の 1 か所（`dispatch/nodes/landqueue.py`）に持ち、札の形を写して合わせないためにある（写すと、片方だけ直したときに札の形がずれ、互いを見ずに同時に push しうる）。この項を読んで手を動かすのは、そういうツールを書く人で、することは 1 つ: ツールの中の、メインブランチを取り直してから push し終えるまでの手を 1 つのコマンドにまとめ、そのコマンドを下の `--queue-run` で包んで走らせる（例 `"$WORKS_DISPATCH_PYTHON" "$WORKS_DISPATCH" --queue-run -- git push origin HEAD:master`）。部署と判断役は何もしなくてよい。

- `python3 dispatch.py [--repo <代表の clone>] --queue-run -- <コマンド> [<引数> ...]` は、打った場所（か `--repo`。worktree の中でもよい）の会社の形の `[land]` の `queue` の列に申し出て、先頭を取ってからコマンドを打った場所で走らせ、終わったら列を抜けて次に渡す。dispatch の引数は `--queue-run` の前に書き、`--` の後ろは全部コマンドとその引数になる。
- コマンドはシェルを通さずに起動し、標準入出力と環境をそのまま渡す。列で待つ間の行（前に何本居るか）と止めた訳は標準エラーに出す（標準出力はコマンドの物）。
- 終了の値はコマンドの物。シグナルで落ちたら 128 + その番号（シェルと同じ）。コマンドを走らせる前に止めたときは、GNU coreutils の `env` と同じ値で分ける（<https://www.gnu.org/software/coreutils/manual/html_node/env-invocation.html>）: 列に入れない（会社の形が読めない・`[land]` に `queue` が無い・列のフォルダを書けない）は 125、コマンドが在るのに起動できないは 126、コマンドが見つからないは 127。`--queue-run` の後ろに `--` とコマンドが無い・`--repo` と `--config` のほかの引数を一緒に書いた、は 2。
- 列で待つ処理は、それぞれ列のフォルダに自分のファイル（札）を作る。`--queue-run` の札には部署の名が無いので、順の指定（決める人が `--land-order <部署>...` で列のフォルダに書く `order` のファイル。名を書いた `--land` の札を前へ出す）では動かず、`order` に名のある札の後ろを申し出た順で通る。`--land-order` の一覧には「名乗りの無い札」と出る。待つ長さに上限は置かない。列で待っている間に止めるのは人の Ctrl-C（札を消して 130 で抜ける）。
- コマンドが走っている間に Ctrl-C・SIGTERM・SIGHUP を受けても、列はコマンドが終わるまで持つ（Ctrl-C は同じプロセスグループのコマンドにも届き、SIGTERM と SIGHUP は `--queue-run` がコマンドに送り直す）。先に列を抜けると、次の処理がまだ走っているコマンドと同時に push しうるため。コマンドが自分で起動した子の処理を止めるのはコマンドの受け持ち。`--queue-run` が SIGKILL で落ちたときだけは列を持てない（OS がロックを外す）。
- `--queue-run` と一緒に書けるのは `--repo` と `--config` だけで、ほかの引数を混ぜると 2 で止まる（`--land` などほかの入口〔処理を選ぶ引数〕に黙って飲まれて、コマンドが走らないまま終わらないように）。
- 会社の形の機械窓口のツール（`--call` が走らせる物と、`[[land.after]]` の合図）には、今走っている `dispatch.py` のパスを環境変数 `WORKS_DISPATCH` に、それを走らせている Python を `WORKS_DISPATCH_PYTHON` に入れて渡す。ツールは `"$WORKS_DISPATCH_PYTHON" "$WORKS_DISPATCH" --queue-run -- <コマンド>` で並べる（プラグインの版ごとの置き場のパスを書かなくてよい）。

例（my_notes。検証は `tools/check.py` を手元で回し、通れば fast-forward で入れる）:

```toml
[land]
mode = "ff-after-ci"
gate = "check"
check = "python3 tools/check.py"
```

例（claude-plugins。部署は変えたプラグインのフォルダの下の試験だけを手元で回し、ゲートは `release/*` への push で走る CI。版は取り込むときに上げる。`gate` が CI のブランチなので `--land` は `check` を回さない。`check` の行は works-dispatch を変えたときの書き置きで、部署はほかのプラグインを変えたら、`check` のコマンドの `-s` に渡すフォルダ〔`works-dispatch/dispatch/tests`〕を、変えたプラグインの試験のフォルダに替えて手元で回す）:

```toml
[land]
mode = "ff-after-ci"
gate = "release/*"
check = "python3 -B -m unittest discover -s works-dispatch/dispatch/tests -t ."   # 変えたプラグインの試験に替えて回す
bump = "marketplace"
```
