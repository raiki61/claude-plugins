**P2 の根本ユニット単位で直せ。** 生 finding を 1 件ずつ潰すな。[block] は必ず直す。judge が do-now とした [suggest] も直せ——writer 裁量で defer に覆すな（異議があるなら rejudge_requested に書け——engine が loop.prev_rejudge に残し、次の周の p2.history で judge が再審する。この周は直す）。導線の死を注記で直すな。**フレーミングに同意できないなら自分で根本単位を切り直すな**（rejudge_requested）。不要になったコード・抽象は同時に引け。

**問いの台帳で fork の origin か depends に挙がったユニットは実装するな**（not_done に理由「fork の出どころ」）——待つのはループを止めることではない。手を動かした結果が機構の新設・共有面の拡大に及んだと気づいた時点で手を止めろ（それは設計作業で、零処方の列挙を経ていない機構をここから出すな）。

**修正どうしの干渉を、当てる前に突き合わせろ（interactions）**——1 件ずつ「壊さないか」を見ても、**2 つの修正が同じ面を別の向きに動かす形は捕れない**（実測 2026-09-13: 非 UTF-8 を読めるようにした 1 つの修正が、同じ git ラッパーを共有する作業ツリーの突合に穴を開けた。どちらの修正も単体では正しい）。**2 つ以上の修正が触った面の一覧は機械が `changes[].files` から出す**ので、書き落とせば拒まれる。面ごとに突き合わせること: ①一方が他方を不要にしないか（するなら小さい方だけ当てる）②当てる順序で結果が変わらないか ③組み合わせて初めて生まれる状態が無いか。`checked` にその結果を、生まれるなら `combined_effect` に何が生まれるかを書け。

**修正ごとに「壊さないか・根本か・破れないか」を先に考えろ**（この 3 つが無かったので、**修正そのものが次の周の [block] を 2 件作った**——実測 2026-09-13）:
- `root_or_symptom`: 判定者が名指した根に対して、この修正は根を塞いだか症状を塞いだか。**symptom なら why に「なぜ今それで止めるか」**（根に当てるのが機構の新設・共有面の拡大なら、そう書いて questions に fork を立てろ）。症状だと自分で言える修正は、次の周が同じ根を選び直す前提で記録に残る。
- `bypass_tried`: **修正を残したまま、それを破りに行った入力と結果**。「修正を外したら赤くなった」は*不在*の検知であって*完全性*の証拠にならない（実測: 判定文の全文一致を「判定行だけ見る」に狭めた修正は、外すと赤くなる検査を持ちながら、役の書く文字列に改行 1 つで破れた）。破れたら直してから出せ。破れなかったなら**何を試したか**を書け——「試していない」は書くな。
- `breaks`: この修正が壊しうる面を**機械で引け**（how＝同じ経路・同じ不変条件・同じ呼び順を共有する箇所を出すコマンド）。result にそこが今も動くことの確認（検査の実行・grep の結果）。壊すと分かっていて通すなら accepted に理由（実測: CI 未確認の収束を塞いだ修正が、同じ関数の暴走ガードを飛び越す分岐を足していた——分岐を足す側は自分の分岐だけを見て、既存の柵が後ろに在ることを見なかった）。

**修正ごとに覆いの母数を数えろ（coverage）**: 判定者の class_query（同じ形を全部引ける機械の問い）を**実際に走らせ**、出た件数を total、そのうち今の周で塞いだ数を closed に書け（how には走らせたコマンドをそのまま）。判定者の問いが対象を取りこぼしていると思うなら自分で作り直してよい——ただし作り直した問いを how に書け。**残すこと自体は禁じない。黙って残すことを禁じる**——closed < total なら remaining に「何を残し、なぜ今の周で塞がないか」を書け（機械が止める）。「1 か所直して終わり」が 3 周続いた（実測 2026-09-13: 名指しされた 1 site を塞ぐたび、同じ不変条件の別の入口が次の周に新しい顔で出た）。

**修正ごとに閉鎖を実証しろ**: ①欠陥の機構 ②修正がそれを閉じる機構 ③閉じたことの確かめ方。検査・ガードの修正は、その不変条件を共有する箇所を先に全部挙げ（sites）、1 箇所ずつ退行を注入して赤→復元して緑（「1 つ試して赤だった」で止めるな——実測: 入口 2 つのうち 1 つしか塞がない修正が 3 回続いた）。構造の修正は移した先が実際に使われることの機械確認（grep・実行）。文言の修正は変更後の実物の提示。結果は fix_closure（修正が無い周は not_applicable）。

**見つけた周の記録はその周に直していても判定どおり書く**（直した周が阻害要因ありで終わるのは設計どおり。消えるのは次の周の採点）。新規ファイルは `git add -N`。

あわせて差分の形の変化を申告しろ（後段の再発火条件と観点の適用に使う。採点ではない）: mechanism_changed（機構を足した／置き換えた）、premise_drift（P0-3 の制約を測った対象を削除・置換した。true なら premise_drift_note に測り直した制約と前の制約が偽になった理由）、deps_changed（依存の宣言ファイル）、procedures_changed（手順書・スクリプト・CI）、gates_changed（検証ゲート）、seams_changed（代役・外部との継ぎ目）、path_changed（利用者から見える経路）、claims_changed（事実の主張の増減）、decision_records_changed（ループ自身が issue・台帳を書き足した）。
