**事前審査の穴（faces）と別案（shrink）に 1 件ずつ答えろ（plan_faces。key は上の no）**——取り込んだなら absorbed と、どう取り込んだかを how に。取り込まないなら declared と、残す理由を how に（誤検知なら現物のどこで誤りと言えるか）。答えない key が在れば機械が拒む。block の穴を declared で残すなら、次の周の全体レビューが同じ穴を [block] で挙げる前提で書け。書いた直後に、この周の修正だけの差分を別の役（inspector）が見て、穴が塞がれたかを確かめる。

**`owed` が偽の開いた行は実装するな**（人に諮っている問いを待つ単位。not_done に理由「fork の出どころ」）——待つのはループを止めることではない。手を動かした結果が機構の新設・共有面の拡大に及んだと気づいた時点で手を止めろ（それは設計作業で、零処方の列挙を経ていない機構をここから出すな）。

**修正どうしの干渉を、当てる前に突き合わせろ（interactions）**——1 件ずつ「壊さないか」を見ても、**2 つの修正が同じ面を別の向きに動かす形は捕れない**（実測 2026-09-13: 非 UTF-8 を読めるようにした 1 つの修正が、同じ git ラッパーを共有する作業ツリーの突合に穴を開けた。どちらの修正も単体では正しい）。**2 つ以上の修正が触った面の一覧と、面ごとにどの修正が触ったかは機械が `changes[].files` から出す**ので、面を書き落とせば拒まれる（触った修正の一覧は書かない）。面ごとに突き合わせること: ①一方が他方を不要にしないか（するなら小さい方だけ当てる）②当てる順序で結果が変わらないか ③組み合わせて初めて生まれる状態が無いか。`checked` にその結果を、生まれるなら `combined_effect` に何が生まれるかを書け。

**修正ごとに「壊さないか・根本か・破れないか」を先に考えろ**（この 3 つが無かったので、**修正そのものが次の周の [block] を 2 件作った**——実測 2026-09-13）:
- `root_or_symptom`: 判定者が名指した根（上の置き場の why_chain）に対して、この修正は根を塞いだか症状を塞いだか。**symptom なら why に「なぜ今それで止めるか」**（根に当てるのが機構の新設・共有面の拡大なら、そう書いて questions に fork を立てろ）。症状だと自分で言える修正は、次の周が同じ根を選び直す前提で記録に残る。
- `bypass_tried`: **修正を残したまま、それを破りに行った入力と結果**。「修正を外したら赤くなった」は*不在*の検知であって*完全性*の証拠にならない（実測: 判定文の全文一致を「判定行だけ見る」に狭めた修正は、外すと赤くなる検査を持ちながら、役の書く文字列に改行 1 つで破れた）。破れたら直してから出せ。破れなかったなら**何を試したか**を書け——「試していない」は書くな。
- `breaks`: この修正が壊しうる面を**機械で引け**（how＝同じ経路・同じ不変条件・同じ呼び順を共有する箇所を出すコマンド）。result にそこが今も動くことの確認（検査の実行・grep の結果）。壊すと分かっていて通すなら accepted に理由（実測: CI 未確認の収束を塞いだ修正が、同じ関数の暴走ガードを飛び越す分岐を足していた——分岐を足す側は自分の分岐だけを見て、既存の柵が後ろに在ることを見なかった）。
- **動きを変えたら、その動きを述べた文を全部直せ**: 注記・docstring・テスト名・拒否文・別の文書に、変える前の動きを述べた文が残っていないかを検索で引き、直すか消せ（引いた検索は breaks.how に並べて書け）。新しい注記は、テスト名・拒否文・名前で言えるなら足すな——注記は「なぜ」だけを言う（Google のコードレビューの指針: "comments are useful when they explain why some code exists, and should not be explaining what some code is doing"）。実測 2026-09-24: 修正で動きを変えても別のファイルの注記が古いまま残り、テストに理由の写しを足し、意味を失った引数が残った（3 周目の R1 が写しの注記を 17 件挙げた）。

**修正ごとに先行例を書け（precedent）**: 機構を足す・形を変える修正は、同じ問題を世の中がどう解いているかを一次情報で確かめてから書け（REVIEW.md「処方の最小性」の「世界の解を採る」）。**Web を読む調べは自分でやるな——convergence-loops:investigator を起こして任せ、返った行（problem・source・verdict・理由）だけを受け取れ**（ページを読むとその分があなたの文脈に入り、回し役の文脈が修正より先に尽きる）——problem・source・verdict（値と意味は末尾の schema の verdict の note）・reason、not_found なら searched。判定者の先行例の行をそのまま採ったなら from_judge_row: true と書き、verdict はその行の値、reason にどの行か（単位の key）を書けばよい。自前の機構を作るなら、世界の解が無い・使えない理由を reason に出典つきで書け（実測 2026-09-24: 修正役が作った数え直しの機構が、世界の解を使わない自前の言語で 3 周続けて隙間を出した）。
**修正ごとに覆いの母数を示せ（coverage）**: 判定者が class_query を持つ単位（一覧の行の `has_class_query` が真）は coverage.how を書かなくてよい——書かなければ engine が判定者の how（同じ形を全部引ける機械の問い）を補う。判定者が class_query を持たない単位だけ how（欄で書く）と counts を書け。**修正の前後の件数は engine が数える**——修正前は判定者が読んだのと同じ固定の版で、修正後は同じ世界（未追跡も含め、.gitignore に当たる物は外す）で数え、向き（defects / population）は判定者の値を使う。件数は書くな（coverage に total の欄は無い）。判定者の問いが対象を取りこぼしている・根の 1 行だけを数えていると思うなら how を作り直してよい——ただし作り直した how を書け（engine は作り直した how も修正前の版で数え、判定者の母数より狭ければ remaining に理由を求める）。欠陥の形を数える問い（defects）で母数を全部塞いだと言うのに修正後も数えれば拒まれる。**残すこと自体は禁じない。黙って残すことを禁じる**——閉鎖を実証した site が母数に届かないなら remaining に「何を残し、なぜ今の周で塞がないか」を書け（機械が止める）。「1 か所直して終わり」が 3 周続いた（実測 2026-09-13: 名指しされた 1 site を塞ぐたび、同じ不変条件の別の入口が次の周に新しい顔で出た）。

**修正ごとに閉鎖を実証しろ**: ①欠陥の機構 ②修正がそれを閉じる機構 ③閉じたことの確かめ方。検査・ガードの修正は、その不変条件を共有する箇所を先に全部挙げ（sites）、1 箇所ずつ退行を注入して赤→復元して緑（「1 つ試して赤だった」で止めるな——実測: 入口 2 つのうち 1 つしか塞がない修正が 3 回続いた）。構造の修正は移した先が実際に使われることの機械確認（grep・実行）。文言の修正は変更後の実物の提示。結果は fix_closure（修正が無い周は not_applicable）。

**新しく書く参照は、書けるなら Markdown のリンクで書け**（`[名前](相対パス#見出し)`）——engine は申告に依らず、差分が足した .md の行（コードブロックとコードスパンの外）のインラインのリンク（参照形式は拾わない。拾う形の範囲は rules の MD_LINK の注記）を拾い、指し先のファイルと、指し先が .md なら見出しまで引いて、届かなければ拒む。
**リンクにできない指しを申告しろ（wrote_refs）**: 引くのは申告された指しだけ——申告しなかった散文の指しは誰も引かない。他の文書の節名・見出し・ファイル名・引用を新しく書いたなら、1 件ずつ挙げろ（欄の意味は末尾の schema の note）。**引くのは今この瞬間の作業ツリー**なので、この周に作ったファイル・書き足した見出しを指してよい。ファイルそのものを指したなら kind を file に、ファイルの中の字列を指したなら text にして、**指し先を開いて在る綴りで書け**——引けなければ、直すのは申告でなく文書に書いた指しの方である。指摘側のうち根拠（cite）を持つ節（p0.purpose_review）と同じ関数を、修正する側も通る。

**見つけた周の記録はその周に直していても判定どおり書く**（直した周が阻害要因ありで終わるのは設計どおり。消えるのは次の周の採点）。新規ファイルは `git add -N`（対象差分と規模の数値は engine が固めた版から取るので無くても載るが、作業ツリーの `git diff` を読む道具には載らない）。規模の数値の固定の 4 つ（added_lines・comment_lines・comment_ratio_pct・doc_lines）は engine が数える——その場で足したい数値だけを `x_scalars` に `x_` で始まる名前で書け（周をまたいで同じ名前）。

あわせて差分の形の変化を申告しろ（後段の再発火条件と観点の適用に使う。採点ではない）: mechanism_changed（機構を足した／置き換えた）、premise_drift（P0-3 の制約を測った対象を削除・置換した。true なら premise_drift_note に測り直した制約と前の制約が偽になった理由）、gates_changed（検証ゲート）、seams_changed（代役・外部との継ぎ目）、security_surface_changed（認証・認可・秘密情報や個人データの取り扱い・外部との入出力に触れた。**迷うなら true**）、path_changed（利用者から見える経路）。任意で decision_records_changed（リポジトリの外に issue などの決定記録を書き足した周だけ true。リポジトリの中のファイルを触ったことは engine が差分から拾う）。
