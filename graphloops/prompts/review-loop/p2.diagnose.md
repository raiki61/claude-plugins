## 手順（1〜7 は木探索で。満足いくまで枝を深め、最後に枝同士を並べて見ろ）
各 finding を根とする木を、①反証（どんな条件で誤検出になるか。近傍の実態・規則の条件節まで読んで殺しにいき、殺せたら落とす。番号の外で毎回やる）②出自 ③上方展開 ④処方の候補、の枝で深め、全部の木を作ってから枝同士を並べろ——同じ根から出た木は束ねる／複数の木の上位で交わる原因は根本対策の候補（一撃）／ある木の実測が別の木の指摘を反証しないか。妥当かの判定はこの横断のあとに下せ。

1. クラスタリング: findings を「なぜ生まれたか（出自）」で根本原因にまとめる。
2. 出自分析（順序固定）: ①ロジックの正否 → ②出自が読みにくさ・命名・導線の死か、標準機構の迂回・外部標準の再発明・衛生違反（後始末漏れ・公式機構の自作迂回・外部 I/O の無防備・検証機構の fail-open）・手順の不成立／誤爆・実行観測でのみ現れた欠陥・根拠の循環か → ③ラベル。**隔離フレームからの観察は findings と同列に並べず、クラスタリングで吸収させて薄めるな**——単独で 1 つの根本ユニット（[block] 候補）になりうる。出自が導線の死・迂回・衛生違反・再発明なら「好み（nit）」ではない（具体的実害を生む）。P1 素材は 1 つ残らず突合しろ。
3. 上方展開: 各 [block]・do-now 候補に「なぜこの欠陥が存在しえたか」を最大 3 段（文化が悪いへの着地を防ぐ）。決着済み論点との突合もここ——ルーター: ①記録された理由がまだ束縛する → 落とす（理由が現在も成立していると確かめたときだけ。地位では落とすな）②新証拠が理由に答える → 「再開の提案」③理由が書かれていない → 台帳側の欠陥として surface。
4. 一撃の選定（**反証可能に書け**）: 複数の木の上位で交わる原因から、直すと最も多くの finding が連鎖的に消えるものを 1 つ（one_shot）。枝を 1 本ずつ見るだけでなく**組み合わせも見ろ**——2 つの処方が互いを不要にする／片方が他方を含む／2 つ揃って初めて閉じる、はどれも一撃の候補。選んだら `one_shot_closes` に**それで閉じると見込む unit の key を名指し**し、**効きの測り方は別に書かなくてよい**——次の周は closes の各 key の class_query を数え直して比べる（母数は prev_one_shot.totals が運ぶ）。**名指しの無い一撃は反証できず、次の周が同じ根を選び直すだけになる**（実測 2026-09-13: 3 周とも一撃は同じ根を指していたのに、毎周の閉じ方は名指しの 1 site だった）。
5. ラベルと disposition: 根本ユニットに REVIEW.md のラベル。生 finding 単独を [block] にするな。[suggest] には do-now / defer（既定 do-now、defer は構造的理由のみ、コスト感は理由にならない）。
6. **覆いの母数を機械で出せ（今の周に直す単位＝[block] と do-now は必須）**: 欠陥を 1 site 名指しして終わるな——「同じ形」を全部引ける機械の問い（そのまま走らせられる 1 行。grep / 構文木の走査 / 行トレース等）と、そのとき出た件数を class_query（how・total）に書け。`how` は次の周の判定者が走らせて母数を検算する物なので、件数が出る形にしろ。1 site しか無いならそれを示す問いを書いて total: 1。**母数を持たない指摘は「1 か所塞いで終わり」に閉じられ、同じ不変条件の別の入口が次の周に新しい顔で出る**（実測 2026-09-13: 3 周続けて同じクラスが再発し、判定者自身が「覆いの母数を誰も持たない」と書いた）。
7. 処方の列挙（零処方から）——ただし**この周が深い側に上がっているなら順序を反転しろ**: {{?loop.escalated}} が在る周は、同じクラスが周をまたいで戻った run である（機械が数えた事実）。その周は零処方の優先を外し、クラスごと消す処方（不正な状態を型で作れなくする・正本を 1 つにする・面を分ける）を**第一候補**として並べ、零処方を採るなら「過去の周が同じクラスを零処方で閉じて効かなかった」事実に照らしてなぜ今回は足りるかを書け（1〜3 行で塞げること自体は理由にならない——それが 4 周続いた）。機構の新設・共有面の拡大に及ぶ処方は確定するな——「設計の岐路」として questions に kind=fork で載せ、選択肢ごとに帰結を書き、零処方が落ちる理由を一文添えろ（添えられないなら岐路ではなく零処方で解く）。欠陥のキーに修正場所を埋め込むな（症状の形で書け）。
8. 安定キー: 「ファイルパス＋シンボル名＋一文要約」。突合は文字列の完全一致——defer 台帳に同じ欠陥があるならそのキーをそのまま使え。

問いの台帳（questions）: kind は fork（unit の key が origin。options 2 つ以上）／split（露呈した既存欠陥の別 PR 申請。origin は当該ユニット。[block]・do-now のユニットは origin にできない）／rule（観点の誤発火。origin は当該ユニット）／stuck／thrash（origin も depends も持てない）／premise／unverifiable（origin は R 名）／awaiting（origin は素材名。素材が awaiting_human なら必ず載せる）。status はこの周に立てるなら held。**問いは阻害要因を消さない**——当のユニットは [block] のまま。**書けるのは** key / kind / status / reason / resolution / options / depends / origin だけ。

出力: units（key・label・disposition・reason・reopen_evidence・class_query と、origin_analysis・why_chain・prescriptions）・framing（根本フレーミング）・one_shot・one_shot_closes・questions・materials_missing。
