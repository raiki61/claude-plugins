基準点 BASE を次の順で決めろ。**依頼文が基準点を名指ししていれば（SHA・タグ・枝名）それを使い、method は 4**——push 済みの既定ブランチで「ここから先を全部見ろ」と頼まれると、下の 2 は分岐点が HEAD になり 3 に落ちて直前コミット 1 つに縮む（実測: 6 コミット 95 ファイル +13,371 行の依頼が 1 コミットになった）。名指しが無ければ:
1. 作業ツリーに未コミット変更があれば `BASE=$(git rev-parse HEAD)`。
2. クリーンなら上流との分岐点 `BASE=$(git merge-base <既定ブランチ> HEAD)`（既定ブランチは `git symbolic-ref refs/remotes/origin/HEAD` で引く）。**`HEAD~1` を既定にするな**——複数コミットのブランチで直前コミットだけを見るとレビュー範囲が対象の数 % に縮み、見ていない範囲について収束を宣言できてしまう（実測: 6 コミット +416 行のブランチで 1.5% になった）。
3. 分岐点が取れない（上流が無い・既定ブランチが不明・分岐点が HEAD と同じ）なら `BASE=$(git rev-parse HEAD~1)`。

HEAD がマージコミットなら対象範囲を依頼者に確認しろ（merge_commit=true）。未追跡の新規ファイルは `git add -N` で差分に載せ、そのパスを intent_to_add に書け（ループが途中で終わったら `git reset -- <path>` で戻す。これがこの手順が index を変える唯一の書き込み）。以降の対象差分は engine が `git diff <BASE>` で取る。

material（base_determination）には SHA と、1〜4 のどれで決めたかと、対象差分が何コミット分かを書け。SHA だけでは範囲が縮んでいることが読み手から見えない。決められないなら awaiting_human。

あわせて差分の形を申告しろ（後段の観点の適用条件になる。採点ではない）: touches_gates（検証ゲート＝CI ジョブ・assert・テスト・pre-commit を新設・変更しているか）、touches_external_seams（別プロセス・別サービス・ブラウザ・外部 API・プロトコルとの継ぎ目に触れるか）、touches_user_path（利用者から見える経路を変えているか）。
素材（material）の書き方: status は found（見つけた。count と detail）／clean（今ラウンドに見たが無かった。checked に何を見たか）／not_applicable（条件に当たらない。reason）／awaiting_human（人の起動待ち。reason）／not_run（やるべきだったが飛ばした。reason）。前の周の判定を流用するなら carried_over（from_round と reason）。欄と値の正本は review-record.py。
