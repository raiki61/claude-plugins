欠陥は `/code-review high`、規約準拠は `pr-review-toolkit:code-reviewer`、品質は `/simplify`、認証・データ取扱い・外部 I/O に触れるなら `/security-review` も実行し、findings のみ取得しろ。**findings を機械的に集めるだけで、採点・ラベル確定はするな。** `/code-review` は指摘に裏取りの verdict（CONFIRMED / PLAUSIBLE）を付けて返す唯一の検出器だが、**その verdict は P2 の judge への入力であって、ここで確定させるな**。`--comment`（PR へ投稿）も `--fix`（作業ツリーへ適用）も付けるな——投稿は R1、当てるのは P3 で、この節は作業ツリーを変えてはいけない。`/simplify` は既定で修正まで行う skill なので、指摘だけ返す形で呼べ——4 観点（再利用・単純化・効率・高度）を修正を禁じたプロンプトでそれぞれ起こす（当てるのは P3）。**まとめ役の `pr-review-toolkit:review-pr` は挟むな。レンズは 1 つずつ名指しで起こせ**（`pr-review-toolkit:silent-failure-hunter` / `pr-review-toolkit:type-design-analyzer` / `pr-review-toolkit:pr-test-analyzer`）——散文の振り分けは差分の形（try/except・型定義・テストの有無）に依るが、この 3 レンズが当たるクラス（黙って無力化される検査・恒真になった柵・不変条件を平坦な値で持つ設計・振る舞い網羅の穴）は差分の形に関係なく出る（実測: 3 周続けて型設計のレンズが起動されなかった）。`pr-review-toolkit:code-simplifier` は指摘でなく修正を当てる agent なので呼ぶな。

各 skill を呼ぶプロンプトには次を課せ（REVIEW.md に書くだけでは skill に届かない）: 指摘の提出基準（`REVIEW.md`「指摘の提出基準」）: 機構（なぜそうなるかのコード上の因果を一文）・実測（動かせるものは動かす。動かせないなら「未実測」と明記して仮説として出す）・提出前の自己反証（規則を引くならその条件節が当たるか・近傍の実態まで読み、殺せなかった指摘だけ提出する）・誤検出の見積もり（どんな場合に誤りになるかを一行）。

skill の呼び出し自体が失敗したら（権限・実行時エラー）止めるな——findings に failed を書き、material を awaiting_human にして理由を書け。**無かったことを not_applicable にするな。** 直前の周から対象差分にロジック変更が無いなら /simplify の再実行は持ち越してよい（simplify_carried=true と理由）。作業ツリーを変えるな（engine が P1 の前後で突き合わせる）。
素材（material）の書き方: status は found（見つけた。count と detail）／clean（今ラウンドに見たが無かった。checked に何を見たか）／not_applicable（条件に当たらない。reason）／awaiting_human（人の起動待ち。reason）／not_run（やるべきだったが飛ばした。reason）。carried_over（前の周の流用）は走らなかった節に機械が書く——走った役は今の周の判定を書け（流用と書いても拒まれる）。欄と値の正本は review-record.py。
