判定:
- 削除候補のうち名指しされた「同じ内容の在り処」が実在するもの → 削る（deletions）。残すと判断されたのに運んでいる事実を言えなかったもの → 削る候補。説明が目的とずれた箇所 → 注記でなく構造か名前で直す。
- **問いの台帳の監査**（この経路は R1 しか無い）: split の origin が凍結した目的の内側なら、fork の選択肢に零処方（取り下げ・既存の機構 1 つ）が列挙も棄却もされずに人へ回されているなら redesign-needed（逃げ道の検知）。ledger_audit に問いごとの判定。
- 累積差分が最小か: (a) 小修正が積み重なって本来 1 根本で済むものを症状パッチしていないか (b) 他所から導ける内容の重複・より少ない記述で同じ目的を運べる箇所。simplify は制約付き——削ってよいのは検証済みの値打ち（挙動・テスト・導出の再現性）が落ちない分だけ。他所に無い情報（事実・導出根拠・why）を運ぶかだけをキーにし、書き手の意図を判定に使うな。同一情報の反復は自動保護しない（読み手の動線上必要と一文で言える場合だけ保護）。順序は『必要な内容が在るか（冷たい読み手が本文だけから再現できるか）』→『在るとして最小か』。
- do-now で直した修正も累積差分の一部として含めろ。採られた処方が「処方の最小性」に照らして正当化されているか（大きい処方に小さい方が落ちる理由が付いているか。列挙を経ずに機構が足されていないか）。
- scalar の相殺削除なき単調増の増分ごとに「他所に無い情報か」の正当化を要求しろ（increments）。正当化できない増分は集約・再配置の対象。

status は pass / redesign-needed / unverifiable。reason は最終報告にそのまま転記される。
