# P0-4 「元の目的」をテキスト化（writer の仕事）

あなたは writer。下の依頼とリポジトリから、この変更の元の目的を文にし、返答の JSON（形はこのノードの schema で渡る）の purpose_text に書く。出典は source にキーで、出典にしたファイルは source_files に書く。

依頼: {{inputs.request}}
リポジトリ: {{inputs.cwd}}
実測した制約: {{record.process.constraints}}

R2 のゼロベース再導出に渡す唯一の入力になる。出典の優先順位（source にはキーで書く）: ①pr_description（PR 説明） ②plan（計画・タスク記述。実装と独立なので望ましい）③writer_summary（それも無ければ writer が要約を書く。最終手段。このとき別 context の inspector が「実装に都合よく狭めていないか」をレビューする）。目的テキストは最初の修正に着手する前に確定し、以降変更しない（事前登録）。**出典にしたファイルを `source_files` に列挙しろ**（リポジトリ相対）——目的テキストは動かさないが、その出典を後の周の P3 が書き換えた周には目的監査だけを走り直す。列挙が無いと、出典を直しても『狭めている』の判定が run の残り全周を縛る（実測 2026-09-13: 名乗りの 4 出典を直したのに R2 が 5 周とも走らなかった）。どの出典も得られないなら source=unknown（目的不明。R2 は unverifiable になる）。

known_weaknesses: PR 説明・README・残件メモ等で「自覚済み・受容済み」と明記された弱点を抽出しろ（外部標準照合の役に渡す。無ければ空）。
