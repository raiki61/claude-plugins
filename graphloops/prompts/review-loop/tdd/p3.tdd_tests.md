この周の TDD の盤面（テストを書く前の版 start・元の結末 baseline。前の試行が赤の確認で差し戻されたなら problems に理由が在る）: {{loop.tdd}}

**この段ではテストだけを書く。実装のファイルに触れるな**——触れたファイルは engine が「テストを書く前の版」からの差で測り、`test_files` の外に触れていれば赤の確認が差し戻す。実装は次の段（p3.fix）で行う。この段の返答と赤の確認の結果は、次の段の指示書に貼られる（engine が会話を続けるのではない——書いた理由や却下した案は返答の欄に残せ）。次の段は `test_files` を書き換えられない（テストはここで凍る）。

直す義務の単位（[block] と do-now のうち、人に諮っている fork の出どころ・depends を除いた物）を全部、1 度ずつ次のどちらかに振れ:

- **tdd** — 今は落ちるテストを書き、`tests` に名指しする（実行器が JUnit XML に書く識別子。例: `path/test_x.py::test_y` の形）。
  - **使う側の呼び口で書け**（公開の関数・CLI・ファイルの形）。叩いた呼び口を `surface` に書け。テストの名前で意図を運べ（REVIEW.md「導線を作る手段の優先順位」）。
  - **書きにくさを記録しろ**（`friction`）: 準備が重い（`setup_heavy`）・内部の関数や欄を直に叩くか差し替えないと確かめられない（`reaches_internals`）・呼び口の名前から意図が読めずテスト名で補った（`name_unclear`）。旗を 1 つでも立てたら `note` に何が書きにくかったかを書け。書きにくさは設計への早い知らせで、実装の段と修正差分の審査に渡る。
  - **書きにくさを消す呼び口・名前の直しは、テストの側で先に決めろ**: 直した後の呼び口・名前でテストを書き、その案を `surface_change` に書け。実装の段はその呼び口を作る（テストは凍るので、実装の段で呼び口を変えるとテストが通らない）。まだ無い呼び口を呼ぶテストは、呼び口が無いこと自体で落ちてよい。
  - **赤は狙いどおりの失敗で**: engine はテスト一式を 1 回走らせ、名指しのテストが全部 failure で落ちることを確かめる。読み込み（import・構文）の失敗・準備の例外（JUnit の error）・一式に居ない・もう通る・飛ばされた、は失格。まだ無い関数を呼ぶなら、モジュールの頭で import せずテストの中で呼べ（頭の import の失敗は一式の読み込みごと落ちる）。**元の結末で通っていたテストは緑のまま**でなければならない（元から落ちていたテストは問わない）。
- **direct** — 先に落ちるテストを書けない単位（文書・指示書・注記だけの直し、JUnit を出さないテストでしか確かめられない振る舞い等）。`why` に理由を書け。今の修正の流れで次の段が直す。**TDD を強制して空のテストを書くな**。

`test_files` にこの段で書いた・書き足したテストのファイルを全部挙げろ（リポジトリ相対）。**件数の定数**（テスト一式が集めたテストの数を突き合わせる定数。件数の柵で、どこに在るかは対象リポジトリの側が名指しする）も、名指しのテストを足した分と、並行の線が修正の前に重ねたテストの分をこの段で合わせ、そのファイルを `test_files` に挙げろ——次の段はテストの置き場を書き換えられない。
