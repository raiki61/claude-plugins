盤面: {{loop}}
人が決めることの本文（前の節）: {{out.report.human_items.text}}
初見検査の結果（詰まりが残っていれば直してから出す）: {{out.report.cold_check}}
判定者の生の返答（judge・R1〜R4・比較役・隔離フレーム。要約で丸めず、根本ユニットのキー集合と verdict と理由はそのまま転記する）:
{{ref:raw}}

報告は {{inputs.lang}} で書く。subagent の出力が違う言語でも揃える（コード識別子・パス・エラー文はそのまま）。

報告の 1 行目には、保存のときに engine が来歴の行（プラグインの版・run の番号・周）を刻む——自分で書き写すな。この行は下の前置きの行にも『冒頭 3 行』にも数えない。

判定から入った run（記録の process.request_entry が在る）なら、冒頭 3 行の前に 1 行で「判定から入った run（出どころ）。P1 の役は、修正が入るまで起こしていない」と書く。依頼の外を見る目が欠けた周があったことを、収束の見た目に埋もれさせない。
依頼の入口にバッチが積まれた run（process.request_history と process.request_findings のバッチ。入口かどうかに依らない。人の依頼のほか、仕様の道の受け入れ条件・並行の線の見逃しのバッチも含む）なら、続けて 1 行で全バッチを周・出どころ（origin）・件数つきで並べる（例:「依頼: round 1 に 3 件（人: 出どころ）・round 3 に 1 件（並行の線）」）。人の依頼と機械の線を『人の依頼』と一括りに書くな。周で絞らない——どの周に積まれた依頼も報告から落とさない。
人の方針の文書が、最後に固定した版（init か、関所で人が通した版）から変わったまま run が終わった（記録の process.policy_change が在る）なら、続けて 1 行でそのことと差分・写しの置き場を書く。関所で通した変更は process.policy.amendments に在る。

構成:
1. 冒頭 3 行は人が決めること（前の節の本文を、初見検査の詰まりを直して置く）。次に「ループが自分で決めたこと」（resolved / decided の問いと resolution）。
2. 判断材料として検証器の履歴（全ラウンドの推移）をそのまま貼る。
3. 各根本ユニットの「ラベル・対応内容／対応不要の理由」。defer の台帳（全ラウンドの和集合。後の周の judge が挙げ直さなかったキーも受容は続いている）。
4. R1・R2・R3・R4 それぞれの verdict と理由（記録の reviews から。持ち越したものは実際に走らせた周も）。R1 は削ったコメント・残した why も。
5. 問いの台帳の全推移——各問いが何周目に立ち、どの周に何で決まった（または人へ回った）か。決めた根拠は resolved にした周の resolution から。
6. grader の生出力（根本ユニットのキー集合）・grader 再実行の回数・元の目的の出典（①②③）・BASE の SHA。
7. 主経路の実行観測: 何をどこで動かし何を観測したか（「テストが緑」を観測として書くな）。
8. 新設機構の棚卸し: この差分が導入する機構・配管（ビルド設定・環境変数・CI ジョブ・テンプレートのノブ・スクリプト等）を、判定抜きで一覧する。
9. 収束せずに止まった run なら、台帳の held / escalate をまとめて聞く。前提のドリフトがあれば、測り直した制約と前の制約が偽になった理由。
返答は報告の本文そのもの（Markdown）。
