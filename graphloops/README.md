# graphloops

**Who this is for.** The loops are procedures an AI agent in Claude Code repeats round by round until the result stops changing — reviewing a code change, researching a design question, diagnosing a repository, or checking that a document reads well to a newcomer. Most users who want these loops should install [convergence-loops](../convergence-loops/README.md) instead. Install graphloops if you want the program-driven versions `/review-graph` and `/research-graph` (a program, not the conversation, keeps track of the steps), or if you develop the loops themselves. To use it, follow "Installation" below and then the quick reference in [skills/review-graph/SKILL.md](skills/review-graph/SKILL.md#早見); everything after "Installation" is reference material for contributors.

The graph-executed version of the convergence loops (procedures that repeat until the result stops changing). The 4 commands that convergence-loops in the same repository ships (`/review-loop`, `/research-loop`, `/doctor-loop`, `/firstread-loop`) write the procedure as prose instruction files, which an LLM reads and follows. graphloops maps the same loops into JSON of "nodes (steps) + dependencies + round conditions", and a machine (the engine) holds the board and runs them. The LLM on the running side only executes the nodes it is handed and returns the results. The skills' and commands' instructions and descriptions are in Japanese.

There are 2 executable versions: `/research-graph` (the executable version of `/research-loop`) and `/review-graph` (the executable version of `/review-loop`). Of the existing 4 commands, 3 (`convergence-loops/commands/doctor-loop.md`, `research-loop.md`, `review-loop.md` (relative to the repository root; they are not in the installed plugin, so look at a clone or on GitHub: https://github.com/raiki61/claude-plugins)) were touched when graphloops was first added — sentences saying that roles with Read get a path instead of the pasted text (1 line in doctor, 1 in research, 2 in review), and 1 line in `review-loop.md` on how to set the baseline. In total 5 lines were replaced; allowed-tools and `firstread-loop.md` are unchanged (you can confirm with `git diff <BASE> --stat -- commands/ convergence-loops/commands/`, where `<BASE>` is the commit just before graphloops was added. When they were touched they lived in the root `commands/`, so passing both that and the location they were moved to makes git count the move as a rename and show only the changed lines. An earlier version of this README said "only the 1 line about how to pass the text to roles", which disagreed with the actual diff. During the review of that change, the purpose audit — the review-loop check of the fixed purpose text before it is handed to the R2 reviewer, R2 being the step that re-derives the ideal solution from the purpose alone — cited that disagreement and blocked R2). The prose loops stay in convergence-loops unchanged; graphloops sits next to them rather than replacing them. The record format and the validators (convergence-loops' `scripts/<loop>-record.py`) are shared, and they are the bridge between old and new — running both on the same target and comparing the records that passed the same validator is the acceptance test.

Changes per version are in [CHANGELOG.md](CHANGELOG.md). How versions are released (the step that appends to the change log; no git tags are created) is in [docs/releasing.md](../docs/releasing.md) (relative to the repository root, and not in the installed plugin. Look at a clone or on GitHub: https://github.com/raiki61/claude-plugins).

## Three layers

| Layer | Location | What it holds |
|---|---|---|
| engine | `scripts/loop.py` | board, waves (groups of nodes whose dependencies are all met, so they may run at the same time), fan-out, conditions, placeholder filling, type checks, generic writes, coverage, working-tree comparison, asking a human, escalation, traces |
| graph | `graphs/<loop>.json` | nodes, dependencies, roles, prompt_file, schema, writes, cond (the name of a condition function), reads. At the top level: plugin (the plugin that holds the role agents and validators), runners (each node's `run_by` names who runs it — a role agent, `driver` for the engine itself, or a runner; `runners` lists the `run_by` values that count as runners, e.g. `writer` and `skill` in review-loop), thickness.tiers / default / deciders (thickness is how heavy a run is: `tiers` lists the levels, e.g. light / standard / heavy, `default` is the level used when none is given, and `deciders` lists the allowed values for who chose the level — the default, or the requester asking for a lighter run), deliver.path_tools (tools that can read on their own) |
| rules | `rules/<loop>.py` | the record's initial shape, how fan-out items are chosen, node conditions (CONDS; functions that declare the fields they read), machine nodes, post-checks for consistency, finalization |
| blocks | `blocks/<loop>/<name>/` | groups of nodes (`nodes` in `block.json`) and the exit schema (`exit.schema.json`; the types of the node outputs that nodes in other blocks read, keyed by node name). Shared core types are in `blocks/shared/<name>/`. The graph points here with the top-level `blocks` and `shared_blocks`, and with `$ref` in the `schema` of exit nodes |

The engine knows neither the loop's node names nor the record's field names. The graph refers to them by name, and the engine calls the rules by name. What cannot be written in JSON is only arithmetic (count equations, consecutive counts, random sampling, writes specific to a record format), and that lives in the rules.

Prompts are in `prompts/<loop>/<node>.md` (paragraphs that are the same across loops — the human-policy paragraphs `prompts/policy*.md` — are placed directly under `prompts/` and appended to nodes with the graph's `prompt_append`. How their location is decided is `rules/policy_input.py`, shared by the rules of both loops. How to run them: [「人の方針」 (human policy) in skills/review-graph](skills/review-graph/references/policy.md#人の方針)). Placeholders (forms like `{{record.claims | pick id,claim}}`) are filled only if declared in the graph's `reads` — "what must not be passed" is protected by not pasting it. `out.<node>` is the output of an earlier node, `prev.<node>` is that node's output from the previous round in which it last ran (the same scope for placeholders and for `ref:`; the same prefix is not given two meanings), `file:` is a file's body, and `section:<path>#<heading>` is one section of a markdown file (both are for pasting to roles without tools; if they exceed the limit they are cut and this is recorded). The engine does not hold the loop's vocabulary (role names, tier names, tool names, plugin names) — all of it is declared at the top level of the graph, and graphcheck looks for gaps. `ref:record` `ref:out.<node>` `ref:prev.<node>` `ref:raw` give not the body but the location path and a 1-line summary — used for runner nodes (the runner already read the reply once when it received it, so pasting it again uses the context twice). Where role replies are stored is also decided by the engine (`out_path` in `next`. The engine starts the role with `loop.py launch`, writes the reply there, and finishes acceptance, so the reply does not pass through the runner's context). How the prompt is passed to the role is also decided by the engine (`deliver` in `next`): if the `tools` in the role's definition include any of the graph's `deliver.path_tools`, path (the runner does not touch the body); otherwise paste. For nodes that continue the same role (`same_context_as`), the engine carries over the conversation number (`session_id`) from when the previous node was started with `launch`, and continues the same conversation with `--resume` (for a node started with Agent, the id left with `done --agent-id`).

## What happens when you run it

`init` creates the board (`$(git rev-parse --git-dir)/graphloops/<loop>/<run-id>/`; outside the working tree), and `next` returns, as JSON with prompts, "the nodes that may run now". The runner (here: the conversation that drives the run; a runner node is a node whose `run_by` is one of the graph's `runners`, done by that conversation) has the engine start role nodes (nodes answered by a role agent [the plugin's `agents/*.md`; tooled roles are those among them that have tools]) and nodes with a delegate (nodes that have `launch`) via `loop.py launch` (the engine waits directly for the child to exit, writes the reply, and finishes acceptance. If the reply is rejected, the engine sends the reason back to the same role conversation (`--resume`) and asks it to resubmit. No time limit is set), does its own nodes (runner nodes) itself, and returns replies with `done`. **Delegates are started inside the OS sandbox** — the working directory is a copy of the real one, and they cannot write to the real working tree, the gitdir's actual contents, the shared `.git`, other working trees, or the board (a fix for an incident where a delegate started with the Agent tool ran `git reset --hard` in the real working tree and erased the runner's uncommitted fix; 2026-09-25). Only for runs that need work that cannot be done inside the fence, such as using docker, can a human remove the fence with `init --unfenced-delegates "<reason>"` (the fact that it was removed stays on the board and in the notes of `next`). Where the delegates of an unfenced run are started depends on how the run is driven (delegates of a fenced run are inside the sandbox as above, however it is driven): in a run without a runner role (a run where the engine also starts the runner nodes and no conversation does nodes; see "Running without a runner role" below) the engine starts them outside the sandbox (the working directory stays a copy of the real one); in a `--no-engine-runners` run and on boards started with an earlier version, the runner starts them in the foreground of the Agent tool and waits for that return as the exit (background delegates are not waited for). If a human stops it midway, it is `loop.py stop --reason`; the reason for stopping stays in the record and only the report node runs. A failed attempt is restarted with `loop.py relaunch` — after writing the new attempt, the engine stops the children of the previous attempt it started, whole tree, and the number of attempts and the reasons stay on the board and in the trace. Children left over after acceptance (trees that could not be fully stopped, children of an attempt whose launch died first) are listed by `loop.py children` from the markers on the board and stopped with `--stop --reason` (it does not search by ps strings; running attempts and instances before acceptance are included only with `--include-running`). The engine checks replies by type, copies them into the record, counts fan-out coverage (whether the returned answers cover all items), runs machine nodes (count cross-checks, convergence judgment), and opens the next round, stops, or asks a human. Before the final `report`, it finalizes the record and runs the validator, and if it does not pass, it does not emit `report`. `loop.py run` (`engine/runner.py`) is what gives this next → launch → done cycle to a program instead of a conversation. A conversation runs `loop.py run` in the foreground; it starts a detached driver (a background process; 1 per run, determined by the lock on the board's directory) that keeps running the nodes the engine can start. `loop.py run` itself returns with an exit code only for nodes handed back to the conversation, waiting for a human's answer, a round stop, or the end (how to run it and the values are in item 2 of 「早見」 (quick reference) in [skills/review-graph/SKILL.md](skills/review-graph/SKILL.md)). A run stopped with `init --stop-after-round` advances to the next round with `loop.py resume`.

**Running without a runner role** (a runner role is a conversation that does the runner nodes itself; it is different from the driver above [the background process]. This is `init` without a flag. The conversation-driven path is chosen with `--no-engine-runners` — scheduled for removal): the engine also starts the runner nodes (baseline, premises, purpose, fix proposal, fix, rework, report, and local review; among the runner's nodes, those that have no delegate and no run-only declaration [the graph's `engine_run`; a node that only runs a command such as the test suite]) as `claude -p` children, and the driver runs them. The parent (a human or a conversation) types `init` → `run` and gets control back only where it stops (a human's answer, a round stop, the end). Read-only nodes take the same form as tooled roles (measuring commands run inside the sandbox); nodes that rewrite the working tree (the graph's `launch.runner.edits`) have only path-restricted `Edit(./**)` and `Write(./**)` plus Bash inside the sandbox, and cannot write to `.git`, other working trees, the board, or the user's settings (source of truth: `role_run.runner_permission`; the reason is in the graph's `launch.runner.why`). Local-review skill nodes are started as read-only children that have Skill and Agent (`role_run.skill_permission`). Background lines (nodes, like mutation re-checks, that are run side by side without waiting for them to finish) are started by the driver as detached children after it has done the acceptance of that node. Nodes the engine cannot start go to a human with a reason (the instance's `unlaunched`) (`run`'s 14), and the 13 that returns to the conversation is left only for engine bugs (contradictions in the board) (boards started with an earlier version behave as before). In a `--no-engine-runners` run, the conversation does the runner nodes as before. The steps are in [「早見」 (quick reference) in skills/review-graph/SKILL.md](skills/review-graph/SKILL.md#早見). research-graph does not yet have a declaration for the engine to start its judgment node (surveyor), so the conversation runs it regardless of the flag.

What a machine can enforce better than prose instructions: dependencies and waves, what must not be passed, role assignment, limits, consecutive counts, silent omissions (coverage cross-check), resuming after compaction (the board is on disk), and before/after comparison of the working tree (**its reach is narrow on 2 axes** — only what git reflects 〈under .git/, ignored files, and anything outside the repository are invisible〉, and only the time points before and after P1, the review-loop stage that gathers review material 〈rewrites during judgment or fixing are not seen. Measured 2026-09-13: during this run's judgment the engine was rewritten in 1 place and the board stopped nothing〉). **"No downgrading by the runner" is not in this list** — what the machine enforces goes only as far as graphcheck's check 2 (a node's run_by does not touch verdict fields); the engine does not watch the paths by which the runner lowers the tier, answers itself without starting a role, or rewrites a role's reply (rule U in the repository's `docs/loop-contract.md` — "the runner must not decide its own level of checking" — as it stood at BASE, the base commit a review compares the change against, also lists the same item as "prose only"). So downgrading by the runner is a current, accepted limitation, not enforced by machine. An earlier version of this README listed it among the enforced items above, which contradicted its own list of limitations.

What remains unenforceable: **the context isolation of the isolated roles (roles with zero tools) is not complete** — `--setting-sources ""` can drop only the 3 sources user / project / local; settings from organization management (managed-settings.json, MDM, the console) cannot be dropped. In particular, the standard output of SessionStart / UserPromptSubmit hooks is added to the context as plain text even for a role with no tools at all (per the official hooks specification; it is not tied to a tool call, so `--tools ""` does not stop it either). `--bare` is a single flag with the same purpose, but it limits authentication to an API key and does not read OAuth or the keychain, so it is not a simple replacement and is not used. ／**Children do not inherit the interactive claude's authentication**, so `launch.argv` is prefixed with a thin layer that adds only authentication (`scripts/with-auth.py`) (measured 2026-09-12: a round stopped on a single 73-byte line "Failed to authenticate"). The stages are "respect authentication present in the parent's environment → on mac, the Keychain → at every stage, pass `CLAUDE_CONFIG_DIR` explicitly to the child", and **in environments without a Keychain only the last stage (passing `CLAUDE_CONFIG_DIR`) works** (= if that config-dir has no authentication, nothing can save it. In that case a line `with-auth: auth=…` appears on standard error, so you do not mistake it for a bad role reply). ／**Roles are started by the engine** (`loop.py launch`). Having the runner start them from Bash was dropped because spellings that redirect output to a file get stopped by the auto mode classifier (measured 2026-09-15: with the same layer, the form whose output appears in the conversation passed, while `< material > out_path` was rejected as "Auto-Mode Bypass". The gates plugin in this repository starts a reviewer with the same kind of command from a hook and is not stopped, because the classifier does not look at hooks, not because of a difference in authentication). Since launching moves into the engine, **what gets started is enforced by the engine by machine** — it starts nothing except its own interpreter and the bundled layer, and reads the words after claude against a per-form flag allow table (it rejects words not in the table — official aliases, the `--flag=value` spelling, `--add-dir`, `--mcp-config`, `--agents`, flags that remove permissions, positional arguments — and a second occurrence of the same flag). Only values decided by the engine are allowed: for tool-less roles, `--tools ""` and `--setting-sources ""`; for tooled roles, `--setting-sources ""`, `--permission-prompts none`, and the permission form, the pre-allowed tools and the settings (`--settings`; the sandbox of roles that have Bash) are the values the engine decided (`role_run.tooled_permission`), and the tools passed match the role's definition and include no file-writing tool. For all roles: model, effort, and system prompt body match the role's definition, and only conversations decided by the engine are continued (the form is decided by the role definition re-read at launch time. A fence that decides by reading the graph's declarations is not a fence, because anyone who can write the graph can rewrite the fence along with it). **Tooled roles are also not given CLAUDE.md** (`--setting-sources ""`): what a role sees is only what the graph's `reads` declared (the perspectives' REVIEW.md is passed via `reads`) ／ the user's CLAUDE.md is output etiquette aimed at the runner and conflicts with the contract of returning only JSON (measured 2026-09-25: when it was read, a marker got attached to the head of the reply) ／ the user's and plugins' hooks do not fire in the child, so the read record covers only the runner's reads. The cost is that the project's CLAUDE.md rules also do not reach the role (pass the rules you need via `reads`). Children do not load plugins, so the engine copies the body of the role definition from `agents/<role>.md` onto the board and adds it to the system prompt, and lists tools, model, effort, and permissions in argv (the facts that determine permissions are not placed outside the argv that the fence reads). ／The runner skipping the engine or rewriting prompts (the trace and prompt hashes remain, so it can be detected. To block it, check the hash in an Agent PreToolUse hook — not implemented). **Also included in the same accepted limitation**: taking the source of truth for execution from the tree under review and from environment variables (the flags and values of the launched words are bound by the engine's allow table, but the actual thing launched (where claude is) is looked up from PATH, and relative paths in the rules are not confined under the graph's directory. `<PLUGIN>_ROOT` / `CLAUDE_CONFIG_DIR` switch the exec target, the role definitions, and where the scripts live. The perspectives' `REVIEW.md` is taken from the working tree, not from BASE, the review's base commit) — in a self-review the runner is in a position to edit the graph / rules / perspectives that run it. **The board's save path**: commands that write the board re-read → compare → write under the lock on the board's directory (`engine/filelock.py`; the OS releases it if the holder dies), so the driver, the conversation, and a human writing at the same time do not interrupt each other. However, the non-atomicity of committing the 2 files state.json / record.json (a crash after writing record and before writing state) remains. And the quality of the roles' judgment itself.

### Running under an external harness

<a id="外の土台の下で回すとき"></a>

When the engine (any subcommand of `loop.py`) receives a stop signal (SIGTERM, SIGHUP, SIGINT), it stops the trees of children it started. On POSIX it sends SIGTERM to each tree, waits for a grace period, and then sends SIGKILL to what remains (on Windows it stops them immediately with taskkill /T /F, and uses the grace period only as an upper bound on waiting to reap the leader). The grace period defaults to 5 seconds and can be chosen with the environment variable GL_KILL_GRACE (seconds; a finite number 0 or greater). An unreadable value is an error at engine startup (import) — silently falling back to 5 seconds would leave grandchildren behind without warning while you believe you shortened it. The source of truth is `DEFAULT_KILL_GRACE` and `_grace_from_env` in `engine/role_run.py`; the source of truth for the stop procedure is `_stop_tree` and `kill_all` in the same file.

- **Upper bound (no guarantee)**: if you run under a harness that starts the engine as a child and, on cancellation, sends SIGKILL after SIGTERM, make the grace period sufficiently shorter than that harness's cancellation grace period. If it is the same or longer, the engine itself disappears from an external SIGKILL before it sends SIGKILL, and grandchildren that ignore SIGTERM remain. But shortening it is necessary, not sufficient: GL_KILL_GRACE shortens only the waiting part; the time until SIGKILL has been sent also grows with the number of trees being stopped (trees are stopped one at a time) and with the per-tree enumeration (ps; up to 30 seconds each time, not bound by the grace period). There is no value that guarantees everything is stopped within the external harness's grace period (a known limitation; stopping trees concurrently and bounding ps are candidates for a separate request).
- **Lower bound**: make it longer than the time roles (`claude -p`) and the executors running under the engine take to finish cleaning up their own children on SIGTERM. If it is shorter, they receive SIGKILL in the middle of cleanup. 0 sends SIGKILL right after SIGTERM.
- **Where to set it**: in the environment from which the harness starts the engine (where every `loop.py` call inherits it). If you set it for only one call, the other subcommands (`next`, `done`, `relaunch`, `stop`, `children`) stop with the default.
- **What inherits it**: the value is also inherited by the children the engine starts. Roles and delegates (`claude -p`) do not load the engine, so it has no effect on them. This repository's test suites (`tests/run.sh`, `graphloops/tests/run.sh`, pytest's `conftest.py`) unset it before running — so that checks that stop children assuming the default 5 seconds do not break only under a harness.

## Recording problems you hit (/graphloops:intake)

<a id="踏んだ問題を残すgraphloopsintake"></a>

Records problems hit in the user's environment, 1 line per problem, without having to carry them over by pasting the conversation (the design is stages 1 and 2 of [docs/feedback/intake.md](../docs/feedback/intake.md); relative to the repository root, and not in the installed plugin). The recorder is the single file `engine/intake.py`, and only it assembles the provenance (the plugin's name, version, commit if obtainable, run number and round).

- **What is recorded automatically**: calls where `loop.py` ended non-zero (including everyday rejections with exit 1; the everyday ways `loop.py run` stops — 10, 11, 13, 20 — are not recorded. A 13 in a run without a runner role is an engine bug, so the driver records 1 line), and lines where a role failed or rejections continued up to the limit in `loop.py launch` (launch itself still exits 0. Instead of an exit code, the line carries the kind of failure, and the key is split by it too — `commands.launch_cause`). Things that do not go through `loop.py` (`with-auth.py`, `graphcheck.py`, `parallel-pr.py`, `quality-ledger.py`, the hook `record-read.py`) are not recorded
- **The manual entry point**: `/graphloops:intake <1 line>`. Collect what has accumulated into 1 file with `export <destination>` and hand it over. If you set a destination with `set-url <URL>`, `send` POSTs it (`{"text": summary, "records": lines}`; stage 3, which sets up the receiving side, has not been built). All of these are flags of `loop.py intake`
- **Storage**: `intake.jsonl` in Claude Code's persistent storage `${CLAUDE_PLUGIN_DATA}` (not erased by updates; erased on the final uninstall). That variable is not passed to Bash commands, so the automatic entry point derives `<plugins>/data/<plugin>-<marketplace>` from the engine's location `<plugins>/cache/<marketplace>/<plugin>/<version>` by the same rule as Claude Code. Runs loaded with `--plugin-dir` and runs executed directly from a checkout cannot derive it, so no automatic lines are recorded (the manual entry point still records, because the instruction file's body passes the location)
- **Fields and confidentiality**: by default only structured fields — plugin name, version, commit if obtainable, OS and Python versions, call site (down to the node id; item keys and paths are dropped), exit code, exception type and the function that raised it, run number and round, and the 1 line a human wrote. Bodies, diffs, and record contents are not kept. The key for counting the same problem does not include the version. The head of standard error is kept only when the environment variable `GRAPHLOOPS_INTAKE_STDERR=1` is set, and is dropped by default from exports and from the body that is sent
- **Never blocks**: whatever happens, the recording does not change the original exit code or output. It uses neither authentication nor the network (only send, which the user calls explicitly, uses the network, and no deadline is set on it)
- **Report header**: when saving a `save_text_as` node (the final report of both loops), the engine stamps the provenance on line 1 (`graphloops <version> (<commit>) / <loop> run <run_id> / round <round> / graph <sha>`)

## Counting run quality per version (scripts/quality-ledger.py)

An entry point that answers "is the graph's quality improving version by version?" with numbers. It reads across boards and outputs 1 line per run (`--runs`, as JSON Lines) and a summary per engine version (text by default, JSON with `--json`): `python3 graphloops/scripts/quality-ledger.py [root ...]`. The default root is the shared git directory of the repository at cwd, and it picks up the boards of the main checkout and of linked worktrees (boards created elsewhere with `init --dir` are counted only when you pass their parent as a root). What it counts are the values written on the boards themselves — round verdicts (R1–R4, the 4 whole-change reviews of review-loop's final overview stage: R1 redundancy and minimality, R2 zero-based re-derivation from the purpose, R3 overall consistency, R4 cross-cutting risks outside the diff; rows filled in by the machine and carried-over rows are excluded using the validator's and rules' predicates, and rows with keys or values the current predicates do not know are reported separately as "uncountable" per R key and value), states and reasons for stopping, gate answers (who gave the answer is not recorded on the board), acceptance results and the heads of rejection reasons (grouped after masking absolute paths and login names), relaunches, elapsed time and role run times, cost (the sum of per-conversation maxima), and the time since the last trace of a running run. It only reads, writing neither to boards nor to the plugin's location; a broken board is counted as "unreadable", and locations are output relative to the root. The denominator of each R's numbers is the number of genuine verdict rows for that R (「判定 N」 (verdicts N) in the text output). Machine rows, carried-over rows, and uncountable rows are excluded and counted separately per R row, not per round (in the same round R1 can be genuine and R2 carried over; an R with no key in a round goes into none of them). 「閉じた周」 (closed rounds) in a version's header is the number of `rounds/round-<N>.json` files, not the denominator of R. A round is attributed to the engine version that ran it, and the predicates of the current plugin are applied to rounds of older versions too. The source of truth for the fields and how they are counted is the script's docstring. This is a display that reads existing boards, not the cross-run record that [docs/adr/0061-cross-run-record.md](../docs/adr/0061-cross-run-record.md) decided to build (one file per run in a shared local directory, so that flaky tests and repeated problems can be counted across runs; not implemented yet).

## Checks

```bash
python3 graphloops/scripts/graphcheck.py graphloops/graphs/research-loop.json scripts/research-record.py
bash graphloops/tests/run.sh
```

Paths in this section and the next: `tests/simulate.py`, `tests/simulate_review.py`, `tests/parallel.py`, `tests/py/…` and `tests/replay_boards.py` are under `graphloops/`; `tests/mutate.py`, `tests/mutations.json` and "the root `tests/run.sh`" are at the repository root.

`graphcheck` checks the shape of a graph (dependencies exist and have no cycles, the runner does not output verdicts, the validator's fields appear in node outputs, placeholders are declared in reads, the runner's writes do not touch verdict fields, names exist in the engine or the rules). `tests/run.sh` additionally runs end-to-end simulated runs in which role replies are replaced by scripts — for research: unattended stop, consulting a human who is present, lightweight cut-off, rejection of replies that must be rejected (the standard 3-round convergence was moved to pytest's `tests/py/test_sim_research.py` — see "Where pytest tests live" below); for review: convergence over 2 consecutive rounds, to a human on a failed premise, to a human when attributed to a held question, continuing after passing the answer, stopping at the limit, rejection of replies that must be rejected (each round's record is passed through the real validator review-record.py as a directory). It does not look at the quality of the roles' judgment (that is for real runs).

**In CI the scripts are run split into shards** (`.github/workflows/test.yml`): the full set of scripts was the bottleneck within 1 job, so the test job became an OS × 4-shard matrix, and the i-th script in definition order runs in shard i % 4 (the contract follows Bazel's test sharding; the source of truth is `shard_spec` and `assign` in `graphloops/tests/parallel.py`). Checks that need the sum over all scripts (reaching of the verdict vocabulary, hits of delivery modes) cannot be judged inside one shard, so each shard only writes its counts, its number of scripts, and its reached sets into a roster (a per-shard manifest file whose location CI passes in `GL_SHARD_MANIFEST`); the count fences (`EXPECTED_CHECKS`, `EXPECTED_TESTS`) and the sum checks are applied in 1 place by the shards job, which waits for all shards, with `parallel.py merge`. The shard is specified by environment variables that the CI step passes, and the root `tests/run.sh` passes them only to its 1 step that runs `graphloops/tests/run.sh`. **When you run `bash tests/run.sh` or `bash graphloops/tests/run.sh` locally as a single run, there is no shard specification, so, whichever of the two you start, all scripts (the test functions) of each script file — `graphloops/tests/simulate.py` and `graphloops/tests/simulate_review.py` — run concurrently on threads within that file's 1 process**, and the fences are applied on the spot — in CI shards, what runs concurrently narrows to scripts in the same shard, so interference between scripts is caught by this single run.

**Foundation for board-running scripts** (`graphloops/tests/py/glharness.py`; `conftest.py` loads it as a plugin): it does not copy the script bodies (`Run`, `drive`, `check`, the stand-in claude); it imports and uses the script modules.

- **2 entry points** (`--gl-driver=cli|inproc`, default cli): cli starts `loop.py` in a child process as now. inproc replaces the name `subprocess` in the script module and routes only the `subprocess.run` calls that start `loop.py` to `loop.cli()` in the same process (code paths in a script that start `loop.py` with `Popen` instead stay child processes — it emits a warning; these are not mutation arms). inproc restores the engine's global state on every call (the table `glharness.RESTORED`: `util.GIT_CWD`, `role_run.LIVE`, the validator's load cache, `tempfile.tempdir`, signal handlers, cwd, environment variables, standard input/output). Since it touches signals it can only be called from the main thread, and parallelism is by pytest-xdist processes, not threads
- **fixtures**: `gl_script("review")` (returns the script module through the chosen entry point), `gl_run(kind, name, **Run arguments)`, `gl_check` (the same `check` and `skip` as the scripts, plus `reach`, which records reaching), `fake_claude` (an environment with the stand-in claude at the front of PATH), `gl_tmp` (points the temporary-location environment variable TMPDIR at `tmp_path` — so that the scripts' workspace, the engine's location, child processes, and the base of `parallel.rm` all look at the same place; cleanup is left to `tmp_path`), `wave` (`tests/py/waves.py`; by wave name, like `wave("review/neg/p2")`, it starts from a board snapshotted after running the first half of a script once in the same process. During the checks, both scripts call loop.py through the inproc entry point. The snapshot is a per-worker session fixture), `scene` (`tests/py/scenes.py`; by list name and marker, like `scene("review/stop1", "status")`, it copies back from the snapshot everything up to just before the marker, and returns the reply of the marked event and the board after it)
- **How checks are counted**: the source of truth for the line format and the counting is the scripts' `check`. The pytest side reads the difference in the scripts' counts and failures before and after each test, fails the test if there is even 1 failure, and appends `  FAIL <desc>` lines one by one to the location in the environment variable GL_CHECK_LOG
- **Cross-checking the 2 entry points** (`test_drivers_agree` in `test_harness.py`): runs the same scenario through both entry points and compares the boards (`state.json`, `record.json`, round records) after normalizing run number, times, workspace root, durations, and prompt summaries (the bodies paste workspace paths). Durations are only measured and output (2026-09-26, load around 100: review's standard scenario took 354 seconds with cli and 145 seconds with inproc)
- **Size markers** (Google's Test Sizes): `small` fails if it calls a child process or sleep (it fails even if the error is swallowed). `medium` is for tests that run child processes, git, or boards, and mutmut does not select them (`graphloops/setup.cfg`). Time limits and automatic retries of failed tests are not added

**Fences** (`graphloops/tests/py/fence.py`): skips are failures (both per-test skip/xfail and whole-module skip/importorskip). The only exception is a declared skip for a test that looks at a capability the OS does not have — write the reason in the form `SKIP <capability>: <reason>`; it is allowed only when that capability is in the environment variable SKIP_ALLOW (the list of permissions CI passes per OS; the source of truth is `matrix.skip_allow` in the CI settings, the same value as for the skips in `tests/run.sh`; empty by default), and allowed skips are listed. The number of collected tests is compared against `EXPECTED_ITEMS` with `!=` — only in runs that collected every test file in the location; runs that narrowed files by path, node id, `--ignore`, etc. drop the fence and print 1 line saying so (`-k` selects after collection, so the fence stays on). The number of script checks that ran is compared against `EXPECTED_SIM_CHECKS`, and the number of values reached against `EXPECTED_SIM_REACHED`, with `!=` — only in full runs that also deselected nothing with `-k` or `-m`. In `-n` runs, the controller collects the values counted by the workers and applies them (the list of node ids arriving from the workers cannot see a file whose tests were all deleted). CI runs the whole location.

**A tool to run only the tests related to a change (pytest-testmon)**: if used, only for fast local runs; before commit and in CI, run everything. testmon does not collect files, so the fence above treats such a run as a "narrowed run" and drops itself. Measured facts (2026-09-25, Python 3.14, pytest-testmon 2.2.0, coverage 7.16.1): with the settings as they are, it does not track changes to `engine/`, which is outside the rootdir (`graphloops/tests/py/`), and selected not a single test even when `schema.py` was broken. With `--rootdir=graphloops` it tracks them, but under Python 3.14's default (coverage's `COVERAGE_CORE=sysmon`) it missed tests that should fail, and with `COVERAGE_CORE=ctrace` it selected correctly. It has no effect on changes to graph JSON or prompts:

```bash
cd graphloops/tests/py && COVERAGE_CORE=ctrace uv run --no-project --with pytest --with pytest-testmon python -m pytest --rootdir=../.. -c pytest.ini --testmon .
```

**Mutation testing**: the arms generated by machine from the diff (`tests/mutate.py --auto`) fire mainly at pytest (human decision 2026-09-27). It first makes a marked copy (a copy of the working tree with a marker inserted at every line to be mutated, used to record which tests pass through each line), runs the script suite and the pytest suite on it in order, and then, for each arm, fires first at the pytest tests that passed through the line (narrowed by node id; for arms whose node id list is too long, by file; for lines that cannot be attributed and lines run at import time, the whole pytest suite), and stops if red. If green, it always also fires the current path — the way arms were fired before pytest was added, with only the scripts that passed through the line (the net does not get narrower than when there were only scripts). Lines that no script passes through and only pytest does are not fired at the scripts; lines that neither passes through are not fired and become NoCoverage (lines without coverage), and their count is output in `summary.uncovered` of `--out` and in `--gate-efficacy` (in a run where the scripts' marked copy is red it says they cannot be counted, and in a run that did not use pytest coverage it notes that coverage was decided by the scripts alone). Which test passed through is distinguished only in the pytest run of the marked copy, by `conftest.py` setting an environment variable (whose name `MUTATE_MARK` in `conftest.py` holds) to the test's node id during each test (it reaches child processes through the environment too. coverage's dynamic context cannot be used with Python 3.14's default core and does not reach child processes, so it is not used). Which script passed through is distinguished by the markers that the scripts' foundation `parallel.py` attaches (the name of the thread running the script, and, only in the marked-copy run, the script name inserted into the workspace name), so a child process is attributed if it is started with the script's workspace as cwd (a child started outside the workspace cannot be attributed, and that arm is fired with the whole script suite). Hand-written arms (`tests/mutate.py` and `tests/mutations.json`) are kept for arms that target mutations that add calls, decorated functions, JSON, Markdown, and shell, and for cross-checking which check caught them. Hand-written arms can also name node ids in this location in `tests`, and arms that do so fire at pytest first (condition 2 of the conditions for deleting scripts in docs/adr/0067 — the optional "hand-written arms" evidence — is read from the reds of this stage that hit a named node id; the source of truth for the rules is the docstring of `tests/mutate.py`). Firing at whole modules that pytest covers, regardless of the diff, is done with off-the-shelf mutmut (fired in the mutmut job of CI's `.github/workflows/mutation.yml`; not fired locally — human policy), configured in `graphloops/setup.cfg` (key names are mutmut 3's, which differ from 2.x's `paths_to_mutate` and so on; run with a pinned version). mutmut creates its working copy in `mutants/` where it is run and carries over the previous "killed" results, so **fire it on a temporary copy of the working tree, fresh every time** (if you create `mutants/` in the working tree, the `tests/run.sh` fences that walk the file system directly also count that copy). It does not work on Windows:

```bash
tmp=$(mktemp -d) && git ls-files -co --exclude-standard | tar -cf - -T - | tar -xf - -C "$tmp"
cd "$tmp/graphloops" && uv run --no-project --with mutmut==3.8.0 --with pytest mutmut run --max-children 4 && uv run --no-project --with mutmut==3.8.0 --with pytest mutmut results
```

Of the survivors that `mutmut results` lists, kill the ones that matter with tests on the pytest side. The steps above explain how to fire it; the one that fires it is CI's `mutation.yml` (Linux and macOS; not fired locally — human policy).

## Calling the rules from an external harness (scripts/gl.py)

An entry point for calling the same rule functions from outside the engine, such as from a node of Archon (an open-source workflow harness that runs YAML graphs of AI and shell steps). It reads a real board (the location `loop.py init` creates), assembles the read view, calls the function, and returns the result (including the write requests `effects`) as 1 line of JSON. **It writes to neither the board nor the working tree** — the only entry point that applies effects and advances the board is `done`, `answer`, and `next` of `loop.py`. Rejections are also returned with exit code 0; it exits 2 only when the arguments, the board, or the graph cannot be read.

```bash
python3 graphloops/scripts/gl.py cond    --dir <board> --name <condition>
python3 graphloops/scripts/gl.py accept  --dir <board> --node <node or instance id> --reply <reply.json> [--item <item.json>]
python3 graphloops/scripts/gl.py request --dir <board> --file <request.json> --reason <source>
python3 graphloops/scripts/gl.py machine --dir <board> --node <machine node>
python3 graphloops/scripts/gl.py exit    --graph <graph.json> --node <node> [--against <external-schema.json>] [--strip-notes]
```

`accept` applies the same chain of checks as done (the engine's `commands.check_reply`: type, empty body, restoring names from numbers, fan-out coverage, tier, per-node consistency, effects, copying into the record, record consistency) on a copy of the board — a reply that done rejects is also rejected by gl. gl does not reject a reply just because the board cannot take it right now; instead `pending` says whether the reply would pass the engine's gate (`commands.accept_gate`, the same gate `done` uses: the run is stopped, the instance is not waiting for a reply, or its dependencies are not done yet) (the working-tree comparison is decided only at done time, so it is not included). Fan-out nodes are pointed at by instance id or with `--item`. Per-node consistency can be called only for functions moved to the new form (new-form functions declare the fields they read and receive a read-only view of just those fields; old-form functions receive the whole board — see step 3 of "Adding a loop") (18 of review-loop's 22 acceptance functions; for machine nodes, `delta_owed`), and old-form functions return `called: false`, `form: legacy` (old-form functions take the board itself and write files next to it, and gl must not write to the board). `request` applies the same rules `add` as `loop.py add` to the copy and returns the list of requests after stacking. `exit` returns a node's exit schema; `--strip-notes` drops the annotation word `note` (the form pasted into an external harness's `output_format`), and `--against` returns the paths that disagree with a copy of the external harness's schema.

## Adding a loop

1. Write `exec: true` and `rules` in `graphs/<loop>.json`, and add `prompt_file`, `schema` (or `text: true`), `reads`, and `writes` to each node. If the rules write keys into the board's loop (`b.loop_state`), write the key names in the rules' `LOOP_KEYS` and the shape in the graph's top-level `state_schema` (a JSON Schema with `type: object` and `additionalProperties: false`; keys whose names change per round use `patternProperties`) — graphcheck aligns the two and checks paths that read loop down to the last field, and the engine checks at save time and records deviations in `state.loop_drift` (it does not stop). Keys that only the rules read and write, and that conditions, node `reads`, and prompt placeholders do not read, get `writeOnly: true`. In a graph that writes a per-key merge mode `x-reducer` (`overwrite`, `append`, `merge_by_key`, `set_once`; source of truth `engine/effects.py`) on the top-level keys of state_schema, the rules do not write loop directly and write only through the effect entry points (`effects` in the return value of new-form functions that take a read view, and the injected `write_loop` for old-form functions that take the board) — graphcheck rejects direct writes in the rules' bodies, and the `loop.py patch` remedy records the skipped merge mode in `bypass` in `state.patches`. Values closed within one block are not put in loop; put them in the writing node's output and read them with `cur.<node>.<field>` (`cur.<node>` is the output that node produced in the current round, as opposed to `out.<node>`, the latest from any round, and `prev.<node>`, the latest from earlier rounds). Of the values that span rounds, those that can be built from history (round records, per-round node outputs) are not copied into loop; write them as functions in the rules' `HIST` that build them at read time (declaring what they read with `hist_reads`), and write the shape in the graph's top-level `hist_schema` — conditions, `reads`, and placeholders read them as `hist.<name>`, and every time the engine saves the board it writes a snapshot `hist.json` (marked as not the source of truth) next to the board. Machine nodes (`run_by: driver`) also write the shape of their return value in `schema` — the engine checks the return value (a deviation stops it), and graphcheck checks the fields that read the output. A copy-only graph (without `exec`) only needs to pass graphcheck's copy-shape checks. If you set up block contracts, split nodes into `blocks/<loop>/<name>/block.json` (`description`, `nodes`, `exit`), move the schemas of nodes that nodes in other blocks read (via `reads`, the condition's `cond_reads`, hist's `hist_reads`, `pointers`, `delegate.result_to`) into `properties.<node>` of `exit.schema.json`, and point the graph node's `schema` there with `$ref` — graphcheck (check 18) checks membership, exits, parallel overrides, and shared cores, and derives and shows the entry points from the reading side (they are not held by hand).
2. Per-node prompts in `prompts/<loop>/`. Keep the "why" of the prose instructions in the preamble (if you cut them down to instructions only, the discipline is kept but the quality of judgment drops).
3. In `rules/<loop>.py`: `init_record`, `FAN_OUT`, `WRITE_OPS`, `BUILTINS`, `POST_CHECKS`, `check_record`, `finalize`, `on_answer`, `on_unattended`, `on_stop`, `on_thickness`, `add` (only what is needed). If acceptance functions (`POST_CHECKS`) and machine nodes (`BUILTINS`) declare the fields they read with `cond_reads`, they are called with a read view (only the declared fields are visible, and values read are copies), and they take the new form: acceptance returns `{ok, reason, note, reply, effects}` (a rejection is also `ok: false`, not an exception), and machine nodes return output and `effects` (the engine's `Board.rule` tells old and new apart. Functions without a declaration are called with the board as before). Ops that write the record (`WRITE_OPS`) are also called with a read view if they declare, and only return the value to write — the destination is the op's `writes_to` (a record path pattern whose `{to}` is filled with the `to` of the graph's writes; graphcheck checks the declaration), and the engine places it there. If you want the human stop entry point (`loop.py stop`) to reach the report, write `stop` at the graph's top level (a machine node regarded as "done" after stopping. It needs a report node downstream — graphcheck checks this).
4. Add scripts to `tests/simulate.py` (most scripts are still there. The pytest-side foundation can import and run the scripts, and the move is progressing stage by stage — what has moved is in `tests/py/MIGRATION.md`. For checks that call functions directly, write them with pytest in `tests/py/` — see "Where pytest tests live" above).
5. `commands/<loop>-graph.md` holds only how to call the engine.

## Adding a version that replaces part of the flow

A version that replaces only some nodes of the same loop with a different flow (for example `graphs/review-loop-tdd.json`, where fixing follows a TDD flow) writes only the difference, without copying the original graph. If you write `"extends": "<original graph file name>"` at the top level, the engine (`load_graph` in `engine/schema.py`) layers it onto the original graph with RFC 7396 (JSON Merge Patch): objects merge key by key, `null` deletes a key, and arrays are replaced.

- The original must be a file in the same location (`graphs/`), because relative paths in inherited nodes' `prompt_file` and `rules` are read relative to that same location.
- You may layer a further replacement version on top of a replacement version (`extends_chain` in `engine/schema.py`). The chain is layered in order from the root, and later stages win. Cycles (including pointing at itself) are rejected, and an error in a middle stage is reported with that stage's file name.
- In a replaced node's `deps` and `reads`, also write the original elements (arrays are replaced). If you drop an original element, graphcheck stops — so that dependencies later added to the original graph do not silently disappear in the replacement version.
- To add paragraphs to the original instructions, write them in the node's `prompt_append` (a list of files appended after the instructions). Do not copy the original instructions.
- To add rules, put them in a separate file that loads the original rules and exports a copy with additions to the tables (`CONDS`, `BUILTINS`, `POST_CHECKS`) (the shape at the top of `rules/review-loop-tdd.py`). Do not touch the original rules.
- Which version to run is chosen with `init --loop <version name>`. Runs on the original graph behave the same whether or not replacement versions exist.
- `$ref`s pointing at block files (`../blocks/…json#/…`) are expanded from each file's location **before** layering (`inline_block_refs` in `engine/schema.py`). So the type of an exit node also merges partially if you write fields in the replacement version's `nodes.<node>.schema`. Fields layered onto an alias in the graph's `$defs` (a definition that points at a block file) reach only users inside the graph, not users inside the block file — to change an exit node's type, layer onto the node's `schema`.
