## 道具と正本の場所

- **スクリプト**: プラグイン同梱。以降 `review-record.py` / `comment-ratio.sh` と書いたものは `${CLAUDE_PLUGIN_ROOT}/scripts/` 配下を指す（実行例は P4 と P-R の R1 に書いてある）。
- **ラウンド記録**: `.claude/review-rounds/round-<N>.json`。**書き方の実例は `${CLAUDE_PLUGIN_ROOT}/templates/round-1.example.json`〜`round-3.example.json`**（3 つ並べて読むと、問いが立って・ループが決めて・人へ回るまでの 3 周の推移が分かる。欄と値の正本は `review-record.py`）。`<N>` は 1 から 1 ずつ増やす**ラウンド番号**（P4 の「1ラウンド = P1→P4 を1周」の定義に一致させろ）。ディレクトリは無ければ作れ（`mkdir -p .claude/review-rounds`）。**前ラウンド分を消すな**——連続 2 ラウンドの突合・defer 台帳・問いの台帳がこれで成立している。**同じリポジトリで次のレビューを始めるときは、前のレビューの記録を消さずに別ディレクトリへ退避しろ**（例: `.claude/review-rounds/archive-<前の BASE>/`。下位ディレクトリは読まれない）。道具はディレクトリの中の `round-<N>.json` を全部読むので、基準点の違う記録が混ざっていると 1 ラウンド目から `exit 2` で止まる。実測: このプラグイン自身のレビューで、8 月の別レビューの記録 5 件が残っていて止まった。
- **レビュー観点の正本**: `${CLAUDE_PLUGIN_ROOT}/REVIEW.md`（言語・フレームワークに依存しない観点）。対象リポジトリのルートに `REVIEW.md` があれば**それも読み、そのチームが事故から足した固有の追加観点として併用しろ**。無くても走る。**観点の写しをこの手順書に持ち込むな**（二重管理は片方が stale 化する）。
- **役割 agent**: subagent はプラグイン同梱の役割定義で起動する。以降 `inspector` / `investigator` / `cold-reader` / `judge` / `blind-judge` と書いたものは `subagent_type: convergence-loops:<役割>` を指す。モデル・effort・持てる道具は `${CLAUDE_PLUGIN_ROOT}/agents/<役割>.md` が正本で、**この手順書にモデル名を書くな**（写しは腐る）。遮断系（`cold-reader` / `blind-judge`）は道具を一切持たないので、読ませたい本文はプロンプトに貼って渡せ。どの役も書く道具（Edit / Write）を持たないが、`investigator` だけは Bash を持つ——起動する `investigator` のプロンプトには一人称の自己禁止（「ファイルの作成・編集・削除を自らに禁じる」）を書け。書き換えを塞ぐのは定義でも自制でもなく、P1 前後の作業ツリー突合（P1「局所」の項）である。
- **固有の規約**: どちらの `REVIEW.md` にも書かせず、対象リポジトリの一次情報（README・lint 設定・パッケージマニフェスト・CI 定義・近傍コード）から毎回把握しろ——手順は `REVIEW.md`「固有規約の把握」のとおり。**固有の技術名を観点側に書き写した時点で、それは複製で、リポジトリが変わっても古いまま残る。** 把握した内容は次ラウンドへ**参照として**引き継いでよいが、**文脈遮断 grader（P1）と R2（P-R）には渡すな**——渡した時点で隔離が壊れ、「このリポジトリではこうなっている」を所与にした追認になる。疑う役の入力は、対象差分と観点本文だけに保て。

## 依存

局所レビューに使う `pr-review-toolkit` は `plugin.json` の `dependencies` で宣言してあり、このプラグインの導入時に実体ごと入る（機構と入手経路の制約は `README.md`「依存と入手経路」が正本）。**導入コマンドを手順として実行するな**——宣言が解決できない環境ではこのプラグイン自体がロードされないので、`/review-loop` が動いている時点で `review-pr` は在る。

`/simplify` と `/security-review` は Claude Code 本体の組み込みなので、導入は要らない。

`review-pr` の呼び出し自体が失敗したら（権限・実行時エラー）そこで止めるな。素材 `local_review` を `awaiting_human` として記録し理由を書いて進め——**無かったことを `not_applicable` にするな。**

## 役割分担（最重要）

このループを回す session が **writer（実装者）**。**writer は局所レビューを機械的に実行して findings を集めることはできるが、ラベル確定・根本診断・収束判定はしない。** それらは全て別 context の **grader subagent** が行う（writer ≠ grader）。writer は grader が確定した `[block]` を直すだけで、ラベルを自分で上げ下げできない。grader の判定を覆したい時も自分で決めず、別 context の grader に再判定させろ。

**grader を都合よく使うな**: 同一ラウンドで grader を回し直して有利な結果を採るな（やり直しは次ラウンドのみ）。grader subagent の生出力（根本ユニットのキー集合・各 verdict）は最終報告にそのまま転記しろ。

レビュー観点とラベルの正本は `REVIEW.md`（上の「道具と正本の場所」で定義した 2 つ。以降 `REVIEW.md` と書いたものはその併用を指す）。grader はレビュー開始前に `REVIEW.md` を読むこと。ただし道具を持たない隔離 grader（文脈遮断）は自分では読めないため、writer が該当セクションの本文をプロンプトに貼って渡せ。

武器の使い分け: **局所レビューは公式 skill に委譲**し再実装するな。ただし**欠陥と品質は別の道具**で、片方はもう片方を代替しない——欠陥（correctness）は `pr-review-toolkit:review-pr`、品質（reuse / 簡素化 / 効率 / altitude）は `/simplify` が担当する（`/simplify` は「バグは探さない」と自ら明記している）。**両方走らせろ**——「簡素化」は `review-pr` の観点にも含まれるが、観点が重なることは片方を省く理由にならない。根本診断・整合性・俯瞰は grader subagent で行う（公式に相当機能がない）。

## P0: 基準点と「元の目的」の固定（writer）

1. **基準点を固定**——次の順で決めろ。

   1. 作業ツリーに未コミット変更があれば `BASE=$(git rev-parse HEAD)`。
   2. クリーンなら**上流との分岐点** `BASE=$(git merge-base <既定ブランチ> HEAD)`（`<既定ブランチ>` は `origin/main` 等。`git symbolic-ref refs/remotes/origin/HEAD` で引ける）。**`HEAD~1` を既定にするな**——複数コミットのブランチで直前コミットだけを見ると、レビュー範囲が対象の数 % に縮む。実測: 6 コミット・9 ファイル・+416 行のブランチで `HEAD~1` を採ると 1 ファイル・+6 行（全体の 1.5%）になり、その状態で `[block]` 0 件・CI 緑が揃えば**見ていない範囲について収束を宣言できてしまう**。
   3. 分岐点が取れない（上流が無い・既定ブランチが不明・分岐点が HEAD と同じ）なら `BASE=$(git rev-parse HEAD~1)` に落とせ。

   `HEAD` がマージコミットなら対象範囲をユーザーに確認しろ。未追跡の新規ファイルは `git add -N` で差分に載せろ（P3 で新規作成した場合も同様）。**以降の全工程で「対象差分」＝ `git diff <BASEのSHA>`**——後続ラウンドでも基準点を動かすな（`git diff HEAD` は P3 の修正のコミット状況次第で元の変更が差分から消えるため、ラウンド2以降の使用を禁ずる）。

   **結果は素材 `base_determination` に書け**——`SHA` と、上の 1〜3 のどれで決めたか、対象差分が何コミット分かを含めろ。SHA だけでは範囲が縮んでいることが読み手から見えない。決められない（上流も直前コミットも取れない）なら `awaiting_human` だ。
2. CI のテスト・lint をローカル実行し緑を確認。赤ならレビューより先に直す。**結果は素材 `local_checks` に書け**（欄と取りうる値は `review-record.py` が正本）。**実行できなかった場合（権限・CI 専用ジョブ・実機や外部サービスが要る・依存が未導入）は緑を仮定して進むな**——何を走らせようとして何に阻まれたかを理由に書いて `awaiting_human` とし、P4 の突合に載せろ。飛ばしたなら `not_run` だ。**「たぶん緑だろう」で P1 に入る経路を自分に許すな**——これはこのループが塞いだ穴（無言の省略を「なし」と誤認する）と同じ形で、最も上流で起きる。緑を確認できたなら `clean` で、`checked` に何を走らせたかを書け。
3. **前提を実測しろ（目的テキストより先に）**——目的と制約に書く数値・規模・件数・「〜が来うる」の類は、**この作業ツリーで測った値か、ファイルを名指しできる事実**でなければ書くな。記憶・以前の測定・一般論を制約として渡すと、R2 はそれを所与として理想解を導くので、**前提が誤っていても pass が返る**（R2 は実装もリポジトリも遮断されているので、制約の真偽は原理的に検査できない）。実例: 「本文は最大 4MB 級」を制約に書いて R2 が pass を出したが、その 4MB は**同じ PR が削除した経路**の実測値で、実際に運んでいたのは 5,411 バイトだった。5 ラウンド分の作り込みがその上に乗った。各制約に「どう測ったか」を 1 行添えろ。添えられないものは制約でなく仮説として渡せ。
4. **「元の目的」をテキスト化**——P-R2 のゼロベース再導出に渡す唯一の入力になる。出典の優先順位: ①PR 説明 ②`current-plan.md` やタスク記述（いずれも実装と独立なので望ましい）③それも無ければ writer が要約を書く（**最終手段**）。③を使う場合、その目的テキストを**別 context の `inspector` にレビューさせ**（実装に都合よく狭めていないか）、合格分だけ R2 へ渡す。目的テキストは**最初の修正に着手する前に確定し、以降変更しない**。最終報告に出典（①②③）を明記し、③のときは独立性が弱い旨も記せ。どの出典も得られない場合は「目的不明」とし、R2 を `unverifiable` として扱う。
5. **並行 PR 衝突チェック**——次の 6 段を順に踏め。段を飛ばすな。

   1. **対象リポジトリを解決する**: **`git remote get-url <upstream の remote>` から `owner/repo` を導け**（upstream は `git rev-parse --abbrev-ref @{u}` で引く。無ければ `origin`）。以降の `gh` 呼び出しには全て `-R <owner/repo>` を渡せ（機構と危険性は `docs/customize.md`「fork 運用・複数アカウント」を読め）。**`gh repo view` の値をこの確認に使うな**——あれは cwd の remote から解決するので `git remote -v` と突き合わせても原理的にほぼ必ず一致し、検査が恒真になる。remote が引けない・URL から `owner/repo` を導けないなら、以降を「確認できなかった」として扱え。**取り違えた一覧で「衝突なし」と書くな。**
   2. **自分の PR を特定して除外する**: `gh pr list -R <owner/repo> --limit 100 --json number,headRefName,headRefOid` で列挙し、**`git rev-parse HEAD` と `headRefOid` が一致する PR を先に外せ**。自分の PR は変更ファイル集合と必ず 100% 交差するので、外さないと下の 6 段目で**レビュー対象そのものを「担当 PR がある」としてスコープ外にする**（自己言及的な誤判定。実際に起きた）。**ブランチ名で照合するな**——detached HEAD では `git branch --show-current` が空文字を返し（終了コードは 0）、どの `headRefName` とも一致せず自 PR が生き残る。
   3. **列挙が打ち切られていないか確かめる**: 上の列挙は**既定では 30 件で黙って打ち切られる**（`--limit 100` を渡すのはこのため）。返った件数が `--limit` の値と同じなら**打ち切られた可能性がある**——その場合は素材 `parallel_pr` を `awaiting_human` にしろ。**打ち切られた一覧で「衝突なし」と書くな**（この段が禁じているのは、まさにこの形の未確認だ）。
   4. **変更ファイル集合を得る**: `git diff --name-only <BASE>`（対象差分）。
   5. **残った PR の変更ファイルを引く**: `gh pr view <n> -R <owner/repo> --json files --jq '.files[].path'`（列挙だけでは各 PR の変更ファイルが返らないため PR ごとに引く）。変更ファイル集合と交差するものが「同一ファイルを触る並行 PR」。
   6. **交差した箇所を担当 PR に渡す**: 該当 hunk を `gh pr diff <n> -R <owner/repo>` で context に載せ、以降の全 finding を「このギャップは別 PR が既に対応中でないか／自分の修正が、未マージの別 PR が進めている書き換えと同じ関数・領域で衝突しないか」で再評価しろ。衝突・重複が判明した箇所は**その箇所の変更を主導している PR（担当 PR）に渡して本ループのスコープから外せ**（同じ箇所を両 PR で書き換えても merge 衝突を生むだけ・修正は別 Issue でなく担当 PR へコメントで申し送る）。

   **結果は素材 `parallel_pr` に書け**（洗い出した並行 PR と、担当 PR へ申し送った箇所）。GitHub 以外のホストでは同等コマンドに読み替えろ——読み替えられず列挙できないなら `awaiting_human` として理由を書け。**未確認を「衝突なし」（`clean`）と書くな。**
6. **先行議論の突合**——対象差分が触れる領域の決定記録（ADR・意図的保留の台帳・issue / PR の棄却済み一覧・closed issue）を洗い、**決着済みの論点のリスト（決定・理由・再訪条件）**を作れ。差分が触れる領域から先に読ませろ（順序の助言であって、見るなの線ではない。上の規律のとおり、見た範囲と見ていない範囲を返させろ）。検索作業なので `investigator` に切り出してよい。リストは P2 へ渡して各処方・各文書変更と突合させる。**突合は壁でなくルーターである**——①記録された理由がまだ束縛する → 当該の指摘・処方を落とす ②新証拠が理由に答える → 「再開の提案」として明示的に扱う（理由に答えないまま、こっそり「未決」として書き直すな。提案の受理は決定の持ち主＝人の仕事で、ループが自動で覆すな）③理由・再訪条件が記録されていない → 台帳側の欠陥として surface する（書かれていない理由への恭順は要求できない）。**①で落とせるのは、理由が現在も成立していると確かめたときだけ**——「決着済み」という地位を理由に落とすな（結論への恭順は、誤った決定を永久化する。当たるのは常に理由であって地位ではない）。指摘側の実測が記録された理由と食い違うなら、それは①でなく②の新証拠である。**結果は素材 `prior_decisions` に書け。** 洗えなかったら `awaiting_human` として理由を書け——**未確認を「決着済みなし」（`clean`）と書くな**。決定記録に変更が無いラウンドは前ラウンドの結果を持ち越してよい（ループ自身が issue・台帳を書き足したラウンドは引き直せ）。**このリストを文脈遮断 grader と R2 に渡すな**——棄却の履歴を知った独立設計は追認になる（「固有規約の把握」の隔離規則と同じ）。実例: 棄却済み一覧（issue 本文）を洗わずに書いた文書変更が、棄却理由が予言した被害（引用実装例の破壊）をそのまま実現させた。

## P1: 採点用の素材集め（ラベルはまだ付けない）

ラベル付けは P2（grader）で行う。ここでは生の指摘を集めるだけ。grader subagent 群は互いに入力が独立なので、単一メッセージで並行起動しろ。

**素材の返答はラウンド記録（JSON）に書け。** 欄と取りうる値は `review-record.py` が正本で、手順書は列挙を持たない。要点は 2 つ——**「条件に当たらないのでやらなかった（not_applicable）」と「やるべきだったが飛ばした（not_run）」を別の値で書くこと**（散文ではこの 2 つが区別できず、後者が前者に化けるのが元の穴だった）、そして**前ラウンドの判定を流用した素材は `carried_over` と実際に見たラウンドを書くこと**（`clean` と分ける理由は `review-record.py` の当該定義に書いてある）。埋め忘れは検証エラーで落ちるので、各素材の節で「明示的に返せ」と繰り返さない。

**対象差分は「どこから見るか」の起点であって、「どこまで見るか」の線ではない。** 人がレビューするときは全体を見て考える——**差分以外を精読した目で見ると、指摘の場所そのものが変わる**（依頼者の逐語:「差分にしか触れないのはダメ。差分以外も全部精読してから見たコードでは指摘ポイントがかわるかもしれないでしょ」）。**リポジトリを読める役に、差分だけを貼って済ませるな**——入口を渡し、理解に要る限り依存先・近傍・呼び元まで読ませろ。道具を持たない遮断系（`cold-reader` / `blind-judge`）にだけは本文を貼るしかないが、**それは隔離のためであって、視野を狭めてよいという意味ではない**。

**探す役に「ここは見るな」の線を writer が引くな。** 削るのは P2 の仕事である——束ねる・出自を辿る・ラベルを落とす、という手続きは全部あちらに在る。集める側で範囲を切ると、切った外は**判定役の目に一度も入らない**。浅いセンサーは見た範囲で間違えるだけだが、視野を切られたセンサーはその外を一度も見ない。**「ここは見なくてよい」は採点の判断**で、実装を負う側がそれをやると「writer はラベルを決めない」が破れる。実測: 「対象は差分が import している依存に限れ」と書いていたため、**このプラグインが自分で依存として宣言していた役**（自作した機能とほぼ同じもの）が集合の外に落ち、3 ラウンド続けて「定番解の再発明は該当なし」が返ってきた。

代わりに 2 つを課せ。①**読む順の助言はしてよい**（差分が直接使うものから先に、等）——早く見つけるための順序であって、見るなの線ではない ②**見た範囲と、見ていない範囲を返させろ**。量や時間で打ち切ったなら、打ち切った線を書かせろ。そうしないと「見て無かった」と「見ていない」が同じ「該当なし」に化ける——**無言の省略を「なし」と誤認する**のは、このループが最初に塞いだ穴と同じ形である。返ってきた範囲は素材の `checked` / `detail` にそのまま写せ。

**検証手段を持つ役への提出基準**: 局所レビューの各 skill を呼ぶプロンプトと、リポジトリを読める grader（整合性＋迂回・外部標準照合・手順トレース）のプロンプトには、`REVIEW.md`「指摘の提出基準」を課せ——**REVIEW.md に書くだけでは局所レビューの skill には届かない**（それらは REVIEW.md を読まない自前の指示で動く）ので、writer が呼び出し時のプロンプトに本文を貼るか要点（機構・実測・提出前の自己反証・誤検出見積もり）を明記しろ。文脈遮断 grader は対象外（同基準の除外規定のとおり——センサーの浅さは仕事である）。

- **局所（writer が main session で実行）**: 欠陥は `pr-review-toolkit:review-pr`、品質は `/simplify`、認証・データ取扱い・外部 I/O に触れるなら `/security-review` も実行し、findings のみ取得しろ。**findings を機械的に集めるだけで、採点・ラベル確定はするな。** **`/simplify` は既定で修正まで行う skill なので、P1 では指摘だけ返す形で呼べ**——4 観点（再利用・単純化・効率・高度）を、修正を禁じたプロンプトでそれぞれ起こす。当てるのは P3 で、P2 が根本ユニットに束ねたあとである（P1 で当てると、採点前の木が動いて下の作業ツリー突合が成立しない）。実測: 2 つのセッションが独立にこの代用に行き着き、どちらも逸脱として記録していた——**手順書の側が現実に合っていなかった**。
 - **`silent-failure-hunter` と `type-design-analyzer` は名指しで起こせ。** `review-pr` の振り分けは散文の条件（「エラー処理が変わったなら」「型を足した / 変えたなら」）で、**try/except も型定義も触らない差分では起きない**。ところがこの 2 レンズが当たるクラス——黙って無力化される検査・恒真になった柵（前者）、不変条件を平坦な値で持つ設計（後者）——は、差分の形に関係なく出る。実測: このループ自身のレビューで 3 周続けて型設計のレンズが 1 度も起動されず、3 周目に外部の目が「平坦な文字列空間」として同じ欠陥を挙げた。**宣言済みの依存が既に手元に在るのに使っていない**形である。
 - `review-pr` は 6 観点（欠陥・コメント・テスト・エラー処理・型設計・簡素化）を持ち、findings を返すだけで PR へのコメント投稿もコードの修正もしない。簡素化観点も同じく指摘止まりで、修正まで行う `/simplify`（下の作業ツリー確認を参照）の代わりにはならない。
 - **findings を受け取れなかった素材は、記録に `awaiting_human` と書いて P2 へ進むな。**欠落したまま P2 が「局所 findings なし」と読むと、無いことが合格に化ける（`not_run` との区別は `review-record.py` が正本）。
 - **P1 の局所レビュー全体の前後で `git status --short` と `git stash list` と `git diff --shortstat <BASE>` を取り、作業ツリーが変わっていないことを確認しろ。** 変わっていたら戻せ（P0 で固定した BASE 起点の差分追跡が崩れる）。**確認の対象を道具名で列挙するな**——`/simplify` は既定で修正まで行う skill なので最も疑わしいが、実際には**指摘だけを返すはずの grader が検証のためにファイルを書き換えて戻し忘れた**ことがある（型ガードを削って緑になることを実証した跡）。どの道具が汚したかを当てるのでなく、P1 を抜ける時点の作業ツリーを機械で突き合わせろ。
 - 直前ラウンドから対象差分にロジック変更が無いラウンドは `/simplify` の再実行を持ち越してよい。

- **整合性 ＋ 標準機構の迂回（grader subagent・findings 非共有の独立フレーム）**: `inspector` を起動し、`REVIEW.md` の「整合性観点」に従ってリポジトリ横断の整合性を確認させろ——「標準機構の迂回」の中身・捕捉条件も正本のとおりで、ここに写しは持たない。迂回の検査は整合性確認とは**必ず独立に**実行させ、プロンプトに「お前は他の指摘を受け取っていない」と明記しろ。**この grader には P1 局所の findings を渡すな**——入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` だけにしろ。findings を共有すると全 grader がそのフレームにアンカーされ、近傍が迂回している機構に気づかなくなる（隔離フレームなら気づく——実証済みの捕捉条件）。この出力は整合性 findings とは**別系統の素材**として P2 へ渡せ。

- **文脈遮断（grader subagent・タスク文脈そのものを遮断）**: `cold-reader` を起動し、**「元の目的」も機能名もタスクの説明も一切渡さず、対象差分の本文と `REVIEW.md` の「コード衛生観点」のセクション本文（writer がプロンプトに貼って渡せ。観点の中身と遮断の理由は貼る本文＝正本のとおりで、ここに写しは持たない）だけ**を入力にしろ。上の整合性＋迂回 grader が「タスク文脈は共有しつつ findings を非共有」なのに対し、これは「diff が何の機能かを知らせない」点が新しい——整合性側がリポジトリ近傍から「このコードベースの標準機構」の逸脱を拾うのに対し、こちらは近傍を見ずに「言語 / フレームワーク一般の衛生」の逸脱を拾う（入力が違うため拾う層が違う）。プロンプトには **「お前はこの diff が何の機能かを知らされていない——『この用途なら妥当』という正当化はするな」** を課せ。`cold-reader` は道具を持たないので、渡された diff 本文と貼られた観点本文だけで判断する——近傍コードを読めると「このコードベースの標準機構」を学習して整合性 grader と同じ層に堕ち、隔離が崩れる。この出力も整合性・迂回素材と同様、**別系統の素材**として P2 へ渡せ。**貼り切れない差分は、この役に道具を渡して解決するな——貼る側を割れ**（ファイル単位・節単位で複数回起動し、出力を 1 つの素材にまとめる）。道具を渡して「この入口以外を開くな」と言い渡す形は、隔離が指示だけになる（**道具は path で縛れない**——この手順書が他所で書いているとおり）。割れば遮断は保ったまま通る。実測: 24 万字の差分を 3 分割して回した。**割ったことと、割り方は素材に書け**（読んだ範囲が変わる）。

- **外部標準照合（grader subagent・web で外部一次情報を当たる）**: `investigator` を起動し、`REVIEW.md` の「外部標準照合観点」に従わせろ——観点の中身（問題クラスの抽出・一次情報での裏取り・粒度・「定番解なし」も正当な結論・受容済み弱点の再照合）は正本のとおりで、ここに写しは持たない。入力は対象差分の本文と変更ファイル一覧と「元の目的」テキストと `REVIEW.md`、および PR 説明・README・残件メモ等で「自覚済み・受容済み」と明記された弱点のリスト（writer が抽出して渡せ。無ければ「なし」と明示しろ）で、**P1 局所の findings は渡すな**（findings に当たると問題クラスの抽出がそこへ寄り、近傍にしか目が行かなくなる）。この grader だけはリポジトリの外（web・公式ドキュメント・当該 OSS の issue / PR・ソース）を当たり、「エコシステムの定番解」からの逸脱を見る。**あわせて手元の依存も見ろ**——`REVIEW.md`「外部標準照合観点」の「手元の依存の使い残し」のとおり（内容は正本のとおりで、ここに写しは持たない）。**差分が import している依存から先に読ませろ**——差分から機械的に導ける集合なので着手が速い。**そこで打ち切らせるな**: このリポジトリが依存として宣言しているもの（言語のパッケージに限らず、プラグイン・ツールの宣言を含む）は、import されていなくても「既に手元に在るのに使っていない」の当たりどころである。読み切れなければ、どこまで見てどこを見ていないかを返させろ。依存の宣言ファイルに変更が無いラウンドは前ラウンドの判定を持ち越せ。この出力も整合性・衛生素材と同様、**別系統の素材**として P2 へ渡せ。**この grader は P4 が毎ラウンド P1 をやり直すため毎ラウンド走るが、web の引き直しは「アプローチ」をキーにせよ——初回ラウンドと、機構を足す / 変えたラウンドだけ引き直し、体裁だけのラウンド（テスト追加・リネーム・コメント）は前ラウンドの判定を持ち越せ。ただし確証に要る一次情報は必要な分すべて取れ（コスト削減を理由に取得を打ち切るな——削ってよいのは冗長・二次情報の重複 fetch だけ）。迷ったら引き直せ（頻度より精度を優先）。**

- **手順トレース（grader subagent・該当 PR のみ）**: 対象差分に実行手順の文書（README 等）・スクリプト・CI 定義が含まれる場合に起動しろ。`investigator` を起動し（この観点は読解でなく実行で確かめる——`REVIEW.md`「検証の原理」の「読むより動かす」——ので、コマンドを叩ける役）、入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` の「手順トレース観点」で、**P1 局所の findings は渡すな**。変更された手順書・スクリプトの全文を Read させた上で「手順トレース観点」（初期状態からの逐次実行・暗黙の環境状態・誤爆半径）に従わせろ——観点の中身は正本のとおりで、ここに写しは持たない。状態を変える実行はこの役が自らに禁じているので、実機で確かめられなかった箇所は「未実測」と明記して仮説として返させろ。この出力も別系統の素材として P2 へ渡せ。手順書・スクリプト・CI に変更が無いラウンドは前ラウンドの判定を持ち越してよい。

- **ゲートの実効性確認（writer が実行・該当 PR のみ）**: 対象差分が検証ゲート（CI ジョブ・assert・テスト・pre-commit）を新設・変更しているなら、そのゲートが検知すべき違反を、**条件の腕ごとに 1 つずつ**作って赤くなることを確認し、確認後に戻せ。**検査をまるごと外して赤いことは、腕が守られている証拠にならない**——実測: 人に聞く印を修正必須のユニットに付ける禁止（設計が最も強く禁じた形）は、検査全体を外せば赤くなるのに、`label` が修正必須である腕には 1 度も当たっていなかった（ローカルで再現できるステップは手元で実行しろ）。**壊していない写しでも 1 本走らせて緑を確認しろ**——仕掛け自体が壊れていると全部の腕が同じ色に出て、**逆の結論を書ける**（実測: 置換前の文字列が合わずに 1 腕が黙って飛び、別の実行者は全腕が「塞げていない」と出て危うくそう報告しかけた。古い測定結果がディスクに残っていて正常な入力が赤になった例もある）。これは**検査が空振りしても合格に見える形**で、この確認がまさに塞ごうとしているものと同じである。結果（赤を確認できた／できなかった／未確認とその理由。対照の緑も）を、P2 への素材に含めろ。**赤を一度も確認できていないゲートを「検証済み」と扱うな**——検査は、検査自体が失敗・空振りしたとき合格扱いにならないこと（fail-closed）まで含めて初めて機能する。赤の確認は当該ゲートを変更したラウンドだけやり直せばよい。**本物の作業ツリーを壊すな——腕ごとにリポジトリの写しを作り、写しの上で壊して検査一式を走らせろ**（`.git` は要らない。検査が自分の位置から根を決める作りなら写しでそのまま走る）。「並行して読んでいる役が返るまで待て」という順序の約束で塞ぐな——**守ったかを確かめる手段が無く、上の「局所」が置いた作業ツリー突合は前後 2 点の比較なので、壊して戻すサイクルを原理的に検出できない**（端点は必ず一致する）。実測: 共有の木を壊して戻す形で回したとき、3 つの役がこれを「別セッションの書き換え」として観測し、1 つは構文の壊れた写しを踏んだ。写しなら順序への依存自体が消え、腕を並行して回せる（実測: 34 腕を 6 並列で 3 分）。

- **代役の忠実性（writer が実行）**: 対象差分が**外部との継ぎ目**（別プロセス・別サービス・ブラウザ・外部 API・プロトコル）に触れるなら、**テストの代役（モック・スタブ・フェイク）の形が実物と一致するか**を、実物から取った値1件で確認しろ。代役は本物の再現度でなく「実装の誤りが観測できるか」で線を引くが、**入力の形が実物と違う代役は誤りを観測できない**——代役にだけ通る形でテストが緑になる。不一致の箇所は素材として P2 へ渡せ。

- **主経路の実行観測（writer が実行）**: 対象差分が利用者から見える経路・外部との継ぎ目を変えているなら、その経路を **実際に1回動かし、通った値を観測しろ**。観測の対象は「テストが緑になること」ではなく **本番と同じ経路を流れた実物**である。**動かしていない経路を「検証済み」と扱うな**——P1 の他の観点は全て差分を読む役で、実行して初めて現れる欠陥（実行環境固有の挙動・中間層による値の加工・描画）はどれだけラウンドを重ねても現れない。観測は経路を変えたラウンドだけやり直せばよい。

- **根拠の出所検査（writer が実行）**: 対象差分の本文・PR 説明・docstring から「正本は X」「規約は X」「合意済み」等の**事実の主張**を抽出し、その X が対象差分の内側に無いかを確認しろ（`git log -S` 等で BASE 時点の実在を見る）。**差分が自ら足したものを根拠として引用しているなら循環**で、素材として P2 へ渡せ。外部（他チーム・他システム・取り込み元）との合意を主張する箇所は、BASE に痕跡が無ければ **「未確認の前提」**として扱え——循環した根拠は、次に読む人が「確認済み」と受け取るため、未確認のまま設計判断の土台になる。

## P2: 診断（grader・必須の中間関門）

`judge` を起動し（ラベル確定と disposition は writer が覆せない拘束判断のため上位の役）、[P1 の生 findings ＋ **P1 の整合性＋迂回 grader が返した「標準機構の迂回」の素材 ＋ 文脈遮断 grader が返した「衛生違反」の素材 ＋ 外部標準照合 grader が返した「外部標準の再発明」の素材 ＋ 手順トレース grader が返した「手順不成立・誤爆リスク」の素材 ＋ ゲート実効性確認・代役の忠実性確認の結果 ＋ 主経路の実行観測の結果 ＋ 根拠の出所検査の結果（**以下この一覧を「P1 素材」と呼ぶ**。いずれも findings とは別系統の独立入力として明示的に分けて渡せ）** ＋ P0-6 の決着済み論点リスト（素材 `prior_decisions`） ＋ **P0-4 の凍結した「元の目的」テキスト** ＋ 対象差分 ＋ `REVIEW.md`] を入力に、**まず今ラウンドの材料だけで 1〜7 を確定させ**、そのあとで **履歴**（`review-record.py` に記録ディレクトリを渡して出る全ラウンドの推移。2 ラウンド目以降のみ）を渡して 8 をやらせろ。**履歴を先に渡すな**——前ラウンドの判定を知った目は同じ結論に寄る（追認）。履歴の用途は横断でしか見えない傾向（同じ指摘の再燃・直したはずの再出現・要対応の件数と scalar の推移・露呈の回収が増え続けているか）を見ることで、**履歴を読んでラベルを下げることを禁ずる**（下げてよいのは台帳の defer 理由が今も成立する場合の維持だけ）。**生 findings をそのままラベル付けせず、まず根本原因に変換**させろ。**隔離フレームからの素材（迂回・衛生違反・外部標準の再発明・手順不成立・誤爆リスク・ゲートの fail-open）は findings と同列に並べず「隔離フレームからの観察」として扱い、クラスタリングで他 findings に吸収させて薄めるな**——i18n のような標準機構の迂回や、後始末漏れ・公式機構の自作迂回といった衛生違反、エコシステムの定番解の再発明 / 劣化変種使用、検証ゲートの fail-open、手順の不成立・誤爆リスクは、単独で1つの根本ユニット（`[block]` 候補）になりうる:

**下の 1〜6 は木探索で行え——満足いくまで枝を深め、最後に枝同士を並べて見ろ。** 小さい処方（8 の (a)〜(d) だけで横断を言う）を採らないのは、**横断が要るのは問いの再審だけでなく指摘の診断そのもの**だからである——単独では妥当に見えた指摘が、並べると大きい根の症状だったり別の木の実測で反証されたりする。その判定を 8 に置くと、5 でラベルが確定した後になる。 各 finding を根とする木を、①反証（どんな条件で誤検出になるか。近傍の実態・規則の条件節まで読んで殺しにいき、殺せたら落とす。これは番号の外で、各段に先立って毎回やる）②出自（手順 2）③上方展開（手順 3。ここだけ段数の上限が別に 3 段）④処方の候補（手順 6）、の枝で深め、枝が死ぬか底を打つまで止めるな。**全部の木を作ってから、枝同士を並べて見ろ**——木 1 本の中では見えないものがそこに在る: 同じ根から出た木は束ねる（1）／複数の木の上位で交わる原因は、どの木にも書かれていない根本対策の候補（4 の一撃）／ある木で集めた実測が別の木の指摘を反証しないか／ある木で立った問いを別の木に当てると指摘の場所が変わらないか（別の視点）。**妥当かの判定は、この横断のあとに下せ。**

**素材は観点名でなく欄名で並べて渡せ。** 素材の正本は `review-record.py` の `MATERIALS`（欄名の列挙）だが、P1 の素材は観点の名前（整合性・手順トレース・衛生…）で集まる。**両者を突き合わせる導線がどこにも無いと、丸ごと起動しなかった素材が judge から見えない**——欠落が見えるのは P4 の機械（`素材 '…' の返答が無い` で `exit 2`）まで下り、そこで初めて 1 周ぶんの診断が欠測だったと分かる。渡すときに欄名で並べ、起動しなかったものは「起動しなかった」と明示しろ。下の 2 が「明示返答を欠いていたら P2 を止めろ」と要求できるのは、止める材料が judge に渡っているときだけである。実測: このループ自身のレビューで、15 欄のうち 2 欄（衛生・外部標準照合）が丸ごと起動されず、judge は 48 項目の素材を「全部」として 1〜7 を確定させた。

**目的テキストを渡すのを忘れるな。** この工程は「`split` が目的の内側でないか」「`fork` の零処方が目的と衝突して落ちるか」「`resolved` にしてよいか」を判定するが、**どれも目的テキスト無しには決められない**。渡す先の区別は P1 と同じで、隔離が要るのは P1 の遮断 grader と R2 だけである（P2 の judge は履歴も台帳も渡る上位の役）。実測: 目的テキストを渡さずに回した 2 周で、設計の岐路 1 件が「決まる材料が無い」として `held` のまま空転し、3 周目に同じ judge へ目的テキストを渡した瞬間に `resolved` になった——**2 周ぶんの空転が、入力一覧の 1 項の欠落だけで起きた。**

1. **クラスタリング**: findings を「なぜ生まれたか（出自）」で根本原因にまとめろ。「この5件は1つの命名の死が出自」「この3件は同じ抽象の不在」のように束ねる。
2. **出自分析（順序固定・飛ばすな）**: 各 finding について ①ロジックの正否 → ②（正しくても）出自が読みにくさ・命名・導線の死か、**またはコードベースの標準機構（i18n・エラー分類・共有ユーティリティ等）の手書き迂回・外部エコシステムの定番解の再発明 / 劣化変種使用・衛生違反（後始末漏れ・公式機構の自作迂回・外部 I/O の無防備・検証機構の fail-open）・手順の不成立 / 誤爆リスクか・**実行観測でのみ現れた欠陥**（実行環境固有の挙動・中間層による値の加工・描画）か・**根拠の循環**（差分が自ら足したものを正本として引用）か** → ③ラベル、の順で必ず記録しろ。出自が「習熟した開発者の誤読・導線の死」**または「標準機構の迂回・衛生違反・外部標準の再発明」**なら、それは「好み（`[nit]`）」ではない（迂回は翻訳漏れ・規約逸脱・二重実装の保守負債、後始末漏れは状態汚染・テスト間干渉、再発明は枯れた解の劣化変種を抱え込む保守負債、fail-open は検知すべき違反の素通り、手順不成立・誤爆は初見の実行者の事故という具体的実害を生むため `[block]` 候補）。**P1 素材は 1 つ残らずこのステップで突合し**、列挙されていた項目が診断で `[nit]` に落ちる・取りこぼされることがないようにしろ。**P1 素材のいずれかが明示返答（有無・または「対象外」）を欠いている場合は、ここで P2 を止め、当該 grader を再起動して明示返答を得てから突合に入れ**（無言のスキップを「なし」と誤認すると元の見逃しが構造完備の見た目で再発する。「条件に当たらず起動しなかった」も、その旨の明示返答が要る）。
3. **上方展開（なぜなぜ）**: 各 `[block]`・do-now 候補の根本ユニットに「**なぜこの欠陥が存在しえたか**」を最大 3 段まで遡って添えろ（3 段で打ち切るのは「文化が悪い」への着地を防ぐため。doctor-loop の根本の木と同じ上限）。遡った先がより上の根本を指すなら、そちらへ束ね直せ。**P0-6 の決着済み論点リストとの突合もここで行え**——各ユニットの処方・文書変更が決着済みの決定に触れるなら、ルーター（P0-6 の①②③）で振り分け、理由に答えない再提案を処方に残すな。
4. **一撃の選定**: 上の横断（複数の木の上位で交わる原因）で出た候補を「直すと最も多くの finding が連鎖的に消えるもの」で順位づけし、長期的に最もレバレッジの高い一撃を1つ挙げろ。

 **出自が「導線の死」のユニットには、`REVIEW.md`「導線を作る手段の優先順位」を付けて渡せ**（内容は正本のとおりで、ここに写しは持たない）。導線の死は毎ラウンド `[block]` 候補として出るのに対し、注記はその場で書けて赤にもならないため、優先順位を渡さないと注記が既定の修正手段になり、ラウンドを重ねるほど注記だけが積み上がる。
5. **ラベル付与と disposition**: 各**根本ユニット**に `REVIEW.md` のラベルを付けろ（`[block]`＝修正必須）。**生 finding 単独を `[block]` にするな**——根本ユニットに束ねるか、束ねられないものは `[suggest]` 以下に落とせ。さらに **`[suggest]`**（`[nit]` は対象外）の各ユニットに **`do-now` / `defer` の disposition** を付けろ——**実体基準は `REVIEW.md`「対応の判断」を正本とし、ここに再掲せず参照する**（既定 `do-now`／`defer` は構造的理由のみ／コスト感は理由にならない）。この disposition は実装を負う writer でなく **お前（grader）が下す**。
6. **処方の列挙（零処方から）**: `[block]`・do-now の各ユニットに処方の候補を並べろ——**実体基準は `REVIEW.md`「処方の最小性」を正本とし、ここに再掲しない**。大きい処方を指定するなら小さい方が落ちる理由を一文で書け。**機構の新設・共有面の拡大に及ぶ処方は処方として確定するな**——「設計の岐路」として記録の**問いの台帳**（`questions`。欄と値は `review-record.py` が正本）に `fork` で載せ、選択肢ごとに帰結を書け（欠陥の等級 `[block]` はそのまま維持してよい。確定できないのは処方の側である）。零処方（取り下げ・既存の機構 1 つ）が候補から落ちる理由を一文添えろ——添えられないなら岐路ではなく、零処方で解く。**欠陥の記述（安定キー）に修正場所を埋め込むな**——キーが場所を名指しした瞬間、処方の列挙が最初からその場所に錨を下ろす。キーは症状の形（誰の何が壊れるか）で書け。
7. **安定キー**: 各 `[block]` および `[suggest]` 根本ユニットに「ファイルパス＋シンボル名（関数 / 型 / 設定キー）＋一文要約」のキーを付けろ（ラウンド間の突合と defer 台帳に使う。**突合は文字列の完全一致**なので、渡された台帳に同じ欠陥が在るならそのキー文字列をそのまま使え——言い換えると別の欠陥として数えられ、台帳も stuck の検知も効かない）。ここでのファイルパスは**欠陥が観測される場所**であって、修正すべき場所の指定ではない（上の 6 の錨の禁止と両立させろ）。

8. **履歴との突合（2 ラウンド目以降。1〜7 の確定後に履歴を渡す）**: 履歴は全ラウンドの記録の推移で、機械は解釈しない。judge がやるのは次の 5 つ。
   - **台帳のルーター**（P0-6 の決着済み論点と同じ）: 前ラウンドまでに `defer` と確定したキーを再び挙げるなら、①構造的理由がまだ成立する → `defer` を維持 ②新証拠（新たな実害・出典）が理由に答える → `do-now` / `[block]` に上げ、新証拠を一文で添える（記録の `reopen_evidence`。無い再出現は記録の不正として機械が止める） ③理由が書かれていない → 台帳側の欠陥として surface する。
   - **同じルーターを、過去ラウンドの `[block]` キーにも課せ**（道具が「過去のラウンドの `[block]` で今ラウンドの記録に無いキー」として出す一覧）: ①まだ残っている → **同じキー文字列で挙げ直す** ②閉じた → 閉じた根拠を一文添えて記録には載せない ③確かめられない → 未確認として挙げる。**機械はこの一覧を数えない**——「消えた」は 2 ラウンド間の遷移で、終了コードは 1 ラウンドの述語なので、和で数えると直したキーが永久に残り、隣接で数えても 1 ラウンド待てば会計から落ちる（どちらも実測・経路で確かめた）。数えられないからこそ、振り分けは judge の義務である。実測: この一覧を振り分けなかったラウンドで、前ラウンドの `[block]` 6 件のうち **3 件が未閉鎖のまま記録から落ち**、次のラウンドで「新規」の顔をして戻った。
   - **再燃の原因**: 新証拠なく同じ指摘が戻る・直したはずのキーが戻る（履歴に「消えて N 回戻った」と出る）なら、原因がコード（本当に残っている）か、レビュアー（同じ癖）か、規約（`REVIEW.md` の観点の誤発火）かを判定しろ。規約なら問いの台帳に `rule`（origin は当該ユニット）で載せ、観点名と理由を書け（剪定するかは人。「この規約の育て方」）。
   - **目的の外への膨張**: 修正が露呈させた既存の欠陥の回収が続き、凍結した目的の外に出ているなら、当該ユニットを `defer` に落とし、問いの台帳に `split`（origin は当該ユニット）で載せ、BASE 時点の実在の確かめ方と、目的の外である理由を書け。露呈の回収は既定のまま（`REVIEW.md`「別 Issue への先送りを既定にするな」）で、これは例外の申請である。
   - **問いの台帳の再審**: 前ラウンドまでに載った問い（`questions` で `held` / `escalate`）を 1 件ずつ、今ラウンドの材料で振り分けろ。①今ラウンドの材料が答えた（実測・並行 PR の結論・別ユニットの修正で形が変わった）→ `resolved`、答えた材料を `resolution` に ②自明——決める規律を名指しできる（零処方が落ちない／凍結した目的の内側なので do-now／候補の 1 つが実測で優越）→ `resolved`、規律を `resolution` に。**ただし同じ `[block]` が 3 ラウンドの記録に続けて在るキーの `stuck` は、その `[block]` が記録から消えるまで `held` のままにし、決めた処方を `reason` に書け**——機械の stuck 検査は「未決のまま載っている」ことを要求するので、判断が付いた周に `resolved` へ動かすと同じ周が `exit 2` になる（P3 は「見つけた周の記録は、その周に直していても判定どおり書け」なので、直した周も `[block]` は残る。この 2 つは必ずその周に衝突する） ③まだ決まらないが次の周の材料で決まりうる → `held` のまま、何が来れば決まるかを `reason` に ④人でないと決められない（好み・組織の方針・可逆性の低い合意・目的そのものの書き換え）→ `escalate`、理由を書く。**自明かの検査は独立再導出で行え**——お前は 1〜7 で台帳を見ずに同じ欠陥を採点している。そこで岐路を立てずに処方を 1 つ置けたなら、その問いは前の周の目にだけ難しかった（`resolved`）。同じ岐路を独立に立てたなら、問いは実在する（`held` か `escalate`）。**1 件ずつ振り分けたあと、台帳全体を並べて枝同士を見ろ**（1〜4 と同じ木探索の規律。1 件ずつでは見えない）: (a) 同じ根から出た問いは束ねる（4 の一撃の選定と同じ。実測の 3 件のうち前の 2 件がこの形だった——別々に立った岐路が同じ仕掛けの上に在り、仕掛けごと落とす零処方 1 つで同時に消えた。実測の全体は「停止条件」が正本） (b) 1 つの答えが決まるまで手を止めるユニットが在るなら、そのユニットの key を `depends` に書く（**問いの key ではない**——機械はユニットの key として突合し、実在しないものは記録の不正になる） (c) `resolved` にした答え同士が矛盾しないか (d) 1 つの零処方（取り下げ・仕掛けごと落とす）で複数の問いが同時に消えないか。**`resolved` にした問いは最終報告に「ループが自分で決めたこと」として根拠つきで並ぶ**——聞かずに決めた側が、人が覆せる形で見せる義務である。台帳から黙って落とすな（機械が止める）。

   **`split` / `rule` の未決の問いは、`origin` にも `depends` にも `[block]` / `do-now` のユニットを書けない**（人に聞く前に直す義務が消えると逃げ道になる。機械が止める。条件の正本は `NO_OPEN_ORIGIN` の定義）。`fork` / `stuck` は `[block]` に付くが、**問いは阻害要因を消さない**——当のユニットは記録に `[block]` のまま残り、答えが出るまで収束しない（問いは阻害を説明するだけで、免除しない）。**ループは止めない**——問いは台帳に溜め、次の周の judge が再審し、止めて聞くのは答え無しに進める仕事が尽きたと機械が言ったとき（停止条件）だけである。目的の内側のものを split に逃がしていないかは R1 が監査する。台帳と履歴を P1 の探す役と R2 に渡さないのは P0-6 と同じ理由（受容の履歴を知った目は追認する）で、judge にだけ、しかも確定後に渡すのは、writer が台帳を当てると「writer がラベルを決めない」が破れ、judge に先に渡すと追認になるからである。

出力は「根本ユニットのリスト（ラベル・キー・disposition・一撃）＋根本フレーミング＋**問いの台帳に載せる問い**」。これが P3 の作業単位になる。

## P3: 修正（writer）

**P2 の根本ユニット単位で直せ。** 生 finding を1件ずつ潰すな。**導線の死を注記で直すな**——手段の優先順位と、注記に書いてよいものの線は `REVIEW.md`「導線を作る手段の優先順位」が正本で、ここに写しは持たない。注記で直すなら、正本の①〜③が落ちる理由を素材 `fix_closure` に書け。**フレーミングに同意できない・個別症状のままに見える場合は、自分で根本単位を切り直すな**——`P2 を新しい context の judge で再起動`し、再集約された根本ユニットを受け取ってから修正に入れ。局所 patch でなく再設計を選んでよい。不要になったコード・抽象は同時に引け（削除・集約の可否は R1 の simplify 制約に従え——他所に無い情報〈事実・導出根拠・why〉を消すのは禁止、同一情報の単純反復は事実を消さない集約・再配置で畳むのが義務）。

`[block]` は必ず直す。**P2 grader が `do-now` とした `[suggest]` も直せ**——writer 裁量で `defer` に覆すな。disposition に異議があるなら自分で覆さず、`P2 を新しい context の judge で再起動`して再判定させろ。`defer` された項目だけ最終報告に理由とともに記載する（実体基準は `REVIEW.md`「対応の判断」）。

**見つけた周の記録は、その周に直していても判定どおり書け。** 直したことを理由にラベルを軽くするな——消えるのは**次の周の採点**であって、書き換えではない。**直した周が阻害要因ありで終わるのは設計どおり**で、収束はそもそも連続 2 ラウンドを要求している。ここが書かれていないと、実行者は「直したのに阻害が残る」を不具合と読み、ラベルを軽い側へ倒して通す——**それは writer が採点していることになる**（実測: 別の実行者が、どこにも書かれていない慣習としてこの倒し方を踏襲していた）。直したことは素材 `fix_closure` に書け。

**問いの台帳で `fork` の origin か `depends` に挙がったユニットは、この工程で実装するな**（`REVIEW.md`「処方の最小性」が正本）。**待つのはループを止めることではない**——他のユニットを直し、次の周の P1〜P2 を回せ。前の周の目にだけ難しかった問いは次の周の judge が独立再導出で解き、そうでない問いは台帳に残る。止めて聞くのは、答え無しに進める仕事が尽きたと機械が言ったとき（停止条件）で、**writer が「もう聞くしかない」と決めるな**（根拠の実測は「停止条件」が正本）。印が無くても、**手を動かした結果が機構の新設・共有面の拡大に及んだと気づいた時点で手を止めろ**——それは修正ではなく設計作業で、P2 の列挙（零処方）を経ていない機構をこの工程から出すな。実例: レビュー修正として共有ファクトリに入れた変換ミドルウェアが、次ラウンドで捕捉範囲・適用先・既存フラグの設計判断を 3 方向から差し戻された——1 ラウンド分のレビュー火力が、飛ばされた設計の穴埋めに使われた。

**修正ごとに閉鎖を実証しろ**——`[block]`・do-now の各修正について、①欠陥の機構と②修正がそれを閉じる機構を一文ずつ書き、③閉じたことを確かめろ。確かめ方は修正の性質に比例させる: 検査・ガードの修正は、**その不変条件を共有する箇所を先に全部挙げ**、1 箇所ずつ退行を注入して赤→復元して緑（ゲートの実効性確認と同じ規律）。**「1 つ試して赤だった」で止めるな**——実測: この規則が「退行を 1 つ」と書いていたため、入口 2 つのうち 1 つ・枝 3 本のうち 1 本しか塞がない修正が 3 回続けて出た（写し先の封じ込め・コメントの消し方・ゲートの赤の確認）。**挙げた箇所と、それぞれ赤を見たかを `fix_closure` に書け**——挙げずに直すと、残った腕は次のラウンドで「新規」の顔をして戻る。構造の修正は移した先が実際に使われることの機械確認（grep・実行）、文言・文書の修正は変更後の実物の提示で足りる。**結果は素材 `fix_closure` に書け**（修正が無いラウンドは `not_applicable`）。実例: 「fixture を共有側へ移して重複を消す」修正が、テストフレームワークのローカル定義優先を確かめずに適用され、重複を 1 個から 2 個に増やしたうえコミットメッセージまで嘘にした——移設後に共有側が実際に使われることの grep 1 回で止まっていた。

## P4: 再採点と収束判定（writer が段取り、判定は grader）

やり直しの段取りは writer が担い、採点・突合の判断は全て grader に置く:

1. **writer**: CI を再実行（緑維持。赤なら P3 に戻って先に直せ）。
2. **writer**: P1 を新しい context でやり直せ——局所レビューの再実行と、各 grader subagent の新規起動。**前ラウンドの grader 出力・修正の経緯を P1 / P2 の subagent に渡すな**（渡すと前ラウンドのフレームにアンカーされ、再採点が追認になる）。続けて P2 grader を新しい context で再起動し、根本ユニットを再採点させろ。
3. **突合（機械）**: `python3` が無い環境では `python` に読み替えろ。

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/review-record.py .claude/review-rounds/
   ```

   ディレクトリを渡すと `round-<N>.json` を全部読み、最新を今ラウンドとして突合し、**履歴**（全ラウンドの推移）を出す。履歴は次ラウンドの P2「履歴との突合」に渡す入力で、最終報告の冒頭にも使う。連番に穴があれば落ちる（前ラウンド分を消すな）。**終了コード 2 は「記録が不正」で、1（阻害要因あり）と取り違えるな**——2 は記録を直して再実行する合図であって、非収束の判定ではない。機械が拾うもの: `[block]`（新規か残存か。残存には印が付く——ただし**この印は手順書の stuck（2 ラウンド連続）より広く発火する**ので、印だけで stuck と診断するな）・未対応の `do-now`・素材と R1〜R4 の未実施・**連続 2 ラウンド**（前ラウンドに阻害があれば、今ラウンドが阻害なしでも「1 ラウンド目」として阻害要因に数える。**writer が数えるな**）・持ち越しの連鎖（実際に見たラウンドが途中で書き換わっていないか）・defer 台帳（前ラウンドで `defer` と確定したキーが `reopen_evidence` 無しに `[block]` / `do-now` へ戻れば記録の不正）・**問いの台帳**（前ラウンドの `held` / `escalate` が今ラウンドに無ければ記録の不正。同じ `[block]` が 3 ラウンドの記録に続けて在るのに、**未決の** `stuck` か `fork` として台帳に無ければ記録の不正）・**阻害要因の帰属**（各阻害要因が保留中の問いの origin か `depends` に帰属するかを分け、**帰属する阻害要因が在って、帰属しない阻害要因が 0 なら「答え無しに進める仕事は無い。ここで止めて聞け」と出す**。writer が数えるな。前提不成立が `escalate` で確定したときは件数に依らず先に出る——止まる経路の全体は「停止条件」が正本）・scalar の増加。記録を消すなの理由は「道具と正本の場所」に書いてある。ここで足すのは 1 つだけ——新しい context の再採点は前ラウンドの受容判断を知らないので、台帳を P2 の judge に渡さないと同じ提案が毎ラウンド再燃して収束しない（渡し方は P2「履歴との突合」）。
4. **writer（問いの台帳）**: P2 の judge が返した問いを、記録の `questions` に**そのまま写せ**（欄と値は `review-record.py` が正本）。**writer が要約し直したり丸めたりするな**——`reviews` の verdict と同じ規律である。judge は書く道具を持たないので、台帳を記録に置くのは writer の仕事だが、中身を決めるのは judge だ。人に聞く候補が無いラウンドは空の配列を書け。
5. **writer（scalar 記録）**: 規模指標を記録の `scalars` に書け。文書・手順書を含むなら当該文書の行数、コードを含むなら `bash ${CLAUDE_PLUGIN_ROOT}/scripts/comment-ratio.sh <BASE>` の出力（手で数え直すな——物差しが揺れるとラウンド間の比較が成立しない）。**scalar はゲートにしない**——増加は R1 への入力であって、閾値で止めるものではない（測れるものをゲートにすると、規則が測れるものへ寄る）。

採点を writer の自己申告にするな（採点は P2 grader、突合は上の機械）。

**1ラウンド = P1 → P4 を1周**（P-R から差し戻されて P1 に戻った場合も1ラウンド）。判定後の分岐:

- 新規/残存 `[block]` > 0、**または P2 grader が `do-now` とした `[suggest]` が未対応のまま（新たな構造的 defer 理由の提示なし）** → P3 に戻り当該根本ユニットを直し、再度 P4。
- `[block]` = 0 かつ CI 緑 → P-R へ進め。

**ただし R1（最小性）と R2（ゼロベース再導出）は `[block]` = 0 を待つな。** この 2 つは**第 1 ラウンドで必ず走らせ**、以降は下記の再発火条件で回せ。P-R の位置に置いたままだと、欠陥の多い差分では永久に到達しない——**欠陥が多いほど枠自体の検査が遠ざかる**という逆向きの構造になる（実例: 5 ラウンド連続で新規 `[block]` が出続け、R1 が初めて走ったのは 6 ラウンド目。走った瞬間に「機構の規模が実態に対して大きい」と差し戻し、-1,193 行の削減になった）。

**R1 / R2 の再発火条件**（どれかに当たったら P-R を待たずに回す）:
- 差分が**機構を足した／置き換えた**（コメント・テストだけのラウンドは持ち越してよい）
- 差分が、P0-3 の制約が測られた対象を**削除・置換した**（＝**前提のドリフト**。制約を測った経路を差分自身が削れば前提は壊れるのに、それを検知する仕組みは他に無い）
- 累積差分の行数が前回 R1 実行時から **1.5 倍**を超えた
- **台帳の未決の問いが前ラウンドから変わった**（R1 だけ。R2 は台帳を監査しないので持ち越してよい）——「行が増えたか」でなく「**監査対象が変わったか**」で見る。問いの `key` だけを見ていたとき、同じ `key` のまま種類・出どころ・選択肢を総取り替えする周と、`resolved` を `held` に戻す周が、どちらも監査を素通りした（実測）。票の持ち越しを決める定番（Gerrit の `copyCondition` は変更の種類を、GitHub の保護ブランチは差分を変える push を見る）と同じ述語である——**台帳を監査する経路は R1 しか無い**のに、上の 3 条件はどれも差分の中身についての条件である。`fork` / `split` は処方が機構に及ぶ種類なので**その周の差分に機構の追加が無いのが普通の姿**で、問いが立った周ほど R1 が持ち越しになり、監査が一度も走らない構成が正規の記録として成立していた（同梱の雛形 3 周がまさにその形で、機械も通した）。**この条件だけは機械が縛る**——問いが新しく載った周に `reviews.R1` が `carried_over` なら記録の不正で落ちる。

**R1〜R4 の verdict はラウンド記録の `reviews` に書け**（値は `review-record.py` が正本）。R1 / R2 を再発火条件に当たらず持ち越すラウンドは `carried_over` と実際に走らせたラウンド、R3 / R4 に到達しなかったラウンド（`[block]` が残った等）は `not_applicable` と到達しなかった理由。**散文の最終報告だけに書くな**——記録に無い verdict は、走らせたかどうかを誰も確かめられない。

## P-R: 俯瞰（収束ゲート・完了宣言の前に必ず）

`[block]` が 0・CI 緑でも、それは収束の**必要条件にすぎない**。R1〜R4 を実行し全て通るまで収束を宣言するな。**R1・R2 は P4 で前倒し実行しているので、最後の実行以降に再発火条件（P4）へ当たっていなければその結果を使ってよい**——当たっているなら回し直せ。R3・R4 はここで必ず実行しろ。対象はループ開始時点からの**累積差分**（対象差分＝ `git diff <BASE>`）。**`judge` / `inspector` は shell を持たないので、累積差分の本文と変更ファイル一覧は writer が `git diff <BASE>` で取ってプロンプトに貼って渡せ**（P1 の grader と同じ）。R1・R3・R4 の subagent は `verdict: pass | redesign-needed | unverifiable` のいずれかと理由を返せ（R2 の verdict は後述の比較 grader が確定する。ただし `premise-invalid` だけは R2 subagent が直接返す）。**返った verdict と理由は、そのままラウンド記録の `reviews` に写せ**（P4 の突合が読む。writer が verdict を要約し直したり丸めたりするな）。1つでも `redesign-needed` なら非収束——P1 から新ラウンドに戻れ（`premise-invalid` は `redesign-needed` と違って再設計ラウンドには送らない——停止条件「前提不成立」の項が扱う。そこで別 context の judge が根拠を検算し、仮定を偽と示せたら次の周で R2 を回し直す）。

- **R1 冗長と最小性** — `judge`（設計判断なので上位の役）。**前段としてコメントの削除候補を取れ**（writer が段取る）: `pr-review-toolkit:comment-analyzer` を、累積差分が触れたファイルを対象に起動しろ。この役は「コードをなぞっただけのコメントは削除候補に挙げろ」「削除を勧めるなら理由を明示しろ」を定義に持っている。**writer は呼び出し時のプロンプトに次の 3 つを足せ**——定義に無く、足さないと迷ったときに残す側へ倒れる: ①削除候補ごとに**同じ内容がどこにあるかを名指しさせる**（コード・他のコメント・文書・テスト名。名指しできないなら削らない）——名指しは後から確かめられるので、提案が意見のまま残らない ②**残すと判断したコメントにも、それが運んでいる事実を一文で言わせる**——削る側にだけ義務があると、黙って残す方が安くなる ③残してよい線は `REVIEW.md`「導線を作る手段の優先順位」のとおり（内容は正本のとおりで、ここに写しは持たない）。あわせて**コメントアウトされたコード・編集の実況（「〜を追加した」）・名前のすぐ隣で名前を言い直しているもの**を、具体的な引き金として明示的に探させろ。以前ここには、コメントを剥がした写しを文脈を知らない読み手に精読させる自作の仕掛けが在ったが、3 ラウンド回して削除の実績が 0 件で、写しにリポジトリ全体が入るため隔離も 2 ラウンド続けて破れた（同じ期間に注釈の割合は 22% → 29% に増えた）。落として、既に依存に入っている役に寄せてある。
  **前段の一覧が取れなかったからといって、`reviews.R1` の verdict まで `not_run` に倒すな**——R1 の残りの仕事（最小性・場当たり累積・処方の正当化・問いの台帳の監査）は前段なしでも判定できるので、そちらで verdict を決め、理由に「コメントの削除候補は未取得（理由）」を明記しろ。実測: 前段が取れないと verdict ごと倒す形にしていたとき、`not_run` は阻害要因なので**このリポジトリ自身のレビューは原理的に収束できなかった**（安全側に倒したつもりが、収束不能という別の壊れ方になっていた）。
  R1 の judge にはこの一覧と目的テキストと累積差分を渡し、次を判定させろ: **削除候補のうち、名指しされた「同じ内容の在り処」が実在するもの** → 削る（do-now）／**残すと判断されたのに運んでいる事実を言えなかったもの** → 削る候補として扱う／説明が目的とずれた箇所 → 注記でなく構造か名前で直す（do-now）。**あわせて問いの台帳の監査**——`split` の origin が凍結した目的の内側なら、また `fork` の選択肢に零処方（取り下げ・既存の機構 1 つ）が列挙も棄却もされずに人へ回されているなら `redesign-needed`（逃げ道の検知）。そのうえで累積差分が最小か。(a) 小修正が積み重なって本来1根本で済むものを症状パッチしていないか（場当たり累積）。(b) 単一の修正でも、他所から導ける内容を重複して述べていないか・より少ない記述（コード/文章）で同じ目的を運べる箇所がないか。**ただし simplify は制約付き**: 削ってよいのは削っても変更の *検証済みの値打ち*（コードなら挙動・テスト、設計/論拠文書なら *導出の再現性*）が落ちない分だけ。保護するかは**内容で判定しろ——「他所に無い情報（事実・導出根拠・why）を運ぶか」だけをキーにし、書き手の意図を判定に使うな**（意図は新 context から見えず、ループ自身が足した注記ほど「意図的」に見える）。他所に無い情報を運ぶ残余・caveat・why は消すな。**同一情報の反復は「あえての冗長」として自動保護しない**——複数箇所への配置自体が読み手の動線上必要と一文で言える場合（例: 破壊的コマンドの直前ごとの確認ガード）だけ保護し、そうでない単純反復・散在は、事実を消さない**集約・再配置（1節に抽出して各所から参照する形を含む）を simplify の義務**として指摘しろ。順序は固定で『必要な内容が在るか（＝**冷たい読み手**——文脈を持たない初見の第三者——が、書かれた指示・論拠だけから結論や手順を再現できるか。再現に要る前提・制約が省かれていないか）』→『在るとして最小か』。局所の simplification は `/simplify` が担当——ここで見るのは累積差分全体・文章の密度・抽象の重複である。**`do-now` で本ループ内に直した修正も累積差分の一部として必ず対象に含めろ——do-now を口実に症状パッチが積まれていないか、disposition（do-now/defer の判断）自体が場当たりでないかも見る。採られた処方が `REVIEW.md`「処方の最小性」に照らして正当化されているか（大きい処方に、小さい方が落ちる理由が付いているか。列挙を経ずに機構が足されていないか）もここで監査しろ。R1 は P-R の必須ゲートで、この場当たり検証を素通りするな。** **writer から scalar 推移（P4「writer（scalar 記録）」）が渡されたラウンドでは、相殺削除なき単調増の増分ごとに「他所に無い情報か」の正当化を要求しろ——正当化できない増分は集約・再配置の対象。**
- **R2 ゼロベース再導出** — `blind-judge`（元の目的から理想解を独立設計するため深い推論が要る）、**完全隔離**: この役は道具を持たないので git・実装ファイル・コミット履歴に触れられない。渡すのは『元の目的』テキストだけにし、そこから理想解を独立設計させろ。**ただし独立設計に入る前に、まず目的そのものの実在を疑え**: 「この変更が解く問いは実在するか。既存機構で自明に満たされていないか（例: 1デプロイ＝1リポジトリならリポジトリ自体が識別子で、別途記録する問いは生じない）。要件が未確定のまま実装に踏み込んでいないか」。問いが実在しない・既存機構で自明・要件未確定と判断したら、理想解の設計に進まず `premise-invalid`（解くべき問いが立っていない）を返せ——`redesign-needed` と混同するな（routing が違う: `redesign-needed`＝新ラウンドで再設計、`premise-invalid`＝別 context の judge が根拠を検算してから人へ。停止条件「前提不成立」）。問いが実在するなら通常どおり理想解を独立設計しろ。**理想解には、目的の当事者が日常で回す動線（反復開発・運用・撤収）まで含めろ——成果物の一回の起動で設計を閉じるな**（当事者が毎日触るものの目的には、暗黙に「日常の回し方」が含まれる）。**subagent は独立設計（または「問いが立っていない」判定）だけを返す。突合と verdict 確定を writer がやるな**——独立設計と累積差分の本文を別の比較役（`blind-judge`・新しい context）に貼って渡し、本質的な食い違いの有無で verdict を確定させろ（writer≠grader を収束判定でも守る）。P0 で「元の目的」が `unverifiable` なら R2 も `unverifiable`。
- **R3 全体整合** — `inspector`: 変更全体でファイル横断の整合（命名・規約・界面・docs 追従）。**R3 が見るのは diff が触れた範囲の整合**（変更したものが既存と揃っているか）。**既定・推奨の文書間一致**（変更が触れる文書群が読者に示す推奨ツール・手順・構成が単一に収束しているか——一次検出は P1 整合性観点、ここは最終ゲートの再確認）も含む。diff が触れていない横断リスクは R4 が見る。
- **R4 見えてないスコープ** — `inspector`、**SRE・セキュリティ・データガバナンスの複数レンズ**で、diff の中でなく **diff が解こうとしている領域に潜む、変更が手を付けていない横断リスク**を探せ（観点は `REVIEW.md`「横断リスク観点」——レート制限・濫用耐性、PII の外部送信、可用性の外部結合、誤爆半径、移行退行の棚卸し（BASE 能力インベントリ）。列挙は代表例で限定ではない）。R1〜R3 が diff 内中心なのを補う。この grader には `REVIEW.md`「横断リスク観点」を **Read させて**従わせろ——移行退行の棚卸し（BASE 能力インベントリ）の中身・発火条件・BASE 比較の基準・明示返答の要求は正本のとおりで、ここに写しは持たない。棚卸しが発火する diff（移行・手順・開発フロー・UX）で「消えた能力」の有無の明示返答を欠いた出力は受け取るな（無言の省略を禁ずる）。**該当リスクは「この変更で導入・露呈したか」で扱いを分けろ**——この変更が導入・露呈させたものは本ループで回収（`redesign-needed`）、純粋に既存かつ無関係なものは最終報告に `[suggest]` 以下で surface するに留め `pass` を妨げない（`REVIEW.md`「別 Issue への先送りを既定にするな」の因果判定に従う）。

## 停止条件

**種類の正本は `review-record.py` の `QUESTION_KINDS` で、ここに写しは持たない。** 下に挙げるのは、**0.27 まで「停止条件」として別々に並んでいたもの**が今どう扱われるかと、その再審の問いである（`split` / `rule` は単独では周を止めないので、ここでなく P2「履歴との突合」が扱う）:

- **前提不成立**（`premise`）: R2 が `premise-invalid` を返した。**立った周に、別 context の `judge` に根拠を検算させろ**——`blind-judge` は道具を持たないので、「既存機構で自明に満たされている」「1 デプロイ＝1 リポジトリ」の類は目的テキストの外の**仮定**である。judge がリポジトリの実態で仮定を偽と示せたら `resolved`（実測した事実を制約に**足し**——目的は動かすな。前提のドリフトと同じ事前登録の例外——次の周で R2 を回し直せ。この周の R2 は `premise-invalid` のまま書け）。仮定が真か、根拠が目的テキストの内側で閉じていて実測で反証できないなら `escalate`——**このときだけは残る仕事が全てその答えに従属するので、他の阻害要因の帰属を問わず止めて聞け**（機械もそう出す）。
- **独立検証不能**（`unverifiable`）: R2 が `unverifiable`（元の目的を独立に取れない）。再審の問い: 出典①②③の外（issue・コミットメッセージ・設計文書）に目的の記述が無いか。
- **未観測**（`awaiting`）: 主経路を動かせない（環境が無い・権限が無い・実機が要る）。素材を `awaiting_human` にして台帳に載せろ。再審の問い: 動かす手段が本当に無いか（テスト用の設定・写し・fixture）。**「静的レビューを何ラウンド重ねたか」で観測の欠落を埋めるな**——読む役をいくら増やしても、実行して初めて現れる欠陥は現れない。誰がどこで動かすかは人の判断で、ループ内で `pass` に丸めるな。他の `awaiting_human` の素材（並行 PR の一覧が打ち切られた・決定記録を洗えなかった・CI を手元で走らせられない）も同じ形で載せろ——「打ち切られた」は上限を上げれば済むことが多く、人に聞く前に再審で消える。

**問いではないもの（台帳に載せない）。** 次の 1 つは同じ節に置くが、人に聞く候補ではなくループ内の手当てである:

- **前提のドリフト**: 差分が P0-3 の制約の根拠を壊した（制約を測った対象をこの PR 自身が削除・置換した）→ **事前登録の例外**（P0-4 の「以降変更しない」は目的テキストを凍結し、そこに書いた制約＝P0-3 で測った値も一緒に凍る。ここで解くのはその制約の部分だけで、目的そのものは動かすな）。制約を測り直し、R1 と R2 を回し直せ。事前登録の規律はゴールポストを動かさないためのもので、**作業自身が前提を反証した場合まで凍結する意味は無い**（凍結すると、消えた前提の上に作り込みが積み上がる）。測り直した制約と、前の制約が偽になった理由を最終報告に書け。

## 最終報告

**報告は利用者の言語で書け。** この手順書が日本語であることは、報告を日本語にする理由にならない——判断を下すのは人で、読めない言語の報告では下せない。**冒頭 3 行は「人が決めること」だけ**——問いの台帳で `held` / `escalate` のもの（別 PR に積むか・どの観点を見直すか・設計の岐路・前提不成立・誰がどこで動かすか）。無ければ「人が決めることは無い」と 1 行。**台帳で `resolved` にした問いは「ループが自分で決めたこと」として、根拠つきで冒頭の直後に並べろ**——聞かずに決めた以上、人が覆せる形で見せる義務がある。判断材料は `review-record.py` の履歴（全ラウンドの推移）をそのまま貼れ。

**人に聞くところは、ループを見ていない人が初見で読んで決められる形にしろ。** 人はラウンドの間ずっと別の作業をしていて、報告を読む時点で文脈を持っていない。**内部の語彙（`[block]`・do-now・`defer`・零処方・R1〜R4・素材名・安定キー）で書かれた問いは、それだけでは決められない。** 次を満たすこと:

1. **急ぐものと後でよいものを分け、件数を先に言え**（「決めないと次のラウンドが進まないもの N 件／後でよいもの M 件」）。一度に読める量には上限がある——全部を同じ重さで並べると、どれも決まらない
2. **1 件ずつ独立して読める形にしろ。** 前の項目を読んでいる前提にするな
3. **1 件につき、何を決めるのか・なぜこれが出てきたか（きっかけの実物）・選択肢ごとに何が起きるか・決めないと何が止まるか**を書け。**内部の語彙を使わずに言えないなら、まだ問いになっていない**
4. **選ぶ側の材料を出せ。**「どちらもありえます」で終えるな——決める人は文脈を持っていない。ただし**書いてよいのは judge が台帳に書いた `options`（機械が 2 つ以上・帰結つきを要求している）と `reason` だけで、writer が新たに 1 つを推すな**——`escalate` は judge が「人でないと決められない」と確定したもので、そこに実装を負う側の判断を戻すと、人が覆すべきものを先に決めることになる。`options` を持つのは `fork` だけなので、それ以外の種類は選択肢と帰結を自分で書いて推奨は書くな

書けたら**出す前に確かめろ**。`cold-reader` を起動し、**人に聞くところの本文だけ**を貼って渡して（ラウンドの経緯・記録・差分は渡すな）、①どこで意味が取れず止まったか ②何を推測で埋めたか ③この本文だけで決められるか、を返させろ。詰まりが残っているうちは出すな。**別プラグインの投稿ゲートに頼るな**——それは導入していない実行者では黙って飛ばされる。**自己評価で代用するな**——書き手は全文脈を持つので、読者が持っていない前提を自分では検出できない。これはこのループが他の全ての役でやっている分離（評価する目と評価される側を分ける）を、報告そのものに当てるだけである。統合後の最終報告に次を必ず含めろ（欠けた報告は収束とみなさない）:

- 各根本ユニットの「ラベル・対応内容／対応不要の理由」
- **R1・R2・R3・R4 それぞれの `verdict` と理由**（記録の `reviews` から写せ。持ち越したものは実際に走らせたラウンドも）。R1 は読み手の実測の結果（ずれた箇所・削ったコメント・残した why）も
- **問いの台帳の全推移**——各問いが何周目に立ち、どの周に何で決まった（または人へ回った）か。**推移は `review-record.py` の履歴から、決めた根拠は `resolved` にした周の記録の `resolution` から写せ**——履歴は状態と種類の推移しか持たないので、決めた根拠はそこには出ない（`resolved` は次の周の台帳から落ちてよいので、最終周の機械出力にも残らない）
- **`defer` の台帳**——全ラウンドの記録に現れた `defer` キーと構造的理由の和集合（後のラウンドの judge が挙げ直さなかったキーも受容は続いているので落とすな。`review-record.py` が「今ラウンドの記録に無いキー」として出す）
- **grader subagent の生出力（根本ユニットのキー集合）**・grader 再実行の回数・**「元の目的」の出典（①②③）**・基準点 `BASE` の SHA
- **主経路の実行観測**: 何をどこで動かし、何を観測したか（観測できなかったなら理由）。**「テストが緑」を観測として書くな**——本番と同じ経路を流れた実物だけを書け
- **新設機構の棚卸し**: この差分が導入する機構・配管（ビルド設定・initContainer・環境変数・CI ジョブ・テンプレートのノブ・スクリプト等）を、どの grader も指摘しなかったものも含め判定抜きで一覧する。自動ゲートが全て緑でも「この機構は存在すべきか」は機械判定の外にあり、短い一覧が見えていれば人間が目利きで気づける——その導線として開示する（一覧に留め、良し悪しの判定は書くな）

subagent の出力が報告の言語と違っても揃えろ。コード識別子・ファイルパス・エラーメッセージ等の固有名詞はそのままでよい。
