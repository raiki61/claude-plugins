## 道具と正本の場所

- **スクリプト**: プラグイン同梱。以降 `review-record.py` / `comment-ratio.sh` と書いたものは `${CLAUDE_PLUGIN_ROOT}/scripts/` 配下を指す（実行例は P4 に書いてある）。
- **ラウンド記録**: `.claude/review-rounds/round-<N>.json`。`<N>` は 1 から 1 ずつ増やす**ラウンド番号**（P4 の「1ラウンド = P1→P4 を1周」の定義に一致させろ）。ディレクトリは無ければ作れ（`mkdir -p .claude/review-rounds`）。**前ラウンド分を消すな**——連続 2 ラウンドの突合と defer 台帳がこれで成立している。
- **レビュー観点の正本**: `${CLAUDE_PLUGIN_ROOT}/REVIEW.md`（言語・フレームワークに依存しない観点）。対象リポジトリのルートに `REVIEW.md` があれば**それも読み、そのチームが事故から足した固有の追加観点として併用しろ**。無くても走る。**観点の写しをこの手順書に持ち込むな**（二重管理は片方が stale 化する）。
- **固有の規約**: どちらの `REVIEW.md` にも書かせず、対象リポジトリの一次情報（README・lint 設定・パッケージマニフェスト・CI 定義・近傍コード）から毎回把握しろ——手順は `REVIEW.md`「固有規約の把握」のとおり。**固有の技術名を観点側に書き写した時点で、それは複製で、リポジトリが変わっても古いまま残る。** 把握した内容は次ラウンドへ**参照として**引き継いでよいが、**文脈遮断 grader（P1）と R2（P-R）には渡すな**——渡した時点で隔離が壊れ、「このリポジトリではこうなっている」を所与にした追認になる。疑う役の入力は、対象差分と観点本文だけに保て。

## 依存

局所レビューに使う `pr-review-toolkit` は `plugin.json` の `dependencies` で宣言してあり、このプラグインの導入時に実体ごと入る（機構と入手経路の制約は `README.md`「依存と入手経路」が正本）。**導入コマンドを手順として実行するな**——宣言が解決できない環境ではこのプラグイン自体がロードされないので、`/review-loop` が動いている時点で `review-pr` は在る。

`/simplify` と `/security-review` は Claude Code 本体の組み込みなので、導入は要らない。

`review-pr` の呼び出し自体が失敗したら（権限・実行時エラー）そこで止めるな。素材 `local_review` を `awaiting_human` として記録し理由を書いて進め——**無かったことを `not_applicable` にするな。**

## 役割分担（最重要）

このループを回す session が **writer（実装者）**。**writer は局所レビューを機械的に実行して findings を集めることはできるが、ラベル確定・根本診断・収束判定はしない。** それらは全て別 context の **grader subagent** が行う（writer ≠ grader）。writer は grader が確定した `[block]` を直すだけで、ラベルを自分で上げ下げできない。grader の判定を覆したい時も自分で決めず、別 context の grader に再判定させろ。

**grader を都合よく使うな**: 同一ラウンドで grader を回し直して有利な結果を採るな（やり直しは次ラウンドのみ）。grader subagent の生出力（根本ユニットのキー集合・各 verdict）は最終報告にそのまま転記しろ。

レビュー観点とラベルの正本は `REVIEW.md`（上の「道具と正本の場所」で定義した 2 つ。以降 `REVIEW.md` と書いたものはその併用を指す）。grader はレビュー開始前に `REVIEW.md` を読むこと。ただしリポジトリ探索を禁じた隔離 grader（文脈遮断）は自分では読めないため、writer が該当セクションの本文をプロンプトに貼って渡せ。

武器の使い分け: **局所レビューは公式 skill に委譲**し再実装するな。ただし**欠陥と品質は別の道具**で、片方はもう片方を代替しない——欠陥（correctness）は `pr-review-toolkit:review-pr`、品質（reuse / 簡素化 / 効率 / altitude）は `/simplify` が担当する（`/simplify` は「バグは探さない」と自ら明記している）。**両方走らせろ**——「簡素化」は `review-pr` の観点にも含まれるが、観点が重なることは片方を省く理由にならない。根本診断・整合性・俯瞰は grader subagent で行う（公式に相当機能がない）。

## P0: 基準点と「元の目的」の固定（writer）

1. 基準点を固定: 作業ツリーに未コミット変更があれば `BASE=$(git rev-parse HEAD)`、クリーンなら直前コミットをレビュー対象とみなし `BASE=$(git rev-parse HEAD~1)`（HEAD がマージコミットなら対象範囲をユーザーに確認しろ）。未追跡の新規ファイルは `git add -N` で差分に載せろ（P3 で新規作成した場合も同様）。**以降の全工程で「対象差分」＝ `git diff <BASEのSHA>`**——後続ラウンドでも基準点を動かすな（`git diff HEAD` は P3 の修正のコミット状況次第で元の変更が差分から消えるため、ラウンド2以降の使用を禁ずる）。`BASE` の SHA は最終報告に記せ。
2. CI のテスト・lint をローカル実行し緑を確認。赤ならレビューより先に直す。
3. **前提を実測しろ（目的テキストより先に）**——目的と制約に書く数値・規模・件数・「〜が来うる」の類は、**この作業ツリーで測った値か、ファイルを名指しできる事実**でなければ書くな。記憶・以前の測定・一般論を制約として渡すと、R2 はそれを所与として理想解を導くので、**前提が誤っていても pass が返る**（R2 は実装もリポジトリも遮断されているので、制約の真偽は原理的に検査できない）。実例: 「本文は最大 4MB 級」を制約に書いて R2 が pass を出したが、その 4MB は**同じ PR が削除した経路**の実測値で、実際に運んでいたのは 5,411 バイトだった。5 ラウンド分の作り込みがその上に乗った。各制約に「どう測ったか」を 1 行添えろ。添えられないものは制約でなく仮説として渡せ。
4. **「元の目的」をテキスト化**——P-R2 のゼロベース再導出に渡す唯一の入力になる。出典の優先順位: ①PR 説明 ②`current-plan.md` やタスク記述（いずれも実装と独立なので望ましい）③それも無ければ writer が要約を書く（**最終手段**）。③を使う場合、その目的テキストを**別の grader subagent にレビューさせ**（実装に都合よく狭めていないか）、合格分だけ R2 へ渡す。目的テキストは**最初の修正に着手する前に確定し、以降変更しない**。最終報告に出典（①②③）を明記し、③のときは独立性が弱い旨も記せ。どの出典も得られない場合は「目的不明」とし、R2 を `unverifiable` として扱う。
5. **並行 PR 衝突チェック**——次の 5 段を順に踏め。段を飛ばすな。

   1. **対象リポジトリを解決して突き合わせる**: `gh repo view --json nameWithOwner -q .nameWithOwner` の値と `git remote -v` の remote が一致するか確認し、以降の `gh` 呼び出しには全て `-R <owner/repo>` を渡せ（機構と危険性は `docs/customize.md`「fork 運用・複数アカウント」を読め）。一致しない・解決できないなら、以降を「確認できなかった」として扱え——**取り違えた一覧で「衝突なし」と書くな。**
   2. **自分の PR を特定して除外する**: `gh pr list -R <owner/repo> --json number,headRefName` の一覧から、`git branch --show-current` と `headRefName` が一致する PR を**先に外せ**。自分の PR は変更ファイル集合と必ず 100% 交差するので、外さないと下の 5 段目で**レビュー対象そのものを「担当 PR がある」としてスコープ外にする**（自己言及的な誤判定。実際に起きた）。
   3. **変更ファイル集合を得る**: `git diff --name-only <BASE>`（対象差分）。
   4. **残った PR の変更ファイルを引く**: `gh pr view <n> -R <owner/repo> --json files --jq '.files[].path'`（`gh pr list` 単体では各 PR の変更ファイルを返さないため PR ごとに引く）。変更ファイル集合と交差するものが「同一ファイルを触る並行 PR」。
   5. **交差した箇所を担当 PR に渡す**: 該当 hunk を `gh pr diff <n> -R <owner/repo>` で context に載せ、以降の全 finding を「このギャップは別 PR が既に対応中でないか／自分の修正が、未マージの別 PR が進めている書き換えと同じ関数・領域で衝突しないか」で再評価しろ。衝突・重複が判明した箇所は**その箇所の変更を主導している PR（担当 PR）に渡して本ループのスコープから外せ**（同じ箇所を両 PR で書き換えても merge 衝突を生むだけ・修正は別 Issue でなく担当 PR へコメントで申し送る）。

   洗い出した並行 PR は最終報告に記せ。GitHub 以外のホストでは同等コマンドに読み替えろ——読み替えられず列挙できないなら、確認できなかった旨を最終報告に書け（未確認を「衝突なし」と書くな）。

## P1: 採点用の素材集め（ラベルはまだ付けない）

ラベル付けは P2（grader）で行う。ここでは生の指摘を集めるだけ。grader subagent 群は互いに入力が独立なので、単一メッセージで並行起動しろ。

**素材の返答はラウンド記録（JSON）に書け。** 欄と取りうる値は `review-record.py` が正本で、手順書は列挙を持たない。要点は 1 つ——**「条件に当たらないのでやらなかった（not_applicable）」と「やるべきだったが飛ばした（not_run）」を別の値で書くこと**。散文ではこの 2 つが区別できず、後者が前者に化けるのが元の穴だった。埋め忘れは検証エラーで落ちるので、各素材の節で「明示的に返せ」と繰り返さない。

- **局所（writer が main session で実行）**: 欠陥は `pr-review-toolkit:review-pr`、品質は `/simplify`、認証・データ取扱い・外部 I/O に触れるなら `/security-review` も実行し、findings のみ取得しろ。**findings を機械的に集めるだけで、採点・ラベル確定はするな。**
 - `review-pr` は 6 観点（欠陥・コメント・テスト・エラー処理・型設計・簡素化）を持ち、findings を返すだけで PR へのコメント投稿もコードの修正もしない。簡素化観点も同じく指摘止まりで、修正まで行う `/simplify`（下の作業ツリー確認を参照）の代わりにはならない。
 - **findings を受け取れなかった素材は、記録に `awaiting_human` と書いて P2 へ進むな。**欠落したまま P2 が「局所 findings なし」と読むと、無いことが合格に化ける（`not_run` との区別は `review-record.py` が正本）。
 - **P1 の局所レビュー全体の前後で `git status --short` と `git stash list` と `git diff --shortstat <BASE>` を取り、作業ツリーが変わっていないことを確認しろ。** 変わっていたら戻せ（P0 で固定した BASE 起点の差分追跡が崩れる）。**確認の対象を道具名で列挙するな**——`/simplify` は既定で修正まで行う skill なので最も疑わしいが、実際には**指摘だけを返すはずの grader が検証のためにファイルを書き換えて戻し忘れた**ことがある（型ガードを削って緑になることを実証した跡）。どの道具が汚したかを当てるのでなく、P1 を抜ける時点の作業ツリーを機械で突き合わせろ。
 - 直前ラウンドから対象差分にロジック変更が無いラウンドは `/simplify` の再実行を持ち越してよい。

- **整合性 ＋ 標準機構の迂回（grader subagent・findings 非共有の独立フレーム）**: `subagent_type: general-purpose` / `model: sonnet` を起動し、`REVIEW.md` の「整合性観点」に従ってリポジトリ横断の整合性を確認させろ——「標準機構の迂回」の中身・捕捉条件も正本のとおりで、ここに写しは持たない。迂回の検査は整合性確認とは**必ず独立に**実行させ、プロンプトに「お前は他の指摘を受け取っていない」と明記しろ。**この grader には P1 局所の findings を渡すな**——入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` だけにしろ。findings を共有すると全 grader がそのフレームにアンカーされ、近傍が迂回している機構に気づかなくなる（隔離フレームなら気づく——実証済みの捕捉条件）。この出力は整合性 findings とは**別系統の素材**として P2 へ渡せ。

- **文脈遮断（grader subagent・タスク文脈そのものを遮断）**: `subagent_type: general-purpose` / `model: sonnet` を起動し、**「元の目的」も機能名もタスクの説明も一切渡さず、対象差分の本文と `REVIEW.md` の「コード衛生観点」のセクション本文（この grader にはリポジトリ探索を禁じるため、writer がプロンプトに貼って渡せ。観点の中身と遮断の理由は貼る本文＝正本のとおりで、ここに写しは持たない）だけ**を入力にしろ。上の整合性＋迂回 grader が「タスク文脈は共有しつつ findings を非共有」なのに対し、これは「diff が何の機能かを知らせない」点が新しい——整合性側がリポジトリ近傍から「このコードベースの標準機構」の逸脱を拾うのに対し、こちらは近傍を見ずに「言語 / フレームワーク一般の衛生」の逸脱を拾う（入力が違うため拾う層が違う）。プロンプトには **「お前はこの diff が何の機能かを知らされていない——『この用途なら妥当』という正当化はするな」** を課し、あわせて R2 と同じ自己禁止を課せ: Read / Grep / Bash でのリポジトリ探索を禁じ、渡された diff 本文と貼られた観点本文だけで判断させろ（近傍コードを読めると「このコードベースの標準機構」を学習して整合性 grader と同じ層に堕ち、隔離が崩れる）。この出力も整合性・迂回素材と同様、**別系統の素材**として P2 へ渡せ。

- **外部標準照合（grader subagent・web で外部一次情報を当たる）**: `subagent_type: general-purpose` / `model: sonnet` を起動し、`REVIEW.md` の「外部標準照合観点」に従わせろ——観点の中身（問題クラスの抽出・一次情報での裏取り・粒度・「定番解なし」も正当な結論・受容済み弱点の再照合）は正本のとおりで、ここに写しは持たない。入力は対象差分の本文と変更ファイル一覧と「元の目的」テキストと `REVIEW.md`、および PR 説明・README・残件メモ等で「自覚済み・受容済み」と明記された弱点のリスト（writer が抽出して渡せ。無ければ「なし」と明示しろ）で、**P1 局所の findings は渡すな**（findings に当たると問題クラスの抽出がそこへ寄り、近傍にしか目が行かなくなる）。この grader だけはリポジトリの外（web・公式ドキュメント・当該 OSS の issue / PR・ソース）を当たり、「エコシステムの定番解」からの逸脱を見る。**あわせて手元の依存も見ろ**——`REVIEW.md`「外部標準照合観点」の「手元の依存の使い残し」のとおり（内容は正本のとおりで、ここに写しは持たない）。**対象は差分が import している依存とその直接の依存に限れ**——差分から機械的に導ける集合で、これを外すと読む先が際限なく増える。依存の宣言ファイルに変更が無いラウンドは前ラウンドの判定を持ち越せ。この出力も整合性・衛生素材と同様、**別系統の素材**として P2 へ渡せ。**この grader は P4 が毎ラウンド P1 をやり直すため毎ラウンド走るが、web の引き直しは「アプローチ」をキーにせよ——初回ラウンドと、機構を足す / 変えたラウンドだけ引き直し、体裁だけのラウンド（テスト追加・リネーム・コメント）は前ラウンドの判定を持ち越せ。ただし確証に要る一次情報は必要な分すべて取れ（コスト削減を理由に取得を打ち切るな——削ってよいのは冗長・二次情報の重複 fetch だけ）。迷ったら引き直せ（頻度より精度を優先）。**

- **手順トレース（grader subagent・該当 PR のみ）**: 対象差分に実行手順の文書（README 等）・スクリプト・CI 定義が含まれる場合に起動しろ。`subagent_type: general-purpose` / `model: sonnet`、入力は対象差分の本文と変更ファイル一覧と `REVIEW.md` の「手順トレース観点」で、**P1 局所の findings は渡すな**。変更された手順書・スクリプトの全文を Read させた上で「手順トレース観点」（初期状態からの逐次実行・暗黙の環境状態・誤爆半径）に従わせろ——観点の中身は正本のとおりで、ここに写しは持たない。この出力も別系統の素材として P2 へ渡せ。手順書・スクリプト・CI に変更が無いラウンドは前ラウンドの判定を持ち越してよい。

- **ゲートの実効性確認（writer が実行・該当 PR のみ）**: 対象差分が検証ゲート（CI ジョブ・assert・テスト・pre-commit）を新設・変更しているなら、そのゲートが検知すべき違反をわざと1つ作って赤くなることを確認し、確認後に戻せ（ローカルで再現できるステップは手元で実行しろ）。結果（赤を確認できた／できなかった／未確認とその理由）を、P2 への素材に含めろ。**赤を一度も確認できていないゲートを「検証済み」と扱うな**——検査は、検査自体が失敗・空振りしたとき合格扱いにならないこと（fail-closed）まで含めて初めて機能する。赤の確認は当該ゲートを変更したラウンドだけやり直せばよい。

- **代役の忠実性（writer が実行）**: 対象差分が**外部との継ぎ目**（別プロセス・別サービス・ブラウザ・外部 API・プロトコル）に触れるなら、**テストの代役（モック・スタブ・フェイク）の形が実物と一致するか**を、実物から取った値1件で確認しろ。代役は本物の再現度でなく「実装の誤りが観測できるか」で線を引くが、**入力の形が実物と違う代役は誤りを観測できない**——代役にだけ通る形でテストが緑になる。不一致の箇所は素材として P2 へ渡せ。

- **主経路の実行観測（writer が実行）**: 対象差分が利用者から見える経路・外部との継ぎ目を変えているなら、その経路を **実際に1回動かし、通った値を観測しろ**。観測の対象は「テストが緑になること」ではなく **本番と同じ経路を流れた実物**である。**動かしていない経路を「検証済み」と扱うな**——P1 の他の観点は全て差分を読む役で、実行して初めて現れる欠陥（実行環境固有の挙動・中間層による値の加工・描画）はどれだけラウンドを重ねても現れない。観測は経路を変えたラウンドだけやり直せばよい。

- **根拠の出所検査（writer が実行）**: 対象差分の本文・PR 説明・docstring から「正本は X」「規約は X」「合意済み」等の**事実の主張**を抽出し、その X が対象差分の内側に無いかを確認しろ（`git log -S` 等で BASE 時点の実在を見る）。**差分が自ら足したものを根拠として引用しているなら循環**で、素材として P2 へ渡せ。外部（他チーム・他システム・取り込み元）との合意を主張する箇所は、BASE に痕跡が無ければ **「未確認の前提」**として扱え——循環した根拠は、次に読む人が「確認済み」と受け取るため、未確認のまま設計判断の土台になる。

## P2: 診断（grader・必須の中間関門）

`subagent_type: general-purpose` / `model: opus` を起動し（ラベル確定と disposition は writer が覆せない拘束判断のため上位モデル）、[P1 の生 findings ＋ **P1 の整合性＋迂回 grader が返した「標準機構の迂回」の素材 ＋ 文脈遮断 grader が返した「衛生違反」の素材 ＋ 外部標準照合 grader が返した「外部標準の再発明」の素材 ＋ 手順トレース grader が返した「手順不成立・誤爆リスク」の素材 ＋ ゲート実効性確認・代役の忠実性確認の結果 ＋ 主経路の実行観測の結果 ＋ 根拠の出所検査の結果（**以下この一覧を「P1 素材」と呼ぶ**。いずれも findings とは別系統の独立入力として明示的に分けて渡せ）** ＋ 対象差分 ＋ `REVIEW.md`] を入力に、**生 findings をそのままラベル付けせず、まず根本原因に変換**させろ。**隔離フレームからの素材（迂回・衛生違反・外部標準の再発明・手順不成立・誤爆リスク・ゲートの fail-open）は findings と同列に並べず「隔離フレームからの観察」として扱い、クラスタリングで他 findings に吸収させて薄めるな**——i18n のような標準機構の迂回や、後始末漏れ・公式機構の自作迂回といった衛生違反、エコシステムの定番解の再発明 / 劣化変種使用、検証ゲートの fail-open、手順の不成立・誤爆リスクは、単独で1つの根本ユニット（`[block]` 候補）になりうる:

1. **クラスタリング**: findings を「なぜ生まれたか（出自）」で根本原因にまとめろ。「この5件は1つの命名の死が出自」「この3件は同じ抽象の不在」のように束ねる。
2. **出自分析（順序固定・飛ばすな）**: 各 finding について ①ロジックの正否 → ②（正しくても）出自が読みにくさ・命名・導線の死か、**またはコードベースの標準機構（i18n・エラー分類・共有ユーティリティ等）の手書き迂回・外部エコシステムの定番解の再発明 / 劣化変種使用・衛生違反（後始末漏れ・公式機構の自作迂回・外部 I/O の無防備・検証機構の fail-open）・手順の不成立 / 誤爆リスクか・**実行観測でのみ現れた欠陥**（実行環境固有の挙動・中間層による値の加工・描画）か・**根拠の循環**（差分が自ら足したものを正本として引用）か** → ③ラベル、の順で必ず記録しろ。出自が「習熟した開発者の誤読・導線の死」**または「標準機構の迂回・衛生違反・外部標準の再発明」**なら、それは「好み（`[nit]`）」ではない（迂回は翻訳漏れ・規約逸脱・二重実装の保守負債、後始末漏れは状態汚染・テスト間干渉、再発明は枯れた解の劣化変種を抱え込む保守負債、fail-open は検知すべき違反の素通り、手順不成立・誤爆は初見の実行者の事故という具体的実害を生むため `[block]` 候補）。**P1 素材は 1 つ残らずこのステップで突合し**、列挙されていた項目が診断で `[nit]` に落ちる・取りこぼされることがないようにしろ。**P1 素材のいずれかが明示返答（有無・または「対象外」）を欠いている場合は、ここで P2 を止め、当該 grader を再起動して明示返答を得てから突合に入れ**（無言のスキップを「なし」と誤認すると元の見逃しが構造完備の見た目で再発する。「条件に当たらず起動しなかった」も、その旨の明示返答が要る）。
3. **一撃の選定**: クラスタを「直すと最も多くの finding が連鎖的に消えるもの」で順位づけし、長期的に最もレバレッジの高い一撃を1つ挙げろ。

 **出自が「導線の死」のユニットには、`REVIEW.md`「導線を作る手段の優先順位」を付けて渡せ**（内容は正本のとおりで、ここに写しは持たない）。導線の死は毎ラウンド `[block]` 候補として出るのに対し、注記はその場で書けて赤にもならないため、優先順位を渡さないと注記が既定の修正手段になり、ラウンドを重ねるほど注記だけが積み上がる。
4. **ラベル付与と disposition**: 各**根本ユニット**に `REVIEW.md` のラベルを付けろ（`[block]`＝修正必須）。**生 finding 単独を `[block]` にするな**——根本ユニットに束ねるか、束ねられないものは `[suggest]` 以下に落とせ。さらに **`[suggest]`**（`[nit]` は対象外）の各ユニットに **`do-now` / `defer` の disposition** を付けろ——**実体基準は `REVIEW.md`「対応の判断」を正本とし、ここに再掲せず参照する**（既定 `do-now`／`defer` は構造的理由のみ／コスト感は理由にならない）。この disposition は実装を負う writer でなく **お前（grader）が下す**。
5. **安定キー**: 各 `[block]` および `[suggest]` 根本ユニットに「ファイルパス＋シンボル名（関数 / 型 / 設定キー）＋一文要約」のキーを付けろ（ラウンド間の突合と defer 台帳に使う）。

出力は「根本ユニットのリスト（ラベル・キー・一撃）＋根本フレーミング」。これが P3 の作業単位になる。

## P3: 修正（writer）

**P2 の根本ユニット単位で直せ。** 生 finding を1件ずつ潰すな。**フレーミングに同意できない・個別症状のままに見える場合は、自分で根本単位を切り直すな**——`P2 を新しい context の grader subagent で再起動`し、再集約された根本ユニットを受け取ってから修正に入れ。局所 patch でなく再設計を選んでよい。不要になったコード・抽象は同時に引け（削除・集約の可否は R1 の simplify 制約に従え——他所に無い情報〈事実・導出根拠・why〉を消すのは禁止、同一情報の単純反復は事実を消さない集約・再配置で畳むのが義務）。

`[block]` は必ず直す。**P2 grader が `do-now` とした `[suggest]` も直せ**——writer 裁量で `defer` に覆すな。disposition に異議があるなら自分で覆さず、`P2 を新しい context の grader subagent で再起動`して再判定させろ。`defer` された項目だけ最終報告に理由とともに記載する（実体基準は `REVIEW.md`「対応の判断」）。

## P4: 再採点と収束判定（writer が段取り、判定は grader）

やり直しの段取りは writer が担い、採点・突合の判断は全て grader に置く:

1. **writer**: CI を再実行（緑維持。赤なら P3 に戻って先に直せ）。
2. **writer**: P1 を新しい context でやり直せ——局所レビューの再実行と、各 grader subagent の新規起動。**前ラウンドの grader 出力・修正の経緯を P1 / P2 の subagent に渡すな**（渡すと前ラウンドのフレームにアンカーされ、再採点が追認になる）。続けて P2 grader を新しい context で再起動し、根本ユニットを再採点させろ。
3. **突合（機械）**: `python3` が無い環境では `python` に読み替えろ。**初回と 2 回目以降でコマンドが違う。**

   ```bash
   # 初回（N=1）——前ラウンドの記録は存在しないので引数は 1 つ
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/review-record.py .claude/review-rounds/round-1.json

   # 2 回目以降（N>=2）
   python3 ${CLAUDE_PLUGIN_ROOT}/scripts/review-record.py .claude/review-rounds/round-<N>.json .claude/review-rounds/round-<N-1>.json
   ```

   初回に `round-0.json` を渡すな——そのファイルを作る手順は無く、開けずに落ちる（空の記録を捏造して埋めるな）。**終了コード 2 は「記録が不正」で、1（阻害要因あり）と取り違えるな**——2 は記録を直して再実行する合図であって、非収束の判定ではない。新規 `[block]`・未解消・未対応の `do-now`・素材の未実施・scalar の増加を機械で拾う。**`defer`（構造的理由つき）で確定したキーの再出現を「新規」と扱わせないため、記録は前ラウンド分を残せ**（新 context の再採点は前ラウンドの受容判断を知らないので、台帳が無いと同じ提案が毎ラウンド再燃して収束しない）。再審してよいのは新しい根拠（新たな実害・出典）が付いたときだけ。
4. **writer（scalar 記録）**: 規模指標を記録の `scalars` に書け。文書・手順書を含むなら当該文書の行数、コードを含むなら `bash ${CLAUDE_PLUGIN_ROOT}/scripts/comment-ratio.sh <BASE>` の出力（手で数え直すな——物差しが揺れるとラウンド間の比較が成立しない）。**scalar はゲートにしない**——増加は R1 への入力であって、閾値で止めるものではない（測れるものをゲートにすると、規則が測れるものへ寄る）。

採点を writer の自己申告にするな（採点は P2 grader、突合は上の機械）。

**1ラウンド = P1 → P4 を1周**（P-R から差し戻されて P1 に戻った場合も1ラウンド）。判定後の分岐:

- 新規/残存 `[block]` > 0、**または P2 grader が `do-now` とした `[suggest]` が未対応のまま（新たな構造的 defer 理由の提示なし）** → P3 に戻り当該根本ユニットを直し、再度 P4。
- `[block]` = 0 かつ CI 緑 → P-R へ進め。

**ただし R1（最小性）と R2（ゼロベース再導出）は `[block]` = 0 を待つな。** この 2 つは**第 1 ラウンドで必ず走らせ**、以降は下記の再発火条件で回せ。P-R の位置に置いたままだと、欠陥の多い差分では永久に到達しない——**欠陥が多いほど枠自体の検査が遠ざかる**という逆向きの構造になる（実例: 5 ラウンド連続で新規 `[block]` が出続け、R1 が初めて走ったのは 6 ラウンド目。走った瞬間に「機構の規模が実態に対して大きい」と差し戻し、-1,193 行の削減になった）。

**R1 / R2 の再発火条件**（どれかに当たったら P-R を待たずに回す）:
- 差分が**機構を足した／置き換えた**（コメント・テストだけのラウンドは持ち越してよい）
- 差分が、P0-3 の制約が測られた対象を**削除・置換した**（＝**前提のドリフト**。制約を測った経路を差分自身が削れば前提は壊れるのに、それを検知する仕組みは他に無い）
- 累積差分の行数が前回 R1 実行時から **1.5 倍**を超えた

## P-R: 俯瞰（収束ゲート・完了宣言の前に必ず）

`[block]` が 0・CI 緑でも、それは収束の**必要条件にすぎない**。R1〜R4 を実行し全て通るまで収束を宣言するな。**R1・R2 は P4 で前倒し実行しているので、最後の実行以降に再発火条件（P4）へ当たっていなければその結果を使ってよい**——当たっているなら回し直せ。R3・R4 はここで必ず実行しろ。対象はループ開始時点からの**累積差分**（対象差分＝ `git diff <BASE>`）。R1・R3・R4 の subagent は `verdict: pass | redesign-needed | unverifiable` のいずれかと理由を返せ（R2 の verdict は後述の比較 grader が確定する。ただし `premise-invalid` だけは R2 subagent が直接返す）。1つでも `redesign-needed` なら非収束——P1 から新ラウンドに戻れ（`premise-invalid` は新ラウンドに回さず停止条件「前提不成立」へ直行）。

- **R1 冗長と最小性** — `model: opus`（設計判断なので上位モデル）: 累積差分が最小か。(a) 小修正が積み重なって本来1根本で済むものを症状パッチしていないか（場当たり累積）。(b) 単一の修正でも、他所から導ける内容を重複して述べていないか・より少ない記述（コード/文章）で同じ目的を運べる箇所がないか。**ただし simplify は制約付き**: 削ってよいのは削っても変更の *検証済みの値打ち*（コードなら挙動・テスト、設計/論拠文書なら *導出の再現性*）が落ちない分だけ。保護するかは**内容で判定しろ——「他所に無い情報（事実・導出根拠・why）を運ぶか」だけをキーにし、書き手の意図を判定に使うな**（意図は新 context から見えず、ループ自身が足した注記ほど「意図的」に見える）。他所に無い情報を運ぶ残余・caveat・why は消すな。**同一情報の反復は「あえての冗長」として自動保護しない**——複数箇所への配置自体が読み手の動線上必要と一文で言える場合（例: 破壊的コマンドの直前ごとの確認ガード）だけ保護し、そうでない単純反復・散在は、事実を消さない**集約・再配置（1節に抽出して各所から参照する形を含む）を simplify の義務**として指摘しろ。順序は固定で『必要な内容が在るか（＝**冷たい読み手**——文脈を持たない初見の第三者——が、書かれた指示・論拠だけから結論や手順を再現できるか。再現に要る前提・制約が省かれていないか）』→『在るとして最小か』。局所の simplification は `/simplify` が担当——ここで見るのは累積差分全体・文章の密度・抽象の重複である。**`do-now` で本ループ内に直した修正も累積差分の一部として必ず対象に含めろ——do-now を口実に症状パッチが積まれていないか、disposition（do-now/defer の判断）自体が場当たりでないかも見る。R1 は P-R の必須ゲートで、この場当たり検証を素通りするな。** **writer から scalar 推移（P4 手順4）が渡されたラウンドでは、相殺削除なき単調増の増分ごとに「他所に無い情報か」の正当化を要求しろ——正当化できない増分は集約・再配置の対象。**
- **R2 ゼロベース再導出** — `model: opus`（元の目的から理想解を独立設計するため深い推論が要る）、**完全隔離**: この subagent のプロンプトに一人称の自己禁止を書け——「お前はこの subagent。git・実装ファイル・コミット履歴を Read / Bash / Grep で読むことを自らに禁じる。渡された『元の目的』テキストだけから理想解を独立設計しろ」。**ただし独立設計に入る前に、まず目的そのものの実在を疑え**: 「この変更が解く問いは実在するか。既存機構で自明に満たされていないか（例: 1デプロイ＝1リポジトリならリポジトリ自体が識別子で、別途記録する問いは生じない）。要件が未確定のまま実装に踏み込んでいないか」。問いが実在しない・既存機構で自明・要件未確定と判断したら、理想解の設計に進まず `premise-invalid`（解くべき問いが立っていない）を返せ——`redesign-needed` と混同するな（routing が違う: `redesign-needed`＝新ラウンドで再設計、`premise-invalid`＝即ユーザー）。問いが実在するなら通常どおり理想解を独立設計しろ。**理想解には、目的の当事者が日常で回す動線（反復開発・運用・撤収）まで含めろ——成果物の一回の起動で設計を閉じるな**（当事者が毎日触るものの目的には、暗黙に「日常の回し方」が含まれる）。**subagent は独立設計（または「問いが立っていない」判定）だけを返す。突合と verdict 確定を writer がやるな**——独立設計と累積差分を別の比較 grader（`subagent_type: general-purpose` / `model: opus`）に渡し、本質的な食い違いの有無で verdict を確定させろ（writer≠grader を収束判定でも守る）。P0 で「元の目的」が `unverifiable` なら R2 も `unverifiable`。
- **R3 全体整合** — `model: sonnet`: 変更全体でファイル横断の整合（命名・規約・界面・docs 追従）。**R3 が見るのは diff が触れた範囲の整合**（変更したものが既存と揃っているか）。**既定・推奨の文書間一致**（変更が触れる文書群が読者に示す推奨ツール・手順・構成が単一に収束しているか——一次検出は P1 整合性観点、ここは最終ゲートの再確認）も含む。diff が触れていない横断リスクは R4 が見る。
- **R4 見えてないスコープ** — `model: sonnet`、**SRE・セキュリティ・データガバナンスの複数レンズ**で、diff の中でなく **diff が解こうとしている領域に潜む、変更が手を付けていない横断リスク**を探せ（観点は `REVIEW.md`「横断リスク観点」——レート制限・濫用耐性、PII の外部送信、可用性の外部結合、誤爆半径、移行退行の棚卸し（BASE 能力インベントリ）。列挙は代表例で限定ではない）。R1〜R3 が diff 内中心なのを補う。この grader には `REVIEW.md`「横断リスク観点」を **Read させて**従わせろ——移行退行の棚卸し（BASE 能力インベントリ）の中身・発火条件・BASE 比較の基準・明示返答の要求は正本のとおりで、ここに写しは持たない。棚卸しが発火する diff（移行・手順・開発フロー・UX）で「消えた能力」の有無の明示返答を欠いた出力は受け取るな（無言の省略を禁ずる）。**該当リスクは「この変更で導入・露呈したか」で扱いを分けろ**——この変更が導入・露呈させたものは本ループで回収（`redesign-needed`）、純粋に既存かつ無関係なものは最終報告に `[suggest]` 以下で surface するに留め `pass` を妨げない（`REVIEW.md`「別 Issue への先送りを既定にするな」の因果判定に従う）。

## 停止条件

**収束（不動点）で止めるのが正常終了。** 収束 ＝ **連続2ラウンド**（採点のゆらぎを吸収するため）で `review-record.py` が阻害要因を返さず・CI 緑・R1〜R4 が全て `pass`。**この道具が出す「阻害要因は無い」は収束の宣言ではない**——機械で見つかる範囲に何も無いという意味で、R1〜R4 の verdict と、記録に載らない懸念の有無は人が見る。**機械に合格を宣言させるな。不合格を宣言させろ。**「ラウンド」は P4 の定義（P1→P4 を1周）を使い、連続2ラウンドと下記の暴走ガードは**同一カウンタ**を参照する。残った指摘は「意図的に受容した設計判断」として理由を明示して終わる。**連鎖は `[nit]` を受容して再修正を止めることで断つ——検証を止めることではない（コスト感での検証スキップは `REVIEW.md`「対応の判断」で禁止）。**

収束以外は、カウントで黙って打ち切るのでなく**ユーザーに判断を仰げ**:

- **stuck**: 同じ `[block]` キーが修正後も残る／2ラウンド連続で残る → 修正困難な設計問題。
- **thrash**: 新規 `[block]` キーが出続け収束に向かわない → アプローチを疑う。
- **ゼロベース乖離**: R2 が `redesign-needed` で、再設計ラウンドを1回経ても解消しない → 機械では決められない設計の岐路。
- **前提のドリフト**: 差分が P0-3 の制約の根拠を壊した（制約を測った対象をこの PR 自身が削除・置換した）→ **事前登録の例外**（P0-4 の「以降変更しない」は目的テキストを凍結し、そこに書いた制約＝P0-3 で測った値も一緒に凍る。ここで解くのはその制約の部分だけで、目的そのものは動かすな）。制約を測り直し、R1 と R2 を回し直せ。事前登録の規律はゴールポストを動かさないためのもので、**作業自身が前提を反証した場合まで凍結する意味は無い**（凍結すると、消えた前提の上に作り込みが積み上がる）。測り直した制約と、前の制約が偽になった理由を最終報告に書け。
- **前提不成立**: R2 が `premise-invalid`（解くべき問いが立っていない＝PR の前提自体が誤り）を返したら、再設計ラウンドで回収しようとせずただちにユーザーに諮れ——diff 内の修正では回収できない結論に、ループ内の disposition 経路は無い。
- **独立検証不能**: R2 が `unverifiable`（元の目的を独立に取れない）→ pass でも redesign でもないので収束を宣言せずユーザーに諮れ。
- **未観測**: 主経路を動かせない（環境が無い・権限が無い・実機が要る）→ `unobserved` として収束を宣言せずユーザーに諮れ。**「静的レビューを何ラウンド重ねたか」で観測の欠落を埋めるな**——読む役をいくら増やしても、実行して初めて現れる欠陥は現れない。誰がどこで動かすかを決めるのは人の判断なので、ループ内で `pass` に丸めるな。
- **暴走ガード（具体上限）**: 総ラウンドが **5** を超えたら「収束せず」として必ず停止し報告しろ。これは収束前の打ち切りでなく、非収束を検知する上限。

## 最終報告

**報告は利用者の言語で書け。** この手順書が日本語であることは、報告を日本語にする理由にならない——判断を下すのは人で、読めない言語の報告では下せない。統合後の最終報告に次を必ず含めろ（欠けた報告は収束とみなさない）:

- 各根本ユニットの「ラベル・対応内容／対応不要の理由」
- **R1・R2・R3・R4 それぞれの `verdict` と理由**
- **grader subagent の生出力（根本ユニットのキー集合）**・grader 再実行の回数・**「元の目的」の出典（①②③）**・基準点 `BASE` の SHA
- **主経路の実行観測**: 何をどこで動かし、何を観測したか（観測できなかったなら理由）。**「テストが緑」を観測として書くな**——本番と同じ経路を流れた実物だけを書け
- **新設機構の棚卸し**: この差分が導入する機構・配管（ビルド設定・initContainer・環境変数・CI ジョブ・テンプレートのノブ・スクリプト等）を、どの grader も指摘しなかったものも含め判定抜きで一覧する。自動ゲートが全て緑でも「この機構は存在すべきか」は機械判定の外にあり、短い一覧が見えていれば人間が目利きで気づける——その導線として開示する（一覧に留め、良し悪しの判定は書くな）

subagent の出力が報告の言語と違っても揃えろ。コード識別子・ファイルパス・エラーメッセージ等の固有名詞はそのままでよい。
