## 位置づけ（一家の分業）

差分が無いところから候補を掘るのが本ループ。掘った候補の採用と実装は人がやる。リアーキ級候補の見立てを一次情報で校正するのは `/research-loop`。1 回の実行の中でもラウンドを回す——**1 ラウンド＝P1→P3 を 1 周**で、新しい目（新規コンテキストの scout）で掘り直し、新規候補が出なくなるまで（理論的飽和）続ける。回数を数えて「N 回やったから網羅した」と言うな——飽和だけが掘り尽くしの証拠である。

**このループは提案のみを行い、リポジトリへの変更を一切適用しない。** frontmatter に編集道具が無いのは設計だが、Bash とサブエージェントがある以上、変更禁止は構成だけでは保証されない。Bash は読み取り専用の計器（lint・型検査・未使用検出・テスト実行・git 履歴）としてのみ使え。scout・refuter・cartographer・rederiver のプロンプトにも一人称の自己禁止を書け——「お前はこのサブエージェント。ファイルの作成・編集・削除を自らに禁じる」。保証を与えるのは自制でも frontmatter でもなく、下の前後突合である。提案の採否・実装・固定化・記録はすべて依頼者が行う。issue 起票も本ループはしない。成果物は最終報告だけである。

## 依存

実行時のハード依存は無い——スクリプト・追加プラグイン・カスタムエージェント定義を使わず、この本文だけで走る。同一プラグイン内の正本参照は 1 箇所だけ: ライブラリ級判定の**出典の格の全階層**は `research-loop` P1 を参照する（ただし判定に効く規則——公式一次まで——は本文に書いてあるので、参照が切れても走る）。`/research-loop` への「委譲」は呼び出しではなく提案文であり、委譲するか決めるのは依頼者である。計器は在れば使い、無ければ「試せなかった計器」として報告する——導入を手順に含めるな。**欠陥（バグ）探しは本ループの守備範囲外**——欠陥は既存の欠陥レビューの領分で、ここで再実装するな。

## 変更禁止の機械確認

走査を始める前に `git status --porcelain` と `git stash list` を記録し、報告の直前に再取得して突合しろ。差があれば、**自分が汚した分を元に戻せ——これがこのループで許される唯一の書き込みであり**、何をどう戻したかを報告に書け。計器の実行が生成物（キャッシュ・カバレッジファイル等）を作った場合の削除も同じ扱い。追跡対象ファイルの内容を意図して変える操作は、依頼者の指示なしに行うな。**無変化（または復旧済み）の確認結果は最終報告の必須欄**——確認せずに「変更していない」と書くな。

## 厚みの三段（最初に決める）

| 段 | 使う時 | 走らせるもの |
|---|---|---|
| **軽量** | 「ここを特に見て」のスポット確認・下調べ | P0-1・P0-2（指定範囲に限って簡略可）・**P0-3（必須）**＋指定レンズの P1 と、出た候補への refuter。1 ラウンドで打ち切り、P3 の束ね・P4・cartographer なし |
| **標準（既定）** | 通常の走査 | P0〜P4 全部（計器→レンズ別 scout→敵対検証→統合→飽和まで反復＋被覆ゲート） |
| **重厚** | 構造への疑いがある・半年に一度の棚卸し | 標準＋独立再導出＋模範照合 |

- 軽量への降格は依頼者が明示に指定した場合のみ（「ここだけ見て」というスポット指定は軽量指定を兼ねる。ただし候補が構造起因を示唆したら昇格を提案しろ）。昇格は自律で自由——複数レンズの候補が同じ構造起因を示唆したら重厚へ上げろ。
- **P0-3 はどの段でも省くな**——飛ばした走査は必ず決着済みの蒸し返しをやる（反パターン参照）。省いてよいのは P0-4 までである。
- 段は P0 の冒頭で固定し、**どの段か・誰が決めたか（依頼者指定／既定）・根拠**を記録して最終報告に載せろ。「時間がないから」「十分そうだから」は根拠ではない。
- 省略した機構は最終報告に明示しろ。

## 実行の効率（依存が無ければ同時に走らせろ）

直列を許すのは依存があるときだけ。原理は「安い網を先に、高い針を後に・反証で早く刈る・差分だけ再検証」。具体的に並走できるもの:

- **P0-3（先行議論の突合）は検索作業**なのでサブエージェントに切り出し、P0 の他項目と並走させてよい。
- **P1 第 1 層（計器）は P0-1（面積×レンズの固定）だけに依存する**——P0-2〜4 の完了を待たずに回し始めてよい。
- **scout はレンズごとに並行起動**（P1）。さらに **返ってきた scout の候補から順に refuter へ回せ**——全レンズの返答を待ち合わせるな。待ち合わせが要るのは P3 の束ね（全判定が揃ってから）だけである。
- **cartographer は入力が P0 だけ**（面積×レンズとドメイン要約。scout の所見は遮断が要件）なので、起動自体はループ序盤に先行してよい。既走査範囲との突合だけを収束ゲート時に行え。
- 重厚の **rederiver（入力は P0-2 要約のみ）と模範照合（入力は対象と web のみ）も P1 と並走できる**——どちらも scout の所見からの隔離がそもそも要件なので、並走しても壊れない。
- **抜き取り検査と cartographer の突合は互いに独立**——新規ゼロのラウンド後、同時に走らせろ。

## P0: 断面の固定（prospector＝このループを回すセッション）

1. **範囲を「面積×レンズ」で固定しろ。** 面積はコードに限らない——CI 定義・ビルド・開発環境・文書もリポジトリの一部で、同じレンズが当たる。依頼者が指定しなければ、リポジトリ構成から候補範囲を挙げて確認を取れ。全体×全レンズは禁止——有界なのは面積とレンズの積である（全体×1 レンズ、1 モジュール×全レンズは可）。全体が指定されたらレンズを 1 つに絞れ——どのレンズかは依頼者に確認し、指定がなければ P0-4 のホットスポット信号と計器の出力量から選び、選定理由を報告に書け。
2. **ドメイン地図**: 対象リポジトリの正典（README・docs の索引・戦略/設計文書・ADR 索引）を読み、製品の目的・制約・モジュール構成を 3〜10 行に要約しろ。**要約の出典は正典に限れ——実装の読み取りや prospector の記憶で埋めるな**（重厚の rederiver はこの要約だけを入力にするので、実装に寄って狭まると再導出が追認になる）。正典から再構成しきれず補った箇所があるなら、別コンテキストのサブエージェントにその要約をレビューさせ（実装に都合よく狭めていないか）、合格分だけ rederiver へ渡せ。正典から取れないなら、それ自体を候補（文書の欠落）として記録し、rederiver は `unverifiable` として扱え。
3. **先行議論の突合**: 対象範囲に関わる ADR・closed PR・決定の記録を洗え。**決着済みの論点を候補として蒸し返すな。** 異議があるなら「再開の提案」として新証拠付きで別立てにしろ。洗えなかったら「確認できなかった」と報告に書け——未確認を「重複なし」と書くな。
4. **ホットスポット信号**: `git log` の変更頻度×変更規模で深読みの優先順位を付けろ。判断が要る候補ほど、よく触られる場所を優先する（誰も触らない汚さは直す価値が低い）。ただし機械的に安全が示せる候補（未使用・重複の削除等）は温度に関係なく全域が対象——エージェントはリポジトリ全体を読むので、冷たい場所の悪い見本も将来の編集の教師データになる。

## P1: 発見（層化走査——全部を深読みしない）

**第 1 層（計器・prospector）**: 対象範囲に読み取り専用の計器を当てろ——リポジトリに既にある lint・型検査・テスト、未使用コード/依存の検出、重複検出、文書のリンク・パス実在、git 履歴の信号。リポジトリに導入されていない計器の一時実行は、**作業ツリーに痕跡を残さない方法（使い捨て実行・一時ディレクトリ指定・lock を更新しない実行）に限れ**。依存の追加や lock の更新を要する計器は諦め、「試せなかった計器」として報告に書け。計器の出力は生データであって候補ではない——第 2 層の入力にしろ。

**第 2 層（レンズ別 scout サブエージェント・`model: sonnet`・所見非共有）**: レンズごとに独立の scout を並行起動しろ。互いの出力を渡すな（同じフレームに固定されて別の層を拾えなくなる）。レンズ:

- **減らす**: 死んだコード・重複・過剰な抽象・自前実装で既製の枯れた部品に置換できるもの・退役すべき文書（古い文書は読まれて実装の誤りとして再生産される）
- **縛りの余地**: **人とエージェントの注意力で守られているものを、決定的な機械チェックへ移せる点**。対象は規約文書・レビューの反復指摘だけでなく、エージェントへの指示（CLAUDE.md・エージェント向け規約）で毎回判断させている規律も含む——エージェントに確率的に守らせているものを lint 規則・CI 検査・型・スキーマ・DB 制約・フックが決定的に止められるなら、それが候補である。判断する主体（人／エージェント）が消えて検査だけが残る形が上がりで、優先順位は「表現不能にする＞機械が止める＞文書で頼む」
- **構造を正す**: 依存の向きの乱れ・境界の漏れ・同じ概念の複数実装・正典と実装の不整合
- **時代に合わせる**: 変化した環境に置いて行かれたもの——EOL・サポート切れの処理系や依存、非推奨 API の使用、現行の言語・フレームワークでは不要になった回避策や古い書き方、老朽化した CI 定義・開発環境。陳腐化の検出には読み取り専用の計器（outdated 系・非推奨警告）が使える

このレンズ一覧は思いつきではなく、**ソフトウェア保守の標準分類（ISO/IEC/IEEE 14764）に係留してある**——適応保守＝時代に合わせる、完全化保守＝減らす・構造を正す、予防保守＝縛りの余地。是正保守（欠陥修正）は意図的に守備範囲外（「依存」参照）、追加保守（機能追加）は改善ではなく開発の領分。レンズを足す・削る提案にはこの分類との対応を添えろ——対応の無いレンズ案は、新しい着想か守備範囲外への逸脱かのどちらかで、どちらかを判定してから足せ。レンズ一覧の完全性や係留先の分類そのものに疑いが出たら、それは走査ではなく調査の問いである——本ループの中で解こうとせず、`/research-loop` の問いとして立てることを提案しろ。

scout への指示に含めろ:

- 候補には根拠（ファイルパス:行）・期待効果・確度を付けろ。**確度の語彙は固定（増やすな）**: **確実**＝計器の出力で機械的に示せる／**有力**＝リポジトリの実態か一次情報で裏取り済み／**仮説**＝未確認の前提を含む。
- 内包知識（このパターンにはこの定石があるはず）は仮説の生成に自由に使ってよいが、**判定の根拠に使うな**——判定は計器の出力・リポジトリの実態・一次情報で裏取りしろ。
- **各レンズについて「候補あり（列挙）」か「このレンズ・この面積では見つからなかった」のどちらかを必ず明示して返せ。無言で項を落とすな。** prospector は指示したレンズ数と返答のあったレンズ数を突合しろ——返答の欠落を「見つからなかった」と読むな。

**読解の盲点（scout と refuter の双方に課せ）**: 動的な結び付き（文字列ベースのディスパッチ・リフレクション・DI・設定駆動の読み込み）、環境の実態（実際に入っている版・実挙動）、並行・時間の挙動は、読むだけでは確定できない。これらに当たる主張は断定を禁じ、「未確認の前提」を明記させろ。読み間違いは静かで、実行の失敗は赤く光る——静かな側にいる自覚を持て。

## P2: 敵対検証（refuter サブエージェント・`model: opus`）

候補ごとに refuter を**新しいコンテキスト**で起動しろ。入力は当該候補の本文・根拠（パス:行）・その根拠が指すファイルの内容だけにし、**他の候補・prospector の統合見立て・前ラウンドの経緯・他レンズの所見を渡すな**（渡すと候補群のフレームに乗り、反証が体裁になる）。「直す価値がない・壊れる・既に決定済み・読み違いだ」の側から本気で反証させろ。

**判定語彙（固定・増やすな）**: **推奨** / **条件付き**（成立条件を明記） / **棄却** / **検証不能**（裏取りに要る一次情報・実行環境・実挙動に到達できない）。**検証不能を棄却に丸めるな**——未確認は否定ではない。検証不能の候補は「何が確認できれば判定できるか」を添えて、棄却の付録とは別枠で最終報告に残せ。

- **件数突合**: refuter へ渡した候補数と返った判定数を突合しろ。判定が返っていない候補は当該分だけ refuter を再起動し、明示の判定を得てから P3 に入れ。**判定の欠落を「指摘なし」と読むな。**
- **refuter を都合よく使うな**: 同一ラウンドで refuter を回し直して有利な判定を採るな（やり直しは次ラウンドのみ）。再判定は新しい根拠（計器の出力・一次情報・リポジトリの実態）を添えたときだけ請求できる——「納得できない」は根拠ではない。再判定が 1 回目と食い違ったら打ち切り、両方の判定と根拠を並記して「判定不一致」として報告しろ。多数決のために 3 回目を回すな。回し直した回数と生の判定は最終報告に書け。
- **ライブラリ級**（依存の追加・置換を含む候補）は追加で: 保守状況・互換性・ライセンスを一次情報で確認しろ。出典の格は `/research-loop` P1 の階層に従え——**判定の根拠にできるのはベンダー/プロジェクト公式一次まで**。あわせて死んだ試み（アーカイブ済み・撤回・事業転換）も探せ——内包知識の「定番」は死んでいることがある。人気・有名・採用実績の多さを根拠に書くな——メカニズムと適用条件で語れ。

## P3: 統合と一撃（prospector）

1. **安定キー**: 各候補に「ファイルパス＋シンボル名＋一文要約」のキーを付けろ。ラウンド間の新規/既出の判定はこのキーの突合で行い、印象で数えるな。**突合の相手は棄却・検証不能も含む全既出集合**——採用候補だけと突き合わせると、棄却された候補が毎ラウンド再燃して飽和しない。
2. **出自で束ねろ**: 複数の候補が同じ根本（同じ抽象の不在・同じ境界の欠落・同じ誤った前提）から出ていないか。症状を個別に並べず、根本を 1 つの候補に統合しろ。統合で生まれた根本候補には、束ねた症状候補のキー一覧を添えて新しいキーを与え、**新規として refuter に回せ**。束ねられた症状候補は既出集合に「統合済み」の印付きで残し、再提示するな。
3. **一撃の選定**: 「直すと最も多くの候補が連鎖して消えるもの」を 1 つ選べ。
4. **束ねの確定は refuter に通せ**: 束ねた根本と一撃の候補を新しいコンテキストの refuter に渡し、「この束ねは症状の寄せ集めでないか・別の根本ではないか・一撃は派生の方を指していないか」を反証させろ。**prospector が自分の統合を自分で確定するな**——個別候補を採点者に通しておいて、それを束ねた最も重い主張だけ無検査で出すのは分離の抜け穴である。
5. **革命級の条件**: 一撃が構造・方式の変更（リアーキ級）に達するのは、(a) 束ねた根本が複数レンズにまたがる、かつ (b) 重厚の独立再導出が同じ構造を指す、の**両方が揃ったときだけ**。1 実行 1 件まで。仮説マーク必須。標準段は (b) を満たせないので革命級を宣言できない——束ねが複数レンズにまたがった時点で重厚へ昇格して rederiver を走らせるか、「重厚での再走査を要する仮説」として報告するかを選べ。**リアーキ級の当否は本ループで判断しない**——`/research-loop` へ次の 4 点を揃えて委譲を提案しろ: (a) 何を決めるための調査かの**問い一文**、(b) 摩擦の証拠（現行構成と戦っている箇所の列挙・行数・箇所数）から立てた**番号付きの制約**（各制約に「どう測ったか」を 1 行添えろ）、(c) 外部に照合可能な**主張のリスト**（「◯◯の方が適している」は判断でなく主張として書き出せ）、(d) P0-3 で洗った先行議論の結果。揃えずに渡すと、受け手が問いと制約を自分で書き起こすことになり、調査の独立性が入口で落ちる。「〜の方が新しい」は候補の資格がない。資格は摩擦の証拠だけが与える。

## P4: ラウンドと収束判定

**1 ラウンド＝P1→P3 を 1 周。** 2 ラウンド目以降の規律:

- scout は毎ラウンド**新しいコンテキスト**で起動しろ。前ラウンドの候補・経緯を渡すな（渡すと前ラウンドのフレームに固定され、掘り直しが追認になる）。prospector 側で安定キーにより新規だけを拾え。
- refuter は**新規の候補だけ**に、毎回新しいコンテキストで回せ。確定済みの判定を引き直すな（下の抜き取り検査だけが例外）。
- 計器（P1 第 1 層）は決定的なので再実行不要。

**収束（理論的飽和）で止めるのが正常終了**: 連続 2 ラウンドで新規候補ゼロ、かつ抜き取り検査を通過し、cartographer が `pass`。

- **飽和の抜き取り検査**: 新規候補ゼロのラウンドでは、確定済みの判定（棄却・検証不能を含む）から無作為に 1〜2 割を抜き、**新しいコンテキストの refuter** に引き直させろ。1 件でも判定が覆ったら飽和ではない——通常ラウンドに戻れ。新規ゼロが証明するのは「同じ目で見て出なかった」ことだけで、判定のゆらぎは別に測らないと見えない。
- **cartographer（`model: opus`・scout の所見を遮断）**: 起動は序盤に先行してよいが（「実行の効率」参照）、**突合は新規ゼロのラウンドの後に行え**（盲点を足して回した追加ラウンドが再び新規ゼロになるたびに、もう一度）。P0 の面積×レンズとドメイン要約だけを渡し、「この範囲を完全に走査するために要る観点・見るべき場所」を独立に列挙させ、実際に scout が見た範囲との差分＝盲点を prospector が突合しろ。判定は `verdict: pass | redesign-needed | unverifiable` と理由で返させろ（増やすな）——列挙された観点・場所がすべて既走査範囲に含まれるなら `pass`、盲点が候補の有無を変えうるなら `redesign-needed`（盲点を観点に足して新ラウンドへ）、P0-2 の要約が正典から再構成できておらず判定不能なら `unverifiable`（pass でも redesign でもないので、飽和を宣言せず依頼者に諮れ）。**これ無しで「掘り尽くした」を名乗るな**——飽和は「同じ目で見て出なくなった」しか証明せず、目の欠けは検出できない。
- **暴走ガード**: 総ラウンドが 6 に達した時点（6 ラウンド目の完了時）で、飽和していなくても停止し、「飽和せず」と残った観点を報告しろ。cartographer が足した観点による追加ラウンドもこの数に含める。
- **機械に「リポジトリは健全」を宣言させるな。** 飽和が宣言できるのは「この面積×レンズ×この目では、これ以上出なかった」まで。範囲の外と目の外については何も言えない。

## 重厚のみ: 独立再導出と模範照合

- **rederiver（`model: opus`・実装を遮断）**: 一人称の自己禁止を書け——「お前はこのサブエージェント。実装ファイル・コミット履歴を読むこと、ファイルの作成・編集・削除を自らに禁じる。渡された目的と制約（P0-2 のドメイン要約）だけから、あるべきモジュール構成と仕組みを独立導出しろ」。実構成との構造差（何を固定し何を派生と見るか・継ぎ目の位置・何が存在しないか）が候補の種。表現の違いは差ではない。判定は cartographer と同じ `verdict: pass | redesign-needed | unverifiable` の語彙で返させろ。
- **模範照合（比較 scout・`model: sonnet`・web 可・P1 の所見を渡すな）**: 対象と同種の成熟した一線級リポジトリ・製品を 2〜3 特定し、対象範囲に対応する箇所の作りを読み、差を**メカニズム＋適用条件**で報告させろ。**「◯◯社・有名 OSS がやっているから」は根拠として禁止**——彼らの解は彼らの制約（規模・人数・要件）の関数であり、その制約がこちらで成立するかを必ず添えろ。規模の合わない模倣は候補ではなく事故の種。参照した模範と読んだ箇所は報告に書け（次回の走査が再利用できる）。

## 提案の重さ（4 段）

| 重さ | 例 | 報告に必ず添えるもの |
|---|---|---|
| **機械検証可能・小** | 未使用依存の削除、既依存の機能での自前実装置換 | 機械の根拠（計器の出力） |
| **振る舞いに触れる・中** | 内部実装の是正・境界の引き直し（依存追加なし） | 影響範囲の列挙・検証計画 |
| **ライブラリ級** | 新しい依存の追加・置換 | 一次情報の確認結果・移行の当たり |
| **リアーキ級** | 構成・方式の変更 | 摩擦の証拠・research-loop への委譲提案（P3-5 の 4 点） |

## 最終報告（欠けたら未完成）

**報告は利用者の言語で書け。** この手順書が日本語であることは、報告を日本語にする理由にならない——判断を下すのは人で、読めない言語の報告では下せない。サブエージェントの出力が報告の言語と違っても揃えろ（ファイルパス・識別子等の固有名詞はそのままでよい）。次を必ず含めろ:

- 厚みの段・誰が決めたか・省略した機構の明示
- **収束状態**: ラウンド数・連続何ラウンド新規ゼロか・抜き取り検査の結果・cartographer（重厚なら rederiver も）の判定と理由（生出力を転記しろ。要約で丸めるな）・上限で停止したならその旨と残った観点
- **見た範囲の明示**（面積×レンズ×層）と、**見ていない範囲の列挙**（P4 末尾の規律に従う）。候補ゼロは「この範囲・このレンズでは見つからなかった」とだけ書け——空振りは失敗ではなく、被覆が広がった記録である
- 候補一覧: 重さ・確度・根拠（パス:行）・期待効果・**検証計画**（採用時に何で安全を確かめるか。「検証済み」を名乗るな——読むだけのループに安全の立証はできない）・**固定化案**（この改善は機械チェックに変換できるか。新設する検査の提案には「違反例を 1 つ作って赤くなることを確認してから信じる」を採用時の条件として一言添えろ——何にもマッチしない検査は緑のまま居座る）
- **検証不能の候補**と、判定に要る確認手段（棄却の付録とは別枠）
- 一撃（あれば）と、その出自の束
- refuter の生の判定（要約で丸めるな）・回し直しの回数・棄却された候補と理由（付録）
- 変更禁止の機械確認の結果
- 件数を成果として書くな

## 反パターン（自分の走査に見つけたら、走査のやり方をその場で正せ）

- **変更を適用する**（1 行でも）。→ 提案に差分例を含めるのは可。当てるのは依頼者。
- **一覧の水増し**: 弱い候補で件数を稼ぐ。refuter を通らないものを「参考」として滑り込ませる。
- **権威の数え上げ**: 「有名」「一線級も使っている」を根拠にする。→ メカニズム＋適用条件。
- **決着済みの蒸し返し**（P0-3 を飛ばした走査は必ずこれをやる）。
- **さぼり降格**: 走査を減らすために実行者が自分で軽量を選ぶ。→ 降格は依頼者指定のみ・既定は標準・構造起因が示唆されたら昇格。
- **温度の誤用**: 誰も触らない場所の判断系候補を上位に並べる（博物館の掃除）。逆に、機械的に安全な候補を温度を理由に見送る。
- **被覆の外を語る**: 「見ていない範囲は健全」。

## 型への還流（ループの後に一度）

依頼者が候補を却下したら理由を聞き、**この skill 本文への追記案（却下基準・レンズ・反パターンの修正）を差分の形で報告に含めろ。** 本ループは自分の改善も提案止まり——適用するのは依頼者である。本ループが依頼者から引き受けるのは走査までで、判断は引き受けない。
