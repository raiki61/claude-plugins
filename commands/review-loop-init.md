name: review-loop-init
description: review-loop が使うレビュー観点の正本 REVIEW.md を、対象リポジトリのルートに配置して固有欄を埋める。/review-loop を初めて使う前に一度だけ実行する。
allowed-tools: Bash, Read, Write, Edit, Grep, Glob
---

`/review-loop` の観点の正本は**レビュー対象リポジトリのルートの `REVIEW.md`**。プラグインが配るのは言語非依存のテンプレートなので、固有欄をこのリポジトリの実物で埋めるところまでをやる。

1. リポジトリルートに `REVIEW.md` があるか確認しろ。**あれば上書きするな**——テンプレートとの差分を示し、合流するか既存のまま使うかをユーザーに聞け。
2. 無ければ `${CLAUDE_PLUGIN_ROOT}/templates/REVIEW.md` をリポジトリルートへ `REVIEW.md` としてコピーしろ。
3. 「プロジェクト固有の規約」節の `＜＞` 欄を、**このリポジトリを実際に調べて**埋めろ。**推測で埋めるな**——調べて見つからなかった項目は「該当なし（探した先: ...）」と書け。空欄で残すと、後で読む grader が「無い」のか「まだ書いていない」のか区別できない。
   - **アーキテクチャ境界**: 依存表・モジュール境界を定義した文書を探せ（README / docs / CONTRIBUTING / `import-linter`・eslint boundaries 等の設定ファイル）。文書が無く設定ファイルだけある場合は設定ファイルを正本として指せ
   - **言語・フレームワーク・lint**: パッケージマニフェストと lint / formatter の設定から読め。テストの既定（自動 async モード等、書かなくてよい約束）も拾え
   - **標準機構**: i18n・設定読み込み・エラー分類・DI・ロギングの実体を Grep で特定し、**モジュールパスと関数 / クラス名まで**書け（名前が無いと整合性 grader が近傍からの推測に落ちる）
   - **機械強制されている検査**: CI 定義と pre-commit を読み、**既に赤くなる**検査を列挙しろ（設計観点はこれを「緑の確認だけ」に留める。列挙が漏れると人と LLM が二重に同じ検査をやる）
   - **固有の構成要素**: この変更が波及しうる独自の要素（オーケストレータ・外部サービス・モジュール分割）
4. `.claude/review-rounds/` を作り、`.gitignore` に追記しろ（ラウンド記録は連続 2 ラウンドの突合に使う作業ファイル）。**チームで記録を証跡として残す方針なら追記せず**、その旨をユーザーに伝えて判断を仰げ。
5. 埋めた内容を要約して報告しろ。調べても確定できず暫定で書いた項目は **「要確認」と明記**しろ。
