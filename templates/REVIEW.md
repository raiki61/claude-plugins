# レビュー規約

このリポジトリのコードレビュー（人間・自動を問わず）が従う共通規約。

## 文体

- 日本語・です / ます調。断定を避ける（「〜のように見受けられます」「〜かもしれません」）。
- 実装者へのリスペクトを込めて簡潔に。1 指摘あたり最大 3 行。

## 指摘ラベル

各指摘に次のいずれかを付ける。

- `[block]`: 修正必須。次を全て満たすもの — ①事実確認済み（憶測でなくコードや挙動で特定）②影響が具体的（機能破壊・セキュリティ・データ破損・性能劣化、または習熟した開発者が実際に誤読した／導線が死んでいると一文で書ける）③このスコープで直すべき（別 Issue 追跡では不十分）。可読性経路（誤読・導線）で `[block]` にするのは「どう読み違えるかを具体例で再現でき、命名／構造のどの要素が誤読を生むか特定できる」場合のみ。単独の主観的『読みにくい』は `[suggest]` 据え置き
- `[suggest]`: 提案（より良い実装があるが必須ではない）
- `[nit]`: 軽微（スタイル・命名の好み）
- `[question]`: 質問（意図の確認）
- `[info]`: 情報共有（指摘ではない）

確信度が低い指摘・PR スコープ外の既存問題は `[suggest]` 以下に留める。

## 検証の原理（個別観点の上位規範）

個別観点の多く（手順トレース観点、コード衛生観点の「検証機構の fail-open」等）は、この2つの原理の適用例である。適用例として列挙されていない形で原理に反する箇所を見つけたら、観点に無くても指摘してよい。

- **読むより動かす**: 実行できる成果物（手順書・スクリプト・検証ゲート・テスト）は、読んで妥当性を推論するのでなく、動かした結果で確かめる。読解と実行結果が食い違えば実行結果が正。動かして赤・失敗を一度も見ていない保護機構を「機能している」と扱わない
- **保護機構には「どう騙すか」を問う**: 検査・ゲート・ガードは「正しく書けているか」でなく「どうすればこれを黙って無力化できるか、どんな入力・状態なら嘘の合格を出すか」を先に問う。この問いの答えが既存の観点に無ければ、それ自体が指摘であり、新しい観点の候補でもある（「この規約の育て方」参照）

## 全レビュー共通の観点

- PR の目的に沿った実装か。before / after の差分が妥当か
- セキュリティ: 詳細な脆弱性検査は公式 `/security-review` に委ねる。レビューでは明白な入力検証漏れ・機微データ漏れの見落としに留める
- レビュー対象に依存するファイルへの波及影響
- テスト追加の要否
- **開発者導線の整合性**: README.md・docs/・.env.sample・エラーメッセージ・ディレクトリ構造が、初見の開発者を迷わせないか
- コードスタイルが他ファイルと一貫しているか
- **指摘の出自を問う**: 対応しない指摘でも「なぜ生まれたか」を分析する。読みにくさ・命名・導線の死が原因なら、ロジックが正しくても可読性側を直す。習熟した開発者が誤読する箇所は、将来の他の開発者も誤読する
- **導線を作る手段の優先順位**: 導線の死を直すとき、①構造（分割・移動・**型で表して不正な状態を作れなくする**）②命名 ③**仕組みで縛る**（違反したらテスト・型検査・lint が赤くなる形にし、テスト名で意図を運ぶ）④注記（WHY コメント・docstring）の順で選ぶ。**注記は最後の手段**——その場で書けて何も赤くならないため既定の修正手段になりやすく、放置すると注記だけが積み上がって「読む量は増えたが導線は死んだまま」になる。①〜③で作れない理由を一文で言えないなら、④だけで済ませない。ただし**③で既存の検査が恒真になるなら、それは仕組みでなく検査の破壊**——構造化した結果いずれかのテストが必ず緑になるなら、そのテストは削るか、構造化をやめて検査を残す（片方を選び、両方残すな）
- **別 Issue への先送りを既定にするな**: 問題の出自（因果）で判定する。**この PR が導入・露呈させた問題は、同じ PR で回収する**（コンテキストが最も新鮮・別 Issue は死蔵されがち・先送りは未完の PR を残す）。別 Issue が妥当なのは「既存かつこの変更と無関係」な問題だけ。`[block]` 条件③（このスコープで直すべき）はこの因果で判定する。なお無関係な大改善を `[suggest]` で surface するのは別軸でよい
- **対応の判断（今直すか別 Issue か）**: 既定は **do-now**（後回しは負債が腐り、次の実装者が同じ轍を踏む）。`[suggest]` を別 Issue / 別 PR へ defer してよいのは「未解決の設計判断」「スコープ / サブシステムが別」「可逆性が低く合意を要する」の構造的理由を1つ名指しできる時だけ。**判定者の都合（コスト・面倒・「終わらない」）で、対応の先送りも検証（再採点・再レビュー）の省略も正当化するな**——コスト感でなく構造的理由のみで判定し、その判定は作業を負う writer でなく grader が下す（利益相反を断つ）。do-now で直したものも R1（場当たり累積）の検証を通す。

## 出力の構成

- 「修正や確認が必要な箇所」と「修正は不要だが懸念がある箇所」にセクション分けする
- 各指摘にファイルパスと行番号を明示する

## 実装観点 ①④

- 言語・フレームワーク・lint の規約との整合（正本は「プロジェクト固有の規約」節が指すファイル）
- この diff で存在理由を失ったコード・抽象化の削除漏れ
- より少ないコード・少ない抽象化で同じ目的を達成できないか
- 既存パターン・命名との整合。新しいパターンを持ち込んでいないか
- 初見の開発者が処理の意図と流れを迷わず追えるか

## 設計観点 ①

- アーキテクチャ境界（レイヤー依存・モジュール境界）の違反。依存表の正本は「プロジェクト固有の規約」節が指すファイルを Read して照らす。**規約を機械強制している仕組み（lint ルール・CI ジョブ）がある層は、その緑を確認するだけにする**——既に赤くなる検査を人手や LLM で二重にやっても検出は増えない。違反を挙げるときは、その違反が BASE 時点で既に在ったかを確認し、この変更が入れたものか既存かを切り分ける
- **抽象の所有権**: 差分が足したインタフェース・ABC・Port を、**使う側と実装側のどちらが定義しているか**。実装側が定義しているなら依存性逆転になっていない。あわせて、その抽象が**縛れていない部分**（`Any` を返す・戻り値の形を規定していない等）を挙げる——名前だけ縛って形を縛らない抽象は、実際に壊れやすい箇所を素通しにする
- **詳細の染み出し**: 外側の詳細（プロトコルの語彙・ワイヤ形式・表示形式・下流ランタイムの制約）が、内側の層の型やモデルにどこまで入り込んでいるか。境界で変換すべきものが内側に居座っていないか
- 場当たり的な対処でなく根本原因の解決になっているか
- 同じ問題が他にもあり、まとめて解決すべきではないか
- 「プロジェクト固有の規約」節に挙げた固有の構成要素への影響
- この変更をきっかけに最もレバレッジの高い改善を1つだけ挙げる（既存コード含む・PR スコープ外でもよい）

## 整合性観点（リポジトリ横断） ②④

- 宣言–使用の整合性: 宣言的変更（DDL・関数シグネチャ・型定義・設定スキーマ・Literal 列挙等）の使用箇所を Grep で特定し、過不足なく整合しているか。リポジトリ内 Grep で見つからない＝未定義と即断せず、外部ランタイム（フレームワーク・OS・CI 等）が提供する名前の可能性を先に検討する
- 標準機構の迂回: 迂回はシンボルを未定義にしないため、宣言–使用の整合（壊れた契約）では捕捉できない。diff が触る近傍ファイルを Grep / Read してそれらが標準で使っている機構を特定し（対象は diff のドメインで決める。「プロジェクト固有の規約」節の標準機構一覧を先に読み、そこに挙がっていない機構も近傍から拾う——一覧は出発点で、限定列挙ではない）、diff が同種の処理をその機構を経由せず手書きで再実装・直書きしている箇所を、対象集合を findings からでなく diff 本文から作って全て列挙する。同一ファイルが一部で機構を使っていても「迂回なし」と結論しない——import 済みかでなく、各箇所（特にユーザー向け文字列リテラル）が個別に機構を通っているかで判定し、通っていないものを1つ残らず挙げる
- 界面の追従漏れ: 変更が作る／変える接続点（呼び出し元・先・共有状態・規約）の既存側追従（テスト・呼び出し元・docs）
- 意味的整合性: 型注釈・辞書キー・列挙値などの「契約を記述する識別子」が、既存の同種契約および実際の使用形態と一致しているか
- 設定コメントと実装値・PR 説明のファイルパスの整合性
- 既定・推奨の文書間一致: 変更が触れる文書・スクリプト・設定が読者に提示する「推奨・既定」（ツール・クラスタ・手順・バージョン）を各文書から表に抜き出して突き合わせる。自由文中の推奨も宣言として扱う。「兄弟文書の主役が互いの文書に登場しない」「推奨と実機検証済みが別物」のような意味的な割れは文字列一致では出ないため、抽出→突合で確認する
- 並行 PR との衝突・重複: 変更ファイルを触る他のオープン PR を確認し、(a) 指摘したギャップが別 PR で既に対応中でないか、(b) 提案する修正が、未マージの別 PR が進めている書き換えと同じ関数・領域で衝突しないか、を判定する。その箇所の変更を主導している PR（以下、担当 PR）がある箇所は本 PR のスコープから外し、修正は担当 PR への申し送り（別 Issue でなく既存 PR へのコメント）とする

## コード衛生観点 ③

タスクの目的に依らず成立すべき衛生。目的を知ると「この用途なら妥当」と正当化が働くため、文脈を遮断して見る。

- 資源・状態の対称性: 獲得した資源・差し替えた状態（接続・ロック・`app.state` 等の共有状態・モック / override）が、`finally` / teardown / context manager で対称に解放・復元されるか。例外経路で漏れないか
- 公式機構の迂回: テストの依存差し替えは公式の DI override（例: FastAPI の `dependency_overrides`）経由か、状態の直書き（自作）になっていないか。トランザクション・リトライ等も同様に、フレームワークが用意する機構を手書きで再実装していないか。標準ライブラリで賄える処理（パーサ・日付処理・状態機械等）を自作の実装で置き換えていないか
- 外部 I/O の無防備: 外部 I/O・公開エンドポイントが、入力規模・呼び出し頻度・失敗に対して無防備でないか（上限・タイムアウトの欠落）
- 検証機構の fail-open（検査が成立しなくても合格扱いになる構造）: 検査・ゲート・テスト・assert を追加・変更しているなら、①検査自体が実行不能（コマンド失敗・部分実行）に終わったとき赤くなるか（fail-closed）、②検査対象が空・縮退したとき「合格」と区別できるか（非空チェックの有無・「対象なし」を示す空ファイルとの偶然一致）、③実行基盤の既定動作（例: GitHub Actions は `shell: bash` を明示しないと pipefail が付かない）が失敗を握り潰さないか。検知すべき違反をわざと1つ作って赤くなることを確認するまで、新設ゲートを「機能している」と扱わない

## 外部標準照合観点（業界・OSS 横断） ②

「この問題を自分が初めて解いているはずがない」を前提に、外部の標準（フレームワーク・ライブラリ・著名 OSS・標準仕様）に枯れた定番解があるのに自作していないか、定番解の劣化変種を使っていないかを、外部の一次情報で確認する。整合性観点（リポジトリ内 Grep）・コード衛生観点（diff のみ）と狙いは重なるが情報源が違う——本観点だけはリポジトリの外（公式ドキュメント・当該 OSS の issue / PR・ソース）と、**インストール済みパッケージの実ファイル**を当たる。

- 問題クラスの抽出: diff が解いている問題を一文で抽出し、汎用的な問題クラス（初期化順序・認証 / 認可・リトライ・キャッシュ・並行制御・シリアライズ等）に属するなら、定番解の有無を疑う
- 一次情報での裏取り: web で定番解と既知の落とし穴を探し、公式ドキュメント・当該リポジトリの issue / PR・ソースで確証を取る。ブログ・Q&A は仮説に留め、出典 URL を伴わない断定はしない（裏が取れなければ「確証なし」とする）
- **手元の依存の使い残し**: 既にインストール済みのパッケージ（**推移的依存を含む**）の実ファイルを読み、自作した機能と同等のものが無いか、また既に使っている依存の**設定・オプションで済む話でないか**を確認する。web 検索は「世の中に定番解があるか」しか見ないため、**「既に手元に入っているのに使っていない」は素通りする**。取り違えの形は 2 つ——①同等機能を手書きしている（手書き側には本家にある付随機能が欠けていることが多い）②上流の設定 1 つで避けられる問題を、下流に変換処理を足して潰そうとしている
- 粒度: API の使い方だけでなく、自作ユーティリティ・パイプライン / 基盤そのものまで対象にする。最もレバレッジが高いのは「仕組みごと自作していたが既存の枯れた解があった」の検出
- **注記の密度を手がかりに使う**: 説明を厚く書かないと読めない箇所は、**自作が厚いことのサイン**でもある。定番解に乗っていれば読み手が既に知っているので説明が要らない。注釈比率が突出して高いファイル・関数を、まず「そもそも自作すべきだったか」で疑う（注記を削る話に直行しない——削るべきは説明でなく、説明を必要にしている自作かもしれない）
- 枯れた解が無いことも正当な結論: 社内固有のドメインや事実上の標準がまだ無い領域では「探したが定番解は無く、自作は妥当」も合格とする。枯れを疑うことと、何でも既存に押し込むことは違う
- 受容済み弱点の再照合: PR 説明・README・残件メモで「自覚済み・受容済み」と明記された弱点も照合対象から外さない。自覚は解消策が無いことを意味しない（標準機構・標準フィールドで置き換えられる手動運用が典型）

## 手順トレース観点（手順書・スクリプト・CI） ①④

差分に実行手順の文書（README 等）・スクリプト・CI 定義が含まれる場合、文書内の整合だけでなく「実行」を模擬して検証する。前提リソースの不在や環境の取り違えは読解では漏れやすく、実機で実行して初めて見つかることが多い。

- 初期状態からの逐次実行: 文脈を持たない初見の読者が初期状態から上から順に実行すると仮定し、各コマンド時点で前提（リソースの存在・ツールの導入・環境変数・作業ディレクトリ）が先行手順で成立しているかを、状態を追跡しながら確認する
- 環境状態の暗黙前提: コマンドが暗黙に参照する環境状態（kubectl のカレントコンテキスト・ログイン済みアカウント・既定ブランチ等）を洗い出し、想定と違う状態で実行された場合の挙動を問う（横断リスク観点の「誤爆半径」と対）
- 実機で確認できるものは実行結果を優先する。読解と実行結果が食い違えば実行結果が正

## 横断リスク観点（SRE・セキュリティ・データガバナンス） ④⑤

diff 内でなく、変更が触れている領域に潜む、変更が手を付けていない横断リスク。「この変更が導入・露呈させたか」で扱いを分ける（導入・露呈は本スコープで回収、純粋な既存無関係は `[suggest]` 以下で surface）。以下は代表例であり限定列挙ではない——変更が触れる領域に固有の横断リスクも同様に扱う。

- レート制限・濫用耐性: 外部 I/O・公開エンドポイントにレート制限 / スロットリングがあるか
- PII の外部送信: 個人データが外部サービスに渡るなら、データ分類・削除権・保持ポリシーが伴っているか
- 可用性の外部結合: 外部依存の障害・遅延が本体の可用性を巻き添えにしないか
- 誤爆半径（環境取り違え）: 手順書・スクリプトが想定と違う環境（kubectl のカレントコンテキスト・サブスクリプション・本番/ローカルの取り違え等）で実行されたときの被害範囲と、それを防ぐガード（実行前の確認コマンド・明示的なコンテキスト指定）の有無
- 移行退行の棚卸し（BASE 能力インベントリ）: 変更が既存手段を置き換える移行の一部なら、置き換え元（BASE）が提供していた能力を先に列挙し（機能だけでなく、反復開発ループの速さ・デバッグ手段・観測・既定の安全装置などの体験を含める）、各能力が置き換え先で生存しているかを1件ずつ確認して受容可否を問う。比較の基準は理想でなく BASE——「もっと良くできる」は対象外、「あったものが消えた」だけを拾う。置き換え先に無い体験は移行完了時に初めて顕在化するため、diff が手順・開発フロー・UX に触れる場合は必ず実行し、「消えた能力: 一覧」か「消えた能力なし（確認した BASE: 名）」を明示的に返す

## プロジェクト固有の規約

上の観点は言語・フレームワークに依存しない。固有の規約はここに書き、上の各観点はここを参照する。**規約の本文をここに複製せず、正本のファイルパスを指せ**——複製は更新漏れで stale 化し、レビューが古い規約で走る。

書かないまま走らせても致命ではないが、「アーキテクチャ境界」と「標準機構の一覧」が空だと、設計観点と整合性観点は近傍コードからの推測に落ちる（推測は当たるが、機械強制されている検査を二重にやる無駄と、規約に無い流儀を「標準」と誤認する取り違えが出る）。

- **アーキテクチャ境界の正本**: ＜依存表・モジュール境界を定義したファイルのパス。設計観点・整合性観点がこれを Read する＞
- **言語・フレームワーク・lint の規約**: ＜例: FastAPI / uv / ruff。テストの既定（`asyncio_mode=auto` なら `@pytest.mark.asyncio` は不要）等＞
- **標準機構の一覧**（整合性観点「標準機構の迂回」の照合先）: ＜例: i18n は `next-intl` の `useTranslations`、設定読み込みは `config/settings.py`、エラー分類は `core/errors`＞
- **機械強制されている検査**（設計観点が「緑の確認だけ」に留める先）: ＜例: import-linter の CI ジョブ、eslint の boundaries ルール＞
- **この変更が影響しうる固有の構成要素**: ＜例: オーケストレータ・MCP サーバ・モジュラーモノリスの各モジュール＞

## この規約の育て方

観点リストは事故から育てる回帰資産であり、完全な列挙ではない。列挙が発散しないよう、維持の手順ごと規約に含める。

- すり抜けの振り返り: 先のレビューを素通りした指摘が後から見つかったら（後段のレビュー・本番障害等）、その都度 ①どの観点があれば捕まえられたか ②再発しうるクラスか一回性か ③既存観点への統合・新設・棄却のどれが妥当か、を判定して本ファイルに反映する
- クラス単位でだけ足す: 個別インシデントの写しでなく、再発の機構を一文で言えるクラスに束ねてから追加する。束ねられない一回性のものは追加しない
- **原則名・パターン名で観点を足さない**: 「SOLID に従っているか」「適切なデザインパターンか」の形は採らない。①反証できない（「SRP に反する」は水掛け論になり、grader の過大判定を是正する経路が無いという既知の弱点をそのまま悪化させる）②抽象を増やす方向にしか働かない（「OCP 違反だから Strategy を入れろ」型の指摘が量産され、行数と抽象を減らす判断と逆に効く）。原則の実効部分は、**import を読めば決着する問いの形に翻訳してから**足す（依存性逆転とインタフェース分離は「抽象の所有権」へ、単一責任は「詳細の染み出し」へ翻訳済み）。翻訳できない原則は入れない
- 剪定と採用試験: 実際のレビューで発火しない観点・他と重複する観点は統合または削除する（リストの肥大は項目ごとの注意を薄め検出率をむしろ下げる）。新規観点は追加前に、それが捕まえるはずだった過去の実見逃しを、文脈（機能名・目的・正解）を伏せて当該レンズだけを持つ grader に読ませ独力で発火するか実測し、不発なら入れない。**不発だったとき教材を作り直してよいのは、教材の側に問題設定のバグがある場合だけ**（判断に要る材料が教材から欠けていた等）——理由を一文で書けないなら作り直すな。書けないまま作り直すと「発火するまで問題を変える」に退化し、採用試験そのものが恒真になる。作り直した回数と理由は記録に残す。採用後は実レビューの発火実績で剪定する。散文の説得力でなく追試の赤/緑で採否を決める——「読むより動かす」を観点それ自体に適用したもの
- 5問の担当監査: 観点見出しのタグ（①正しく動くか ②この分野の標準のやり方か ③後始末は清潔で漏らさないか ④使って・読んで・運用して良いか ⑤見えない所で何を壊したか）で、基本の査読の問いすべてに担当セクションが在るかを追跡する。剪定・統合で担当が消えた問いは、そのクラス丸ごと見逃しになる（④の担当不在が、内側開発ループの欠落・不適切な既定・手順書の注記肥大の連鎖見逃しを実際に生んだ）
