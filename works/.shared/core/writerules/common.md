## 直し方

- **根本の単位ごとに直せ。** 元の指摘を 1 件ずつ潰すな。判定の `reason` と `origin_analysis` が名指した根を塞げ。[block] は必ず直す。判定役が do-now とした [suggest] も直せ——自分の裁量で後回しに覆すな。導線の死を注記で直すな。不要になったコード・抽象は同時に引け。
- **同じ形を全部直せ。** `class_query` の how（欄で書かれた機械の問い）で同じ形を引き、名指しされた 1 か所だけで止めるな。
- **直す前に既製の物で済まないかを確かめろ。** 同じことを手元の依存（Python の標準・git・Claude Code・Archon の機能）や著名 OSS が既にしていないかを先に確かめ、在れば自作せずにそれを使え。判定の `prescriptions` に自作しない案（零処方）が在ればそれを先に採れ。必要以上に複雑にしない・既存の仕組みを作り直さない。
- **判定のフレーミングに同意できなくても、自分で単位を切り直すな。** 異議は `rejudge_requested` に書け（記録に残り、判定役が読み直す）。この周は判定どおり直す。`rejudge_requested` は判定のフレーミング（単位の切り方・根の見立て・disposition）への異議だけの欄で、読むのは判定役——人への問いはここに書かず、下の「食い違いの申し出」で返せ。
- **問いの台帳（`questions`）で fork の出どころ（origin）か depends に挙がった単位は実装するな**——`not_done` に理由「fork の出どころ」を書け。ただし修正の前に人が答えた問い（人の答えを書いたファイルに「直す義務に戻った」と機械が並べた問い）の出どころ・depends は直す義務に戻っている——一言が選んだ案で、一言が問いに触れていなければ問いの理由の推しで直せ。待つのはループを止めることではない。手を動かした結果が機構の新設・共有面の拡大に及んだと気づいた時点で手を止めろ（それは設計作業で、零処方の列挙を経ていない機構をここから出すな）。
- 人の方針に反するもの・方針を変えないと成り立たないものを、自分の判断で通すな——通すかは人が決める。直す義務の単位なら、次の「義務の単位の行き先」のとおり、方針に反しない範囲の直しで単位が閉じればそれを `changes` に載せ、閉じなければ直したことにせず、下の「食い違いの申し出」で人に回せ（`between` に方針の文書の行を含める）。義務の外の単位なら、どの項とぶつかるかを `not_done` に書け。方針の文書は書き換えるな。
- **義務の単位の行き先**: 直す義務の単位（[block] と do-now）は、必ず直して `changes` に 1 行で載せる（人の答えが無いと直し方が決まらない単位だけは、直さずに「食い違いの申し出」で返す）。判定の前提・直し方に疑いが残っても、方針に反しない範囲で一番ましな直しを載せ（根を塞げなければ `root_or_symptom` を symptom にして why に理由を書く）、それが判定のフレーミングへの異議なら `rejudge_requested` に書く（判定役が次に読み直す）。`not_done` に書けるのは、受け付けが免除する単位（問いの台帳で、修正の前に人がまだ答えていない fork の出どころか depends に挙がった単位。答えた問いの出どころ・depends は免除されない）と、義務の外の単位だけ。
- **動きを変えたら、その動きを述べた文を全部直せ**: 注記・docstring・テスト名・拒否文・別の文書に、変える前の動きを述べた文が残っていないかを検索で引き、直すか消せ（引いた検索は `breaks` の how に並べて書け）。新しい注記は、テスト名・拒否文・名前で言えるなら足すな——注記は「なぜ」だけを言う。

## テストで赤→緑を示せない直しの証拠（変更の種類ごと）

先にテストを書けない直し（文書・指示書・設定・注記や型だけの直し）は、赤→緑の代わりに、変更の種類ごとに次を確かめ、確かめたこと（引いた検索・回したコマンドとその結果）を返答に書け。「読み直した」だけで済ませるな。

<!-- 節 evidence-docs -->
- 文書: 書いた名前・パスが現物に在ることを検索で引く。リンクが指し先（ファイルと見出し）まで届く。前提を知らない初見の読み手として頭から読み直し、それだけで通じる（冷読）
<!-- 節 evidence-prompts -->
- 指示書（プロンプト）: 実際に描いて（描く仕組みが在ればそれで）穴が全部埋まり、崩れないことを見る。同じ文の写しが別の置き場に在れば、全部揃っている。変えた指示は次の run から効き、今の run の役には届かないと書く
<!-- 節 evidence-config -->
- 設定・YAML・workflow: Archon の validate と、リポジトリの設定の検査（`check.sh` など。テストの一式は線の最後のテストの段が回す）を回して通る
<!-- 節 evidence-code -->
- 注記・型: 静的な検査の段（型検査・lint など、リポジトリが持つ物）を回して通る

## 食い違いの申し出（緑にするために曲げない）

- **緑にするためにテスト・依頼・コードのどれかを曲げるくらいなら、食い違いとして返せ。** テストの期待・依頼（判定の単位の元の文と、
  人の修正依頼のファイル）・今のコードのうち、2 つが同時には成り立たないと分かった単位は、直したことにせず、その単位だけを
  申し出る。テストを緩める・期待値を実装に合わせる・依頼を読み替える・特定の入力だけを通す枝を足す、のどれもしない。
- 申し出は 1 単位 1 件で、欄は `unit_key`（判定の単位の key を一字も変えずに）・`between`（食い違う所を 2 つ以上。形は
  `<パス>:<行>` か `<パス>:<行>-<行>`。テストとコードはリポジトリの根からの相対パス、依頼は判定のファイルか依頼のファイルの
  絶対パス、方針は指示書に在る方針の文書の絶対パス）・`why_both_cannot_hold`（なぜ両方は同時に成り立たないか）・`which_is_right`（request・test・code・unknown の
  どれが正しいと見るか。判定者の問いの誤りなら下の query）。
- 判定者の問い（`class_query`）が直した後の正しい形にも当たり、正しく直しても件数が減らない単位は、`which_is_right` を query に
  して、欄 `correct_lines` に問いが当たってしまう直した後の正しい行を 1〜20 行写して申し出る（`between` には判定のファイルの
  `class_query` の行と直した後のコードの行）。機械が判定者の問いをその行に当てて確かめ、問いを置き換える裁定が出たら、新しい
  問いは当たる例・当たらない例と `correct_lines` で機械が試す。
- 機械は名指した所が現物に在るか（ファイルが在り、行がその中に在る）を確かめる。在れば拒否に数えず、その単位だけを止め、
  ほかの単位は進む。無い所を指した申し出は普通の拒否になる。止めた単位は読むだけの裁定役が持ち主の決まりで裁き、
  テストの直しを許す（範囲つき）・コードをこう直す・判定者の問いを置き換える・人に回す のどれかが理由のファイルで届く。
  問いを置き換える裁定が届いた単位は、閉鎖の数え直しを機械がその新しい問いで数える。その単位も直して `changes` に 1 行を書く。
- **人に聞きたいこと・人にしか決められない疑いの行き先はここ**（`rejudge_requested` ではない）。方針を変えないと直らない・
  依頼の意図が材料から決められない・テストと依頼とコードのどれが正しいか決められない単位は、直したことにせず、
  `which_is_right` を unknown にして申し出る（方針なら `between` に方針の文書の行を含める）。裁定役が持ち主の決まり
  （材料から決められない物は人に回す）で裁き、人に回した単位は最後の人の関所と次の run の依頼に載る。
- 疑いが残るだけで両方が成り立ちうるなら申し出ではない。そのときは上の「義務の単位の行き先」のとおり直し、
  その疑いが判定のフレーミングへの異議なら `rejudge_requested` に書く。

## 守ること

- **テストを消すな・緩めるな。** 既存のテストの削除・skip・期待値を実装に合わせる書き換え・検査を甘くする変更はしない。直した単位の欠陥を捕まえるテストが無ければ足してよい。
- **プロジェクトのテストを回せ。** 直した単位に当たる試験だけを絞って回せ（pytest の node id か `-k`、unittest の `-k` かモジュール名。絞り方はリポジトリの `run.sh`・テストの置き場から探す）。テストの実行器が在る run では、受け付けが版からの変更に当たる試験を機械で選んで回し、元で赤でなかった試験が赤なら理由のファイルで返す——自分で回すなら同じく変えたファイルに当たる試験を選べ。リポジトリのテスト一式は線の最後のテストの段が回すので、役は回さない。絞る手が無い時だけ、返答の直前に一式を 1 回だけ回せ。赤が残るなら、どの単位のどこかを直してから出せ。Python は `PYTHONDONTWRITEBYTECODE=1` を立てて回せ。git が無視する生成物（`__pycache__` など）のうち、あなたの前に無かった物は後の節が消す（消した物は人に見せる）。
- **作業ツリーのファイルは Edit・Write で書け。** 包みが Edit・Write の書き込みを記録し、受け付けが版からの変更と突き合わせて、記録も申告も無い変更を拒む。Bash（ヒアドキュメントの `python3 -`・`cat >`・`sed -i`・整形の道具など）で書くのは、実行の権限・バイナリ・大量の機械的な置き換えの時だけにし、その時は返答の欄 `bash_writes` にパスと理由を 1 件ずつ書け。
- **`git commit` するな。** `git add`・`git commit`・`git stash`・`git reset`・`git checkout` で作業ツリーや履歴を動かさない。差分は作業ツリーに残したまま返せ（後の節が版からの差分と未追跡のファイルで確かめる。新しいファイルも未追跡のままで数えられる）。
- 作業ツリーの外（ホームや /tmp の設定など）を書き換えない。
