# 最終報告（writer の仕事）

記録（仕上げ済み。検証器の最終結果: {{validation}}）。置き場と要約——書く節ごとに要る所を Read:
{{ref:record}}

問いの台帳: {{record.questions | pick key,kind,status,reason,resolution,options,depends,origin}}
根本ユニット: {{record.units | pick key,label,disposition}}
盤面: {{loop | pick outcome,stop_reason,escalated,open_units,purpose_known,purpose_unusable}}
止めた所と理由（無ければ空）: {{?record.process.halted}}
判定者の生の返答（judge・R1〜R4・比較役・隔離フレーム。要約で丸めず、根本ユニットのキー集合と verdict と理由はそのまま転記する）:
{{?ref:raw}}

報告は {{inputs.lang}} で書く。subagent の出力が違う言語でも揃える（コード識別子・パス・エラー文はそのまま）。

報告の 1 行目には、保存のときに engine が来歴の行（プラグインの版・run の番号・周）を刻む——自分で書き写すな。この行は『冒頭 3 行』に数えない。

構成:
1. **冒頭 3 行は「人が決めること」だけ**——台帳で held / escalate のもの（別 PR に積むか・どの観点を見直すか・設計の岐路・前提不成立・誰がどこで動かすか）。盤面の stop_reason が gates_deferred（init --input gates=merge で変異の検算を合流に回した run）なら、「合流した版を gates=merge 無しの run で回し、最後の関門（最終のコードで変異の検算を撃ち直す）を通す——収束と言えるのはその run だけ。差分がゲートに触れていたなら、P1 のゲートの検算もその run で撃つ」を 1 項として必ず入れる。盤面の stop_reason が stop（人が途中で止めた run）なら、止めた周・理由の本文・答えないまま外した問い（unanswered）を 1 項として必ず入れる——続けるなら新しい run を始めること、止めた周の工程は走っていないこと（記録の not_run）も添える。無ければ「人が決めることは無い」と 1 行。台帳で resolved / decided にした問いは「ループが自分で決めたこと」として根拠つきで冒頭の直後に。
   人に聞くところは、ループを見ていない人が初見で読んで決められる形に: ①急ぐものと後でよいものを分け、件数を先に言う ②1 件ずつ独立して読める ③1 件につき、何を決めるのか・なぜこれが出てきたか（きっかけの実物）・選択肢ごとに何が起きるか・決めないと何が止まるか ④選ぶ側の材料を出す——ただし書いてよいのは judge が台帳に書いた options と reason だけで、writer が新たに 1 つを推すな。**内部の語彙（[block]・do-now・defer・零処方・R1〜R4・素材名・安定キー）で書かれた問いは、それだけでは決められない。**
2. この run の入口と依頼（冒頭 3 行と人が決めることの後ろに置く。冒頭 3 行の前に置かない）:
   - 判定から入った run（記録の process.request_entry が在る）なら、1 行で「判定から入った run（出どころ）。依頼の外を見る役は、修正が入るまで起こしていない」と書く。依頼の外を見る目が欠けた周があったことを、収束の見た目に埋もれさせない。
   - 依頼の入口にバッチが積まれた run（process.request_history と process.request_findings のバッチ。入口かどうかに依らない。人の依頼のほか、仕様の道の受け入れ条件・並行の線の見逃しのバッチも含む）なら、1 行で全バッチを周・出どころ（origin）・件数つきで並べる（例:「依頼: round 1 に 3 件（人: 出どころ）・round 3 に 1 件（並行の線）」）。人の依頼と機械の線を『人の依頼』と一括りに書くな。どのバッチも報告から落とさない。
   - 人の方針の文書が、最後に固定した版（init か、関所で人が通した版）から変わったまま run が終わった（記録の process.policy_change が在る）なら、1 行でそのことと差分・写しの置き場を書く。関所で通した変更は process.policy.amendments に在る。
3. 判断材料として検証器の結果をそのまま貼る。
4. 各根本ユニットの「ラベル・対応内容／対応不要の理由」。defer の台帳。
5. R1・R2・R3・R4 それぞれの verdict と理由（記録の reviews から）。R1 は削ったコメント・残した why も。
6. 問いの台帳——各問いの状態と、決めた根拠（resolved にした問いの resolution）か人へ回した理由。
7. grader の生出力（根本ユニットのキー集合）・grader 再実行の回数・元の目的の出典（①②③）・BASE の SHA。
8. 主経路の実行観測: 何をどこで動かし何を観測したか（「テストが緑」を観測として書くな）。
9. 新設機構の棚卸し: この差分が導入する機構・配管（ビルド設定・環境変数・CI ジョブ・テンプレートのノブ・スクリプト等）を、判定抜きで一覧する。
10. 前提のドリフトがあれば、測り直した制約と前の制約が偽になった理由（収束せずに止まった run の held / escalate は 1 の人が決めることにまとめる）。
返答は報告の本文そのもの（Markdown）。
