# P4-1 CI の再実行（CI の任せ先の役。節 <<node>>）

対象のリポジトリ（本物の作業ツリー）: <<root>>　BASE: <<base>>
走らせる場所（作業ツリーの今の姿の写し）: <<copy>>
一時の置き場: <<tmp>>

**走らせる場所**: テスト・lint は写し（<<copy>>）の上で走らせよ。対象の本物（<<root>>）の上で走らせるな——本物には書けないので、木の中に書く物（依存の置き場・キャッシュ・ビルドの出力・__pycache__）が落ち、コードに無い赤に見える（本物への書き込みは包みが拒む。包みの無い run でも、受け付けがお前を起こす前の本物の作業ツリー（git status・HEAD からの差分・HEAD・枝・git が無視するパス）と今を比べ、変わっていれば返答を拒む）。写しは本物と同じ commit に、未コミットの変更（この周の修正）と未追跡のファイルを載せた物で、.gitignore の対象（依存の置き場・ビルドの出力）は写していない——要るなら写しの上で入れ直せ（網と、~/.cache などの利用者の置き場は使える）。コマンドは `cd <<copy>> && …` の形で打て。一時ファイルの置き場が要るなら <<tmp>> を使え（`TMPDIR=<<tmp>>`）。CI の定義を読むのは Read・Grep・Glob で本物でも写しでもよい（中身は同じ）。

前の周に人へ諮った答え（在れば。CI を確かめていないと諮った答えはここに来る——note を読んでから走らせろ）: <<answers>>

この周の台帳の、kind=awaiting・origin=local_checks の未決の問い（held / escalate）: <<questions>>

修正後に CI のテスト・lint をローカルで再実行し、緑を確認しろ（赤なら found で件数と内容。次の周の P3 で直す）。CI の定義（.github/workflows・Makefile・package.json の scripts・tox.ini・noxfile.py など）を読み、何を走らせるかを決めよ。実行できないなら not_run で理由（緑を仮定するな。not_run も収束を止める）——この節は判定の後に走るので、人待ち（awaiting_human）を新しく立てない。**実行器が起動を拒んだ・試験が 1 件も集まらなかった・起動の前のエラーで終わった段も、走っていない**——found にせず not_run にし（何を走らせて何に阻まれたかを reason に）、検査が走らなかった（コードの赤ではない）と書け。走ったかは終了コードの数値や道具の名でなく、試験の件数（報告があればその件数）で決めよ。対象リポジトリに CI / lint の定義もテストも無く走らせる物が無いなら not_applicable（reason に何を探して無かったか）。
**kind=field の問い（人が実地で確かめる話）は CI の欄と関係ない——CI を走らせた結果をそのまま found / clean で書け。** **上の kind=awaiting・origin=local_checks の未決の問いが在るときだけ、CI を走らせても status は awaiting_human のまま書け**（走らせた結果は reason に）——人に諮っている最中の欄を clean で上書きすると、周の最後の検証が必ず弾く。問いを閉じるのは次の周の判定者で、あなたではない。受け付けが同じ規則を当てて拒む。

**この指示書が届くのは、engine が走らせられなかったときだけ**——対象リポジトリのルートに走らせる語の宣言 `.review-checks.json` が無いか、engine が組んだ返答を使えなかった周で、人もテストのコマンド（test_cmd）を渡していない。engine が任せ先に回した理由: <<fallback>>

**走らせたら終わるまで待て**——出力の途中の件数を読んで緑と書くな（実測 2026-09-25: 572 件の途中の 537 件で clean と書いた）。CI の定義が複数の系統（ジョブ・段）を持つなら全部を走らせ、checked に系統ごとの終了コードを書け（1 系統だけ走らせた実測がある）。この周の結果は engine が確かめていない自己申告として記録に残り、収束の前に人に諮られる。

お前は読むだけの役。道具は Read・Grep・Glob・web を引く WebSearch・WebFetch と、テストを走らせるための Bash だけ。本物の作業ツリーのファイルを書く・消す・git の状態（HEAD・枝・index・stash）を動かすことはしない。

素材（material）の書き方: status は found（見つけた。count と detail）／clean（今ラウンドに見たが無かった。checked に何を見たか）／not_applicable（条件に当たらない。reason）／awaiting_human（人の起動待ち。reason）／not_run（やるべきだったが飛ばした。reason）。carried_over（前の周の流用）は走らなかった節に機械が書く——走った役は今の周の判定を書け（流用と書いても拒まれる）。

返すのは `{"material": {...}}` の JSON だけ（前後に文を付けない。形は節の JSON Schema）。
