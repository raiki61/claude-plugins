## 決めてほしいこと（推しつき）

1. **B: 「目的の外」の所見の見せ方。** 判定が「依頼の目的の外」とした所見を、報告の冒頭 1（人が決めること）に 1 件ずつ並べるのをやめるか。推し: やめる。冒頭 1 には件数と次の依頼の下書きの置き場だけを書き、中身は下書きのファイルに残す。訳: 10-09 の利用者は 23 件を読み、採ったのは 3 件だった。これらは人が決める事ではなく、次の run に回すかの材料にすぎない。今の形だと、人が全部を選り分ける手間を負う。
2. **C2: 依頼者が手元で測った結果を、run が測れなかった確かめの代わりに使うか。** 依頼の答えの欄（answers）にコマンドと出力が付いている時、run の中で測れなかった素材（ほかの PR との重なりの確かめなど）の測りとして、その素材の役に渡すか。推し: 渡す。ただし使えるのはコマンドと出力の両方が在る行だけ。役は使ったことを素材の理由に書く。訳: 今の答えは判定役が立てた問いにしか当たらず、素材の「未実施」は答えがあっても残る。10-09 の 2 本目の run は、利用者が `gh pr list` の出力まで付けたのに、答えはどこにも当たらず「直しきれず」で終わった。計画 [request-answers](plans/2026-10-05-request-answers.md) の決め 4 は「依頼者の言明は測りの代わりにならない」と決めた。これを、出力つきの行に限って緩める形になる。
3. **C3・F: 結末の名前。** 直しは入り、最後のテストも緑で、残ったのが「run の中では測れない確かめ」だけの run を、結末「決めた周の数のうちに直しきれずに止まった（round_limit）」と呼ぶのをやめるか。推し: 分ける。「直したが、人が確かめる物が残る」と名乗らせる。次の依頼に運ぶ物は今と同じにする。訳: 10-09 の 2 本はどちらも直しが入って緑だった。それでも冒頭の 1 行目は「直しきれず」になり、利用者は「GitHub が落ちると毎回止まる」と受け取った。Terraform のように、plan に雲の資格が要るリポジトリでは、毎回この結末になる。
4. **E: 軽い run の事前審査を 1 往復にするか。** 全部の単位が軽量の run で、修正案の事前審査の往復（opus の審査役）を 1 往復に絞るか。推し: すぐには絞らない。先に計画 clean-whole の段 7 の測りで、軽量の run で 2 往復目が案を変えた率を数え、低ければ絞る。訳: 10-09 の 1 本目は、全部の単位が軽量なのに、費用の 44%（9.06 USD のうち 4.03 USD）が修正案と事前審査だった。ただ、その run の 1 往復目は止め 1 つ（記録の名 ledger-body-inverts-canonical）を出し、2 往復目で案が直った。効いていないとは言えない。

## 語

- run: works の 1 回の実行。周: run の中の 1 巡り（今の作りは 1 run 1 周）。盤面: run の記録の置き場。報告の冒頭 1: 報告の「1. 人が決めること」の節。緑: テストが通ったこと
- 利用の家: 利用者の作業コピーごとに works が作る、run の記録と設定の置き場（`~/.local/state/works/use-*`）
- 推し: works の役か、この文書の書き手が勧める答え
- 線: run の工程を並べた流れ（`darkfactory/darkfactory.yaml`）。殻: 人が打つ起動のシェル（`dev/use.sh` など）
- 包み: AI の役の起動を間に入って包む殻。役の sandbox（隔離）の設定を足す。works-gh: 包みが役に渡す、GitHub を読むだけの gh の口。sandbox の外で走らせてよいのは、この名で始まるコマンドだけ
- 関所: 人に答えを聞いて止まる所。無人の run: 関所に着いたら人を待たずに止めて報告へ進む起動の形。人の居る run はその逆
- 検証器の阻害: run の記録を照らす機械（検証器）が、確かめの欠け（素材の未実施など）を見つけた物。報告では「残り」に数える
- 素材: 判定の前に集める確かめの結果（ほかの PR との重なり、主な経路を動かした観測など）。状態は見つけた・無かった・条件の外・人待ち・未実施（not_run）のどれか。未実施が 1 つでも残ると、結末は「直しきれず」になる
- 局所レビュー: 素材の 1 つ。差分に、Claude Code の汎用のレビューの道具（レンズ。`/code-review`・`/simplify` と、pr-review-toolkit の agent）を 1 本ずつ当てて所見を集める。どのレンズを起こすかは、別のプラグイン graphloops から写した工程の表（写しの graph）が決める
- 判定・単位: 判定役が依頼を、根本の原因ごとの「単位」に切る。依頼の目的の外と判じた所見は単位にせず、次の run の依頼の下書き（盤面の `next-request.json`）へ回す
- 修正案・事前審査: 直す前に計画役が書く案と、それを別の役が叩く往復。審査役は opus（Claude の上位の模型）で走る。止め: 審査役が「このままでは通さない」とした穴
- 修正役・並べの枝: 修正案どおりに直す役。単位ごとに別の作業場所で同時に直す枝（並べの枝）と、その後に全体を直す順の修正役がいる
- 独立設計・構造の目・独立の目: 独立設計は依頼の目的だけから別の役が作る設計。構造の目は「この直しでコードが汚れないか」を見る役。独立の目（R1〜R4）は直した後に別の目で見る 4 つの審査。前提・目的の役: 依頼の前提を測る役と、目的を 1 文にする役
- keep-essence: works を作り替えても残す 11 の仕組みの一覧（`docs/keep-essence.md`）
- 返答の契約: 役に返答を本文で返させ、受けた後に型を確かめ、合わなければ同じ会話で出し直させる受け方
- 処方: 判定役が単位ごとに書く「こう直せ」の文（判定の出力の欄 prescriptions）
- 深さ: 単位ごとの工程の厚さ。軽量の単位は差分の審査と独立の目を省く。標準は全部を回す
- 依頼の答え（answers）: 依頼のファイルの欄。人が前の run の問いに答える。問いの名か出どころの名で、判定役が立てた問いに当たる
- 計画の段: 計画 [clean-whole](plans/2026-10-09-clean-whole.md) の段 0〜7 と、その中の Task の番号。「決め n」は同じ計画の 1 節の、持ち主の決めの番号

状態の語:

- 直した版: 直しを入れた版が出ている（どの版かを書く）
- 直し中: 直しの枝が在る
- 計画の段: 計画の文書に、直す段と形が書いてある
- 未着手: 直し方は決まっているが、枝も計画の段も無い
- 決め待ち: 持ち主の決めが要る（上の「決めてほしいこと」）
