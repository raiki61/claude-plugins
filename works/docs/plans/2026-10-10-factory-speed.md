# 工場の待ち時間を減らす（速さの計画）

## 平たく言うと（3 行）

- 何の話か: works の工場 darkfactory（依頼を受けて直しを出す AI の流れ）が遅いので、works 自身の直しを工場に回さず会話の下請けで作っている。工場を速くすれば開発を工場の run に移せる。そのために、run の時間がどこで消えているかを、最近の 48 本の run の記録から測った。
- 分かったこと: 時間の多くは「修正案と事前審査の往復」で消えている（利用の run で動いていた時間の 36%、works を対象にした run では 65〜71%）。往復の 3 回目は 10 本中 6 本で収まらずに人の関所へ行った。事前審査の受け付けの拒否 28 回のうち 21 回は、審査役が余分な行を書いただけで、機械が捨てれば済んだ。works を対象にした run では、直す前の同じ木で同じ 1993 件の試験を 3 回（命令は 2 種）走らせて、約 11 分を使っている。
- 持ち主に求めること: 9 節の 3 点を決めてほしい。(1) 往復の止め時の決まり（2 回目の残りの block が 2 つ以上なら 3 回目を回さず関所へ）を入れてよいか。(2) 試験の結果を使い回す範囲を、同じ run の中だけにするか、run をまたいでもよいか。(3) run をまたぐ控えの口 `Store` を web の住処から中立の住処へ移すか。

状態: 計画だけ（2026-10-10）。数はすべて 1 節の測り方で引いた。版は枝 `wip/world-w10`（03fd1586）の事実で書いた。

> **実装する者へ:** superpowers:subagent-driven-development で、Task ごとに opus の実装役と審査役を立てて回す。8 節の手順は `- [ ]` で追う。案 D（往復の止め時）は 9 節の (1) の答えを待ってから入れる。

**目的:** 品質の関所（keep-essence の 12）を一つも弱めずに、works を対象にした run の「直す前の関所」までの時間（今は 65〜69 分）を、1 本あたり 7〜26 分縮める（6.1 節で 2 本に当てた見積もり）。利用の run も、往復と受け付けの拒否の分を縮める。

**作り:** 新しい段は足さない。速さは次の 3 つから取る。
- 同じ物を 2 度作らない: 試験の結果の使い回しと、閉じた項目の写しを機械が受け持つ。
- 拾える誤りは役が返す前に機械が拾う、または捨てる: 事前審査の余りの行と、範囲の外の書き込み。
- 往復の止め時を、指摘の減り方で決める。

**道具:** Python 3.12（標準ライブラリだけ）・unittest・git・Archon v0.11.1 の YAML。

## 2. 語

- 動いた時間: 人の関所で待った時間を除いた、線の上の節が動いていた時間。

## 4. 根の原因

1. 役が同じ物を書き直す:
   - 直しの役は、閉じた項目も「一字も変えずに」書き直して返す（`converge.REVISE_ASK`「直した案を丸ごと plan に返せ」と `CLOSED_ASK`）。受け付けは、それが前と同じかを hash で確かめる（`converge.closed_gaps`）。
   - 直しの往復で閉じた・保留の項目は、113 項目中 60（53%）。直しの役の時間 77.1 分（35 回）は、書く速さに縛られている（1 秒 113 トークン）。
   - 受け付けの拒否も「丸ごと出し直せ」で、出し直しのたびに全体を書き直す。
2. 機械が拾える誤りを、役が返した後で、役ごと拒んでいる:
   - 余りの行は捨てても失う物が無いのに、拒否で出し直させている（21/28）。
   - 範囲の外の書き込みは、書いた時でなく、修正の節が終わった後の受け付けで初めて分かる。
3. 往復の止め時が「同じ block か、3 回目か」だけで、減り方を見ていない:
   - 2 回目の block の 93%（14/15）は新しい key だった。3 回目まで回した 10 本のうち 6 本は、収まらずに人の関所へ行った。
   - 審査役は毎回新しい会話で、穴を「見つけ直す」。往復は収束より抜き取りに近い（文献の 5.2 節）。
4. 同じ木の同じ試験を、結果を残さずに何度も走らせる: 3.6 節。
5. 線の順が、中身の依存より強い: 独立設計と修正案、start の試験と前提・目的・世界の解（3.7 節）。

## 5. 前の作り（review-graph）と世の中（問い 4）

### 5.1 review-graph（graphloops）の同じ輪

- 事前審査は 1 周に 1 回だけ。直した案を審査し直さない。代わりに、直しの後の差分だけを見る 2 回の差分審査（`delta_review`・`delta_review2`）を固定の回数で回し、3 回目は無い。残りは次の周の判定役へ行く（`graphloops/graphs/review-loop.json` の 4369〜4561 行）。
- 差分審査の face は、その周の直しが触ったファイルに在る字を引かないと受け付けない（`graphloops/rules/review-loop.py` の `delta_review_output`、2269〜2292 行）。変えていない所への新しい指摘を、機械が締め出す。
- 止め時: 記録の検査で blocker が 2 周続けて無い、など。周の上限 5 に着いたら人に聞く。同じ `[block]` が 3 周続けば `stuck`、新しい `[block]` が出続ければ `thrash`。block の数が減らない周が続くと、深い処方へ一方向に上げる（`escalate_on_thrash`）。
- 並べ: 準備のできた節をまとめて最大 8 本で回す（`engine/commands.py` 153・476〜478 行）。修正役は 1 本で縦。
- 使い回し: 素材は、前の周の直しが触っていなければ `carried_over` で引き継ぐ（触ったかは役の申告でなく、実際に触ったファイルで決める）。

works はこれより審査を厚くしている。2 回目からは差分だけを見よと指示しているが（`planblk.DIFF_ASK`）、機械はそれを確かめていない。差分の外への指摘を締め出す機械の確かめは、graphloops にしか無い。

### 5.2 世の中

本文で数を確かめた物は [読]、検索の抜粋だけの物は [検] と印をつけた。

- 往復の伸びは最初の 1〜2 回に集まる:
  - Self-Refine（Madaan ほか、NeurIPS 2023、https://arxiv.org/abs/2303.17651 ）[読]: Code Opt の伸びは 5.0 → 0.9 → 0.9。ただし制約つきの生成は 3 回目でも伸びた（11.3 → 6.4 → 3.0）。往復ごとに上下することがあるので、全部の往復から一番良い版を選ぶ。
  - Teaching LLMs to Self-Debug（Chen ほか、ICLR 2024、https://arxiv.org/abs/2304.05128 ）[検]: 1 往復の後の上積みは 0.1% 以内。
- 外からの確かな指摘が無い往復は悪くなる:
  - Large Language Models Cannot Self-Correct Reasoning Yet（Huang ほか、ICLR 2024、https://arxiv.org/abs/2310.01798 ）[読]: GSM8K で 95.5 → 91.5 → 89.0。
  - 「本当に？」と聞き返すと答えを平均 46% 翻す（Laban ほか 2023、https://arxiv.org/abs/2311.08596 ）[検]。閉じた項目を固めて審査に戻さない今の作りを支える。
- 安定したら止める:
  - Early-Stopping Self-Consistency（Li ほか、ICLR 2024、https://arxiv.org/abs/2401.10480 ）[検]: 直近の答えがそろったら標本を止める。精度を保ったまま、標本を GSM8K で 80.1% 減らした。
- 見落としの数の推定を止めの決まりにする:
  - Capture-recapture in Software Inspections after 10 Years Research（Petersson ほか、JSS 2004、https://wohlin.eu/jss04-1.pdf ）[読]: 独立した審査役が 4 人以上いる時に使える。多くの推定は少なめに出る。今の 1 項目 1 審査役では使えない。
- 安い確かめを先にかける:
  - SWE-agent（Yang ほか、NeurIPS 2024、https://arxiv.org/abs/2405.15793 ）[検]: 編集の時に検査を掛けて、壊れた編集をその場で捨てさせた。解決率は 15.0% から 18.0% に上がった。
  - Instructor の文書（https://python.useinstructor.com/ ）[検]: 出し直しは呼び出しを丸ごと 1 回増やす。出し直しが続くなら、回数より形の定義を直せ。
- 並べ:
  - Building effective agents（Anthropic、2024-12、https://www.anthropic.com/engineering/building-effective-agents ）[読]: 独立した部分に分けて並べる型（sectioning）と、生成役と評価役の往復（evaluator-optimizer）には止める条件を付けるのが普通、と書く。
  - LLMCompiler（Kim ほか、ICML 2024、https://arxiv.org/abs/2312.04511 ）[検]: 依存の図で独立した呼びを同時に走らせ、待ちを最大 3.7 倍縮めた。
- 結果の使い回し: 入力の hash を鍵にした成果物の控え。ビルドの道具の遠隔の控えと同じ考え（記憶から。出典は確かめていない）。

持ち主の「止め時は指摘の減り方で決める」との照らし: 支えがある（最初の 1〜2 回に伸びが集まる・安定したら止める）。ただし条件が 2 つ付く。
- 数えるのは、変えた所への指摘か、機械が確かめた指摘だけにする（5.1 節の差分の締め出し）。新しい会話の審査役は、穴を見つけ直し続ける。
- 48 本では、減る割合（2 回目 ÷ 1 回目）は収まる run と収まらない run を分けなかった。分けたのは 2 回目の残りの数（6.4 節の D）。

### 6.3 D 往復の止め時を残りの数で決める

- 何をする: 2 回目の審査の後、block の残りが 2 つ以上なら 3 回目を回さず、今の persisted・unsettled と同じ人の関所へ行く。残りが 1 つ以下なら 3 回目を回す。

  - 3 回目を飛ばすのは 4 本（97fd532f・bfdd2624・4d7304ce・5efa75f0）。4 本とも 3 回目の後に収まらず、関所へ行った（unsettled 2・persisted 2）。
  - 縮む時間は 3 回目の区間の和で 35.75 分（1 本あたり 8.9 分。bfdd2624 は 14.6 分）。
  - 3 回目で clean になった 4 本（f57a5374・44d0979a・73a0ab23・546c1d5a）は、どれも 2 回目の残りが 1 で、今どおり 3 回目を回す。
  - 167e14c3 と fabd340e も 2 回目の残りが 1 なので 3 回目を回す（今と同じ）。

- 危うさ:
  - 標本が 10 本と少ない。関所で人が見るのは、3 回目の案でなく 2 回目の案になる。
  - 3 回目で収まる run を止めてしまう恐れ: 48 本では 0 本。

- keep-essence: どれにも当たらない（事前審査の往復は 12 の外。9 の独立設計との突き合わせは、1 回目の審査で今どおり行う）。

### 6.4 C 直しの役は開いた項目だけを書く

- 何をする: 直しの役 `plan-revise` の型の `plan` を「開いた項目の行だけ」にする。閉じた・保留の項目は、受け付けが前の往復の控えから差し込んで、全体の案を組み直す。

- 品質: 閉じた項目を変えさせない決まり（`converge.closed_gaps`）が、検査から作りそのものに変わる（役は変えられない）。強くなりこそすれ、弱まらない。
- 住処: `.shared/core/converge.py`（`REVISE_ASK`・`CLOSED_ASK`・閉じた行の控え `note_plan`・`prev_row`）と `blk-plan/lib/planblk.py`（直しの型 `output_format("plan-revise")`・受け付け）。

### 6.5 B 事前審査の余りの行を捨てる

## 7. 捨てた案

- 模型を軽くする・effort を下げる: 持ち主の段の模型の表（`.shared/core/stage-models.json`）を変える話で、品質を直に動かす。この計画は量と往復の数だけを扱う。
