### 2.3 段 1 の形（修正案の事前審査を木にする）

節の並びは今の壁打ちの輪（`blk-plan.yaml` の converge-loop。外の輪の 1 回が 1 往復）のまま。中身を次のように変える:

1. **波及の一覧（新しい script の節。機械）**: 案を受けた後、往復ごとに事前審査の支度の前で走る。項目ごとに、変える名を引く:
   - 単位の key の `+` の後の名（`report.py+always_rows` なら always_rows）と、案の adds の name に在る ASCII の名のうち、対象リポジトリに既に在る物。
   - 各名を `git grep -n -w` で引き、当たりを「本体の呼び出し元」と「試験」に分ける。Python の試験は当たりを含む試験の関数の id（`path::Class::test_x`）まで引く（ast。ほかの言語はファイルと行まで）。
   - 当たりを項目の allowed_paths と rewrite_tests・受け入れの試験に照らし、覆っていない当たりを名指す。盤面の今の周の作業ファイル（`b.work("ripple/<項目>.json")`）に置く。
   - 同じ一覧を修正案の役と直しの役にも渡す（書く前に波及を知らせる。195g の 5 件はこれで書く時点で避けられた見込み）。
2. **事前審査（今の節 plan-review）を「束ね役」にする**: 束ね役は、まだ開いている項目ごとに審査の下請けを Agent の道具で 1 つのメッセージに並べて起こす。下請けは 1 項目だけを、その項目の波及の一覧と独立設計を手に深く見る。下請けは覆っていない当たりの全部に答える（覆っている／影響しない＋理由／block）。束ね役は下請けの答えを項目ごとにまとめて返す。
3. **相乗りの審査**: その往復で開いた項目が全部 clean になった時、束ね役は同じ往復の最後に相乗りの下請けを 1 つ起こす。下請けは全部の項目と、機械が出した「項目どうしの重なり」（2 つ以上の項目の allowed_paths・波及の一覧に出たファイルと試験）を見て、枝をまたぐ穴（同じファイルへの食い違う変更・順番の依存・重複・まとめられる所）を挙げる。195g なら項目 1 と項目 2 が両方 report.py の always_rows を変えるので、ここで突き合わせる。
4. **受け付け（機械）**: 開いた項目の全部に答えが在るか、覆っていない当たりの全部に答えが在るか、前の往復の block の key の全部が resolved か挙げ直しか（今の決まり）、全部が clean の往復に相乗りが走ったか、を確かめる。足した欄（項目ごとの答え・相乗り）は役の型にだけ在り、盤面へ渡す前に faces の和に畳む（今の `resolved` と同じ道。写しの graph は変えない）。
5. **抜け方（`converge.decide` を項目ごとに）**: 項目ごとに clean・persisted・again を出す。clean の項目は閉じ、次の往復で審査も直しもしない（直しの受け付けは閉じた項目の中身の hash が変わっていたら拒む）。相乗りの block は、その穴に名指された項目だけを開き直す。全体の抜け方は「全部の項目が閉じ、相乗りが clean」で clean、柵の往復で開いた項目か相乗りの block が残れば unsettled、項目のどれかが persisted なら persisted（その項目は保留にして、ほかの項目は柵まで進める）。
6. **直しの役**: 開いている項目と、相乗りが名指した項目だけを直す（今どおり修正案の役の会話の続き）。

項目の見分けは unit_keys の組で持つ。直しの役が項目を組み直した（unit_keys の組が変わった）時は、組が変わった項目を新しい項目として開く。

### 2.4 Archon の上でどう並べるか（選んだ形と理由）

候補は 3 つ:

- (a) **fan_out**（Archon が include の子を同時に走らせる）: 採らない。理由は 3 つ。今は線の最上段の fan_out しか測っていない（`blk-plan` の中では盤面を開く所で拒む）。Archon は AI の起動の前に、どの子の起動かを包みに渡さない（merge e654b0c2 の止まり）。盤面の節 `p2.plan_review` は 1 周に 1 つの出力しか受けないので、子ごとに盤面へ渡せない。
- (b) **同じ深さの loop_group の節を枠の数だけ並べる**（枝 1・枝 2…の節を YAML に書き、項目の数で `when:` を切る）: 段 1 では採らない。節の名で包みが起動を見分けられる点は良いが、Archon が依存の無い節を本当に同時に走らせるかを works は測っていない。枠の数が新しい数の決まりになる。YAML の重複を試験で縛る手間も要る。
- (c) **Agent の道具での並べ（採る）**: Archon の節は 1 つのまま、束ね役の会話の中で下請けを同時に起こす。審査の下請けは読むだけで、parallel-units が要った単位の worktree・柵の外し・差分の当てが要らない。盤面への渡しは今どおり往復ごとに 1 つなので、写しの graph と盤面の決まりを変えない。

(c) の注意:

- 事前審査の節の allowed_tools に Agent を足す。下請けは Claude Code の型で道具を持つので、書かない事は 2 つで縛る。会話の設定の permissions.deny が下請けにも掛かる事と、今の「読むだけの役の作業ツリーの比べ」（事前審査の後に作業ツリーが変わっていたら拒む）。下請けにどの道具が残るかは段 1 の最初の Task で本物の起動で測る。
- 下請けは会話を持たないので、往復をまたいで同じ項目を同じ下請けに見せ続ける事はできない。毎往復、前の往復のその項目の block と直しの答えを下請けのファイルに書いて渡す（今の事前審査の 2 往復目からと同じ）。
- 束ね役が下請けを起こさずに自分で全部を見る事を、受け付けは見分けられない。下請けの起動の数と項目の数を、包みの起動の記録（Agent の呼び）で突き合わせ、合わない時は trace に名指す（拒みはしない。拒むと役の言い分を検査できないので、まず測る）。
