## 分かったこと

1. **差分を見る審査は、もう最後に 1 回ずつ。** 修正が全部済んだ後に、レンズ・差分の審査・手直し・独立の目が 1 回ずつ走った（壁の時計で lensing 0.2 分・reviewing 0.4 分・refixing 1.4 分・eyeing 1.9 分、合わせて約 4 分。run の約 1%）。単位ごと・受け付けの回ごとに差分を審査する所は無い。線の形でも、差分の審査（include `reviewing`）と独立の目（include `eyeing`）は `darkfactory/darkfactory.yaml` に 1 つずつで、計画の項目の直し（refitting）や判定のやり直し（rejudging）を通っても合流してから 1 回走る。依頼 243 の「審査は最後に 1 回」は、差分の審査については今の形のままで満たしている。
2. **2 回目の差分の審査（review2）は入力が変わった時だけ。** 手直しの役が穴を fixed と答えた時だけ走る（`blk-refix/blk-refix.yaml` の route1）。195g では手直しが差分を戻した（`fix-delta2-r1.patch` は `fix-delta-r1.patch` の逆）ので、見る差分が変わっていた。
3. **計画の審査の 3 回は、毎回ちがう計画を見ている。** 1 回目の 9 件の block を受けて修正案の役が直し、2 回目・3 回目は直した案を新しい会話で審査した（`r1/plan-converge.json`）。入力が毎回変わるので、決まりの上で省けない。修正の前の関所なので、最後に動かすこともできない。
4. **報告の初見の読み手の 3 回も、毎回ちがう下書きを読む。** 省けない。
5. **同じ入力でテストを 2 度走らせた所が 2 か所ある。**
   - (a) 修正前の木で test_cmd を 2 度: start の p0.local_checks が宣言の段の後に test_cmd（`WORKS_TESTS=fast sh works/tests/run.sh` と根の柵）を走らせ（87.4 秒・緑）、約 50 分後に tdd-start が同じ木で同じ test_cmd をもう 1 度走らせた（`tdd-1/test-cmd-0.log`。約 1.3 分）。間の工程（判定・設計・計画）は作業ツリーを書かない約束の工程。結末が違った（tdd-start の方は赤 3・誤り 9）のは、節の環境の `ARCHON_*` が試験に漏れた不具合（0.2.25 で直した）のためで、木とコマンドは同じだった。

## 案

### 案 A: 修正前の木の test_cmd の結末を tdd-start が使い回す

- 中身: p0.local_checks が test_cmd の段を走らせた時の作業ツリーの木（追跡の外で無視されないファイルも含む）とコマンドを控える。tdd-start は、今の木とコマンドが控えと同じなら走らせずに控えの終了コードとログを元の結末に使う。違えば今どおり走らせる。
- 配線: 控えは線の側（start）が書き、パスを `darkfactory/darkfactory.yaml` の with で blk-fix に渡す（blk-fix は出どころを知らない。入力は「修正前の木で test_cmd を走らせた控えのパス。空は無い」の形で述べる）。
- 見込み: 1 run 約 1.3 分。
- 止めた理由: tdd-start の元の結末を組む所は `blk-fix/lib/tddloop.py`（`start`）で、いま別の実装役が直している。その後に回す。

### 案 B: 最後のテストが、修正前の CI と同じ木なら段の結末を使い回す

- 中身: `entry.run_ci` が engine に渡す runner（今は `_with_test_cmd` が包む `board.tree_runner`）を、もう 1 段包む。段ごとに（作業ツリーの木・argv・走らせる所）を鍵にした控えを盤面の共有の記録 `runs/` の下に残し、p4.ci の時に鍵が p0.local_checks の物と同じ段は走らせず、控えのログを今の試行のログの置き場へ写して前の行を返す。試験の報告（junit）を宣言した段は、報告の新しさを `checks_reply` が `started` で見るので使い回さない。
- 見せ方: 使い回した段は trace に 1 行残し、最後の関所と報告の「テストの一式」の行に「使い回した（同じ木）」と出す。写しの engine が組む素材の文は「engine が宣言を走らせた」のままなので、works の側の行で補う。
- 見込み: 195g で 4.4 分。差分の在る普通の run では 0。
- 持ち主に決めてほしいこと: 鍵に入れない物（git が無視するファイル・環境）を入力と見なさないでよいか。195g の (a) の赤のように、木とコマンドが同じでも環境で結末が変わった前例が在る（その不具合は 0.2.25 で直した）。効くのは差分が空の run だけなので、入れる値打ちが小さいとも言える。

### 案 C: 宣言の段に読む物の範囲を足し、差分が触らない段は修正前の結末を使い回す

- 中身: `.review-checks.json` の段に任意の欄（読む物のパスの形）を足し、最後のテストは、差分の変えたパスがどれも段の範囲に当たらない段を走らせず、p0.local_checks のその段の結末を使う。GitHub Actions の paths の絞りと同じ考え。
- 見込み: このリポジトリで 1 run 約 3 分（graphloops の pytest の段）。
- 持ち主に決めてほしいこと: 宣言の形は本流の graphloops の物で、読み方は写しの engine（`.shared/core/graphloops/`）に在る。本流の宣言の形を変えるか、works の側だけで別の欄を読むか。範囲を書き違えると、触った段を走らせずに緑と言う（確かめが黙って消える）。範囲の外の変更に当たった時は走らせる、の向きに倒すかも決めがいる。
