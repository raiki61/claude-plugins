## 3. 目標と保証の形

### 3.1 何を保証するか・何は保証しないか

保証する:

1. 柵の表に載った考え（住処の在る 13 と、段 3 で数を掛ける散らばりの 9）を知る場所は、どの道の変更でも黙って増えない。増えたら CI か run の中の機械が赤にし、増やすなら表と地図を直す差分が要る（外の開発は暫定の道なので、その差分にも工場の審査の run は足さない。決め 3）
2. 構造の目が「汚れる」と言った単位は、修正案が避け方に従うか、従わない訳を書くかのどちらかでしか先へ進まない。訳は報告と最後の関所に並ぶ
3. 直しの後に、実物の差分で知る場所の増減と写しの塊を機械が測る（軽量の run でも省かない）
4. 構造の目が決めきれない設計の問いは、修正の前の関所に案の形で上がる（最後まで持ち越さない）
5. 出荷ごとに全体を測り、前の出荷より悪くなった所が見える

保証しない（AI の判断の質で、機械では縛れない物）: 選んだ避け方が本当に一番簡潔か。ここは判断の 1 軸の文を役に配ることと、測り（Task 2.8）で見張る。

### 3.2 1 歩の輪（1 本の run の中）

```
依頼 → 判定 → 構造の目（地図・決まり・実測を見て、汚れる形と避け方。決めきれなければ人へ上げる行）
     → 修正案（避け方に従うか、外れの訳を項目に書く）→ 事前審査（従ったか・訳を照らす）
     → 修正前の関所（目が決めきれなかった問いはここで早く聞く）→ 修正
     → 直しの後の実測（実物の差分で、柵の数・新しい名の場所・写しの塊）→ R1・R3（1 軸と数を見る）
     → 最後の関所（増えた所・外れの訳を並べる）→ 報告・次の依頼の下書き
```

1. 構造の目に地図と決まりを渡す: 今の目は単位 1 つと実測だけを見る。これに、触る考えの地図の行（機械が単位のパスから選ぶ）・対象の決まり（今は「控えるだけ」の入力 policy_path の中身、根の ARCHITECTURE.md・AGENTS.md）・知る場所の数を渡し、判定を「知る場所が増えるか」の 1 つの問いで下させる（Task 2.3）
2. 修正案は従うか訳を書く: 修正案の works の欄（`.shared/core/planmarks.py`）に、汚れる行ごとの「従う／外れの訳」を必須で足し、計画の受け付けが欠けを拒む（Task 2.4）。判定の処方（prescriptions）も同じ欄で扱う
3. 直しの後に実物で測る: `blk-structure` を直しの後にもう 1 回差し込み、修正の前の版から今の作業ツリーまでの差分を `measure.py --diff` と柵の道具で測る（Task 2.5）。柵の表を持つ対象では、住処の在る考えの知る場所が増えた run は結末を fixed にせず、増えた所を次の依頼の下書きに載せる（構造の観点の計画の決め事 4 の、R1 の作り直しと同じ扱いを機械で）
4. 1 軸を役へ: 「目的と keep-essence を保って、全体がより簡潔になるか」の文を 1 か所（`.shared/core/concepthome.py`）に置き、修正案・事前審査・R1・R3・構造の目に配る。R1 の「最小」は行数でなく知る場所の数で量る（Task 2.1・2.2）
5. 決めきれない物だけ人へ: 構造の目の行き先に「人に上げる」を許し（今は `eye.py` の `ROUTE` が「自分で決める」に固定）、その行を修正前の関所の項目に載せる（関所の決め手の欄 `gatemarks.FIELDS` と推し RECOMMEND をそのまま使う）。関所が聞かずに通す行は、決め手の出どころが現物に在ることを機械が確かめる（Task 2.6）

### 3.3 全体の歯止め（run をまたぐ）

1. 散らばりの 9 にも数を掛ける: 柵の表に、住処の無い考えの語の形と今の知る場所を既知の漏れとして置く（知ってよい所は空）。数は減る向きにだけ動く。まとめが済んだ考えは住処ありに替える（Task 3.1）
