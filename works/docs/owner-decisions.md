## 平たく言うと（3 行）

- 持ち主が「工場（darkfactory）はこう判断し、こう作り、こう人に上げる」と決めたことを 1 行ずつ並べ、それが works の中のどの部品に入っているかと、どれだけ強く効いているかを書いた地図。
- 決定は会話の記憶に置かず、works のライン・ブロック・役・機械の確かめに入れて、どの対象のリポジトリにも効かせる（持ち主 2026-09-29「メモリじゃなくてこのグラフの仕組みとして入れないといけない」）。
- この地図で大事なのは各行の「隙間」。隙間は、決定がまだ works に入っていない所で、直す候補になる。

## 語

- 決定: 持ち主が言葉で決めた、工場の判断・作り・人への上げ方の決まり。出典は持ち主の言葉と日付
- 住処: その決定を今持っている works の部品（ブロック `blk-*`・役の指示書・`.shared/core` のモジュール・入力・表）
- 強さ: 次の 3 つのどれか
  - 機械で強制: 機械の確かめ・受け付け・試験が、決定に反する形を拒むか、線の動きを決める
  - 役への助言: 役（AI）の指示書に書いてあるだけで、守ったかを機械が見ない
  - 未実装: どこにも無い（設計書や計画だけが在る物も含む）
- 隙間: 住処が決定の一部しか持っていない所。直す時に足す先の部品も書く
- 用語のほか（線・役・盤面・関所・包み）は `docs/concepts.md`（枝 wip/concept-fences）と `README.md` の意味で使う

## 判断の軸

### `one-axis` 全体がより簡潔になるかの 1 軸で決める

- 決定: 迷い所は場合分けを足さず、「依頼の目的を満たし、守る仕組みが働いたまま、全体がより簡潔・綺麗になるか」の 1 つで決める。削る・弱める変更も、この軸で良くなるなら通す
- 持ち主の言葉: 「そういう場合ごとの対応を書いたらキリがないから、より綺麗にスマートになってたらいいってことだよね本質として」（2026-10-02）。「単に上位互換のものを作りたいってだけ。移植するときのあるあるは、削ってしまったとか」（2026-10-03）。「全体が綺麗かはかなり重要。特に AI にコーディングさせるにおいて」（2026-10-09）
- 住処: どの役にもこの軸そのものは渡っていない。近い物は 3 つ
  - 構造の目（`blk-structure/lib/eye.py` の `QUESTION`）: 修正の前に「次に同じ所を直す人が、設計を知らないまま足す形が増えるか」を聞く
  - 事前審査の穴の種類（写しの指示書 `p2.plan_review.md` の copy・entrance・contract_drift・dead_path・scope_creep）
  - 独立の目の R1（最小性。`blk-eyes/commands/r1-minimality.md`）
- 強さ: 役への助言（一部）
- 隙間:
  - 修正の後に「全体が簡潔になったか」を見る所が無い。構造の目は修正の前の案だけを見る
  - 修正案の狭め（narrows）の行は、決め手の出どころが在れば人に聞かずに通る（`gatemarks.decided`）。通す条件に「全体が簡潔になるか」が入っていない
  - works 自身の守る仕組みは `docs/keep-essence.md` に在るが、対象のリポジトリが「守りたい能力」を宣言する口は無い（在るのは守りのファイルの一覧と方針の文書だけ）

### `dirty-area` 汚れる領域は先に設計し、決まらない物だけ上げる

- 決定: 設計の話は 2 つの軸で扱う。①自明か ②設計なしで踏み込むと汚くなる領域か（共有の物を run ごとに書き換える・責務が 2 か所に割れる・既存の仕組みを横から曲げる など）。②に当たれば先に設計の段で先例を調べ、汚れない形を選んで記録して進める。考えても決まらない時だけ、案として人に上げる
- 持ち主の言葉: 「何でもかんでもエスカレーションされてたら大変なので本当にまあ一つの軸は自明かどうかっていう軸なんだけど、それ以外は設計話に踏み込むと汚くなりそうな領域だったりとか」（2026-09-29）。「関所でも一応考える認識であってる？今回の汚くならないかはどうしても難しい場合は人にエスカレーションというのは変わってないよ」（同日）
- 住処: 構造のブロック `blk-structure`
  - 段 A（AI なし）: `scripts/measure.py` が単位のファイルを git で実測する（伸び・変更の頻度・写しの在りか・入口の数・設定の口）
  - 構造の目（道具ゼロ）: 6 つの形（`eye.py` の `FORMS`）で「汚れる・汚れない」を判じ、推しの案・捨てた案と代償（`design-row.schema.json` の chosen・rejected）を書く
  - 目の行は修正案の役の指示書の頭に貼られる（`.shared/core/structmark.py` の `PLAN_ASK`「守るか、守らないなら理由を書け」）
- 強さ: 役への助言
- 隙間:
  - 人に上げる道が無い。行き先はいつも「自分で決める」（`eye.py` の `ROUTE`）。設計書 `docs/specs/2026-09-29-structure-block-design.md` の 6 節・10 節の S3（設計の関所と戻り）が未着手
  - 修正案が目の推しを守ったかを機械が見ない
  - `measure.py` の差分の形（`--diff`。案の patch を当てた前後の増減と新しい名の場所）は試験でしか呼ばれず、線から使われていない（設計書 11 節の段 B が未決）

### `two-places` 2 か所目に出たら先に部品へ寄せる

- 決定: 直しや機能を足す前に、その考えに名前の付いた部品（1 つのモジュール・1 つの schema・1 つの表）が在るかを確かめる。無くて 2 か所目なら、先に部品へ寄せてから足す。審査は振る舞いだけでなく、知る場所が増えたかも見る
- 持ち主の言葉: 「そういう風にあなたが作りこまなかったのも理由としてはあるのでは」「それこそ弱点な気がする」「汚くなったか見る所が機能してないか粗いか」（2026-10-09）
- 住処:
  - 事前審査と差分の審査の穴 copy（「既に正本を持つ規則・型・語彙・手続きを別の場所に写していないか」。`blk-delta/commands/delta-review.md`）
  - 段 A の写しの在りか（`measure.py`。空行を落とした 6 行の塊のハッシュを追跡ファイル全体で引く）。ただし修正の前の単位のファイルにだけ当たる
  - works 自身には考えの住処の地図と柵（`docs/concepts.md`・`tests/test_concept_fences.py`。枝 wip/concept-fences で、この版には未合流）
- 強さ: 役への助言
- 隙間:
  - 対象のリポジトリの差分について、「この直しで、ある考えを知る場所が増えたか」を機械で数える所が無い。審査役は差分を起点に読むだけで、散らばりは差分ごとに 1 か所ずつ増えるので見えにくい
  - 写しの穴が見つかっても、手直しの役に回るだけで、関所や結末を変えない

## 関所と人に上げる物

### `obvious` 自明な物は聞かずに決める

- 決定: 決め手（人の前の決定・人の方針・対象の同じ場面・世界の解）のどれかで答えが 1 つに決まるなら、聞かずに決めて出どころを残す。決め手どうしが割れる・優先の付け方で変わる・前の決定や方針とぶつかる時だけ聞く
- 持ち主の言葉: 「下位互換になりそうなやつだけ注意して。同等か上位互換なら考えておしでいいよ」（2026-09-26）。「ようは自明かそうじゃないかってことです」（2026-09-28）。「あとは全部おしでいいよ。自明なものは聞かないで」（2026-09-26）
- 住処:
  - 判定役の指示書 `blk-judge/commands/diagnose.md` の 7 項（4 つの決め手と、人に問う 3 つの場合。人に回す行は `undecided_because` が要る）
  - 修正前の関所の決め手の欄（`.shared/core/gatemarks.py` の `FIELDS`。`decided_by` が在り、`undecided_because` が空で、柵の印が無い行は `decided` が真になり、聞かずに通って報告に並ぶ）
- 強さ: 機械で強制（ただし欄は役の自己申告）
- 隙間: `decided_by` は空でない文なら何でも通る。出どころ（ADR・URL・対象のファイルと行）が現物に在るかを確かめない。食い違いの申し出では名指しの在りかを機械が確かめている（`.shared/core/conflict.py` の `cite_problem`）ので、同じ確かめを決め手にも当てられる

### `gates` 関所は答えで次の動きが変わる時だけ

- 決定: 人に聞く関所は、答えで run の次の動きが変わる時だけ開く。情報だけの物は報告の冒頭に並べる。止めるのは 4 種類だけ（①取り消せない・外に出る ②安全（秘密・権限を広げる） ③今ある能力を減らす・守る仕組みを外す・方針を変える ④仕様も方針も定石も決めず、後で測れず戻せない）。ほかは裁きの 1 行を残して進む
- 持ち主の言葉: 「なんかこの報告もいちいち聞かなくてよくないかなって思う」（2026-09-30）。「持ち主に見てほしいと言ってくる判断をほとんどあなたがさばけてる…あなたの判断基準とかやり方をグラフにいれたら帰ってこないのでは」（2026-10-02）
- 住処:
  - 柵の印（`gatemarks.py` の `FENCES`: 外への書き込み・取り消せない操作・方針の文書の変更・守りを広げる・web の結果が新しい疑いを出した）
  - 聞かずに通した行の 1 行（`gatemarks.lines`。報告と最後の関所に並ぶ）
  - 最後の関所の開き方（`entry.py` の `FINAL_GATES`: always・when_needed・protected_only）
  - 無人の run で範囲を広げるだけの案の直しは関所を開かない（`.shared/core/replan.py`。持ち主 2026-10-08）
- 強さ: 機械で強制（一部）
- 隙間:
  - 4 種類のうち③の「能力を減らす」と④の「測れず戻せない」に当たる柵の印が無い
  - 最後の関所の既定が入口で違う。線の入力の既定は always、`dev/use.sh` は protected_only、`dev/dogfood.sh` は always（`docs/concepts.md` の `human-gates` の散らばりと同じ根）

### `world` 人に回す前に世の中の解を当たる

- 決定: 人に聞く前・機構を作る前に、同じ問題を世の中がどう解いているかを一次情報（標準・公式文書・著名 OSS）で当たる。web は必須でない。鵜呑みにせず、損が小さくない決定は独立の導出と突き合わせ、割れた時だけ web、それでも割れたら人
- 持ち主の言葉: 「世界の解があるでしょ。ここで再発明するようなことじゃない」「あなたの中ですべて発明しようとするな」（2026-09-24）。「webをひくことはMustではないが、割と世界が解いてることが多い」（2026-10-01）。「鵜呑みにせず最適を考えて」（2026-10-02）
- 住処: 判定役の 7 項 (d) と先行例の行（`diagnose.md`。引いても当たらなければ `searched` が要る）、関所の行の `world` の欄（`gatemarks.py`）
- 強さ: 役への助言（欄の有無は受け付けが見る）
- 隙間: 「独立の導出と突き合わせ、割れた時だけ web」の段取りは無い。判定の裏取り（`blk-judge` の verify）は在るが、2026-10-08 から既定で切っている

### `web-split` web の調べは集める役と判断する役に割る

- 決定: 集める役は URL と原文の抜き書きだけを返し、要約も評価もしない。判断する役（opus）が抜き書きだけを材料に、一次情報か・古い版でないかを決める。機械が、返った URL を本当に読んだか・抜き書きが本文に在るかを照らす
- 持ち主の言葉: 「WEB からとってきてまとめるところは sonnet とかつかってもいい」、回す側が「わかりました」とだけ返したのに対して「わかりましたじゃなくて、考えて」（2026-09-29）
- 住処: 設計書 `docs/specs/2026-09-29-structure-block-design.md` の 5 節と 10 節の S4 だけ。判定役は自分で WebSearch・WebFetch を使う
- 強さ: 未実装
- 隙間: 読んだ記録（`.shared/core/reads.py`）は Read だけを残し、web の取得の URL と本文を残さない。抜き書きの照合ができない

### `ask-shape` 上げる時は案の形で、初見に通じる詳しさで

- 決定: 上げる時は案として出す（推しを 1 つ・捨てた案・代償）。選択肢だけを並べず、何の話か・具体例・答えごとに何が変わるか・推しを、文脈の無い人が決められる詳しさで書く
- 持ち主の言葉: 「ふつうに案として私にエスカレーションしたりする必要がある」（2026-09-29）。「聞きたいことがあれば初見にもわかりやすく詳しく教えて」（2026-10-02）。選択肢型の問いに「なに？」（2026-09-12）
- 住処:
  - 関所の行の推し（`gatemarks.py` の `RECOMMEND`: answer・note・why）
  - 構造の目の行（`design-row.schema.json` の chosen・rejected・chosen_reason）
  - 報告の頭は道具ゼロの初見の読み手が確かめる（`blk-report`）
- 強さ: 機械で強制（一部）
- 隙間: 関所の行には「捨てた案と代償」の欄が無い（構造の目の行には在る）

## 設計と構造

### `one-input` 入口ごとに流れを分けず 1 つの入力の形に

- 決定: 依頼・変更・PR の入口ごとに流れを分けない。どの入口も同じ入力の形（基の版・差分（空でもよい）・依頼の行（空でもよい）・付帯の材料）にそろえ、後の段は入力の中身（差分が空か等）だけで動きを決める
- 持ち主の言葉: 「抽象化するとやることは同じはず。プログラムでも同じでしょ。どの入り口でも最終的に環境変数に何をセットするのかだけみたいな」（2026-10-09）
- 住処: まだ無い。入口の種類は `.shared/core/entry.py` が決め、後の段が種類で分かれる（`request_entry` の名指しが works の 4 つのモジュールに約 70 か所）。計画は枝 wip/one-entry-plan
- 強さ: 未実装
- 隙間: 決定の全体

### `scope` 部品の状態は自分の置き場に閉じ込める

- 決定: 部品が読み書きしてよいのは、自分専用の置き場と宣言した入出力だけ。部品の中だけの状態は宣言させず、include の単位で置き場を自動で分ける。流れの道具（Archon）に触る所は小さな 1 つの口に集める。役どうしの聞き直しは塞がない
- 持ち主の言葉: LangGraph・Mastra に state が在るのは効く場面が在るから（2026-10-03。言葉の要約で、原文は残っていない）
- 住処: `.shared/core/scopes.py` と `.shared/core/manifest.schema.json`・ブロックごとの `manifest.json`、Archon への口 `.shared/core/flow_adapter.py`、聞き直しは範囲の相談の節（修正案を書いた役の会話の続き）
- 強さ: 機械で強制
- 隙間: 無し（型つきの共有 state は持ち主の推しどおり作っていない）

### `block-blind` ブロックは他のブロックを知らない

- 決定: ブロックの中に他のブロックの名前・出口・振る舞いを書かず、在る前提でも書かない。入力は形で述べ、どのブロックが作るかは線の側に書く
- 持ち主の言葉: 「他のブロックに他のブロックの情報が書かれてないかとか。ありきで書いてないかとかは注意しておいてね」「すべてのブロックやノードを疎結合にしないとノードごとの精度やコストやブラッシュアップが純粋にやりにくいよね。組み換えも」（2026-09-28）
- 住処: 試験 `tests/test_block_blind.py`（道具 `tests/blockblind.py`。既知の漏れは件数つきの表で、減らす向きにだけ動く）、繋ぎは `darkfactory/darkfactory.yaml`
- 強さ: 機械で強制
- 隙間: 既知の漏れの表が残っている

### `lang-neutral` 対象の言語の知識を持たない

- 決定: 言語ごとの表や差し替え口を作らない。言語をまたぐ事実上の標準（JUnit XML・git の差分・終了コード・SARIF・hash）は使ってよい。言語に依る見分けは、読むだけの AI の役が生の出力を読んで決める。works 全体でこれにそろえる
- 持ち主の言葉: 「抽象化が必要」「事実上の標準は書いてよい」「全体的に統一。そこだけじゃなくて」、「SuperPower だったり、抽象化したり、示唆したり、その言語のベストプラクティスだったりでいいのでは」（2026-10-03）
- 住処: 赤緑の判定は JUnit XML の結末で見る（`blk-fix/lib/tddloop.py`）。外す所の棚卸しは `docs/language-neutral-inventory.md`
- 強さ: 機械で強制（一部）
- 隙間: 言語を名指す分かれが増えたら赤にする柵が無い。TDD の輪のテストの名指しは pytest の node id の形を前提にした所が残る（`tddloop.py`）。既定の実行器は `dev/use.sh` が pytest の 1 コマンドからしか作らない

### `oss-as-is` 磨かれた外の物はそのまま使い版を固定する

- 決定: 世の中で磨かれ続けている物（superpowers など）は中に作り直さず、そのまま呼ぶ。works が勝る所だけを外側の関門として足す。版は固定し、黙って最新に従わない。開発を再開する時に新しい版を確かめる
- 持ち主の言葉: 「構造を変えてそっちのほうがよくなるなら、ぶつかることを恐れるな」「直接呼んでもいいのですよ」「私が勝ってるところがあればそのエッセンスを使える形で使えばいいだけ」「再開するときにその Ver を確かめるサイクル」（2026-10-02）
- 住処: `.shared/borrow/borrow.json`（版・commit・ファイルの hash）、`.shared/borrow/seams.json`、座の組み立てと固定の照らし（`.shared/core/seat.py` の `pinned`）
- 強さ: 機械で強制
- 隙間: 固定より新しい版が出たかを見る道具が無い

## run の形

### `small-core` 芯は 1 つ・独立設計が作り直しと言えば取り込まない

- 決定: 1 本の run の芯（直す面）は 1 つ。大きな物は設計を先に通して小さな run に割る。独立の目の R2 が作り直し（構造が独立設計と違う・芯が作られていない）と言った run は、部分を取り込まない
- 持ち主の言葉: 「修正する前に…設計の段階である程度固めるほうがいい」「ここ注意ね。汚くなりそうなところなんで」（2026-09-29）
- 住処: 判定役が依頼を単位に切る（`blk-judge`）。R2 の作り直しは結末を fixed にせず、次の run の依頼の下書きの prior_failures に載る（`.shared/core/report.py` の `R2_REDESIGN` と `prior_failures`）
- 強さ: 機械で強制
- 隙間: 依頼に芯がいくつ在るかを入口で見ない

### `carry` 1 run は 1 周・残りは次の run へ運ぶ

- 決定: 同じ run で 2 周目を回さない。審査の指摘や使っていて見つけた不具合は次の run の依頼にする。止まった run も無駄にせず、受けられた所は受けて先へ進む
- 持ち主の言葉: 「試験運用で実際に使っていき、不具合が出れば次のrunに出して回収していく」「2周目せずに次のrunっていめーじ」（2026-09-27）。「じゃあ大きく治して、とまっても無駄にならないようにあなたがフォローしたり」（2026-10-04）
- 住処: 次の依頼の下書き（`report.next_doc`・`next-request.json`）、修正の受け付けの 3 回目で受けた単位だけ先へ進める形（`docs/keep-essence.md` の 4）
- 強さ: 機械で強制（一部）
- 隙間: 最後の関所に付けた条件の文は報告に写るだけで、次の依頼の下書きに載らない（`gatemarks.answer_drafts` が拾うのは無人の run で止まった項目と保留の問いだけ）。持ち越しの考えそのものが散らばっている（`docs/concepts.md` の `carry-over`）

### `design-only` 改造の案は設計だけの run にまとめて流す

- 決定: 改造の案がいくつも在る時は 1 件ずつ直しの run に流さず、1 本にまとめて判定・計画・事前審査・独立設計までで止まる run に流し、結果を読んでから小さく割る
- 持ち主の言葉: 「全部を設計の壁打ちのところにだけ流してもめないかってこと いっきにね」（2026-09-30）
- 住処: 入力 design_only（`entry.py` の `DESIGN_ONLY_WORDS`。語の外は拒む）、修正前の関所を必ず開ける（`gatemarks.design_only`）
- 強さ: 機械で強制
- 隙間: 無し

### `model-effort` 段ごとに模型と effort を明示する

- 決定: AI の段の全部に模型と effort を書き、道具の既定に頼らない。割り当ては任されているが、結果（作り直しの率と費用）で比べて戻す
- 持ち主の言葉: 「別に effort は考えて最適化してくれたらいいよ」（2026-09-29）。段ごとの明示と今の割り当ては 2026-10-06 の持ち主の決定（`CHANGELOG.md` の同日の行）
- 住処: `.shared/core/stage-models.json`（前付けの無い役）と `.shared/core/agents/*.md` の前付け、試験 `tests/test_tool_parity.py`
- 強さ: 機械で強制
- 隙間: 無し

## works の外の決まり（開発の進め方）
