# 変更の記録（works）

works（Archon の上の生産ライン darkfactory の pack と、Claude Code 側の入口 `/works` スキル）の版ごとの、利用者に効く違いを新しい順に並べる。形は [Keep a Changelog 1.1.0](https://keepachangelog.com/ja/1.1.0/) に従い、版の番号は [Semantic Versioning](https://semver.org/lang/ja/) の形（x.y.z）で振る。節は Added（足した）・Changed（変えた）・Deprecated（やめる予定）・Removed（消した）・Fixed（直した）・Security（安全の直し）のうち、中身の有るものだけを使う。

版を名指しする git の tag（例: `works--v0.2.0`）の名前の決まり・付け方と、この記録を書き足す段は、リポジトリのルートの `docs/releasing.md` に在る。0.1.0 はこの記録に無い。

## [0.2.33] - 2026-10-06

### Added

- 修正案の段に波及の一覧を足した（線の木の段 1。設計は docs/plans/2026-10-06-tree-line.md）。機械が、修正案の項目が変える名（単位の key の `+` の後の名と、項目が足す名のうち対象に在る物）を `git grep` で引き、呼び出し元と試験（Python は試験の関数の id まで）を並べ、項目の書いてよいパス・受け入れと書き換えの試験に入っていない当たりを名指す。当たりのファイルが多い名は数だけを載せる（持ち主の決定 2026-10-06）。修正案の役は書く前に単位ごとの一覧を、直しの役と事前審査は項目ごとの一覧を受け取る。直しが触る当たりは案の範囲に先に入れさせ、修正の時に範囲の相談をしなくて済むようにした。修正の段には入力 `ripple_file` で渡し、範囲の相談の節が名指す（範囲の外の当たりを触る前に相談させる）。run 195g の事前審査の block 9 件のうち 5 件はこの波及の見落としで、審査役は 1 往復 4〜5 分の大半を探しに使っていた。

### Changed

- 既定の修正の形 g3 の TDD の輪で、振り分けの直後に書いてよい範囲（修正案の項目の allowed_paths と受け入れのテストのファイル）が互いに重ならない tdd の単位が 2 つ以上あれば、その単位のテスト → 赤 → 直し → 緑 → 整えを単位ごとの小さい worktree で同時に回すようにした（依頼 243 の並べの 2 段目。今までは輪の中は 1 単位ずつで、run 195g の輪は 5 単位で 67 分かかった）。確かめの節が run ごとの置き場の下に worktree を切り、並べの周（段 lanes）の輪の役が単位の下請けを Agent で 1 つのメッセージで同時に起こす。下請けは段ごとに機械のコマンド（`blk-fix/lib/tddlanes.py`）を走らせ、赤・緑・凍ったテスト・名指しの外のテストの書き換え・消えたテスト・test_cmd・軽量の単位の扱いは今の輪と同じ関数が単位の worktree で決める。次の確かめの節は、単位ごとに赤を確かめ直し（単位の頭の木に赤の時のテストのファイルだけを置いて名指しを回す。下請けが書ける控えの赤の記録を信じない）、差分を作業ツリーへ 3 方向で当て、当てた後の木で当てた単位の名指しのテストと変更に直に関わる試験の緑をもう 1 度確かめ、下請けの書き込みの記録を作業ツリーへ写す。済まなかった単位・赤が再現しない単位・当たらない単位・当てた後に赤い単位は、今どおり作業ツリーで 1 つずつ最初の段から回し直す（前の試みの差分を指示書に添える）。範囲の分からない単位・重なる単位・形 af と current・tdd の単位が 1 つの run は今と同じ。輪の役の道具に Agent を足し、包みは g3 の外の輪の役の Agent を拒む。輪の出口に欄 lanes（単位ごとの結末と段のコマンドの呼び）を足した（calls は今どおり輪の役の起動 1 回に 1 行）。設計は docs/plans/2026-10-06-tdd-parallel.md
- 修正案の事前審査を項目ごとにした（線の木の段 1）。事前審査の役は束ね役になり、開いている項目ごとの下請けのファイル（機械が書く）を Agent の道具で 1 つのメッセージに並べて同時に起こし、下請けは 1 項目だけを波及の一覧と一緒に深く見て、覆っていない当たりの全部に答える。開いた項目の全部が clean の往復の最後に、項目どうしの関わり（同じファイルへの食い違う変更・順番・重複）を見る相乗りの審査の下請けを 1 つ起こす。受け付けは、開いた項目の全部の答え・当たりの全部の答え・相乗りの審査を確かめる。block の無い項目は閉じて次の往復で審査も直しもせず（直しの役が閉じた項目を変えたら拒む）、同じ block が続いた項目は保留にしてほかの項目を柵（3 往復）まで進め、相乗りの block は名指した項目だけを開き直す。修正前の関所の理由と報告の壁打ちの行に、固まった項目と保留の項目を並べる。人の関所の決まりは変えない（保留か柵で止まった案は今どおり修正前の関所で止まる）。前は 1 人の審査役が全部の項目を毎回読み直し、run 195g では 3 往復とも別の項目の穴が出て関所で止まった。下請けの起動の数は読んだ証拠の節が盤面の trace に名指す（拒まない。本物の run で測る）。写しの graph は変えない（足した欄は役の型にだけ在り、盤面へ渡す前に外す）

## [0.2.31] - 2026-10-06

### Added

- 修正役と下請けが、修正案の項目の書いてよい範囲の外（直しに伴う変更の記録など）や凍ったテストの書き換えが要る時、機械のコマンド（`blk-fix/lib/askplan.py`）で修正案を書いた役の会話を再開して範囲を相談できるようにした（持ち主 2026-10-06「範囲を広げるかは仕様の判断なので計画さんと会話して決める」）。会話の記録を run ごとの置き場の私物の設定の置き場へ写して `--resume` するので、元の会話は変わらない。答えは allow・deny・defer で、許された範囲は受け付けが項目の範囲とテストの変更の許しに入れる（最後の関所の書き換えたテストの一覧にも並ぶ）。相談は全部盤面の trace に写し、報告の冒頭に並べる。食い違いの申し出は、相談が聞けない時と仕様として意見が割れた時の道に残る。線 darkfactory は修正の 2 つの段に入力 `plan_session: plan` を渡す（設計は docs/plans/2026-10-06-ask-planner.md）
- 修正役が返答の前に、受け付けの事実の確かめ（凍ったテスト・書き込みの出どころ・承認済みの修正案の範囲）を試験なしで回せる事前の確かめのコマンド（`blk-fix/lib/factchecks.py`）を足した。受け付けと同じ口（確かめを scripts/accept.py から lib/factchecks.py へ移した）で、盤面は読むだけ
- 前の run で最後まで通らなかった物を次の run に引き継ぐようにした。受け付けの出口は、受け付けごとの最後の結果を scope の根の `accept-last.json` に上書きで残し（出し直して通った拒否は残らない）、報告の段が run の終わりにそのうち通らなかった物の最後の理由と、独立設計の目（R2）の作り直し（redesign-needed）の理由を盤面の根の `prior-failures.json`（`[{where, text}]`）にまとめ、報告に節「次の run に引き継ぐ落ちた理由」を出す。依頼のファイルに欄 `prior_failures`（同じ形）を足し、次の run では判定役の材料と修正案の役の指示書にだけ「直す穴ではない注意」として貼る。目的の役と独立設計の役には渡さない（前の run の判断を追認させない）。今までは run が前の run の落ちた理由を覚えておらず、同じ落ち方をくり返した。

### Changed

- 次の run の依頼の下書き `next-request.json` を、findings の配列から object `{"findings": [...], "prior_failures": [...]}` に変えた。そのまま次の run の依頼に使える（配列の形の依頼も今どおり読む）。R2 の作り直しの行は findings から外し、prior_failures にだけ載せる（findings は目的の役が生のまま読み、独立設計の入力に流れるため）。
- TDD の輪の役の指示書（tdd-prep）に、前に済んだ単位の引き継ぎの節を機械が書くようにした（単位の key・直したファイル・緑にしたテスト・整えの結末。諦めて direct に回した単位・申し出で止めた単位はそう書く）。最初の単位と振り分けの段には載らない。単位ごとに新しい会話で起こす準備で、会話はまだ今までどおり継ぐ（設計は docs/plans/2026-10-06-fresh-session.md）。
- 修正の段の役を単位ごとに新しい会話で起こすようにした（依頼 243 の 2）。TDD の輪の役は、同じ単位の段は会話を継ぎ、単位が替わる周だけ包みが新しい会話で起こす（支度が run ごとの置き場に書く単位の鍵で見分ける。起動の記録の session に unit が載る）。既定の修正の形 g3 の修正役は、輪の後に残った単位を自分の 1 つの会話で直さず、修正案の項目（項目に無い単位は 1 単位ずつ）ごとに新しい会話の下請けを Agent で起こす（g1 と同じ型の節。輪が緑にした単位には起こさない。輪が全部を緑にした周は前のとおり）。前の単位の物は会話の履歴でなく引き継ぎで渡す。今までは輪の 24 周が 1 本の会話に積もり、修正役は 5 単位を 1 つの会話で直して 86 分かかっていた（run 195g）。
- 既定の修正の形 g3 の修正役の 1 回目の周で、書いてよい範囲（修正案の項目の allowed_paths と受け入れのテストのファイル）が互いに重ならない項目の下請けを、項目ごとの小さい worktree で同時に回すようにした（依頼 243 の並べ）。支度が run ごとの置き場の下に worktree を切り、修正役はその下請けを 1 つのメッセージで同時に起こし、機械のコマンドが差分を項目の番号の順に作業ツリーへ 3 方向で当てる。当たらない項目は作業ツリーで順に直し直し（直しは差分のファイルに残る）、範囲の分からない項目・重なる項目・出し直しと裁定の後・g1 は今どおり順。修正役と受け付けの間に締める節 fix-units を足し、当て残しを機械が当て、下請けの書き込みの記録を作業ツリーへ写して worktree を片付ける。受け付けの決まりは変えない。包みは、run ごとの置き場の下でこの作業ツリーの守りの参照を持つ worktree だけを書かせない所から外す（設計は docs/plans/2026-10-06-parallel-units.md）。
- 判定が切った単位ごとに、機械が深さ（軽量か標準）を決めるようにした（持ち主の依頼 2026-10-06。計画 `docs/plans/2026-10-06-variable-depth.md`）。修正の前の節 `h-depth` が、修正案の項目の形（触るファイルが 3 個以下・受け入れと書き換えのテストが 2 本以下・schema や yaml・json の表を触らない・テストのコマンドか実行器が在る）を全部満たす単位を軽量にし、盤面の根の `depth.json` に理由と一緒に残す。修正の後の節 `h-redepth` は、食い違いの申し出・止めた単位・答えていない問い・案の直し・再審のどれかが立てば標準へ上げる。全部の単位が軽量のままの run だけ、差分の審査（とそれに続くレンズ・手直し）と独立の目（コメントの削除候補と R1〜R4）を省き、報告の冒頭 2 に「軽量で省いた: …」と 1 行ずつ名指す。どれも 2026-10-05 の小さい自分食いの run（依頼 245・246）で何も見つけなかった物。R1〜R4 と差分の審査を省けるよう、持ち主の決定（2026-10-06）で写しの graph のこの 5 節に optional を足し（台帳 COPIED_FROM の ! 行）、周の記録と検証器に省いた R の値 skipped（理由つき・阻害でない）を足した。graph_sha は 2eb140b879e5 に替わる（盤面の手本は撮り直した）。AI の報告は省かない。標準は今の振る舞いのすべて。入力 `thickness` の既定は「自動」になり、「軽量」「標準」で全部の単位を固定できる（今までは「標準」だけを受け、「軽量」は拒んだ）。ブロックはレンズの `skip`・独立の目の `skip_optional`（省く理由の文。空は今どおり）の平の入力を受けるだけで、深さの規則は線だけが持つ。修正のブロックの中の単位ごとの段に深さを効かせる口（入力 `unit_depths`）は、単位ごとの修正役の並行の後に入れる。
- 修正のブロックに入力 `unit_depths`（`{"<単位の key>": "軽量" | "標準"}` の JSON の文字列。既定は空）を足し、線の 1 回目の修正の段に単位ごとの深さを渡すようにした。軽量の単位だけ、TDD の輪が緑の後に run のテストのコマンド（test_cmd。dogfood では 1 回 4〜5 分）を走らせない（同じコマンドを線の最後のテストが木の全部で走らせる）。赤・緑の確かめ・受け付けの選んで回す試験・裁定の輪は省かない。標準の単位・名指しの無い単位・2 回目の修正の段（案の直しの後で全部の単位が標準へ上がる）は今どおり。TDD の輪の出口の単位の欄 test_cmd に、走らせなかった印 light が加わる。
- 修正役の返答の受け付けと TDD の輪の緑の回が走らせる試験を、変更に直に関わる物だけにした（持ち主の決定 2026-10-06）。選ぶのは、変えた・足した試験、変えたファイルを直に読む・言及する試験（変更の周りの地図で辺 1 本の所）、修正案の受け入れ・書き換えのテストと輪で名指したテスト。届くだけの先の試験は受け付けで回さず、「最後のテストの段に任せた試験」として盤面の trace の行と最後の関所に名前で並べ、線の最後のテストの一式が 1 回で確かめる（そこで赤なら最後の関所・報告・次の依頼の下書きに載る）。版の姿との比べも、選んだ狭い試験だけで回す。前は変更が届く試験を全部回し、run 195g では中心のファイルを変えた受け付けが 1 回に 1340 件（3 分 51 秒）と版の比べに 1516 件（7 分 41 秒）を回していた。分からない物（動的な import など）が直に関わる所（変えたファイルか辺 1 本の所）に在る時だけ受け付けと輪の緑で一式を回し、辺 2 本以上の遠くの物は最後の関所に「最後のテストの段に任せた分からない物」として並べる（持ち主の決定 2026-10-06。最後のテストの段がテストのコマンドの一式を必ず回すため。195g は辺 2 本先の動的 import 1 件で毎回一式になっていた）。地図の部品の既定の選び（ほかの呼び手）の決まりは変えない。

### Fixed

- 次の run に引き継ぐ落ちた理由（`prior-failures.json`・`next-request.json` の prior_failures）に、TDD の輪の拒否・投げ出しが載らないようにした。輪の受け付けは単位を問わず 1 つの行を上書きしていたので、輪が投げ出した単位を修正役が直して受け付けが通っても落ちた理由として残り、前の単位の投げ出しが後の単位の通過で消えることもあった。輪の投げ出しは修正役への引き渡しなので、受け付けの最後の結果の控え `accept-last.json` に書かない。
- 止まった run が対象のリポジトリに残す、修正の段の単位の worktree と守りの参照（`refs/works/units/<印>/` の下の `base-*`・`u-*`）を、dev の殻 `use.sh` の run の片付け（`clean`・終わった run の自動の片付け・start の前の掃除）が run の worktree と一緒に消すようにした。今までは同じ run の次の修正の支度しか片付けず、止まった run の物は残り続けた。

## [0.2.28] - 2026-10-06

### Changed

- 修正の受け付け（fix-accept・fix-ruled-accept）が、修正前の版（base）で試験を走らせた結末を控えて使い回すようにした。事後の関門の束の赤緑（base の worktree で受け入れのテストを含む一式）は、base の版・実行器・テストの id・そのテストのファイルと写す conftest.py の中身を鍵に、盤面の周の置き場の `fixgates-base.json` に名指しごとの結末を残し、鍵が同じなら走らせない（受け付けの回・最後の回の通し直し・2 回目の修正の段をまたぐ。テストのファイルを変えれば走らせ直す）。変更に当たる試験の新しい赤を版の写しで比べる回（`accept-rev-cache.json`）も、同じ版・実行器・-k で名指したファイルが前の回に含まれれば走らせない。判定の決まりは変えない。今までは受け付けの回ごとに base 側の一式を 2 本（195g で 3 分半と 1 分半）走らせ直し、1 回の受け付けが 10〜12 分かかっていた。
- 修正の段の TDD の輪は、赤・緑の確かめごとにテストの一式を回さない。赤の回は名指しのテストだけ、緑の回（直し・変えた整え）は名指しと、単位の変更が届く試験のうち元の一式に載ったモジュールのファイルだけを走らせ、元で通っていたテストの緑と消えたテストの照らしをそこで確かめる（届く試験が分からない時は一式）。実行器（入力 `tdd_suite`）には env `TDD_SUITE_ONLY=1` を付けて呼び、`works/dev/tdd-suite.sh` はそれで段の一覧を集めない。解かない実行器は今どおり一式に足して走らせる。届かない試験の赤は受け付けの選んだ試験と線の最後のテストの段（一式）が拾う。今までは 1 回ごとに既定の段（約 1200 件・約 1.5 分）を回し、5 単位の run で約 20 分を使っていた（run 195g）。

## [0.2.27] - 2026-10-05

- 独立設計（R2 の設計の半分。目的だけから理想解を作る道具ゼロの役）を、最後のテストの後ではなく修正案と同じブロックで修正の前に作る。修正案の事前審査の指示書の頭にその設計を貼り、案と設計の構造の食い違いを block の穴として挙げさせる。最後の R2 は先に作った設計と差分の比較だけを回す。今までは設計が修正と最後のテストの後にしか作られず、作り直しが要ると分かっても同じ run に直す周が無かった。設計は作り直さないので、比較の頭に修正の中で申告された前提のずれと記録の制約を貼り、設計の前提を崩していれば「設計の前提が変わった」と理由つきで出させる（`darkfactory/downgrades.json` に下げた所として載せた）。設計の役が 3 回とも拒まれても修正案・事前審査・修正・最後のテストは止めず、事前審査は設計なしで進み、最後の R2 が「独立設計が取れなかった」と言って目の層で止める。直す物の無い判定でも、設計を作るために修正案のブロックへ入る。
- 修正の受け付けが、閉じたかを判定役の問いの数え直し（修正前の版と修正後の作業ツリー）で決め、修正役の申告（塞いだ site の件数・remaining）と合わない時は返答を拒まずに単位ごとの表（盤面の置き場）に記録する。合わない単位は最後の人の関所を開けて並べ、報告にも載る。今までは申告が数え直しと合わないだけで返答全体が拒まれ、輪の最後の回は拒否の文の句を照らして単位を外していた。輪の最後の回は、写しの受け付けの拒否も凍ったテスト・赤い試験と同じく単位の key かファイルで 1 単位に結べればその単位だけを戻して人に回し、残りの単位で通し直しが通らなければ戻した直しと裁定を元に戻す。
- 依頼のファイルが在る run の裁定役の `ask_human` は、裁きの出どころ（`grounds`）に依頼の行を挙げるか、`request_searched` に依頼で何を探して答えが無かったかを書かないと拒まれる。`grounds` の名指しは機械が現物で引く。今までは依頼に先に書かれた人の答えを読んだかが残らなかった。

- 素材集めの p1.local_review の受け付けが、必須のレンズを起こさなかった返答と、そのまま material を awaiting_human にした返答を拒み、同じ会話で起こし直させる。拒みが 3 回目に届いた時だけ人に渡す。今までは最初の失敗で run が人待ちに止まっていた。レンズのプラグインが隔離した設定に入っていない時は、起こし直しても毎回落ちるので、プラグインを名指してすぐ人に渡す。`/simplify` の持ち越し（`simplify_carried: true`）は、本流と同じ条件（前の周から 1 ファイルも変わっていない周）の時だけ認める。写しは本流の `changed_since_prev_round` を出さないので、写しが周ごとに残す周の頭の版の木を前の周と比べて決める。写しの指示書の「ロジック変更が無いなら持ち越してよい」より狭く、どれかのファイルが変わった周と 1 周目は `/simplify` を起こし直させる（役への読み替えの文にもそう書く）。条件付きのレンズ（`/security-review`）の失敗は今までどおり受ける。
- `use.sh start` の対象の条件を緩めた。対象はリポジトリの下のフォルダでもよく（git の根で回す）、省けば今いるフォルダの git の根。commit していない変更・未追跡のファイルが在っても止めず、一時の index で包んだ commit（`.gitignore` の物は入れない。対象の作業ツリー・index・枝は動かさない）から run を切り、「包んだ（wrapped）」の行に出す。包んだ commit は `refs/works/wraps/<commit>` で守り、`clean` が run と一緒に消す。remote の `origin` も求めない（無ければ 1 行で知らせる）。`test_cmd` も省ける（対象の宣言か CI の役に任せる）。今までは汚れた対象・`origin` の無い対象・根でないフォルダを 1 行で拒み、`test_cmd` は必須の引数だった。
- `use.sh` の既定を変えた。最後の関所は要る時だけ開く（`when_needed`。毎回開くなら `WORKS_USE_FINAL_GATE=always`）。Claude の包みは既定で通す（外すなら `WORKS_DEV_ADAPTER=0`。起動の 1 行目と報告に「包み無し」と出る）。今までは最後の関所が毎回開き、包みは `WORKS_DEV_ADAPTER=1` を付けた時だけ通ったので、付け忘れると包みの守り無しで回った。
- 対象に `.review-checks.json` の宣言が在っても、渡した `test_cmd` を宣言の一式の後に走らせ、両方が緑の時だけ緑にする（宣言の段と同じコマンドなら 1 度だけ）。最後の関所と報告に、走らせた一式・環境で起こせなかった段・走らせなかった物を 1 行で並べる。今までは宣言が在ると渡した `test_cmd` は走らず、何を根拠にした緑かも出なかった。
- TDD の輪と修正の受け付けが、修正役が足した・変えた試験を、実行器の既定の一覧の外に在っても回す。`tdd_suite` の実行器は、後ろに試験のファイル・node id（絶対パス）と `-k` を足して呼ばれることがある。受け付けは、元の結末に無い試験の赤を版の姿（一時の写し。作業ツリーは動かさない）でも回し、版でも赤なら外す。選んだ試験が 1 件も走らなかった時は「新しい赤なし」にせず知らせる。今までは一覧の外に書いた試験が走らないまま通った。
- 修正前の関所で、修正案の狭めと事前審査の後退・方針の穴の行のうち、役が決め手の出どころ（依頼の引用・URL と節・本流の同じ場面・持ち主の前の決定）を書き、決め手を当たっても答えが割れず、柵（外への書き込み・取り消せない操作・方針の文書の変更・守りを広げる・web の結果が新しい疑いを出した）に当たらない行は、人に聞かずに通す。通した行は出どころつきで報告の冒頭にいつも並び、最後の関所が開いた時はその文にも並ぶ（通した行だけでは既定の最後の関所は開かない）。今までは決め手が明らかな行も全部関所に出て、人の答えを待った。
- run の中で試験を起こす所（宣言の段・`test_cmd`・最後のテスト）が、機械全体の重いテストの枠（台本は `WORKS_TESTSLOT`。同時に 4 本まで）を通る。枠を待つ間は `use.sh show` に `試験の枠: 待っている（N 分…）` の 1 行が出る。台本が無い・枠の置き場に書けない機械では 1 行出して枠を取らずに回す。今までは並べた run の重い試験が同時に何本でも走った。

### Security

- Claude の包みが、道具を持つ役の system prompt に「検索語に対象の名前を載せるな」の規律（写しの `agents/judge.md` の塊を字のまま）を足す。今までは works の役の指示書にこの規律が無く、WebSearch・WebFetch の問い合わせに対象のリポジトリ名・本文が載りえた。SDK が `--append-system-prompt-file` を渡す起動と、規律の正本を読めない起動は起こさない。包み無しの run には載らない。
- Claude の包みが、対象リポジトリの `.claude/settings.json`・`.claude/settings.local.json` の `permissions.deny` を役の `--settings` に写す。今までは役が隔離した設定で起きるため持ち主の禁止（例: e2e の一式を手元で回さない）が役に効かなかった。ファイルが読めない・形が違う時は、そのファイルを名指して役を起こさない。包み無しの run には載らない。

### Fixed

- 報告が、周の記録の検証器の阻害（1 周目にいつも出る帳尻の行「前ラウンドの記録が無い…」を除く）・最後のテストの赤・独立の目の block が残った run にも `fixed` を出していた。残りが 1 つでも在れば新しい結末 `round_limit` にし、報告の冒頭 1 と次の run の依頼の下書きに残りの各行を出す。
- 報告の費用の行がいつも「取れない」だった（Archon v0.11.1 の実物に無い平らな `cost_usd` と `workflow_completed` を読んでいた）。節の費用は実物の `data.spend.costUsd` を読み（報告された費用は Archon の `executionSpendSchema` の `{source: provider, value}`）、報告されなかった費用（`source: unavailable`）は 0 と混ぜずに見た欄・`reason`・版を添えて「取れない」と出す。報告は run の中で走るので run の和は読まず、合計は節の和を「途中」として出す。会話を継いだ起動の費用は、`costUsd` が累積か 1 回分かを測れていないので引かず、「累積かどうか未確認」と添える。0.2.2 の「`cost_usd` だけを読む」決定を上書きした。
- 走っている run の `use.sh show` が、節ごとの費用をいつも「取れない（report を読めない…）」とだけ出していた（報告の費用の直しで消えた関数を呼んでいた）。報告の費用の行（`report.head_cost`）をそのまま出す: 節ごとの `data.spend.costUsd`、報告されなかった節の件数と理由（合計に数えない）、1 つも取れない時の「取れない」、欄の形が未確認の印、run の中の和を読まない途中の節の和。
