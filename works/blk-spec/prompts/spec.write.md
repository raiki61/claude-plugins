# 仕様を書く（writer の仕事。仕様の道だけ）

依頼: {{inputs.request}}
人の修正依頼（init の直後に積まれた分。無ければ「無い」と出る）: {{?record.process.request_findings}}
リポジトリ: {{inputs.cwd}}

**この工程が在る理由**: 依頼文に書かれていない条件は、修正案に入らず、事前審査が穴として挙げるまで表に出なかった
（実測 2026-09-25: 判定から入る入口を作る run で、依頼に要件を 6 つ書いたが「2 周目以降は P1 を通常どおり走らせる」が無く、
最初の案は P1 が run の最後まで戻らない形になり、事前審査が修正必須で止めた）。**案より前に、何が成り立てば完成かを 1 件ずつ書く。**

## やること

1. `requirements` — 依頼が完成と言える条件を 1 件ずつ。`key` は短く一意に（R1・R2 …）、`text` は 1 文。
   依頼文に書かれていなくても、依頼が成り立つのに要る条件（既定の振る舞いが変わらない・周をまたいだ振る舞い・
   失敗したとき・無人のとき・元に戻す方法）を自分で掘って足せ。
2. `acceptance` — 要件ごとに 1 件以上の**受け入れ条件を、実行できるテストとして対象リポジトリに書け**（今この工程で書く）。
   テストの中に Given / When / Then の 3 語で前提・操作・期待を書く（docstring かコメント）。**本文はテストのファイルが正本**で、
   この返答には置き場（`file`：リポジトリ相対・`name`：テストの名前）と走らせるコマンド（`run`）だけを書く——本文を返答に写すな。
   テストはリポジトリのテストの組（CI が走らせる物）に入る場所に置け。修正が入る前なので、**今は赤になるのが正しい**
   （engine は `run` のコマンドの字面を人に見せて承認を求め、承認の後に走らせて終了コードを記録する——承認の前には走らせない。
   その時点で緑なら「赤を見ていない」と判定役に渡る）。
   同じテストが、後で TDD の「先に書く赤いテスト」になる。
3. `out_of_scope` — 依頼の範囲の外と決めたこと（無ければ空）。

作業ツリーに書いてよいのはテストのファイルだけ。実装はまだ書くな。
