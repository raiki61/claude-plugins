# works

works is a Claude Code plugin for handing code-fix requests to AI. The sections from "Installation (using it in another repository)" through "Claude Code skill" are for people who use works (how to install it, run it on a repository, and take in the fix); the sections from "Development workflow" onward are for people who develop works itself (how it is built, tested, and checked).

- Its engine, a workflow called "darkfactory" (the "line" in the rest of this README; "line" next to a command name, such as "the `wait` line", instead means a one-line command to type), takes a fix request and runs these steps in order as one flow.
  1. Investigate
  2. Research how others solve the same kind of problem (established practice), and compare it with the approach the request indicated
  3. Judge what the problem is (judgment)
  4. Plan the fix (follow the established practice, or write why it departs from it)
  5. Fix
  6. A different AI reviews the diff
  7. Run the tests
  8. Final independent check
  9. Report
- At every step, a machine checks the form and content of the AI's reply, and the flow moves to the next step only when the reply passes. It pauses at human checkpoints ("gates"): at launch, and whenever the AI and the automated checks cannot settle a decision (a setting makes the final gate pause every time).
- A diagram of the flow and what each step does are in [docs/darkfactory-flow.md](docs/darkfactory-flow.md).

Key points of the design: it is a workflow bundle ("pack") for Archon (a tool that runs AI steps defined in YAML in order). Archon decides the step order. The per-step reply checks (acceptance rules) and the record validators are copied from graphloops, another plugin in this repository (raiki61/claude-plugins), into `.shared/core/` and used from there.

## Installation (using it in another repository)

Start by running the `/works` skill in Claude Code (`skills/works/SKILL.md`). That file has the full, authoritative procedure; this section is a summary.

1. Install the plugins: works, and the two plugins that works's AI roles (the agents that run each step) borrow (the plugins named gates and pr-review-toolkit; the plugin name gates is unrelated to the human checkpoints called "gates"). The two borrowed plugins are dependencies of works (`dependencies` in `.claude-plugin/plugin.json`) and are installed together with works. If those marketplaces are not added first, the dependencies are not installed and works will not load. You do not need to install the superpowers skills (a skill collection for Claude Code): works bundles a pinned copy. You do not need to clone the repository.
   - `claude plugin marketplace add anthropics/claude-plugins-official` (the marketplace of pr-review-toolkit; not needed if already registered)
   - `claude plugin marketplace add raiki61/claude-plugins` (if already registered, `claude plugin marketplace update raiki61`)
   - `claude plugin install works@raiki61` (also installs the dependencies gates and pr-review-toolkit)
2. The launch shell script `dev/use.sh` and the pack are inside the install directory where Claude Code put the plugin (`~/.claude/plugins/cache/raiki61/works/<version>/`). This directory is `<install-dir>` below. The skill refers to it through CLAUDE_PLUGIN_ROOT, which Claude Code expands to that absolute path when it reads the skill, so `/works` runs the installed `use.sh`.
3. Verify the setup against your repository, the target (does not call the AI): `sh <install-dir>/dev/use.sh check <target>`. If the last line is `Results: 1 valid, 0 with errors, …`, the install is OK (3 harmless WARNING lines for Claude Code's built-in skills `code-review`, `simplify`, and `security-review` may appear). If borrowed plugins are not installed, it prints, for each missing item, a one-line reason and the install command, then stops (`start` also stops at the same point, before starting the AI). Other missing prerequisites (uv, claude, authentication, conditions on the target) are listed the same way, with how to install them, and it exits non-zero.
4. Run: `sh <install-dir>/dev/use.sh start [--base <version> | --pr <number>] [--spec] [--rounds <N> [--budget-usd <X>]] [--] [<target>] <request-JSON or -> ["<test_cmd>" [<tdd_suite>]]` (the fields and format of the request JSON are defined in section 1 of `skills/works/SKILL.md`, not in this README; if you omit the target, the git root of the current folder is used. `--base` and `--pr` name the diff base (`<version>` is a commit in the target's history, not a plugin version); put flags before the target. To work only from existing changes without a written request, pass `-` as the request JSON. This `-` means "no request", not standard input. `--spec` inserts a spec stage before judgment. `--rounds N` (2 or more) is a chain that links rounds; see "Round chains" below). For every entry, the line's entry block (`blk-entry`) normalizes the input into a single shape (diff base, diff, request lines, PR title and body; the `input` field of the start record `r1/start.json`), and later steps are decided only by content (whether the diff is empty, whether request lines exist). A run with an empty diff enters from judgment; if there is neither a diff nor request lines, it stops before the AI. Each time it stops at a gate, it prints the command to type next. The other commands (`show`, `wait`, `approve`, `answer`, `stop`, `apply`, `clean`, `check`) are at the top of [dev/use.sh](dev/use.sh); how to answer at gates and how to take in the diff are in `skills/works/SKILL.md`. Key points:
   - If there are uncommitted local changes, the wrapped commit (a temporary commit that wraps those changes; see "Rules of `use.sh`" below) becomes the run's HEAD, so `--pr` is rejected as differing from the PR head, and the `--base` diff also includes the wrapped changes.
   - `approve`, `answer`, and `stop` on a run waiting at a gate run the remaining steps detached and return immediately (output in `<home>/logs/`; `<home>` is the use home, see "Rules of `use.sh`" below); after that, `wait` returns within a fixed time and reports the state.
   - **Round chains** (`--rounds N`. N is an integer of 2 or more; if not given, a single round as now. `--budget-usd X` is the cost cap, valid only when combined with `--rounds`): each round is one run as now (1 run = 1 round). Each time you type the `wait` line printed at the end of `start`, `wait` looks at the finished round and starts the next round detached. The next round branches from the previous round's result version (the commit of the tree with the diff applied, protected by the ref `refs/works/chains/<chain>/<round>`); the diff base is the starting version of round 1, and the request is the previous round's remaining findings and previous failures plus the `answers` and PR given in round 1's request. A `wait` that started and linked the next round exits with code 6 and prints the new run id and the next `wait` line; a stopped chain exits with 5 and prints a one-line reason for stopping. The stop conditions, checked in a fixed order, are: the specified number of rounds; the outcome closed (the round's outcome is fixed, or nothing needed fixing); stopped (halt marker, `stop` at a gate, line stop); human judgment needed (a question still put to a human, unreviewed draft lines left); no progress (the round's result tree equals the round's head, or the remaining findings are the same as the previous round's); cost (only when a cap is set: the cumulative cost plus the largest round cost may exceed the cap, or some round's cost cannot be read). No deadlines or timeouts are added. When a human is needed, it does not continue; review the drafts and start a new chain (no entry point for pausing and continuing is provided). When it stops, it writes the last diff `final.diff` (from the original base to the result of the last round not reported as stopped) and the per-round and total report `chain.md` to `<home>/chains/<chain-id>/`. `apply <target> <chain-id>` applies `final.diff` with the same checks as the current `apply` (permission for deleted lines, whether it applies cleanly, permission for stopped runs), `show <target> <chain-id>` prints `chain.md`, and `clean <target> <chain-id>` deletes the chain's records and refs (it rejects if the last round is alive or the next round is being started). `--rounds` cannot be combined with `WORKS_DESIGN_ONLY=1` or `WORKS_USE_FIX_FIXTURE`. The chain logic lives in `.shared/core/chain.py` (design: [docs/plans/2026-10-09-chained-rounds.md](docs/plans/2026-10-09-chained-rounds.md)).
   - A run's worktree, branch, and records are cleaned up automatically (a finished run after `wait` or `show` writes its diff to `<home>/diffs/`; a failed run after the next `start` writes its diff. The unit worktrees cut by the fix stage and the protection refs are cleaned up with it). Runs that are running or waiting at a gate, and runs whose diff could not be written, are kept. Diff files and the board (the run's record store, where the line keeps each step's records, such as the start record and the trace) are not deleted. A cleaned-up run cannot be continued with Archon's resume, so recover the fix from the diff file with `apply`. For failed runs that `clean` or `start` cleaned up, the Archon record is also closed with `workflow abandon` (so that a resumable record does not keep saying it is the human's turn and the herdr slot does not stay in the human's turn; herdr is the terminal tool that splits the terminal into one workspace per task, and the herdr slot is the herdr pane the run was launched from. It closes even runs whose worktree is already gone, so a run with only its record left is closed by running `clean` again). The id and state of runs that `start` cleaned up appear on one line in `start`'s output and in report head part 2.
   - Right after launch, `start` binds to the one run whose board holds this launch's request (it does not guess by taking the top of the list), and writes the run record (`<home>/runs/<run-id>.json`: model, claude executable, keychain item name, adapter). `answer` and `stop` typed in a different shell start Archon with those values, and the proceed and continue lines that `show` prints are built from those values too.

When fixing works itself in a clone of this repository, you may run the clone's `works/dev/use.sh` directly (it is the same shell script; the pack is copied from that clone's `works/`). To try works before the marketplace's works entry (`.claude-plugin/marketplace.json` at the repository root) reaches GitHub, use `claude --plugin-dir <clone>/works`.

Rules of `use.sh`:

- The pack is not placed in the target; each launch copies it into the Archon global workflow location `archon-home/workflows/works` of the use home (`WORKS_USE_HOME`. Default `${XDG_STATE_HOME:-~/.local/state}/works/use-<first 8 chars of the sha256 of the target clone's real path>`. Archon can register a clone of the same repository at only one place per home, so homes are separated per clone. The home holds a marker `target`, a single line with the real path of the clone that created the home. Runs left in the previous default home `works/use` can be continued by naming `WORKS_USE_HOME=${XDG_STATE_HOME:-~/.local/state}/works/use`). Archon v0.11.1 also searches `$ARCHON_HOME/workflows/<pack>/` (confirmed in the search logic inside the executable; `validate` and `workflow test works` passed on a throwaway target).
- Archon and the AI roles are started only through `archon.sh`. The home does not inherit the dev home (`WORKS_DEV_HOME`) (so that it does not rewrite a running dogfooding home).
- The run's worktree is cut with `--from <target HEAD>`. If there are uncommitted changes or untracked files, it is cut from a commit wrapped with a temporary index (files matched by `.gitignore` are not included. The target's working tree, index, and branch are not moved. So that `git gc` does not remove the wrapped commit, a ref is placed only at `refs/works/wraps/<commit>`. The ref is kept in `wrap_ref` of the run record `<home>/runs/<run-id>.json`, and `clean` deletes it together with the run that has that record. When `start` could not bind a run, there are three cases for this ref: (i) the launch exited 0 and a live candidate run exists: that run uses the commit, so the ref is not removed but recorded together with the candidates in `<home>/unbound/`, and the candidate run's `clean` deletes it (it is not deleted while other candidates are alive; the last candidate's `clean` deletes it); (ii) the launch failed, or the run list could be read and has no candidates: the ref is removed on the spot; (iii) the run list cannot be read: it is unknown whether a live run exists, so the ref is not removed; it stays in a record with no candidates and `start` exits 1 (a `clean` after the target has no live runs deletes it). Refs of runs whose record has no `wrap_ref` (runs started before this mechanism) are unknown to `clean` and remain; remove them with `git update-ref -d refs/works/wraps/<commit>`), and the wrapping is reported at launch and in `show`. The target may be a subfolder (it runs at the git root). Under `/private/tmp` or outside a git repository, every command stops with one line without doing anything; when the pack copy `.archon/workflows/works` exists, there is no remote `origin`, or the request, authentication, uv, or claude is missing, `start` stops with one line without doing anything (`check` lists everything).
- The default of the final gate differs by entry point: `use.sh` (and `canary.sh`, which starts it) uses `protected_only` (opens only when protected files are touched; switch to `when_needed` or `always` with `WORKS_USE_FINAL_GATE`; details in `skills/works/SKILL.md`), the dogfooding `dogfood.sh` uses `always` (switch with `WORKS_DOGFOOD_FINAL_GATE`), and when the line input `final_gate` is passed empty (such as when starting directly with `archon.sh`) it is `always`. The Claude adapter is on by default (turning it off with `WORKS_DEV_ADAPTER=0` gives `adapter=optional` and 「包み無し」 ("no adapter")). `WORKS_USE_UNATTENDED=1` passes the launch gate, and when the run reaches a gate where a human decides, it stops there and proceeds to the report (a pending judgment question alone does not open the pre-fix gate; instead the run fixes everything except the item the question came from, and lists the questions at the head of the report). The automation never answers gates itself. The report places draft answers for the items stopped at gates and for the pending questions in the question ledger (the list of open questions the roles record on the board) (the recommendation `recommend` written by the role, or the recommendation from the question's reason; if there is no recommendation, `text` is left empty and the non-narrowing option (a way to fix that keeps the existing behavior instead of narrowing it), the world's solution (the established practice found in step 2 above), and the question's choices go in `note`) into `answers` of `next-request.json`, the draft of the next run's request, with `draft: true` and the source `source` (they are placed even when the run did not stop at a gate, if pending questions remain), and the line printed right after stopping and `show` state that location. The request entry rejects lines still in draft, so a human reviews them and deletes `draft` and `source` (and `note`) before use (lines with empty `text` are rejected until a human writes an answer. Ledger question lines match the next run's questions by the `question` key. Gate item lines are material for the one-word `continue` at the next run's gate). If, in the fix stage, a plan item is ruled wrong and is revised within the same run (replan) only by widening the scope (only adding to `allowed_paths` or removing from `out_of_scope`, with the other fields literally unchanged, and the pre-review of the plan raising no hole (a gap the reviewer found in the plan) that needs a human), an unattended run does not open the replan gate (`replan-gate`) and returns to fixing with the revised item, and records which item's scope was widened by what in the board's trace (`replan_widened_unattended`) and in report head part 1 (plan items revised within the same run) (the diff made with the widened scope is checked by the later diff review). Revisions that add `rewrite_tests` or also change other fields still stop at the gate as now. A run with a human present still asks at the gate as now, even for revisions that only widen the scope. `WORKS_USE_UNATTENDED` and `WORKS_DESIGN_ONLY` accept only 1 or empty; any other value (such as `on`) stops without creating anything. The inputs `policy_md`, `gates`, and `thickness` are `WORKS_USE_POLICY_MD`, `WORKS_USE_GATES`, and `WORKS_USE_THICKNESS`. The default of `thickness` is automatic (the machine decides lightweight or standard per judgment unit (a unit of the problem that the judgment step sets; the fix plan groups units into items), and only in runs where all units are lightweight does it skip the diff review (and lenses and rework) and the independent reviewer (comment deletion candidates and R1–R4, its four review checks), naming them in report head part 2). `標準` ("standard") runs all the current steps, and `軽量` ("lightweight") fixes all units to lightweight.
- Tree- and lane-shaped features can be turned off or on per run (inputs `features_off` and `features_on`; for `use.sh`, `WORKS_USE_FEATURES_OFF` and `WORKS_USE_FEATURES_ON`; for `dogfood.sh`, `WORKS_FEATURES_OFF` and `WORKS_FEATURES_ON`. This is the entry point for running the same request with different features and comparing). List the words separated by commas: `graph_map` (the adapter adds a map of the steps to roles with the `map` flag; see "Claude adapter" below), `judge_verify` (starts verification subagents for judgment and attaches hand-off notes to the planner role), `review_tree` (per-item subagents and synergy review in the pre-review of the plan. When turned off, a single reviewer role reviews (the whole plan in the first round trip; from the second round trip, the diffs and ripple effects of the open items). Same acceptance as the path that uses no tree for a plan with one item), `tdd_lanes` (parallel rounds of the TDD loop. When turned off, tdd units run in order), `fix_lanes` (per-item unit worktrees for the fixer role. When turned off, item subagents are started in order in the working tree).
  - Defaults (when named in neither; decision of the owner, the maintainer of this repository, 2026-10-08): `judge_verify` is off, `review_tree` is auto (counts open items per round trip; 2 or more uses the tree, 1 or fewer uses a single reviewer role), and the others are on. The reason is measured data: judgment verification never changed a later stage across 11 runs with 27 units, and added 0.6–3 USD and 1–2 minutes per run; the tree cost 2–3 times as much as a single reviewer role and found no real hole the single reviewer missed (in the measurement of the set with both turned off, cost dropped by about 30%, or 2.6 USD, and time by 2.3 minutes).
  - Naming beats defaults: words in `features_on` are on (`judge_verify` runs; `review_tree` uses the tree regardless of the number of items), and words in `features_off` are off (`review_tree` always uses a single reviewer role). Naming a value equal to the default (such as the older `features_off=judge_verify`) is not rejected either. Naming the same word in both, or an unknown word, makes `start` stop before the AI. The labels of the hole lanes in the diff review (stage 4a of the tree) are display only, so there is no switch to turn them off.
  - The inputs remain in `settings.features_off` and `settings.features_on` of the run's `versions.json` and in the start record on the board, and features that are not on remain in the first line of report head part 2 (for example `機能: judge_verify off・review_tree auto` ("features: judge_verify off, review_tree auto"); if all are on, `機能: 全部 on` ("features: all on")), so runs can be lined up and compared. Changing them when re-invoking a run makes it stop. Runs that start from a fixture (`fix_fixture`) may change them (judgment and the fix plan stay as in the copy; what takes effect is `tdd_lanes` and `fix_lanes`).
- To compare models for the role that writes the fix plan, use `WORKS_DEV_MODEL` (see the "model" paragraph below). The explicit setting affects all stages listed in the table `.shared/core/stage-models.json` (stages of roles without frontmatter) and cannot be narrowed to the fix-plan stage alone. In the current table only the planner roles (plan, plan-revise) are opus, and the code-writing roles and light roles are sonnet, so when you compare a run with `WORKS_DEV_MODEL=sonnet` against a run without the explicit setting (planner roles are opus), the only roles that change in the darkfactory line are the planner roles (plan, plan-revise) (the spec-writing roles spec-write and spec-revise also change via this table, but they run only in the spec stage that `--spec` inserts, so they are not part of this comparison of runs without `--spec`). `WORKS_DEV_MODEL=opus` also switches the code-writing roles and light roles to opus, so it is not a comparison of the planner roles alone. effort stays at the stage's value, and roles with frontmatter (judge and blind-judge, such as the judge role and the pre-review role) do not change. In runs with the adapter (`WORKS_DEV_ADAPTER`) turned off, the explicit setting has no effect on stages. The changed stages appear in the report's 「## 模型」 ("## Model") alongside the stages' declarations.
- If `tdd_suite` is omitted, then only when `test_cmd` is a single pytest command does it write a runner that adds `--junitxml` into the home's `suites/` and pass it; otherwise it leaves it empty (fix directly) and reports this in one line.
- **test_cmd and worktrees**: `test_cmd` and `tdd_suite` run at the root of the run's worktree, and in the TDD loop and the parallel fix lanes at the root of the unit worktree. Both are cut from a commit, so things the target's git ignores (`.venv`, `node_modules`, build output, `.env`) are absent (neither the shell script nor the line copies or links them). Write `test_cmd` in a form that builds the environment inside the worktree. For uv targets, `uv run pytest -q` (it creates `.venv` per worktree and reinstalls the target from that worktree. The shell script `dev/archon.sh` isolates Archon's HOME and XDG into the use home, so the uv cache is `xdg-cache/uv` in the use home (or the `UV_CACHE_DIR` location if set), and the first run in that home fetches dependencies from the network). For npm targets, `npm ci && npm test`. Go: `go test ./...`; Rust: `cargo test`; Java: `mvn -q test` or `./gradlew test`; IaC such as Terraform: `terraform init -backend=false && terraform validate`. The machine runs `test_cmd` directly outside the roles' sandbox (the network is available too), while the Bash of the AI roles in the run runs inside the sandbox and most roles also have the network closed, so put checks that fetch dependencies or providers from the network into `test_cmd` (things like `terraform plan` that need cloud credentials or a state location run on neither path and remain as verification materials). For poetry, `poetry run` does not install dependencies, so run `poetry install` first (poetry has not been tried in this version). For chained commands the shell script does not write a TDD runner, so pass `<tdd_suite>` if you want the loop to run. Relative paths like `.venv/bin/python` do not exist in the worktree, so they do not run. Pointing at the target's `.venv` by absolute path, and starting from a shell with that `.venv` activated, do run, but if the target is installed editable into that `.venv` (the default of `uv sync`), it tests the target's local code instead of the fix in the worktree and misreads red and green (confirmed in a local trial on 2026-10-08). For the same reason, do not link or copy the target's `.venv` into the worktree (this includes Archon's `worktree.copyFiles`, which affects only the run's worktree). `start` inspects the form of `test_cmd` before starting Archon. Forms that run the target's local copy (the original clone) (pointing at something local by absolute path; pointing at a virtual environment outside the target into which the target is installed editable, or starting from a shell where it is activated) can make the run's tests test the local code instead of the fix in the worktree and go green whether or not the fix is right (a silent false green), so it prints a `止める（test_cmd）` ("stop (test_cmd)") line with the reason, the form to rewrite it into, and a one-line way to lift the stop, and stops with exit code 2 (it creates neither the request copy nor the pack copy). To run it as is, knowing the form, retype the command with `WORKS_USE_ALLOW_TESTCMD=1` in front (it accepts only unset, empty, or 1). Forms that do not run in the worktree (relative paths to paths git ignores; if run, they fail, so you will notice) are only reported with a `注意（test_cmd）` ("caution (test_cmd)") line and do not stop the run. The stop forms, the caution forms, how forms that change location are traced, and the forms not read (gaps) are described at the top of [dev/testcmd_check.py](dev/testcmd_check.py).
- The diff is `diffs/run-<id>.diff` in the home. A human applies it (`apply` applies it after `git apply --check`; diffs that delete target files are applied only with `WORKS_USE_ALLOW_DELETE=1`. Diffs of runs whose record shows a stop (`stop` at the final gate, halt marker, line stop) are applied only with `WORKS_USE_ALLOW_STOPPED=1`. It does not commit).
- **Continuing after failure or interruption** (the line `use.sh show` prints; underneath it is Archon's `workflow resume <run-id>`): Archon v0.11.1's resume skips finished nodes and reruns nodes that failed or were running. Loops restart from round 1 in a fresh conversation, and finished nodes that depend on the failed node are also rerun. The loop position of the fix stage is on the board (`tdd-<k>/state.json` for the TDD loop, the lane records for parallel lanes), so the TDD loop, its parallel lanes, and the fixer role's parallel lanes continue from the stopped unit, item, and stage (unit worktrees are reused). The role's reply in the stopped round is not kept, so that stage is redone in a new conversation (half-written files remain; writes with no record are rejected by the check and redone). Even if one parallel-lane loop fails (account limits, etc.), the join node runs and hands the rest to the sequential loop, and the run proceeds while marked failed. Resume reruns that lane's loop and the join, but the lane loop exits without starting a role, and the join returns its previous output (it does not revert the applied diff). Loops (the sequential TDD loop, parallel-lane loops) that stopped right after the check node wrote 「済んだ」 ("done") to the state but before Archon recorded the loop as finished also exit without starting a role when resume starts them from round 1. The machine report (`report`) is rerun on every resume (`always_run`), so if the failed node finishes on resume, the outcome is no longer 「途中で終わった」 ("ended midway", interrupted) (previously the interrupted outcome of the earlier attempt was reused, and the exit `result` failed no matter how many times you resumed). Whether to run the AI report (`ai_report_go`) does not change on a resume after the AI report has started, so the finished stages of the AI report are reused. Resume runs from the workflow source that Archon copied when the run started (`<workspace>/workflow-source/runs/<run id>/`), so replacing works has no effect on that run's continuation (the fixed version takes effect from the next `start`). Where it cannot continue: on power loss or `kill -9` the run stays running, and `workflow resume` accepts only failed and paused (Ctrl-C and `kill` make it failed). So the 「続ける」 ("continue") line of `show` appears only for failed and paused runs. For a run still running whose owner (the host and pid Archon stamps on the run) is gone, `show` says `持ち主が消えた` ("owner gone"), and instead of the approve, cancel, and continue lines it prints an `abandon` line that closes the record, plus guidance to restart. Recover the fix of a run that cannot continue with `apply`. Once the next `start` cleans up a run that is not alive, it can no longer be resumed, so if you want to continue, do it before that (design [docs/plans/2026-10-07-lane-nodes.md](docs/plans/2026-10-07-lane-nodes.md), section 4).
- works does not read repositories outside its own location (`works/`). This is because Claude Code copies only the plugin's location into the cache (`plugins/cache/raiki61/works/<version>/`) and copies neither `.git` nor neighboring plugins (such as `gates/`). Borrowed items are taken from plugins the user installed (see "Isolated Claude configuration with only selected items (borrowed superpowers skills and parts, gates, pr-review-toolkit)" below). When copying into the pack, it excludes the markers Claude Code places in the cached version's location (`.in_use/`, `.orphaned_at`).

Installing with `archon plugin install raiki61/claude-plugins/works@<tag>` and running Archon directly does not work until a tag is made, and even once installed, the AI roles would read the user's real `~/.claude` (see "Isolated Claude configuration with only selected items (borrowed superpowers skills and parts, gates, pr-review-toolkit)" below), so this form is not used yet.

## Requirements

- Archon v0.11.1 or later and below 0.12.0 (`compatibility.archon` in `archon-plugin.json` is `>=0.11.1 <0.12.0`; only v0.11.1 has been checked).
- uv (script nodes start with `runtime: uv`) and git. The nodes' scripts embed PEP 723 inline metadata, so even if the target has a pyproject.toml, uv does not pick up the target's project (it creates no .venv or uv.lock in the worktree). Known limitation: the target's uv settings (`[tool.uv]`, `uv.toml`) are read, so if they are broken or carry a `required-version` that does not match the local uv, works' script nodes stop at startup with exit code 2. The fix belongs in the target's settings or uv's settings. Working around it by setting `UV_NO_CONFIG=1` in Archon's environment is not recommended: it also changes how the target's own uv behaves (test commands and the fixer role's Bash resolve from public PyPI without reading a private index), which risks false reds and mixed-up dependencies.
- The core needs only git; gh and GitHub are an outer layer (the forge layer). When the target's remote (the remote of the branch's upstream, or `origin` if there is none) is not a host that holds PRs (github.com and `<name>.ghe.com`; in ssh form, also aliases like `github.com-work`) — no remote, a local path or `file:`, GitLab or a self-hosted host — the machine (`.shared/core/forge.py`) decides this at the start of the run, puts it in the board's `loop.forge`, and makes the parallel-PR check not applicable (material `parallel_pr` is `not_applicable`, with reason `no_forge: <kind>`). It does not ask any AI role, and it becomes neither a verifier blocker nor a human wait in the question ledger (one line in report head part 2). The run's entry point (the start node; `ghreads.read_named`) reads the PRs and issues named by the request and by `--pr` inside the run, inheriting the user's gh login (if they are named under the no-auth launch `WORKS_DEV_NO_AUTH=1`, it stops with one line). It reads with gh even for a target with no forge (gh can read via `GH_REPO`, another remote, or a GitHub Enterprise Server on a self-hosted domain; it does not silently drop what was named). Only for items where gh also found no GitHub host (gh says "the remote does not point to a GitHub host" or "there is no remote", or it is not logged in anywhere, or gh does not start) does it write `not_applicable` instead of `unreadable`; for `--pr`, if base and head cannot be read, it stops at start, telling you to name the base and run. Items that gh tried to read as a GitHub host but could not read (the login expired on a GitHub Enterprise Server on a self-hosted domain, HTTP 401, etc.) stay `unreadable` even for a target with no forge, keeping gh's words in the reason, and the no-forge decision is written separately in the `forge` field (to tell them apart from items that are truly not applicable). For `--pr`, it stops, telling you to log in and then run. In either case, the parallel-PR check stays not applicable for a target with no forge. On a GitHub remote, when gh is missing, not logged in, or the API is down, the behavior is as before (there was something to check but it could not be checked: a human wait or the delegate role). A GitHub Enterprise Server on a self-hosted domain cannot be recognized from its form, so it falls on the no-forge side.
- The target repository needs the git remote `origin` (Archon v0.11.1, even when given `--from`, cannot create the run's worktree for a target without origin and fails with exit code 1). If it is missing, `check` in `dev/use.sh` lists it, and `start` stops before starting Archon. To add it: `git remote add origin <URL>`. If there is nowhere to push to and you run only locally, create `git init --bare <target>.origin.git` outside the target and make it origin, then, after `git push origin HEAD`, set `origin/HEAD` with `git remote set-head origin <pushed branch>` (the same form that `dev/dogfood.sh` and `dev/canary.sh` create for throwaway targets). The shell wrapper does not rewrite the target's remotes. The request JSON may be placed outside the target (`dev/use.sh` copies the request into the use home and passes it on).
- `start` passes origin's default branch (the branch `origin/HEAD` points to, or else `origin/main`, then `origin/master`) to Archon as the base (`--base`) every time (Archon remembers the branch from when the target was first registered and does not update it, so this way it does not stop even if the branch from registration time is gone). If none of them exists, it does not guess a branch; before starting Archon, it stops and suggests `git fetch origin` and, if that is still not enough, `git remote set-head origin -a` (or `git remote set-head origin <branch>`) (for a target where only a feature branch was pushed to a bare origin, fetching does not create `origin/HEAD`). When `origin/HEAD` points to a branch that is gone (`git fetch --prune` after a rename), it does not pass that and moves on to `origin/main`, then `origin/master`.

## Development workflow

The tests are `works/tests/run.sh`. For the steps to actually run on Archon (fetching the executable, making throwaway targets, checks equivalent to `archon workflow test`, dogfooding), see `works/dev/`. When the sha256 of the cached Archon executable does not match, delete that file, which is shown in the one line printed when it stops, and run again to re-fetch it (the shell wrapper does not delete it).

The writing roles in the line (fix, the TDD loop, rework) do not run the whole suite; they run only the tests that correspond to the units they changed (「守ること」 ("what to keep") in the canonical rules [`works/.shared/core/writerules/common.md`](.shared/core/writerules/common.md#守ること)). The line's final test stage confirms that the whole suite is green, and in a run that has a TDD runner, the fix acceptance check (`fix-accept`) mechanically selects and runs the tests that correspond to the changes from the base. What you run while fixing is the fast tier `WORKS_TESTS=fast sh works/tests/run.sh [-k 名前]` (only modules that do not create a git repository per test and do not use uv run, Archon, golden files, process trees, or fixed-second waits; handing out a seed git repository via a copy of the template in `works/tests/gitkit.py` is allowed. `WORKS_TESTS=heavy` is the remaining heavy tier; the two together make up everything). The fast tier is split across child processes and run in parallel (the count is `WORKS_JOBS`; if unset, it is decided from the CPU count, and `WORKS_JOBS=1` gives one process; the contract is at the head of `tiers.py`). At the end of a piece of work and before a merge, run the default (no options), which is everything. CI splits everything into 4 groups with `WORKS_SHARD=<number>/<shard count>` (the number is 0-based) and runs them in parallel on separate runners (the split is `shard_of` in `tiers.py`; `test_tiers` enforces that the groups add up to exactly everything; to see only the names of the modules to run, use `python3 works/tests/tiers.py list <fast|heavy|all>`). Which module belongs to which tier is written in one place, `works/tests/tiers.py`, and each new test module must be added to one of the two (if you forget, tier-selected runs and the tests stop). The full run and heavy go through a slot that limits heavy tests to 4 at a time across the whole machine ([`.shared/core/slotwrap.sh`](.shared/core/slotwrap.sh); the script can be replaced via `WORKS_TESTSLOT`; its head is canonical for the script's default location, the slot location, and the behavior when the script is missing), and wait with no time limit until a slot frees up before running. The entry points that start tests inside a run (the engine's declared stage, `test_cmd`, blk-tests' stages named plain and mid, and the runners of the TDD loop and of the fix acceptance check) also go through the same gate via `tree_run.slotted_run`, so heavy tests across parallel runs are also at most 4 at a time. While waiting for a slot, `use.sh show` shows it as the one line `試験の枠: 待っている（N 分…）` ("test slot: waiting (N min…)"), and the herdr tally (the per-slot run count that works sends to herdr) shows it as `走る N（うち枠待ち k）` ("running N (k of them waiting for a slot)") (it is not a wait that needs a human answer, so it is not marked blocked). A stage that took a slot records the seconds it waited separately in `wait_s`, and `wall_s` remains the execution time. For the TDD runner, the outer `tddloop.run_suite` takes the slot with `nice -n 19` and writes the seconds waited at the end of `suite-<n>.log` (ADR [0071](../docs/adr/0071-test-sizes-and-where-they-run.md), section 3, item 1). Inside the fast tier and the TDD runner, `WORKS_TESTSLOT` is emptied so that tests started by the tests inside do not take a slot either (so they are not counted twice with the slot taken outside).

The test runner used by the TDD fix stage (line input `tdd_suite`) is [`works/dev/tdd-suite.sh`](dev/tdd-suite.sh) `<JUnit XML output path> [pytest の引数]`. It runs the same tests with stock pytest and writes the outcome to JUnit XML. The tier (`WORKS_TDD_TIER`), the handling of trailing arguments, the split per test root, the exit codes, and how the slot is taken are at the head of the script. The TDD loop's red and green rounds call it with env `TDD_SUITE_ONLY=1`, and if tests were appended at the end, the script runs only those without collecting the tier's list (red: only the named tests; green: the named tests and the module files of the original suite that the unit's changes reach; if the reached tests are unknown, the tier's whole suite, as when `TDD_SUITE_ONLY=1` is not set). The TDD loop appends all named tests, whether they are inside or outside the tier, and the acceptance check appends, out of the selected tests, only the pytest test modules changed or added in this run (`test_*.py`, `*_test.py`), as absolute paths at the end, and runs them (if they overlap with the tier's files and the same test appears on two lines, the loop counts it as one). Tests that were only reached and are outside the tier are not run locally; they are listed by name as 『手元で回さなかった』 ("not run locally") in the acceptance notice, the board's trace (`ci_left` of `fix_tests_selected`), and the final human gate. unittest and pytest count outcomes somewhat differently (a test that fails with an exception is an error in unittest and a failure in pytest; `-k` is a partial name match in unittest and an expression in pytest). pytest also picks up top-level `def test_*` as tests, so test helper functions must not start with `test_` (`test_tiers` enforces this).

## Layers and dependency direction

The source of truth is the test `works/tests/test_layers.py` (ruling R59). Below is a summary; if they disagree, the test is right. A higher layer may know only lower layers (this covers imports, and also writing line ids, include ids, or other blocks' names as strings).

- L0 copies: `.shared/core/graphloops`, `.shared/core/scripts`. They know nothing of works' own code
- L1 base: `tree_run`, `script_io`, `node_marker`, `graphmap` (the step map), `jsonfile` (a JSON writer that never exposes half-written files)
- L2 adapter: `adapter`, `ticket`, `claude-adapter`, `record-read.py`, `record-write.py`, `no-post-bin/works-gh`
- L3 board and acceptance: `board`, `accept`, `policy`, `entry` (the shared part), `halt` (halt marker), `refix`, `recount`
- L4 block modules: modules used by exactly one block (`ci_role`, `purpose`, `rejudge`, `prcheck`, `<blk>/lib/`). Only the owning block and lines use them
- L5 blocks: `blk-*/`. They do not know other blocks, lines, or the include id attached to themselves
- L6 line modules: modules used by exactly one line (`<line>/lib/`; e.g. the contents of the boundary nodes in `darkfactory/lib/`). Only the owning line uses them
- L7 lines: `<line>/` (folders that have `nodes.json`). They may include blocks by name
- L8 `dev/` and L9 `tests/`: may know everything. Nothing inside the pack refers to them

It also enforces: no import cycles; `*/scripts/*.py` only for YAML nodes (modules go to `lib/` or core); dynamic imports only with constants. Existing violations are listed in the test's `KNOWN`, which may only change in the shrinking direction (when you fix one, delete its line; leaving it turns the test red). `KNOWN` may hold only violation pairs; markers of the "layer not decided" kind (such as `unassigned` for a new core module) cannot go there. The failure message states, per marker, how to fix it (add a layer to `MOD`, add to `PLANNED_SCRIPTS`, etc.). Archon does not search `lib/` (it searches `scripts/` and so on), so files there are not picked up as scripts.

## Claude adapter

`.shared/core/claude-adapter` is a thin shell wrapper placed in front of the Claude Code executable that Archon starts (its core is `.shared/core/adapter.py`). It handles: recording the files a role read, having the re-judgment role run as a continuation of the judge role's conversation, fences on places roles must not write, and stopping down to grandchildren when stopping. Its shape was confirmed by paid trials with the real Archon v0.11.1, SDK 0.3.282, and claude 2.1.283, and the tests (`tests/test_adapter.py`) pin it with a fake claude. The source of truth for what happens at which stage (the content of the list below) is the numbered sections at the head of [`.shared/core/adapter.py`](.shared/core/adapter.py); this section holds only a summary and the rules not in that head.

How to install:

1. Write the adapter's absolute path in Archon's setting `assistants.claude.claudeBinaryPath` (this is the main way. The env `CLAUDE_BIN_PATH` overrides the setting, so it can be used for a temporary override).
2. Pass the real claude via `WORKS_REAL_CLAUDE` (absolute path). If it is unset, the adapter uses the executable `claude` on PATH (skipping any that points to the adapter itself).
3. Pass the location (adapter home) via `WORKS_ADAPTER_HOME`. The default is `${XDG_STATE_HOME:-~/.local/state}/works/adapter` (same as tickets, the records the line's `start` writes for the adapter; see "Fences" below). If it is not an absolute path, the adapter refuses to start. Put it where a role's sandboxed Bash cannot write (`/private/tmp/claude-*` is not allowed).
4. In the dev shell wrapper, run `dev/archon.sh` with `WORKS_DEV_ADAPTER=1` (`dev/dogfood.sh` and `dev/use.sh` go through the adapter by default even without it; to turn it off, use `WORKS_DEV_ADAPTER=0`). `archon.sh` writes `claudeBinaryPath` into the isolated config, moves `CLAUDE_BIN_PATH` to `WORKS_REAL_CLAUDE`, and sets the home to `$WORKS_DEV_HOME/adapter`. The approval and continuation commands the shell wrapper prints carry the same setting.

What the adapter does and does not do (numbers in parentheses are the sections at the head of `adapter.py`):

- Which node a launch belongs to is identified by the marker `works-node: <node name>[ continue=<node to continue>][ <flag>…]` placed in the top-level `description` of the role's `output_format` (the SDK puts it into argv's `--json-schema`). Launches without the marker (such as the `--tools ""` launch Archon uses to make a run's title) have their argv unchanged apart from closing the network. A launch that has traces of a marker but cannot be read as one is not passed through; it stops without starting claude (the marker grammar is the same as `node_marker.parse`).
- Recording hooks (1): adds to `--settings` of marker launches the hooks that record files read (`record-read.py`; a graphloops copy, in the shape the engine's `hook_evidence` reads directly) and files written (`record-write.py`). The acceptance of writing roles (blk-fix's `fix-accept` and `tdd-step`) matches changes from the base against the write records and the reply field `bash_writes`, and rejects changes found in neither. Its reach goes only as far as whether an editing tool wrote the current content or it was declared, and it does not distinguish a file written with Bash and then rewritten with Edit to the same content (it does not prove the full provenance; `.shared/core/writes.py`). The built-in skill `code-review` runs in a fork, and if it inherits the reply tool it does not return its findings to the parent (measured 2026-10-08). The local review role is started under the reply contract (21), so the fork has no reply tool and findings arrive in the body text. Even so, if the `/code-review` line is empty, the local review acceptance writes 「見ていない」 ("not reviewed") rather than 「所見なし」 ("no findings") (`.shared/core/diverted.py`). Picking subagent replies back up (`record-output.py`) was removed in the 2026-10-09 cleanup.
- Conversation continuation (2): records the judge role's conversation id and starts the re-judgment (`continue=judge`) as a continuation of that conversation. The flag `self-resume`, the flag `fork` (the answer node of a concurrently running lane answers in a copy of the planner role's conversation), and fresh conversations at unit boundaries are also decided by the adapter.
- Fences (3, 6, 6b, 6c): adds the places protected by the ticket the line's `start` wrote (the shared `.git`, other worktrees, the board, etc.) to `permissions.deny` and the sandbox's `denyWrite`. The flags `no-tree-write` (the CI delegate), `isolated` (the zero-tool independent reviewer), and `lane` (starts a parallel lane's role in the unit's worktree; design [docs/plans/2026-10-07-lane-nodes.md](docs/plans/2026-10-07-lane-nodes.md)) are handled in the same place (the per-shape tool rejection of 18 was removed on 2026-10-09).
- Stop the whole tree (4): starts the real claude as a child, and stops down to grandchildren when it receives a signal and after it ends (claude's Bash tool runs commands in a separate group, so stopping only claude leaves grandchildren behind).
- Read-only gh (5): for all marker launches, puts at the head of PATH the entry point `.shared/core/no-post-bin/works-gh`, which rejects gh entirely and passes only 4 read forms (roles type it as a single command with the bare name `works-gh`; only this form goes outside the sandbox. The same entry point is also placed under the name `gh`). `git push` is also rejected. Since the entry point rejects all gh other than the 4 read forms, a target's test that runs `gh --version` or similar turns red. It is a fence against accidents, not a hard boundary.
- Never start without fences (7): if `--settings` cannot be read or merged, the ticket exists but cannot be read, or the conversation id cannot be recorded, it does not start claude, prints one line, and stops with exit code 3.
- Close the network (8; regardless of the marker): Archon drops `strictAllowlist` from the YAML network settings, so the adapter adds `strictAllowlist: true` to launches whose `allowedDomains` does not contain `*`. Only the network of Bash inside the sandbox is closed; WebFetch and WebSearch are outside this key (YAML `allowedDomains: []` does not stop the web. To take the web away from a role, remove WebFetch and WebSearch from its tool list).
- stdin relay (9): relays the stdin of marker launches (bytes unchanged), and writes the launch record when the first prompt arrives. It does not touch the instructions (the entry point for choosing full or diff versions was removed on 2026-10-09).
- System prompt injection table (13): adds the rows of the table `INJECTORS` in a fixed order. The current rows are `query_rule` (a block of the judge role's definition saying not to put the target's name in search terms), `graph_map` (below), and `text_reply` (the reply contract).
  - The map source for `graph_map` (`<name>.graph.json` next to the entry YAML) is written at build time with `uv run --no-project --with pyyaml python3 works/dev/graphmap_build.py build works`, and the test `tests/test_graphmap.py` pins that it is character-for-character identical to what is built from the current YAML. The same tool also writes the design map of roles and information flow [docs/darkfactory-design.md](docs/darkfactory-design.md) (a mermaid diagram and a detail table per step; its materials are the map source, the nodes' `description:`, and the receiver table `RECEIVES`), and the same test as `check works` checks it for staleness. The flag `map` is currently on only the 7 nodes of the planner role's conversation (`plan`, `plan-revise`, `plan-answer`, `plan-answer-ruled`, `plan-answer-lane-1` to `3`) (owner, 2026-10-07: choose per node. Design [docs/plans/2026-10-07-graph-map.md](docs/plans/2026-10-07-graph-map.md)).
- Copy the target owner's prohibitions (14): adds only the `permissions.deny` of `.claude/settings.json` and `.claude/settings.local.json` at the root of the worktree of the role's cwd (allow, CLAUDE.md, and hooks are not read).
- Engine-child marker (15): sets `GRAPHLOOPS_ENGINE_CHILD=1` in the child's env (the same name as upstream's `ENGINE_CHILD_ENV`). In the form the target's `tests/run.sh` and the like already read, this lets them reject heavy full suites from AI roles.
- Classification of child exits (16), per-run writable locations (17; "Dogfooding" below), the run's explicit model (19; "Development workflow" above), re-showing cost (20; so that the cost and model of Archon's node are the true values even for launches where the adapter switched conversations), and the reply contract (21; receives the local review role's output as JSON in the body text, like upstream review-graph, and if it does not fit, makes the role resubmit up to 2 times in the same conversation. Design [docs/plans/2026-10-08-reply-contract.md](docs/plans/2026-10-08-reply-contract.md)).
- For each launch, writes one line (time, node name, fences added, conversation id and how it continued) to `<home>/launches/<cwd hash>.jsonl`. The argument text is not written.
- Conversation rules (every AI node declares which conversation it runs in): Archon v0.11.1, not only inside loops, makes the next AI node inherit the conversation of the AI node that ended just before (dag-executor's `lastSequentialSession`; this continues even across script and bash nodes). It breaks only when a layer has 2 or more nodes (parallel run), when a node has `context: fresh`, when the entry node of an included block is an AI node, or when the provider changes; if a block's entry is a script node, the first AI node inside inherits the includer's previous conversation. Round 1 of a loop (`loop_group`) starts in a new conversation without inheriting the outer one, and loop nodes do not hand their conversation outward when they end. works, like upstream review-graph (a new `claude -p` per role, inheriting a conversation only when declared), inherits conversations only when declared. There are 4 rules: (1) An AI node outside a loop has `context: fresh` or the marker `continue=<peer>` (no node may rely on the current layer shape to cut its previous conversation by accident, for example by happening to sit in a layer of 2 or more nodes). (2) The first AI node to run in a loop (the head; by `depends_on` run order, not writing order) uses a new conversation in round 1, and whether resubmissions from round 2 on continue in the same conversation is declared by writing the loop's `fresh_context` (resubmission in the same conversation when acceptance rejected). (3) A non-head AI node in a loop has `continue=<peer>` or `context: fresh`. (4) If a conversation-inheriting loop has 2 or more AI nodes, the head has the flag `self-resume`, `continue=<peer>`, or `context: fresh`. An `include` inside a loop counts as a conversation-placing node for (3) and (4), since the AI nodes in its expansion place conversations. All of these close within one YAML file, so they hold even when a block is included in another step. `SessionCase` in `tests/test_yaml_rules.py` enforces them across all YAML in the pack. In runs without the adapter, `continue=` and the flag `self-resume` have no effect (`context: fresh` and the loop's `fresh_context` are enforced by Archon itself).
- The flag `self-resume` (`works-node: fix self-resume`; the fixer role of a fix loop with a scope-consultation answer node in between): Archon's loop makes the next AI node inherit the conversation of the AI node that ended just before. If a node that inherits another conversation (the answer node `works-node: plan-answer continue=fix-planner`) sits inside the loop, the fixer role of the next round ends up inheriting the conversation of the role that wrote the fix plan. For a node with the flag, only on launches where the SDK inherits a conversation (from round 2 on), the adapter removes the SDK's conversation flag and starts it with `--resume <own id>` (no fork). If the node has no id of its own, it is not started. Round 1 is a new conversation, the same as for nodes without the flag. The answer node's inheritance target `fix-planner` is the conversation id that the adapter recorded under the name of the block input `plan_session`, copied under this name into the same location by the request node (script) (blocks do not write other blocks' node names in YAML; [docs/plans/2026-10-06-ask-planner.md](docs/plans/2026-10-06-ask-planner.md)). A node holding a unit-boundary key (the role of a fixer parallel lane) is started in a new conversation when the key changes, even on a continuation launch with the flag self-resume (a new conversation per item within the lane). The report writer (`works-node: report-write self-resume`) has the same flag. The writer's loop has a cold reader in between that reads the head of what the writer produced (`report-write-cold`; its YAML node is `context: fresh`, so every round is a new conversation), so without the flag the writer in round 2 inherits the cold reader's conversation. Conversely, without `context: fresh`, the cold reader reads in a continuation of the writer's conversation and is no longer cold even the first time (this happened in run f57a5374). This shape for placing 2 or more AI nodes in a loop (non-head nodes have `continue=` or `context: fresh`; the head of a conversation-inheriting loop has the flag `self-resume`, `continue=`, or `context: fresh`) is enforced, as part of the conversation rules above, by `SessionCase` in `tests/test_yaml_rules.py`.
- Do not end names with `.js` (because Archon adds `--no-env-file` to `.js` executables).
- What could break on version upgrades (nothing is broken now): the SDK changing how it passes `--json-schema`, the spelling of `--resume`, or the position of `--settings`; Claude changing the shape of hook input. After upgrading, re-capture the real argv in `tests/adapter/argv/`.

## Dogfooding (running works on itself)

[dev/dogfood.sh](dev/dogfood.sh) is the shell wrapper that runs fixes to works itself on the line `darkfactory` (it costs money; get the owner's consent before running it). What it builds, which inputs it passes, and where it stops (including the environment variables) are at the head of the script.

1. Write the request JSON (format in `skills/works/SKILL.md`). It can live anywhere (the script makes a per-launch copy and passes that).
2. Run `WORKS_KEYCHAIN_ITEM=<keychain-item-name> sh works/dev/dogfood.sh <request JSON> "<test command>" [<dir>]` in the foreground. It clones this repository's current HEAD (committed content only) to `<dir>/repo`, runs it, stops at the launch gate (`launch`), and returns.
3. Pass the gate with the approve line the script prints. Answer the pre-fix gate (only when needed) and the final gate (every time with this script) with the answer lines printed in the gate text (section 3 of `skills/works/SKILL.md`). The approve, answer, continue, stop, and cancel lines the script prints go through `works/dev/continue.sh`, which sends the before and after state to the herdr slot that launched the run.
4. Once the run has reached the report, take in the diff with the `git -C <this repository> apply <dir>/run-<id>.diff` line the script prints, run the tests locally, and then commit. To write the diff out again, use `sh works/dev/dogfood.sh --show <dir> <run-id>`. If the fix rewrote the pack's copy (`.archon/workflows/works`), do not take in that part (the script prints a one-line 「注意:」 ("Note:")).

What dogfooding runs ran into, which shaped the current form:

- The fixer role sometimes left git-ignored files such as `__pycache__` in the run's worktree, and that swayed the test node's green or red (a test checking that no bytecode exists turned falsely red). Now blk-fix records the git-ignored files before the fixer role (node `ignored-before`), and after the fixer role and before the tests it deletes only those that were not in the record (node `clean`; the full list of deleted items is in the board's `fix-removed.json`; the report head and the final gate show the count and all paths, even when it is 0). The read-only checks of judgment and review (a copy of the working tree) also watch for additions, removals, and rewrites of git-ignored files.
- A role inside the sandbox could write only to the working tree and `$TMPDIR`, and the uv cache and the test location were outside them (if a test uses Claude Code's temporary folder, `guard.sh` rejects it). Now the adapter adds a per-run location as a writable place when it launches roles that have Bash, and sets `UV_CACHE_DIR` and `WORKS_RUN_PLACE` (which the tests' `linekit.work_home` checks first) in the child env. `TMPDIR` is not redirected, because Claude Code points it at a temporary folder it can write to (rule 17 at the head of `.shared/core/adapter.py`).

## canary (a one-run check per version)

[dev/canary.sh](dev/canary.sh) is the script that takes, in one run with a fixed small target and a fixed request, the paths that ordinary requests take only rarely (it costs money; get the owner's consent before running it). How to invoke it, its flags, environment variables, and the forms it rejects are at the head of the script; the rules for judging whether it passed and the exit codes are at the head of [dev/canary_check.py](dev/canary_check.py); how the fixture is built and checked is at the head of [dev/canary_fixture.py](dev/canary_fixture.py). This section holds the paths (a)–(k) each request targets, and why the seeds and requests take their form.

Seed and request per request keyword (`--request`):

- `tdd` (default): seed `dev/canary-seed/` (`calc.py` and `textfmt.py` using only the standard library, a single test file `test_lib.py`, `CHANGELOG.md`, and `README.md` stating the rules. The seed's tests are green, and there is no test yet that hits the bugs. There are two public functions without docstrings) and request `dev/canary-request.json` (2 cases: the denominator in `calc.py:mean` and the capital letters in `textfmt.py:initials`). Paths (a)–(d)
- `fix`: the same seed and request `dev/canary-request-fix.json` (2 cases: the missing docstrings in `calc.py:clamp` and `textfmt.py:squeeze`). Path (e)
- `units`: does not start from judgment; starts from the board just before the fix in the fixture `dev/canary-fixture-units/`. Path (f)
- `large`: the measurement run. Seed `dev/canary-seed-large/` and request `dev/canary-request-large.json` (5 cases). Path (g)
- `lanes2`: seed `dev/canary-seed-lanes2/` and request `dev/canary-request-lanes2.json` (4 cases). Path (k)
- `--diff` (a flag; combined with a keyword): adds an uncommitted one-line change to the keyword's seed and request, and launches with `use.sh start --base`. Paths (h)(j). The former keyword `change` was replaced by `--request fix --diff` (keyword `change` is rejected with a message giving the replacement invocation)

For every request case, the docstring contract and the seed README's rules settle the fix to exactly one way (no room is left to choose an edge behavior without a deciding factor. In the earlier form, `truncate` had no contract for its behavior with a limit smaller than the marker, the fix chose ValueError, the independent design saw that as a human judgment, and it remained (round_limit)). Each case's request also names its CHANGELOG line. The line runs as a one-round run (`stop_after_round=1` in `entry.start`; not something canary decided), and 「周の締めの後で止めた: init --stop-after-round 1」 ("stopped after the round's join: init --stop-after-round 1") in the report's 「止めたか」 ("did it stop") section is a normal end. No second round runs, so the outcome is round_limit if remainders exist (verifier blockers, a red final test, independent reviewer blockers), and fixed otherwise. canary aims to end in fixed. origin is a bare local repository, so the machine marks the parallel-PR check as out of conditions (`no_forge: local_path`) (the canary script does nothing special).

### Paths it targets

- (a) Two items in different files (`calc.py:mean` and `textfmt.py:initials`): parallel lanes of the TDD loop (if two items the TDD loop did not turn green remain, parallel fixer lanes. The checker counts either kind of parallel run)
- (b) Two items change the same file in different places: the seed README's rules make the tests go into per-module classes (`TestCalc`, `TestTextfmt`) in `test_lib.py`, and make the one `CHANGELOG.md` line go under per-module headings in `[Unreleased]` (`### calc`, `### textfmt`, with unchanged lines between them), so the two items' lanes change distant places in the same `test_lib.py` and `CHANGELOG.md` (adding tests at the same end would be an insertion-only conflict): three-way merge of overlapping lanes (and union of the test files). Passes only when the planner role makes the two units separate items ("Why (b): the planner's rules do not decide it" below)
- (c) A fix that needs something outside scope (the one `CHANGELOG.md` line both cases need under the README rules; the request text tells the fix plan to put it in neither `allowed_paths` nor `out_of_scope`): scope consultation. Depends on the text; not certain ("Why (c): the scope consultation depends on the request text" below)
- (d) Replanning within the run: allowed to happen (not forced)
- (e) `fix`: parallel fixer lanes (`fix-fork` → lane loop `fix-lane-loop-<n>` → `fix-join`; the real check in section 9 of [docs/plans/2026-10-07-fix-lane-nodes.md](docs/plans/2026-10-07-fix-lane-nodes.md)): two items in different files split into two lanes that run at the same time; in each lane a scope consultation about the one `CHANGELOG.md` line takes place; the answer node `plan-answer-lane-<n>` answers with a copy of the planner role's conversation (adapter flag `fork`); and the join merges the two lanes' `CHANGELOG.md` additions three-way ((a)(b)(c) also pass through parallel fixer lanes)
- (f) `units`: two units in one fix plan item (the real check of the 0.2.38 fix): the TDD loop fixes all of the item's acceptance tests in the earlier unit's stage, and the machine closes the later unit without running its stage (`covered_by` of the unit in `tdd-<k>/state.json`). Neither a conflict report (a call to the TDD loop's stage `conflict`, `conflict_parked` in the trace) nor a ruling (`conflict_ruled`, a launch of the ruling role's node `rule`) happens. The judge and planner roles do not run, so the cost covers only the fix onward
- (g) `large`: time and cost with everything on versus everything off ("The measurement for (g)" below)
- (h)(j) `--diff`: the fork lens's findings (h) and the reply contract (j) (local review role `p1.local_review`). In a run with no diff (the entry input shape `input.diff.empty` in start's record `r1/start.json` is true), the local review role does not run, by the condition `not_request_entry` (a one-round run only runs the round before any fix goes in, so no later round gives that role a diff either). `--diff` commits the seed once, then changes characters in one line of the `calc.py:median` docstring without committing (behavior unchanged; the characters changed are `CHANGE_FROM` and `CHANGE_TO` in `canary.sh`), and launches with `use.sh start --base <that commit>`. The run becomes an entry with both a diff and a request, and the local review role looks at the diff. The checker chooses by the input diff, not by the keyword, and for a run with a diff it adds (h)(j) to the keyword's paths when deciding the exit code (`--request fix --diff` is (a)–(e) plus (h)(j)). Run e91112dd, which took the same form by hand (0.2.48; former keyword `change`), was yes for both (h) and (j)
- (i) The report cold reader's conversations (whether every launch of `report-write-cold` is a new conversation): shown for every request, not counted in the exit code
- (k) `lanes2`: items from the second onward in a single parallel fixer lane (the check of the fix for run 97fd532f): the lane check checks each item against that item's head (the tree after taking the same lane's earlier items). It used to check against the lane's base, so files changed by earlier items hit later items' `out_of_scope`, and in run 97fd532f the 2nd and 3rd items of three lanes were rejected 19 times and none got through. Other requests have one item per lane, so they do not take this path. The seed is a copy of `canary-seed-large` with the behavior bugs fixed, and has four public functions without docstrings, one in each of four separate files (`stats.py:mode`, `units.py:km_to_miles`, `money.py:split_even`, `slugs.py:slugify`; current tests check the behavior of each and no test fails first, so direct is the natural plan). The request's decisions make the 4 cases 4 items, with each item's `allowed_paths` only its own file and its `out_of_scope` the other 3 cases' files. There are at most 3 lanes, so with 4 items the 4th waits in the queue, the lane that runs out of items first takes it as its second item and fixes in order (`fixlanes.assign`, `lanekit.take`), and the later item's `out_of_scope` contains the earlier item's file. If the planner role groups them into 3 or fewer items, no two-item lane forms and (k) is no. There is no `CHANGELOG.md` (so no scope consultation is triggered)

### Why (b): the planner's rules do not decide it

The planner role's instructions (`.shared/core/gl-prompts/prompts/review-loop/p2.fix_plan.md`) say 「1 つの案で複数の単位を閉じてよい（一撃の原理に沿うならそれが望ましい）」 ("one plan may close multiple units (this is preferable if it follows the one-strike principle, i.e. closing several problems with one root fix)"), and the judgment-unit verification hand-off note pasted at the head of the instructions (`VERIFY_ASK` in `blk-plan/lib/planblk.py`) says 「重複・関わり・順番は項目の組み方と並べ方に使え」 ("use overlaps, relations, and order for how items are grouped and ordered"). The verification synergy subagent (`SYNERGY_ASK` in `blk-judge/lib/judgeverify.py`) defines a relation as 「同じファイル・同じ名・同じ試験を触る」 ("touching the same file, the same name, or the same test"), so the form where two items touch the same file (the very premise of (b)) is always handed off as a relation, which pushes toward merging them. No instructions say that items become parallel lanes, nor that the lane merge applies items touching different places in the same file three-way.

In real runs, the planner role merged two units touching the same file into one item (run 01004d2e merged them as 「同じ import の行・同じクラスを触る」 ("touching the same import line and the same class") even though the request text asked for separate items; run a2097fd6 merged them following the verification hand-off note and the judge's assessment 「根は 1 つに交わる」 ("the roots converge into one")), and only run 54d81ef1 (verification, review tree, and lanes turned off), which had no hand-off note and where the judge saw 「根が別」 ("separate roots"), produced two items. In response, a rule on grouping items (`planblk.ITEMS_RULE`; merge only for the same root, the same line or the same hunk, or dependence on a result) was added to the head of the planner role, verification relations were split into the same place (`place: same`) and different places in the same file (`place: apart`), and the hand-off request was made to say not to merge for a different-place relation. The later runs 245042a7 (all on) and 4c32bf37 (all off) also merged them into one item, but that was because adding two lines at the same place in an `[Unreleased]` without headings truly conflicts in a three-way merge (`git merge-file` exits with 1), a 「同じ塊」 ("same hunk"), so it was a correct application of the rule. So per-module headings were placed in the seed's `CHANGELOG.md`, so that the two cases' additions land in separate, non-conflicting places in both `test_lib.py` and `CHANGELOG.md` (the request text does not ask for them to be split).

Remaining variance: the unchanged lines between the two additions in `CHANGELOG.md` are only two, a blank line and `### textfmt`, so in a diff with 3 lines of context that combines the two cases they look like one hunk. Room remains for the planner role to read that as the same hunk and merge them again (where to add is decided by the fixer role, so the seed's form cannot constrain it). Reliably making the planner's rules split them needs a change to the instructions, and that is the owner's call. Runs targeting (b) can be run with `WORKS_USE_FEATURES_OFF=judge_verify` (the hand-off note's push goes away, but the run skips verification).

### Why (c): the scope consultation depends on the request text

The request only states its decisions about the fix plan in text, and it does not pass if the planner role does not follow them. The request text itself is not pasted into the planner role's instructions (what is pasted is the judgment unit names, the judge's assessment, the verification hand-off note, and so on); it arrives only when the judge or verification copies it. The fix plan instructions say to put what the fix touches into `allowed_paths`, and the seed README's rules require a `CHANGELOG.md` line, so the planner role putting `CHANGELOG.md` into `allowed_paths` is in fact following the instructions, and then no consultation happens (runs 245042a7, 4c32bf37). Since 0.2.36 the consultation no longer refuses requests that hit `out_of_scope`; it routes them to the answer node. So the canary request text does not say 「相談が断る」 ("the consultation refuses"): a request given to the factory (darkfactory) must not state anything untrue, and that sentence would now be untrue. A path that reliably triggers the consultation through the seed's form (creating an out-of-scope need the planner role cannot read or foresee) cannot be found without changing the factory, as long as the planner role can read the whole repository and the instructions say to put what the fix touches into scope. Making it reliable takes a change on the fix plan acceptance side or the instructions side, and that is the owner's call. The checker attaches the reason for a refused consultation (`why_refused`) to the (c) line.

### Why (e): the default request plants no parallel fixer lanes

Only items that have a scope (`allowed_paths`) and whose units the TDD loop did not turn green enter lanes (`candidates` in `blk-fix/lib/fixlanes.py` removes the TDD loop's green units (`tddloop.green_units`: routed as tdd, green ok, not given up) with `fixrules.dispatched`, and removes items without `allowed_paths` with `fixrules.item_ranges`), and `fix-fork` cuts lanes only when those split into two or more groups that share no unit (at first one group per lane; groups that did not get in wait in the queue, and a lane that runs out of items takes them) (`fixlanes.fork`; it also requires shape g3, input `fix_lanes` on, and a run with the adapter's write log). The default request's 2 cases are turned green by the TDD loop, so there are 0 lanes (run 0a5062f4's `fix_lanes_planted` was 「並べる枝が 2 本に満たない（範囲の在る項目 0・枝 0）」 ("fewer than 2 lanes to run in parallel (items with scope 0, lanes 0)"); the current text is 「並べる組が 2 つに満たない（範囲の在る項目 0・組 0）」 ("fewer than 2 groups to run in parallel (items with scope 0, groups 0)")).

A unit leaves the TDD loop when the fix plan item's route (`route`) is direct and the TDD role's routing also makes it direct (a unit whose contract is tdd cannot be routed direct; `tddloop._plan_tdd`), when the TDD loop gives up, or in a run with no runner (`tdd_suite`). `fix` makes the first route the natural one through facts in the seed: the seed README's rules require docstrings on public functions, require a `CHANGELOG.md` line also for fixes that add or correct docstrings, and say the tests check only behavior and do not constrain whether docstrings exist or what they say. A fix that only adds docstrings has no acceptance test that fails first, so direct is the natural plan under both the fix plan instructions (tdd needs at least one acceptance test that fails first; `planmarks.HEAD`) and the TDD role's routing instructions (which give documentation-only fixes as an example of direct; `tddloop.DO`). The request text says neither the route nor how to split items. Using a run with no runner was not adopted: in such a run all units also enter lanes, but it does not run the tests of the lane check, so it would not check the lanes as ordinary runs with a runner use them. In `fix`, the TDD loop runs only once, for the routing.

As with (c), if the planner role puts `CHANGELOG.md` into `allowed_paths`, no consultation happens and (e) becomes attempted. If the judge role or the planner role merges the two missing docstrings into one unit or one item (they are the same kind of fix and share the out-of-scope `CHANGELOG.md`, so the push toward merging remains), there is one lane and (e) is no. If the TDD role writes a test that constrains the docstrings and routes it as tdd, that unit turns green and does not enter a lane (the seed README's rules are shaped to suppress that).

### The fixture for (f)

The form of two units in one item does not arise naturally with the current seed (the seed's form makes the planner role create one item per unit). So it starts from a copy that the line's node h-fix wrote (the fixture of `.shared/core/fixture.py`: the board just before the fix) in real run 245042a7 (0.2.36; the TDD loop's two units reported a conflict, were parked, and had 2 rulings), in which the planner role merged two units into one item under the earlier seed, and it does not recreate judgment and the fix plan. Import rejects unless the target tree, the request text, and the start input are the same as when the copy was made, so `dev/canary-fixture-units/` carries three things: `seed/` (that run's seed; different from the current `canary-seed/`), `request.json` (that run's request; different from the current `canary-request.json`), and `fix-fixture/` (the copy of the board). Location paths inside the copy are replaced with markers, so it can be used on any machine.

When the board is opened, if works's tables, graph, or location version differ from when the copy was made, start rejects with 「固定材料と works の版が違う」 ("the fixture and the works version differ"). Staleness does not turn tests red (so that every change to the line's tables or graph does not demand a real run; `tests/test_canary.py` only checks that, when stale, start also rejects naming the same thing), so the fixture can be stale even when CI is green, and this only shows up with `python3 works/dev/canary_fixture.py check works/dev/canary-fixture-units` or `canary.sh --request units` (which stops at this check before building anything). When it goes stale, run a real run at that version that produces a one-item, two-unit plan and copy it again with `canary_fixture.py build` (running with `seed/` and `request.json` as the seed and request is the shortcut).

### The measurement for (g)

Launch canary.sh with the same request, prefixed with `WORKS_USE_FEATURES_ON=judge_verify,review_tree` for all on and with `WORKS_USE_FEATURES_OFF=judge_verify,review_tree,tdd_lanes,fix_lanes,graph_map` for all off (use.sh reads them as is; a run with neither is the default), and line up the `canary_check.py --request large` lines. The seed is five modules (`stats.py`, `textfmt.py`, `units.py`, `money.py`, `slugs.py`), the test file `test_lib.py` (one class per module), and the rules in `README.md`. The request is 3 behavior bugs (the even count in `stats.py:median`, the padding side in `textfmt.py:pad_left`, the coefficient in `units.py:c_to_f`; each breaks the docstring contract on inputs the current tests do not hit) and 2 missing docstrings (`money.py:split_even`, `slugs.py:slugify`). The 5 cases have separate roots and separate files, so under the item grouping rule 5 items is the natural plan, and the expectation is that the 3 behavior items are tdd (3 TDD loop lanes = the lane limit) and the 2 docstring items are direct (2 parallel fixer lanes). The request text says neither how to split items nor the route. All 3 behavior cases add acceptance tests to `test_lib.py`, so room remains, as in (b), for verification synergy to push toward merging, and if they are merged, (g) for the all-on run becomes attempted. There is no `CHANGELOG.md` (so no scope consultation is triggered, and the measurement is narrowed to the parallel stages). The cost target is 25 USD or less per run (canary run 245042a7 with 2 cases cost 7.4 USD).

### How to run it

1. Launch `WORKS_KEYCHAIN_ITEM=<keychain-item-name> sh works/dev/canary.sh [--request <keyword>] [<install-dir>]` in the background (it is an unattended run that stays in the foreground until the report, so from Claude Code launch it with `run_in_background` or a detaching wrapper). The default location is `~/.cache/works-canary/<datetime>-<pid>`. `--build-only` only builds the target and origin and prints the launch line (it uses neither authentication nor Archon).
2. While it runs, see the run id and state with the `use.sh show` line the script prints first. When it finishes, the script prints the run id and the check line.
3. `python3 works/dev/canary_check.py <install-dir> [<run-id>] [--request <keyword>]` shows what actually passed (read-only; `--json` for JSON). It shows the evidence for yes, attempted, or no per path (and `not_exercised` for (h)(j) in a run with no diff), each fix plan item's scope and the files it actually changed, and the minutes per stage and the cost of AI nodes (nodes for which Archon recorded no cost are named, and the sum is a lower bound). The paths counted in the exit code differ per keyword (`fix` also counts (e); `units` counts only (f), `large` only (g), `lanes2` only (k)). A run given a diff (`--diff`) also counts (h)(j) regardless of keyword (chosen by the input diff).

The premises of the seeds and requests (the seed tests are green and the contracts red; the reference fix fixes each case independently; (b)'s two additions merge three-way without conflict, and the per-case lanes do not conflict in either `git merge` or the lane join entry points (`unittrees.diff`, `unittrees.apply`); the request does not ask in text how to split items; each request's cases and scope decisions; the characters (h) changes appear exactly once in the seed; the fixture is not broken) are enforced by `tests/test_canary.py` (FAST), and that the script builds the target and launches `use.sh` with the correct arguments is enforced by `tests/test_canary_sh.py` (HEAVY; a fake `use.sh`).

## Known gaps

- There is no loop that runs rounds within one run (running a second round and beyond until it can be called fixed). The current line is a one-round run (`stop_after_round=1` in `entry.start`), and if remainders exist the outcome stays round_limit and it ends with the report (if the only remainders are checks that could not be measured in the run, fixed_needs_check: the fix is in and green, and a human check remains). The continuation is connected either by the outer chain of `start --rounds N` ("Round chains" above), or by a human writing it into the next run's request (the `next-request.json` draft in the report). The in-run loop is Track B ("Specs" below), shelved (2026-10-09). It is not in main.
