# 冷読チェック

外部へ出す文章を、書き手の文脈を持たない読み手(coldreader)に読ませ、詰まった事実を集めて直す。
書き手は全文脈を持つため「読者が持っていない前提」を自己評価では検出できない。
評価器と被験者を分離することがこの手順の目的である。

「冷読」はこのプラグインの自作語で、読み手の役は **coldreader** の名で呼ぶ。英語の
cold reading は演劇の初見読み上げ・占い師の話術を指す別の語(文書の初見検査の慣用は
fresh eyes / first-time reader)。外部向け文書では毎回説明を書くより coldreader の名で指し、
初出にだけ短い注(文脈ゼロの読み手)を添えること。

## ゲートに止められたとき(gh への投稿)

gh への投稿は、同梱のフックが coldreader を自動で走らせる。deny メッセージに coldreader の
「詰まり」がそのまま載っているので:

1. **直す前に、読み手が何を見ているかを確かめる。** 既に在る PR/issue のスレッドへの返信なら、
   coldreader はフックが取った画面(題・番号・状態・本文・変更ファイル・file と行・元の指摘・
   これまでの返信・参照する番号の題)を見た上で読んでいる。画面に有るもの——PR 番号・リポジトリ名・
   相手の名前・相手が付けた印(`[block]` 等)・相手が何を書いたか——は**本文で説明しない**(説明すると
   「冗長: 」として返る)。直すときは足すより削る。相手の語は**指してよいが、相手の語で書かない**——
   相手の言い回しを地の文に写した箇所は、画面に同じ語が有っても「なぞり: 」として止まる(画面が既知に
   するのは何を指しているかであって、語彙ではない)。直し方は説明を足すことではなく、自分の言葉に置き換える。
   詰まりは画面と本文を合わせても解けないものだけなので、その語の初出 1 か所に中身を添える。
   新規作成(issue・PR・release・gist)は読み手が何も持たないので、**指摘の類型を言語化して**
   (例:「読者が持っていない前提に寄りかかっている」)その類型で本文全体を掃討する。
2. 直した本文で同じコマンドを再実行する——新しい coldreader が直した本文を検査する。
3. 「詰まり: 」はその箇所で意味が取れず読み進められなかったものだけで、根拠・出所・答えが欲しい
   ものは「疑問: 」に出る(読み手にもそう指示してある)。「疑問: 」は投稿を止めない申し送りで、反映するかは判断してよい。「冗長: 」も止めない
   (削ってよい箇所)。止めるのは「詰まり: 」と「なぞり: 」の 2 つ。「補完: 」は coldreader が推測で埋めた箇所で、これも止めない——ただし
   **意図と違う補完は詰まりより重い**。読み手は自信を持って誤読しているので詰まりとして
   出てこないし、通ってしまえば誤読のまま読まれる。時制・主体・範囲の補完は特に確かめること。
4. 直すときは本文を足して膨らませない。画面と本文を合わせても解けない語の初出 1 か所に中身を添える。
   coldreader の指摘は読み手ごとに揺れ、足した文がまた新しい指摘を生む(PR 1583 で 1 本の
   返信が 39 回止まり、1,021 字 → 2,555 字に膨れた実測。PR 1429 では 6 回で 5,455 字 → 10,179 字)。
5. 同じ投稿が 3 回続けて止まると、ゲートが「上限に当たった。持ち主に渡して止まれ」を deny 理由の先頭に出す。
   **そこで書き直しをやめ、投稿の宛先・本文の場所・止めた理由を持ち主に渡して止まる。** 検査を外す逃げ道は無い
   (`COLDREAD_SKIP=1` は付けても効かない)。出すかどうかは持ち主が決め、出すなら持ち主が自分で打つ。
6. 本文は、ヒアドキュメント・本文旗(`--body` 等)・本文ファイル(`--body-file <絶対パス>` 等)のどれで渡してもよい。
   ゲートはファイルを自分で読む。止まるのは、中身を静的に決められない形(パイプの標準入力・解けない変数・
   `"$(cat …)"`・同じコマンドの中で本文ファイルを書き換える命令)だけ。

## 手元の文書(自動。書いた後に読まれる)

拡張子が md・mdx・adoc・asciidoc・rst・txt の文書を書くと(Write・Edit のほか、Bash の `cat >`・`tee`・`sed -i`・python などで書いても、MCP の書く道具で書いても)、同梱のフックが名前だけを書いた役ごとに記録し、
書いた役が終わるときに、その役が書いた文書を 1 本 1 回だけ coldreader(既定は haiku・effort high)に読ませる。
前から在る文書は、書き換えた所を含む節と冒頭だけを読ませる(新しい文書は全体)。指摘はその節についてのものなので、
直すのもその節でよい。Bash で拾うのは、中身をコマンドの字面に書いた文書(ヒアドキュメント・echo・printf・sed -i)と、
git の作業ツリーの中で書き換わった文書で、ほかの命令の出力をリダイレクトした写しと cp・mv の行き先は拾わない。
投稿と違って書き込みは止めない。書いた役に返すのは詰まりが在るときだけで、推測で埋めた箇所と疑問はそのとき一緒に返る(推測と疑問だけなら返らない)。返り方は、書いた役で変わる:

- **作業役(サブエージェント)として書いたとき**: その役の終わりに、指摘の全文が返る。
  1. 指摘の類型を言語化してから、同型を文書全体で掃討する(上と同じ)。
  2. 直した文書は、また終わるときに読まれる。直さずに残すと決めた指摘はそのままでよい——同じ中身は読み直さない。
- **親の会話で書いたとき**: 本数・件数と、指摘の全文を書き出したファイルの場所だけが返る。対話の会話では、ターンを終えた後に
  読み終えたところで会話が起こされて届く(読む間はターンの終わりで待たせない)。`claude -p` の会話では、ターンの終わりに待って届く。
  1. 全文を親の会話に読み込まず、新しい作業役にそのファイルと直す文書を渡して直させる(作業役の書き直しは、その役の終わりにまた読まれる)。
  2. 「推測で埋めた箇所」のうち書き手の意図と違うものだけは、親がファイルのその節を見て、正しい意図を作業役に伝える
     (意図を知っているのは書いた親だけ)。
  3. 知らせが「/clear で終わった前の会話(id)が書いた文書」と言うときは、この会話は意図を持っていない。詰まりだけを作業役に直させ、
     推測で埋めた箇所は、文書のほかの所・commit の記録・頼みのファイルで意図が確かめられるものだけを直させ、確かめられないものは残す。

読まないもの: 300 字未満の文書、1 行目に `coldread:skip`(前の coldwrite の `coldwrite:skip` も効く)を置いた文書、
`.gitattributes` で `linguist-generated` の印を付けた文書(生成物)か `-coldread` を付けた文書(原文と照らす写しなど、ほかの検査が受け持つ所)、書く前と同じ中身、前に読んだのと同じ中身。手元の文書の門番だけを切るなら、環境変数 `COLDREAD_DOCS_OFF=1` を入れて Claude Code を起こす。

本流に入れる前に、枝が書いた文書をまとめて読ませるときは `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/coldread-gate.py" branch-check`
を枝の作業ツリーで走らせる(本流との分かれ目から枝が変えた文書だけを読み、詰まりが在れば終了コード 1。README の「本流に入れる前に読む」)。

## 手で検査するとき(メール・チャットなど、ファイルに書かない文章)

1. 検査対象の本文を一時ファイルに保存する。
2. `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/coldread-gate.py" read <そのファイル>` を走らせる。ゲートと同じ依頼文で、
   新しい coldreader が読む(依頼文そのものは同じ口の `prompt` で出る。観点の正本はゲートの 1 か所で、ここに写さない)。
   詰まりが在れば終了コード 1。重い文章は `COLDREAD_DOC_MODEL=sonnet` を前に付けて読ませてよい。
3. 指摘の類型を言語化してから同型を掃討する(上と同じ)。
4. 直したら同じコマンドで読み直す——毎回新しい coldreader が読む。新しい指摘が出なくなったら収束(最大 3 巡)。

## 書き方の規則(直すときの基準)

- **ポインタは初出で「中身→ポインタ」の順に置く。** パス・節番号・識別子・略語は、
  読者が参照解決できて初めて意味を持つ。「署名アルゴリズムの名前(`alg`)」のように書く
- **冒頭 3 行で「何の話か・自分に関係があるか・急ぐか」に答える。** 権威づけは答えにならない
- **危険の話は「今壊れているのか・壊れる余地だけか」を冒頭で言う。** 安全である事実を
  後ろに置くと、そこまで読者を緊張させたまま読ませることになり、理解が落ちる
- **読者の寿命で前提の厚さを変える。** issue は 3 ヶ月後に文脈ゼロで読まれるので前提を厚く。
  PR の返信はレビュアーの語彙のままでよく、スレッドに見えているものは説明しない
  (ゲートの coldreader もそう読む)
- coldreader に点数は付けさせない。集めるのは詰まった事実だけ(点数は coldreader ごとに揺れて
  収束判定に使えない)。ただし**指摘の件数は数えてよい**——「新しい詰まりが 0 件」が
  収束の計器で、評点と件数は別物である

## 使い分け

リポジトリの文書(入口からの導線を含む検査)は firstread-loop を使う。本 skill と同梱の
ゲートは、issue・PR コメント等、単体で読まれる短い文章向けの軽い姉妹版である。
