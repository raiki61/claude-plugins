## 決めたこと（ループの側で決めた。覆すなら理由を足して直す）

### D1. 修正役が新しく書いた指しは、リンクなら差分から機械が拾い、散文の指しは申告のまま

世界の解: 文書の中の参照はリンクの形で書かせてリンク検査にかける（lychee の `--include-fragments` は Markdown の見出しのアンカーまで
確かめる。https://github.com/lycheeverse/lychee）。

決めたこと: 差分が足した .md の行（コードブロックとコードスパンの外）の相対リンクを engine が申告に依らず全部拾い、指し先の
ファイルと見出し（GitHub の書き方のアンカー）まで引いて、届かなければ修正役の done を拒む。外部の道具は足さない（このリポジトリの
Python は標準ライブラリだけで書かれている）。書き方の規約（REVIEW.md）は変えず、修正役のプロンプトで「書けるならリンクで」と
求める。リンクにできない散文の指し（「〇〇の節」）は申告制のまま残し、名乗りを「申告された指しだけを引く」に狭めた。

理由: このリポジトリの文書の相対リンクは 2 本しか無く、`[#番号](URL)` の大半はコードスパンの中の書式例だった（2026-09-24 に
`git grep` で数えた）。規約をリンクへ一斉に変えると、散文版と共有する REVIEW.md と既存の文書の書き方がまとめて動く。

### D2. 独立の目（R1〜R4）の所見は、今のまま次の周の判定を経て修正役へ渡す

世界の解: Gerrit は新しい patch set ごとに前の patch set との差分（interdiff）で見直し、票は条件に合うものだけを引き継ぐ
（https://gerrit-review.googlesource.com/Documentation/config-labels.html）。

決めたこと: 同じ周のうちに修正役へ返す段は足さない。

理由: 検証器は「連続 2 ラウンド阻害なし」で収束を数えるので、R1 の削除候補を同じ周に当てても、その周の R1 の非 pass の判定は
記録に残り、収束は 1 周も早まらない（R1 が見つけた周 N・当てた後に R1 が pass する周 N+1・2 周目の N+2 で収束するのは、次の周に
当てても同じ）。同じ周に当てるには CI（P4）を測った後にコードを消すことになり、確かめていない変更が周の記録に入る。
Gerrit の形（直したら同じ変更の中で interdiff を見直し、票を引き継ぐ）を採るなら、R の判定そのものを同じ周に取り直す段が要り、
それは節を 2 つ以上足す設計作業になる——1 周遅れの実害（コメントの写しが 1 周長く残る）に見合わない。

範囲: この決定は R1〜R4 の所見の扱いに限る。修正役自身の修正の差分を同じ周で見る段は、依頼者の決定（2026-09-24、4 周目の
human_answers の scope）と 3 周目の実測（修正が作った穴が次の周に 8 件）で足した——R9。D2 が退けた『同じ周に取り直す段』のうち、
修正差分の分だけを覆した形で、R の判定そのものを同じ周に取り直すことは今もしない。

### H1. `_cite_errors` は割らない

共有しているのは行の事前検査と拒否の形だけで、数え方は呼び元で分かれている。割る得は実測できていない（割った後に片方だけ
直る事故の方が、この関数の履歴では多い——同じ関数の docstring が記録している）。世界の解: 当たらない（関数の割り方の話）。

### H2・H3

- H2（修正後の件数 after の意味が how の向きで割れる）: 向きを欄（`counts`: defects か population）にした。defects の問いで
  全部塞いだと言う修正の after が 0 でなければ拒む
- H3（同じ周の class_query の写しが 2 つ）: 最新の判定を正本にした——`p2.history` も `process.diagnosis` を書く。修正役・母数の
  突合・再審・報告は全部そこを読む

## 残ること

### V1・V2. 申し送りの直しのうち、実走でまだ通っていないもの

- **V1. 2 番（素材の awaiting_human を受ける）。** 3 周の run では、ゲートの腕が人の起動待ちになる場面が無かった
- **V2. 3 番（本文を返す節の out_path を .md にした）。** 通るのは最後の節 `report` だけ

### R1. 散文版（`/review-loop`）には、書いた時点の検査が無い

`awaiting` の出どころの規則・先行例の行・数える問いの欄は、実行版（review-graph）では節の done で機械が当てるが、散文版は
検証器が周の最後に見るものだけ（`awaiting` の出どころ）か、機械の検査が無い（先行例・数える問い）。散文版の手順書に同じ規則を
足すか、検証器に先行例の欄を持たせるかは、散文版を回した実走の申し送りを待って決める。世界の解: 未調査。

### R2. 先行例の行は、形しか機械で見ない

判定役・修正役・外部標準照合の先行例は、行が在ること・出典の欄が空でないこと・順位の綴りまでを機械が見る。出典が本物か、
問題に当たっているかは見ない（次の周の判定役と R1 が読む）。世界の解: 未調査。

### R3. 注記の追随（F5）は、プロンプトの指示だけで機械の検査が無い

修正役に「動きを変えたら、その動きを述べた注記を検索で全部引いて直せ」と書いたが、引いた検索を返答に書かせる欄は足していない
（`breaks` と重なる）。実走で注記の取り残しが続くなら欄にする。世界の解: Google のコードレビューの指針は、注記は「なぜ」を言い、
「何をしているか」を言うべきでないとする（https://google.github.io/eng-practices/review/reviewer/looking-for.html）。

### R4. 週 1 回の全腕（`.github/workflows/mutation.yml`）は、まだ一度も走っていない

所要時間は未実測（手元は 24 コアで 21〜35 分）。push した後の最初の手動起動（workflow_dispatch）で測り、`timeout-minutes` を
実測に合わせて下げる。

### R5. 続きの判定を運び手経由にする手順（2 通目の申し送りの 5）は、実走で確かめていない

運び手（汎用 agent）が自分の起こした判定役へ SendMessage で続けられること、運び手の id を `--agent-id` に残せば engine の
agent_continue がその運び手を指すことは、手順書の上の設計で、2 周目以降の `p2.history` を運び手経由で回して確かめる。

### R6. 判定役の文脈は、2 周目以降に Web を読んだ分だけ詰まりうる

判定役（`convergence-loops:judge`）は `p2.diagnose` → `p2.history` → `p2.rejudge` と同じ会話を続け、W1 で先行例を一次情報で
引くようになった。判定役は別の役を起こす道具を持たないので、読んだページ（WebFetch の要約・WebSearch の結果）はその会話に積もる。
修正役と回し役の側は、Web を読む調べを読み役（investigator）に任せるよう手順書とプロンプトに書いた（2026-09-24、利用者の指示）。
判定役の側は実測が無いので節を足していない——2 周目以降の判定が文脈の不足で崩れる兆し（差し戻しの増加・材料の読み落とし）が
出たら、判定の前に先行例を調べる読み役の節を足す。世界の解: 未調査。

### R8. 回す側（このループを回す session）の文脈が、周を重ねるほど膨らむ

2026-09-24 の review-graph（この変更自身のレビュー）で、回す側の文脈が 2 周目の途中で大きく膨らんだ（利用者の指摘）。役の返答は
運び手が置き場に書くので回す側に入らないが、回す側が自分でやる節（CI の再実行・規模の数値・ゲートの実効性・主経路の観測・代役・
根拠の出所・局所レビューのまとめ）の出力と、修正（P3）のために読む判定の単位・差分・台本の出力が積もる。

したこと: 回す側の節のうち、判断が回す側の修正と独立な節に graph で任せ先を宣言した（`delegate: {model, why}`。機械的な節は haiku、
読んで判断を書く節は sonnet）。engine は宣言を ready にそのまま載せるだけで、どの loop かを知らない。手順書が「delegate の付いた節は
その model の汎用 agent に prompt_file ごと任せ、wrote だけ受け取れ」と書く。graphcheck が任せ先のモデルの名前と、回す側の節にだけ
書けることを見る。

残ること: 実走で回す側の文脈がどれだけ減るかは測っていない（この run の 3 周目以降で見る）。修正（P3）は回す側の判断そのものなので
任せ先を宣言していない——1 周の修正が大きい run で回す側が詰まるなら、判定の単位ごとに修正役の agent（sonnet）へ任せ、回す側は
修正の要約と閉鎖の実証だけを受け取る形を検討する。判定役の側の同じ問題は R6。
世界の解: Claude Code の subagent は定義の model 欄と Agent ツールの model 引数でモデルを選べる（別名 sonnet・opus・haiku・fable・inherit、
https://code.claude.com/docs/en/sub-agents）——任せ先の宣言はこれをそのまま使い、graph には別名だけを書く（graphcheck の DELEGATE_MODELS）。
自前でモデルを選ぶ機構は足していない。

### R9. 修正を直す前と直した直後に見る目（2026-09-24 に足した。効いたかは次の周で測る）

3 周目の指摘のうち 8 件は 2 周目の修正が作った（`faces_created_by_prev_fix`）。修正の良し悪しを見る段が全部『直した後』
（P3 の自己申告・R1〜R4・次の周の全体レビュー）に在ったため。利用者の指摘を受けて 2 か所に目を足した:

1. 修正案の事前審査: writer が書く前の案（`p2.fix_plan`。新しく生まれる物と正本の在りか・消す物・足さずに閉じる形）を出し、
   判定をした judge と別の judge（`p2.plan_review`）が、書いた後に生まれる穴（写し・塞がない入口・契約のずれ・死んだ道・範囲の膨張）と
   全部を小さく閉じる別案を予測する。P3 は穴と別案に key ごとに答える（`plan_faces`: absorbed / declared。答えない key は機械が拒む）
2. 修正差分の即時レビュー: 周の頭に固めた版から修正後の姿（同じ手続きで固める）までの差分（`p3.fix_delta`）を inspector が
   3 点（写し・入口・宣言と実装のずれ）だけ見て（`p3.delta_review`）、挙がった穴を同じ周で直す（`p3.delta_fix`）

全部 graph・rules・プロンプトの側で、engine は触っていない。3 周目の途中（P3 の前）から今の run に当てて試している。
見つけた穴を次の周に持ち込まない形（利用者の指摘で 3 つの漏れ道を塞いだ）:

- 修正差分のレビューは、修正が塞いだと言う事前審査の穴を 1 件ずつ検算する（`checks`。塞がっていないものは穴として挙げ、手直しが答える）
- 手直しにはもう 1 回だけ差分レビューを当てる（`p3.fix_delta2` → `p3.delta_review2` → `p3.delta_fix2`）。3 回目は無い
- 直さずに残すと宣言した穴と、2 回目の手直し（誰も検算していない）は、次の周の `p2.history` が 1 件ずつ振り分ける
  （`declared_routed`: to_unit＝直す単位に上げる／accept＝残すことを認める。振り分け漏れは機械が拒む）

3 周目で試した結果: 事前審査は 9 件の穴（block 3）と別案 3 件を挙げ、11 件を修正に取り込んだ（block 3 件は、当て終えたつもりの修正が
閉じていなかったもの——次の周の全体レビューで新しい指摘になっていた形）。修正差分のレビューは、その周の修正が作った穴を 2 件挙げ
（engine の柵の入口・素材を書く op の名前の表の写し）、同じ周の手直しで閉じた。
4 周目の測定: `faces_created_by_prev_fix` は 8 → 7（横ばい）。7 件のうち 4 件は仕組み自体の作りの穴（周の一致を見ない起こし方・腕の無い 3 分岐・
義務の集合の食い違い・世界の解の記録が無い）——仕組みを 3 周目の途中で作ったので、仕組み自身は事前審査を通っていない。1 件は事前審査に従って
入口を足した結果。差分レビュー（読み役が 3 点を見る）は『新しい分岐に腕が在るか』を見ないので、腕の欠けを拾えなかった。
4 周目に足したこと: ① 修正差分の腕（`p3.delta_gates`。修正差分の柵の分岐ごとに退行を注入して赤を見る。証拠にならない腕は手直しが
`arm:<腕>` の key で答える）② 事前審査の入口の穴に『足さずに閉じる形』（`no_add`）を必須にした ③ ゲートの実効性を任せ先に渡すときの注意
（時間の上限を付けない・`--reuse`・完了は通知で待つ。4 周目に任せ先が timeout 1800 で全腕を撃ち、見張りのループを 4 本立て、結果の無いまま
書いたと返した）。本測定は 5 周目（上限の周）の `faces_created_by_prev_fix` が 7 から減るか。

世界の解（2026-09-24 に読み役で調べた）。調べて変えた点: Gerrit の票が patch set に属する形（config-labels.html）を採り、修正差分の状態を
周に結び付けて読む側で照らす形（_delta_of）に直した（4 周目の判定が、前の周の差分を今の周の物として読む穴を挙げた）:
- 修正が欠陥を作る率: Yin ら "How do fixes become bugs?"（ESEC/FSE 2011, https://dl.acm.org/doi/10.1145/2025113.2025121）——OS 4 系のリリース後の修正の 14.8〜24.4% が不正な修正。型は「別の経路への副作用の見落とし」「症状だけを塞ぐ」。対策は論じていない
- 書く前の審査: Fagan "Design and Code Inspections to Reduce Errors in Program Development"（IBM Systems Journal, 1976）——設計・コードのインスペクションの検出効率 82%、早い工程ほど直す費用が小さい。修正案を穴の種類で審査する形は無い（(a) はこれを修正の設計に絞って当てたもの＝adapt）
- 版と版の差のレビュー: Gerrit の patch set 比較（https://gerrit-review.googlesource.com/Documentation/concept-patch-sets.html）・GitHub の "Changes since your last review"——(b) の骨格はこの定番（adopt）。見つけた穴を同じ周で直し、1 回だけ見直して残りを次に回す規則は定番に無い（独自）
- 2 段を 1 つのループにした確立した定番は一次情報で見つからなかった。回帰テストを修正ごとに必須にする軸は語られるが、一次の定量根拠は見つからなかった（併用の候補）

### R10. 途中で graph を変えると、既に出した節は新しい deps を待たなかった（engine。2026-09-24 に直した）

3 周目の途中で `p3.fix` の deps に `p2.plan_review` を足したが、既に出していた `p3.fix` の instance は ready に残り、
事前審査の前に done を受け付けうる形だった（回す側が手で待たせた）。engine は graph の変更を `process.graph_changes` に残すが、
出した instance の deps を当て直さない。直すなら engine の側（done の時点で deps_ok を見る、または graph の sha が変わった next で
未完了の instance の deps を見直す）。ループに依らない話なので engine で直した: done が節の deps の済みを見て、済んでいなければ
拒む（扇の節は instance_deps で出した項目を通す。腕 DW1）。ready の一覧には出したまま残る——回す側は拒否文で気づく。

## 設計の記録: 修正側の裏取り（wrote_refs）

申し送り 10・11 番（修正が新しく書いた節名・見出し・引用を誰も検算しない）の直しで、採った道と落とした道。
コードの注記（`graphloops/rules/review-loop.py` の `fix_covers_open_units` と `_cite_errors`）がここを指す。

**既にある裏取りを、修正側にも向けた。** 指摘側の findings の cite は機械が git grep で数え直して 0 件なら拒むが、
修正側の文字列は誰も引いていなかった。新しい機構は作らず、当てる先を増やした: `p3.fix` の schema に `wrote_refs`
（書いた字列 `cite`・指しているファイル `target`・書き込んだファイル `where`）を足し、findings の中に埋まっていた
検査を `_cite_errors` に切り出して両方から呼ぶ。修正役の差し戻し文には、指し先を読んだ記録（フックの hook_evidence）の
有無を併記するが、柵にはしない。

**target の中だけを引く。** リポジトリ全体を数えると、同じ名前が別の文書に在るだけで通る。ディレクトリは受け取らない。

**引くのは作業ツリー。** 採点する版は周の頭で固まるので、修正役が P3 で書いた字列はその版に入っていない。版を
固め直す道は、post_check の中から共有状態を周の途中で書き換えることになるので落とした。固めた版を引いていた間は、
この周に作ったファイルを指す正直な申告が必ず落ちた（この変更をレビューした 1 周目に 5 つのレンズが再現）。

**「在る」の世界は次の周の版に揃える。** `git ls-files --cached --others --exclude-standard` で決める——この周に作った
未追跡のファイルは入り、`.gitignore` に当たるファイルは入らない。数える世界を無視指定まで広げると、次の周の版にも
コミットにも入らない指し先を合格にした。字列は、解決した 1 ファイルを上限付きで直接読んで数える。

**where も同じ規律で解く。** target に書いた当のファイルを書くと、書いた行そのものに当たって必ず通る。拒むと同じ
ファイルの中の正当な指しまで落ちるので、`where == target` の行に印（self）を付け、次の周の判定役に見せる。

**申告の種類で満たし方を分ける（kind）。** `text` は指し先の中にその字列が在るかを数え、`file` は指し先が版に在るかだけを
見る。1 種類で判定していた頃は、ファイル名の指しを正直に申告すると必ず落ちた。

**指摘側と修正側が共有するのは、行の事前検査（素の文字列・空・改行・NUL）と拒否の形まで**で、数え方は呼び元で分かれる
（指摘側は版全体の git grep と件数の突合、修正側は版の一覧と 1 ファイルの直接読み）。関数を割るかは H1。

残る穴（申告制・差し替え）は、Markdown のリンクについては塞いだ（差分が足したリンクを engine が申告に依らず拾う。下の「決めたこと」の D1）。リンクにできない散文の指しは申告制のままで、名乗りを「申告された指しだけを引く」に狭めた。
