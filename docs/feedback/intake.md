# 利用環境からこの repo へ問題を上げる口（実装指針）

このリポジトリのプラグイン（convergence-loops / graphloops / gates / attention / coldwrite）を
**使っている環境**で踏んだ問題を、こちらへ届けるための設計。2026-09-22 時点の方針で、未実装。

**この文書がこの変更に同梱されている理由**: 届ける口の話（受領の記録の節『この 2 run が届いた経路（型の外の所見）』）の出どころが、同じ日に届いた同じ申し送りで、受領の記録（`docs/feedback/review-loop-remaining-findings.md`）と分けると出どころが辿れなくなるため。実装は未着手で、この変更にコードは含まない。

## なぜ要るか——今日の損失は輸送ではなかった

review-loop の実走 2 run から 10 件の所見が届いた（`docs/feedback/review-loop-remaining-findings.md`）。
届いた経路は「エージェントが会話に書き、人が貼った」。**輸送は成立している。**
落ちていたのは次の 3 つで、いずれも輸送を自動化しても塞がらない。

- 版（plugin.json の version）・コミット・run_id・周が、レポートの側に残っていない。本文の数値は
  会話の中だけに在り、突き合わせられない
- 形が揃っていないので、同じ問題が別の run で再発しても同じものと数えられない
- 1 回しか出てこない。エージェントの context が閉じれば消える

したがって**先に作るのは「踏んだ事実を構造化してローカルに残す」層**で、届け先はその後。
この順なら、届け先が何に決まっても書いたものは無駄にならない。

## 段階

1. **ローカルに残す（先に作る）**——踏んだ瞬間に 1 件 1 行を追記。認証ゼロ・ネットワーク不要・
   失敗しても本体の処理を止めない。手で出す口（このリポジトリが新設するスラッシュコマンド。**Claude Code 組み込みの `/bug`・`/feedback` とは別物なので、名前は衝突しないものにする**）と、フックからの自動追記の 2 経路
2. **届け先を設定 1 行にする**——送信先が設定されていれば送る、無ければローカルのみ。
   Claude Code のフックは `"type": "http"` で URL を直接指定でき、フックの JSON がそのまま POST される
   （`headers` に環境変数を差せるので共有キーも渡せる）。自前の curl を書かずに済む
3. **受けを立てる（必要になったら）**——無料の関数実行環境に受けを 1 つ置き、検証・伏字・重複判定を
   して GitHub API で issue を起票する。トークンは受け側だけが持つ

### 3 をいま作らない理由

Worker が最適になるのは、①利用者が社外にも広がる ②頻度が上がって取りこぼしが実害になる
③人手の転記が追いつかない、のどれかが立つとき。現状は社内の数人・2 run で 10 件という規模で、
受けを持つ代償（secret の管理・URL が漏れたときの荒らし・会社ネットワークから叩けるかの検証・
落ちたときの面倒）が自動化の利得に見合わない。**逆に受けから作ると、会社ネットワークから叩けないと
分かった時点で全部止まる。** 1 と 2 のコードはどの届け先でも共通なので、決定は遅らせてよい。

## レポート 1 件の形

`what` 以外は機械が埋める。中身（記録の本文・差分・コード片）は既定で載せない。

```
plugin: graphloops 0.15.0 (396e21e)
env:    darwin 25.6.0 / claude <version> / python 3.14
where:  loop.py done --node p2.diagnose   exit 1
stderr: 先頭 500 字だけ
run:    review-loop / run_id 7f3a… / 周 9（置き場のパスは載せるが中身は載せない）
key:    sha1(plugin+version+where+exit) — 重複判定の鍵
what:   ＜人が書く 1 欄。自動追記のときは空＞
```

- 置き場は**利用者の環境に残る場所**（例 `~/.claude/plugin-feedback/<plugin>.jsonl`）。
  marketplace 経由で入れたプラグインの実体は `~/.claude/plugins/…` のキャッシュなので、そこに書くと
  更新で消える
- 新設するコマンドの `--export` で未送信ぶんを 1 ファイルにまとめる（手渡し経路の正本）

## 届け先の候補（3 を選ぶときに）

| 候補 | 要るもの | issue 起票まで |
| --- | --- | --- |
| 社内 Teams / Slack の webhook | URL 1 本 | 手動 |
| 社内 GitHub Enterprise の repo | 社内 org | 直接 issue |
| 無料の関数実行（Cloudflare Workers 等） | アカウントと PAT | 自動 |

受けを立てる場合にやること: 共有トークンで認証（無効なら 401）／本文の上限（32KB）と件数の絞り／
受け取る欄を許可リストで固定し `stderr` は先頭だけ／`key` が同じ open issue が在れば新規でなく
コメント追記／fine-grained PAT（この repo の Issues: write のみ）は受け側の secret に置く／
自動起票には `intake` ラベルを付け、人が見て昇格させる。

## 前提として確かめた事実（2026-09-22）

- **Claude Code にプラグイン作者へ送る口は無い。** `/bug`（`/feedback`）は Anthropic 宛で、
  会話全文と環境情報を送る。`plugin.json` に在るのは連絡先のフィールド（`author` / `homepage` /
  `repository`）だけで、送信の機構は付いていない
- **コミュニティも解いていない。** 公開されている feedback プラグインは「ログ専用」で、
  marketplace ディレクトリの FEEDBACK.md に追記するだけ。作者にどう届くかは文書に無い。
  Claude Code 本体にも「スキル／プラグインの改善のためにフィードバックを回収する口が無い」という
  要望 issue（anthropics/claude-code#36073）が立っている
- **フックは HTTP エンドポイントを直接指定できる**（`"type": "http"`・`url`・`headers`・`allowedEnvVars`。
  フックの JSON が POST 本文になる）
- **OTEL では代用できない。** Claude Code の OpenTelemetry は組み込みイベントのみで、フックや
  プラグインから独自イベントは出せない。使うならプラグインが自分で OTLP に POST する形になる
- **会社アカウント（Enterprise Managed User）は、所属 enterprise の外にある repo に issue を作れない。**
  この repo は public で読めるが、EMU のトークンでは `createIssue` が `Unauthorized` で弾かれる
  （2026-09-22 実測）。利用者が全員 EMU なら、**利用者側から GitHub を触らせない設計にする**のが前提

## 秘匿の既定

**Claude Code 組み込みの** `/feedback` が会話全文と `.git/config`（SSH のエンドポイント等）まで送って
問題になった前例がある（anthropics/claude-code#67719。ここで作る口の話ではないが、同じ轍である）。既定は構造化フィールドだけにし、本文・差分・記録の中身は opt-in。
利用先のコードやパスが混ざる欄（stderr・run の置き場）は、長さを切るか欄ごと落とせるようにする。
