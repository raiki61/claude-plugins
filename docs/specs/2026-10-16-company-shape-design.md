# 会社の形で部署を回す仕組みの設計

2026-10-16、持ち主（raiki61。この仕組みを使い、方針を決める人）と窓口の会話で決めたことの記録。読み手は、この設計から下回りを作る作り手（Claude Code の部署の会話か人）である。文中の「今」は 2026-10-16 の時点を指す。同じ日のうちに、この設計の多くが、このリポジトリ（claude-plugins）のプラグイン works-dispatch（0.5.0〜0.11.0）と新しいプラグイン tiers（0.1.0〜）として作られて main に入った。作られた所は、作られた形で書き直してある。同じ日の夕方に、持ち主の言葉で部署を「受け持ちごとの常設の部」と「一時の作業役」に分けた（4.12）。作り手がこれから作るのは、10 の「残っている物」で、4 の決めたことに沿って作る。前に作り手に任せた事（7）は、どれも決まった。持ち主の答えを待っている問い（8）は、10 の最後の 1 つ（my_notes の指示ファイルの書き換え）だけである。この文書は、もとは枝 `docs/company-shape` に置いていたが、2026-10-16 夕に本流に入れた。

ここでの言葉は次のとおり。

- **会社**: git のリポジトリ 1 つを会社に見立てた比喩（4.1）。同じ会社の部署どうしを社内、ほかの会社（別のリポジトリ）を社外と呼ぶ。ただし「勤め先のリポジトリ」は比喩でなく、持ち主が実際に勤める会社のもの（例: IL-SW-AI/guided-resolver）。
- **部署の会話**: 部署（4.1。枝の作業場 1 つ）で働く Claude Code の会話。Claude Code の裏の会話として動き、画面は herdr の区画（ペイン）1 つに出す（下の「窓」）。
- **役**: 部署が受け持つ仕事の種類（振り分け部、調べ役など）。どんな役を置くかは会社ごとに決める（4.3）。部署には、立てたまま置いておく**常駐**と、仕事ごとに立てて終われば畳む**都度**がある。
- **部**: 受け持ち（プラグインやフォルダ）ごとに常駐で置く部署（4.12）。その部署の役の名前も「〜部」にする（振り分け部など）ので、役の名前としても使う。
- **作業役**: 都度の部署に当てる役の名前。受け持ちを持たず、一度きりの作業や、部が並べて進めたい作業のために、頼みごとに部署を立てる（4.12）。前はこの文書で、部署の会話をみな作業役と呼んでいた。
- **窓口**: 持ち主と話す、長く生きる Claude Code の会話。部署を立てて仕事を渡し、結果をまとめる。名前は会社が分かる形にする（例: `my_notesの窓口`。4.12）。この文書の書き手で、本文の「私」は窓口を指す。
- **herdr**: 端末を区画に分け、複数の Claude Code を並べて外から操作できる道具（今は 0.9.3）。区画をまとめる単位がワークスペースで、リポジトリを開いたものを親、そこから作った worktree のものを子と呼ぶ。
- **作業場**: 部署（4.1）の作業フォルダ、つまりその git worktree の場所。
- **窓**: 部署の会話の画面を出した herdr の区画。部署の会話は裏で動き（9.1）、その区画で `attach`（裏の会話の画面を呼び出す Claude Code の命令）を打って画面を出す。
- **下回り**: この設計で作る、どの会社でも同じ部品（スキルと命令）。
- **アカウント**: Claude の契約のアカウント。設定のフォルダ（`CLAUDE_CONFIG_DIR`）ごとに別で、部署の会話には週の使用率に余裕のあるものを選ぶ。

## 1. 何のために作るか

前の作り（works-dispatch の PR の作業場と、手で立てていた作業ごとの会話）は、持ち主のノートのリポジトリ my_notes を起点に固まっている。works-dispatch はこのリポジトリ（claude-plugins）のプラグインで、自分の番の PR を作業場に開き、Claude Code を起こして /catchup を送る。GitHub の鍵の読み込み（gh〔GitHub CLI〕が使う `GH_TOKEN` を、my_notes の `mise.toml` と Claude Code の SessionStart フックで入れる仕組み）は my_notes の中でしか効かず、作業ごとの会話も my_notes で起こしていた。その会話に渡す頼みの文章は窓口の一時置き場にあった。作業場の置き場は 2 通り混ざっていた（手で作った `~/src/<repo>-wt-*` と herdr の既定の場所）。どれも持ち主の手元の置き場と設定に頼っているので、ほかの人は使えない。勤め先のリポジトリを個人の仕組みで汚したくない、という制約もある。

そこで、リポジトリ 1 つを会社 1 つと見て、会社ごとに組織の形を持たせる。道具は、どの会社でも同じ下回りだけを持つ。

## 2. 目標・目標外・失敗の条件

目標:

- どのリポジトリでも、要る道具がそろっていれば（足りなければ使うときに案内される。4.11）、部署を立て、社内と社外に仕事を頼み、結果を受け取れる。
- 持ち主以外の人が、自分の PC と自分のアカウントで同じことができる。
- 会社と部署と役の様子を、ツリー図 1 つで見られる。

目標外:

- herdr 以外の道具（Orca、Superset、cmux など）で動かすこと。herdr に縛られてよい（持ち主の決定）。
- 定時実行。複数のアカウントがあることを前提にすること（1 つでも動くこと）。
- 別の PC へ、commit しなかった会社の形まで持ち運ぶこと。

失敗の条件（動いても失敗とみなす）:

- 頼む側のリポジトリに、相手の会社の名前（「my_notes に頼め」など）を書かないと動かない。
- 勤め先のリポジトリに、持ち主の仕組みのファイルを commit しないと動かない。
- herdr を立ち上げ直すと、会社と部署の構造が失われる。
- 部署が要約を付けずに「終わった」とだけ返せる。

## 3. 制約

- 配布物に持ち主の値（パス、アカウント名、リポジトリ名、鍵の名前）を決め打ちしない。設定か、その場で調べた値から引く。
- 手作業を前提にしない。OS に依存しない（Windows でも試験が通る）。
- herdr への呼び出しは、下回りの中の 1 か所（アダプタ）に集める。herdr は 0.x で互換を約束していないため。
- 既存の試験の流儀に合わせる（このリポジトリの `bash tests/run.sh`。herdr と claude を本当に起こす試験は書かず、呼び出しを偽物に替える）。

## 4. 決めたこと

### 4.1 会社と部署

- 会社 = git のリポジトリ 1 つ。本社は代表の clone（そのリポジトリの主たる手元の clone）で、herdr の親のワークスペースに当たる。
- 部署 = 作業ごとの git worktree（枝 1 本）。herdr の子のワークスペースに当たる。置き場は herdr の既定（`worktrees.directory`。既定 `~/.herdr/worktrees/<リポジトリ>/<枝>`）にそろえる。worktree は下回りが herdr に作らせ、部署の会話（Claude Code の裏の会話。9.1）には自分で worktree を作らせない（作られた形。9.1）。
- 段は「会社 → 部署」の 2 段。herdr は、子のワークスペースから worktree を作れない（試した。エラー `linked_worktree_source`、"New and open worktree actions start from the repo parent workspace."）。部署の下の上下関係が要るときは、木ではなく部署の属性（`boss`）で持つ。
- 部署の会話は、自分の部署（作業場）で起こす。その会社の AGENTS.md・CLAUDE.md とフックを効かせるため。鍵の読み込み（gh が使う `GH_TOKEN`）は、作業場でも効く形に直した。会社の形に gh のアカウントの名前（`gh_user`）を書き、部署を立てるときに下回りがその名前だけを部署の属性 `company.gh-user` に書く。部署の会話が始まるとき、プラグインの SessionStart フックが、Bash の各コマンドの前に `gh auth token --user <名前>` で鍵を取り出す 1 行を足す（Claude Code の `CLAUDE_ENV_FILE`。鍵の値はどこにも書かない）。起こすコマンドの前に `GH_TOKEN=…` を置く形は、裏の会話に届かなかった。勤め先のリポジトリには何も足さない。実際の部署で、この 1 行で名指しのアカウントの gh が動くかは、まだ確かめていない（works-dispatch 0.7.0 の README）。

### 4.2 正本と表示

- 構造の正本は git に置く。下回りは別の台帳を持たない。
  - 会社 → 部署: 本社で `git worktree list`。
  - 部署の属性（役・アカウント・上役・頼み元など）: 作業場ごとの git の設定（`git config --worktree company.<名前>`）。リポジトリに `extensions.worktreeConfig = true` を入れる必要がある。試したところ、値は本社の `.git/worktrees/<部署>/config.worktree` に入り、ほかの部署と本社に混ざらず、`git worktree remove` で一緒に消えた。commit されない。
- herdr は表示と操作の場所とする。下回りが正本を読み、herdr の木・区画の名前・表示名・札（区画に付く短い表示。`herdr pane report-metadata` の `--display-agent`、`--title`、`--token`）を組み立て直す。何度実行しても同じ結果になる形にする。

### 4.3 会社の形

- 会社の形 = その会社の役、各役が常駐か都度か、仕事の流れ、社外から受ける仕事。会社ごとに違う。
- セットアップのとき、そのリポジトリで作る。commit するかは利用者が選ぶ。
  - commit する: リポジトリの中のファイル `.claude/company.toml`。clone した人みなに効く。
  - commit しない: 下回りの設定の置き場（works-dispatch の設定のファイルの隣）の `companies/<代表の clone の場所を符号にした名前>.toml` に、そのリポジトリの分として置く。勤め先のリポジトリを汚さない。
  - 書式は TOML。欄の名前は、エージェントが受ける仕事を告げる世間の形である Google の A2A の Agent Card に合わせた（`name`・`description`・受ける仕事の `[[skills]]`）。ここだけの欄は、受ける役の `role`、役ごとの項目の `[[roles]]`（4.8）、gh のアカウントの `gh_user`（4.1）。書き方の正本は works-dispatch の SKILL.md。
  - 書き方は 1 つ。読む順は、リポジトリの中、無ければスキルの設定。Claude Code の `settings.json` と `settings.local.json` の分け方と同じ考え。
- 会社の形には、ほかの会社の情報を書かない。
- 会社の指示ファイル（AGENTS.md など）には、この仕組みの名前（部署・窓口・下回りの命令）を書かない。決まりが要るときは、道具に依らない言い方（「作業ごとの枝で頼まれた作業は、載せ直して検証が通れば早送りで入れてよい」など）で書く。仕組みの名前は会社の形とプラグインの側に置く。道具を替えても指示ファイルが古くならないようにするため（持ち主の指摘、2026-10-16）。
- 例（今の会社に当てはめた窓口の見立て）:
  - my_notes: 窓口（常駐）、調べ役（都度。主題ごとの部署、枝 `research/<主題>`）。社外から「調べもの」を受け、結論と原典の一句を返し、自分の `reference/` を育てる。
  - claude-plugins: 受け持ちごとの部（振り分け部・関門部・収束部・見渡し部・文書部・試し部）と、一時の作業役（4.12）。出荷役は置かない。本流に入れるのも版上げも、部署が打つ `--land` が受け持つ（8）。
  - guided-resolver（勤め先）: PR と issue ごとの担当（1 ターン目 `/catchup`、2 ターン目 `/my-turn`。どちらもこのリポジトリ（claude-plugins）の attention プラグインの命令で、前者はその PR のどこで止まっていたかを出し、後者は持ち主の番の PR を進める）。commit しない側に置く。今の works-dispatch の設定がこれに当たる。

### 4.4 問い合わせとツリー図

- ほかの会社の情報は持たず、要るときに問い合わせる。同じ PC の中なので、下回りがその会社の情報を読みに行けば足りる。
- 問い合わせられる会社の範囲 = herdr に開いているワークスペースが指すリポジトリ。herdr がリポジトリの情報を持っていないワークスペースは、そこの区画の場所から `git rev-parse --git-common-dir` で本社の `.git` の場所を出し、どの会社かを決める。
- ツリー図の命令を作る。会社ごとに、受ける仕事と、部署（枝・役・アカウント・herdr の状態）を出す。試しの台本で、持ち主の実物の herdr と git から読み取りだけで出せた。作られた形は works-dispatch の `--tree`（`--json` で JSON）。ツリー図に出す会社は、上の範囲より広く、herdr に開いているワークスペースに加えて、全アカウントの会話（終わった裏の会話も）が指すリポジトリ（herdr に開いていない会社の部署も見落とさないため）。問い合わせの範囲は上のまま。部署の行は、枝・状態・会話の名前・役・アカウント・上役・窓の有無。herdr の表示の付け直しは `--sync`（4.2）。

### 4.5 依頼と納品

- 宛先は「会社/役」。会社を省けば社内。社内の部署どうしの依頼も、社外への発注も同じ仕組みで扱う。
- 宛先の役の部署が立っていればそこへ、無ければ部署を立てて届ける。窓口のある会社では、窓口を通すかを会社の形で決める。
- 受付箱（依頼や納品の本文を置く、commit されない置き場）は、頼み元の会社の共通の `.git` の中の `company/inbox/` に置く。commit されず、部署の worktree を消しても残り、勤め先のリポジトリの `.gitignore` も触らない。頼みと納品の本文を 1 件 1 ファイルで置き、台帳 `log.jsonl` に、誰が誰に何を頼み何が返ったかを 1 行ずつ足す。
- 頼みは、本文を受付箱に置き、宛先の部署の窓に herdr で 1 行を打ち込んで知らせる。短い頼みは本文ごと打ち込み、改行を含むか長い頼み（400 字を超える物）は受付箱のファイルを指す。
- 納品の命令は、要約の項目（既定は結論〔3 行以内〕・決め手〔原典の URL を含む〕・残った疑問・枝）がそろっているかを確かめ、欠けていれば送らずに欠けた項目を部署に返す（部署が書き足して出し直す）。そろっていれば要約を頼み元の受付箱に置き、頼み元の窓に要約を打ち込む。
- 窓が見つからないか、herdr が打ち込みを受け付けなかったときは、要約を受付箱に置いたまま納品済みにせず、台帳に失敗を残す。頼み元の窓が開いたら、部署が `--deliver` を打ち直す（下回りは自分では打ち直さない）。
- 頼みと納品は herdr の書き込みで送る。アカウントが違っても届く道だからである。Claude Code の SendMessage（ほかの会話やエージェントに文を送る道具）は同じアカウントの会話にしか届かないので、頼みと納品には使わない。部署が作業の区切りに窓口へ短く知らせる報告だけは、窓口と同じアカウントなら SendMessage でもよい。ただし、窓口や持ち主の判断が要ること（手元に残った変更の扱い・次の頼みの候補など）は、納品の後に出たものでも、画面に書いて止まらず、もう一度 `--deliver` で返す。画面にだけ書いた問いは窓口に届かず、2026-10-16 に、足りない道具の案内の部署で問いが 30 分ほど放置された（窓口の判断。会社の形の役の本文に書いた）。
- 作られた形は works-dispatch 0.8.0 の `--ask <会社/役 か部署の名前>` と `--deliver <要約のファイル>`（下の Stop フック〔4.10 の 3〕も同じ版）。

### 4.6 部署にしない役

点検役（inspector。書いた役と別の文脈から採点する読み取り役）や初見の読み手のように、作業場を持たず、すぐ終わる読み取りの役は、頼んだ会話の中のサブエージェントのままにする。ツリーには出さない。部署にするのは、作業場が要り時間がかかる役だけ。

### 4.7 節約

持ち主は節約術をしっかり入れたいと言った。根拠は my_notes（`~/src/my_notes`）の `reference/secondary/ai/claude-code-usage-levers-named-widely-measured-rarely.md`（各社の測った数）で、原典の一句と測った条件はその表と脚注にある。どれも 1 社の 1 つの環境の数である。今の見立てで効く所:

- 起動時の文脈を役ごとに絞る（クラスメソッド: 使わないスキルなどを外して約 10 万 → 2.5 万トークン）。
- 役の中身を 1 つの大きな指示ファイルに詰めない（Systima: 72KB の指示ファイルで要求ごとに 2 万トークン強）。
- 読みの多い役には安いモデルを当てられるようにする（Spotify: 大きな読みを安いモデルに回し、Claude が読むトークンが 3 つの場面で 82〜94% 減）。
- 常駐を窓口だけにし、調べ役などは都度立てる（TOKIUM: 60 分を超えて間が空くと、キャッシュの命中率が 6% 前後に落ちた）。claude-plugins では、この見立てを持ち主の決定（4.12）が覆し、受け持ちごとの部を常駐にした。同じファイルを取り合う都度の部署どうしの載せ直しと衝突のほうが高く付いたためである。部の会話は頼みをまたいで文脈が積もり、間が空いた後の最初の要求はキャッシュに当たらないので、その分の費用は残る（10 の残り）。
- 部署を細かく割りすぎない（Systima: サブエージェント 2 つに分けると入力の合計 4.2 倍）。

手元で測った数（2026-10-16、my_notes の `notes/knowledge/claude-code-startup-context.md`。対話の会話を起こして最初の要求を count_tokens API で数えた）: my_notes で会話を起こすと最初の要求は 5.15 万トークンで、使わない道具とプラグインをすべて外すと 2.2 万になった。いちばん大きいのは Artifact の道具の定義（約 1.2 万）。そこで、会社の形の役の項目に、その役用の設定（`claude --settings` に渡す JSON。`enabledPlugins` で要らないプラグインを切る、`permissions.deny` で要らない道具を消す、`skillOverrides` で同梱のスキルを切る）を持たせ、部署を起こすときに渡す（4.8 の「起こすときの引数」と同じ道）。利用者の全体の設定とリポジトリの設定は触らない。役の設定の効きは、`claude plugin details` の見積もりではなく、実際の最初の要求を数えて確かめる。SessionStart フックで足す役の文は、毎回の起動時の量に入るので短くし、AGENTS.md と同じことは書かない。

作られた形（works-dispatch 0.7.0）: 会社の形の `[[roles]]` の `settings` を `--settings` に、`model` を `--model` に渡して部署を起こす。使い捨ての clone で、プラグイン 10 個と道具 5 つを切った役の設定と Haiku で部署を起こすと、最初の要求は 2.10 万トークンだった（works-dispatch の README）。

### 4.8 役の渡し方

- 部署の会話は、起動したときに自分の役を取りに行く。プラグインの SessionStart フック（会話が始まるときに走る処理）が、起動した場所の `git config --worktree company.role` を読み、会社の形からその役の中身を引いて、会話の指示に足す（フックの additionalContext）。役の無い場所（本社や普通の clone）では何も足さない。
- `claude --agent` は使わない。役の本文が Claude Code の既定の指示を丸ごと置き換えるため（5）。フックは置き換えずに足すだけで、フックはプラグインの中にあるのでリポジトリを汚さない。会話をやり直しても、起動のたびに役が付き直す。
- モデルと使える道具の制限は、会話の途中の指示では変えられない。会社の形の、その役の項目に書いておき、部署を立てて起こすときの引数（`--model` など）に渡す。
- 作られた形（works-dispatch 0.7.0）: フックは `dispatch/role_hook.py`。役の項目は `[[roles]]` の `name`・`instructions`（足す本文）・`model`・`settings`。`--task --role <役>` で名指した役が会社の形に無ければ止まる。

### 4.9 既存の部品を共通に昇格して使う

持ち主の方針: 今までの仕組みやスキルで形になっているものは、共通に昇格して使い、書き直さない。下回りは、今ある部品を使う。例: アカウントの順位付け（works-dispatch の `nodes/accounts.py`。週の枠の切り替わりの近い順 → 週の使用率の低い順、使用率が上限〔既定 95%〕以上のものは選ばない）と割り振り（`nodes/assign.py`）、使用率の控え（アカウントごとの使用率を残した JSON。作って読むのは works-dispatch の `dispatch/limits.py`）、herdr のアダプタ、起こす・名付ける（`nodes/launch.py`）、呼んだ会話の見つけ方。作り手は最初に claude-plugins の全プラグインから棚卸しをし、置き場を移すかは棚卸しの表を見て決める。

### 4.10 作り手の目で読ませて出た問いへの、窓口の判断

作り手の目で読ませたら、計画の前に要る問いが 6 つ出た。窓口が決めた。持ち主が覆せる。

1. **部署の畳み方と成果の取り込み**: 取り込み方（本流に入れる・PR を出す・枝のまま置く）は、会社の形に会社ごとに書く（8 の持ち主の答え）。役によって違う会社は、役の項目で上書きできる。作られた形（works-dispatch 0.9.0）は、会社の形の `[land]` と、部署が打つ `--land <部署>`（8）。前は「役ごと」とだけ書いていたが、持ち主の答えは「会社ごと」だったので、会社ごとを既定にして役ごとの上書きを残した（2026-10-16 夕に文書を実物に揃えたときの判断。役ごとに替えられる能力は減らさない）。都度の部署は、本流に入れた後（`--land`）、会話が止まり、未 commit・未 push が無ければ下回りが畳む（会話がまだ止まりきっていなければ入れた印を書いて残し、次の `--land` か `--clean --apply` が畳む。0.9.3）。常駐の部署は畳まず、次の頼みを同じ部署で受ける。常駐か都度かは、部署を立てるときの `--resident` で決まり、部署の属性（`company.residency`）に書く。片付けとツリー図と、役で宛てた頼み（4.5）はそれを見る。会社の形には、役が常駐かを書く欄がまだ無い（10 の残り。claude-plugins では、部を `--resident` で立てることを会社の形の組織の決まりのコメントに書いた）。誰が誰に何を頼んで何が返ったかは、頼み元の受付箱に残し、部署と一緒に消さない。
2. **同じ役の部署が複数あるとき**: 都度の役は、頼みごとに新しい部署を立てる。枝の名前は頼む側が渡す（`--task` の `--branch` 必須と同じ。日本語の作業名から作ると崩れるため）。「立っている同じ役の部署に足す」は、常駐の部署で受ける形になった（作られた形。works-dispatch 0.8.0 の `--ask <会社/役>` は、その役の常駐の部署へ届け、無ければ新しく立てる。常駐の部署が 2 つ以上なら止まり、部署の名前で宛てさせる）。常駐の部署は作業場を変えず、頼みごとに `origin/main` から枝を切り替える（4.12）。
3. **要約なしで終われないことの強さ**: 納品の命令の確かめに加え、プラグインの Stop フック（会話が止まる直前に走る処理）で、その会話の部署に未納品の頼みがあれば止める。リポジトリには何も足さない。必須の項目は 4.5 のものを既定にし、受ける仕事ごとに会社の形で替えられる（コードを書く部署なら、差分と試験の結果など）。作られた形（works-dispatch 0.8.0）: Stop フックは同じ会話・同じ頼みで 3 回まで差し戻し、その後は止まるのを許す（会話が止まれないまま回り続けないため）。項目は役ごとに `[[roles]]` の項目の `deliver` で替える（0.8.0 は `[roles."<役>"]` で読んでいたが、4.8 の `[[roles]]` と両立しないので、0.9.0 で `[[roles]]` に揃えた。前の書き方には注記を出す）。
4. **宛先の会社の選び方**: 頼む側の会話（AI）が、ツリー図の「受ける仕事」を読んで選ぶ（持ち主の言葉「スキルを見て herdr を見て考える感じ」）。機械の照合はしない。宛先の会社が herdr に開いていなければ、下回りが本社を herdr に開いてから届ける。
5. **今の PR の流れ**: 作り直さない。今の設定（`~/.config/works-dispatch/dispatch.toml` の `[[repos]]`）を、guided-resolver の会社の形として読む薄い層で済ませる。利用者に設定を書き換えさせない（`docs/adr/0002-backward-compatibility.md`、今ある能力と使い方を減らさない）。
6. **窓口の居場所と立て直し**: 窓口は本社の区画に居る。本社（代表の clone。部署の作業場ではない）の、本社だけに効く git の設定（`git config --worktree company.desk`）に窓口の会話の名前を書いて見分ける。herdr を立ち上げ直したときに下回りが立て直すのは、構造と区画の名前と札だけ。会話の識別子は属性に残し、会話を `claude --resume` で戻すかは利用者が選ぶ（herdr は、既定でないアカウントの会話を自動で戻さない。herdr の issue #1269）。

### 4.11 要る道具の段と、点検と準備

持ち主の案（2026-10-16）は、プラグインを要る道具で段に分け、段ごとにセットアップのスキルを用意して各プラグインが流用する形。段は、段 0: Claude Code だけ、段 1: gh（GitHub の CLI）、段 2: herdr と複数のアカウント、段 3: Archon（AI の工程を順に回す道具）。

世間の形を調べた（my_notes の `reference/secondary/architecture/extension-hosts-declare-sibling-extensions-but-not-individual-outside-tools.md`）。段ごとに共有の部品を作る点は、Neovim の `:checkhealth`（点検の枠を共有し、中身は各プラグインが持つ）や Python の extra（名前付きの段）に近く、案のとおりでよい。ずれるのは準備の時で、Claude Code の hooks の文書は、一度きりの準備に頼らず "check for the dependency on first use and install on miss" を実用の形に挙げる。外の道具（gh・herdr・Archon）を要るものとして機械が読む形で宣言する欄は、調べた土台のどれにも無い（Agent Skills の `compatibility` は自由な文で、Claude Code は受け付けるだけで何もしない）。

そこで次の形にする（窓口の判断。持ち主が覆せる）。

- 段ごとに、共有の「点検と準備」の部品を 1 つ持つ。点検は、その段の道具が在るか・使えるか（gh ならログイン済みか、herdr なら動いているか）を確かめ、足りない物と入れ方を返す。準備は、足りない物を入れる手順を案内する（手で入れる物は、入れ方を示して止まる）。
- 各プラグインは、自分の要る段を書き、使い始めにその段の点検を呼ぶ。通らなければ、点検の返した案内を出して止まる。利用者が先にセットアップを走らせておく必要はない（走らせてもよい）。
- 点検の部品は、共通のプラグイン tiers（0.1.0）に置いた。各プラグインは `plugin.json` の `dependencies` で tiers に依存し、使い始めに `tiers --tier <段> --json` を呼ぶ。人は `/tiers:check` で同じ点検を走らせる。点検は足りない物と OS ごとの入れ方を返すだけで、何も入れない（今の段の道具は、どれも OS に入れる物か対話のログインなので、断らずに走らせてよい物が無い）。最初につないだのは works-dispatch の `--check`（段 2）。
- 文書に書かれていなかった 2 点は、使い捨ての marketplace で試して確かめた。依存として入ったプラグインの `bin/` は Bash の道具の PATH に入り、依存先のスキルは `<依存先>:<スキル>` の名前で呼べた。GitHub から足した marketplace でも同じかと、Windows で拡張子の無い `bin/tiers` を名前で起こせるかは、まだ確かめていない（tiers の README）。

### 4.12 部（常設・受け持ちごと）と作業役（一時）

持ち主の言葉（2026-10-16 夕）: 「もっと部署っぽく役割ごとにすべきでは」「常設がいてもいいんだし」「一次作業の人は一次作業の人だし」（一時の作業の人は、一時の作業の人として残す）「部署間の連携があってもいいし」。その日、claude-plugins では役が作業役 1 つだけで、頼みごとに都度の部署を立てていた。works-dispatch に触る都度の部署が 5 つ並び、同じファイル（README・SKILL.md・CHANGELOG）を取り合って、載せ直しと衝突が何度も起きた。部署の名前も頼みの名前で、何の担当かが分からなかった。

そこで部署を 2 種に分けた（窓口の案を持ち主が受けた）。

- **部**: 受け持ち（プラグインかフォルダ）ごとに 1 つ置く常駐の部署。`--resident` で立て、片付けで畳まれず、次の頼みを同じ会話で受ける。受け持ちの文脈を持ち続け、同じファイルの直しは部の中の順番になるので、取り合いにならない。作業場は同じまま、頼みごとに `origin/main` から決まりどおりの名前の枝（`fix/…`・`feat/…`・`work/…`）を切り替えて作業し、済んだら自分で `--land` を打ち（本流が先に進んでいれば載せ直し〔rebase〕て打ち直す）、入ったら頼み元（上役）に納品する。
- **作業役**: 前と同じ、頼みごとに立てて入れたら畳む都度の部署。受け持ちの無い一度きりの作業（claude-plugins なら、根の `scripts/`・`tests/`・`.github/` や会社の形）と、部が同じ受け持ちの作業を並べて進めたいときに使う。並べると同じファイルの取り合いが戻るので、並べるのは触るファイルが重ならない作業に限る。
- **連携**: 部は、ほかの部と作業役に、頼む命令（`--ask <会社>/<役>`）で頼んでよい。頼んだ部が上役（頼み元）になり、納品はその部に返る（4.5 の頼みと納品と同じ仕組み）。受け持ちの外のファイルを変える必要が出たら、その受け持ちの部に頼む。
- **名前**: 窓口の会話と部の部署の名前は、会社が分かる名前にする（例: `my_notesの窓口`・`claude-pluginsの振り分け部`。「窓口」だけでは、どの会社の窓口かが分からないと持ち主が言った）。役の名前（`振り分け部` など）は会社の形の中の名前なので、会社を付けない。
- **書く場所**: 部の受け持ちと決まりは、会社の形（`.claude/company.toml`）の `[[roles]]` の本文に短く書く。受ける仕事（`[[skills]]`）も部ごとに足し、どの頼みをどの部が受けるかが `--tree` の一覧で分かるようにする。部と作業役の違いは、会社の形の組織の決まりのコメントに書く。

claude-plugins の部（正本は `.claude/company.toml`）: 振り分け部（works-dispatch・tiers）、関門部（gates）、収束部（convergence-loops・graphloops）、見渡し部（attention）、文書部（根の README.md・CLAUDE.md と docs/。docs/trials/ を除く）、試し部（まっさらな環境・Windows・Linux で入れて試し、詰まりを docs/trials/ に記録する。プラグインは直さず、直しは受け持ちの部に頼む）。works と works-factory は、持ち主が別に自動で回している所なので、部を作らず、どの部も触らない。

確かめたこと（2026-10-16 夕、works-dispatch 0.10.0）: 常駐の部署の作業場で枝を替えると、`--tree`・`--land <部署の名前>`・`--land <今の枝>`・`--deliver` は今の枝を指し、前の枝の名前では部署が見つからなかった（狙いどおり。済んだ前の枝を取り違えて入れない）。部署の属性は作業場ごとの git の設定（4.2）で枝に依らず、枝はその都度 `git worktree list` から読むためである。試しは、属性だけを書いた作業場で、部署の会話は起こしていない。会話を起こした部で頼みを 2 つ続けて回す確かめは、まだしていない。

## 8. 持ち主の答え（2026-10-16）と、残っている問い

持ち主は「依頼が終わったら人待ちではない。仕組みで worktree を片付けないと、人が反応する点が増える。本質はサブエージェントと同じ」と言った。部署は、納品を受け取ったら人を待たずに畳む（4.10 の 1）。そのうえで次を答えた。

- **成果を本流（本社の主の枝。main など）に入れるとき**: 会社ごとに会社の形で決める。my_notes と claude-plugins は、検証（my_notes は `tools/check.py`、claude-plugins は部署の手元の、触ったプラグインの試験）が通れば機械で本流に入れる。勤め先のリポジトリは PR を出して止める。my_notes の AGENTS.md の「commit と push は持ち主に頼まれたときだけ」はこの答えと食い違うので、機械で本流に入れ始める前に書き換える必要がある（誰がいつ書き換えるかは決めていない）。
  - **検証をどこで回すかも会社の形に書く**（2026-10-16 に足した。窓口の判断）。部署は、その会社の `.claude/settings.json` の禁止（`permissions.deny`）に縛られる。claude-plugins は、リポジトリ全体の試験（`tests/run.sh` と `graphloops/tests/run.sh`）を手元で回すことを禁じている。禁止は、2 つの試験それぞれを `bash`・`sh`・`./` の 3 通りで呼ぶ形を並べた 6 つである（ADR 0069。持ち主の方針「テストの設計の作り直しが済むまで手元で e2e を回さない」）。2026-10-16 には、claude-plugins の部署 2 つがこの禁止に当たり、全体の試験を回せずに止まった。窓口は別のリポジトリ my_notes で動くので claude-plugins の設定が効かず、窓口が代わりに回してしまった。このずれを無くすため、会社の形（`.claude/company.toml`）の `[land]` に、関門（本流に入れる前に必ず通す検証）を書く。claude-plugins の関門は、写しの一致の検査（`python3 scripts/shared-copies.py`）だけを機械で回す。触ったプラグインのフォルダの下の試験（例: works-dispatch なら `works-dispatch/dispatch/tests`）は、部署が `--land` の前に手元で回す（役の本文に書いた）。
  - **CI は待たない**（持ち主の方針、2026-10-16 夕）。前は `release/*` の枝への push で走る GitHub Actions の CI を関門にし、緑を待ってから本流に入れる形にしていたが、やめた。CI は本流に入った後に壊れを見つける役で、main の CI が赤なら、最初の手は入れた commit を戻すこと（`git revert`）である。直すのはその後に、部署に失敗を渡して頼む。
  - 同じ日に、CI の試験の OS から macOS を外した（ubuntu と Windows だけ。macOS の runner が 40 分以上動き出さず、出荷が止まったため。持ち主の決め）。works の試験の job だけは macOS のまま。
  - **部署は版を上げない**（持ち主の方針、同じ日）。版は、本流に入れる命令 `--land` が、取り込むときに上げる（会社の形の `[land]` の `bump = "marketplace"`。works-dispatch 0.9.0）。版上げの commit は、本流に入れる一連の commit の最後に置く（claude-plugins の CLAUDE.md の出荷の決まり。版上げの後に commit を積むと main の CI が赤になる）。前は窓口が手で上げる形だった。
  - 本流に入れる順（作られた形。works-dispatch 0.9.0 の `--land`）。(1) 部署は自分の枝に commit し、触ったプラグインの試験を通して、自分の枝に push する。(2) 部署が自分で `--land <自分の部署の名前>` を打つ。`--land` は、本流がその枝の祖先なら、版上げの commit を足して関門を通し、本流を早送りして push する。(3) 本流が先に進んでいて早送りにならないとき（ほかの部署が先に入れたとき）は、`--land` は自分では merge せず、部署の窓に「本流の上に載せ直して push し直す」と打ち込んで止まる。部署は載せ直して push し、(2) を打ち直す。部署が 2 つ同時に入れようとしても、本流に入る順は早送りで 1 本ずつに決まる。(4) 入ったら、部署は入った commit を納品する。push の後に main の CI が赤なら、最初の手は入れた commit を戻すこと（上の CI の箇条）。
  - 窓口も、部署にできない検証（リポジトリ全体の試験）を代わりに回さない。全体の試験は CI が回す。
- **依頼を出すとき**: 承認を挟まない。アカウントの使用率の上限（既定 95%）で機械が止める。
- **同じリポジトリの別の clone**（`guided-resolver-cockpit`、`claude-plugins-work1`）: 代表の clone のほかに作った clone を片付け、1 つのリポジトリに clone は 1 つにし、部署は worktree で作る形に寄せる。片付けは中身を確かめ、消す物を持ち主に見せてからする。

前に「残っている問い」に置いていた、鍵の読み込みを作業場でも効かせる方法は、窓口の勧め（gh のアカウントの名前を渡す形）に沿って作られた（4.1）。持ち主の答えを待っている問いは、上の my_notes の AGENTS.md を誰がいつ書き換えるかだけである。
