# 借りるか買うかの部品（rentbuy）の設計

状態: 下書き（2026-10-24。持ち主と話して詰める途中。決まった所から「決めた」と書き替える）

頼み: my_notes の受付 20261024-044835-ea3e82（前の取り下げた頼み 20261024-033714-c5f1de の言葉も同じ件）

## 0. これは何か

keepalive の止め時・compact の打ち時・キャッシュの寿命の選び方は、どれも「少しずつ払い続ける（借りる）か、まとめて 1 回払う（買う）か」を、先が分からないまま決める問題（ski rental。https://en.wikipedia.org/wiki/Ski_rental_problem ）。今はどれも決まった数を手で持っている。

- keepalive: works-dispatch が 5 分で 25 本・1 時間で 40 本まで、寿命 − 90 秒おき（`works-dispatch/dispatch/nodes/role.py` の `keepalive_for`）
- compact: works-dispatch の `COMPACT_FLOOR = 100000`（`works-dispatch/dispatch/nodes/wake.py`）と、my_notes の役「相談」の「10 万トークンを超えていそうなら」の目安
- 単価: works-dispatch の `claudex.py` の倍率（読み 0.1 倍。5.5 系は 0.05 倍で古い）、my_notes の `claude_call.py` の `PRICES`

この設計は、判断の中心を 1 つの小さな部品にまとめ、keepalive と compact をその上に載せる。会話の文脈には何も足さず、フック（ハーネス）の側で判断する。

## 1. 形（全体）

```
       呼ぶ側（フック・待ち受け・スクリプト）
              │ JSON（その場の事実: モデル・寿命・文脈の量・送った累計 …）
              ▼
  ┌───────── 翻訳（場面ごとに 1 つ）──────────┐
  │ keepalive │ compact │ （後で）寿命 │ 続けるか新しく │
  └─────────────────┬───────────────────────┘
                    │ rent・buy・spent・certain（同じ単位＝ドル）
                    ▼
            中心: decide（止め時の決め方は差し替え: 固定 → 乱数 → 記録から学ぶ）
                    │ {action: rent|buy, why: 1 行}
                    ▼
            JSONL に 1 行残す（後で効きと外れを測る）
  値段の表（prices.toml。値ごとに原典の URL と確かめた日）を翻訳が読む
```

- 中心は場面を知らない。場面の知識（何が rent で何が buy か）は翻訳だけが持つ。
- 状態を持たない。呼ぶ側が毎回、累計（送った本数の費用・余分に読んだ累計）を渡す。
- 部品が無い・落ちたら、呼ぶ側は今の決まった数で動く（費用の最適化で、止めるゲートではない）。

## 2. 中心: decide

### 2.1 入力と出力

| 鍵 | 型 | 意味 |
|---|---|---|
| rent | 数 | 次の 1 回を借りる費用 |
| buy | 数 | 買う（まとめて 1 回払う）費用 |
| spent | 数 | この回（エピソード）で借りに払った累計 |
| certain | 真偽 | 次の出来事（待っている物）が来ることが確かか |
| miss | 数（既定 0） | 借り続けても買いを避けられない割合（外れ率） |
| hazard | 数か無し | 次の区間で出来事が来る確率（分かるときだけ） |
| policy | 字（既定 fixed） | 止め時の決め方 |

出力は `{"action": "rent" | "buy", "why": "…", "policy": "fixed", "version": "…"}`。

### 2.2 決め方（fixed。最初の版はこれだけ）

```
b' = (1 − miss)·buy                 外れの分だけ、借りて避けられる買いが減る
certain のとき:    rent  ⇔  spent + rent < b'
certain でないとき: rent  ⇔  hazard が有り、hazard > rent / b'   （無ければ buy）
```

- 1 回ごとの rent が一定なら、`spent + rent < b'` は指南 3.5 の「K = ceil(ρ) − 1 本まで送る」（ρ = b'/rent）と同じ。累計で比べるので、rent が回ごとに変わっても同じ式で済む。
- 決定的な止め方の最悪は、後から見た最適の 2 倍以内（2 − 1/ρ）。原典は https://en.wikipedia.org/wiki/Ski_rental_problem 。乱択なら e/(e−1) ≈ 1.58 まで下がる（同じ原典）。
- certain でないときは競合比が決まらない（来なければ最適は 0）。指南 3.5 の「来る確率が rent/buy を超える間だけ借りる」をそのまま使う。

### 2.3 差し替える決め方（後の段）

- random: 買う時点を確率で選ぶ（最悪 1.58 倍）。再現のために乱数の種を JSONL に残す。
- learned: 記録（JSONL と会話の記録）から待ちの長さや残りのターンの見込みを出し、見込みを信じる度合い λ を付けて止め時を決める（予測つきの ski rental。https://proceedings.neurips.cc/paper/2018/hash/73a427badebe0e32caa2e1fc7530b7f3-Abstract.html 。見込みが当たれば最適に近づき、外れても最悪の倍率が (1 + 1/λ) に収まる）。指南 13.1 の「残り n ターンなら」は、この見込みの入力に当たる。

### 2.4 外れ率 miss の扱い（頼みの宿題への答え）

1 時間の寿命でも約 1 割、訳の分からない外れがある（my_notes の受付 67bb10 の残った疑問 3。40〜60 分の間の 118 件のうち 14 件）。keepalive を送っても防げない外れなので、借りて避けられる買いはその分減る。式の入力 `miss` として扱う（1 時間は 0.1、5 分は測るまで 0）。1 時間・極限で上限は 39 本から約 35 本に下がる。値は値段の表と同じファイルに、測った日と出どころを付けて置く。

## 3. 翻訳

記号は指南（my_notes の `notes/knowledge/llm-agent-workflow-cost-design-guide.md`）に合わせる。`N` 文脈のトークン数、`p_r` 読み、`p_w'` 寿命に合う書き込み、`p_o` 出力の単価。

### 3.1 keepalive

```
rent  = c_k = p_r·N + p_w'·g_k + p_o·o_k     （g_k・o_k は実測 335〜380・5。呼ぶ側が上書きできる）
buy   = ΔC  = (p_w' − p_r)·N
spent = この待ちで送った keepalive の c_k の累計
certain = 仕事が終わっていない（受けた頼み・出した頼み・保留の頼みが在る）
```

- action が rent なら送る、buy なら止める（以後この待ちでは送らない）。
- 出力に `next_at`（送る時刻）を足す。下の 3.2 の寄せ方で出す。

### 3.2 送る時刻を寿命ぎりぎりに寄せる

```
next_at = 最後の api-request の時刻 + L − m
```

- 測り始めは、ターンの終わりでなく、会話の記録（transcript の JSONL）の最後の `api-request` の行の時刻にする。キャッシュの寿命は要求の開始から数える（https://code.claude.com/docs/en/prompt-caching ）。記録の時刻は手元で要求を出す前に付くので、サーバーが受けた時刻より早く、測りは安全側に寄る。
- `m`（余裕）は、待ち受けの見る間（`POLL = 1.0` 秒）・フックから要求が出るまでの遅れ（実測 0.3 秒。my_notes の調べものの部署の 04:34:19.8 → 04:34:20.1）・ずれの余裕を足した物。今の 90 秒は、ターンの終わりからの応答の生成の時間も含んでいた。測り始めを api-request にすると、その分が要らない。
- 寄せの得と損: 5 分の寿命で `m` を 90 → 30 秒にすると、1 時間あたりの本数は 17.1 → 13.3 本（約 22% 減）。1 本あたり約 0.22 本分浮き、外れ 1 回は約 22 本分（ρ）なので、寄せて増える外れが 1 本あたり 0.22 / 22 ≈ 1% 未満なら得。JSONL と会話の記録で、keepalive のターンの書き込み（cache_creation）が大きい本を外れとして数え、超えたら `m` を戻す。
- 無駄撃ちを避ける: 送る直前に、待っている物の知らせが届いていないか（台帳・裏の処理の終わり）を見て、届いていれば送らない（調べものの部署の 04:30〜04:38 の 1 本目は、裏の処理の終わりと同じ秒に送っていた）。

### 3.3 compact

```
rent_t = (C_t − C')·p_r                              要求 1 回ごとに、縮めていれば浮いた読み
buy    = 温かい: C·p_r + o_s·p_o + C'·p_w'
         冷えた: o_s·p_o + C'·p_w'                    （下の注）
spent  = 前の compact（無ければ会話の始め）から後の rent_t の累計
certain = true（次の要求が来るかは分からないが、来なければ rent も積もらないので、累計で比べる形は崩れない）
```

- action が buy になったら打つ。累計で比べるので、残りのターンの見込み（指南 13.1 の n）が無くても決まる。見込みが有れば learned の決め方の入力にする。
- 注（冷えたとき）: 冷えたキャッシュでは、打たなくても次の要求が文脈 C を書き直す。打つ側と打たない側の両方が C を払うので、差は要約の出力と C' の書き込みだけになる。これは指南 13.1 の残った疑問（「縮めない側も書き直しの費用を払う場合を入れていない」）への答えで、冷えたときは打つのに一番安い時になる。compact の要求が先頭を書き込みで払うか普通の入力で払うかは確かめていない（要確認。確かめるまで、冷えた buy に差の項 `C·(p_x − p_w')`〔`p_x` は compact の要求が先頭に払う単価〕を足せる形にしておく）。
- C' は前の compact の後の文脈の量の記録から出す（無ければ 2.5 万。指南 13.1 の例）。o_s は 5,000。
- buy も rent も C とともに増えるので、2 倍の保証は買値が一定の古典の形ほどきれいには言えない（要確認。測りで外れを数える）。
- 誰が打つか: 判断は待ち受け（works-dispatch の wake_hook）に移し、役の本文から「10 万トークンを超えていそうなら」の目安を外す。打ち方は今ある `--compact` の仕組み（入力フィールドが空なら機械が窓に `/compact <焦点>` を打つ）を使い、`COMPACT_FLOOR` の決まった数を decide に替える。

### 3.4 後で足す翻訳（最初の版の外）

- キャッシュの寿命（5 分か 1 時間）: rent = 5 分の寿命で待ちごとに払う書き直しや keepalive、buy = 1 時間の書き込みの割増し。指南 3.3 の規則を翻訳 1 つにする。
- works-factory の「前の会話を続けるか、新しく始めるか」: compact と同じ形で、C' を引き継ぎの量、buy を新しい会話の基本の文脈の書き込みにする。

## 4. 入出力の形と置き場

### 4.1 コマンド

```
rentbuy decide    < {"rent":…, "buy":…, "spent":…, "certain":true}
rentbuy keepalive < {"model":"claude-opus-5-5","ttl":300,"context":100000,"spent":0.033,
                     "certain":true,"last_request_at":"2026-10-24T04:30:44.330Z"}
rentbuy compact   < {"model":…, "ttl":…, "context":…, "after":25000, "warm":true, "spent":…}
```

- 標準入力に JSON、標準出力に JSON。Python の標準ライブラリだけで書き、関数としても読み込める（works-dispatch は Python なので、毎回プロセスを立てずに呼べる）。
- 判断ごとに JSONL を 1 行残す（入力・出力・版・時刻）。置き場は `~/.cache/rentbuy/decisions.jsonl`。足し続ける物なので上限を持つ（docs/standards/breakage-detection.md の「足し続ける物の上限」）。

### 4.2 値段の表

`prices.toml`。モデルごとに入力・出力・5 分の書き込み・1 時間の書き込み・読みの単価と、原典の URL（https://platform.claude.com/docs/en/about-claude/pricing ）と確かめた日。実測の値（`g_k`・`o_k`・`miss`）も同じファイルに、測った日と出どころ（受付番号）を付けて置く。呼ぶ側は JSON で上書きできる。works-dispatch の `claudex.py` の倍率と、my_notes の `claude_call.py` の `PRICES` は、この表を読む形にする。

### 4.3 置き場（決めた）

- 正本（式・記号の表・入出力）はこの設計書。my_notes の指南の 3.5 と 13.1 は、この設計書を指す短い要約に縮める（my_notes の部署が直す）。
- コードと値段の表は、このリポジトリの新しいプラグイン `rentbuy/`（marketplace に載せる）。中に薄いスキル（判断の読み方と JSONL の見方）を添える。
- 版の固定はタグでなく commit の SHA にする（このリポジトリはタグを作らない。持ち主 2026-09-29。works-factory の `PIN` と同じ形）。同じリポジトリの works-dispatch は、Claude Code の入れた物の控え（`installed_plugins.json`）から `rentbuy` の置き場を引き、無ければ今の決まった数で動く。

## 6. 試験

置くのは部品の約束 1 本: fixed の決め方は、どんな待ちの長さでも、費用が後から見た最適の 2 倍以内（持ち主 2026-10-24「テストは最小に」）。

## 7. 実装の割り振り（決めた）

- 部品 `rentbuy/` はこの部署で作る（受け持ちの無い新しいプラグイン）。
- works-dispatch のつなぎ込み（`keepalive_for` の上限・送る時刻・`COMPACT_FLOOR`）は、works-dispatch の受け持ちの割り振りへ頼む（会社の形 `.claude/company.toml` の受け持ちの決まり）。
- my_notes の側（指南の縮め・役「相談」の目安の削除・`PRICES`）は my_notes の部署へ一覧で渡す。
