# まっさらな環境で 4 回目の試し: Windows で道を最後まで通した（2026-10-16）

3 回目（[2026-10-16-clean-env-3.md](2026-10-16-clean-env-3.md)）の詰まりを、割り振りの担当が works-dispatch 0.19.1・tiers 0.4.3 で直した（本流 e1512dd）。今回の主は Windows で、README だけを読んで道を最後まで通した。macOS と Linux は、3 回目の直しの確かめに絞った。直してはいない。

この記録の言葉は 2 回目・3 回目の記録と同じ（窓口・部署〔担当と作業〕・会社と会社の形・関門・納品・「部署の回」・「人だけなら止まる」・段 2）。「3 回目の N」は 3 回目の記録の N 番目の項。`vm.sh` は Windows の VM に SSH で入る試しの道具（[windows-vm.md](windows-vm.md)）。

## 結果のあらまし

- Windows: 道（入れる → 点検 → 会社の形 → 担当を立てる → 頼む → `--land` → 納品 → 同じ担当に 2 つ目の頼み → 作業を頼んで `--clean` → `--reorg` と前の名前）を、作業の部署の片付けを除いて最後まで通した。
  - 3 回目に止まった Python の詰まりは消えた。フックは `python3` の代わりの物を飛ばして本物の Python を選び、担当の会話に役の本文と受け持ちが入った（下の 1）。
  - 新しく止まる所が 2 つあった。どちらも Windows だけで出た。
    - 部署を立てるたびに `launch_failed` になり、部署の窓に会話がつながらない。2 つ目の頼みが「窓に会話が居ない」で止まった（下の 2）。部署の窓で手で `claude attach <id>` を打つと先へ進めた。
    - 作業の部署の属性の会話の id が窓口の会話を指し、`--clean` がその部署を「会話がまだ動いている」として片付けない（下の 3）。
  - 3 回目の注記「信頼の印を付けられない（no_file）」は、今回は出なかった。代わりに、窓口が信頼したフォルダを「信頼していない」と言った。訳は、パスの区切りの字の違い（下の 4）。
- macOS と Linux: 3 回目の直しの確かめた 4 つは、どれも効いていた（下の「3 回目の直しの確かめ」）。macOS では、担当の `--land` を Claude Code の自動の権限の判定が止めた（下の 6）。
- 2 回目の 6（鍵を `GH_TOKEN` で渡す人の `gh_user`）は直っていた（下の「3 回目の直しの確かめ」）。
- 作った物は全部片付け、鍵の値が残っていないことを確かめた（下の「片付けと鍵」）。

## Windows で見つけた詰まり

### 1. Python の詰まりは消えた（3 回目の 7）

- 会話の中の `--check` は通った。窓口の AI は「python3 は Microsoft Store の代用品なので python で実行する」と言って、SKILL.md の `python3 …/dispatch.py` を `python` に替えて打った（下の 5）。
- 担当の会話の記録では、会話の始まりのフックが成功し（hook_success）、「この会話は会社「demo」の部署で、役は「担当」。受け持ちは「計算」（src/ の直し）。」と役の本文が入った。止まる前のフックも誤り無く走った。
- `--check` が出す herdr の連携を入れる命令は、PowerShell の形（`$env:CLAUDE_CONFIG_DIR='C:\Users\dev\.claude'; herdr integration install claude`）になった（3 回目の 8 も直った）。

### 2. 部署を立てるたびに `launch_failed` になり、部署の窓に会話がつながらない（人だけなら止まる）

- 何をして: 窓口から `--ask demo/担当 --task 計算 --branch feat/calc-sub --text …` と `--ask demo/作業 --task 説明：使い方 --branch feat/readme-usage --text …` を打った。
- どうなったか:
  - どちらも「打ち込んだが、会話の一覧に「計算」の裏の会話が出ない（画面の終わり: ）」の後に `launch_failed` となり、終了の値は 1 だった（3 回目の 9 の終了の値は直った）。
  - それでも、頼みは「新しく立てた部署 sent」で渡り、裏の会話は立って働いた。担当は sub を足して本流に入れ、納品した。
  - 部署のペインは、`claude --bg …` を打った後の PowerShell の入力待ちのままだった。dispatch は、会話を見つけた後に打つ `claude attach <id>` を打たない。
  - 2 つ目の頼み（`--ask 計算`）は「止めた: 宛先の部署 demo/計算（feat/calc-sub）の窓に会話が居ない（--sync で付け直すか、部署を開き直す）」で止まった。窓口の AI は、部署を立て直す案を出した。
  - 部署のペインで手で `claude attach <裏の会話の id>` を打つと、同じ `--ask` が通った。
- 訳（推定。確かめていない）: 打った直後に一覧を 1 回だけ見るので、Windows で裏の会話が一覧に出るより早く見ている。ペインには「Starting background service…」の後に「backgrounded · <id> · 計算」が出ていた。会話の名前は一覧に UTF-8 で正しく出ていた（VM の Python で `claude agents --json` を読んで確かめた）。
- 文書の足りない所: 部署の窓に会話が居ないときの直し方（`claude attach <id>` を部署の窓で打つ）を、どこにも書いていない。止めたときの言葉が勧める `--sync` は、属性の会話の id が違う（下の 3）ので効かないと見られる（試していない）。

### 3. 部署の属性の会話の id が窓口の会話を指し、`--clean` が作業の部署を片付けない

- どうなったか:
  - 担当と作業のどちらの部署も、作業場の git の設定の `company.session` が、窓口の会話の id（`aee2a240…`）だった。部署自身の裏の会話（`b1ffa499…`・`5d20abea…`）ではない。
  - `--clean` は作業の部署を「残す（会話がまだ動いている）」とした。部署の裏の会話を `claude stop` で止めても同じだった。窓口の会話は動き続けるので、この部署は `--clean` では片付かない。
  - `--tree` は、本社を「会話なし」、作業の部署を「作業中（会話 2）」と出した。
  - どこで窓口の id が書かれたかは確かめていない。上の 2 で会話を見つけられなかった回にだけ起きる形と見られる（macOS と Linux では起きていない）。
- この試しでは、作業の部署は VM の片付けの中で手で消した。

### 4. 窓口が信頼したフォルダを「信頼していない」と言う。訳はパスの区切りの字

- どうなったか:
  - 窓口の会話を代表の clone で起こし、信頼の確認で「Yes」を選んだ。その後の `--ask` は、毎回「アカウント default は C:\Users\dev\trial4\demo を信頼していない」「元の clone を信頼していないので、Claude Code がフォルダの信頼の確認を出す」と注記した。
  - Claude Code は、信頼を `.claude.json` の `projects` に `C:/Users/dev/trial4/demo`（区切りが `/`）で記録していた。dispatch の `claudex.is_trusted` は、`C:\Users\dev\trial4\demo`（区切りが `\`）の字のまま `projects` を引く。字が違うので見つからない。1 回目の 10（macOS の `/tmp` と `/private/tmp` の違い）と同じ形。
  - 部署の作業場に信頼の印は付かなかった。それでも、部署の裏の会話は信頼の確認で止まらずに立った。
  - 3 回目の「信頼の印を付けられない（no_file）」は今回出ていない。3 回目は代表の clone を信頼していなかったので、同じ根かは確かめられない。

### 5. 窓口の AI が、SKILL.md の `python3` の命令を自分で `python` に替える

- 窓口の AI は毎回「python3 は Microsoft Store の代用品なので python で実行する」と言ってから打った。今回は AI が埋めたので通った。SKILL.md の命令の形（`python3 "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py"`）は、Windows で人が打つと Store へ誘う代わりの物に当たる。README の「要る物」は代わりの物の切り方を書く。

## 3 回目の直しの確かめ（macOS と Linux）

- Python 3.9 の止まる前のフック（3 回目の 5）: 直った。PATH を `/usr/bin` だけにして（`python3` は 3.9.6）ふつうの会話を 1 つ起こすと、会話の始まりと止まる前のフックが両方とも「works-dispatch: Python 3.11 以上が見つからない（python3・python・py -3 を試した）。…」の 1 行で終わった（終了の値は 1）。traceback は出ない。
- Claude Code の外から打つ `--check`（3 回目の 6）: 直った。macOS と Linux のシェルから、herdr の server を起こす前に打つと、tiers を見つけて段の点検を走らせ、「段 2 herdr の動き: herdr の server が動いていない」を足りない物として止まった（macOS は終了の値 2）。
- 担当の最初の枝（3 回目の 4）: 直った。macOS と Linux で `--task 計算 --branch work/calc --role 担当 --brief …` で立てた担当は、最初の頼みで `feat/calc-sub` に移った。その `--land` の後、`work/calc` は消えた（`--land` の出力: 「前の枝 work/calc は消えました」）。
- commit に足すファイル（3 回目の 3）: 直った。3 つの OS の担当は、どれも `git add src/calc.py` で触ったファイルだけを足した。
- 鍵を `GH_TOKEN` で渡す人の `gh_user`（2 回目の 6）: 直った。macOS の一時の環境で、gh の鍵を `GH_TOKEN` にだけ入れて（`gh auth status` は「Logged in … (GH_TOKEN)」）`--init-company` を打つと、`gh_user` を書かず、「鍵を gh auth token --user で取り出せないので書かない（GH_TOKEN で鍵を渡しているときなど）」と注記した。その後の `--task --dry-run` は止まらなかった。

## macOS と Linux で見つけた詰まり

### 6. 担当の `--land` を、Claude Code の自動の権限の判定が止めた（macOS）

- どうなったか:
  - macOS の担当は、sub を足して commit した後、`--land 計算` を打った。Claude Code の自動の権限の判定（auto mode classifier）が「Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Merge Without Review]」で止めた。
  - 担当は、納品の要約に「本流への取り込みは権限の判定で拒否された。可否の判断を」と書いて返した。2 つ目の頼みでは「前回と同じく拒否される見込みのため実行していません」と書き、打たずに返した。
  - 窓口から `/works-dispatch:dispatch --land 計算` を打つと、拒否されずに通った。
  - 同じ版の Linux の担当と、2 回目・3 回目の担当では、拒否されなかった。判定は毎回同じではない。
- 文書の足りない所: 下書きの担当と作業の本文は「自分で --land して本流に入れる」と言う。自動の権限の判定に止められたときにどうするか（窓口に頼む・役の `settings` の `permissions.allow` に足す、など）は、どこにも書いていない。

### 7. 部署が試しに走らせた Python の `__pycache__` で、`--land` が止まる

- どうなったか: 上の 6 の後に窓口から `--land 計算` を打つと、「未コミットの変更か、git に足していないファイルがある」で止まった。担当が sub を確かめるために import して作った `src/__pycache__/` が、作業場に残っていた。窓口の AI は、消してよいかを持ち主に聞いた。消して打ち直すと通った。
- 3 回目の直し（関門の検証が作るファイルは消す・commit に足すのは触ったファイルだけ）は、部署の会話が自分で作って足さなかったファイルには効かない。試しのリポジトリには `.gitignore` を置いていない。
