# まっさらな環境で README だけを頼りに部署の仕組みを入れて使ってみた（2026-10-16）

持ち主以外の人が自分の PC で使えるかを確かめる試し。直してはいない。詰まった所・推測で埋めた所・持ち主の環境でしか動かない前提を集めた。

## 結果のあらまし

- marketplace の追加 → works-dispatch を入れる（tiers は依存として自動で入った）→ tiers の点検 → `--init`・`--check` → 部署を 1 つ立てる、まで通った。部署は頼みどおり commit し、窓口へ SendMessage で 2 回知らせた。
- 人だけでは止まる所が 3 つあった。
  - Python 3.11 以上が要ると、どこにも書いていない（下の 6）。
  - 使い捨ての手元のリポジトリでは部署を立てられない（下の 9）。
  - 根の README に、利用者向けの入れ方が無い（下の 1）。
- 試しで作った物（一時の HOME、clone、会話 2 つ、herdr の server と作業場）は全部片付けた。残っている処理は無い（ps で確かめた）。

## 試しの環境

- 版: macOS（Darwin 25.6.0）、Claude Code 2.1.301、herdr 0.9.3、gh 2.102.0、git 2.50.1。python3 は 2 つあった（`/usr/bin/python3` 3.9.6 と Homebrew の 3.14.7）。
- 隔離:
  - `mktemp -d /tmp/clean-env-trial.XXXXXX` の下に、`HOME`・`CLAUDE_CONFIG_DIR`（`$HOME/.claude`）・`XDG_CONFIG_HOME`（`$HOME/.config`）を作った。命令は `env -i` で起こし、渡したのは PATH・言語・proxy の変数（`HTTPS_PROXY`・`HTTP_PROXY`）だけ。
  - Claude Code の鍵は、Keychain から読んで `CLAUDE_CODE_OAUTH_TOKEN` にだけ渡した。ファイルにも画面にも出していない。
  - gh は「ログイン済みの人」に見立てた。持ち主の `gh auth token` の値を、`GH_TOKEN` として子の環境にだけ渡した。
- herdr: 今動いている物は使わず、一時の HOME で別の server（`herdr server`）を立てた。今動いている server の pane は持ち主の HOME と shell の設定を継ぐので、そこで起こす `claude` は持ち主の関数（`_claude_launch`）と持ち主の設定のフォルダになってしまう。それを避けた。一時の server なら、socket・作業場の置き場（`~/.herdr/worktrees`）・pane の環境が全部一時の HOME に入る。
- 使い捨てのリポジトリ:
  - 初めは、手元の bare リポジトリを origin にした clone で試した。これは通らなかった（下の 9）。
  - 代わりに、小さな公開リポジトリ `raiki61/reproduce_error_for_langmem`（既定の枝は master）を一時の場所に clone して使った。GitHub には何も書いていない。部署の commit は手元だけで、push していない。

## 記録（1 件ごとに: どこで・何をして・どうなったか・文書のどこが足りないか）

### 1. 根の README に、利用者向けの入れ方が無い（推測で埋めた）

- どこで: 根の `README.md`。
- 何をして: marketplace を足すコマンドを探した。
- どうなったか: 書いていなかった。根の README が書くのは、プラグインの表と、開発する人向けの「動作確認」の節だけだった。そこで次を推測して打ち、どれも通った。
  - `claude plugin marketplace add raiki61/claude-plugins`
  - marketplace の名前の `raiki61`（`.claude-plugin/marketplace.json` の `name` から読んだ）
  - `claude plugin install works-dispatch@raiki61`
- 文書の足りない所: 「入れ方」の節（marketplace の追加・install の名前・入れた後に使い始めの命令〔`/works-dispatch:dispatch setup`〕）。プラグインごとの README の行き先は表に有るが、works-dispatch の README は冒頭で「直す人向けに書く。使う人向けは SKILL.md」と言う。その SKILL.md への行き先は、リンクになっていない。

### 2. marketplace の追加は SSH の鍵が無くても通る（詰まりではない）

- 何をして: `marketplace add` の出力に `git@github.com:…` と出た。そこで、SSH の鍵を使えない形（`GIT_SSH_COMMAND` で鍵と設定を外した）で打ち直した。
- どうなったか: 「SSH clone failed, retrying with HTTPS」の後に https で通った。鍵の無い人でも詰まらない。

### 3. tiers は依存として入り、GitHub から足した marketplace でも `bin/` が PATH に入る（tiers の README の「要確認」が 1 つ解けた）

- 何をして: `works-dispatch@raiki61` を入れた。その後、一時の環境の `claude -p "/tiers:check 段 2 を点検して"` を走らせた。
- どうなったか: install の出力に `(+ 1 dependency: tiers)` と出た。会話の中の Bash で `tiers --tier 2` が名前で見つかり、走った。
- 文書: tiers の README の「確かめていないこと: GitHub から足した marketplace（キャッシュに写る形）でも同じか」は、macOS ではそのとおり動いた。Windows はまだ確かめていない。

### 4. attention が依存に入っていない。`--check` の言葉が、何を入れるかを言わない

- どこで: `dispatch.py --check`。
- 何をして: works-dispatch だけを入れて `--check` を打った。
- どうなったか: 「アカウント default で /catchup の命令が 1 つに決まらない（commands/catchup.md を持つプラグイン: 無し）」で止まった。`claude plugin install attention@raiki61` を打つと通った。
- 文書の足りない所:
  - README の前提の 4 は「`/catchup` を持つプラグイン」とだけ書き、attention の名前も入れ方も書かない。SKILL.md の前提には attention の名前が有るが、入れ方（`attention@raiki61`）は無い。
  - `--check` の言葉も、入れるコマンドを出さない（tiers が足りないときは出すのに）。
  - attention を `dependencies` に入れない訳も書いていない。部署（`--task`）だけを使う人には要らないから、なら筋は通る。

### 5. `--init` の下書きは「欄の意味: README」と言うが、利用者向けの欄の説明は SKILL.md に在る

- どこで: `--init` が書く `~/.config/works-dispatch/dispatch.toml` の 2 行目。
- どうなったか: README の前提の節は直す人向けの書き方だった。`accounts` の書き方の 3 通りは SKILL.md の「アカウントの書き方」に在った。
- ついでに:
  - 設定がもう在ると、`--init` は「上書きしない。足すなら手で書く」で終わる（終了の値 1）。2 つ目のリポジトリを足す手（`[[repos]]` を手で足す）は、文書に無い。
  - `--init` は `--repo` を origin と突き合わせない。存在しない `trial/demo` でも下書きを書いた。違いは `--check` で初めて出る。

### 6. Python 3.11 以上が要ると書いていない。macOS 付属の python3（3.9）では dispatch もフックも落ちる（人だけなら止まる）

- どこで: SKILL.md の `python3 "${CLAUDE_PLUGIN_ROOT}/dispatch/dispatch.py"`。それと、プラグインのフック（`hooks/hooks.json` の SessionStart と Stop。どちらも `command -v python3`）。
- 何をして、どうなったか:
  - シェルから `/usr/bin/python3`（3.9.6）で `--check` を打った。`import tomllib` の `ModuleNotFoundError` で落ちた。
  - 一時の環境の窓口の会話（Claude Code の中）で `/works-dispatch:dispatch --task …` を打った。Bash の `python3` は 3.9.6 で、同じく落ちた。1 回目の窓口は止まって、どの Python を使うかを人に聞いた。起こし直した 2 回目の窓口は、自分で `/opt/homebrew/bin/python3.14` を見つけて走らせ直した。AI が埋めたので通ったが、人が手で打つなら止まる。
  - Stop のフック（`orders.py stop`）は、窓口の会話のターンが終わるたびに `tomllib` の traceback を「Stop hook error: Failed with non-blocking status code」として画面に出した。部署でない、ふつうの会話でも出る。works-dispatch を入れただけで、全部の会話の毎ターンに出ることになる。
  - 部署の会話のフックは通った（SessionStart の役の文が入った）。違いは、Claude Code を起こしたシェルの PATH と見ている。窓口の pane のシェルは、Homebrew の PATH を足す `~/.bash_profile` を置く前に起きていた。部署の pane のシェルは、置いた後に起きた（推定。確かめていない）。
- 文書の足りない所:
  - 要る Python の版（3.11 以上）を、README・SKILL.md の前提に書いていない。
  - tiers も Python の版を見ない。
  - README は 3.9 の問題を、herdr のタブ欄から呼ぶ道（`limits.py`）にだけ書いている。

### 7. Claude Code の外から `--check` を打つと、「tiers が見つからない、install せよ」と出る（入っているのに）

- どこで: `dispatch.py --check` を、一時の環境のふつうのシェルから打った。
- どうなったか: 「段の点検の部品（tiers プラグインの bin/tiers）が見つからない。works-dispatch の依存だが、claude plugin update では入らない。シェルで claude plugin install tiers@raiki61 を打ち…」と出た。tiers は入っていた。原因は、Claude Code の外で走らせたので PATH にプラグインの `bin/` が無いこと。そのうえ、tiers の段の点検（herdr が動いているか、gh のログイン）は飛ばされた。
- 文書の足りない所: README は見つからない訳を 2 つ書く（「依存の入っていない古い入れ方・Claude Code の外から走らせた」）。言葉は 1 つ目しか言わない。SKILL.md の setup の手順も、Claude Code の中で打つ前提を書いていない。シェルで打つ人は、要らない install に誘われる。

### 8. tiers は、herdr の socket が見つからないと「server が動いていない」と言う（この試しの作り方の都合で出た）

- どうなったか: `HOME`・`XDG_CONFIG_HOME` を替えると、動いている herdr の socket（`~/.config/herdr/herdr.sock`）が見えない。tiers は「herdr の server が動いていない: status: not running」「作業するフォルダで herdr を起こす」と出した。
- 文書: ふつうの利用者には起きにくい。出るときは、どこの socket を見たかが無いと、動いているのに何故、で止まる。

### 9. 使い捨ての手元のリポジトリでは、部署（`--task`）も立てられない（人だけなら止まる）

- 何をして: 手元の bare リポジトリを origin にした clone で、`--init --repo trial/demo` → `--check` → `--task … --dry-run` を打った。
- どうなったか: `--task --dry-run` も「始める前の確かめで足りない物」で止まった。理由は次の 2 つ。
  - 「元の clone が、このリポジトリの clone でない」
  - 「gh が trial/demo を読めない。whose-turn が自分の番の PR を集められない」
  部署は PR を読まないが、確かめは PR を開く回と同じだった。
- 文書の足りない所: SKILL.md の「部署を立てる」には、GitHub に在って gh で読めるリポジトリが要るとは書いていない。試しの手順を書く人（この頼みも）は、使い捨ての手元のリポジトリで済むと読む。

### 10. フォルダの信頼の判定が、記号のリンクの先のパスで外れる（macOS の `/tmp`）

- 何をして: 窓口の会話を代表の clone で起こし、信頼の確認で「Yes, I trust this folder」を選んだ。その後に `--check` を打った。
- どうなったか: Claude Code は、信頼を実体のパス `/private/tmp/…/demo` で記録した。dispatch は設定の `source` の字（`/tmp/…/demo`）のまま引くので、「信頼していない」の注記が消えなかった。macOS の `/tmp`・`/var` のように、記号のリンクを通るパスなら誰でも起きうる。
- 文書の足りない所: `source` を実体のパスで書くことは、どこにも書いていない。

### 11. 信頼の印を付ける先の `.claude.json` を、環境から入った `CLAUDE_CONFIG_DIR` で探さない（この試しの作り方で出た）

- どうなったか:
  - 部署を立てたとき、窓口の報告に「信頼の印は書けなかった（no_file）」と出た。
  - dispatch は、`config_dir` を書かないアカウントのフォルダを、`CLAUDE_CONFIG_DIR` を外して起こした新しいログインのシェルの値で決める（`_login_config_dir`）。
  - この試しでは、`CLAUDE_CONFIG_DIR` をシェルの設定ではなく、親の環境（herdr の server）から継がせていた。だから dispatch は `$HOME/.claude.json` を探し、無かった。
  - 部署の裏の会話は、信頼の確認で止まらずに動いた。
- 文書の足りない所: SKILL.md の「アカウントの書き方」は、`CLAUDE_CONFIG_DIR` をシェルの設定ではなく環境（ログインの環境・端末の設定・herdr を起こした環境）で入れている人の書き方を言わない。`config_dir` を書けば避けられるかは確かめていない。

### 12. 初めての Claude Code の画面（README の「Esc で信頼済み」は確かめていない）

- どうなったか: 一時の設定のフォルダで初めて対話の Claude Code を起こすと、次の 3 つの画面が順に出た。
  - 色の選び
  - 安全の注意
  - フォルダの信頼。選択の頭が「No, exit」に在り、下に「Enter to confirm · Esc to cancel」と出た
- 文書: README の「試しの実行で確かめた外の振る舞い」は、「信頼の確認の画面で Esc を押すと、会話は終わらずに進み、そのフォルダが信頼済みとして記録された」と書く。今回は Esc を試さず「Yes」を選んだ。画面の案内（Esc to cancel）と README の記述が逆に読めるので、2.1.301 で確かめ直す値打ちがある。

### 13. 持ち主の環境にしか無い前提・行き先

- 持ち主のシェルでは `claude` が関数（`~/.config/shell/env.sh` の `_claude_launch`。Keychain の項目 `claude-code-oauth-default` から鍵を入れる）。持ち主の herdr の pane で設定の `command = "claude"` を打つと、この関数になる。他人の PC では素の `claude` で、文書の言うとおりに動く。ただし、持ち主の pane で他人の環境を試すと、持ち主の関数と設定のフォルダに化ける（今回、herdr を別に立てた訳）。
- README・SKILL.md が名指す設計の正本 `docs/specs/2026-10-16-company-shape-design.md` は、main ではなく枝 `docs/company-shape` にだけ在る（origin に在ることは確かめた）。main の `works-dispatch/docs/specs/` には 10-14 の物しか無い。
- tiers の README が名指す世間の形の調べは、持ち主の非公開のリポジトリ my_notes に在る。他人は読めない。
- README の `--land` の例の `tools/check.py` は my_notes の物。他人には例としてだけ読める。

### 14. この試しの作り方の都合で詰まったこと（文書の穴ではない）

- `env -i` で proxy の変数まで外すと、`claude -p` は答えを返さず、ECONNREFUSED の再試行を 5 分続けた。社内の proxy の内側の人は、`HTTPS_PROXY` が要る。SKILL.md は herdr のタブ欄の道にだけ書く。
- 一時の HOME を `~/.claude/jobs/…` の下に置くと、上の階の `~/.claude/CLAUDE.md` が「project instructions」として会話に入った。`/tmp` の下に移して避けた。

## 通ったこと（同じ版で確かめた）

- `/tiers:check` の段 2（gh にログイン済み・herdr が動いている状態）は全部 ok。
- `--task 試し --branch trial/one --brief <頼み>` を窓口の会話（`claude --name 窓口`）から打った。結果は次のとおり。
  - herdr が `$HOME/.herdr/worktrees/demo/trial-one` に worktree と子の作業場を作った。
  - 部署の属性（`company.role` = 作業役・`residency` = per-task・`account`・`name`・`boss` = 窓口・`boss-account`・`session`）が worktree の git の設定に入った。
  - 裏の会話が起き、SessionStart のフックが「この会話は会社「demo」の部署で、役は「作業役」。」を足した。
  - 連絡の道は同じアカウントなので SendMessage になり、部署から窓口へ 2 回届いた。
- `--tree` は、本社（master・窓口）と部署（trial/one・終わった・上役 窓口）を出した。
- `--clean` は「残す（手元にしか無い commit か stash が有る）」で、書いてあるとおり消さなかった。
- 片付け: 次の順に済ませた。最後に ps で、一時の場所を指す処理が無いことを確かめた。
  1. `claude rm <部署の会話>`
  2. `herdr worktree remove --workspace <部署>`（手元の枝は残る → 一時の場所ごと消した）
  3. 窓口を `/exit`
  4. `herdr server stop`
  5. 一時の場所を `rm -rf`
