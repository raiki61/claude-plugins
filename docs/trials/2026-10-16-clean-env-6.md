# まっさらな環境で 6 回目の試し: 締めの確かめ（2026-10-17）

5 回目（[2026-10-16-clean-env-5.md](2026-10-16-clean-env-5.md)）の後に、割り振りの担当（works-dispatch と tiers を直す受け持ちの部署）が道の外の 5 項目を works-dispatch 0.19.4・tiers 0.4.4 で直した（本流 586a53e）。3 つの OS で道を最後まで通し、5 回目までの直しが戻っていないかと、落ちた部署の戻し方を確かめた。直してはいない。

この記録の言葉は前の記録と同じ（窓口・部署〔担当と作業〕・会社と会社の形・関門・納品・「部署の回」・「人だけなら止まる」・本社・部署の属性）。「N 回目の M」は N 回目の記録（[1 回目](2026-10-16-clean-env.md)〜[5 回目](2026-10-16-clean-env-5.md)）の M 番目の項。`vm.sh` は Windows の VM に SSH で入る試しの道具（[windows-vm.md](windows-vm.md)）。

## 結果のあらまし

- 道の上の詰まりは、3 つの OS とも 0 のまま。macOS・Linux・Windows で、道（入れる → 点検 → 会社の形 → 窓口を名付ける → 担当を立てる → 頼む → `--land` → 納品 → 同じ担当に 2 つ目の頼み → 作業を頼んで `--clean` → `--reorg` と前の名前）を手当て無しで通した。
- 落ちた部署の戻し方（0.19.4 の直し）は、3 つの OS のどれでも働かなかった。人だけなら止まる（下の 1・2）。
  - 部署の窓に会話がまだ居ると見なされる落ち方（裏の処理が止まり、窓の attach の画面が終わった）では、`--ask` は attach を打たずに「まだ納品していない」で止まる（Linux と Windows）。
  - 窓が無くなった落ち方（herdr も止めて起こし直した）では、`--ask` は attach を打つが、会話の id を長い形（UUID）で渡すので「No job matching」になり戻らない（macOS）。
  - どの OS でも、部署の窓で短い id（`claude attach 1afcdb7e` のような 8 字）を手で打つと前の続きから戻り、続きを頼むと本流に入れて納品した。
- 5 回目の直しの確かめた 4 つは、どれも効いていた（下の「5 回目の直しの確かめ」）。
- 作った物は全部片付け、鍵の値が残っていないことを確かめた（下の「片付けと鍵」）。

## 落ちた部署の戻し方（0.19.4 の直しの確かめ）

### 1. 窓の attach が終わっても「窓に会話が居る」と見なされ、`--ask` は戻さずに止まる（Linux と Windows。人だけなら止まる）

- 何をして: 担当に larger を頼み、10 秒ほど後に Claude Code の裏の処理を止めた（`claude daemon stop --any`。裏の会話が全部落ちる）。herdr の server は動かしたまま。続けて窓口から別の頼み（smaller）を `--ask 計算` で打った。
- どうなったか:
  - 部署のペインには「Session cb2d81c3 has exited.」が出て、シェルの入力待ちに戻っていた（attach の画面は終わっていた）。
  - `--ask` は attach を打たず、「止めた: 宛先の部署 demo/計算係 は受付 …（頼み元 窓口）をまだ納品していない。納品を待つか、別の部署に頼む（部署の会話が動いていないなら、部署の窓で続きを頼む）」で止まった（終了の値 2）。
  - 言葉は「部署の窓で続きを頼む」と言うが、窓はシェルなので、そのまま打っても会話には届かない。
- 部署の窓で `claude attach <短い id>` を手で打つと会話が戻った。「止まる前の頼みを続けて、本流に入れてから納品して」と打つと、担当は larger を本流に入れて納品した（Linux と Windows）。
- 確かめたコード（`dispatch/orders.py`）: 窓に会話が居るかを先に見て、居なければ戻す（`revive`）。この落ち方では窓が在ると見なされたので、戻す道に入らなかった。何をもって「居る」としたかは確かめていない。

### 2. 窓が無くなった落ち方では attach を打つが、長い id で「No job matching」になる（macOS。人だけなら止まる）

- 何をして: 作業の部署に README の節を頼み、30 秒ほど後に裏の処理と herdr の server を両方止めた（再起動の代わり）。herdr を起こし直し、窓口を起こし直して `--desk` を打ち、`--ask 説明：使い方` を打った。
- どうなったか:
  - `--ask` は部署のペインに `claude attach 1afcdb7e-4e4f-4b39-953e-20699b490e28` を打った。Claude Code は「No job matching '1afcdb7e-…'. Run 'claude agents' to list running sessions.」と返した。
  - `--ask` は「ペイン w3:p1 で claude attach 1afcdb7e-…（長い id）を打ったが、窓に会話が戻らない（画面を見て、会話が戻ったら --ask を打ち直す）」「止めた: …の窓に会話が居ない」で止まった。
  - 同じペインで短い id（`claude attach 1afcdb7e`）を打つと、会話が戻った。`claude stop` で止めた担当の会話も、短い id なら戻った。
  - 戻した後の `--ask` は「まだ納品していない。…（部署の会話が動いていないなら、部署の窓で続きを頼む）」で止まった。窓で続きを頼むと、作業の部署は本流に入れて納品した。
- 確かめたコード（`dispatch/orders.py` の `revive`）: 打つ命令は `attach {sid}` で、`sid` は部署の属性の `company.session`（長い id）。部署を立てるときの attach は、`claude agents --json` の短い `id` を先に使う。
- 5 回目の 1 で Windows の担当が戻ったのは、手で短い id を打ったからだった。

## 5 回目の直しの確かめ

- 古い Python の会話の始まりのフック（5 回目の 2）: 直った。PATH を `/usr/bin` だけにした macOS の会話を `claude -p` で 1 ターン、続けて `--continue` でもう 1 ターン回した。会話の始まりのフックの 1 行は 1 ターン目にだけ出て（終了の値 1）、2 ターン目（`SessionStart:resume`）は何も出さなかった（終了の値 0）。止まる前のフックは、どちらのターンも何も出さなかった。
- `--init` の下書き（5 回目の 3・1 回目の 5）: 直った。2 行目は「# 欄の書き方: works-dispatch の skills/dispatch/SKILL.md の「初めて」と「アカウントの書き方」（前提の訳は docs/prerequisites.md）」になった。origin が `raiki61/claude-plugins` の clone に `--repo trial/demo` を渡すと、「止めた: --source の … は origin が raiki61/claude-plugins の clone で、--repo の trial/demo と合わない」で止まった（終了の値 2）。下書きには「CLAUDE_CONFIG_DIR をシェルの環境でだけ入れて claude を起こす人も、そのフォルダを config_dir に書く」が入った。
- tiers の socket の言葉（5 回目の 4・1 回目の 8）: 直った。herdr の server を起こす前の `tiers --tier 2` は「NG 段 2 herdr の動き: herdr の server が動いていない（見た socket: …/home/.config/herdr/herdr.sock）: status: not running」と出した。
- macOS の信頼の印（5 回目の「1 回目の 11」）: 直った。部署の作業場の印は `/private/tmp/…/feat-calc-sub` の形で書かれ、Claude Code が代表の clone を記録した形（`/private/tmp/…/demo`）と揃った。担当の裏の会話は信頼の確認で止まらずに立った。
