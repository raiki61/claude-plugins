# 自分のリポジトリに合わせる

## 固有の規約はどこにも書かない

同梱の `REVIEW.md` には固有の技術名が無い。アーキテクチャ境界・標準機構・機械強制されている検査は、grader が対象リポジトリの一次情報から毎回把握する（`REVIEW.md` の「固有規約の把握」）。

**書き写したくなったら止まる。** 書いた瞬間に正本の複製になり、リポジトリが変わっても古いまま残る。lint 設定を 1 行変えたのに観点側の記述が古い、という形で事故が起きる。

一次情報が薄いリポジトリ（README にアーキテクチャの記述が無い等）では、grader は近傍の実際の import から推定し、推定であることを明記する。**推定が続くなら、直すべきは観点ではなくリポジトリの文書のほう**——それ自体が「開発者導線の整合性」観点の指摘になる。

なお grader が見るのは、文書に書かれた理想ではなく**近傍が実際に使っている機構**である。両者が食い違っていれば、その食い違い自体が指摘になる。

## 自分のリポジトリの観点を足す

対象リポジトリのルートに `REVIEW.md` を置くと、同梱の観点と併用される。同梱側と同じ観点を書き写さず、そこに無いものだけを置く。

## 言語・ホストが違う場合

**注釈比率が測れない言語**: `comment-ratio.sh` は Python（`tokenize`）と C 系コメント（`//` `/* */`）の言語だけを数える。`#` 系（Ruby・Shell）を `EXTS` に足すと、注釈を 1 行も拾えないまま「注釈 0%」を出す——足さず、行数で別に測る。C 系の言語で対象に入っていないものは `EXTS` に足せば動く。

**GitHub 以外のホスト**: `/review-loop` の P0-5（並行 PR の衝突チェック）が `gh` を使う。同等コマンドに読み替える。読み替えられないなら、未確認を「衝突なし」と書かせず「確認できなかった」と報告させる。

**fork 運用・複数アカウント（`gh` の取り違え）**: これが `-R owner/repo` を毎回渡す理由の正本。**`-R` に渡す値は `git remote get-url` から導け**——`gh repo view` は cwd の remote から解決するので、それを `git remote -v` と突き合わせても原理的にほぼ必ず一致し、取り違えを弾けない（恒真な検査になる）。`-R` 無しの `gh` は cwd の remote と `gh` のログイン状態に暗黙依存し、fork 運用や別アカウントでログイン中でも**エラーにならず別リポジトリの PR 一覧を返す**。取り違えは正常終了するので、上の「GitHub 以外のホスト」のフォールバック経路には乗らない——衝突チェックが静かに空振りする。`gh auth switch` で複数アカウントを使い分けているなら、解決された `owner/repo` が意図したものか毎回確認させること。

**計測が exit 2 で止まる場合**: `git add -N <path>` で未追跡の対象ファイルを差分に載せてから測る（P0-1 が指示している手順）。止まる条件と、その 1 条件だけに絞ってある理由は `comment-ratio.sh` のヘッダが正本。

**`Workflow` ツールが無い環境**: `/research-loop` の P1 はワークフロースクリプトで checker → refuter の扇を回す。使えない環境では、同じ構造（checker=`investigator` → 相違と【荷重】確証に refuter=`judge`・同じ判定語彙と schema）を `Agent` の並列起動で再現する。手順本文にその指示がある。

## 役割 agent を変える

4 ループが立てる subagent は `agents/` の 6 つの役割定義（`convergence-loops:<役割>`）で起動する。モデル・effort・持てる道具はそこが正本で、手順書は役割名しか書かない。

**手順書にモデル名を書き戻さないこと。** `tests/run.sh` がモデル名の出現（`model:` の形でも散文でも）と `general-purpose` の復活を検知して落ちる。

モデルや effort を変えたいときは、この plugin を fork して `agents/<役割>.md` の frontmatter を直す。手順書は `convergence-loops:` 付きの識別子で役を指すので、対象リポジトリの `.claude/agents/` に同名の定義を置いても上書きにならない。全 subagent のモデルだけを一括で差し替えたいなら環境変数 `CLAUDE_CODE_SUBAGENT_MODEL` が定義より優先される（effort と道具は定義のまま）。

**遮断系（`cold-reader` / `blind-judge`）の `tools: []` を消さないこと。** 空にすると道具なしで起動する（実測 2026-08-21・Claude Code 2.1.238・`claude -p` で `tools: []` の agent にファイルを読ませようとして失敗、`tools: Read` なら読めた）。`tools` の行ごと消すと全道具を継承し、「読むな」が言い渡しに戻る。

## ラウンド記録の置き場所

既定は `.claude/review-rounds/round-<N>.json`。作業ファイルなので `.gitignore` に入れておく。

**前ラウンド分を消さないこと**。連続 2 ラウンドの突合と、`defer` の台帳がこれで成立している。新しい context での再採点は前ラウンドの受容判断を知らないので、台帳を P2 の judge に渡さないと同じ提案が毎ラウンド再燃して収束しない（渡すのは judge だけ。P1 の探す役と R2 には渡さない——手順書 P2「履歴との突合」）。`review-record.py` は前ラウンドの `defer` キーが新証拠（`reopen_evidence`）無しに `[block]` / `do-now` へ戻った記録を不正として止める。

チームで記録を証跡として残す方針ならコミットしてよい。記録には findings の要約が入るので、レビューの経緯が追える。

## 記録の schema

正本は `scripts/review-record.py` の `MATERIALS` / `STATUS`（素材）、`REVIEWS` / `REVIEW_STATUS`（P-R の R1〜R4）、`LABELS`。手順書は列挙を持たない（二重管理を避けるため）。実例は `templates/round-1.example.json`（`[block]` が残る初回）・`round-2.example.json`（解消した直後。連続 2 ラウンドの 1 ラウンド目）・`round-3.example.json`（連続 2 ラウンド成立。持ち越しと、問いの台帳の `escalate` / `split` の書き方）。問いの台帳の 3 周の推移（`held` → `resolved`、`held` → `escalate`）は 3 つを並べて読む。

素材は P1 の各観点に加え、**P0 の各段のうち他に検査経路を持たないもの**も含む（どれが該当するかは `MATERIALS` のコメントが正本。手順書側は各段が自分の素材名を名指しする）。writer の自己申告に留めず突合に載せるためで、素材を増やすと**それ以前に書いた記録は明示返答を欠いて `exit 2` になる**（全素材の返答が要るため）。

素材の状態の値と、値ごとに要求される欄は `STATUS` が正本（ここに写すと腐る）。**「条件に当たらない」と「やるべきだったが飛ばした」と「人の起動待ちで止まっている」を別の値にして潰さない**のがこの schema の要点で、潰すと報告上で見分けられなくなる。`clean`（今ラウンドに見たが無かった）には「何を見たか」を要求する——見た範囲が書けないものは、見たと言えない。`carried_over`（前ラウンドの判定を流用）には実際に見たラウンド `from_round` を要求し、持ち越しが続いてもその値が動かないこと（連鎖）を前ラウンドと突合する——`clean` に混ぜると、最後に見たのが何ラウンド前かが誰にも見えなくなる。

R1〜R4 の判定も同じ記録の `reviews` に載る。取りうる値と、値ごとにどの R に許されるかは `REVIEW_STATUS` / `STATUS_ONLY_FOR` が正本。**役ごとに許す値を絞ってあるのは、P-R に到達していない R3 / R4 と、再発火条件に当たらず持ち越した R1 / R2 を、記録の上で区別するため**である。「直せ」の印と「人に諮れ」の印も分かれて出る。阻害要因が他に無いのに R3 / R4 が `not_applicable` なら、P-R を飛ばしたとして阻害要因になる。

連続 2 ラウンドは道具が数える。今ラウンドに阻害が無くても、前ラウンドに阻害があれば「1 ラウンド目」として exit 1 になる。初回に阻害が無ければ 2 ラウンド目で成立する。

**欄の名前は `status`**（`verdict` ではない）。素材も R1〜R4 も問いも、状態を書く欄はすべて `status` で、追加で要る欄がその値ごとに決まる（正本は `review-record.py` の `STATUS` / `REVIEW_STATUS` / `QUESTION_STATUS`）。散文でこれを「verdict」と呼ぶのは役の呼び名であって欄名ではない。

`review-record.py` には記録のディレクトリを渡す。全ラウンドを読んで最新を突合し、**履歴**（キーごとの判定の推移・直したはずの再出現・要対応の件数と scalar の推移・問いの台帳の推移）を出す。履歴は P2 の judge に「ラベル確定後に」渡す入力で、最終報告の冒頭にも貼る。機械は履歴を解釈しない。

**問いの台帳**（`questions`）は人に聞く候補の置き場で、**載せた周には聞かない**。種類と状態の値、値ごとに要求される欄、種類ごとの `origin` の域は `review-record.py` の `QUESTION_KINDS` / `QUESTION_STATUS` が正本（**ここに写すと腐る**——素材の `STATUS` と同じ理由）。次の周の judge が再審して振り分ける。**状態は 2 軸**——決着したかと、出どころの欠陥がまだ開いているか。決着済みで欠陥が残っていれば `decided`（台帳から降りないが、人に聞く候補には数えない）、欠陥も閉じたら `resolved`（次の周の台帳から落としてよい）。2 軸目は欄でなく記録から判定するので、出どころが開いたまま `resolved` と書くと記録の不正になる。止まる経路は手順書の「停止条件」が正本——どれも writer が「もう聞くしかない」と決めるのではなく、機械か上限が言う。「立った周には聞かない」を機械が持つのは帰属の条件 1 つで、中身と実測は `blockers()` の docstring が正本。ループが自分で決めた問いは最終報告に根拠つきで並び、人が覆せる。人に聞く候補が無いラウンドは空の配列を書く（雛形はどれも非空なので、そこからは読み取れない）。

R1 の前段は、累積差分が触れたファイルのコメントの削除候補を `pr-review-toolkit:comment-analyzer` に挙げさせる。呼ぶときのプロンプトに 3 つ足すのが要点で、①削除候補には同じ内容の在り処を名指しさせる（確かめられる形にする）②残す判断にも運んでいる事実を一文で言わせる（片側にだけ義務があると残す側に倒れる）③残す線は `REVIEW.md` が正本。0.22.0 まではコメントを剥がした写しを文脈を知らない読み手に読ませる自作の仕掛けだったが、3 ラウンドで削除の実績が 0 件・隔離も 2 ラウンド連続で破れたので落とした。
