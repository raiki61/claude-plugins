# coldread 網の次段: シェル文字列の解析をやめる乗り換え先メモ

急ぎではない。coldread ゲート(gates プラグインの投稿前検査フック)の判定方式を、条件が満たされたときに乗り換えるための設計メモ。読むだけでよい。

## 何の話か

coldread ゲートは「Bash で実行されようとするコマンド文字列」を受け取り、その中の gh コマンドが GitHub へ本文を投稿する操作かどうかを判定して、投稿なら本文を読み役に検査させる。この「文字列から判定する」方式には原理的な限界がある——シェルの引用・複合コマンド・ヒアドキュメントを自前で解釈する必要があり、完全なシェル解析器は Python 単体スクリプトの配布形に載らない(Python 製 bashlex は引用符付きデリミタのヒアドキュメントで終端検出が壊れる既知バグ https://github.com/idank/bashlex/issues/99 、完全な mvdan/sh は Go 製)。

2026-08-28 の調査で、gh 公式にも代替は無いと確認済み:

- コマンドの read/write を機械判定したい要求は https://github.com/cli/cli/issues/12912 に起票済みのまま停滞。本文に「正規表現でのコマンド検証は脆弱」と明言がある
- 投稿前に確認を挟む公式機構の要求も https://github.com/cli/cli/issues/12624 のまま停滞

現行は段階的な解き方——`\bgh\b` の粗選別 → ヒアドキュメントの盾置換 → 標準ライブラリ shlex でトークン化 → 単純コマンド単位で旗の帰属を判定——を採っている。盾置換の前処理は RoaringFerrum/claude-code-bash-guardian に同型の先行例があるが(あちらの本体は bashlex の構文木)、単純コマンド分割と旗表は自作で、網羅性はテストで守っている。静的判定を先に置き曖昧なものだけ LLM に回す構成が純 LLM 判定より優るという評価もある(CARE, https://arxiv.org/html/2607.21642v2 。ただし当該論文の対象は本ゲートと別ドメインで、数値をそのまま持ち込めない)。

## 乗り換え先の案 1: PATH シム

**PATH シム方式**: gh と同名のラッパースクリプトを PATH の先頭に置く。シェルが解析を終えた後の引数列(argv)がそのまま届くので、引用・複合コマンド・ヒアドキュメントの解釈が一切不要になる。本文が stdin から来る場合も実物のバイトが届く。判定後は実物の gh に引数をそのまま渡す。

- 旗の意味(たとえば -F が --body-file か --field か)は、gh の隠しコマンド `gh __complete <サブコマンド> "-"` に聞くと gh 本体が文脈込みで答える(補完スクリプトの実体がこれ)
- gh api の書き込み判定は公式ルールがある: パラメータ付きで -X 未指定なら POST になる( https://cli.github.com/manual/gh_api )
- 方式の前例: バージョン管理ツール(asdf/rbenv)の shims、gh を含む 8 CLI の呼び出しを記録する監査ツール DEPOSE( https://github.com/Aftermath-Technologies-Ltd/depose )

## 何が起きたら乗り換えるか

1. セグメント判定の誤判定(素通り・誤ブロック)の実例が、実運用・レビューを問わず繰り返し出る
   (「実運用で観測されたら」を条件にしない——素通りは定義上「黙って通った」ことなので実運用では
   観測されず、条件が原理的に発火しない。0.3.1 の時点で複合リダイレクト・`sh -c` 前置など
   レビューでの再現例が出ており、次に同種が出たら乗り換えを検討する)
2. gh が旗の体系を大きく変え、旗表の追従が繰り返し発生する
3. 配布形の制約が変わり、シムのインストール手順を許容できるようになる

## シム方式の代償(乗り換え判断のときに読む)

- 配布が「フック 1 枚」から「PATH に置くファイル+導入手順」に重くなる
- Claude 経由でない人間自身の gh 投稿にもゲートが掛かる(400 文字未満は素通しなので実害は小さいが、挙動の変化として明記が要る)
- gh __complete は公開契約でない内部実装の流用で、gh 側の変更で壊れうる

## 乗り換え先の案 2: Write 入口に prompt 型フックを置く(2026-08-28 実測)

判定したいことは「書かれたものが、文脈を持たない読み手に通じるか」で、gh の投稿はその出口の
1 つにすぎない。Claude Code 本体のフックには LLM 判定型が 2 つあり(prompt 型 / agent 型、
https://code.claude.com/docs/en/hooks#prompt-based-hooks )、Write ツールを入口にすると
本ゲートが自作している層——シェル解析・coldreader の起動・認証・入れ子防止——が全部不要になる。
claude 2.1.250(macOS、headless の claude -p に --settings でフックを渡す構成)で実測した事実:

- PreToolUse + matcher Write の prompt 型フックは headless でも発火し、deny 理由(詰まり箇所の
  引用付き日本語)が書き手のモデルへツールエラーとして返る——再修正ループが成立する
- prompt 型の判定モデルは会話履歴を見ない(会話中に宣言した合言葉を「知っていれば言え」と
  フックに指示しても再現できなかった)。道具も無いので、初見性が構造で守られる
- agent 型は coldreader には不適格: Read 等の道具を持ち、フック入力の transcript_path から
  会話全文を読める(同じ実験で合言葉を言い当てた)。初見性が指示への従順さ頼みになる
- tool_input.content は 9.7KB の末尾 30 字まで一字違わず判定モデルへ届いた(打ち切りなし。
  それ以上の長さは未測)
- 罠: model にエイリアス(sonnet 等)を書くと unrecognized_model の警告が stderr に出るだけで
  フックごとスキップ=素通しになる(fail-open)。フル ID(claude-sonnet-5)は効き、使用量も
  modelUsage に別枠で載る
- 全フック共通の if 欄で "Write(docs/**)" のようなパス絞りが宣言でできる——検査対象の
  選別(段 1 のふるい)も自作不要

### 採るときの条件

- model は書かないのを既定にする。書かなければ既定の高速モデルに本体が追従し、モデルの引退で
  壊れない(既定モデルでも詰まり 5 箇所を引用付きで返し、検査の質は足りていた)
- model を書くならフル ID にし、フックが実際に発火することを確かめる canary(わざと詰まる
  Write を流して deny を確認する自己検査)を隣に置く。fail-open のため、設定の誤りは
  門番が黙って消える形で現れる
- 本 Bash 入口のゲートとは役割が別で併存する——投稿本文はヒアドキュメントで gh へ直接渡り、
  ファイルを経由しないため、Write 入口では捕まらない
