# 0027. 実行の核は今の engine を続ける（LangGraph に載せ替えない）

- 状態: 採用
- 日付: 2026-09-25
- 決めた人: 人（13:50・15:50 に試作の結果を報告、19:00 に H1 を今の engine の上で作ることを承認）
- 実装: 変更なし（今の engine を続ける）

## 文脈

- [0026](0026-langgraph-as-core.md) を保留にした後、LangGraph と 3 回比べた（どれも試作。langgraph 1.2.12）。
- 試作 1（修正と検算のブロック）: 差し引き約 +180 行（推測、幅 −150〜+500）。engine の変更行のうち LangGraph が引き受ける所は 22〜29%。変更の多い所（役の起こし方・受け付け・穴埋め）はどちらの仕組みでも残る。
- 試作 2（慣れた書き方で見直し）: 約 −60 行で境界。回す側の LLM を無くす形なら約 −386 行だが、そのうち約 −100 行は今の engine でも得られる。
- 試作 3（H1 を両方の上に作り、同じ 8 種の試験）: 改名を除く 7 種で結果は同じ。汎用の行は今の engine 57 行、LangGraph 218 行。LangGraph の側は正本が 2 つになり突き合わせる柵が要った。所要時間は 1.8〜4.5 倍、保存は 1 run で 2.5〜4.1MB（盤面は 190〜380KB）。
- 事故の棚卸しでも、LangGraph で防げる重さは最少（19/133）で、その大半は既に直っていた。

## 決定

- 実行の核は今の engine を続ける。
- LangGraph は、手順 H3（writer を役にする）の後に実行の仕組みの事故（並行の線・再開・人待ち）が残り、共有の層の直しでも消えないときだけ見直す。
- 新しい実行の仕組みを別のディレクトリ（`graphloops/next/`）や別のプラグインに置く計画は、載せ替え前提だったので捨てた。分けた graph を並べて置き run の開始時に選ぶ形だけを残す。

## 比べた案

- LangGraph（上の 3 回の試作）。載せ替えで新たに困る所（試作で踏んだ）: 止まっている節の名前を変えて再開すると例外を出さずに残りを撃たずに終わる（走っている run の graph の書き換えは棚卸しの 2 週間で計 17 回あった）／盤面で節を待ちに戻しても LangGraph は知らない／保存が人に直接読めない／依存 41 パッケージ。
- DBOS Transact（依存が最も重い。グラフでなくコードで書く）・LlamaIndex Workflows（入れ子が弱い）・サーバーが要る物（Temporal・Hatchet・Restate）・周回を組めない物（Dagster）・節が LLM 前提の物（OpenAI Agents SDK）・再試行が無い物（Burr・Microsoft Agent Framework）・依存が重い物（CrewAI・Google ADK）。

## 理由

保守性（[0025](0025-maintainability-as-axis.md)）で比べて、載せ替えの得が境界か負で、防げる事故も最少だった。

## 結果

- 載せ替えの道は残っている: rules と engine の部品は書き直さずに LangGraph へ載った（翻訳は 23 行）。載せ替えるときの必須の柵: 再開の前に止まっている節の名前が今の graph に在るかを見る・人待ちは独立した節にする・受け付け済みの置き場を見て役を二重に起こさない・部品に入口と出口の型を切る・記録は状態の外に置く。
- 外側の土台（回す層）をどうするかは別の論点として続いた（[0029](0029-orchestration-layer-is-replaceable.md)・[0032](0032-archon-migration-decided-by-trial.md)）。
- 関係: [先行例の見立て](../graphloops-prior-art.md)の再評価の引き金 (b)（engine の行数か変更頻度が rules を超えたとき）は、2026-09-12 の時点で行数の条件が成立しており、再評価するか引き金を定義し直すかは同じ文書の「残る決定事項」にある。

## 見直す条件
