## 文脈

- graph 5,679 行・review の rules 2,504 行・engine 3,035 行で、節の間の参照 128 本の約半分が段をまたぎ、部品を差し替える場所が無かった（計画版の 1 章）。
- 修正ブロックを差し替えられる口にしたい。組み方は 3 通り（置き換え・直列・並行）で、ブロックの約束は 3 つとも満たす形で決める（人、2026-09-26）。
- 修正役の指示書（p3.fix）は 6.4〜11.1 万バイトで、同じ単位の表が 2 つの穴から 2 回貼られていた。

## 決定

- 既定の流れも部品にする。差し替え先がある所だけでなく、独立して意味のある区切りは 1 つずつブロックにし、ループはブロックの組み合わせで定義する（人、2026-09-25）。
- 区切りの規則は「1 つの位置に 1 ブロック」。review は 13・research は 8・共有 3。2 か所に出てくる物は同じブロックを 2 回使う。
- 約束の置き場は engine に依らない `graphloops/blocks/<ブロック>/`（`block.json` と入口・出口の JSON Schema）。schema は JSON Schema の標準の語だけで書き、engine の独自の語は run の状態の合わせ方（x-reducer）の 1 つだけ。
- 出口は必ず object で、真偽の `ok` を持ち、欄を包まず並べる。周の番号は出口に持たせない。入口は `{ctx, needs}`。
- run の状態を書くのは engine の口だけで、規則の関数は書き込みの依頼（effects）を返す。条件・受け付け・収束は純粋な関数、機械の節だけ外の世界（git など）を受ける。拒否は例外でなく `ok: false`。
- 修正の出来事は種類（did）を名乗り、種類ごとの必須の欄は受け付けの関数が確かめる。単位ごとのファイルの割り当ての機械化は H3 の後。
- テストだけの変更かどうかの判定は、対象リポジトリの宣言の glob で行い、宣言が無ければ安全な側（振る舞いの変更と同じく扱う）。
- 共有ブロックの名前の違いは writes で吸収し、記録の欄の名前は変えない。
- 検算の線（周をまたいで背景で走る変異の検算）は、薄い層が背景で起こし、次の周の頭の節で拾う（今の engine と同じ形。gates=merge 固定にして線を捨てるのは能力の後退なので採らない）。
- 3-1（state_schema の宣言）で、research の読める鍵の絞りを残すため、読める鍵の一覧を新しく置く。

## 比べた案

- 以前の棚卸しの 10 ブロックの区切り: 仕様の道が無く、前提・判定・再審・周の締めの位置が今の流れと合わなかった（BLOCKS の 3.1 に変えた所と理由 7 点）。
- 検算の線を Archon では gates=merge だけにする: 線の位置を失うので能力の後退。

## 理由

- 1 つの位置に 1 ブロックにすると、Archon の include 1 つ・今の engine の差し込み口 1 つ・外の流れとの受け渡し 1 回に、そのまま当たる。
- 約束の正本を graph の JSON の中に置くと、graph を退けたときに約束ごと消える。ブロックは自分の資産として持ち続ける（[0029](0029-orchestration-layer-is-replaceable.md)）。
- 出口に `ok` を必ず持たせると、Archon の成否の欄がそのまま効き、条件が出口の欄を直に読める。
