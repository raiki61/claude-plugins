## 用語

- **graphloops**: このリポジトリの Claude Code プラグイン。レビューなどの「結果が動かなくなるまで回す手順」を JSON のグラフに書き、Python のプログラム（engine）が進行を管理する。
- **engine**: `graphloops/engine/` の Python。どの工程を次に走らせるかを決め、指示書を組み、返答を受け付ける。
- **節**: グラフの 1 工程（例: 判定役が判定する `p2.diagnose`）。
- **段**: 節のまとまり。P0（前提をそろえる）→ P1（素材集め。差分を別々の観点で読む役の節が 9 つ）→ P2（判定と修正案）→ P3（修正と、修正差分の審査・検算）→ P4（記録）→ R1〜R4（最後の独立の目）。
- **役**: 節の仕事をする AI（判定役・調べ役など）。
- **回す側**: engine に次の節を聞き、役を起こす Claude のセッション。
- **運び手**: 回す側と役の間に挟む小さな AI。役を起こし、返答をファイルに写す。
- **周**: P0〜R4 の 1 巡。指摘が無くなるまで繰り返す。
- **変異テスト**: コードをわざと壊して、テストが気づく（赤になる）かを確かめる検算。

## 1. なぜ作り直すか（実測した困りごと）

2026-09-24〜25 に回したレビューの run（5 周）と、その横で回した「判定から入る入口を作る run」で起きたこと。

1. **止まっても誰も気づかない。** 回す側は役の完了の通知だけを待つ。通知が届かないと止まり続ける（別セッションで 7 時間）。5 周目に利用上限で P1 の役が全部落ち、回す側が起こし直したが、engine には起こし直した記録が残らなかった。
2. **AI が中継と写しで間違える。** 運び手が、ファイルに写していないのに「写した」と返した。続きの返答が回す側に戻り、回す側が手で写した。役に長い文字列（判定の単位の名前など）を一字一句写させる受け付けで、5 周目に 2 回差し戻された。
3. **1 周が長い。** 4 周目は約 8 時間。うち変異テスト（修正差分への注入 173 分・見逃しへの手直し 167 分・差分全体の検算 56 分）で約 6.5 時間。トークンでは P1 が 1 周の約 8 割、うち局所レビューの節 1 つが約 6 割。
4. **部品を差し替えられない。** 判定から入る入口を作るのに、P1 の 9 節それぞれに「依頼があれば外す」条件を書き足した。事前審査が「外す節の一覧が 2 か所に写されている」と指摘した。軽い検算や TDD 版の修正を載せる場所が無い。
5. **大きな 1 ファイル。** グラフ 5,679 行、review の rules 2,504 行、engine 3,035 行。49 節の参照 128 本のうち約半分が段をまたぐ。
6. **直すと隣が古くなる。** 前の周の修正が作った指摘が、8 → 7 → 6 件と毎周出る（注記・文書・写しのずれが多い）。

## 2. 前回の検討（2026-09-12）の結論と、崩れた前提

前回の検討（`docs/graphloops-prior-art.md`）の結論は「既製の実行基盤に載せ替えることは、LangGraph のようなライブラリなら組めるが、差し引きの行数がほぼゼロで割に合わない。今は自前の engine を続ける」だった。その文書は、次のどれかが起きたら考え直すと決めていた: engine の行数が rules の行数を超える／engine に再試行・入れ子のグラフ・別プロセスでの再開が要るようになる。

崩れた前提:

- 「役を起こせるのはメインの会話だけなので、外の基盤からは起こせない」→ 役を `claude -p`（画面なしで Claude Code を 1 回動かすコマンド）で起こせば崩れる。道具を持たない役は、既に engine が `loop.py launch` でこの形で起こしている。CLI には `--agent`・`--resume`・`--allowedTools`・`--output-format` の旗がある（挙動は未検証）。5 周目は修正の節も別の AI に任せて回った。
- 「基盤に任せられるのは engine 1,091 行のうち約 400 行」→ engine は 3,035 行に増え、基盤が元から持つ機能（期限・再試行・入れ子のグラフ・別プロセスでの再開）が実際に必要になった。考え直す条件はどちらも満たしている。
- 「pip の依存を足さない」→ uv（スクリプトの先頭に依存を書く PEP 723 の形）か、Python 標準の venv で使い捨ての環境を作れば、利用者の導入手順は増えない（代償は 6 章）。

崩れていない前提: 記録（run ごとの record.json）と検証器（記録の合否を決める `scripts/review-record.py` など）が状態の正本であること。基盤に状態を二重に持たせない。

## 3. 目標の作り（層）

1. **記録と検証器（変えない）。** 新旧どちらの実行でも同じ形の記録を書き、同じ検証器で合否を決める。
2. **役を起こす関数（1 つ）。** 節 1 つ分を完結させる: 指示書を組む → `claude -p` を起こす（役に許す道具の一覧と期限をつける）→ 返答を置き場のファイルに書く → 受け付けの検査（今の `loop.py done` の中身）→ 拒まれたら同じ会話に続きを頼む（`--resume`）。実行の要約（時間・往復数・トークン・費用・会話の番号・試行回数）を run のディレクトリに JSON Lines で残す。今の engine からも、将来の OSS の節からも、この関数を呼ぶ。
3. **ブロック（部品）。** 素材集め（通常／人の依頼から）・判定・修正（通常／TDD 版）・検算（重い／軽い）・締め（P4・R1〜R4）。ブロック同士は入口と出口の型だけでつなぐ:
   - run の入力（凍結した目的など）
   - 前の周の修正差分（engine が機械で切り出した patch。修正役の自己申告の旗は使わない）
   - 素材集め → 判定: findings の型（where・text・mechanism・measured・false_positive_if の 5 欄）
   - 修正 → 記録: 修正の結果
   「別ブロックの中の節を名指しして待つ」依存は、ブロックの順番に置き換える。
4. **実行の核。** 当面は今の engine。将来は OSS（候補は調査中）。核が受け持つのは順番・並列・周回・期限・再試行・中断と再開・部品の差し替えだけで、レビューの中身は持たない。
5. **観測。** 当面は 2 の要約の JSON Lines。核を載せ替えたら OpenTelemetry（節ごとのスパンと、`claude -p` 側の計測。run の番号・節・試行回数を属性で渡してつなぐ）。

## 4. 移行の原則（移行中も今の仕組みで回す）

- 一度に入れ替えない。1 段ずつ進め、各段でテスト一式（`graphloops/tests/run.sh`・`tests/run.sh`）が緑のまま。
- 記録の形と検証器は新旧で共通にする。同じ依頼を新旧で回して記録を比べられるようにする。
- 今の engine に入れる直しは、今起きている止まり方への手当てに限る。核を載せ替えれば捨てる前提で、作り込まない。
- 各段は、そこで止めても役に立つ形で終える。

### 置き場（2026-09-25 に決めた）

抽象の層を 1 枚挟み、新旧の実装を切り替えながら置き換える（branch by abstraction）。

- 段 1〜4 は今の `graphloops/` の中で直す。
- 段 5（ブロック化）と段 7（核の載せ替え）は新しいディレクトリ（例: `graphloops/next/`）に置く。置くのは新しい実行の仕組み（ブロック化したグラフの定義・OSS の核への呼び口・観測）だけ。
- 新旧で 1 か所のまま共有し、写さないもの: rules（`graphloops/rules/`）・指示書（`graphloops/prompts/`）・記録の検証器・役を起こす関数（段 1）。レビューの中身を 2 か所に持つと、同じ直しを 2 回入れる必要が出て、片方を忘れた所が食い違う。
- run の開始時に新旧を選ぶ（例: `loop.py init --runtime next`）。既定は旧のまま。
- 旧を消す条件: 同じ依頼を新旧で回して、同じ形の記録が出て、検証器の判定が一致したら、既定を新に替え、しばらくして旧の engine を消す。
- 長く別のブランチで育てず、main に少しずつ入れて切り替えの旗で隠す。
- 例外: 新しい実行の仕組みが別の言語（TypeScript）や大きな依存を持ち込むなら、利用者が新旧を別々に入れられるよう別のプラグイン（例: `graphloops-next`）に分ける。中身は同じリポジトリの中で参照させる。段 0 で言語と核が決まってから判断する。

   試作で確かめたこと（langgraph 1.2.12・langgraph-checkpoint-sqlite 3.1.1 を `uv run` のスクリプト内の依存宣言で即席に入れた。入ったのは 41 パッケージ、2 回目以降は 0.1 秒）: 周回（2 周）・並列（2 節）・部品（サブグラフ）の中の人待ちで止めてプロセスを終え、別プロセスで答えを渡して再開・部品の中の節でプロセスを落とし（`os._exit`）、別プロセスで続きから再開・非同期の節の期限切れ（`NodeTimeoutError`）。どれも期待どおりに動いた。人待ちの節は再開のとき先頭から走り直す（文書どおり）が、その前の節は走り直さなかった。落ちた節は再開のとき 1 回だけ走り直した。

### 順番の改訂（2026-09-25、人が承認。同日、核の載せ替えだけを保留にした）

保留にしたのは実行の核の載せ替え（LangGraph）だけ。ブロック分割・コマンドだけの節の組み込み・開発手法の差し替えは、核に依らず今の engine の上で進める。

### 手順 0: 片付け
- 走っているレビューの run（5 周目）と、判定から入る入口を作る run を締める。
- 入口を作る run の成果を本体に取り込み、5 周目の変更との重なりを解く。
- この文書を `docs/graphloops-rearchitecture.md` に置く（コミットと push は人の指示で）。

### 手順 1: 役を起こす関数（新旧で共有）
- 指示書を組む → `claude -p --agent <役>`（権限の設定を役ごとに明示）→ 返答を置き場に書く → 受け付けの検査 → 拒まれたら `--resume <会話の番号>` で同じ会話に続きを頼む → 実行の要約（時間・往復数・トークン・費用・会話の番号・試行回数）を JSON Lines で残す。
- まず今の engine から使い、運び手を無くす（止まっても気づかない・中継の間違いがここで直る）。後で LangGraph の節からも同じ関数を呼ぶ。
- 判定役などに CLAUDE.md を読ませるか（`--setting-sources`）をここで決める。

### 期限を外した
- 2026-09-25、人の依頼で、節の期限（graph の `deadline_minutes` と、期限の無い節に付いていた 30 分の既定）と、それを過ぎたら役の子を止める動作・`loop.py wait`・期限を条件にした `loop.py relaunch` の資格を外した（run 20260925-115422）。
- なぜ: 期限は「止まっても気づかない」への手当てとして入れた。その元（完了の知らせの迷子）は、engine が子の終了を直接待つ形（役を起こす関数）で解消した。残った期限は実測でない目安の値で、役の子を止める上限を兼ね、判定役・調べ役を打ち切りうる形になっていた。
- 残したもの: 経過時間の表示（`next`・`status` の `elapsed_min`）、起こし直しの回数と理由（`attempt_log`）。起こし直す（`relaunch`）ときは、新しい試行を盤面に書いてから、engine が起こした前の試行の子を木ごと止める（子のグループの番号を置き場の隣の `<out_path>.pgid` に置き、`relaunch` がそれを読んで止める。番号の再利用は印の時刻とプロセスの開始時刻で見分ける。先に止めると、止められた古い launch の締めと版が競って relaunch が落ちた）。任せ先（delegate）は回す側が Agent ツールの前景で起こし、その返りを終了とする。
- 後で検討する: 子が応答しないまま動き続ける場合への備えは、経過時間でなく「進んでいるか」（例: 役の会話の往復や出力が増えているか）で見る形にする。期限を付け直すなら、役を起こす関数が `trace.jsonl` に残す所要時間の実測から節ごとに決める。

### 手順 2: 写させない（新旧で共有）
- 判定の単位などに engine が番号を振り、役は番号で指す。記録と報告では名前に戻す。
- 済み（2026-09-25、今の engine の上で）: 節の `pointers` 宣言（graphloops/engine/pointers.py）。engine が貼る一覧に no を振り、役は番号で指し、done が名前に戻してから rules と記録に渡す。当てたのは他の節の一覧を指す欄（単位・事前審査の穴・修正の応答・答える義務・前の周の削除候補と宣言した穴）。判定者が同じ返答の中で自分の units を指す欄と、外部標準の順位（diff_at）は字面のまま残した——自分の配列の位置の数え違いは黙って別の値に当たり、拒まれないため。

### 手順 3: ブロック分割（今の engine の上で）
- engine にグラフの部品を取り込む仕組みを足す（部品の中の節の名前の衝突を避ける・部品同士の順番を書ける・部品の差し替えを宣言できる）。ループに依らない汎用の仕組みなので engine に置く。
- ブロックは素材集め・判定・修正・検算・締め。各ブロックは入口と出口の型だけでつなぐ（LangGraph の試作でも、型を持たせないと部品と親で値が重複した）。
- 段をまたぐ参照を整理する: 順番だけの依存 → ブロックの順番／凍結した目的 → run の入力／P1 のどの観点を走らせるかの判定 → 素材集めの中へ／修正役の自己申告の旗 → 修正差分からの機械の判定。
- 検証器をブロックごとの検査に割る。
- 最初に分けるのは、差し替えの需要が見えている所（素材集め：通常と人の依頼から、検算：重いと軽い）。
- 既定の流れも部品にする（2026-09-25、人）: 差し替え先がある所だけでなく、既定の流れの中でも独立して意味のある区切りは 1 つずつブロックにし、ループはブロックの組み合わせで定義する。候補（棚卸しで確かめる）: 前提をそろえる（P0）／素材集め（P1。レンズごとの小ブロック）／判定（診断と履歴の突合）／修正案と事前審査／修正（既定・TDD）／修正差分の審査と手直し／変異の検算の線と最後の関門／周の締め（P4）／独立の目（R1〜R4）／報告と初見検査。research-loop と共有できるブロック（独立の目・初見検査・判定の型など）は共有する。
- 棚卸しの結果（2026-09-25、読むだけの調査。合成の版 768f56c で）: review-loop の 52 節は 10 ブロック（前提／素材集め＋レンズ 9 本／判定／修正案と事前審査／修正／修正差分の審査と手直し×2 回／検算の線と最後の関門／周の締め／独立の目／報告と初見検査）、research-loop の 22 節は 8 ブロック（前提／素材の棚卸し／判定／内部の突合／統合／独立の目のゲート／締め／適応・報告・還流）に分かれる。修正差分の審査と手直しは、rules の DeltaPass の表が既に「同じブロックを 2 回使う」形を持っている。
- 一番の難所: 記録（record）の外に、型の無い共有の辞書（loop_state。30 鍵を超える: prev_fix_files・escalated・gates_cut・lanes・r1_refire・purpose_unusable など）があり、ほぼ全ブロックがここを直接読み書きしている。入口と出口の型に収まらず、LangGraph の試作で踏んだ「部品と親が同じ鍵を共有すると値が重複する」と同じ穴が本体側にある。ブロック分割の最初の一歩は、この辞書の鍵を「ブロックの出口の欄」と「run 全体の実行の状態（engine が持つ）」に振り分けて型を付けること。
- 片付けの 2 本目（2026-09-26、3-2 の run）: run の入力（inputs）は init で固まり途中で書き換えない（周に固めた版の正本は loop.reviewed_revision、方針の文書の置き場は record.process.policy.path）。条件の文脈に inputs の頭を足し、flow・gates の loop への写しを消した。1 ブロックの中で閉じる値（tree_before・diff_stat・delta_owed(2)・gates_cut・r2_refire・ledger_changed・lines_ratio・facts_to_add・spec_pending・spec_changed）は書く節の出力へ移し、読む側は今の周の出力 cur.<節>.<欄>（プロンプト・delegate.result_to・pointers も読める）で読む。記録へ写すだけの鍵（validator_outputs・purpose_review_stale・cold_check・research の load_zero_reason）は記録へ直接書くか節の出力から組み、誰も読まない retaken_for_reviews は p4.assemble の出力の retaken に置いた。機械の節の返りに schema を付け、engine が照らす（外れは止める）。読んでよい loop の鍵の絞りは state_schema の writeOnly に寄せた。節の出力の手当ては loop.py patch --path out.<節>.<欄>。
- ほかに型に収まらない参照: 順番だけの依存（ブロックの順番に）／全節の素材の宣言を舐める fill_materials（ブロックごとの検査に割る）／段をまたいで効く再発火の旗 escalated（run 全体の旗を各ブロックの入口の条件として渡す）／前の周の個々の役の出力を直接読む所（束ねた record.reviews だけを読ませる）／段をまたぐ条件の関数（ブロックの中だけで定義し、またぐ値は前のブロックの出口として渡す）／節の定義を直接引く所（共有の型 $defs に統一）。
- 共有できるブロック: 過去の決定の突き合わせ（両ループの p0.prior_decisions がほぼ同じ型）／独立の目の二段構え（隔離して導出 → 突き合わせ。review の r2.design→r2.compare と research の p3.rederiver→p3.rederiver_compare・p3.cartographer→compare）／初見の読み手（review の p1.hygiene・report.cold_check と research の p3.cold_reader）。
- 差し替えの需要: 検算（出口の型 lane_reply が既に固定。いちばん差し替えやすい）／素材集め（今は 9 節に条件が散っている。ブロック単位の切り替えに畳む）／修正（既定と TDD。TDD 版は出口に赤→緑のテストの証拠の欄が要る見込み）。
- 組み合わせの約束: ブロックは入口と出口の型だけでつなぎ、同じ型の出口と入口なら差し替えられる。組み合わせの正本は宣言（どのブロックをどの順に・どの版で）にし、graphcheck が型の合致を実行前に確かめる。
- 合流の線引きを出口の型で表す: 修正ブロックの出口は「振る舞いの変更」（次の工程が待つ）、検算ブロックの出口は「テストの追加」（並行の線で後から合流）と型を分け、テストだけの変更かどうかを機械が扱えるようにする。それまでは手順書の文と運用で守る。
- 分けたグラフは今のグラフと並べて置き、run の開始時に選ぶ。記録と検証器の判定が一致したら既定を替えて、旧いグラフを消す。

- **状態の型は世の中の定まった解に寄せる（2026-09-25、人「世界の解があるのでは」。scratchpad/stateworld/SURVEY.md、出典 28 件）**: 共通の形は「工程の出力を名前で読む・全体の状態は小さく決まった口でだけ書く・履歴から作れる値は保存せず読む時に作る」で、loopstate の設計案（scratchpad/loopstate/DESIGN.md）と同じ向き。借りる物: 状態の型の名前 state_schema と鍵ごとの合わせ方（reducer。既定は上書き、append 等。人の手当ては Overwrite）は LangGraph／節が全体の状態を書く口の段の順（出力を照らす→足す→照らす）は Serverless Workflow 1.0 の export、値の見え方の規則は Step Functions の変数（Assign）／出力は依存に書いた工程の物しか読めない約束は GitHub Actions・Argo の needs／履歴から作る見方 hist. はイベントソーシングの projection と Temporal の Query の意味、旧い盤面は upcaster で読む。借りない物: Step Functions の ResultPath（今の loop_state の書き方そのもの。AWS も JSONata で置き換えた）・式の言語。直し: x-merge → x-reducer、run 全体の 10 鍵を書ける状態と読むだけの ctx. に分ける、inputs.review_rev を途中で書き換えない、graphcheck に「並列の節が同じ鍵を書くなら上書き以外の reducer を必須」「cur.X は祖先だけ」。合わない所: 回す側が LLM（loop.py patch が盤面を直接書く）・盤面を人と AI が直接読む（hist. の控えを印つきで書き出す）・走っている run の graph の書き換え（upcaster）・周の輪（Temporal の Continue-As-New が近い: 周の境目を『次の周の入力を組む関数』にする）。

- **p4.assemble を独立の目のブロックの入口へ移す（2026-09-25、人が承認）**: 修正後のチェックは 1 つも減らさない（撮り直しは R の直前に必ず走る）。変わるのは順番だけ（CI・数値と R が並んで走れる）。気をつける所: p4.scalars が修正前・修正後のどちらの一覧を読むかを明示で選ばせ、物差しが変わることを記録に書く／出力は R・p4.record のほか report.human_items も読む（R を撃たない周も入口は必ず走る）／名前を参照する所（spec.check の deps・graphcheck・文書と図・テスト）を一緒に直す。
- **履歴から作る見方 hist. を足す（2026-09-25、人が承認）**: イベントソーシングの projection と Temporal の Query の意味で定義する（読み取り専用・いつでも作り直せる・履歴に何も足さない）。盤面から写しの 20 鍵が消える。盤面を直接読む人と AI のために、engine が『正本でない・作り直せる』印を付けた控えを盤面の隣に書き出す。last_seen・last_material は定義を『閉じた周の記録＋今の周の素材集めの出口』にして突き合わせ直してから移す。
### 手順 3b: コマンドを打つだけの節を engine の組み込みにする
- 節の単位でなく、節の中の「走らせる・数える」を engine に、「読む・決める」を役に分ける（当初は変異テストの 2 節と、CI と数値を写す 2 節を、節ごと LLM から外すと書いていた——判定で範囲を直した）。
- **実施（2026-09-25、判定から入る run・1 周目）**。任せ先（haiku）が走り切る前の件数で clean と書く・CI の一部の系統を飛ばす・規模の数値を写し違える、が 1 周目で止めた run の全部で出た件を受けて:
  - engine に走らせるだけの節の口を足した: graph の回す側の節に `engine_run: {builtin, why}` を書くと、rules の `ENGINE_RUNS[builtin].plan` が走らせる語を返したときだけ instance が `mode=engine_run` で出て、`loop.py launch` が役と同じ起こし方（`role_run._spawn`——別のプロセスグループ・期限なし・relaunch が木ごと止める）で走らせ、`reply` が終了コードから返答を組んで `accept_output` に通す。`done` は拒む。組んだ返答が拒まれた・役の判断が要る結果（並行 PR の交差）なら、同じ節を任せ先の節として出し直す（出口を作る）。
  - 載せた節: `p0.local_checks`・`p4.ci`（宣言の語）、`p0.parallel_pr` の 1〜5 段（同梱の `scripts/parallel-pr.py`。交差が在る周と GitHub でない remote は任せ先——6 段の申し送りと読み替えは判断）、`p4.scalars`（機械の節。`p3.gates_cut` の版で comment-ratio.sh と `git diff --numstat -- '*.md'`。x_ の数値は p3.fix の `x_scalars`）。haiku の任せ先は 0 になった（宣言の無いリポジトリで出る任せ先は sonnet）。
  - 一式の緑の自己申告を消した: 線（`p3.delta_gates`）と最後の関門（`p4.final_gates`）の返答の `suite` は読まない。最後の関門の版の一式は同じ周の `p4.ci`、線の足したテストは合流した周の `p4.ci` が正本。収束は、この周の CI を engine が走らせて緑だったときだけ（宣言の無いリポジトリの clean は任せ先の自己申告として `process.checks` に残り、`converge` が人に諮る）。
  - **権限**: 宣言の語は Claude Code の許可の仕組みを通らないので、direnv の allow の形にした——人が `loop.py allow-checks` で宣言の中身の sha256 を承認する（置き場は git の共通ディレクトリ。worktree で共有）。承認が及ぶのは宣言の中身だけで、語が呼ぶスクリプトの中身は含まない（前の経路の分類器も語しか見ていなかった）。回す側が承認を打たないことは手順書が縛る（機械では縛れない）。
  - **承認を外した（2026-09-25、人の決定『テストはなんで承認制にしてるのめんどくさい』、判定から入る run）**: 無人の run 4 本が承認の無いまま関門で人を待って止まった。人は普段の使い方（自分のリポジトリを回す）で承認の手間を要らなくすると決めた。判定役は、承認が止めていたのは宣言の argv の書き換えという 1 経路だけで、スクリプトの本文の書き換えで素通りする（手間に見合わない）と判定した。世界の解は GitHub Actions（自分のリポジトリの push のワークフロー定義は承認なしで走り、承認を求めるのは外部の貢献者の fork の PR だけ）と VS Code の Workspace Trust（中身ごとに聞き直さない）。承認の代わりに、走らせる直前に対象リポジトリのルート（盤面の欄でなく run の inputs.cwd から引く）の宣言を読み直して instance の語と一致を確かめる——盤面の手当てで語を足しても走らない柵は残す。**守られなくなった物**: 初見のリポジトリ・レビューしている差分・修正役が書き換えた宣言の語を、人が見る前に engine が Claude Code の許可の仕組みの外で走らせる。**残る物**: shell を通さない argv と書式の検査・同梱の語の免除は argv の頭で決める柵・盤面の書き換えでは宣言に無い語が走らない柵・宣言の無いリポジトリは任せ先の節。**もともと守っていなかった物**: 語が呼ぶスクリプトの本文。OS の境界（sandbox）で包む案は、役の sandbox では `uv run --with` が止まる実測（`engine/role_run.py` の注記）で今の宣言が走らなくなるので採らなかった。正本の注記は `graphloops/engine/declared.py` の冒頭。
  - **待ち**: next の中で同期に走らせない。launch の口で別プロセスとして走らせ、子の終了を直接待つ（期限なし）。
  - **宣言の書式**: ルートの `.review-checks.json`（`{"suite": [{"name", "argv"}]}`、shell を通さない argv）。読み手の正本は `engine/declared.py`。CI の定義を engine が読む形（YAML と GitHub の式の評価）は採らなかった。
  - **残した物（次の手）**: 変異の実行器を engine が撃つ部分（`p1.gate_efficacy`・`p3.delta_gates`・`p4.final_gates` の腕を撃って赤・対照の緑・当たりの証拠を組む段）は、腕の自己申告（`_unproven` が読む欄）のまま。この run では人の指示で変異テストを起こせず確かめられないので、同じ口（engine_run と宣言の `mutation` の段）に載せるのは次の run にした。宣言の `mutation` の段そのもの（書式と振る舞いの正本は `graphloops/engine/declared.py`）は、変異の宣言の run（gates）で足した——engine が撃つ段はまだ次の手。

### 手順 3a: 条件（cond）を Python の関数にする（2026-09-25、人が承認）
- 原則: JSON には「何を約束するか」（指示書・読み込み・返答の型・書き込み先）を置き、「どう判断するか」（条件・算術）は Python の関数に置く。
- 条件は rules の名前付きの関数にし、graph には名前だけを書く。関数は（真偽, 理由の文）を返し、読む欄を宣言する。graphcheck は宣言を読んで「前の節の出力として実在するか」を実行前に確かめ、engine は宣言した欄だけが見える入れ物を渡して、宣言外を読んだらその場で落とす（今は検査の外の `loop.`・`record.` の葉も検査に入る）。
- 条件ごとの真偽表を書き（実施では台本 simulate_review.py・simulate.py の test_cond_truth_tables に置いた。下の実施の項）、変異は既製の道具に任せる（graph の JSON の条件を壊す手書きの腕 13 本が要らなくなる）。
- 移し替えは、review-graph の run 20260924-081523 の 5 周分の盤面で新旧の評価が全部一致することを確かめてから切り替える。
- 次の候補: 書き込みの宣言（writes）も同じ考え方で検討する。
- **実施（2026-09-25、判定から入る run）**。上の計画と違えた点と、確かめた範囲:
  - 条件は `rules/<loop>.py` の `CONDS`（数は rules の CONDS が正本）。読む欄は `cond_reads(...)` で宣言し、engine は `Board.cond(名前)` から `run_cond` を通して宣言した欄だけの入れ物（`CondView`）を渡す。graph の `cond` と `applies_cond` は名前だけになり、`when` は関数の返す理由に移った。loop の鍵の名前は `rules` の `LOOP_KEYS`、形は graph の最上位の `state_schema`（JSON Schema）が正本で、graphcheck が両者を両向きでそろえ、条件・節の `reads` と `outputs`・プロンプトの穴が読む `loop.<…>` を `state_schema` の木で最後の欄まで照らす。engine は盤面を保存する時に `state_schema` で照らし、外れを `state.loop_drift` に残す（止めない。記録の `process.loop_drift` と報告に出る）。旧い評価器（engine の eval_cond と op の表・graphcheck の check_cond と check_cond_paths・rules の _without_entry）は消した。入口で外れたかは、同じ関数を入口の印を外した重ね書きの文脈でもう一度評価して決める。
  - 真偽表は pytest でなく今の台本（`graphloops/tests/simulate_review.py`・`simulate.py` の `test_cond_truth_tables`）に置いた——この版に pytest の土台が無いため。
  - 手書きの腕は消さずに付け替えた（EN1・EN2・EN4・EN6〜EN9・EN14・EJ4〜EJ9・LP2。graph の JSON の木を壊していた 7 本は rules の各条件の行を壊す形に）。既製の道具に任せるのは変異テストの道具の移行（下の「作り直しと独立に進められるもの」）と一緒に。
  - 新旧の突き合わせは、本体の `.git/graphloops/review-loop/` の 9 run（36 周）に旧（3643420 の engine と graph）と新を当てた。周ごとの文脈は、rounds を r 周までに切り、出力を r 周までに done した instance から組み直した近似で、loop と record は最終の値しか残っていない——歴史の再現ではなく、同じ入力に新旧を当てた一致である。結果は 1,188 評価で真偽の不一致 0（旧が落ちた 1 件は新も同じ欄で落ちる）。loop と record の欄を同じ種で揺らした盤面（各周 40 通り、48,708 評価）でも真偽の不一致 0。research-loop の盤面は置き場に 1 本も無いので、research の条件（6 節・関数 5 個）は、真偽表と、種つきで揺らした文脈 5,000 通り（30,000 評価）に旧の eval_cond と新の関数を当てた突き合わせ（不一致 0）で確かめた。

### 手順 3c: 実行の核の決め直し（保留中）
- 判断の軸は保守性ひとつ（人、2026-09-25）。行数はその代理の 1 つにすぎない。保守性は次で測る: 自分で持つ汎用の仕組み（ループに依らない実行の機能）の量と、そこに入る直しの頻度・直しが作る穴／ブロックや手法を足す手間／初見の人と AI が読んで直せるか／依存の追従の手間（載せ替えれば、汎用の仕組みの直しが上流に移る代わりに、版上げへの追従が増える）。
- 判断の材料（手順 1・2・3a の後に集める）:
