## 用語

- **graphloops**: このリポジトリの Claude Code プラグイン。レビューなどの「結果が動かなくなるまで回す手順」を JSON のグラフに書き、Python のプログラム（engine）が進行を管理する。
- **engine**: `graphloops/engine/` の Python。どの工程を次に走らせるかを決め、指示書を組み、返答を受け付ける。
- **節**: グラフの 1 工程（例: 判定役が判定する `p2.diagnose`）。
- **段**: 節のまとまり。P0（前提をそろえる）→ P1（素材集め。差分を別々の観点で読む役の節が 9 つ）→ P2（判定と修正案）→ P3（修正と、修正差分の審査・検算）→ P4（記録）→ R1〜R4（最後の独立の目）。
- **役**: 節の仕事をする AI（判定役・調べ役など）。
- **回す側**: engine に次の節を聞き、役を起こす Claude のセッション。
- **運び手**: 回す側と役の間に挟む小さな AI。役を起こし、返答をファイルに写す。
- **周**: P0〜R4 の 1 巡。指摘が無くなるまで繰り返す。
- **変異テスト**: コードをわざと壊して、テストが気づく（赤になる）かを確かめる検算。

## 1. なぜ作り直すか（実測した困りごと）

2026-09-24〜25 に回したレビューの run（5 周）と、その横で回した「判定から入る入口を作る run」で起きたこと。

1. **止まっても誰も気づかない。** 回す側は役の完了の通知だけを待つ。通知が届かないと止まり続ける（別セッションで 7 時間）。5 周目に利用上限で P1 の役が全部落ち、回す側が起こし直したが、engine には起こし直した記録が残らなかった。
2. **AI が中継と写しで間違える。** 運び手が、ファイルに写していないのに「写した」と返した。続きの返答が回す側に戻り、回す側が手で写した。役に長い文字列（判定の単位の名前など）を一字一句写させる受け付けで、5 周目に 2 回差し戻された。
3. **1 周が長い。** 4 周目は約 8 時間。うち変異テスト（修正差分への注入 173 分・見逃しへの手直し 167 分・差分全体の検算 56 分）で約 6.5 時間。トークンでは P1 が 1 周の約 8 割、うち局所レビューの節 1 つが約 6 割。
4. **部品を差し替えられない。** 判定から入る入口を作るのに、P1 の 9 節それぞれに「依頼があれば外す」条件を書き足した。事前審査が「外す節の一覧が 2 か所に写されている」と指摘した。軽い検算や TDD 版の修正を載せる場所が無い。
5. **大きな 1 ファイル。** グラフ 5,679 行、review の rules 2,504 行、engine 3,035 行。49 節の参照 128 本のうち約半分が段をまたぐ。
6. **直すと隣が古くなる。** 前の周の修正が作った指摘が、8 → 7 → 6 件と毎周出る（注記・文書・写しのずれが多い）。

## 2. 前回の検討（2026-09-12）の結論と、崩れた前提

前回の検討（`docs/graphloops-prior-art.md`）の結論は「既製の実行基盤に載せ替えることは、LangGraph のようなライブラリなら組めるが、差し引きの行数がほぼゼロで割に合わない。今は自前の engine を続ける」だった。その文書は、次のどれかが起きたら考え直すと決めていた: engine の行数が rules の行数を超える／engine に再試行・入れ子のグラフ・別プロセスでの再開が要るようになる。

崩れた前提:

- 「役を起こせるのはメインの会話だけなので、外の基盤からは起こせない」→ 役を `claude -p`（画面なしで Claude Code を 1 回動かすコマンド）で起こせば崩れる。道具を持たない役は、既に engine が `loop.py launch` でこの形で起こしている。CLI には `--agent`・`--resume`・`--allowedTools`・`--output-format` の旗がある（挙動は未検証）。5 周目は修正の節も別の AI に任せて回った。
- 「基盤に任せられるのは engine 1,091 行のうち約 400 行」→ engine は 3,035 行に増え、基盤が元から持つ機能（期限・再試行・入れ子のグラフ・別プロセスでの再開）が実際に必要になった。考え直す条件はどちらも満たしている。
- 「pip の依存を足さない」→ uv（スクリプトの先頭に依存を書く PEP 723 の形）か、Python 標準の venv で使い捨ての環境を作れば、利用者の導入手順は増えない（代償は 6 章）。

崩れていない前提: 記録（run ごとの record.json）と検証器（記録の合否を決める `scripts/review-record.py` など）が状態の正本であること。基盤に状態を二重に持たせない。

## 3. 目標の作り（層）

1. **記録と検証器（変えない）。** 新旧どちらの実行でも同じ形の記録を書き、同じ検証器で合否を決める。
2. **役を起こす関数（1 つ）。** 節 1 つ分を完結させる: 指示書を組む → `claude -p` を起こす（役に許す道具の一覧と期限をつける）→ 返答を置き場のファイルに書く → 受け付けの検査（今の `loop.py done` の中身）→ 拒まれたら同じ会話に続きを頼む（`--resume`）。実行の要約（時間・往復数・トークン・費用・会話の番号・試行回数）を run のディレクトリに JSON Lines で残す。今の engine からも、将来の OSS の節からも、この関数を呼ぶ。
3. **ブロック（部品）。** 素材集め（通常／人の依頼から）・判定・修正（通常／TDD 版）・検算（重い／軽い）・締め（P4・R1〜R4）。ブロック同士は入口と出口の型だけでつなぐ:
   - run の入力（凍結した目的など）
   - 前の周の修正差分（engine が機械で切り出した patch。修正役の自己申告の旗は使わない）
   - 素材集め → 判定: findings の型（where・text・mechanism・measured・false_positive_if の 5 欄）
   - 修正 → 記録: 修正の結果
   「別ブロックの中の節を名指しして待つ」依存は、ブロックの順番に置き換える。
4. **実行の核。** 当面は今の engine。将来は OSS（候補は調査中）。核が受け持つのは順番・並列・周回・期限・再試行・中断と再開・部品の差し替えだけで、レビューの中身は持たない。
5. **観測。** 当面は 2 の要約の JSON Lines。核を載せ替えたら OpenTelemetry（節ごとのスパンと、`claude -p` 側の計測。run の番号・節・試行回数を属性で渡してつなぐ）。

## 4. 移行の原則（移行中も今の仕組みで回す）

- 一度に入れ替えない。1 段ずつ進め、各段でテスト一式（`graphloops/tests/run.sh`・`tests/run.sh`）が緑のまま。
- 記録の形と検証器は新旧で共通にする。同じ依頼を新旧で回して記録を比べられるようにする。
- 今の engine に入れる直しは、今起きている止まり方への手当てに限る。核を載せ替えれば捨てる前提で、作り込まない。
- 各段は、そこで止めても役に立つ形で終える。

### 置き場（2026-09-25 に決めた）

抽象の層を 1 枚挟み、新旧の実装を切り替えながら置き換える（branch by abstraction）。

- 段 1〜4 は今の `graphloops/` の中で直す。
- 段 5（ブロック化）と段 7（核の載せ替え）は新しいディレクトリ（例: `graphloops/next/`）に置く。置くのは新しい実行の仕組み（ブロック化したグラフの定義・OSS の核への呼び口・観測）だけ。
- 新旧で 1 か所のまま共有し、写さないもの: rules（`graphloops/rules/`）・指示書（`graphloops/prompts/`）・記録の検証器・役を起こす関数（段 1）。レビューの中身を 2 か所に持つと、同じ直しを 2 回入れる必要が出て、片方を忘れた所が食い違う。
- run の開始時に新旧を選ぶ（例: `loop.py init --runtime next`）。既定は旧のまま。
- 旧を消す条件: 同じ依頼を新旧で回して、同じ形の記録が出て、検証器の判定が一致したら、既定を新に替え、しばらくして旧の engine を消す。
- 長く別のブランチで育てず、main に少しずつ入れて切り替えの旗で隠す。
- 例外: 新しい実行の仕組みが別の言語（TypeScript）や大きな依存を持ち込むなら、利用者が新旧を別々に入れられるよう別のプラグイン（例: `graphloops-next`）に分ける。中身は同じリポジトリの中で参照させる。段 0 で言語と核が決まってから判断する。

### 手順 1: 役を起こす関数（新旧で共有）
- 指示書を組む → `claude -p --agent <役>`（権限の設定を役ごとに明示）→ 返答を置き場に書く → 受け付けの検査 → 拒まれたら `--resume <会話の番号>` で同じ会話に続きを頼む → 実行の要約（時間・往復数・トークン・費用・会話の番号・試行回数）を JSON Lines で残す。
- まず今の engine から使い、運び手を無くす（止まっても気づかない・中継の間違いがここで直る）。後で LangGraph の節からも同じ関数を呼ぶ。
- 判定役などに CLAUDE.md を読ませるか（`--setting-sources`）をここで決める。

### 期限を外した
- 2026-09-25、人の依頼で、節の期限（graph の `deadline_minutes` と、期限の無い節に付いていた 30 分の既定）と、それを過ぎたら役の子を止める動作・`loop.py wait`・期限を条件にした `loop.py relaunch` の資格を外した（run 20260925-115422）。
- なぜ: 期限は「止まっても気づかない」への手当てとして入れた。その元（完了の知らせの迷子）は、engine が子の終了を直接待つ形（役を起こす関数）で解消した。残った期限は実測でない目安の値で、役の子を止める上限を兼ね、判定役・調べ役を打ち切りうる形になっていた。
- 残したもの: 経過時間の表示（`next`・`status` の `elapsed_min`）、起こし直しの回数と理由（`attempt_log`）。起こし直す（`relaunch`）ときは、新しい試行を盤面に書いてから、engine が起こした前の試行の子を木ごと止める（子のグループの番号を置き場の隣の `<out_path>.pgid` に置き、`relaunch` がそれを読んで止める。番号の再利用は印の時刻とプロセスの開始時刻で見分ける。先に止めると、止められた古い launch の締めと版が競って relaunch が落ちた）。任せ先（delegate）は回す側が Agent ツールの前景で起こし、その返りを終了とする。
- 後で検討する: 子が応答しないまま動き続ける場合への備えは、経過時間でなく「進んでいるか」（例: 役の会話の往復や出力が増えているか）で見る形にする。期限を付け直すなら、役を起こす関数が `trace.jsonl` に残す所要時間の実測から節ごとに決める。

### 手順 2: 写させない（新旧で共有）
- 判定の単位などに engine が番号を振り、役は番号で指す。記録と報告では名前に戻す。
- 済み（2026-09-25、今の engine の上で）: 節の `pointers` 宣言（graphloops/engine/pointers.py）。engine が貼る一覧に no を振り、役は番号で指し、done が名前に戻してから rules と記録に渡す。当てたのは他の節の一覧を指す欄（単位・事前審査の穴・修正の応答・答える義務・前の周の削除候補と宣言した穴）。判定者が同じ返答の中で自分の units を指す欄と、外部標準の順位（diff_at）は字面のまま残した——自分の配列の位置の数え違いは黙って別の値に当たり、拒まれないため。

### 手順 3: ブロック分割（今の engine の上で）
- engine にグラフの部品を取り込む仕組みを足す（部品の中の節の名前の衝突を避ける・部品同士の順番を書ける・部品の差し替えを宣言できる）。ループに依らない汎用の仕組みなので engine に置く。

### 開発手法の候補（旧の段 6 の中身）
- TDD 版の修正ブロック: 先に落ちるテスト → 実装、を engine が確かめる（修正前に落ちて修正後に通るテストと、前後とも通るテストで判定する）。

- 仕様駆動（GitHub Spec Kit・AWS Kiro の形）: 新しい仕組みを作る依頼の前に仕様ブロックを置く。受け入れ条件は文章でなく実行できるテスト（Given/When/Then）で持ち、TDD の「先に赤いテスト」と同じ物にする（仕様とテストを 1 つにし、写しを作らない）。
- **検算を並行の線に出す（2026-09-25、人が承認）**: 変異の検算と見逃しへの手直し（4 周目は 173 分 + 167 分、1 周約 8 時間のうち約 5.7 時間）を、次の工程を止める段から外し、テストの線として並行に回す。見逃し 109 本のうち 104 本はテストを足すだけで閉じ、6 本は振る舞いの変わらない変異だった——大半はコードの誤りでなくテストの不足なので、後で見つかっても手戻りは小さい。条件: main に入れる前に、最終のコードで変異の検算をやり直し、見逃しに全部答え（テストを足すか、振る舞いの変わらない変異と宣言する）、テスト一式を緑にする関門を置く。テストの追加では閉じない見逃し（コードの欠陥）は、次の周の判定に人の依頼の入口で流す。ブロックとして「その場で待つ版」と「並行の版」を選べるようにし、速さと手戻りを測って比べる。
- 依頼の種類で流れを選ぶ: 新しい仕組み＝仕様 → 判定 → TDD の修正 → 検算／既存の不具合＝判定 → TDD の修正 → 検算／小さな直し＝直接直す。
- **手法は測って残す。** 足した手法ごとに、効くはずの量を決めてから入れ、周ごとに記録する（前の周の修正が作った指摘の件数・修正差分への変異の見逃しの本数・周の時間・トークン）。ブロックの差し替えで新旧を同じ依頼に当てて比べる。効かなかった手法は外す——足すだけだと 1 周が重くなり続ける。
